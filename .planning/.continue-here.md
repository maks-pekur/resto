## Critical Anti-Patterns

| Pattern                                      | Description                                                                                                                                                                                                                                          | Severity | Prevention                                                                                                             |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------- |
| verification that stops at static gates      | PR #261 made coordinates required and broke 11 call sites across eight e2e suites. Typecheck, lint and unit tests were all green.                                                                                                                    | blocking | When a request/response contract changes, grep every caller in `test/` before calling it done.                         |
| deleting a base branch closes its stacked PR | Merging #261 with `--delete-branch` **closed** #262 instead of retargeting it, and GitHub refuses to reopen a PR whose base is gone. Same again for #264.                                                                                            | advisory | In a stack, retarget the child to `main` _before_ merging the parent — or expect to open a replacement PR.             |
| two branches, one migration number           | #261 and #263 both added `0001_*`. Resolved by renumbering the location one to `0002`, because `0001_two_factor_verified` had already reached `main`.                                                                                                | advisory | Never renumber a migration that has been merged. Check `packages/db/migrations/meta/_journal.json` when branching.     |
| api e2e batched in one process               | Two or more `apps/api` e2e specs in a single vitest process produce failures that vanish when run alone. Hit twice.                                                                                                                                  | advisory | One spec per process.                                                                                                  |
| stale `node_modules` across branches         | `better-auth` differed between branches; checking out without `pnpm install` typechecks new source against old types and invents errors.                                                                                                             | advisory | `pnpm install` after every checkout, and after every merge that touches a lockfile.                                    |
| commitlint rejects merge commits             | `git merge -m "Merge X"` fails the husky `commit-msg` hook.                                                                                                                                                                                          | advisory | Conventional subject: `chore: merge …`.                                                                                |
| `nx run db:test` without env                 | The `packages/db` integration specs need the root `.env`; without it they fail in a way that looks like a defect.                                                                                                                                    | advisory | `set -a; . ./.env; set +a` first.                                                                                      |
| sourcing `.env` skews rate-limit specs       | The opposite trap to the row above. `.env` sets `RATE_LIMIT_AUTH_SIGNIN_PER_MIN=1000` vs a schema default of 10, so `security.e2e`'s rotating-cookie test can never see a 429 and reads as a security regression. Cost an audit cycle on 2026-08-28. | blocking | Rate-limit specs need the schema defaults. Pin the limits explicitly in any CI job — never inherit a developer `.env`. |

## What the audit found

### 1 false positive — the audit method itself, incl. the script this file used to carry

`security.e2e` "a rotating session cookie cannot mint fresh sign-in buckets" fails
ONLY because the runner sources the root `.env`, which sets
`RATE_LIMIT_AUTH_SIGNIN_PER_MIN=1000` (schema default is 10). The test tries 12
sign-ins and expects a 429 by the 10th — unreachable at a ceiling of 1000.
Re-run with the schema defaults: **9 passed (9)**. The limiter is fine.

### 6 specs of rot, and 5 of them are ONE cause

`country` became a required field on tenant provisioning (D-32/D-34: currency and
locale are derived from it, `defaultCurrency` was dropped). Five specs still send
`defaultCurrency: 'USD'` with no `country` and get 400:

    audit-pipeline.e2e            3/3    POST /internal/v1/tenants
    tenancy.e2e                   5/9    (4 payload sites)
    tenancy-offboarding.e2e       7/11
    tenancy-erasure.e2e           4/4
    identity-email-verification   1/2    (cousin: posts to the D-29-closed
                                          /api/auth/sign-up/email, 403; the
                                          replacement /v1/signup also needs country)

Sixth, different cause, same family:

    payment-lifecycle.e2e         1/6    the spec holds THREE disagreeing currencies —
                                         mock tenant GBP (line 35-36), db seed EUR
                                         (line 98-99), orders EUR. The service reads
                                         the mock, so an EUR order meets a GBP tenant
                                         and CurrencyMismatchError fires. Production
                                         is correct; the guard is doing its job.

Fix: give every one of them a consistent country/currency. Mechanical.

### 1 UNRESOLVED — candidate real defect, highest priority

`tenants-controller.e2e` — `DELETE /v1/tenants/me/offboard`, "returns 200 and clears
offboardingScheduledAt for owner" -> **403**.

The owner schedules offboarding (POST, 202, passes) and is refused on the cancel
seconds later with the same cookie. **Reproducible in isolation** (single `-t` run,
fresh tenant/owner/session) so it is not pollution or ordering.

Ruled out already, so do not re-tread: identical `@Permissions` on both routes; the
admin-403 neighbours pass on both; the domain expects cancel to work from
`pending_offboarding`; both offboarding domain errors map to 409 not 403;
`TenantSuspendedError` (the only tenancy 403) is never thrown anywhere;
PermissionsGuard has no status logic; no tenant-status filter in the BA store.

By elimination it is the guard's own `auth.forbidden` — the owner really fails the
`tenant:delete` check the second time. **Mechanism not identified. Do not guess —
use `/gsd-debug`.** If real, a tenant that requests deletion cannot reverse it
through the API, which is what the 30-day cool-off exists for.

## The CI gate needs env pinning (this changes the CI plan)

The blocker was "api:e2e is not in ci.yml". The audit found the reason that is not
a one-line fix: **some specs pass or fail purely on which env is loaded.**
`security.e2e` is red locally (because `.env` raises the rate limits) and would be
green in CI (no `.env`, so schema defaults apply).

So the CI job must pin rate-limit env explicitly rather than inherit whatever a
developer has in `.env`. Otherwise the suite is green in CI and red on every laptop
— which is exactly how a suite stops being trusted and rots again.

Sequence: fix the 6 rotted specs -> `/gsd-debug` the offboard-cancel 403 -> add
api:e2e to ci.yml with pinned env -> then admin:e2e (still brand-era, see todo).
