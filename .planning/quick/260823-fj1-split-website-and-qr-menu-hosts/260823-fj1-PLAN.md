# Give the restaurant website its own host, separate from the QR menu

Founder asked for the landing on the apex, the admin on `admin.<domain>` and the guest menu on a
menu host. Measuring the current state redirected the ask, and the redirection is the substance.

## What is already true

The separation is **already the design**, and two thirds of it already work:

| host                    | surface                                    | state                                  |
| ----------------------- | ------------------------------------------ | -------------------------------------- |
| `admin.<domain>`        | operator sign-in                           | works                                  |
| `<slug>.admin.<domain>` | operator dashboard                         | works                                  |
| `<slug>.menu.<domain>`  | QR menu at the table (`apps/qr-menu`)      | works                                  |
| `<slug>.<domain>`       | the restaurant's own site (`apps/website`) | **reserved but unreachable**           |
| `<domain>`              | the RestOS landing                         | does not exist yet — out of scope here |

`apps/website` is not a landing page. It is the restaurant's public site — menu, about, delivery,
contact, checkout, order confirmation, themed per tenant. It currently runs on
`<slug>.menu.localhost:3002`, squatting the QR-menu host, because that is the only host the menu API
will answer to.

Two places in the codebase already name `<slug>.resto.app` as the website's host — the
`resolveByCustomerHost` docstring and the `AUTH_COOKIE_DOMAIN` docstring. So this task implements a
decision already taken, rather than making a new one.

## Correction to the ask

A single `menu.<domain>` cannot serve the guest menu, because the menu belongs to one restaurant and
one host cannot say which. The restaurant has to be in the hostname: `<slug>.menu.<domain>`. That is
what the API already enforces, and it stays.

## Task 1 — teach the resolver the website host, without widening it by accident

`TenantResolverService.resolveByCustomerHost` accepts only `<slug>.menu.<rest>` today, and
`PublicMenuController` re-checks the request host against it specifically so the menu cannot leak
onto the reserved website host. Both must now accept the website host as well.

The naive rule — "any `<slug>.<anything>`" — is wrong twice over, and both traps are worth writing
down because they are easy to reintroduce:

- **`resto` is in `RESERVED_SLUGS`.** Gating the second label on that set would reject
  `pizza.resto.app`, the very host being added. The reserved set answers "may a tenant be called
  this", not "may this appear in a hostname".
- **An unregistered custom domain would resolve by accident.** `pizzapalace.com` splits into
  `[pizzapalace, com]`, and a tenant whose slug happens to be `pizzapalace` would be served there
  without ever having registered the domain.

So the website branch is gated on the platform's own apex, introduced as `PUBLIC_APEX_DOMAIN`
(`localhost` in dev, `resto.app` in production). Optional: **when it is unset the resolver behaves
exactly as it does today**, so no environment changes behaviour until it opts in.

Resolution order becomes:

1. `findByDomainHost` — verified custom domains. Unchanged, still first.
2. `<slug>.menu.<rest>` — QR menu. Unchanged.
3. `<slug>.<apex>` — the restaurant website, only when `PUBLIC_APEX_DOMAIN` is set and the host ends
   in it.

Rejected in every branch: a reserved slug in the first label (`admin.`, `api.`, `menu.`, `www.`), an
infrastructure label in the second (`<slug>.admin.<domain>`), and the bare apex — which belongs to
the RestOS landing, not to any tenant.

`files`: `tenant-resolver.service.ts`, `env.schema.ts`, and their specs.

## Task 2 — move the dev hosts apart

`.env` / `.env.example` gain `PUBLIC_APEX_DOMAIN=localhost`. The website is then reached at
`pizza.localhost:3002` and the QR menu keeps `pizza.menu.localhost`. Both must be verified against
the running stack, not just asserted.

## Task 3 — stop the login form lying

`login.tsx:68` prints "Invalid email or password." for **any** `res.error` — a network failure, a
rejected origin, a 500. That is what made a missing cookie-domain look like a wrong password and
cost an hour today. Distinguish credential rejection from everything else.

## Task 4 — correct the stale cookie-domain guidance

`env.schema.ts` tells the reader to "leave unset in dev/test so cookies bind to host-only". That
advice predates D-21: the tenant now lives in the hostname, so every successful sign-in hops from
`admin.<domain>` to `<slug>.admin.<domain>`, and a host-only cookie does not survive the hop. Dev
needs `.admin.localhost` for exactly the reason production needs `.admin.resto.app`.

## Verification

`nx run-many -t typecheck lint`, api unit suites, and `packages/db`.

Behavioural, against the running stack — the part that counts:

- `pizza.localhost:3002` serves the restaurant site, and its menu API call resolves the tenant.
- `pizza.menu.localhost` still resolves for the QR menu.
- `admin.localhost:4000`, `pizza.admin.localhost:4000`, `api.localhost`, `www.localhost` and the
  bare apex all resolve to **no** tenant on the guest path — asserted, not assumed.
- Sign in at `admin.localhost:4000` still lands on the dashboard with a live session.
