# Fix the three refund blockers found by the first live Stripe payment

All three were found by moving real test-mode money through `acct_1U7VOwRvgubyWPMy`, not by reading
code. Each is invisible to the stub provider, which is why the suite is green. Fixes are ordered by
how early a user hits them.

Out of scope, deliberately: F-52 (minimum-amount 500) and F-53 (stale "a human must click through
Stripe" docs).

## Task 1 — F-51: stop shipping operator prose into Stripe's closed reason enum

`stripe-provider.adapter.ts:274` does `reason: input.reason as Stripe.RefundCreateParams.Reason`.
Stripe accepts only `duplicate`, `fraudulent`, `requested_by_customer`; this product's reason
vocabulary contains none of them, so every operator-triggered refund 502s.

**Approach.** A pure `toStripeRefundReason(domainReason)` returning
`Stripe.RefundCreateParams.Reason | undefined`:

- the three Stripe values pass through unchanged (existing callers and specs keep working);
- `duplicate_order` maps to `duplicate`;
- everything else returns `undefined` and the field is omitted.

Omitting beats defaulting. `fraudulent` and `duplicate` feed Stripe's risk signals, and
`requested_by_customer` is a factual claim that is false when the kitchen ran out of an ingredient.
The operator's real reason travels in `metadata.resto_reason` instead, so nothing is lost and
nothing is misreported.

The `as` cast is deleted — it is what silenced the only check that would have caught this.

**Regression test.** A fake Stripe client that rejects out-of-enum reasons the way the real API
does, exercised across all seven domain reason codes. A test against a permissive fake would pass
today and prove nothing.

`files`: `apps/api/src/contexts/payments/infrastructure/stripe/stripe-provider.adapter.ts`, plus its
spec.

## Task 2 — F-49: stop parsing a Refund as a Charge

`handle-stripe-event.service.ts:70-72` routes `charge.refunded` and `refund.updated` into one
handler that reads `amount_refunded` / `amount_captured`. A `refund.updated` event carries a Refund,
which has neither, so both read `0` and the handler overwrites a correct full refund with
`status = partially_refunded`, `refunded_amount = 0.00`. Verified consequence: the app-side
double-refund guard is defeated and only Stripe stops the second refund.

**Approach.** Two handlers, each reading its own object shape.

- `handleChargeRefunded` — today's body, unchanged in behaviour, narrowed to the Charge shape. It
  stays the single authority on `payments.status` and `refunded_amount`, because only the Charge
  carries cumulative totals.
- `handleRefundUpdated` — reads the Refund's `id` and `status`, resolves the tenant from
  `event.account`, and calls the repository method that already exists for exactly this,
  `updateRefundStatusByStripeId`. It never touches `payments`.

This is also the semantically right split: `refund.updated` exists to report one refund's own
lifecycle (a refund can fail days later at the bank), which today is silently discarded.

**Regression test.** A `refund.updated` event with a real Refund payload — `object: 'refund'`, an
`amount`, and no `amount_refunded` — asserting `payments.status` and `refunded_amount` are
untouched and the ledger row's status moved. Plus the existing `charge.refunded` path still
computing totals correctly.

`files`: `apps/api/src/contexts/payments/application/handle-stripe-event.service.ts`, plus its spec.

## Task 3 — F-50: let a refunded order reach `refunded`

`order.aggregate.ts:422-442` — `refund()` pushes `OrderRefunded` and sets `updatedAt`, but never
assigns `status`. `markFailed()` twenty lines below does. So `'refunded'` is a declared but
unreachable member of `OrderStatusSchema`, and a fully refunded order shows as paid to both guest
and operator.

**Approach.** On a refund that brings the total to the captured amount, set `status = 'refunded'`
and push `OrderStatusChanged` alongside the existing `OrderRefunded`. Partial refunds leave the
status alone.

`OrderStatusChanged` is not optional here: the guest screen is driven by the
`ordering.order_status_changed.v1` subject
(`nats-guest-notification.subscriber.ts:26`). Setting the field without emitting the event would fix
the database and leave the guest looking at a stale screen — half a fix that reads like a whole one.

**Regression test.** Aggregate unit tests: full refund sets `refunded` and emits both events;
partial refund changes neither status nor emits a status event; a second refund completing the total
still transitions.

`files`: `apps/api/src/contexts/ordering/domain/order.aggregate.ts`, plus its spec.

## Verification

Static, per commit: `nx run-many -t typecheck`, targeted `vitest` for the touched packages, `eslint`
on the touched trees.

Behavioural, and this is the one that counts — the dev stack is up with a working connected account:

1. Guest order on `pizza` above the GBP floor, paid with `pm_card_visa`, reaches `paid`.
2. Refund it with `kitchen_out_of_stock` — the exact input that returns 502 today. Expect 200.
3. After both webhooks land: `payments.status = refunded`, `payments.refunded_amount` equal to the
   captured amount, `orders.status = refunded`, and the guest status endpoint agreeing.
4. Attempt a second partial refund on that order and confirm **our** guard refuses it, rather than
   Stripe.

Step 4 is the real acceptance test. Today it reaches Stripe; if it still does after the fix, F-49 is
not fixed no matter what the unit tests say.
