<objective>
Two operator write paths — `CancelOrderService` and `RefundOrderService` — persist the order status transition by calling `OrderDrizzleRepository.save()`, which is INSERT-only (`ON CONFLICT (tenant_id, idempotency_key) DO NOTHING RETURNING id`, then `if (result.length === 0) return;`). Both are invoked on an order that already exists, so the insert conflicts, the method returns early, and two things are silently lost:

1. `orders.status` is never updated — a canceled or refunded order stays `paid`/`created` forever.
2. The domain events were already drained off the aggregate by `order.pullEvents()` at the top of `save()`, so `ordering.order_canceled.v1` / `ordering.order_refunded.v1` are discarded, not deferred. Nothing downstream ever hears about the cancel or the refund.

`OrderDrizzleRepository.update(order, tx?)` is the correct method and is already verified to do both halves of the job: it UPDATEs `status`/`updatedAt`/`scheduledFor` (throwing if no row matched) **and** appends every drained event to the outbox in the same transaction (`#runUpdate`, lines 127–153). No repository change is needed — only the two call sites are wrong. Reference call sites that already do it right: `create-checkout-payment.service.ts:117` and `handle-stripe-event.service.ts:217`.

This bug reached production because both unit specs mock the repository and assert the in-memory aggregate (`orderRepo.save.mock.calls[0][0].toSnapshot().status`), and the only e2e touching the money path asserts `payments.status`, never `orders.status`. The fix is two lines; **the deliverable is the test that reads the row back from Postgres**, written first (RED) so it demonstrably fails against today's code.

Purpose: unblock Phase 10 (Admin Order Intake), which assumes cancel/refund status persistence is green.
Output: three DB-read-back e2e cases + the two corrected call sites + two unit specs realigned onto `update`.

**Transaction shape (decided, do not re-derive):**
- `RefundOrderService.executeWithOrder` already runs its whole body inside `this.db.withTenant(async (tx) => ...)`. It MUST call `this.orderRepo.update(order, tx)` — passing `tx` keeps the orders UPDATE, the `refunds`/`payments` writes, the `ordering.order_refunded.v1` append and the `payments.order_refunded.v1` append in ONE transaction (CLAUDE.md "Event Publishing Pattern", ADR-0020 I-1/I-4). It also removes today's accidental nested `withTenant` (the current `save()` opens a second transaction from inside the first).
- `CancelOrderService.execute` is NOT inside a transaction. It calls `this.orderRepo.update(order)` with no `tx`; `update()` opens its own `withTenant`, which still binds the status write and the `ordering.order_canceled.v1` append into one commit.

**OUT OF SCOPE — do NOT touch (all belong to Phase 10):**
- Widening `Order.cancel()` to allow cancel after `accepted` (`order.aggregate.ts:307`).
- The `status === 'paid'` guard in `Order.refund()` (`order.aggregate.ts:321`).
- The `wasPaid` predicate / the `currentStatus === 'paid' || 'created'` branch in `cancel-order.service.ts:33,53`.
- Moving the Stripe `createRefund` call outside the DB transaction.
- Any RBAC/permission change, any schema migration, any new column.
- `OrderDrizzleRepository.save()` itself — it is correct for its one legitimate caller (order creation). Change the callers, not the method.

**Current semantics the new tests must encode as-is (not "fix"):** canceling a *paid* order routes through the auto-refund branch, so the aggregate lands on `refunded` (full refund) and `order.cancel()` is skipped. That asymmetry is Phase 10's D-08/D-09 problem. Assert what the code does today; the point of this task is that it now *persists*.
