- **D-04 (Account & currency scoping — REVISES Phase 8 D-05):** **PER-BRAND, immediately.** The payment connection lives on the **BRAND**, not the tenant: each brand has its own connected account, KYC/onboarding status, `paymentProvider`, and **currency**. ## Summary

Phase 08.1 is a **follow-on hardening + UX phase** on top of a shipped Phase 8 money path. The heavy lifting (PaymentIntent direct charges, idempotency keys, webhook raw-body + signature + inbox dedup, partial refunds, disputes, SCA state) already exists and **must be reused, not redesigned**. Three deltas: (1) move the Stripe connection from the **tenant** aggregate to the **brand** aggregate (clean reshape, no backfill); (2) add an **embedded onboarding** UX (Express, via Stripe Account Sessions + `@stripe/react-connect-js` in the admin Vite SPA) plus a **Standard OAuth** "connect existing Stripe" path; (3) generalize `StripeConnectPort` → `PaymentProviderPort` with a `paymentProvider` discriminator, a stub second adapter, and an architecture test — **no runtime registry**.

The codebase is unusually well-positioned for this: `orders.brand_id` **already exists** (composite-FK to `brands`), the `Order` aggregate snapshot **already exposes `brandId` and `currency`**, the `payments` table **already has a `provider` column** (default `'stripe'`), `brands` **already has a `stripe_account_id` column** (currently unused — Phase 8 wrote to `tenants` instead), and `env.schema.ts` **already declares `STRIPE_CONNECT_CLIENT_ID`** (for OAuth). The reshape is therefore mostly: relocate the four `stripe_*` capability columns + currency semantics from `tenants` to `brands`, repoint the webhook tenant-resolution (`findByStripeAccountId`) and checkout account-resolution to the brand, and add `payment_provider` + `account_type` columns to `brands`.

**Critical external finding (HIGH-impact, plan-shaping):** Stripe has **deprecated the `type: 'express'` / `type: 'standard'` account-type model for new integrations** in favor of **controller properties**, and explicitly says _"Express connected accounts are deprecated, so don't use them for new integrations."_ However, **type-based accounts remain fully supported and backwards-compatible**, and **embedded components work with both type-based and controller-based accounts.** Phase 8 already ships `accounts.create({ type: 'express' })`. The locked money model (direct charges, connected account bears fees + disputes) is preserved by the existing `type: 'express'` behavior — switching to controller properties would change the `fees.payer`/`losses.payments` allocation and **must NOT be done casually**. Recommendation: **keep `type: 'express'` and add OAuth-based `type: 'standard'` connection**; treat the controller-property migration as out of scope (note it for a future phase). This keeps the money model identical and avoids touching the working charge path.

**Primary recommendation:** Reshape Stripe connection columns onto `brands`, reuse the existing `StripeConnectAdapter` resilience wrapper behind a renamed `PaymentProviderPort`, add `accountSessions.create` (embedded) + OAuth token-exchange to the adapter, install `@stripe/connect-js` + `@stripe/react-connect-js` in the admin SPA, keep `type: 'express'` and webhook route Stripe-specific, and prove the seam with a stub adapter + an ESLint `no-restricted-imports` architecture test forbidding `stripe` imports in the payments application/domain layers.

### Pattern 1: Embedded onboarding — server mints Account Session, browser renders component

**What:** The API creates a Stripe Account Session for the brand's connected account with the `account_onboarding` component enabled and returns its `client_secret`; the admin SPA initializes Connect.js with that secret and renders `ConnectAccountOnboarding`.

**When to use:** Express onboarding only (D-02). Standard uses OAuth.

**Server (account session endpoint):**

```ts
// Source: https://docs.stripe.com/connect/get-started-connect-embedded-components (Ruby example transposed to stripe-node)
// POST /v1/tenancy/brands/:slug/onboarding/account-session  (Permissions: tenant transfer; RequireActiveTenant)
const accountSession = await stripe.accountSessions.create({
  account: brand.stripeAccountId, // ensure the express account first (accounts.create type: 'express')
  components: {
    account_onboarding: { enabled: true },
  },
});
return { clientSecret: accountSession.client_secret };
```

**Client (admin Vite SPA):**

```tsx
// Source: https://github.com/stripe/react-connect-js (README, verbatim shape)
import { loadConnectAndInitialize } from '@stripe/connect-js';
import {
  ConnectComponentsProvider,
  ConnectAccountOnboarding,
} from '@stripe/react-connect-js';

const fetchClientSecret = async () => {
  const res = await apiFetch<{ clientSecret: string }>(
    `/v1/tenancy/brands/${brandSlug}/onboarding/account-session`,
    { method: 'POST' },
  );
  if (!res.ok || res.data === null) throw new Error('account-session failed');
  return res.data.clientSecret;
};

const connectInstance = loadConnectAndInitialize({
  publishableKey: import.meta.env.VITE_STRIPE_PUBLISHABLE_KEY, // VITE_* — fail loud if missing (apps/CLAUDE.md)
  fetchClientSecret,
});

<ConnectComponentsProvider connectInstance={connectInstance}>
  <ConnectAccountOnboarding onExit={() => refetchBrandPaymentStatus()} />
</ConnectComponentsProvider>;
```

> `onExit` fires when the operator leaves the embedded flow — use it to refetch per-brand status. **Completion is authoritative only via the `account.updated` webhook** (`charges_enabled`/`details_submitted`), exactly as Phase 8 already handles — `onExit` is a UX trigger, not a source of truth.

### Pattern 2: Standard OAuth ("connect existing Stripe")

**What:** Redirect the operator to Stripe's OAuth authorize URL; Stripe redirects back with a `code`; the API exchanges it for `stripe_user_id` (the connected account id) and links it to the brand with `accountType='standard'`.

**Server:**

```ts
// Source: https://docs.stripe.com/connect/oauth-reference (verbatim URL + params)
// 1) GET /v1/tenancy/brands/:slug/onboarding/oauth/start  → 302 to:
//    https://connect.stripe.com/oauth/authorize?response_type=code
//      &client_id=${STRIPE_CONNECT_CLIENT_ID}&scope=read_write
//      &redirect_uri=${callback}&state=${signed(brandId)}
// 2) GET /v1/tenancy/brands/:slug/onboarding/oauth/callback?code&state
const tokenResp = await stripe.oauth.token({
  grant_type: 'authorization_code',
  code,
});
const connectedAccountId = tokenResp.stripe_user_id; // the connected account id
// link to BRAND: accountId=connectedAccountId, accountType='standard', provider='stripe'
// then retrieveAccount() to seed charges_enabled / payouts_enabled, or wait for account.updated
```

> `access_token` and `stripe_publishable_key` in the OAuth response are **deprecated** — do NOT store them; use the platform secret key + `stripeAccount` request option (the existing direct-charge pattern). `state` MUST be CSRF-validated and carry the `brandId` so the callback links to the right brand. `STRIPE_CONNECT_CLIENT_ID` is already declared in `env.schema.ts`.

### Pattern 3: Provider-agnostic port (minimum, D-03)

**What:** Rename `StripeConnectPort` → `PaymentProviderPort`, move it into the **payments** context domain (the consumers live there), keep method names provider-neutral, add `verifyWebhookSignature`, and key the existing Symbol-token DI on `PAYMENT_PROVIDER_PORT`.

**Example interface (planner refines exact signatures — Claude's discretion):**

```ts
// payments/domain/ports.ts
export type PaymentProvider = 'stripe'; // discriminator; only real value for now (Zod enum)
export type AccountType = 'express' | 'standard';

export interface PaymentProviderPort {
  // account onboarding
  ensureOnboardingAccount(i: {
    brandId: string;
    displayName: string;
    defaultCurrency?: string;
    accountType: AccountType;
  }): Promise<{ accountId: string }>;
  createOnboardingLink(i: {
    accountId: string;
    returnUrl: string;
    refreshUrl: string;
  }): Promise<{ url: string; expiresAt: number }>; // hosted fallback (Express)
  createOnboardingSession(i: {
    accountId: string;
  }): Promise<{ clientSecret: string }>; // embedded (Express)
  exchangeOAuthCode(i: { code: string }): Promise<{ accountId: string }>; // Standard OAuth
  retrieveAccount(i: {
    accountId: string;
  }): Promise<{
    chargesEnabled: boolean;
    payoutsEnabled: boolean;
    requirementsDue: unknown;
  }>;
  // payment + refund (unchanged shapes, reuse Phase 8 wrapper)
  createPaymentIntent(
    i: CreatePaymentIntentInput,
  ): Promise<CreatePaymentIntentResult>;
  cancelPaymentIntent(
    i: CancelPaymentIntentInput,
  ): Promise<CancelPaymentIntentResult>;
  createRefund(i: CreateRefundInput): Promise<CreateRefundResult>;
  // webhook (D-08): verification in the port, route stays Stripe-specific
  verifyWebhookSignature(i: {
    rawBody: Buffer;
    signature: string;
  }): WebhookEvent; // returns a provider-neutral parsed event (or the Stripe.Event for now)
}
export const PAYMENT_PROVIDER_PORT = Symbol('PAYMENT_PROVIDER_PORT');
```

> Keep it MINIMUM (D-03): no factory/registry, no `getProvider(name)`. The module wires exactly one real adapter (`StripeProviderAdapter`). `connectedAccountId` stays the parameter name where it already is — it is provider-neutral enough.

### Pattern 4: Stub adapter + architecture test (D-03)

**What:** A `StubProviderAdapter implements PaymentProviderPort` that returns canned values (never wired in prod) proves the port is implementable by a non-Stripe provider. The **architecture test** asserts the payments **application + domain** layers depend only on the port, never on `stripe`.

**Mechanism (reuse existing infra):** the repo already uses ESLint `no-restricted-imports` for ADR boundaries (`apps/api/eslint.config.mjs`). Add a scoped rule:

```js
// apps/api/eslint.config.mjs — new override block
{
  files: ['src/contexts/payments/application/**/*.ts', 'src/contexts/payments/domain/**/*.ts'],
  rules: {
    'no-restricted-imports': ['error', { paths: [
      { name: 'stripe', message: 'PAY-16: payments app/domain must depend on PaymentProviderPort, not the Stripe SDK. Stripe stays in infrastructure/stripe/.' },
    ], patterns: ['**/infrastructure/stripe/**'] }],
  },
},
```

Plus a Vitest assertion that imports each application service module and the stub adapter, and verifies the stub satisfies `PaymentProviderPort` (type-level) — a compile-time `satisfies` check is the cheapest "architecture test" and runs in CI via `tsc`. ESLint enforces the no-import direction; the stub + `satisfies PaymentProviderPort` proves substitutability.

### Anti-Patterns to Avoid

- **Switching `type: 'express'` → controller properties as part of this phase.** It changes `fees.payer`/`losses.payments` and risks altering the locked money model. Out of scope.
- **Treating `onExit` as onboarding completion.** Completion is the `account.updated` webhook (`charges_enabled` + `details_submitted`). `onExit` only triggers a status refetch.
- **Storing the OAuth `access_token`.** Deprecated; use the platform key + `stripeAccount` option (existing pattern).
- **Building a provider registry / `getProvider(name)`.** D-03 says minimum: one real adapter + one stub. YAGNI.

## Common Pitfalls

### Pitfall 1: Stripe deprecated `type: 'express'` for new integrations — but switching is a money-model trap

**What goes wrong:** A reader sees "Express is deprecated, use controller properties" and migrates `accounts.create({ type: 'express' })` to a controller config. The controller mapping for Express is `controller.fees.payer=application`, `controller.losses.payments=application` — choosing different values silently changes who pays Stripe fees and who bears disputes, breaking the locked money model (Phase 8 D-02).
**Why it happens:** Stripe's docs push controller properties; the deprecation note reads as urgent. It is not — type-based accounts are fully supported and embedded components work with them.
**How to avoid:** **Keep `type: 'express'`** for new express accounts. Do NOT introduce controller properties this phase. The money model (direct charges, connected account bears fees + disputes, `application_fee=0` default) is preserved by the existing code unchanged.
**Warning signs:** Any diff to `accounts.create` params beyond `default_currency`/`business_profile`; any appearance of `controller` in the adapter.

### Pitfall 2: Embedded `accountSessions.create` requires a sufficiently recent API version

**What goes wrong:** The adapter pins `apiVersion: '2025-02-24.acacia'`. `accountSessions.create` with `components.account_onboarding` has evolved; an older pinned version can reject the component shape or omit fields.
**Why it happens:** The installed SDK is `17.7.0` while latest is `22.3.0`; the pinned API version may predate some component options.
**How to avoid:** Verify `accountSessions.create({ components: { account_onboarding: { enabled: true } } })` is accepted on `2025-02-24.acacia` (it is — Account Sessions GA'd in 2024). Only bump the SDK/API version if a specific component option (`features`, `collection_options`) is missing. Test against the live Stripe test mode in a `checkpoint:human` smoke.
**Warning signs:** Stripe API errors mentioning unknown `components` keys or `account_onboarding`.

### Pitfall 3: `onExit` mistaken for onboarding completion

**What goes wrong:** The SPA flips the UI to "Payments active" on `onExit`, but KYC may be incomplete (operator exited early) or Stripe still has `currently_due` requirements.
**Why it happens:** `onExit` is the only client-side signal and looks like "done".
**How to avoid:** Treat `account.updated` webhook (`charges_enabled && details_submitted`) as the **only** completion authority — Phase 8's `handleAccountUpdated` already computes this. `onExit` triggers a status **refetch**, nothing more. The per-brand `canAcceptPayments()` predicate (D-07) gates checkout regardless of UI.
**Warning signs:** UI shows "active" but checkout throws `PaymentsNotEnabledError`.

### Pitfall 4: Per-brand reshape must repoint the webhook tenant-resolution AND checkout account-resolution

**What goes wrong:** `handle-stripe-event.service.ts` resolves the tenant via `tenantRepo.findByStripeAccountId(accountId)` for `account.updated` / `charge.refunded` / `charge.dispute.created`. `create-checkout-payment.service.ts` reads `tenant.stripeAccountId` and `tenant.defaultCurrency`. If only the schema moves but these call sites don't, capabilities update the wrong record and checkout reads stale/empty account ids.
**Why it happens:** The Stripe linkage is referenced in 3+ places keyed on the tenant.
**How to avoid:** Add `brandRepo.findByStripeAccountId(accountId)` (currently only `tenant` has it); repoint webhook handlers to update the **brand** capabilities; change checkout to load the brand from `order.brandId` (the `Order` snapshot already exposes `brandId` and `currency` — no new join) and resolve `brand.stripeAccountId` + `brand.currency`. The `PaymentsNotEnabledError`/`canAcceptPayments` predicate moves to the brand aggregate.
**Warning signs:** `account.updated` arrives but the brand stays `pending`; checkout currency mismatch against `brand.currency`.

### Pitfall 5: New brand payment columns must respect RLS + composite-FK invariants

**What goes wrong:** Adding payment columns to `brands` is column-only (brands already has RLS via `0013_brands_rls.sql` and `UNIQUE (id, tenant_id)` via `tenantParentUniqueIndex`), so no new policy is needed for columns on `brands`. But if any **new child table** is introduced (e.g., a separate `brand_payment_accounts`), it MUST carry `tenant_id NOT NULL` + composite FK `(brand_id, tenant_id) → brands(id, tenant_id)` + RLS enable/force (ADR-0020 I-2; packages/db CLAUDE.md).
**Why it happens:** Easy to forget the composite FK / RLS on a brand-new table.
**How to avoid:** Prefer **columns on `brands`** (simplest, no new RLS, matches D-05's flat model). If a child table is unavoidable, follow the `brand_domains` pattern exactly (`compositeTenantFk` + `tenantIdColumn` + RLS policy migration). Migration is a hand-tuned file via `pnpm db:generate` + journal entry (next idx 57, tag `0057_*`).
**Warning signs:** `pnpm db:audit-fks` (planned) or `tenant-isolation.spec.ts` flags a missing composite FK; cross-tenant phantom rows.

### Pitfall 6: `application_fee` on a Standard account works — but the operator owns disputes/support differently

**What goes wrong:** Assuming Standard behaves identically to Express in every dimension. Money-wise it does (direct charge + `application_fee_amount` is supported on Standard), but **Standard connected accounts have full Dashboard access and (for direct charges) the connected account handles disputes**, while Express uses the Express Dashboard and the platform is the default dispute manager.
**Why it happens:** The money model is identical, masking the operational differences.
**How to avoid:** Store `accountType` on the brand (D-05) and branch UI/operational copy on it (Standard: "manage in your own Stripe Dashboard"; Express: "managed here"). The charge-creation code path is identical — `createPaymentIntent` with `stripeAccount` + `application_fee_amount` works for both. Do NOT add per-type charge logic.
**Warning signs:** Operator confusion about where to handle a dispute; UI offering Express-dashboard actions to a Standard account.

## Project Constraints (from CLAUDE.md)

- **RLS double-enforcement:** every tenant-scoped query goes through `ScopedTx` AND Postgres RLS (ADR-0020 I-1). New brand payment columns inherit `brands` RLS (`0013_brands_rls.sql`); any new child table needs its own RLS enable/force + repo-layer `eq(table.tenantId, ...)`.
- **Composite FK on tenant-scoped child tables (ADR-0020 I-2):** any new child table MUST declare `(brand_id, tenant_id) → brands(id, tenant_id)` via `compositeTenantFk`; `brands` already exposes `UNIQUE(id, tenant_id)`.
- **Hard deletes forbidden:** `resto_app` has no DELETE privilege; status-as-soft-delete. The tenant-column DROP (D-06) is a schema migration (DDL), run under the admin role — not an app-level delete.
- **No raw SQL outside `packages/db`:** all new queries via Drizzle + `ScopedTx`; migrations are files via `pnpm db:generate` (NOT `drizzle-kit push`), with a `_journal.json` entry (next idx 57, tag `0057_*`).
- **DDD layering:** domain (pure, zod-only) → application (ports via Symbol token) → infrastructure (adapters) → interfaces (controllers). The `PaymentProviderPort` lives in payments domain; the Stripe adapter in `infrastructure/stripe/`.
- **Symbol-token DI:** `PAYMENT_PROVIDER_PORT` replaces `STRIPE_CONNECT_PORT`; application services depend on the interface only.
- **Zod as source of truth:** `paymentProvider`/`accountType` are Zod enums; types via `z.infer`. HTTP-boundary DTOs via `nestjs-zod` `createZodDto` (match `stripe-onboarding.controller.ts`).
- **Web-layer rules (apps/CLAUDE.md):** server-side `fetch` needs `AbortSignal.timeout`; `VITE_*` env vars must fail loud with no prod fallback; admin SPA error UI needs a "Try again" affordance; no source maps to prod (`'hidden'`).
