# Phase 08.1: Payments — Provider Layer & Onboarding UX - Context

<domain>
## Phase Boundary

Extend the Phase 8 Stripe Connect money path with a provider-agnostic abstraction and a
better tenant onboarding UX. Three deliverables:

1. **Embedded Connect onboarding** (PAY-14) — Express KYC via Stripe embedded components
   inside the admin Vite SPA, no off-domain redirect; pending-KYC gate preserved.
2. **Connect Standard OAuth** (PAY-15, PAY-17) — a second onboarding path ("I already have
   Stripe", one-click OAuth) alongside Express; operator picks the method.
3. **Provider-agnostic port** (PAY-16) — generalize `StripeConnectPort` → `PaymentProviderPort`
   so Mollie/Adyen/local acquirers (PAYMP-01/02/03) slot in via adapter + config only.

Covers PAY-14, PAY-15, PAY-16, PAY-17.

**Not in scope (deferred — see `<deferred>`):** the RestOS monetization model (commission vs
flat subscription — FIN-07, Phase 14); a full runtime multi-provider registry + provider-aware
webhook routing (lands with PAYMP); Custom (fully white-labeled) Connect accounts;
multi-currency _within_ a brand. The money model from Phase 8 (direct charges, `application_fee`
= config default 0) is unchanged.
</domain>

<decisions>
## Implementation Decisions

### Onboarding methods (PAY-15 / PAY-17)

- **D-01:** Offer **both** onboarding paths. **Express ("Create new") is the default/primary
  CTA**; **Connect Standard OAuth ("I already have Stripe") is the secondary option**. Rationale:
  most restaurants have no Stripe account → Express is the low-friction default; Standard serves
  tenants who already run Stripe (they keep their own dashboard + support). The admin exposes a
  resumable method choice (PAY-17).

### Embedded onboarding (PAY-14)

- **D-02:** **Embedded-primary + hosted fallback.** The Express path uses Stripe **embedded
  Connect components** (Connect.js) rendered inside the admin **Vite SPA** as the primary UX —
  no off-domain redirect. The hosted `account_link` is **retained as a fallback** (resume,
  component errors, regions/requirements the embedded component does not cover). Embedded applies
  to **Express only** — Standard uses OAuth, not embedded onboarding. The Phase 8 pending-KYC
  capability gate (PAY-13 / Phase 8 D-12) is preserved.

### Provider abstraction depth (PAY-16)

- **D-03:** **Minimum viable abstraction.** Generalize `StripeConnectPort` →
  provider-agnostic **`PaymentProviderPort`** (account onboarding, payment intent, refund,
  `verifyWebhookSignature`), add a **`paymentProvider` discriminator**, and **prove the seam with
  a stub second-provider adapter + an architecture test** (matches ROADMAP SC#3). **No runtime
  provider registry / config-driven provider selection yet** — only Stripe is real; Mollie/Adyen
  (PAYMP-01/02) come later. Explicitly avoids YAGNI.

### Account & currency scoping — REVISES Phase 8 D-05

- **D-04:** **Per-brand, immediately.** The payment connection lives on the **brand**, not the
  tenant: each brand has its own connected account, KYC/onboarding status, `paymentProvider`, and
  **currency**. This **revises Phase 8 D-05** ("one currency per tenant") — currency is now
  **per-brand**, fixed at the brand's onboarding. For a single-brand first customer, per-brand and
  per-tenant coincide.
- **D-05:** **Payment-connection model on the brand:**
  `{ provider, accountType (express | standard), accountId, onboardingStatus, currency,
chargesEnabled, payoutsEnabled, requirementsDue }`. `accountType` drives the onboarding flow:
  Express → embedded / `account_link`; Standard → OAuth connect.

### Migration

- **D-06:** **Clean reshape, no backfill.** Phase 8 linked Stripe to the **tenant** aggregate;
  move the connection columns to **brand** level and **drop** the tenant-level linkage. No data
  backfill — there are no live connected accounts (prod stand-up deferred to first customer). Do
  **not** keep tenant-level as a compatibility default.

### Capability + checkout (consequence of D-04, locked)

- **D-07:** The server-side "can this brand accept money?" predicate (Phase 8 D-12) and the
  checkout PaymentIntent account resolution now key on the **order's brand**, not the tenant. The
  UI gate alone stays insufficient — the per-brand capability check is enforced **at checkout**.

### Webhook generalization

- **D-08:** `verifyWebhookSignature` is part of `PaymentProviderPort`, but the **HTTP webhook
  route stays Stripe-specific** until a second provider lands; provider-aware routing
  (e.g. `/webhook/:provider`) is deferred to PAYMP. The stub adapter proves the port contract,
  not the HTTP wiring.

### Claude's Discretion (planner/researcher decide)

- Exact `PaymentProviderPort` method signatures; shape of the Express embedded `account_session`
  (client_secret) endpoint; Connect.js React integration in the Vite SPA (`@stripe/connect-js` +
  `@stripe/react-connect-js`); migration mechanics (column moves, composite-FK `(brand_id,
  tenant_id)` adjustments per ADR-0020 I-2, RLS); how the `accountType`-specific onboarding branch
  is structured in the admin UI; stub-adapter shape + architecture-test mechanism; whether
  `paymentProvider` / `accountType` are enum columns or small lookups; Standard OAuth Connect app
  registration + config (client id/secret, redirect).
  </decisions>

## Existing Code Insights

### Reusable Assets

- **`StripeConnectAdapter`** (`stripe-connect.adapter.ts`) — `withRetry` / `withTimeout` / idempotency-key wrapper around accounts / accountLinks / paymentIntents / refunds. Generalize behind `PaymentProviderPort`; keep the resilience wrapper.
- **Phase 8 onboarding service + KYC capability predicate** (D-12) — extend to per-brand; `account.updated` handling (chargesEnabled / payoutsEnabled / requirementsDue) reused per brand.
- **Inbox dedup + outbox** (`@resto/events`) — webhook idempotency on Stripe event id; unchanged.

### Established Patterns

- Domain ports keyed by **Symbol token**, adapters wired at module composition (`STRIPE_CONNECT_PORT` → `PAYMENT_PROVIDER_PORT`).
- **Composite FK** on every tenant-scoped child table (ADR-0020 I-2) — brand-level payment columns + any new rows must respect `(brand_id, tenant_id)` FKs and RLS + ScopedTx.
- Status-as-soft-delete; no hard deletes.

### Integration Points

- **Brand record ↔ payment connection** (new home for accountId/status/provider/currency).
- Checkout (payments ctx) resolves the **brand** connected account (D-07).
- Webhook ↔ inbox dedup; `verifyWebhookSignature` via the port (D-08).
- Admin **Vite SPA** ↔ embedded Connect components + onboarding/account-session endpoints + method choice.

<specifics>
## Specific Ideas (locked direction for the planner)

- **Express = embedded** (Connect.js in admin) **+ hosted `account_link` fallback**;
  **Standard = OAuth one-click**; **Express is the default CTA** (D-01/D-02).
- **Provider seam = minimum:** `PaymentProviderPort` + `paymentProvider` discriminator + **stub
  adapter + architecture test**; **no runtime registry** (D-03).
- **Per-brand** connected account **and** per-brand currency (revises Phase 8 D-05); **clean
  schema reshape** off the tenant, **no backfill** (D-04/D-06).
- **`accountType` (express | standard) stored per brand**, drives the onboarding branch (D-05).
- **`verifyWebhookSignature` in the port; HTTP route stays Stripe-only** until provider #2 (D-08).
- Money model unchanged from Phase 8: **direct charges, `application_fee` = config default 0**.
  </specifics>
