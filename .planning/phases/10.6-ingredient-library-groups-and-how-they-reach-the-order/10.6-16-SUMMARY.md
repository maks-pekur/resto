tests fail identically: `seedOrder`'s fixture always inserts `status: 'paid'`, which stopped being
a legal `orders.status` value once migration `0010_order_payment_status.sql` split the column into
a fulfilment-stage `status` and an independent `payment_status` — every insert now hits
`orders_status_chk` (SQLSTATE 23514).

Verified this predates 10.6 by inspecting the tree at the true phase-10.6 branch point
(`3ec7a96950643c99efe1193db2a475f7893e90e4`, before any 10.6 commit):
- `git show 3ec7a969...:apps/api/test/e2e/order-lifecycle.e2e.spec.ts` already contains the
  identical `status: 'paid'` literal at all 11 `seedOrder(...)` call sites.
- `git show 3ec7a969...:packages/db/migrations/0010_order_payment_status.sql` already exists with
  the same restrictive `orders_status_chk`.
- `git log -- apps/api/test/e2e/order-lifecycle.e2e.spec.ts` shows the only post-BASE commit
  touching the file is `1a88a409` (an unrelated `fulfillmentMode` → `orderType` rename); no
  10.6-prefixed commit ever touched it.

A full worktree re-run at the phase-start commit was attempted for extra confirmation but hit an
unrelated testcontainers/role-provisioning error (`role "resto_app" does not exist`) before
reaching this assertion — abandoned in favor of the byte-for-byte source comparison above, which is
conclusive on its own (identical fixture code + identical constraint = identical outcome).
Logged to `deferred-items.md` ("Plan 16 — order-lifecycle.e2e.spec.ts's seedOrder fixture inserts
an invalid status, unrelated to ingredients"); not fixed, per Task 2's own scope-boundary rule
