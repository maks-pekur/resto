## Deviations from Plan

### Auto-fixed Issues

**1. [Bug — fixed per explicit task instructions] `menu_modifier_options_id_tenant_uq` missing, migration 0019 failed to apply**
- **Found during:** Task 2, reproducing the orchestrator-captured error before touching anything
- **Issue:** `menu_modifier_group_options_option_fk`, `menu_item_modifier_options_option_fk` and `menu_option_stop_list_option_fk` all reference `menu_modifier_options(id, tenant_id)`, but `menu_modifier_options` — an existing table since `0000_baseline.sql` — never had a `(id, tenant_id)` unique index, because nothing referenced it as a composite-FK parent before this migration. Every other composite-FK parent in the codebase (`locations`, `menu_items`, `menu_modifier_groups`, etc.) has one; this table was the first pre-existing table to become a first-time parent under ADR-0020 I-2.
- **Fix:** Added `CREATE UNIQUE INDEX menu_modifier_options_id_tenant_uq ON public.menu_modifier_options (id, tenant_id);` immediately before the first referencing FK, and corrected the section's comment to explain the general case (existing table becoming a first-time composite-FK parent), not just the three brand-new tables.
- **Files modified:** `packages/db/migrations/0019_ingredient_library.sql`
- **Verification:** `pnpm -C packages/db exec pnpm db:migrate` applies cleanly and is a no-op on a second run; full psql verification below.
- **Committed in:** `65c016ce`

**2. [Rule 3 - Blocking] Guarded four pre-existing unconditional `GRANT ... TO resto_app` statements that broke every fresh-Postgres bootstrap in the packages/db integration suite**
- **Found during:** Task 3, first attempt to run the three required specs via `pnpm -C packages/db exec vitest run ...` — `startPostgres()` (test/setup.ts) failed with `role "resto_app" does not exist` while applying migration `0006_delete_empty_location.sql`
- **Root cause:** `test/setup.ts`'s `startPostgres()` runs `migrate()` against a brand-new testcontainer BEFORE calling `provisionAppRole()` (this ordering is correct and intentional — migrations use a guarded `DO $$ IF EXISTS (SELECT 1 FROM pg_roles ...) THEN GRANT ... END IF; END $$;` pattern specifically so they no-op when the role doesn't exist yet, and `provisionAppRole()`'s `roles.sql` re-grants access to every table that exists by the time it runs). Migrations `0006_delete_empty_location.sql`, `0011_table_qr_sessions.sql`, `0015_order_feedback.sql` and `0017_service_requests.sql` never used this guard — their `GRANT ... TO resto_app` statements are unconditional, so on a truly fresh bootstrap (any testcontainer run, or any from-scratch empty database) `migrate()` aborts partway through with a Postgres error, and NO integration test in the package can start. Confirmed this is 100% pre-existing and unrelated to phase 10.6 by running an untouched spec (`erase-includes-table-zones.spec.ts`) and observing the identical failure before any fix.
- **Fix:** Wrapped each unconditional `GRANT` in the same `DO $$ IF EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'resto_app') THEN ... END IF; END $$;` guard already used by `0003_table_zones_and_tables.sql` and this plan's own `0019_ingredient_library.sql`.
- **Safety for the already-migrated live dev database:** verified directly in `drizzle-orm@0.45.2`'s `pg-core/dialect.js` `PgDialect.migrate()` — migration re-application is gated purely on comparing each migration's journal `when` timestamp (`folderMillis`) against the last applied migration's `created_at`; the stored `hash` column is written but never read back for a skip/re-run decision. Editing the SQL text of an already-applied migration is therefore a complete no-op against any database that has already advanced past it (including the live dev database used in Task 2, which applied 0006/0011/0015/0017 long before this session).
- **Files modified:** `packages/db/migrations/0006_delete_empty_location.sql`, `0011_table_qr_sessions.sql`, `0015_order_feedback.sql`, `0017_service_requests.sql`
- **Verification:** `pnpm -C packages/db exec vitest run test/integration/erase-includes-table-zones.spec.ts` (untouched file, used only as a probe) progressed past the role-creation step after the fix, confirming the fresh-bootstrap path now works; full db test suite run afterward (201 passed / 3 skipped / 2 pre-existing unrelated failures, see below).
- **Committed in:** `5aeb17fe`

**3. [Rule 1 - Bug] Stale `status: 'created'` literal in tenant-isolation.spec.ts's pre-existing ORD-06 fixture**
- **Found during:** Task 3, second obstacle after the role-guard fix — `tenant-isolation.spec.ts`'s own `ORD-06: cross-tenant matrix for orders / order_items` describe block (not touched by this plan otherwise) failed with `orders_status_chk` violation
- **Issue:** `orders.status`'s CHECK constraint (`orders_status_chk`, `packages/db/src/schema/ordering.ts:99`) only allows `'placed', 'accepted', 'preparing', 'ready', 'completed', 'canceled'`. The pre-existing ORD-06 fixture (two `orders` inserts) still used the old value `'created'`, which no longer validates.
- **Fix:** Changed both occurrences to `'placed'`, matching the schema's own CHECK constraint and every other passing fixture in the file.
- **Scope justification:** `tenant-isolation.spec.ts` is one of this task's three explicitly owned files (`files_modified` in the plan frontmatter), and the plan's own acceptance criterion requires "All three named specs pass in one `pnpm -C packages/db exec vitest run` invocation" — a single failing test anywhere in the file fails that literal command. The identical bug exists in `erase-includes-table-zones.spec.ts` and `erase-includes-ordering.spec.ts` (neither owned by this plan); those were left untouched and are logged below instead, per the scope boundary rule for unrelated files.
- **Files modified:** `packages/db/test/integration/tenant-isolation.spec.ts`
- **Verification:** `pnpm -C packages/db exec vitest run test/integration/tenant-isolation.spec.ts test/integration/composite-tenant-fk.spec.ts test/integration/erase-includes-ingredients.spec.ts` → 3 files, 61/61 tests passed, 0 failed.
- **Committed in:** `5aeb17fe`
