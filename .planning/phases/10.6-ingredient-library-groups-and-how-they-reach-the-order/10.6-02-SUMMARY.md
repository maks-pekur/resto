## Decisions Made

- **Composite FK count:** the plan's Task 1 action text says "the five composite FKs named exactly as plan 01 named them," but plan 01's own schema.ts (verified directly, not trusted from either plan's prose) defines six: `menu_modifier_group_options_group_fk`, `menu_modifier_group_options_option_fk`, `menu_item_modifier_options_item_fk`, `menu_item_modifier_options_option_fk`, `menu_option_stop_list_option_fk`, `menu_option_stop_list_location_fk`. This mirrors the exact defect the orchestrator flagged in plan 01 task 2's own acceptance criterion ("exactly 5" vs. 6 named in the action text). Implemented all six, matching ADR-0020 I-2 (composite FK on every tenant-scoped parent link) and the actual schema.ts. This plan's own acceptance criteria never asserted a specific count, so no criterion conflict.
- **GDPR erasure scope held to plan boundaries:** while reproducing `tenancy_erase_tenant`, checked migrations 0004-0018 for tenant-scoped tables absent from the function per the plan's explicit instruction. Found three: `table_sessions` (0011), `order_feedback` (0015), `service_requests` (0017) — none are deleted by `tenancy_erase_tenant` today. Per the plan's explicit instruction ("record it in the SUMMARY as an out-of-scope finding — do NOT silently add it, that changes erasure semantics outside this phase"), these were left untouched. **This is a real GDPR-erasure gap that predates this phase** and should be raised as a follow-up (own ticket/quick-task), not folded into this migration.
- **RESTO_SPINE_MIGRATION=1 used for the Task 1 commit.** The husky pre-commit hook runs `nx affected -t typecheck --uncommitted`, which pulled in `apps/api:typecheck` as affected (via the `packages/db` dependency graph edge) even though Task 1 touched zero TypeScript files. `apps/api/src/contexts/catalog/infrastructure/catalog-drizzle.repository.ts` still references the pre-reshape schema shape (`modifierGroupId`, `minSelectable`, `maxSelectable`, `ingredients`) that plan 01 already removed from `packages/db/src/schema/menu.ts` — 20 type errors, all pre-existing (present at the worktree's base commit before this plan touched anything; confirmed by the fact that Task 1's diff contains no `.ts` files). This is exactly the scenario the hook's own comment documents the escape hatch for ("a rename that crosses packages/domain or packages/db and cannot leave the repo type-green until every call site is fixed... the phase that sets it owes a green gate before it closes"). Plan 02's own `<verification>` section requires only `pnpm exec nx run db:typecheck`, not `api:typecheck`, confirming this plan is deliberately scoped DB-only. **A later plan in phase 10.6 owes the `apps/api` catalog repository rewrite** (moving from a direct `modifierGroupId` FK join to the new link-table join, `display`/`behaviour` instead of `min/maxSelectable`, `composition` instead of `ingredients`) before the phase can close with a green gate.
