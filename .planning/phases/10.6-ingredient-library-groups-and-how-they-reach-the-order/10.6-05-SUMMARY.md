# Phase 10.6 Plan 05: Ingredient and group write/list paths onto the new column set Summary

**`catalog-drizzle.repository.ts` and the four modifier CRUD services now read and write display/behaviour, ingredient identity fields (description/imageS3Key/source) and two-mode composition instead of the dropped numeric range and `ingredients` column — the file's 16 type errors and all six plan-03 `eslint-disable` markers are gone.**

## Accomplishments

- `catalog-drizzle.repository.ts` is fully green: `upsertModifierGroup`/`upsertModifierOption` write `display`/`behaviour` and ingredient identity fields; `upsertModifierOption` no longer validates a parent group (an ingredient has no parent, D-01); `listModifierGroups` computes `optionCount` from `menu_modifier_group_options` instead of the removed `menu_modifier_options.modifier_group_id`; `getModifierGroupById` reads options through the link table ordered by the link's own `sort_order` and returns each option's `description`/presigned `imageUrl`; `upsertItem`/`getItemById` read and write `composition`/`compositionMode`/`compositionAssembled`
- All four plan-03 `eslint-disable` directives (six flagged lines) are deleted — the underlying dropped-column reads no longer exist, so the lint violations they were silencing are gone by construction
- `CatalogRepository` contracts (`UpsertModifierGroupRow`, `UpsertModifierOptionRow`, `UpsertItemRow`, `ItemDetailRow`, `ModifierGroupListRow`, `ModifierGroupDetailRow`) and their DTOs carry no numeric selection range and no `modifierGroupId` on an option — a group is display+behaviour+required, an ingredient is identity-only
- `MenuIngredientAlreadyAttachedError` added to the domain error union and to `error-mapping.ts`'s exhaustive switch (`catalog.ingredient_already_attached`, 409) — ready for plan 06/07's duplicate-attachment refusal (D-04)
- `ModifierOptionListRow`/`ModifierOptionListResponseSchema`/`ModifierOptionUsageResponseSchema` added as unwired contracts (three usage lists per D-28/D-22) for plan 06's ingredients-library screen — no new repository method added, per the plan's explicit scope boundary

**1. [Rule 3 - Blocking] Updated `upsert-item.service.ts` and `get-item.service.ts` — not in this plan's `files_modified`, broken by task 1's DTO/row rename**
- **Found during:** Task 1 verification (`api:typecheck`)
- **Issue:** Task 1 renamed `UpsertItemInput.ingredients`/`UpsertItemRow.ingredients`/`ItemDetailRow.ingredients` to `composition` (+ two new required fields). `UpsertItemService.execute` and `GetItemService.execute` both read the old field name and are direct, mechanical consumers of the interfaces this plan reshapes — neither file is in the plan's `files_modified` list, and the plan's own `<known_broken_after_this_plan>` note does not list them as expected-red.
- **Fix:** `UpsertItemService` forwards `composition`/`compositionMode`/`compositionAssembled` from the input to the repository row; `GetItemService` maps the same three fields from the row to the response.
- **Files modified:** `apps/api/src/contexts/catalog/application/items/upsert-item.service.ts`, `apps/api/src/contexts/catalog/application/items/get-item.service.ts`
- **Verification:** `apps/api:typecheck` filtered to `contexts/catalog|test/unit/catalog` returns 0; `test/unit/catalog/upsert-item.service.spec.ts` passes.
- **Committed in:** `e70161e4` (Task 3 commit)

**2. [Rule 3 - Blocking] Fixed a second fixture in `upsert-modifier-group.service.spec.ts`'s "no tenant context" test**
