# Phase 10.6 Learnings: Ingredient library, groups and how they reach the order

Sixteen plans across ten waves, much of it executed by parallel agents in sibling worktrees off a
long-lived stacked branch. That shape — parallel, stacked, worktree-isolated — produced most of
what is worth carrying forward, and almost none of it is about ingredients.

## Decisions

### A group's look and its arity became two independent fields
`display` (`tabs` | `tiles`) and `behaviour` (`one` | `several`) replaced the numeric
`minSelectable`/`maxSelectable` pair on `menu_modifier_groups`.

**Rationale:** the numbers conflated three separate questions — how the group renders, how many
options a guest may pick, and whether picking is mandatory. Operators were setting `max 0` to mean
"unlimited", which no one could read off the form. Splitting them made each answer explicit and
made `isRequired` orthogonal to both.
**Source:** 10.6-CONTEXT.md (D-01…D-34), 10.6-01-SUMMARY.md

### `SetItemCompositionInputSchema` is a flat object, not a discriminated union
`10.6-PATTERNS.md` specified `z.discriminatedUnion('mode', [...])`. It does not compile.

**Rationale:** `nestjs-zod`'s `createZodDto` needs `z.infer` to resolve to a single object type;
a union of two object types cannot serve as a class base (TS2509). The flat
`z.object({ mode, text: [].default([]), lines: [].default([]) })` matches what
`UpsertItemInputSchema` already proved compiles, and the service clears whichever array does not
match `mode`, so the wire contract is unchanged.
**Source:** 10.6-07-SUMMARY.md

### Composition saves on the main submit, not as its own action
Sizes and modifier groups each have an independent save action; composition does not.

**Rationale:** composition is `react-hook-form`-bound like `name`/`description`/`allergens`, not
local component state like the sizes and groups cards — there is no independent trigger to hang a
separate action off. It fires immediately after `upsertItem` succeeds, using the saved item id.
Necessary rather than merely tidy: the server field is named `composition`, not `compositionText`,
so the main upsert alone would silently drop free-text content.
**Source:** 10.6-14-SUMMARY.md

### `RESTO_SPINE_MIGRATION=1` is the sanctioned escape hatch for a cross-package rename
Used by plans 08, 11, 12, 13 and 14 — every time for the same reason.

**Rationale:** the pre-commit hook runs `nx affected -t typecheck --uncommitted` and fails on any
error in an affected project, with no way to tell pre-existing red from newly-introduced red. A
rename that crosses packages cannot leave the repo type-green until every call site is fixed, and
those call sites belonged to plans running concurrently in sibling worktrees. Each use was gated on
proving the executor's own files carried zero errors first.
**Source:** 10.6-08-SUMMARY.md, 10.6-11-SUMMARY.md, 10.6-13-SUMMARY.md, `.husky/pre-commit`

### An ingredient description is a single-line input; localization happens at the edge
The UI-SPEC asked for a plain `Input` with no locale tabs. The server wants `LocalizedText`.

**Rationale:** rather than push locale tabs into a sheet the spec deliberately kept simple, the
sheet flattens an existing description through `fromLocalizedText(..., defaultLocale)` for editing
and re-wraps it as `{ [defaultLocale]: text }` on save. The UI stays what was designed; only the
wire conversion moved.
**Source:** 10.6-12-SUMMARY.md

### The closing browser checkpoint was recorded as attestation, not observation
`10.6-16-SUMMARY.md` states plainly that the founder signed off and that no agent observed the
rendering.

**Rationale:** writing "verified in the browser" when nobody watched a browser would have made the
phase's own evidence untrustworthy. What could be verified independently — what the API actually
returns — was verified and tabulated; the rendering claims were marked as not covered.
`apps/qr-menu/test/item-detail-rendering.spec.tsx` was written afterwards to close that gap with
eight tests.
**Source:** 10.6-16-SUMMARY.md

## Lessons

### A green test suite proves nothing when module resolution points somewhere else
In the worktrees, `apps/qr-menu/node_modules/@resto/ui` was a relative symlink whose parent was
itself a symlink into the main checkout — so `@resto/ui` resolved to the **unedited** copy. Plan 10
reported `qr-menu:typecheck`, `website:typecheck` and 89/89 vitest green while exercising none of
its own changes. The executor caught it and said so instead of banking the pass.

**Context:** plan 09 had hit the same defect and fixed it with `pnpm install` from inside the
worktree, which corrupted the main checkout's `node_modules` and cost a repair cycle. Plan 10 was
therefore told not to, and verified by hand instead.
**Source:** 10.6-09-SUMMARY.md, 10.6-10-SUMMARY.md, todo `worktree-pnpm-install-corrupts-root-node-modules`

### ANSI colour silently turns `grep "error TS"` into a false green
`nx run <p>:typecheck` emits colour even when piped. The escape sequence lands between `error` and
`TS2322`, so the plan's own literal verify command matches zero lines regardless of the real error
count — and zero reads as success.

**Context:** hit independently in plans 03, 13 and 14. Every verify from then on ran with
`NO_COLOR=1 FORCE_COLOR=0` or stripped ANSI with `sed -E 's/\x1b\[[0-9;]*m//g'`.
**Source:** 10.6-03-SUMMARY.md, 10.6-13-SUMMARY.md, 10.6-14-SUMMARY.md

### Editing an already-applied migration's SQL is a no-op, and that is verifiable
Four migrations had unconditional `GRANT ... TO resto_app`. Fixing them meant editing SQL that
every existing database had already run.

**Context:** rather than assume, the executor read `drizzle-orm@0.45.2`'s `PgDialect.migrate()` and
established that re-application is gated purely on comparing each migration's journal timestamp
against the last applied `created_at` — the stored `hash` is written but never read back for a
skip decision. Safe by evidence, not by hope.
**Source:** 10.6-02-SUMMARY.md

### A pre-existing table becoming a composite-FK parent has no `(id, tenant_id)` index
`menu_modifier_options` had existed since the baseline migration and had never been referenced as a
composite-FK parent, so it had never needed the unique index ADR-0020 I-2 implies. Migration 0019
failed to apply until one was added.

**Context:** every other parent in the codebase already had one, because every other parent was born
a parent. This is a first-time-parent trap, not a missing convention.
**Source:** 10.6-02-SUMMARY.md

### A stop-list row's own PK is not the id its DELETE route filters on
`menu_stop_list` rows carry `id` (their own `pkUuid()`) alongside `itemId`. The DELETE routes filter
by the FK column. Passing `item.id` matches nothing, so the server throws
`StopListItemNotFoundError` and the control fails every time.

**Context:** found while extending `resetStopList` for ingredients. The identical bug in
`stop-list-table.tsx`'s per-row resume switch was outside that plan's scope, so it was logged rather
than fixed — every resume click on the items stop-list had been failing with an error toast in
production. Closed later in the phase; the file now sends `item.itemId`.
**Source:** 10.6-15-SUMMARY.md, deferred-items.md

### A test-double that omits a port method fails as a 500, not as a type error
`catalog.e2e.spec.ts`'s `IMAGE_URL_PORT` stub implemented `presignGet` but neither `publicUrl` nor
`publishPublicCopy`. Every `/v1/menu` read whose item had a photo crashed inside `publicPhotos()`.
Nine tests failed as `expected 500 to be 200`, including the file's first unmodified test.

**Context:** the stub predates this phase by a long way (`df8c9f87`). Seeing the real cause required
a temporary `console.error` in `exception.filter.ts` — NestJS's own `Logger` prints nothing under
the e2e harness's `NestFactory.create(..., { logger: false })`, so the filter's `logger.error` runs
and is silently swallowed.
**Source:** 10.6-08-SUMMARY.md

### On a long-lived stacked branch, `git merge-base main HEAD` is not the phase start
`main` had not moved since before phases 10.3–10.5, so the literal BASE formula pointed at
`2a3958db` and attributed three earlier phases' work to this one.

**Context:** plan 16's sweep used the literal BASE where acceptance criteria demanded it, but
cross-checked every diff-based gate against the true phase start (`3ec7a969`). Without that, the
forbidden-pattern sweep and the comment-hygiene review would both have been full of false positives.
**Source:** 10.6-16-SUMMARY.md

## Patterns

### Guard every `GRANT` against a role that may not exist yet
`DO $$ BEGIN IF EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'resto_app') THEN GRANT ...; END IF;
END $$;`

**When to use:** any migration granting to `resto_app`. `startPostgres()` runs `migrate()` against a
fresh container **before** `provisionAppRole()`, deliberately — the guard is what makes that ordering
work, and `roles.sql` re-grants everything afterwards. An unguarded `GRANT` aborts the whole
migration run and no integration test in the package can start.
**Source:** 10.6-02-SUMMARY.md

### Add each task's mock stubs in that task's own commit
The plan asked for all `CatalogRepository` mock stubs to land in a single final task. Plan 06 split
them so each task's commit added its own.

**When to use:** whenever a plan's intermediate commits would otherwise leave a shared test double
incomplete. The net diff is identical; the difference is that every commit passes the repo's own
pre-commit gate without the escape hatch, instead of only the last one.
**Source:** 10.6-06-SUMMARY.md

### Log out-of-scope findings; do not fix them
Six real defects were found in files outside the finding plan's `files_modified` list. Each was
written to `deferred-items.md` with its exact fix, its severity, and proof it predated the phase.

**When to use:** any time a plan trips over a bug it did not cause. The discipline is what kept
sixteen parallel plans from colliding, and the log was in fact read: four of the five items were
closed before the phase ended (`4a30eb53`, `7eb70be0`, the `stop-list-table` id, `8fdee2f3`). Only
the stale `menu.modifierGroups.groupMainDescription` copy is still open. The pattern works — but
only because someone came back to the file.
**Source:** deferred-items.md, 10.6-13/14/15/16-SUMMARY.md

### Prove a pre-existing failure by checking out the base and running it there
Plan 02 ran an untouched spec to show the role-grant failure was universal. Plan 04 used
`git show 77b1bfa3:<file>` to show a wrong assertion predated the plan. Plan 16 used
`git show 3ec7a969:<file>` plus `git log -- <file>` to prove no 10.6 commit had ever touched a
failing fixture.

**When to use:** before claiming any red check is inherited. "It was already broken" is a claim, and
the base commit is where it gets tested.
**Source:** 10.6-02/04/16-SUMMARY.md

### Break the implementation to prove the test would have caught it
The rendering tests written at phase close were verified by deliberately breaking the cache key and
the tile placeholder, and confirming the specific expected failures appeared.

**When to use:** any test written after the fact to cover behaviour that already works. A test that
has never been seen to fail is not yet evidence of anything.
**Source:** 10.6-16-SUMMARY.md

## Surprises

### Ingredient photos are silently erased by any edit that does not re-upload one
`upsertIngredient` does a full-field blind overwrite including `imageS3Key`, and the list DTO never
exposes `imageS3Key` — only a per-request presigned `imageUrl` the client cannot convert back. So
every edit that leaves the photo control alone sends `imageS3Key: null`.

**Impact:** a reproducible data-loss bug on the screen this phase is named after. The executor
designed and implemented the four-file fix, then reverted it rather than ship it half-applied —
regenerating the OpenAPI contract needs a booted `AppModule`, which failed in the sandboxed
worktree, and hand-editing the generated client is forbidden. Closed later in the phase by
`4a30eb53`, once a session with dev-stack access could run the codegen. Reverting rather than
hand-editing is what made that possible.
**Source:** 10.6-12-SUMMARY.md

### A threat-model mitigation had never been implemented
T-10.6-12-01 assumed `PhotoUpload` "sends only a `kind` discriminator" so the server picks the
`ingredients/` S3 prefix. `PhotoUpload` had never sent `kind` at all, and `getPhotoUploadUrl`'s
signature did not accept one — every upload defaulted to `menu-items/`.

**Impact:** the plan simultaneously instructed that `photo-upload.tsx` was "reused unchanged" and
that `git diff --stat` should show no change to it — two instructions that cannot both hold while
implementing the mitigation. The executor implemented it, documented the 3-line diff, and said the
acceptance bullet was not met rather than quietly satisfying it.
**Source:** 10.6-12-SUMMARY.md

### Four unconditional `GRANT`s had broken every fresh-Postgres bootstrap, undetected
Migrations 0006, 0011, 0015 and 0017 could not run against an empty database. No integration test in
`packages/db` could start on a clean testcontainer.

**Impact:** invisible for as long as everyone reused an already-migrated database. It surfaced only
when a plan needed a genuinely fresh one.
**Source:** 10.6-02-SUMMARY.md

### `status: 'created'` and `status: 'paid'` fixtures outlived the column that allowed them
Migration 0010 split `orders.status` into a fulfilment stage and an independent `payment_status`.
Stale literals survived in `tenant-isolation.spec.ts`, two `erase-includes-*` specs,
`outbox-nats-decoupling.e2e.spec.ts` and all eleven `seedOrder` call sites in
`order-lifecycle.e2e.spec.ts`.

**Impact:** each was found separately, by a different plan, as a mysterious `23514` on work that had
nothing to do with orders. A schema change that tightens a CHECK constraint needs a fixture sweep in
the same commit.
**Source:** 10.6-02/04/16-SUMMARY.md

### The plan's own suggested schema shape did not compile
`10.6-PATTERNS.md` — the artifact whose job is to hand executors proven shapes — specified a
`z.discriminatedUnion` that TS2509s against this project's DTO base class.

**Impact:** a reminder that a pattern file is a hypothesis until something compiles it. The executor
replaced it with a shape already proven elsewhere in the same file.
**Source:** 10.6-07-SUMMARY.md

### `npx shadcn add radio-group` was never run
The plan asked for it literally. Running any CLI that might trigger an install from inside a
worktree was an absolute prohibition after wave 4's repair cycle.

**Impact:** the file was hand-authored to match the registry output and the repo's sibling
primitives byte-for-byte. The acceptance criterion ("exists and is unmodified CLI output") is
satisfied in substance but not in provenance — and the executor flagged that rather than claiming
the invocation.
**Source:** 10.6-11-SUMMARY.md

### Two executor agents were killed mid-plan by transient network drops
Plans 07 and 08 both lost their agent to an `ENOTFOUND`-class failure before finishing.

**Impact:** nothing was lost, because the phase's standing rule was to commit each task immediately
rather than batch. Plan 07 additionally found its worktree HEAD on a commit predating the whole
phase, and had to verify with `git merge-base` before resetting. Per-task commits are what made both
recoveries cost nothing.
**Source:** 10.6-07-SUMMARY.md, 10.6-08-SUMMARY.md
