## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `IngredientFormSchema.description` (plain string) vs. the server's localized wire contract**
- **Found during:** Task 3
- **Issue:** `UpsertModifierOptionInputSchema.description` on the server is `LocalizedText.nullable()` (`apps/api/.../application/dto.ts:116`), but plan 11's `IngredientFormSchema.description` is `z.string().max(140).nullable()` per the UI-SPEC's explicit "single-line Input, not a Textarea, no locale tabs" instruction. Sending the form's plain string straight through `upsertIngredient`'s original signature (`Omit<IngredientForm,'name'> & {name: LocalizedText}`, which left `description` as `string | null`) would 400 on the first non-empty description.
- **Fix:** Widened `upsertIngredient`'s parameter type to require `description: LocalizedText | null`; the sheet flattens an existing ingredient's description via `fromLocalizedText(ingredient.description, defaultLocale)` for editing, and re-wraps the plain string as `{ [defaultLocale]: text }` (or `null` when empty) before calling `upsertIngredient`. The UI stays exactly the single-line Input the UI-SPEC asked for — only the wire-format conversion changed, at the edge.
- **Files modified:** `apps/admin/src/lib/queries/catalog.ts`, `apps/admin/src/components/menu/ingredient-form-sheet.tsx`
- **Verification:** `admin:typecheck` clean on both files; manually traced the payload shape against `UpsertModifierOptionInputSchema`.
- **Committed in:** `cbc528a3` (Task 3 commit)

**2. [Rule 2 - Missing critical functionality, T-10.6-12-01] `PhotoUpload` never sent a `kind` discriminator**
- **Found during:** Task 3
- **Issue:** The plan's own threat model (T-10.6-12-01) assumes `PhotoUpload` "sends only a `kind` discriminator" so the server picks the `ingredients/` S3 prefix. In fact `PhotoUpload`'s internal `getPhotoUploadUrl` call never included `kind` at all, and `getPhotoUploadUrl`'s own TS signature didn't accept one — every upload (item or ingredient) would default to the server's `kind: 'item'` and land under `menu-items/`, silently defeating the discriminator the threat model calls a mitigation. Task 3's own read_first note says `photo-upload.tsx` is "Reused unchanged" and one acceptance bullet checks `git diff --stat` shows no change to it — those two instructions are mutually exclusive with implementing T-10.6-12-01 correctly.
- **Fix:** Added an optional `kind?: 'item' | 'ingredient'` prop to `PhotoUpload`, defaulting to `'item'` — fully backward-compatible with the one existing caller (`item-aside.tsx`, unchanged, still gets `kind: 'item'` implicitly). `ingredient-form-sheet.tsx` passes `kind="ingredient"`. `getPhotoUploadUrl`'s type in `catalog.ts` widened to accept the optional field.
- **Files modified:** `apps/admin/src/components/menu/photo-upload.tsx` (3-line diff), `apps/admin/src/lib/queries/catalog.ts`, `apps/admin/src/components/menu/ingredient-form-sheet.tsx`

## Issues Encountered

**Ingredient photos are silently erased by any edit that doesn't re-upload a photo — found, a fix was designed and attempted, then reverted; not shipped.** `ModifierOptionListResponseDto` (and therefore `IngredientApi`) exposes `imageUrl` (a short-lived presigned GET URL) but never the underlying `imageS3Key`. `upsertIngredient`'s single POST endpoint (`UpsertModifierOptionService` → `CatalogDrizzleRepository.upsertModifierOption`) does a full-field blind overwrite on UPDATE, `imageS3Key` included, with no "omit to keep the existing value" semantic — confirmed by reading the repository's `updateTable` call directly. Since the admin client has no way to recover the current `imageS3Key` from a presigned URL (it changes per-request and isn't a stable derivable path, unlike the deterministic `public/`-prefixed published-copy URL used elsewhere in this codebase), every ingredient edit that doesn't touch the photo control sends `imageS3Key: null` and wipes the existing photo. I designed and implemented the correct four-file server fix (add `imageS3Key` to `ModifierOptionListRow`/`ModifierOptionListItemSchema`, thread it through `list-modifier-options.service.ts` and the repository's list query, then round-trip it from `ingredient-form-sheet.tsx`'s `buildDefaults`), but regenerating the committed OpenAPI contract (`pnpm exec nx run api:openapi:emit`) requires booting the full Nest `AppModule`, which failed silently (exit 1, no stderr beyond a Node experimental-loader warning) in this sandboxed worktree with no dev Docker stack running. Hand-editing the generated `packages/api-client/src/generated/api.ts` was rejected — `packages/api-client/CLAUDE.md` explicitly forbids it ("auto-generated ... Never edit by hand") and a hand-edit that doesn't byte-for-byte match real codegen output would itself trip CI's `openapi-drift` job. The four `apps/api` edits were reverted (`git checkout --` on each of the four files) rather than left half-applied. **This is a real, reproducible data-loss bug on the exact screen this phase is named after and needs a fast follow-up** — the fix is fully designed above; a follow-up plan with dev-stack access should be able to land it in well under the time it took to discover and design here.
