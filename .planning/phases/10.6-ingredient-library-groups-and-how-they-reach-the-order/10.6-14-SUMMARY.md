# Phase 10.6 Plan 14: Composition editor and the singles chip row Summary

**Split "ingredients" into two concerns: a singles chip row on the modifier card for direct attachment, and a new form-bound CompositionEditor (text/assembled modes) for the dish's description-adjacent composition.**

- **Completed:** 2026-09-03
- **Tasks:** 3
- **Files modified:** 7 (4 modified, 3 created, 1 doc)

## Accomplishments

- `item-modifier-groups-card.tsx` no longer has a composition field at all — the free-text `ingredientsField`/`ingredientsText`/`commaListFromInput` are gone. The card now shows two visually identical chip rows: assigned groups (unchanged behavior) and directly-attached single ingredients (new, backed by `setItemIngredients`).
- The singles picker refuses (with a tooltip naming the group) attaching an ingredient already reachable through one of the dish's assigned groups — client-side convenience matching D-04, with the server's `MenuIngredientAlreadyAttachedError` → 409 as the actual authority.
- The inline "create group" dialog is now name-only; it creates a `display: 'tiles', behaviour: 'several', isRequired: false` group, identical to what the Groups tab produces by default (D-12 — no per-dish override exists anywhere).
- New `CompositionEditor` component: a `RadioGroup` toggles between free text (the same comma-split `Input` UX the old field had) and an assembled, drag-reorderable list of ingredients. Assembled rows show name only, never a price or unit (D-15), plus a `Switch` for the removable flag and an aria-labelled remove button.
- The item save flow now writes composition through `setItemComposition` (plan 11's endpoint) right after the item upsert succeeds, using the saved item's id — works for both new-item creation and edits.

## Decisions Made

- **Save-path shape for composition:** rides a separate `setItemComposition` call fired from `item-detail-form.tsx`'s `onSubmit`, immediately after the main `upsertItem` call succeeds, using the returned/saved item id. This was the plan's open question ("depends on how this shell already batches its saves"); I picked "separate call, same submit action" rather than "separate call, own independent UI action" (what sizes/modifier-groups do) because composition is `react-hook-form`-bound like `name`/`description`/`allergens`, not local-component-state like the groups/sizes cards — it has no independent save trigger of its own to hang a separate action off of. Verified this is necessary: the server's `UpsertItemInputSchema` field is named `composition` (not `compositionText`), so the main upsert alone would silently drop free-text-mode content while `compositionMode`/`compositionAssembled` field names happen to match verbatim.
- **`disabledIds` computation for the singles picker:** `useQueries` over `modifierGroupQuery(id)` for each of the dish's assigned group ids, unioning every returned option id. No new server endpoint — matches the plan's literal instruction and avoids touching `apps/api` (out of scope for this worktree).

### Logged, not fixed (SCOPE BOUNDARY — pre-existing, not caused by this plan's changes)

**1. `ItemDetailResponseDto` has no field for a dish's directly-attached single ingredient ids**
- **Found during:** Task 1 (singles chip row)
- **Issue:** `apps/api`'s admin item-detail read model (`GetItemService`/`CatalogDrizzleRepository.getItemById`) never joins `menuItemModifierOptions`, unlike `menuItemModifierGroups` (which backs `modifierGroupIds`). The guest-facing *published* read model (`findPublishedItem`) does this join correctly (`extraOptionIds`) — only the admin draft read model is missing it.
- **Effect:** the singles chip row writes correctly (`setItemIngredients`, whole ordered array, D-04 refusal enforced) and session-local adds/removes render immediately, but a page reload shows an empty singles row even though the attachment persisted server-side.
- **Not fixed here:** `apps/api` is outside this plan's `files_modified` scope (admin-only, parallel worktree with plans 12/13), and the gap pre-dates this plan's changes — it is not something Task 1's edits caused.
- **Logged to:** `deferred-items.md` with the exact fix (new DTO field + repository join + OpenAPI/api-client regen + a new `initialIngredientIds` prop), scoped small enough for a single follow-up plan or fold-in.

### Environment workarounds
