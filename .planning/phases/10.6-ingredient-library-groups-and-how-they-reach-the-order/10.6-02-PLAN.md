<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| application role → Postgres | `resto_app` reaches the new tables; RLS + FORCE RLS is the enforcement, `ScopedTx` is the first layer |
| tenant A session → tenant B rows | the classic cross-tenant boundary; the composite FK plus the PERMISSIVE policy are what hold it |
| operator at location A → location B stop rows | `menu_option_stop_list` is location-scoped, so a second RESTRICTIVE policy is required |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10.6-02-01 | Information Disclosure | the three new tables | mitigate | PERMISSIVE `_iso` policy + `FORCE ROW LEVEL SECURITY`, proven by the cross-tenant SELECT test in task 3 |
| T-10.6-02-02 | Tampering | cross-tenant INSERT with a foreign parent id | mitigate | composite `(id, tenant_id)` FK to both parents, proven by the cross-tenant INSERT test in task 3 |
| T-10.6-02-03 | Information Disclosure | `menu_option_stop_list` across locations | mitigate | RESTRICTIVE `_location_iso` policy copied from `menu_stop_list`, proven by the location-grain test |
| T-10.6-02-04 | Denial of Service | GDPR erasure hitting a `foreign_key_violation` | mitigate | `tenancy_erase_tenant` reproduced with three new FK-safe DELETEs; smoke-called in task 2 |
| T-10.6-02-05 | Elevation of Privilege | over-broad DELETE grant | accept | DELETE is granted on exactly three tables, each with a delete-then-reinsert or unstop write path; the default no-DELETE posture is unchanged elsewhere |
| T-10.6-02-SC | Tampering | npm/pip/cargo installs | mitigate | no package is installed by this plan |
</threat_model>
