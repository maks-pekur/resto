# Phase 10.6: Ingredient library, groups and how they reach the order - Research

**Researched:** 2026-09-03
**Domain:** Multi-tenant catalog schema migration (Drizzle/Postgres), NestJS DDD bounded-context CRUD, cached public-menu payload, order-time pricing/validation, Vite/React admin CRUD, and a shared guest UI package consumed by two apps.
**Confidence:** HIGH — every claim below is a direct code read (file:line) in this repository, not training-data inference about the stack in general.

## Summary

This phase touches six surfaces that all currently agree with each other, which is exactly why the change is wide: `menu_modifier_options` is a group-owned row today (`modifier_group_id NOT NULL`), the published-menu DTO nests options inside each group with no top-level dedupe, the order aggregate's allowed-set check is a single `modifierGroupIds.includes(option.groupId)` line, the guest hook's single-choice/checkbox branch is keyed on `minSelectable===1 && maxSelectable===1 && isRequired`, and the admin's three menu screens (categories / items / modifier-groups) all read from the same three Drizzle tables via one repository. Every one of those five facts has to change in the same direction for the phase to work, and none of them can change alone without breaking a caller documented below.

Two structural findings drive the plan more than anything else. First, the guest wire type for `/v1/menu` and `/v1/menu/availability` is **hand-maintained in three separate places** (`packages/api-client/src/menu-types.ts`, `apps/qr-menu/src/api/client.ts`, `apps/website/lib/api-client.ts`) — none of it flows from the OpenAPI generator the way the admin's catalog types do (`apps/admin/src/lib/queries/catalog.ts` derives everything from `components['schemas']`). A schema change here is a manual-sync problem across three files with no compiler check tying them together; get one out of sync and the guest app silently mis-renders. Second, `order_modifiers` has no column that can currently distinguish "the guest added this modifier" from "the guest excluded this composition ingredient" (D-18) — both would produce a row with a populated `option_id`, `price_delta`, and a `NULL` `modifier_group_id`. This needs an explicit decision the plan must make (see Risks §8.3).

The migration itself is well-trodden ground: `0003_table_zones_and_tables.sql` is a complete, recent template for a hand-written multi-table migration with composite FKs, RLS (both PERMISSIVE tenant and, where needed, RESTRICTIVE location), `resto_app` grants, and `tenancy_erase_tenant` updates — every one of those four things is a checklist item this phase's migration must also hit, and the template shows the exact SQL shape for each.

**Primary recommendation:** Treat the schema/domain/catalog-read work as the spine (it gates everything else), extend `CatalogMenuPricingAdapter` and `create-order.service.ts`'s allowed-set check as the second wave, then fan out into catalog CRUD, admin, and guest UI in parallel — but budget an explicit "sync the three hand-written guest type files" task, because nothing will catch a miss at compile time.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Ingredient identity (photo/name/description/price) | Database / Storage (`packages/db`) | API / Backend (catalog CRUD) | New reusable entity; storage shape drives everything downstream |
| Group→ingredient / item→ingredient membership | Database / Storage | API / Backend | Pure link tables; ordering is data, not logic |
| Group display/behaviour semantics (tiles\|tabs, one\|several) | API / Backend (catalog domain) | Browser (guest render branch) | Server is authoritative on what a group *is*; guest only renders it |
| Composition (free-text or assembled, removable flag) | API / Backend (catalog domain) | Browser (guest render + tap-to-exclude interaction) | Authoring lives on the item; the guest's per-order exclusion choice is transient client state until submit |

### Locked Decisions

**The ingredient and its attachments**
- D-01: The Ingredients screen holds identity only — photo, name, description, price. Nothing about behaviour lives there.
- D-02: Behavioural fields belong on the attachment (group→ingredient or dish→ingredient link), not on the ingredient. In this phase the attachment carries only `sort_order`. Do not add nullable behaviour columns "for later."

- D-10: The ingredient's description is shown to the guest as a small line under the name on the tile, single line, ellipsised.

### RLS pattern — exact statements from a recent table

Confirmed in `0000_baseline.sql` for the three existing tables, and in `0003_table_zones_and_tables.sql` (most recent, full pattern):

- Tenant-only tables (`menu_modifier_groups`, `menu_modifier_options`, `menu_item_modifier_groups`) get **one PERMISSIVE policy**:
  ```sql
  ALTER TABLE public.menu_modifier_options ENABLE ROW LEVEL SECURITY;
  CREATE POLICY menu_modifier_options_iso ON public.menu_modifier_options
    USING ((public.is_system_session() OR (tenant_id = public.current_tenant_id())))
    WITH CHECK ((public.is_system_session() OR (tenant_id = public.current_tenant_id())));
  ```
  (`0000_baseline.sql:1167-1173`)

- Location-scoped tables (`menu_stop_list`) get **both** a PERMISSIVE tenant policy **and** a RESTRICTIVE location policy:
  ```sql
  ALTER TABLE public.menu_stop_list ENABLE ROW LEVEL SECURITY;
  CREATE POLICY menu_stop_list_iso ON public.menu_stop_list
    USING ((public.is_system_session() OR (tenant_id = public.current_tenant_id())))
    WITH CHECK (...);
  CREATE POLICY menu_stop_list_location_iso ON public.menu_stop_list AS RESTRICTIVE
    USING ((public.is_system_session() OR (public.current_location_id() IS NULL) OR (location_id = public.current_location_id())))
    WITH CHECK (...);
  ```
  (`0000_baseline.sql:1175-1179`, restated identically for `table_zones`/`restaurant_tables` in `0003_table_zones_and_tables.sql:97-107`)

**Implication for this phase:** `menu_modifier_group_options` and `menu_item_modifier_options` are tenant-wide (not location-scoped) → single PERMISSIVE policy, matching `menu_item_modifier_groups`. `menu_option_stop_list` (the new ingredient stop table) is location-scoped exactly like `menu_stop_list` → needs **both** policies.

Every new table also needs `ALTER TABLE ONLY public.<table> FORCE ROW LEVEL SECURITY;` (separate statement, confirmed pattern at `0003_table_zones_and_tables.sql:21,44`).

### `resto_app` grant pattern (`packages/db/sql/roles.sql`, full file read)

Baseline grants (`roles.sql:18-25`): `GRANT USAGE ON SCHEMA public`, `GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA public`, plus `ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT, INSERT, UPDATE ON TABLES TO resto_app` (`roles.sql:47-48`) — this means **new tables automatically get SELECT/INSERT/UPDATE** for `resto_app` as long as the admin role that ran `ALTER DEFAULT PRIVILEGES` is the same role that later creates the table via migration.

**DELETE is not covered by any default-privileges statement** — it is deliberately excluded (`roles.sql:20-22`, "hard deletes are forbidden"). Every table that needs a real `DELETE` gets an **explicit, idempotent `GRANT DELETE`** guarded by a table-existence check, restated in *both* the migration file and `roles.sql`, "to keep the end state convergent regardless of order":
- `menu_stop_list` (`roles.sql:67-76`) — needed because `removeFromStopList` does a genuine hard DELETE (the "sole sanctioned hard DELETE on a tenant-scoped table" per `catalog-drizzle.repository.ts:709`).
- `menu_item_modifier_groups` (`roles.sql:78-86`) — needed because `replaceItemModifierGroups` does delete-then-reinsert to replace link-table membership (`catalog-drizzle.repository.ts:625-643`).
- `table_zones`/`restaurant_tables` (`roles.sql:100-114`) — these got only SELECT/INSERT/UPDATE, no DELETE (lifecycle is archive, not membership replace).

**Implication:** `menu_modifier_group_options` and `menu_item_modifier_options` will need the delete+reinsert pattern (D-14's "set membership and order in one write" / ING-03's ordered membership) — so they need the same explicit `GRANT DELETE` treatment as `menu_item_modifier_groups`. `menu_option_stop_list` needs it too, matching `menu_stop_list`'s unstop pattern.

### Migration file convention (`0018_menu_item_diets.sql`, full file, and `0003_table_zones_and_tables.sql`, full file)

`0018` is a single line: `ALTER TABLE menu_items ADD COLUMN IF NOT EXISTS diets text[];` — trivial, not representative of structure. `0003_table_zones_and_tables.sql` (117 lines) is the real template and covers every section this phase's migration needs, in this order: (1) header comment explaining why it's hand-written, (2) `CREATE TABLE` + `FORCE ROW LEVEL SECURITY` per table, (3) indexes (unique-`(id, tenant_id)` first, since composite FKs require it), (4) foreign keys, (5) RLS `ENABLE` + policies, (6) any sibling-table column additions (N/A here unless composition's assembled-mode column lands as an ALTER on `menu_items`), (7) `resto_app` grants in a guarded `DO $$` block, (8) **`tenancy_erase_tenant` reproduced in full with new `DELETE` statements inserted in FK-safe order**. Every statement is separated by `--> statement-breakpoint` (Drizzle's migration-splitter marker — required for `drizzle-orm/postgres-js/migrator` to apply statements individually).

### Migration application mechanism — `pnpm db:migrate`

### Excluded composition line as an order row — options in the current schema (not deciding)

`order_modifiers`'s current columns (`optionId`, `nameSnapshot`, `priceDelta`, `amount`, `modifierGroupId`) have **no field that distinguishes "guest added this" from "guest excluded this."** An excluded composition line and a free (`priceDelta: 0`) single-ingredient modifier addition would be byte-for-byte identical rows today: `optionId` populated (composition ingredients are library ingredients — same `menu_modifier_options` rows per the design), `priceDelta = 0`, `modifierGroupId = NULL`, `amount = 1`. Three shapes are visible in the current schema for the plan to choose between:

1. **Add a discriminator column** (e.g. `kind: text` — `'added' | 'excluded'`, or a boolean `is_exclusion`) to `order_modifiers`. Smallest schema change; keeps one table, one write path, one read path (`order-detail-sheet.tsx:320`'s single `item.modifiers.map` would filter on the new field).
2. **Reuse `amount` as a sentinel** (e.g. negative amount for exclusion). Rejected on its face by the existing money formula (`priceDelta × max(0, amount − freeAmount)`, `order.aggregate.ts:154`) — a negative `amount` either breaks that formula or requires special-casing it, and `amount` is typed `smallint` with existing non-negative semantics everywhere else (`min_amount >= 0` checks throughout catalog).
3. **A second table** (`order_excluded_ingredients`, mirroring `order_modifiers`'s shape minus `priceDelta`/`amount`, since D-15 composition carries no cost). Cleanest separation of concerns, but doubles the read/write surface: `order.aggregate.ts`'s snapshot, the Drizzle repository's insert loop, the DTO, and `order-detail-sheet.tsx` all need a second collection instead of a filter on one.

This research does not recommend between these — CONTEXT explicitly asks the plan to report options, not decide. Option 1 is the smallest diff against every file already found to touch `item.modifiers`/`OrderModifierSnapshot` in this research; option 3 is the cleanest domain model. Whichever is chosen, `nameSnapshot` remains the display value in both the admin (`order-detail-sheet.tsx:325`) and the ordering domain — no change needed there.

## 8. Risks, unknowns and landmines

### 8.1 The migration must update `tenancy_erase_tenant` or GDPR erasure breaks for every tenant that ever touched ingredients

`0003_table_zones_and_tables.sql:138-144` documents this exact failure mode happening three times before (migrations 0072/0074/0077 in the pre-squash history): a new tenant-scoped table not added to `tenancy_erase_tenant`'s `DELETE FROM ...` sequence causes a `foreign_key_violation` the first time erasure runs against a tenant that has rows in it. The function is reproduced in full in `0003_table_zones_and_tables.sql:146-268` and already contains, in FK-safe order, `DELETE FROM menu_stop_list`, `menu_item_modifier_groups`, `menu_modifier_options`, `menu_modifier_groups` (lines 185-189). **This phase's migration must add `DELETE FROM menu_option_stop_list`, `menu_item_modifier_options`, `menu_modifier_group_options` (new link/stop tables) in the correct dependency order — before their parent rows are deleted, in the same style as the existing block** — and must NOT simply leave the existing lines unchanged if `menu_modifier_options` gains new required-at-write-time columns that don't affect DELETE order but do affect the function if any `UPDATE`/anonymization logic is added later. This is the single most likely "looks done, breaks GDPR erasure in prod" landmine in the whole phase, and it is easy to miss because the function lives in a migration file, not in `packages/db/src/schema/`.

### 8.2 Hand-written migration needs a `_journal.json` entry, or it silently never runs

Confirmed above (§1) — this is a second, independent failure mode from the `drizzle-kit generate` snapshot problem D-31 already names. Missing the journal entry produces no error at migrate time; the migrator simply doesn't see the file. Existing precedent (`0003`, `0001`) all have matching `_journal.json` entries — the plan's migration task must explicitly include adding one.

### 8.3 `order_modifiers` cannot currently distinguish an added modifier from an excluded composition line

Documented in full in §3 with three concrete schema options. This is not a "nice to figure out during implementation" gap — `order-detail-sheet.tsx:320` and the guest's `onAddToCart` payload (per UI-SPEC's composition-line section: "the excluded set feeds `onAddToCart` as its own array") both assume *some* way to separate the two on read, and nothing in the current schema provides it. The plan must pick one of the three options (or a fourth) explicitly, not discover the ambiguity mid-implementation.

### 8.4 `PricedModifierOption.groupId` and `published.modifierGroupIds.includes(...)` are both non-nullable/group-only today

Confirmed exact code at `ordering/domain/ports.ts:31-38` and `create-order.service.ts:100-103`. A single ingredient attached directly to a dish (ING-04) has no group at all — the allowed-set check as written today has no branch for that case and will reject every single-ingredient order line as `OrderModifierNotAvailableError` until this is extended. Low risk of being missed (it's directly in the pricing hot path, any test would catch it) but sequencing matters: this must land before any admin/guest work that lets an operator attach a single ingredient, or the feature will look wired end-to-end and then 422 at checkout.

### 8.5 The `modifier_group_id`-keyed option query in `loadPublishedMenu` and `findPublishedItem` will silently return empty option lists, not error, if the join isn't updated

`catalog-drizzle.repository.ts:115-124`'s `inArray(schema.menuModifierOptions.modifierGroupId, ...)` — once `modifier_group_id` is dropped from `menu_modifier_options`, this line **fails to compile** (the column won't exist on the Drizzle schema type), which is actually the safe outcome — TypeScript will force every call site to be found. The risk is lower here than it looks; flagging only so the plan doesn't budget separate runtime-testing time for something the compiler already guarantees to catch.

### 8.6 `menu-modifier.ts` domain schema (`packages/domain`) has a root-level `.refine()`, blocking `.extend()` — but it is effectively dead code

`packages/domain/src/schema/menu-modifier.ts:16-29` — `MenuModifier` is `z.object({...}).refine(...)`, which per `packages/domain/CLAUDE.md`'s own stated rule ("Do NOT apply `.refine()` to the root of an object schema you expect consumers to compose... blocks `.partial()`/`.extend()`/`.omit()`/`.pick()`") cannot be safely `.extend()`-ed with new `display`/`behaviour` fields. **However**, a targeted grep found this schema is imported nowhere at runtime outside its own file and the package barrel (`packages/domain/src/index.ts`, `schema/index.ts`) — `apps/api`'s actual runtime types for modifiers come from `PublishedMenuModifierOption`/`PublishedMenuModifierGroup` (plain TS interfaces in `catalog/domain/published-menu.ts`) and Drizzle's own inferred row types, not from this Zod schema. Low risk to rewrite freely; worth an explicit decision (rewrite in place vs. delete as dead weight) rather than leaving a second, silently-stale schema in the domain package that nothing enforces agreement with.

### 8.7 `packages/ui` has no build/publish step — no plan-ordering constraint from that direction

`packages/ui/package.json`: `"main": "./src/index.ts"`, no `build` target in `packages/ui/project.json` (only `lint`/`typecheck`). Both `apps/qr-menu` (Vite) and `apps/website` (Next.js) resolve this workspace package by transpiling its TS source directly — there is no `dist/` artifact to go stale. This means guest UI changes in `packages/ui/src/guest/*` are picked up immediately by both consuming apps' dev servers and builds with no intermediate publish/build step required between plans.

### 8.8 The guest wire-type triplication (§4) is the highest-effort-to-verify risk in the phase

Restated because it is the single fact most likely to cause a late-discovered bug: three independent, hand-written type files (`packages/api-client/src/menu-types.ts`, `apps/qr-menu/src/api/client.ts`, `apps/website/lib/api-client.ts`) must all be updated to add the ingredient/composition/second-availability-array fields, and none of the three has any compiler or CI check tying it to the backend Zod schema or to each other. A plan that only updates the backend and one of the three guest files will type-check cleanly in every project except the one that was missed, and will only surface as a runtime `undefined` in the browser.

### 8.9 The stop-overlay read cost is unbounded by anything in the current code — worth a look, not necessarily a blocker

`loadPublishedMenu` and `findPublishedItem` already do N+1-shaped `Promise.all` fan-outs per read (sizes, item-modifier-links, options-by-group). Per D-23 (stop computed per read, not materialized), adding an ingredient-stop-set fetch and a "is this dish's required group now empty" computation to the same per-read path is consistent with the existing architecture (the whole function is already assembled per-request behind the CDN, not per-write) — flagged only so the plan's read-path task accounts for one more `Promise.all` branch, not treated as a performance redesign.
