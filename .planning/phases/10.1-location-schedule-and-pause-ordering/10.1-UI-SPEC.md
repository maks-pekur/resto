# Phase 10.1 — UI Design Contract

> Visual and interaction contract for "Location schedule and pause ordering." Covers 9 surfaces across `apps/admin` and `apps/website`. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Founder decisions locked before this document (do not re-open):**

1. Location edit lives on a dedicated route `/{brandSlug}/locations/{locationId}` — sectioned page (Details → Opening hours → Date exceptions → Pre-orders), not a sheet/dialog.
2. The weekly schedule editor is an always-visible 7-row grid (all seven days on screen, inline time inputs, per-row open/closed control, "+ interval" reveal, "copy Monday to all days"), not day tabs, not expandable rows.
3. Pre-order slot granularity is 15 minutes, one named constant.

| ----- | ----- | ---------------------------------------------------------- |

| sm    | 8px   | Compact control gaps (e.g. interval field pairs)           |

| 2xl   | 48px  | — (not newly used this phase)                              |
| 3xl   | 64px  | — (not newly used this phase)                              |

**Exceptions:**

- **48px (`h-12`) minimum touch target on every pause-control button, the resume button, and the closed-until-date native input.** This is not a new rule — it is the established precedent for tablet-facing operator controls: `apps/admin/src/components/orders/accept-popover.tsx:69,82-91,96,112,122` and `apps/admin/src/components/orders/order-card.tsx:203-233` all use `h-12` for every button an operator taps mid-rush. The pause control is used in the identical context (busy kitchen, greasy hands) and must match, not introduce a smaller target.
- **7-row schedule grid rows use `gap-2` (8px) between the day label, toggle, and time-field cluster** — denser than `md` because seven rows plus two intervals each must fit on one screen without scrolling per the locked "always-visible" decision.

This pulls in `cmdk` as a new transitive dependency — confirmed absent from `apps/admin/package.json` and the root `pnpm-lock.yaml` today, so this is a real new install, not a re-scaffold.

**Deliberately NOT added — native input is genuinely sufficient, do not add `calendar`:**

- **"Closed until a date" pause branch** and **the date-exceptions editor's date field** both use a plain `<input type="date" min={tomorrowISO}>`. Rationale: both are single-date pickers, not ranges; native date pickers on iPadOS/Android tablet Safari/Chrome — the actual operator device per the brief — render as large, OS-native scroll wheels that are more touch-friendly than a shadcn `Calendar` popover grid of small day cells. Adding `calendar` (+ `react-day-picker` dependency) buys nothing this phase does not already get for free. Style the native input at `h-12` to match the touch-target rule above.
- **Weekly-schedule open/close fields** use `<input type="time">` for the same reason — no time-picker primitive exists in this codebase and none is needed.

**No other admin gaps.** Everything else this phase needs already exists: `Switch` for the per-day Closed toggle (precedent: `order-filter-bar.tsx:98` sound-mute switch), `Popover` for the pause-duration popover (precedent: `accept-popover.tsx`), `Table` for the locations list, `Card` for the edit-page sections, `Sonner` (toast) for save/pause confirmations.

### `apps/website` — add ZERO new shadcn primitives

**Present:** alert-dialog, badge, button, checkbox, dialog, form, input, label, radio-group, scroll-area, separator, sheet, skeleton, sonner, tabs, tooltip.

**Everything this phase needs on the guest side is already present:**

## Surface Specifications

### A1 — `/{brandSlug}/locations` list (`apps/admin/src/routes/(protected)/$brandSlug/locations.tsx`)

Current state (read in full): owner-gated, inline "New location" `Card` (lines 146-203), a plain `<table>` with columns Name / Address / Status / Actions (lines 212-254), Archive-only row action (`Archive` icon button, ghost, size sm, line 238-247).

**Changes:**

- **New "Order intake" column**, inserted between Address and Status. Shows the `LocationStateChip` (built once, shared with A3 — see Component Inventory) for `status === 'active'` rows; shows `—` for archived rows (they cannot take orders regardless).
- **The chip is itself the popover trigger.** Clicking "Accepting orders" / "Paused until 21:20" / "Closed · opens 11:00" opens the same pause/resume `Popover` used on A3 — no separate icon button for pause. This keeps the row from needing a 5th action slot and matches the "one tap" philosophy (D-11).
- **Actions column gains an Edit affordance** — a `Pencil` icon `Button` (`variant="ghost" size="sm"`, matching the existing Archive button's exact treatment at line 238-247), `aria-label={t('locations.list.editAria', { name: location.name })}`, routing to `/{brandSlug}/locations/{location.id}` (A2). Archive stays where it is, unchanged.
- **D-24 site-orders marker.** Below/beside the location `name` cell, render a small `Badge variant="outline"` with a `Globe` icon (lucide) and copy `locations.list.siteOrdersBadge`, shown **only** on the one location `DefaultLocationResolverService` currently resolves to for guest checkout. Wrap in a `Tooltip` carrying `locations.list.siteOrdersHint`. This is the answer to D-24 — "the owner is never surprised by a pause that does nothing."
- **The inline "New location" create Card stays inline, unchanged in position** (this phase does not move location creation to A2 — only _edit_ moves per the locked decision). It gains one change: the free-text timezone `Input` (current `locations.tsx:174-184`, regex-validated, optional) is replaced by the same `TimezoneCombobox` component built for A2 (see below), and the field becomes **required**, not optional — this is the direct fix for BLOCK-1's "created with `timezone = null`" failure mode, applied at the point of creation, not only at edit time. Default value on the create form: `Intl.DateTimeFormat().resolvedOptions().timeZone` (D-04).
- **A brand-new location gets the default week (10:00–22:00 every day) applied automatically at creation, with no schedule-editing UI on the create form.** The operator adjusts afterward via A2's Opening Hours section. This satisfies D-01's guardrail ("never ship an empty-week form") without expanding the inline create Card into a second full schedule editor.

**`?location=all` behavior (D-21):** this page is `@LocationNeutral` already (`locations.controller.ts:86`) and is the one place a multi-location owner sees every location's state — read-only visibility here needs no special-casing; the pause popover on each row still targets that specific row's location id, satisfying "no write path requires `all`."

### A2 — NEW route `/{brandSlug}/locations/{locationId}` (edit page)

Does not exist today — confirmed no `PATCH` route, no edit form, `Location.archive()` is the aggregate's only mutator (`location.aggregate.ts:59`). This is the largest net-new surface in the phase.

**Layout:** a single scrolling page, four `Card`-wrapped sections in the locked order (Details → Opening hours → Date exceptions → Pre-orders), each with a `Heading` (20px/600/1.2) title using the `locations.edit.section*` keys. A `PageHeading` at the top: title = `locations.edit.title` ("Edit location"), no `action` slot needed (Save lives at the bottom).

**Save affordance:** a sticky bottom bar (`sticky bottom-0 border-t bg-background px-4 py-3 lg:px-6`, mirroring the existing sticky-top pattern already used by `OrderFilterBar` at `order-filter-bar.tsx:43`) containing the "Save changes" `Button` (primary, `h-12`) and, when there are unsaved edits, the `locations.edit.unsavedWarning` caption to its left. Single page-level save — no per-section save buttons, no autosave (this is a configuration surface per D-19, not the operational pause path).

**Section 1 — Details:** Name, Address, Phone, Email (existing fields, ported from the current inline create form) + **Timezone**, using the new `TimezoneCombobox`:

- Trigger: a `Button variant="outline"` styled like a `Select` trigger, showing the current zone or `locations.edit.timezonePlaceholder`.
- Popover content: `Command` with a search `CommandInput` (placeholder = `locations.edit.timezonePlaceholder`) and a `CommandList` sourced from `Intl.supportedValuesOf('timeZone')` (~418 entries at build time — verified in RESEARCH.md against this repo's Node runtime). Type-ahead filtering is `Command`'s built-in behavior; no virtualization needed at this list size.
- **Known, accepted gap (cite RESEARCH.md Pitfall 3):** a small number of newer IANA aliases (e.g. `Europe/Kyiv`) are absent from `supportedValuesOf()`'s enumeration even though the server accepts and correctly resolves them. The older alias (`Europe/Kiev`) is present in the list and resolves identically. Do not hand-maintain a superset list to close this gap — it is not worth the maintenance burden for a same-instant alias.
- If the location's stored `timezone` is `null` (legacy row, pre-migration edge case), the Opening Hours section below renders disabled with the `locations.edit.timezoneRequiredHint` caption in its place until a timezone is chosen and (client-side) staged — this should be rare to nonexistent post-backfill, but the UI must not let an operator save hours against an unset zone.

**Section 2 — Opening hours (the locked always-visible 7-row grid):**

- Seven rows, Monday first, each row: weekday label (fixed-width, left) → `Switch` "Closed" toggle (precedent: `order-filter-bar.tsx:98`) → interval 1 (`<input type="time">` open, en-dash, `<input type="time">` close) → **"Next day" badge** (`Badge variant="outline"`, copy `locations.edit.nextDayBadge`) that appears automatically, inline right after the close-time field, the instant the entered close value is numerically earlier than the open value (D-03's mandatory visible affordance — "the owner must never wonder whether 18:00–02:00 was accepted") → "+ interval" `Button` (ghost, small) that reveals interval 2's open/close pair plus a small "×" remove button, capped at 2 intervals per day per D-02.
- A "Copy Monday to all days" `Button` (outline, small) sits above the grid, aligned right. On click: copies Monday's toggle + intervals into all other 6 rows client-side (no request), then shows a `sonner` toast with `locations.edit.copiedToast` so the bulk change is confirmed, not silent.
- Row disabled state: when "Closed" is toggled on for a day, both interval fields (and "+ interval") in that row are disabled/hidden, matching the existing disabled-input visual language already used elsewhere in this app (`opacity-50`).
- Validation surfaces inline under the row, 14px/400, `text-destructive` (matches `locations.tsx:164,171,182,193` existing field-error styling) — e.g. `locations.edit.overlapError` if interval 2's open is before interval 1's close.

**Section 3 — Date exceptions:**

- A list (not a table — expected to be short, a handful of entries per year) of existing exceptions, each row: date (formatted, localized) → either "Closed all day" (`locations.edit.exceptionClosedLabel`) or its own mini interval pair (same `<input type="time">` fields as the weekly grid, max 2 intervals) → remove `Button` (ghost, `X` icon).
- "Add exception" `Button` (outline) appends a new row: a native `<input type="date" min={todayISO}>` (see Component Inventory — no `calendar` primitive) + a `Switch` "Closed all day" that, when off, reveals the same interval-pair inputs as above.
- Duplicate-date validation: `locations.edit.duplicateExceptionError`, shown inline under the offending row on save attempt (client-side pre-check against the in-memory list before hitting the server's own `.refine` on `LocationOrderingScheduleSchema`).
- Never recurring (D-06) — no "repeat annually" checkbox exists anywhere in this UI; do not add one.

**Section 4 — Pre-orders:**

### W3 — Checkout live state (`apps/website/components/checkout/checkout-form.tsx`)

New client hook, e.g. `apps/website/hooks/use-location-ordering-poll.ts`, porting the interval + `focus` + `visibilitychange` pattern verified at `apps/qr-menu/src/App.tsx:61-79`. Recommended interval: **10 seconds** (tighter than the menu banner's 5s edge-revalidate window and the qr-menu's 20s availability poll — checkout is the money-adjacent surface, D-13 calls for the screen to change "immediately," and 10s is a reasonable balance against hammering the `s-maxage=5` availability endpoint).

**The poll must run for the entire checkout lifecycle, including the `payment` stage** — not just while the contact-info form (`payment.stage === 'idle'`) is visible. This is the case the prompt explicitly flags: a guest already inside `StripePaymentElement` (`checkout-form.tsx:131-146`) must not be left there once the location has closed.

**Transition behavior on detecting a state change (open → paused/closed):**

1. Immediately swap the entire visible view to a shared `LocationUnavailableState` component (same one W5 uses — see below), regardless of which `PaymentState` stage the form was in.
2. If `payment.stage === 'payment'` (Stripe Elements mounted): unmount `StripePaymentElement` as part of the swap — do not wait for its own submit-time failure. The already-created `Order` (status `created`, unpaid) is simply abandoned; this matches D-17's accepted failure mode (an abandoned unpaid order, never a paid-but-invisible one).
3. **Cart contents are preserved** (the Zustand cart store is untouched — the guest can still navigate back to the menu or re-enter checkout). **In-progress contact-form field values (name/phone/email typed so far) are discarded**, not preserved across the swap — an accepted, deliberate simplification; re-typing three fields is cheap relative to the complexity of preserving `react-hook-form` state across a hard view swap.
4. **Screen-reader announcement (accessibility requirement):** the swap target must be wrapped in `role="status" aria-live="assertive"` (assertive, not polite — this is an involuntary interrupt of an in-progress purchase, not a passive update) so a screen-reader user learns immediately that the form they were filling in no longer works, and why.

## Accessibility Contract

- **Color is never the sole signal.** Every state chip, banner, and badge carries an explicit text label alongside its color treatment (see Color section).
- **Pause popover keyboard operation:** standard Radix `Popover` behavior — `Tab` cycles through the visible buttons, `Escape` closes and returns focus to the trigger chip, no custom focus-trap code needed.
- **7-row schedule grid keyboard order:** row-major — within each row, `Tab` order is Closed-toggle → open-time → close-time → (+interval, if not already expanded) → interval-2 open/close → remove-interval, then the next weekday row. Native `<input type="time">` and `<Switch>` both carry their own correct built-in keyboard semantics; no custom handling required. "Copy Monday to all days" is a single reachable button; its toast (`locations.edit.copiedToast`) doubles as the accessible confirmation that the bulk copy happened (screen readers pick up `sonner` toasts via its built-in live region — no extra work needed).
- **Slot picker keyboard operation:** the day selector inherits Radix `Tabs`' native arrow-key navigation within the tablist. Each slot button is a standard focusable `<button>` in normal tab order; the selected slot carries `aria-pressed="true"`.
- **Timezone combobox:** `Command`'s built-in type-ahead + arrow-key navigation + `Enter`-to-select; no custom keyboard handling needed. 418 entries render without virtualization at acceptable performance.
- **The W3 live checkout state swap must use `role="status" aria-live="assertive"`** on the replacement container — this is the one place in the phase where an involuntary, mid-task state change happens to a screen-reader user filling out a payment form, and it must be announced immediately, not silently. This is a hard requirement, not a nice-to-have — call it out specifically in the ui-checker pass for this phase.
- **Every new interactive control meets or exceeds the 48px (`h-12`) touch target** on the operator-facing (admin) surfaces per the Spacing exception above; guest-facing (website) controls follow the existing app's standard control heights (no smaller than the existing `Input`/`Button` defaults already in use).
