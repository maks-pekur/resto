# Phase 10.1: Location schedule and pause ordering - Research

**Researched:** 2026-08-18
**Domain:** Timezone-correct interval scheduling with no date library; HTTP caching correctness (ETag) under a time-varying resource; location-scoped write authorization
**Confidence:** HIGH — every claim below was verified by reading the cited file:line or by running a Node reproduction script against this repo's actual `zod`/`Intl` versions (Node v24.15.0 locally; repo requires >=22.22.1). Two persona-review claims were tested and corrected (see "State of the Art" and Pitfall 1).

## Summary

CONTEXT.md already locked storage shape, evaluation order, permissions, and context ownership — this research does not revisit those. What it resolves are the nine items CONTEXT.md left open, all of which are "how exactly" questions, not "what" questions.

The single highest-leverage finding: **the phase does not need the hard direction of timezone math (local wall-clock → UTC instant) for its core enforcement path at all.** `CreateOrderService`'s "is `now` open?" check only needs the easy direction (UTC instant → local weekday + minutes-since-midnight), which `Intl.DateTimeFormat.formatToParts` gives correctly and atomically, with no DST bug surface, in one call. The hard direction (needed only for "next opening instant" and pre-order slot generation) is a well-known fixed-point offset-probe algorithm; this document includes a tested implementation. No date library is needed, and none should be added.

Second finding of comparable weight: the persona reviews' claim that `zonedMidnightUtc` (`list-orders.service.ts:163-190`) is "already DST-fragile" was tested empirically against a full 2026 DST-transition sweep in two zones and **could not be reproduced for its actual purpose (single-day local-midnight computation)**. The real, confirmed, and precisely quantified bug is one level up: `resolveDateRange`'s composition of `zonedMidnightUtc` with naive `addDays()` (fixed 86,400,000ms) for the "yesterday" / "last 7 days" presets is off by exactly one hour on any query made within the lookback window of a DST transition. This is a pre-existing Phase 10 bug, out of this phase's scope to fix, but it is the concrete reason the new `ordering-window.policy.ts` must not reuse `zonedMidnightUtc` + `addDays` as a pattern — it must use per-instant `formatToParts`, never Date-object day arithmetic.

Third: the `scheduledFor` chain is not just theoretically broken as CONTEXT.md's D-15 states — it was reproduced with the repo's actual installed `zod` package. `z.string().datetime()` (no `offset` option) rejects every value the `datetime-local` input can currently produce, with zero exceptions. The clean fix is not "add an offset to the client string" — it's to stop asking the guest to type a time at all. Server-generates a slot list as UTC ISO instants (already valid against the untouched Zod schema); the guest picks one; the wire value the client echoes back was never guest-authored. This also answers the pre-order slot generation question and keeps all DST-sensitive math in one runtime (the API), never duplicated into the website.

Fourth: the path-param authorization hole (D-22) is real and was traced through the actual DI graph — `LocationPermissionChecker` is registered and exported but never bound to `PERMISSION_CHECKER`, and `PermissionsGuard` never reads `activeLocationId` at all. Wiring it "properly" is an app-wide behavioral change to the primary RBAC gate (every `@Permissions`-decorated route in the app), not a phase-local fix; the ~15-line service-level scope assertion D-22 prescribes is correctly scoped for this phase, and this research quantifies why the fourth deferral is the right call.

**Primary recommendation:** No new dependency. Implement `ordering-window.policy.ts` as a pure function using only `Intl.DateTimeFormat`; use the tested fixed-point offset-probe algorithm below wherever a local wall-clock needs to become a UTC instant (next-opening, slot generation); derive the availability ETag from the response body; generate pre-order slots server-side as ISO instants and remove the `datetime-local` free-text input entirely.

### Pattern 1: Forward-direction schedule matching (no DST bug surface)

**What:** Answer "is `at` inside this location's open interval?" using exactly one `Intl.DateTimeFormat.formatToParts` call, never a Date-object midnight anchor.
**When to use:** Every "is it open right now / at this scheduled instant" check — this is 100% of SCHED-04's enforcement need.
**Why this avoids the DST bug family:** `list-orders.service.ts:163-190`'s `zonedMidnightUtc` computes a `Date` representing "local midnight expressed as a UTC instant" and then does day-boundary arithmetic on it (`addDays`, fixed 86,400,000ms per day) — that composition is where the real, verified bug lives (see State of the Art). The schedule-matching operation needs no midnight anchor at all: it only needs "how many minutes past local midnight is this instant," which `formatToParts({hour,minute})` gives directly.

```typescript
// Source: verified by this research session against Node v24.15.0 / repo Intl
// data (ICU 78.2). Tested across 2026 US (Mar 8 / Nov 1) and EU (Mar 29 / Oct 25)
// DST transitions with a 15-minute sweep; zero incorrect classifications.

type Weekday = 'mon' | 'tue' | 'wed' | 'thu' | 'fri' | 'sat' | 'sun';
const WEEKDAY_ORDER: Weekday[] = [
  'mon',
  'tue',
  'wed',
  'thu',
  'fri',
  'sat',
  'sun',
];
// Intl 'short' weekday parts are 'Mon'..'Sun' in en-US — verified via formatToParts sweep.
const INTL_WEEKDAY_TO_KEY: Record<string, Weekday> = {
  Mon: 'mon',
  Tue: 'tue',
  Wed: 'wed',
  Thu: 'thu',
  Fri: 'fri',
  Sat: 'sat',
  Sun: 'sun',
};

interface LocalPoint {
  readonly weekday: Weekday;
  readonly minutesSinceMidnight: number; // 0..1439
}

function localPointAt(at: Date, timeZone: string): LocalPoint {
  const parts = new Intl.DateTimeFormat('en-US', {
    timeZone,
    hour12: false,
    weekday: 'short',
    hour: '2-digit',
    minute: '2-digit',
  }).formatToParts(at);
  const get = (t: string) => parts.find((p) => p.type === t)?.value;
  const hour = Number(get('hour'));
  const minute = Number(get('minute'));
  const weekdayLabel = get('weekday') ?? 'Mon';
  return {
    weekday: INTL_WEEKDAY_TO_KEY[weekdayLabel] ?? 'mon',
    minutesSinceMidnight: (hour === 24 ? 0 : hour) * 60 + minute,
  };
}

interface Interval {
  readonly open: number;
  readonly close: number;
} // minutes; close>1440 = crosses midnight

function isWithinToday(
  intervals: readonly Interval[],
  minutes: number,
): boolean {
  return intervals.some(
    (iv) => minutes >= iv.open && minutes < Math.min(iv.close, 1440),
  );
}

function isWithinYesterdaysOvernightSpillover(
  yesterdaysIntervals: readonly Interval[],
  minutes: number,
): boolean {
  return yesterdaysIntervals.some(
    (iv) => iv.close > 1440 && minutes < iv.close - 1440,
  );
}

function isOpenByWeeklySchedule(
  week: Record<Weekday, readonly Interval[]>,
  at: Date,
  timeZone: string,
): boolean {
  const { weekday, minutesSinceMidnight } = localPointAt(at, timeZone);
  const todayIdx = WEEKDAY_ORDER.indexOf(weekday);
  const yesterday = WEEKDAY_ORDER[(todayIdx + 6) % 7] as Weekday;
  return (
    isWithinToday(week[weekday], minutesSinceMidnight) ||
    isWithinYesterdaysOvernightSpillover(week[yesterday], minutesSinceMidnight)
  );
}
```

This handles overnight crossing (18:00→02:00 stored as `{open:1080, close:1560}`) and both DST transitions with zero special-casing — because `formatToParts` already returns the correct post-jump wall clock (verified: `formatToParts` at `2026-03-08T06:59:59Z` → 119 minutes, at `2026-03-08T07:00:00Z` → 180 minutes, i.e. the US spring-forward gap is silently and correctly skipped by the platform's own ICU data).

### Pattern 2: Reverse-direction conversion (local wall-clock → UTC instant), fixed-point offset probe

**What:** Given a target local wall-clock in zone `Z`, find the UTC instant that formats back to it.
**When to use:** Only for "next opening instant" (`reopensAt`, needed by D-08's "until next opening" and D-16's problem-details body) and pre-order slot generation (Open Q2). NOT needed for the "is it open now" check (Pattern 1 covers that).

```typescript
// Source: tested in this research session. The critical correctness detail —
// missed in a first draft — is that each iteration must re-derive from the
// ORIGINAL naive target (`naive`), not from the previous guess. Iterating
// against the previous guess diverges near a transition instead of converging.

function localToUtc(
  y: number,
  month: number,
  day: number,
  hour: number,
  minute: number,
  timeZone: string,
): { utc: number; gapOrAmbiguous: boolean } {
  const naive = Date.UTC(y, month - 1, day, hour, minute, 0);
  let guess = naive;
  for (let i = 0; i < 4; i++) {
    const asIfUtc = wallClockAsUtcMillis(guess, timeZone); // format `guess` in TZ, re-parse as UTC numbers
    const offsetMs = asIfUtc - guess;
    const next = naive - offsetMs; // <-- always subtract from `naive`, never from `guess`
    if (next === guess) return { utc: guess, gapOrAmbiguous: false };
    guess = next;
  }
  // Did not converge in 4 iterations: `naive` falls inside a spring-forward
  // gap (the target wall-clock literally never occurs that day). Returning
  // the last guess (nearest valid instant before the gap) is an accepted,
  // documented MVP limitation — see Common Pitfalls #2.
  return { utc: guess, gapOrAmbiguous: true };
}

function wallClockAsUtcMillis(ms: number, timeZone: string): number {
  const parts = new Intl.DateTimeFormat('en-US', {
    timeZone,
    hour12: false,
    year: 'numeric',
    month: '2-digit',
    day: '2-digit',
    hour: '2-digit',
    minute: '2-digit',
    second: '2-digit',
  }).formatToParts(new Date(ms));
  const get = (t: string) =>
    Number(parts.find((p) => p.type === t)?.value ?? '0');
  const hour = get('hour');
  return Date.UTC(
    get('year'),
    get('month') - 1,
    get('day'),
    hour === 24 ? 0 : hour,
    get('minute'),
    get('second'),
  );
}
```

Verified empirically (America/New_York, spring-forward 2026-03-08 07:00Z, gap 02:00–03:00 local):

| Target local | Result                             | Notes                                                                                                           |
| ------------ | ---------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 01:30        | `2026-03-08T06:30:00Z` (01:30 EST) | converges, `gapOrAmbiguous: false`                                                                              |
| 02:30        | `2026-03-08T06:30:00Z` (01:30 EST) | does **not** converge — correctly flagged `gapOrAmbiguous: true`, falls back to the last instant before the gap |
| 03:30        | `2026-03-08T07:30:00Z` (03:30 EDT) | converges, `gapOrAmbiguous: false`                                                                              |

Fall-back repeated hour (2026-11-01, 01:00–02:00 local occurs twice): the algorithm deterministically resolves to the **earlier** occurrence (the one still in DST) because it uses the naive target's own offset as its starting guess. This is a documented, consistent choice — since this phase only ever _generates_ candidate instants (never parses free-text guest input), there is no ambiguous-user-intent problem to solve; determinism is all that's required.

### Pattern 3: Composite (body-derived) ETag, verified against the real controller

**What:** Replace `etag = '"' + stopVersion + '"'` with a value that changes whenever the _response body_ changes, not just when a stop-list write happens.
**Verified against:** `public-menu.controller.ts:150-168` (confirmed unchanged since CONTEXT.md was written) and `catalog-drizzle.repository.ts:828-840` (`#bumpStopVersion`, the only writer of `stopVersion`).

```typescript
// Source: apps/api/src/contexts/catalog/interfaces/http/public-menu.controller.ts:154-168
// (current code — the fix is a 3-line change to the etag construction)
async availability(
  @Res({ passthrough: true }) reply: FastifyReply,
  @Headers('if-none-match') ifNoneMatch?: string,
): Promise<AvailabilityResponse | undefined> {
  requireTenantOr404();
  requireBrandOr404();
  const result = await wrap(() => this.getAvailability.execute());
  // BEFORE: const etag = '"' + result.stopVersion.toString() + '"';
  // AFTER — composite key so a schedule/pause state change (no stop-list
  // write) still changes the ETag:
  const etag =
    '"' +
    [
      result.stopVersion,
      result.ordering.state,               // 'open' | 'paused' | 'closed'
      result.ordering.pausedUntilEpoch ?? 0,
      result.ordering.reopensAtEpoch ?? 0,
    ].join('.') +
    '"';
  if (ifNoneMatch === etag) {
    reply.status(304);
    return undefined;
  }
  reply.header('ETag', etag);
  reply.header('Cache-Control', 'public, s-maxage=5'); // unchanged
  return result;
}
```

**Does a body-derived ETag still let a 304 be served correctly?** Yes — 304 is exactly "the client's cached copy is still current," which is precisely what an unchanged `stopVersion.state.pausedUntil.reopensAt` tuple means. This is _more_ correct than the current write-counter-only ETag, not less: it now also correctly issues a **fresh 200** the instant any of those fields changes, including the pure-clock transitions (`state` flips at a schedule boundary, or `pausedUntilEpoch` expires) that today produce a false 304 forever.

**Interaction with `s-maxage=5`:** none, negatively. The CDN still only re-validates with the origin every 5 seconds at most (that bound is unchanged); the fix only affects what happens _at_ that 5-second re-validation — today it can wrongly answer 304 (stale-forever within the ETag's lifetime), after the fix it correctly answers 200 whenever the tuple changed. Worst-case staleness is still bounded by `s-maxage=5`, now honestly.

Do **not** bump `catalog_location_stop_version` from a tenancy write path — confirmed at `packages/db/src/schema/menu.ts:414`, that counter is catalog-owned; reaching into it from `tenancy`'s pause/resume service would invert the context boundary CTO flagged. The composite ETag needs no shared counter at all.

### Pattern 4: The path-param authorization fix (D-22), traced through the real DI graph

**Verified:** `LocationScopeGuard` (`location-scope.guard.ts:39-85`) only ever reads `getLocationId()` — the ALS-bound location from the `x-location-id` header — and returns `true` unconditionally when `@LocationNeutral()` is present (confirmed at line ~30, before any location logic runs). `LocationsController` is `@LocationNeutral()` at line 86. `PermissionsGuard` (`permissions.guard.ts:30-56`) calls `this.checker.hasPermission(principal, required, headers)` — **three arguments, no `activeLocationId`** — against whatever is bound to `PERMISSION_CHECKER`, which `identity-core.module.ts:345-347` binds unconditionally to `BetterAuthPermissionChecker` (org-wide, zero location concept). `LocationPermissionChecker` (`location-permission-checker.ts`) is registered and exported from `IdentityCoreModule` (lines 370, 385) but **is never bound to `PERMISSION_CHECKER` and never `@Inject`-ed anywhere else in the codebase** — confirmed via a full-repo grep. ### Anti-Patterns to Avoid

- **Reusing `zonedMidnightUtc` + `addDays` for schedule matching:** avoids the bug this research found (see State of the Art), but more importantly is simply unnecessary complexity — Pattern 1 needs no midnight anchor at all.
- **Building the reverse-direction (Pattern 2) logic twice, once server-side and once in `apps/website`:** duplicates the hardest part of this phase across two runtimes for no reason — see Open Q2/Pattern 2's "server generates, client displays" resolution.
- **A dispatching-per-permission composite `PermissionChecker`** as a phase-local fix for D-22 — correctly scoped as a _future_, app-wide change (Pattern 4), not this phase's problem.
- **`Intl.supportedValuesOf('timeZone').includes(input)`** as the sole timezone validator — verified to falsely reject valid current IANA names not yet reflected in this Node build's `supportedValuesOf()` enumeration (see Open Q4).

## Common Pitfalls

### Pitfall 1: Believing `zonedMidnightUtc` itself is DST-broken (it isn't, for its actual job)

**What goes wrong:** Both persona reviews assert `zonedMidnightUtc` "samples the UTC offset at UTC midnight... on a DST-transition day... the returned local midnight is an hour off," and recommend against reusing it. Taken as "don't reuse this pattern for the new policy," that recommendation is correct — but taken as "the function computes a wrong answer," it is not.
**What was actually tested:** A 15-minute-resolution sweep of `zonedMidnightUtc(reference, tz)` against an independently-implemented, verified fixed-point local-midnight computation, across the full 2026 US (Mar 8 spring-forward, Nov 1 fall-back) and EU (Mar 29 spring-forward, Oct 25 fall-back) transition days, in `America/New_York` and `Europe/Berlin`. **Zero mismatches.** The single-instant offset-probe-at-UTC-midnight strategy happens to be safe for any zone whose transition rule fires well away from the UTC-midnight-to-local-midnight window (true for the standard 1am/2am/3am local transition rules used almost universally).
**The real, confirmed bug:** `resolveDateRange`'s `addDays(todayStart, -1)` / `addDays(todayStart, -6)` (fixed `days * 86,400,000` ms) for the "yesterday" and "last 7 days" order-feed presets. Reproduced concretely: querying "yesterday" on 2026-03-09 (the day after the US spring-forward) returns a lower boundary of `2026-03-07T23:00 EST` instead of the correct `2026-03-08T00:00 EST` — a 60-minute error, because the spring-forward day was 23 hours, not 24, and `addDays` doesn't know that.
**Why it matters for this phase:** it is the concrete, evidence-based reason to reject the "just reuse `zonedMidnightUtc`" temptation — not because the function itself is wrong, but because its natural composition pattern (`+/- N days` via millisecond arithmetic) is. Pattern 1/2 above avoid this by construction (no Date-object day arithmetic anywhere).
**Warning signs:** any new code that does `new Date(someLocalMidnight.getTime() + N * 86400000)` — that literal pattern is where this bug family lives.

### Pitfall 2: The spring-forward gap in "next opening instant" / slot generation

**What goes wrong:** If a schedule's open time literally falls inside a spring-forward gap on a transition day (e.g., open=02:15 on the one day of the year that jumps 02:00→03:00), Pattern 2's fixed-point loop will not converge.
**How to avoid (accepted MVP scope, per CTO's own reject list):** the function already detects this (`gapOrAmbiguous: true`) rather than looping forever or throwing. For MVP, treat a non-converging result as "use the last guess" (the nearest valid instant before the gap) and do not build further handling — restaurants opening at 2am is not a real scenario, and CTO's over-engineering reject list already excludes building for this.
**Warning signs:** a unit test asserting `evaluate()` for a schedule with an open/close time inside 00:00–04:00 on a known transition date does not crash and returns a deterministic (if slightly early) result.

### Pitfall 3: `Intl.supportedValuesOf('timeZone')` is the wrong validation gate

**What goes wrong:** Using `Intl.supportedValuesOf('timeZone').includes(input)` as the accept/reject test for a location's timezone. Verified: on this repo's Node build (ICU 78.2), `Europe/Kyiv` (the post-2022 canonical IANA name Ukraine requested) is **absent** from `supportedValuesOf()`'s 418-entry list, while the older alias `Europe/Kiev` **is** present — yet `new Intl.DateTimeFormat('en-US', { timeZone: 'Europe/Kyiv' })` **succeeds** at runtime (silently resolving to the same underlying rule as `Europe/Kiev`). A validator built on `supportedValuesOf()` would reject a perfectly valid, currently-correct timezone name a Russian/Ukrainian-market restaurant owner might reasonably pick from a modern timezone-picker UI component.
**Why it happens:** `supportedValuesOf('timeZone')` enumerates canonical zone names as bundled by this Node/ICU version; it lags behind tzdata alias updates. `Intl.DateTimeFormat`'s constructor, however, resolves through the full alias table, which is a superset.
**How to avoid:** validate with `try { new Intl.DateTimeFormat(undefined, { timeZone: input }); return true } catch { return false }` — confirmed this correctly accepts `Europe/Kyiv`, `Europe/Kiev`, `Etc/UTC`, `UTC`, and `America/Argentina/Buenos_Aires`, and correctly rejects `Foo/Bar` (throws `RangeError: Invalid time zone specified: Foo/Bar`).
**Bonus, separately confirmed bug in the existing regex:** `location.aggregate.ts:14`'s `/^[A-Za-z_]+\/[A-Za-z_]+$/` requires _exactly one_ slash — it currently rejects valid three-segment IANA names like `America/Argentina/Buenos_Aires` even though `Intl.DateTimeFormat` accepts them fine. This is a second, independent bug beyond the `Foo/Bar` false-accept CONTEXT.md already flagged. The try/catch replacement fixes both at once.
**Warning signs:** a timezone picker in the admin UI populated from `supportedValuesOf()` (fine, for display/search) whose selected value is then re-validated against a _different, stricter_ rule server-side — the mismatch is exactly this trap.

### Pitfall 4: Assuming a location UPDATE endpoint is a small addition

**What goes wrong:** SCHED-03's phrasing ("operator sets a weekly opening schedule") reads like a config field, but there is no PATCH/update path on `Location` anywhere in the codebase today. Verified: `LocationsController` exposes exactly `POST /` (create), `GET /` (list), `PATCH /:id/archive` (line 96/110/120) — no general update. `Location.archive()` (line 59) is the aggregate's only mutator. `apps/admin/src/lib/queries/locations.ts:66,73` has exactly `createLocationMutation` and `archiveLocationMutation`. This is the bulk of the phase's implementation surface and is easy to underestimate from the requirement text alone.
**How to avoid:** size the plan explicitly for: one new aggregate-mutator-carrying `update()` method (name/address/timezone/contacts), a `PATCH /v1/tenancy/locations/:id` endpoint, and a full admin edit form — in addition to the pause/resume pair and the schedule editor.

### Zod schema for `ordering_schedule` (JSONB), following the `packages/domain` value-object convention

Verified convention source: `packages/domain/src/brand-theme.ts` (`.strip()`, docstring above the schema, HTTP-boundary-vs-domain split pattern) and `packages/domain/src/money.ts` (branded/unbranded pair pattern). This schema is **API-local** (lives in `location.aggregate.ts` alongside `LocationTimezone`/`LocationContactsSchema`), not promoted to `packages/domain`, matching where the sibling value objects already live.

```typescript
// apps/api/src/contexts/tenancy/domain/location.aggregate.ts (new section)
// weekday key order matches Intl's 'short' weekday parts, lowercased —
// verified via Intl.DateTimeFormat({weekday:'short'}) sweep: Mon..Sun.
const WEEKDAY_KEYS = ['mon', 'tue', 'wed', 'thu', 'fri', 'sat', 'sun'] as const;

// D-03: close > 1440 means "crosses into the next calendar day". A single
// interval cannot exceed 24h (that would require a third day, out of scope).
const ScheduleIntervalSchema = z
  .object({
    open: z.number().int().min(0).max(1439),
    close: z.number().int().min(1).max(2879),
  })
  .strip()
  .refine((v) => v.close > v.open, { message: 'close must be after open' })
  .refine((v) => v.close - v.open <= 1440, {
    message: 'an interval cannot exceed 24h',
  });

// D-02: up to two intervals per weekday; [] = closed that day.
const DayIntervalsSchema = z
  .array(ScheduleIntervalSchema)
  .max(2, 'at most two intervals per day')
  .refine(
    (ivs) => ivs.length < 2 || (ivs[1]?.open ?? 0) >= (ivs[0]?.close ?? 0),
    { message: 'intervals must not overlap' },
  );

const WeeklyScheduleSchema = z
  .object(
    Object.fromEntries(
      WEEKDAY_KEYS.map((k) => [k, DayIntervalsSchema]),
    ) as Record<(typeof WEEKDAY_KEYS)[number], typeof DayIntervalsSchema>,
  )
  .strip();

// D-05/D-06: one-off dated overrides, never recurring. `closed: true` needs
// no intervals; `closed: false` requires at least one.
const DateExceptionSchema = z.discriminatedUnion('closed', [
  z
    .object({
      date: z.string().regex(/^\d{4}-\d{2}-\d{2}$/),
      closed: z.literal(true),
    })
    .strip(),
  z
    .object({
      date: z.string().regex(/^\d{4}-\d{2}-\d{2}$/),
      closed: z.literal(false),
      intervals: DayIntervalsSchema,
    })
    .strip()
    .refine((v) => v.intervals.length > 0, {
      message: 'open exception needs at least one interval',
    }),
]);

// `version` makes a future schema widening (e.g. split-shift limits, named
// recurring closures) an explicit, discriminated migration point rather than
// a silent shape change — the read path can branch on `version` if it ever
// needs to.
export const LocationOrderingScheduleSchema = z
  .object({
    version: z.literal(1),
    week: WeeklyScheduleSchema,
    exceptions: z.array(DateExceptionSchema).max(366), // defensive cap, one calendar year
  })
  .strip()
  .refine(
    (v) =>
      new Set(v.exceptions.map((e) => e.date)).size === v.exceptions.length,
    { message: 'duplicate exception date' },
  );
export type LocationOrderingSchedule = z.infer<
  typeof LocationOrderingScheduleSchema
>;
```

Validation deliberately does **not** reject a past exception date — a past date can never match a future/`now` evaluation, so rejecting it adds a clock-dependent validation rule for no behavioral benefit (and would make the schema non-deterministic to test).

### Pre-order slot generation — server-generates, client displays (resolves Open Q2 and Open Q8 together)

**Where:** `catalog`'s `GetMenuAvailabilityService` (the response the client already polls), reusing Pattern 2's `localToUtc`. **Not** a separate endpoint (matches CTO's "don't add a fourth poller" and CONTEXT's cache-safety framing — this rides the existing `s-maxage=5` response).

```typescript
// apps/api/src/contexts/catalog/application/get-menu-availability.service.ts (extended)
function generateSlots(
  schedule: LocationOrderingSchedule,
  timeZone: string,
  leadMinutes: number,
  horizonDays: number, // D-15: 7
  granularityMinutes: number, // 15 — matches independent-restaurant service pacing
  now: Date,
): string[] /* ISO instants, UTC, already valid against dto.ts's untouched z.string().datetime() */ {
  const earliest = new Date(now.getTime() + leadMinutes * 60_000);
  const slots: string[] = [];
  for (let dayOffset = 0; dayOffset <= horizonDays; dayOffset++) {
    const { y, m, d } = localCalendarDatePlusDays(now, timeZone, dayOffset); // pure Y/M/D arithmetic, no DST risk
    const weekday =
      WEEKDAY_KEYS[(new Date(Date.UTC(y, m - 1, d)).getUTCDay() + 6) % 7];
    for (const interval of resolveIntervalsFor(schedule, weekday, y, m, d)) {
      for (
        let minute = interval.open;
        minute < Math.min(interval.close, 1440);
        minute += granularityMinutes
      ) {
        const { utc, gapOrAmbiguous } = localToUtc(
          y,
          m,
          d,
          Math.floor(minute / 60),
          minute % 60,
          timeZone,
        );
        if (gapOrAmbiguous) continue; // Pitfall 2 — skip, don't crash
        if (utc >= earliest.getTime()) slots.push(new Date(utc).toISOString());
      }
    }
  }
  return slots;
}
```

**Client side (`apps/website`):** `order-time-selector.tsx` stops rendering `<Input type="datetime-local">` and instead renders a `<Select>` populated from `availability.candidateSlots` (already fetched for the closed/paused banner — D-13). The value the client submits as `scheduledFor` is a slot string it received from the server, unmodified — this automatically satisfies `dto.ts:34`'s existing `z.string().datetime()` validator (which requires a `Z`-suffixed UTC instant) with **zero change to that Zod schema**. This was verified against the repo's installed `zod`:

```
$ node -e "const {z}=require('zod'); console.log(z.string().datetime().safeParse('2026-08-20T18:30').success)"
false   // current datetime-local output — always rejected, confirmed
$ node -e "const {z}=require('zod'); console.log(z.string().datetime().safeParse('2026-08-20T18:30:00Z').success)"
true    // server-generated slot format — always accepted
```

[VERIFIED: executed against `apps/api`'s installed `zod` dependency, 2026-08-18]

**Cache-safety given `s-maxage=5`:** the slot list is a pure function of `(schedule, timezone, leadMinutes, now)` — no DB write, no per-request randomness. A CDN serving a 5-second-stale slot list means, at most, a guest sees candidate times computed up to 5 seconds ago; since granularity is minutes, this has no observable effect. Payload cost: 7 days × ~2 intervals × ~(4h+5h)/15min ≈ 250 ISO strings ≈ 6KB — negligible against the 5-second TTL.
