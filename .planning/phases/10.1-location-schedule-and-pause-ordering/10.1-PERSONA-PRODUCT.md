# Phase 10.1 — Product Strategist Scope Review

**Reviewer:** `persona-product-strategist`
**Date:** 2026-08-18
**Type:** discuss-phase scope/shape review (pre-planning). Not a code review.
**Origin of phase:** my own BLOCK-3 at `/gsd:discuss-phase 10` (`.planning/phases/10-admin-order-intake/10-PERSONA-PRODUCT.md:50-62`).

---

## TL;DR

1. The phase as scoped is **right in intent and under-specified in three places that will each cost a re-migration or a broken week-one demo**: no location timezone edit path, a permission model that makes pause owner-only, and a feed header that does not render for the multi-location owner.
2. **Pre-orders are the single highest-value product decision in this phase.** The checkout already ships a scheduled-time picker, and SCHED-04's literal wording would reject a Tuesday order for Friday dinner. That turns a bounce into a lost high-intent order. Enforcement must key on the *fulfillment* time, not `now`.
3. **Cut split shifts and holiday calendars; do NOT cut a one-off "closed until \<date\>".** The cheapest form of the latter is one extra option in the pause popover reusing the same column. Without it, an operator's only tool for a public holiday is to edit their weekly schedule and remember to change it back — they will not, and they will be silently closed the following week.

## BLOCK findings

### BLOCK-1 — `locations.timezone` is nullable, unset by default, and has **no edit path**. A weekly schedule is unenforceable until this is fixed.

**Evidence.**
- `packages/db/src/schema/brands.ts:133` — `timezone: text('timezone')`, nullable, no default.
- `apps/api/src/contexts/tenancy/interfaces/http/locations.controller.ts:48` — `timezone: LocationTimezone.nullable().default(null)`. The controller exposes `@Post()` (`:96`), `@Get()` (`:110`), `@Patch(':id/archive')` (`:120`) — **there is no update route at all**.
- `apps/admin/src/routes/(protected)/$brandSlug/locations.tsx:38-44` — free-text field with an IANA regex, `.optional()`, no picker, no default, and the page has create + archive only.
- `apps/api/src/contexts/ordering/application/create-order.service.ts:182` — `const timeZone = rows[0]?.timezone ?? 'UTC';`. Same silent fallback at `list-orders.service.ts:146`.

**Consequence.** Every location created before this phase — including the first paying customer's, created during onboarding by someone who left an optional field blank — has `timezone = null`. A schedule saying "closes 23:00" evaluated in UTC closes a Moscow kitchen at 02:00 local and a Lisbon kitchen at midnight. And the operator **cannot fix it**: there is no PATCH endpoint and no edit form. This is the exact class of bug BLOCK-3 was written to prevent, re-created by the feature meant to prevent it.

**Plannable.**
- `PATCH /v1/tenancy/locations/:id` (name / address / timezone / contacts) + an admin location edit form with a real timezone `<Select>` defaulting to `Intl.DateTimeFormat().resolvedOptions().timeZone`.
- Treat "location has no timezone" as an **explicit blocking state in the schedule UI** ("Set this location's timezone before setting hours"), never a silent UTC fallback.
- Decide in this phase whether `timezone` becomes NOT NULL with a backfill. Do not carry a nullable timezone past the first schedule.

### BLOCK-2 — If pause is gated on `location:update`, it becomes owner-only. The owner is not the person standing at the pass.

**Evidence.**
- `packages/domain/src/rbac/system-roles.ts:14` owner `location: ['read','create','update','delete']`; `:27` admin `location: ['read']`; `:33` staff `location: ['read']`.
- `packages/domain/src/rbac/preset-roles.ts:13-21,27-32,38-42` — `manager`, `cashier-foh`, and `kitchen` have **no `location` key at all**.
- The feed those three roles *do* reach is gated `order: ['read']` / `order: ['update-status']` — `apps/api/src/contexts/ordering/interfaces/http/operator-orders.controller.ts:58,90,102,126`.

**Consequence.** Everyone who can see the flood would be forbidden from stopping it. This is a verbatim regression of the bug Phase 10 D-06 was written to fix ("the only person who can refuse an order at 20:40 on a Friday is the owner"), reintroduced one phase later on a different resource.

**Plannable.** Two permissions, two half-lives:
- **Pause / resume → `order: ['update-status']`** (matches the original spec at `10-PERSONA-PRODUCT.md:59`). It is a shift-level operational action.
- **Weekly schedule edit → `location: ['update']`** (owner) or `settings: ['update']` (owner/admin/manager — `system-roles.ts:9,23`, `preset-roles.ts:19`). It is a configuration action.
Do not conflate them into one gate.

### BLOCK-3 — "Pause control in the order-feed header" is invisible to a multi-location owner, because the feed does not render in `?location=all`.

**Evidence.** `apps/admin/src/routes/(protected)/$brandSlug/orders.tsx:105-106` — `const feedLocationId = mode === 'all' ? undefined : locationId;`; `:118` `enabled: feedLocationId !== undefined`; `:202-207` renders the `empty.pickLocationTitle` state instead of a feed. Recent commit `83e28a13` deliberately scoped the feed to one location. `showLocationBadge` is hardcoded `false` at `:154`.

**Consequence.** ROADMAP success criterion 4 for this phase — "an owner in `?location=all` mode can see and set it per location" — is **not satisfiable** with the placement the phase specifies. A two-location owner sits in `all`, sees "pick a location", and has no pause control anywhere.

**Plannable — decide before planning, do not delegate.** Recommended: the **locations page is the home of location state** (per-row chip: Accepting / Paused until 21:20 / Closed · opens 11:00, with the pause menu on the row), and the feed header carries a *mirror* one-tap chip when a single location is selected. This makes the multi-location story coherent, gives the schedule editor a natural home (it needs a page, not a header), and is cheaper than teaching the feed to render in `all`.

## HIGH findings

### HIGH-1 — Pre-orders while closed: enforce against the **fulfillment** time, not `now`. This is the difference between a bounce and revenue.

**Evidence.** `apps/website/components/checkout/checkout-form.tsx:93` already sends `scheduledFor`. `apps/api/src/contexts/ordering/application/dto.ts:33-39` carries the deferral explicitly: `// ORD-12: no operating-hours source exists yet — accept any future datetime; schedule validation deferred.` This phase is that deferral coming due.

**The product call.** SCHED-04 says "orders attempted outside opening hours are rejected." Read literally, that rejects a Tuesday-morning order for Friday dinner — killing exactly the highest-intent, highest-value order type, and doing it *at the moment* the guest has decided to buy.

**Plannable.**
- ASAP order → require `now` inside an open interval **and** not paused.
- Scheduled order → require the **requested slot** inside an open interval; **ignore pause entirely** (pause is a *now* concept; it must not reject a Saturday pre-order). Require a minimum lead time.
- Both branches go through the one chokepoint at `create-order.service.ts:43`.

### HIGH-2 — The scheduled-order path appears to be **broken today**; this phase inherits it.

**Evidence chain.** `order-time-selector.tsx:38-45` renders `<Input type="datetime-local">`, which emits `2026-08-20T20:30` — no seconds, no `Z`, no offset. `checkout-schema.ts:7` accepts it as `z.string().min(1)`. `checkout-form.tsx:93` forwards it verbatim. `dto.ts:34` validates it with `z.string().datetime()`, whose zod default requires a UTC `Z` suffix.

**Consequence.** Any guest choosing "Schedule for later" plausibly gets a 400 that renders as a generic red error (see MED-3). Planner must verify this with one request before designing on top of it — HIGH-1's whole value proposition sits on this path. Fix is small (normalize to ISO+offset in the form, or relax the DTO and interpret in the location timezone) but must be explicit: a bare local datetime interpreted server-side is a second timezone bug in the same phase.

### HIGH-3 — The guest "closed" signal has no live channel on the website, and the existing channel's ETag will not move when a clock crosses a boundary.

**Evidence.**
- `apps/api/src/contexts/catalog/interfaces/http/public-menu.controller.ts:160-168` — `etag = '"' + stopVersion + '"'`, `Cache-Control: public, s-maxage=5`, and `if (ifNoneMatch === etag) → 304`.
- `apps/api/src/contexts/catalog/application/get-menu-availability.service.ts:30` already resolves the **same default location** as `create-order.service.ts:47` — it is exactly the right carrier, for free.
- But `apps/website/lib/api-client.ts:38-49` fetches availability **once, server-side, at RSC render** (`next: { revalidate: 5 }`), and `apps/website/app/page.tsx:44-48` passes `stoppedItemIds` down as a static prop. There is **no client-side re-poll on the website** — contrast `apps/qr-menu/src/App.tsx:61-79`, which polls on interval + `focus` + `visibilitychange`.

**Consequence.** A guest with the tab open at 22:58 still sees an open checkout at 23:05. Worse: `stopVersion` is a *write*-driven counter, and open/closed is a *clock*-driven state — piggyback naively and a polling client receives `304` forever across the closing boundary and never learns the venue closed.

**Plannable.**
- Extend `GET /v1/menu/availability` with `{ ordering: { state: 'open'|'paused'|'closed', reopensAt, reason } }`.
- ETag must incorporate a coarse time bucket (e.g. `stopVersion` + `floor(now/60s)`) or the next state-transition timestamp. Otherwise the 304 path lies.
- Website polls it client-side (port the qr-menu pattern) or, minimally, re-checks on the cart → checkout transition.
- State explicitly in the phase doc: **`CreateOrderService` is the only real gate; the client copy is UX.** That stops anyone over-engineering the cache to be authoritative.

### HIGH-4 — "Rest of day" is undefined without a schedule, and it must reuse the business-day boundary that already exists in code.

**Evidence.** `create-order.service.ts:178-199` `resolveBusinessDate()` derives a calendar date in the location timezone — an implicit **midnight** boundary — and it already drives the per-location daily short number via `orderSequence.nextShortNumber({ businessDate })` (`:133-137`). Same logic duplicated at `list-orders.service.ts:144-146`.

**Consequence.** A bar closing at 02:00 already has its order numbers reset mid-service. If "pause rest of day" also resolves to local midnight, it silently **un-pauses a closed venue at 00:00** and reopens ordering for the two deadest hours. Overnight closes are not an edge case for the late-night/bar segment — they are the norm, and that segment is disproportionately likely to buy online ordering.

**Plannable.** Define **one** business-day boundary in this phase and have the schedule, "rest of day", and `resolveBusinessDate()` all use it. Minimum viable: allow a day's `closes_at < opens_at` (read as "next day"), and define "rest of day" as "until the next scheduled open", falling back to local midnight only when no schedule exists.

### HIGH-5 — Ship one interval per day; make the **storage shape** accommodate split shifts or you re-migrate.

**Week-one reality.** Per-day open/close plus closed days covers most independents. Lunch + dinner split (12:00–15:00, 18:00–23:00) is genuinely common in this segment and is the first thing requested after "closed Mondays".

**Plannable.** Model as **rows** — `location_schedule(location_id, tenant_id, weekday, opens_at, closes_at)`, a set per weekday — not as columns on `locations` (`mon_open`, `mon_close`, …). The row shape costs nothing extra now; the column shape is a migration later. Ship the **UI** as one interval per weekday with an "add second interval" affordance that may be cut for delivery speed without touching storage.

### HIGH-6 — A one-off "closed until \<date\>" is NOT gold-plating and must not be cut.

**Reasoning grounded in the model.** After this phase, an operator's only escape hatches are (a) pause for ≤ rest-of-day, and (b) edit the weekly schedule. For a public holiday, a staff illness, or a two-day refurb, the only tool is *edit the recurring schedule and remember to change it back*. They will forget. The product will then keep them closed the following Tuesday, silently, and they will not know why orders stopped. That is product-caused revenue loss and a churn story.

**Plannable — cheapest possible form.** Not a holiday calendar. Extend the pause upper bound: durations `20m / 40m / rest of day / until I resume` **plus** a "closed until \<date\>" variant writing the same `paused_until` column with a different reason. One extra option in the same popover, zero new tables, zero new enforcement code. If something must be cut to fit, cut split shifts (HIGH-5), not this.

## MED findings

### MED-1 — Per-fulfillment-mode pause: **scope-boundary finding — do not build the UI here, but reserve the column.**

Real kitchens stop delivery while keeping pickup (driver shortage, weather); Square supports exactly this per-fulfillment pause. The website already forces a mode choice before browsing (`apps/website/components/menu/delivery-pickup-banner.tsx:10-38`) and `orders.fulfillment_mode` is `('dine_in','pickup','delivery')` (`packages/db/src/schema/ordering.ts:90-92`).

**But** RestOS has no delivery *execution* in MVP-1 — Phase 9 Delivery Zones is MVP-2 — so "stop delivery" has no operational counterpart yet. **Recommendation:** add `paused_modes text[] null` (null = all modes) to the pause state now, default null, and have `CreateOrderService` read it. One nullable column, no UI, no decision surface. That makes Phase 9 additive instead of a migration against live pause data.

### MED-2 — Auto-resume, derived from `paused_until`. No cron, no confirmation dialog.

A pause requiring manual resume becomes a permanently-closed restaurant the first time a shift ends mid-pause. Recommendation: `paused_until timestamptz null` + `pause_reason text null` on `locations`; state is **derived at read time**, never a flag flipped by a background job — which removes the need for any scheduler in this phase. Feed/locations chip shows a live countdown; at expiry it flips to "Accepting orders" with a brief highlight. The second action next to "Resume now" should be **"+20 min"** — extending is what operators actually press.

### MED-3 — The rejection needs a distinct problem code carrying `reopensAt`, or the guest sees a generic red error.

`apps/website/components/checkout/checkout-form.tsx:104-107` collapses every failure into `{ stage: 'error', message }` with a single "Try again" button (`:149-177`). `CheckoutApiError` does carry `code` (`apps/website/lib/checkout-api.ts`), but nothing branches on it. Without a branch, "we're closed until 11:00 tomorrow" renders as a red error with a Try-again button that can never work — worse than shipping nothing.

**Plannable.** `ordering.location_paused` / `ordering.location_closed` problem codes with `reopensAt` in the problem-details body, plus a dedicated checkout state that offers the **scheduled-time path** (HIGH-1) instead of "Try again."

### MED-4 — Where "closed" appears: banner + cart CTA + checkout guard. **Do not hide the menu, and do not gate `GET /v1/menu`.**

Browsing must stay open — SEO, Phase 15 content, and the guest deciding for tomorrow all depend on it. Recommendation: sticky banner in the same slot as `delivery-pickup-banner.tsx:11` ("Closed — opens tomorrow at 11:00"); cart CTA **relabelled to "Schedule for later"** rather than disabled; hard guard on checkout submit. Explicitly out: `GET /v1/menu` is `s-maxage=300, stale-while-revalidate=60` edge-cached (`public-menu.controller.ts:188`) — making it stateful destroys the hit rate on the one endpoint that must be fast on cold cache (a PROJECT.md constraint).

### MED-5 — Criterion 2's "in-flight payment already authorized is unaffected" needs a stated boundary.

The order is created, *then* the PaymentIntent (`checkout-form.tsx:86-97`). If a pause lands between the two calls, the order exists at `created` and the guest holds a client secret. **Decision needed:** does pause also block `POST /v1/checkout/payment-intent`? Recommendation: **no** — block order creation only. A `created` order that gets paid is a real order the operator must see and act on. Blocking the intent creates paid-but-invisible orders, which is strictly worse than one extra ticket.

## LOW findings

- **LOW-1 — Publish the hours on the guest surface.** `apps/website/app/contact/` exists. "What time do you open" is the most common inbound phone call; once the data exists, rendering it is near-zero cost. One line in the phase doc, not a task.
- **LOW-2 — `locations.contacts` is untyped `jsonb`** (`packages/db/src/schema/brands.ts:134`); the admin writes an ad-hoc `{phone, email}` (`locations.tsx:86-92`). If BLOCK-1 adds a location edit form, type it in the same pass. Do not defer the same field twice.

## Direct answers to the five open questions

1. **Schedule shape.** One interval per weekday + closed days in the UI; **rows, not columns**, in storage (HIGH-5). Overnight close (`closes_at < opens_at`) is **required**, not gold-plating, and it must share the business-day boundary that `resolveBusinessDate()` already implies (HIGH-4). Split shifts: build the shape, cut the UI if needed. Recurring holiday calendars: **cut**.
2. **Pre-orders while closed.** Yes — a closed location must still accept an order scheduled for an open slot. Enforce against fulfillment time, not `now`; pause never blocks a future-scheduled order (HIGH-1). Verify the scheduled path actually works first (HIGH-2).
3. **Guest "closed" UX.** Menu stays browsable. Banner at the top (same slot as the delivery/pickup tabs) → cart CTA relabelled "Schedule for later" → hard server-side guard at submit with a code the checkout branches on (MED-3, MED-4). Live signal rides `/v1/menu/availability` with a time-bucketed ETag (HIGH-3).
4. **Pause semantics.** `20m / 40m / rest of day / closed until <date>` (HIGH-6). Auto-resume via derived `paused_until`, no cron, "+20 min" as the primary secondary action (MED-2). "Rest of day" = until the next scheduled open (HIGH-4). Per-mode pause: reserve the column, build no UI (MED-1).
5. **What else is needed / what to cut.** Needed and currently missing: a **location edit path** (BLOCK-1) and a **coherent placement for multi-location owners** (BLOCK-3). Cut, in this order: split-shift UI → per-mode pause UI → holiday calendar (replaced by "closed until \<date\>"). Do not cut: the timezone editor, the one-off close, the scheduled-order carve-out.

---

## Scope boundaries I am explicitly NOT recommending here

Capacity/throttling, prep-time-delay-without-stopping-orders (Toast ships this separately from snooze), per-location delivery windows, and shift systems all sit outside "stop taking orders." They belong to Phase 9 / MVP-2. The only forward-compat concession I ask for is the `paused_modes` column in MED-1.

## What I did not review

Migration/RLS mechanics, the `ScopedTx` shape of the new tables, rate-limiting of any new public field, i18n key coverage, and test strategy — CTO/skeptic territory. I also did not execute the scheduled-order path; HIGH-2 is a read of the code chain and needs one request to confirm.
