# Phase 10.1 — Skeptic Review (pre-plan, scope + hidden assumptions)

**Reviewed:** ROADMAP Phase 10.1 block (`.planning/ROADMAP.md:699-716`), `REQUIREMENTS.md:185-193` (SCHED-01..05), `10-PERSONA-PRODUCT.md` BLOCK-3, `10-CONTEXT.md`, `08.4-CONTEXT.md`, `08.5-CONTEXT.md`, and the live code paths below.
**Verdict:** the phase goal is right and the risk is real. **Three of the five success criteria are not buildable as written** against the current codebase. Two of them are not buildable at all without a scope decision the founder has not yet made.

---

## BLOCK

### BLOCK-1 — Success criterion 4 is unbuildable: the order feed does not exist in `?location=all`

- `apps/api/src/contexts/ordering/application/list-orders.service.ts:66-71` — the feed throws `ForbiddenException({ code: 'location.context_required' })` when `getLocationId()` is undefined. There is no brand-wide feed.
- `apps/admin/src/routes/(protected)/$brandSlug/orders.tsx:108` — `const feedLocationId = mode === 'all' ? undefined : locationId;` and `:121,136,149` — every feed query is `enabled: feedLocationId !== undefined`. In `all` mode the Orders page renders **nothing**. `:155` — `const showLocationBadge = false;` is hardcoded, threaded dead through `:250,257,264`.
- SCHED-01 places the pause control "in the order-feed header". SC-1 (one tap from the feed header) and SC-4 (owner can see and set it per location in `all`) are mutually exclusive today.
- 08.5 **D-05** already set the opposite precedent for exactly this shape: _"In `all` the stop-list is read-only — stop/unstop requires selecting a concrete location. The stop/unstop write endpoints stay location-scoped — do NOT make them `@LocationNeutral`."_ (`08.5-CONTEXT.md:42`). Pause is the same class of write.

**Required at discuss:** re-word SC-4 to _"pause/schedule state is visible per location; setting it requires a concrete `?location=<id>`"_, or drop the `all`-mode clause entirely. Do not build an `all`-mode write path.

### BLOCK-2 — The guest cannot address a location, so "per location" enforcement is a whole-brand kill switch wearing a location costume

- `apps/api/src/contexts/ordering/application/create-order.service.ts:47` — `locationId = await this.defaultLocation.resolveForBrand(brandId, tenantId)`.
- `apps/api/src/contexts/catalog/application/default-location-resolver.service.ts:16-19` — returns the **oldest active** location (`orderBy(asc(createdAt), asc(id))`). Same resolver backs guest availability (`get-menu-availability.service.ts:30`) and pricing (`catalog-menu-pricing.adapter.ts:30`).
- 08.4 **D-03** deliberately scoped this out: _"guest checkout binds the order to a default/resolved location automatically this phase; qr-menu / site are NOT reworked for guest location-selection here"_ (`08.4-CONTEXT.md:40`).
- Consequence for a 2-location brand: pausing the _other_ location does nothing; pausing the resolved one blocks the whole brand's guest funnel.
- **The trap on top of the trap:** the admin's default location is **alphabetical by name** (`apps/admin/src/lib/hooks/use-effective-location.ts:38-40,52`, 08.5 D-03) while the guest's is **oldest-created**. For a brand with `Арбат` (created 2nd) and `Центр` (created 1st), the owner lands on `Арбат`, taps Pause, and every guest order continues landing on `Центр`. The operator's emergency brake visibly does nothing and the founder gets a support ticket that looks like a bug in the button.

**Required at discuss:** pick one — (a) declare Phase 10.1 explicitly **single-location-brand scope**, with multi-location enforcement documented as blocked on guest location selection; or (b) pull guest location selection into scope, which is a different, larger phase. Do not let the planner discover this.

### BLOCK-3 — SCHED-04 collides with an already-shipped, unbounded "Schedule for later" input

- `apps/api/src/contexts/ordering/application/dto.ts:33` carries the deferral in a code comment: `// ORD-12: no operating-hours source exists yet — accept any future datetime; schedule validation deferred.` `:34-40` accepts any future ISO datetime, no upper bound.
- `apps/website/components/checkout/order-time-selector.tsx:32-43` renders a raw `datetime-local` field; `checkout-form.tsx:93` passes it through verbatim.
- SCHED-04 says "orders attempted outside opening hours are rejected". A naive `isOpenNow(location)` check rejects a **legitimate pre-order** placed Tuesday 22:00 for Wednesday 13:00, and accepts a scheduled order for 04:00 Sunday.
- The correct rule (ASAP → evaluate `now`; scheduled → evaluate `scheduledFor` against the schedule but **not** against the transient pause window) is nowhere in SCHED-01..05.

**Required at discuss:** state the ASAP-vs-scheduled rule, and cap `scheduledFor` (today it accepts 2031).

## HIGH

### HIGH-1 — There is no location UPDATE path anywhere. SCHED-03 has to build one from scratch.

- `apps/api/src/contexts/tenancy/interfaces/http/locations.controller.ts:96,110,120` — exactly `POST /`, `GET /`, `PATCH /:id/archive`. No update endpoint.
- `apps/api/src/contexts/tenancy/domain/location.aggregate.ts:59` — `archive()` is the aggregate's **only** mutator.
- `apps/admin/src/lib/queries/locations.ts:66,73` — only `createLocationMutation` and `archiveLocationMutation` exist.

SCHED-03 therefore silently includes: a new aggregate mutator, a new application service, a new endpoint + RBAC gate + error mapping, and a new admin edit form. That is the bulk of the phase and it is invisible in the goal statement. Size for it or cut SCHED-03.

### HIGH-2 — `locations.timezone` is NULLABLE, optional in the UI, and every consumer falls back to UTC

- `packages/db/src/schema/brands.ts:134` — `timezone: text('timezone')`, nullable, no default.
- `apps/api/src/contexts/ordering/application/create-order.service.ts:182` — `rows[0]?.timezone ?? 'UTC'`.
- `apps/api/src/contexts/ordering/application/list-orders.service.ts:146` — `const tz = timezone ?? 'UTC'`.
- `apps/admin/src/routes/(protected)/$brandSlug/locations.tsx:38-44` — the create form makes timezone `.optional().or(z.literal(''))`.

Realistic first-customer path: owner creates a location, skips the timezone field, sets "Mon–Sun 10:00–22:00", and the server enforces **10:00–22:00 UTC**. In Moscow that is 13:00–01:00 local — closed at lunch, open after midnight. Exactly the bug the phase was created to prevent, delivered by the feature meant to prevent it. **Do not add a fourth `?? 'UTC'`.** Either make timezone NOT NULL with a backfill, or refuse to persist a schedule on a location with a null timezone.

### HIGH-3 — No date/timezone library exists in this repo, and the one hand-rolled helper is already DST-fragile

- `date-fns` / `luxon` / `dayjs` / `@js-temporal` appear in **no** `package.json` (root, api, admin, website, domain). All time math is hand-rolled `Intl.DateTimeFormat` part extraction.
- `apps/api/src/contexts/ordering/application/list-orders.service.ts:163-190` — `zonedMidnightUtc` samples the UTC offset by formatting `new Date('YYYY-MM-DDT00:00:00.000Z')`, i.e. at **UTC** midnight, not local midnight. On a DST-transition day where the change falls between those two instants, the returned "local midnight" is an hour off. The `hour === 24 ? 0 : hour` special-case at `:185` is the author already having been bitten by `Intl` once.

A weekly schedule needs: wall-clock comparison inside a zone, on days that may be 23 or 25 hours long, with **overnight windows** (open 18:00 → close 02:00) that a naive `open <= now < close` cannot express at all. Reusing this helper reproduces the bug twice a year at 03:00, silently, on the revenue path.

**Required at discuss:** either adopt a library, or restrict SCHED-03 to non-overnight whole-hour windows with the DST hole written down. Do not let the planner hand-roll a third variant.

### HIGH-4 — Under the current RBAC preset, the emergency brake would be owner-only, and `staff` cannot even see the feed

- `packages/domain/src/rbac/system-roles.ts:14` — `location: ['read','create','update','delete']` on **owner only**; `:27` admin = `location: ['read']`; `:33` staff = `location: ['read']`.
- `:31-34` — the `staff` role has **no `order` key at all**. No `order:read`. A line cook or shift lead cannot open the feed today.
- BLOCK-3's own recommendation was to gate pause on `order: ['update-status']` — _"the person who can see the flood can stop it"_ (`10-PERSONA-PRODUCT.md:59`). If pause lands as a `locations` column, `location:['update']` is the natural gate and the brake becomes owner-only — inverting the intent.

**Required at discuss:** name the gating verb, and confirm whether existing tenants need a preset re-sync migration (Phase 10 already needed one for `order:cancel` — `ROADMAP.md:659`).

### HIGH-5 — The guest "closed" view fails OPEN, and its staleness depends entirely on which endpoint carries the flag

- `apps/website/app/page.tsx:47` — `fetchAvailabilityPublic().catch(() => ({ stoppedItemIds: [] }))`. Any availability failure degrades to "nothing stopped". If pause rides this payload, an API blip renders the venue as **open**.
- Staleness budget by carrier: `/v1/menu/availability` = `s-maxage=5` (`public-menu.controller.ts:167`) + `next: { revalidate: 5 }` (`apps/website/lib/api-client.ts:43`) → ≤5 s lag, acceptable. `/v1/menu` = `s-maxage=300, stale-while-revalidate=60` (`:188`, `api-client.ts:25`) → **up to 6 minutes** of guests seeing an open restaurant after the operator taps Pause.
- `public-menu.controller.ts:161-165` — the availability ETag is `'"' + stopVersion + '"'` and returns bare `304` on match. **If pause state is added to that body without bumping the version that keys the ETag, clients get a stale "open" 304 indefinitely — not for 5 s.** This is the single most likely way this feature ships green and broken.

**Required in the plan:** pause/schedule rides the availability response; the ETag-keying version is bumped on every pause/resume/schedule write; the website's catch-fallback for pause must fail **closed**, not open.

### HIGH-6 — The real race is create-order → payment-intent, and SC-2 papers over it

- `apps/website/components/checkout/checkout-form.tsx:86` `createOrder(...)` → `:97` `createPaymentIntent(orderResult.orderId)`. The `orders` row is INSERTed at `created` **before** any payment exists — so a rejection at create time leaves nothing inconsistent. Good.
- `apps/api/src/contexts/payments/application/create-checkout-payment.service.ts:57` gates **only** on `snap.status !== 'created' && snap.status !== 'requires_action'`. It never re-reads location state.
- `checkout-form.tsx:110-119` — `handleRetry` re-mints a payment intent for an existing order with no re-check at all.

Window: guest passes the open check at 22:59:50 → operator taps Pause at 23:00:00 → guest confirms Stripe at 23:02 → **paid order at a paused location**. SC-2's "an in-flight payment already authorized is unaffected" covers the easy half; the created-but-unconfirmed intent is the half that bites. Re-checking at payment-intent time is cheap (an abandoned `created` order costs nothing) and closes it.

## MED

- **MED-1 — A new table costs a 140-line hand-authored erase migration.** `packages/db/migrations/0072_tenancy_erase_locations.sql` (142 lines) and `0077_tenancy_erase_payment_refunds.sql` (140 lines) are full `DROP FUNCTION` + `CREATE OR REPLACE tenancy_erase_tenant` rewrites. Plus a fixture in `packages/db/test/integration/tenant-isolation.spec.ts` (1023 lines; per-table fixtures at `:357,492`). A `jsonb` column on `locations` for a 7-row weekly schedule costs **none** of this. It is never joined, never queried across locations, never indexed. This is the strongest argument for column-not-table.
- **MED-2 — Don't add a fourth poller.** `orders.tsx:119-152` already runs `feedQuery` (5 s), `refundFailedCountQuery` (5 s), and a conditional `activationCheckQuery`. Fold pause state into the existing feed response, not a new endpoint.
- **MED-3 — Test-fidelity trap, precisely the Phase 8/10 one.** `apps/api/test/unit/create-order.service.spec.ts:4-19` mocks the repository, the pricing port, the sequence port **and** `DefaultLocationResolverService`. `apps/api/test/integration/create-order-idempotency.spec.ts:20` — `const suite = dockerOk ? describe : describe.skip;` (59 test files reference `dockerOk`). A pause check added to `CreateOrderService` can be asserted green by a spec that never read a `locations` row, in a suite that silently skips without Docker. `10-CONTEXT.md:181` already declared this non-negotiable — it applies verbatim here. **Acceptance criterion: a real-DB test that writes `orders_paused_until`, calls `POST /v1/orders`, and asserts 4xx + zero new `orders` rows.**
- **MED-4 — "Rest of day" is the expensive third button.** `+20m` and `+40m` are timestamp arithmetic. "Rest of day" needs a correct **local** end-of-day, dragging in HIGH-2 and HIGH-3 for a convenience option. Ship two durations + resume; add the third once timezone is NOT NULL.
- **MED-5 — Pause does not touch the existing queue, and nothing says so.** No capacity/shift concept exists (`08.4-CONTEXT.md:27` — "forward-looking framing only"). State it in the context so nobody builds auto-reject of already-paid orders.

- **LOW-2** — `location.aggregate.ts:12-14` validates timezone with `/^[A-Za-z_]+\/[A-Za-z_]+$/` and a comment admitting no IANA validation exists. `Foo/Bar` passes and then throws inside `Intl.DateTimeFormat` at order time (`create-order.service.ts:193-197` throws a raw `Error` → 500 on the guest checkout path). `Intl.supportedValuesOf('timeZone')` is one line on Node 22.

## CUT LIST — do NOT build these in Phase 10.1

1. **`?location=all` pause/schedule WRITE path.** Contradicts 08.5 D-05; the feed is disabled in `all` (BLOCK-1). Read-only visibility at most.
2. **A guest location picker at checkout.** It is the real fix for BLOCK-2 and it is a separate phase. Declare single-location scope instead.
3. **A separate `location_schedules` table.** Costs a ~140-line hand-authored `tenancy_erase_tenant` rewrite + isolation fixture for data that is never joined or queried across rows (MED-1). Use `jsonb` on `locations`.
4. **"Rest of day" pause.** Needs correct local end-of-day; the other two buttons don't (MED-4).
5. **Multiple open/close windows per day (split shifts, lunch breaks).** SCHED-03 says "per-day open/close", singular. One window per weekday.
6. **Holiday / date-override calendar.** Not in SCHED-01..05. It is the obvious "while we're here" addition and a distinct data model.
7. **A new pause-state endpoint or poller.** Fold into the existing feed + availability responses (MED-2, HIGH-5).
8. **Auto-reject / auto-cancel of already-paid orders on pause.** No capacity model exists (MED-5).
9. **Real-time pause propagation (SSE / websocket).** D-13 already deferred SSE to Phase 18; the 5 s availability TTL is the same order of magnitude.
10. **A pause/schedule domain event + outbox contract.** Nothing consumes it. Add it when a consumer exists.

## MUST NOT be deferred

1. **Timezone NOT NULL (or refuse-to-save-schedule-without-timezone)** before any schedule enforcement ships (HIGH-2). Shipping the schedule on `?? 'UTC'` ships the bug.
2. **ETag/version bump on every pause write** (HIGH-5). Without it the guest sees a cached "open" via 304, forever.
3. **A real-DB rejection test** on `POST /v1/orders` (MED-3).
4. **The RBAC verb decision** (HIGH-4) — an owner-only brake is not a brake.
5. **The re-check at payment-intent creation** (HIGH-6) — it is ~5 lines in an existing service and it closes the only window where money moves at a paused venue.

## Honest read on the phase's own premise

The stated risk is _"tenant takes paid orders at 04:00"_. **The pause does not solve that** — at 04:00 nobody is holding the tablet. Only the schedule does. The pause solves a different, also-real problem (the 40-minute backlog, the fire alarm). So "cut the schedule, ship the pause" would leave the originating risk **fully open**. The honest sequencing is: the schedule is the higher-value half and the higher-cost half; if the phase ships one thing, it must be the schedule, done with the timezone work — and the pause is the cheap rider that comes along for one column and one button.
