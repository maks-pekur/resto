# Phase 10.1 — CTO Review (pre-planning, technical shape)

**Reviewed:** 2026-08-18 · **Scope:** design shape only, no code exists yet
**Inputs:** ROADMAP.md:699-714 (SCHED-01..05), 10-PERSONA-PRODUCT.md BLOCK-3, 10-CONTEXT.md, 08.4-CONTEXT.md, and the live code cited below.

## Verdict

The phase is correctly sized and the enforcement chokepoint already exists. `CreateOrderService.execute` (`apps/api/src/contexts/ordering/application/create-order.service.ts:43-159`) already resolves a location twice and already reads `locations.timezone` — the check is nearly free. **Two things will break this phase if not decided before planning: the nullable `locations.timezone` (BLOCK-1) and the fact that the guest-facing availability ETag is keyed on a write-counter that a time-based schedule never bumps (BLOCK-2).** Everything else is small.

My strong recommendation: **columns on `locations`, no new tables, no new permission verbs, no cron job, evaluation in TypeScript as a pure domain policy.** Concretely that is ~2 columns + 1 JSONB column, one pure function, one port, two endpoints, and an ETag change.

---

## Findings

### BLOCK-1 — `locations.timezone` is nullable and the fallback is silently UTC

`packages/db/src/schema/brands.ts:133` declares `timezone: text('timezone')` — nullable. `apps/api/src/contexts/tenancy/interfaces/http/locations.controller.ts:48` makes it optional on create (`LocationTimezone.nullable().default(null)`). `create-order.service.ts:182` then does `rows[0]?.timezone ?? 'UTC'`.

A weekly schedule evaluated in UTC for a Europe/Moscow restaurant is wrong by 3 hours in both directions: it rejects paid orders at 18:00 local and accepts them at 02:00 local. That is worse than shipping nothing, because the operator will believe the guard works. Silent-UTC is acceptable for `resolveBusinessDate` (it only mislabels a counter reset); it is not acceptable for a rejection rule.

**Do this:** in this phase's migration, backfill and set `locations.timezone NOT NULL`. 08.4 D-13 records there is no production location data, and `0068_stop_list_location_regrain.sql:22-24` already deleted the dev rows on that basis — so the backfill is a one-liner. Make `timezone` required in `CreateLocationInputSchema` and add it to the locations admin form. Fallback: refuse to _enable_ a schedule on a location without a timezone rather than defaulting one.

### BLOCK-2 — the availability ETag is a write-counter; a schedule changes state with no write

`public-menu.controller.ts:160-167` computes `etag = '"' + stopVersion + '"'` and sets `Cache-Control: public, s-maxage=5`. `stopVersion` is bumped only inside `catalog-drizzle.repository.ts:828-840` on a stop-list write. A location that closes at 21:00 produces **no write at all**, so the ETag is unchanged, `If-None-Match` matches, and the endpoint answers `304` forever. Every cached client keeps rendering "open".

`s-maxage=5` bounds CDN staleness to 5s, so the TTL side is already fine. The conditional-request side is not.

**Do this:** derive the ETag from the response body, not from a counter — e.g. `"<stopVersion>.<openState>.<pausedUntilEpochOr0>"`. State flips → body changes → ETag changes → no stale 304. Manual pause additionally gets a real write, so it is covered either way; but do **not** bump `catalog_location_stop_version` from a tenancy write path — that table is catalog's (`packages/db/src/schema/menu.ts:414`) and reaching into it inverts the context boundary. Composite ETag costs nothing and needs no new counter.

Corollary: put open/paused state **only** on `GET /v1/menu/availability` (`s-maxage=5`), never on `GET /v1/menu` (`public-menu.controller.ts:188`, `s-maxage=300`). Adding it to `/v1/menu` would either serve a 5-minute-stale "open" or force the 300s menu cache down to 5s.

### HIGH-1 — gating pause on `location:update` makes it owner-only, reproducing the bug Phase 10 just fixed

`packages/domain/src/rbac/system-roles.ts:14` gives `location: ['read','create','update','delete']` to `owner` only; `admin` and `staff` get `location: ['read']` (lines 24, 32). `PRESET_ROLES` (`packages/domain/src/rbac/preset-roles.ts`) give `manager` / `cashier-foh` / `kitchen` no `location` verb at all. So `@Permissions({ location: ['update'] })` on a pause route = only the owner can hit the emergency brake — which is precisely the failure 10-CONTEXT D-06 called "the bug being fixed."

**Do this — and note it needs zero RBAC migration:**

- **Pause / resume → `@Permissions({ order: ['update-status'] })`.** Held by owner, admin, and all three presets. No new verb, no preset re-sync (10-02-PLAN had to write one; this avoids a second).
- **Weekly schedule edit → `@Permissions({ location: ['update'] })`** (owner) or `settings: ['update']` (adds manager) — schedule is configuration, pause is operations. Pick one and state it.

### HIGH-2 — a pause route will 403 the owner in `?location=all` mode unless the location is a path param

`LocationScopeGuard` throws `location.context_required` when `getLocationId()` is empty (`apps/api/src/contexts/identity/interfaces/http/guards/location-scope.guard.ts:39-46`) unless the route is `@LocationNeutral`. In `?location=all` (08.5 D-01 / 10-CONTEXT D-02) the admin sends no `x-location-id`. This is the identical defect 10-CONTEXT D-02 flags on `RefundsController`.

**Do this:** `POST /v1/tenancy/locations/:id/pause` and `/resume`, on a `@LocationNeutral()` controller — matching `LocationsController` which is already `@LocationNeutral()` (`locations.controller.ts:86`). Take the location from the **path param**, not the header.

### HIGH-3 — with a path param, nothing currently authorizes that param against the caller's location scope

`LocationScopeGuard` validates the ALS-bound location (from the `x-location-id` header), not a route parameter. `@LocationNeutral()` bypasses it entirely. `LocationPermissionChecker` exists and is registered (`apps/api/src/contexts/identity/identity-core.module.ts:370,385`) but is still not threaded into `PermissionsGuard` — deferred in 08.4 D-07, again in 08.5, and a third time in 10-02-PLAN.

Consequence if unaddressed: a `cashier-foh` scoped to Location B can pause Location A by changing a UUID. That is a cross-location write on the revenue path.

**Do this (smallest correct):** in the pause service, load the target location and assert it is in the caller's scope via the existing `MemberLocationScopeReader` port (`apps/api/src/contexts/identity/application/ports/member-location-scope-reader.port.ts`), owner bypassing per 08.4 D-05, out-of-scope → existence-hiding 404. ~15 lines. Wiring `LocationPermissionChecker` properly is the better answer but is a bigger, separate decision — do not let the phase silently defer it a **fourth** time without recording it.

### HIGH-4 — a separate `location_pauses` / `location_schedules` table triggers four invariant obligations for no MVP value

If planning adds a child table it inherits, mechanically:

1. composite FK `(location_id, tenant_id) → locations(id, tenant_id)` per `packages/db/src/schema/_columns.ts:60-75`;
2. a RESTRICTIVE location-grain RLS policy mirroring `0069_stop_list_location_rls.sql`;
3. a new delete line inside `tenancy_erase_tenant` — `0072_tenancy_erase_locations.sql`, `0074_tenancy_erase_order_sequences.sql` and `0077_tenancy_erase_payment_refunds.sql` are three consecutive migrations that exist _only_ because a table was added and erasure was forgotten. A RESTRICT FK to `locations` that is not deleted first makes tenant erasure fail hard;
4. a new entry in `packages/db/test/integration/tenant-isolation.spec.ts` (mandated by `packages/db/CLAUDE.md`).

**Recommendation: put pause state on `locations`.** `locations` is already tenant-RLS'd, already composite-FK'd to `brands` (`brands.ts:139-144`), already handled by `tenancy_erase_tenant`, and already read on the order hot path. The "no hard deletes" rule is about rows, not columns — `orders.status` is the in-repo precedent (`packages/db/src/schema/ordering.ts:31`: "status acts as soft-delete"). Resume = set `orders_paused_until = NULL`.

History is **not** a reason to build the table: see MED-1.

### MED-1 — pause/resume must emit a `tenancy.*` event, or there is no record of who stopped the money

Today location writes emit nothing: `ArchiveLocationService.execute` calls `location.archive()` (which pushes a `LocationArchived` event, `location.aggregate.ts:62-77`) and then never calls `pullEvents()` — the event is dropped on the floor (`apps/api/src/contexts/tenancy/application/archive-location.service.ts:26-30`).

The audit subscriber already listens on the wildcard `tenancy.>` (`apps/api/src/contexts/audit/infrastructure/nats-audit-subscriber.ts:20`). So emitting `tenancy.location_ordering_paused.v1` / `..._resumed.v1` via `buildEnvelope` + `appendToOutbox` in the same transaction as the column write gets you:

- an `audit_log` row for free (one line in `ACTION_TARGET_KIND`, `record-audit.service.ts:7-37`, plus a `location` branch in the `targetId` switch at `:76-104`);
- the exact push signal Phase 18 SSE needs (ROADMAP.md:853-857) with zero Phase 18 rework.

That is the correct answer to "does a pause need to survive as a record" — **yes, as an audit row, not as a table.** Do not emit an event for schedule edits; that is configuration, and `catalog.item_stopped` is the established precedent for operational-only events.

### MED-2 — `scheduledFor` orders will be rejected against the wrong instant

`orders.scheduled_for` exists (`ordering.ts:44`) and the website offers "Schedule for later" (`apps/website/components/checkout/order-time-selector.tsx:31-46`). `CreateOrderService` passes it through at `:153`. If the schedule check evaluates against `new Date()`, a guest at 22:30 pre-ordering for tomorrow 13:00 is rejected.

**Do this:** evaluate the _schedule_ against `input.scheduledFor ?? now`; evaluate the _manual pause_ against `now` only (a pause is "not right now", not "not tomorrow"). One line, easy to get wrong, worth an explicit test.

### MED-3 — the order-created → payment-confirmed window is unguarded, and that is probably correct

Order creation precedes payment: `POST /v1/orders` writes `status='created'`, then `CreateCheckoutPaymentService` requires `status ∈ {created, requires_action}` (`apps/api/src/contexts/payments/application/create-checkout-payment.service.ts:56-59`). SCHED success criterion 2 says an already-authorized payment is unaffected. But an order created at 20:59 can be confirmed at 21:05 after a pause.

**Recommendation: enforce only at `CreateOrderService` and document the window.** Adding the check to the payment-intent path means taking a card away from a guest mid-flow to save a few minutes of exposure. State the decision explicitly so it is not read as an oversight.

### MED-4 — the website availability fetch fails open, so an API blip renders "open"

`apps/website/app/page.tsx:46` does `fetchAvailabilityPublic().catch(() => ({ stoppedItemIds: [] }))`, and `apps/website/lib/api-client.ts:46` returns an empty payload on 404. If pause/open state rides in this payload, a transient failure shows the guest an open restaurant. Server-side enforcement (SCHED-05) still holds, so this is a UX papercut, not a hole — but the guest gets to checkout and then eats a 409. Decide: fail-closed on the _checkout_ page, fail-open on the _menu_ page.

### LOW-1 — `CreateOrderService` already makes a redundant location query; folding the new read in should make it cheaper, not costlier

`defaultLocation.resolveForBrand` selects full `locations` rows and discards everything but `id` (`apps/api/src/contexts/catalog/application/default-location-resolver.service.ts:12-21`); `resolveBusinessDate` then re-selects the same row for `timezone` (`create-order.service.ts:178-183`). Order creation already does ~7 round-trips.

**Do this:** have the port return `{ id, timezone, ordersPausedUntil, pauseReason, schedule }` in one query and drop the second. Net round-trips: **-1**, with the new check included. Per-order cost is a non-issue; do not let the plan invent a cache for it.

### LOW-2 — `create-order.service.ts:11` already imports a catalog service directly; do not extend that pattern

`import { DefaultLocationResolverService } from '../../catalog/application/default-location-resolver.service'` is a concrete cross-context class dependency, contrary to the port rule in `CLAUDE.md`. Don't replicate it for location state. `OrderingModule` already imports `TenancyModule` (`apps/api/src/contexts/ordering/ordering.module.ts:27`), so a Symbol port costs nothing.

## Recommended design (answers to the six questions)

**1. Where state lives.** Three columns on `locations`: `orders_paused_until timestamptz null`, `pause_reason text null`, `ordering_schedule jsonb null`. Schedule shape: `{ tz: <from locations.timezone>, days: { mon: [{open: 660, close: 1380}], ... } }` — **minutes from local midnight**, close may exceed 1440 to express "until 02:00". `null` schedule = always open (correct default; a restaurant that never sets hours must not become permanently closed). No new tables. History via the audit event (MED-1).

**2. Ownership.** `tenancy` owns the write path and the columns — extend `LocationsController` / add `PauseOrderingService` next to `ProvisionLocationService`. `ordering` reads through `LOCATION_ORDERING_STATE_PORT` declared in `apps/api/src/contexts/ordering/domain/ports.ts`, implemented by an adapter in `tenancy/infrastructure/` and exported from `TenancyModule`. Ordering never touches `schema.locations` directly.

**3. Freshness contract.** Manual pause: write + composite ETag → correct within `s-maxage=5`. Schedule: no write, so correctness comes entirely from the body-derived ETag (BLOCK-2) plus the existing 5s TTL. **Contract to write down: "guest-visible open/closed state is at most 5 seconds stale; server-side rejection is exact."** No new counter, no cache invalidation hook, no NATS-triggered purge.

**4. Time correctness — evaluate in TypeScript.** Reasons: `CLAUDE.md` forbids raw SQL outside `packages/db`, so a Postgres `AT TIME ZONE` evaluation would have to live in the db package and be re-plumbed through a repository anyway; the location row is already in memory; and the same `Intl.DateTimeFormat` primitive is already the timezone tool in this codebase (`create-order.service.ts:184-192`). Derive local weekday + minutes-from-midnight from `Intl.DateTimeFormat(tz, {weekday, hour, minute, hour12:false})`, then match today's interval and yesterday's interval where `close > 1440`. DST is handled by the formatter. Document the one pathological case — an open time inside a spring-forward gap simply never matches — and do not build for it.

**5. Where the check lives — a pure domain policy, not the aggregate.** `apps/api/src/contexts/ordering/domain/ordering-window.policy.ts` exporting `evaluate(state, at): { ok: true } | { ok: false; reason: 'paused'|'closed'; reopensAt: Date | null }`. Called by `CreateOrderService` right after the location is resolved (before pricing, so a closed venue costs one query). Not in `Order.create()` — the aggregate's invariants are about the order, and embedding location hours there would force every future caller (manual entry, POS import) to supply a schedule. A pure function is the only way DST/midnight-crossing gets real unit tests, which is this phase's largest correctness risk.

**6. Forward compatibility.** Phase 18 SSE is _helped_ by MED-1 (`tenancy.>` already flows to the audit subscriber; a pause event is a ready-made push signal). 08.4/08.5 collide in exactly two places, both covered: HIGH-2 (`?location=all` needs a path param + `@LocationNeutral`) and HIGH-3 (path-param authorization). No other conflict found.

## Over-engineering to reject at planning

- **A `location_pauses` history table** — four invariant obligations (HIGH-4) to reproduce what one audit row gives free.
- **A cron/scheduler to expire a pause.** `orders_paused_until <= now()` is self-expiring. `apps/api/src/infrastructure/jobs/` should gain nothing here.
- **A dedicated pause version counter / cache-invalidation hook.** The composite ETag plus the existing 5s TTL is the whole mechanism.
- **A new `location:pause` permission verb.** `order:update-status` already exists on every role that needs it (HIGH-1); a new verb means another preset re-sync migration.
- **Per-day multiple intervals (split shifts, lunch break) in MVP-1.** The JSONB shape allows an array so it is not a schema change later — ship the UI with one interval per day.
- **Holiday / date-override calendar.** Manual pause covers "closed today" for MVP-1. Defer.
- **Schedule-aware pre-order windows** ("you may only schedule inside opening hours + 7 days"). MED-2 needs one comparison, not a booking engine.
