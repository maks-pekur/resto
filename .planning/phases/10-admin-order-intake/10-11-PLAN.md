<objective>
Attach the card-face action flows and the alerting layer: the accept popover that captures the operator's prep time, the reject popover with reason chips, the forward status-advance buttons, and the sound plus tab-title alert that makes a new order impossible to miss in a loud room.

Purpose: a silent, purely visual feed is how this feature fails in a real restaurant. And the single most likely runtime failure of the whole phase is an owner in `?location=all` mode getting 403'd on every mutation — which is fixed here, in the client, by always sending the order's own location.

Output: two-tap accept, two-tap reject, one-tap status advance, a chime that cannot fail silently, and a tab title that signals from a backgrounded tab.
</objective>

<interfaces>
**The single most consequential client contract in this phase** (`apps/admin/src/lib/api-client.ts`): `apiFetch` omits the `x-location-id` header entirely when `opts.locationId` is `'all'` or absent. `LocationScopeGuard` throws `location.context_required` on a missing location **before** it reaches its owner-bypass line. Therefore **every order mutation must pass the order row's own `locationId`** — `apiFetch(..., { brandSlug, locationId: order.locationId })` — and never `useEffectiveLocation()`'s value when that value is `'all'`. Plan 10-08 deliberately did **not** add `@LocationNeutral()` to mutation routes, because doing so would short-circuit the non-owner scope check and reopen a cross-location privilege escalation. The client is where this is fixed.

**Backend routes** (plan 10-08):
`POST /v1/orders/:id/accept` body `{ prepMinutes: number }` (5–180 integer; the server computes `eta_at`, the client never sends a timestamp)
`POST /v1/orders/:id/advance` body `{ targetStatus: 'preparing' | 'ready' | 'completed' }`
`POST /v1/orders/:orderId/cancel` body `{ reasonCode, cancelNote? }` — used by both reject and cancel; `canceled_from_status` records the intent server-side.
All transitions are **idempotent by target state**: a second call on an order already in the target status returns 200 with the current state rather than an error.

**Canonical reason codes** (identical in migration 0073's CHECK constraint, RESEARCH §A.3 and UI-SPEC §5/§12): `kitchen_out_of_stock`, `kitchen_too_busy`, `guest_requested`, `guest_no_show`, `payment_issue`, `duplicate_order`, `other`.

**shadcn:** `popover` is **not** installed in `apps/admin`. `apps/admin` uses the `radix-ui` umbrella package (`^1.4.3`), already present — existing primitives import `{ Select as SelectPrimitive } from 'radix-ui'`. Adding `popover` therefore needs **no new npm dependency**.

**No existing precedent** in `apps/admin/src` for `new Audio(`, `HTMLAudioElement`, `document.title` mutation, or a localStorage-persisted setting — all four are net-new. Build them from UI-SPEC §8's explicit design.

**Toasts:** `apps/admin/src/lib/ui/toast-helpers.ts` (`showSuccess`/`showError`) is the established mechanism.

**`use-order-sound.ts`.** Takes the current unaccepted-order rows and:
