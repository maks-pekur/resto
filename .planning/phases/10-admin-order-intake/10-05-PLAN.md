<objective>
Restructure the money path so D-08/D-10/D-11 hold: derive refundability from the captured payment rather than the order status (the CTO HIGH-7 money bug), move the Stripe call outside the database transaction so a refund failure never blocks the kitchen, record every attempt as a durable ledger row, and add a retry that cannot double-refund.

Purpose: once `cancel()` is legal from `accepted`/`preparing`/`ready`, `wasPaid = snap.status === 'paid'` reads false on a fully-paid order and the refund is silently skipped. And with the Stripe call inside the transaction, a Stripe outage rolls back the cancel — exactly what D-11 forbids.

Output: a cancel that always cancels, a refund that always leaves a trace, a retry that is safe, and e2e proof read back from Postgres including the Stripe-failure path.
</objective>

`payment_refunds` today (packages/db/src/schema/ordering.ts):
```
id, tenant_id, payment_id, stripe_refund_id text NOT NULL, amount money NOT NULL,
reason text NOT NULL, status text NOT NULL DEFAULT 'pending', created_at
CHECK payment_refunds_status_chk: status IN ('pending','succeeded','failed')
```

`status = 'pending'` is modelled but only ever used as the column default — never as a pre-call marker.
`stripe_refund_id NOT NULL` is the blocker for inserting a pending row **before** the Stripe call: there is no id yet. This plan makes it nullable and introduces a locally-computed `refund_request_id` as the stable idempotency key.

`RefundOrderService` already computes `const refundRequestId = \`refund:${orderId}:${alreadyRefundedMinor}:${amountMinor}\`` and passes it to `provider.createRefund`. That value becomes the persisted key.

`PaymentRepository` port (apps/api/src/contexts/payments/domain/ports.ts) currently exposes:
`findByPaymentIntentId`, `findByOrderId`, `upsertByPaymentIntentId`, `findRefundByStripeId`, `upsertRefund`, `updateRefundStatus(tenantId, stripeRefundId, status, tx)`.
`PaymentRefundRow.stripeRefundId` is typed `string` and becomes `string | null`.

`HandleStripeEventService.handleRefund()` is the existing inbound reconciliation consumer of `updateRefundStatus` — verify it still compiles and behaves after the type change.

No existing precedent in this codebase for "persist, call an external service outside the tx, then record the outcome": both `create-checkout-payment.service.ts` and `refund-order.service.ts` call the provider **inside** `db.withTenant`. This plan introduces that pattern.

**`CancelOrderService` — rewrite `execute`.** New input: `{ orderId, tenantId, reasonCode, cancelNote?, actorUserId }`. Sequence:

  1. Load the order; 404 via `OrderNotFoundError` if absent.
  2. **TX1 (short):** `order.cancel(reasonCode, cancelNote ?? null, actorUserId)` then `orderRepo.update(order, tx)`. This commits regardless of anything downstream — that commit is what makes D-11's "the order still cancels" true under a Stripe outage. The `OrderCanceled` / `OrderStatusChanged` outbox appends happen in this same transaction via the existing `appendToOutbox` + `buildEnvelope` path.
  3. **Delete `wasPaid` entirely** — do not patch it. `const wasPaid = snap.status === 'paid'` reads false for an `accepted`/`preparing`/`ready` order that is fully paid, silently skipping the refund (CTO HIGH-7). Do not replace it with `capturedMinor > 0` derived from `snap.total` either: order total is not the same fact as amount captured. After TX1 commits, hand off to the refund path unconditionally and let `RefundOrderService`'s own payment lookup (`PaymentNotRefundableError` when there is no `paymentIntentId`/`stripeAccountId`) be the single authority on whether there is anything to refund. Catch `PaymentNotRefundableError` and treat it as "nothing to refund" — a normal outcome for an unpaid `created` order, logged at `log` level, not an error.
  4. Also delete the `if (currentStatus === 'paid' || currentStatus === 'created')` gate that today prevents the cancel from persisting at all for `accepted`/`preparing`/`ready`.
  5. The refund amount is always **full** — the remaining refundable amount computed from the payment row. `CancelOrderService` never accepts an `amountMinor`. A cashier using cancel makes no financial judgement (D-10).
  6. Return a result the controller can surface: `{ canceled: true, refund: { attempted: boolean; outcome: 'succeeded' | 'failed' | 'none'; amountMinor: number | null } }`.

**`RefundOrderService` — split `executeWithOrder` into three short transactions with the provider call between them:**
  - **TX2:** compute `capturedMinor`, `alreadyRefundedMinor`, `amountMinor` and the deterministic `refundRequestId`; call `order.refund(amountMinor, alreadyRefundedMinor)` for its amount validation (post-10-03 it no longer touches order status); `upsertRefund` a row with `status: 'pending'`, `stripeRefundId: null`, `refundRequestId`. Commit. This is the durable record that a refund was attempted even if the process dies before Stripe answers.
  - **Provider call with no open transaction:** `provider.createRefund({ ..., refundRequestId })`. `refundRequestId` is also Stripe's idempotency key, so a retry of the same logical refund cannot double-charge the connected account.
  - **TX3 on success:** `updateRefundOutcome(tenantId, refundRequestId, { status: 'succeeded', stripeRefundId })`, update `payments.refundedAmount` and `payments.status` to `refunded` / `partially_refunded` exactly as today, append `PaymentOrderRefundedV1` to the outbox via `buildEnvelope`.
  - **TX3 on failure** (any provider exception, timeout or network error): `updateRefundOutcome(tenantId, refundRequestId, { status: 'failed', failureReason: <provider message, truncated to 500 chars> })`. Then rethrow a typed `RefundProviderFailedError` (new, in `payments/domain/errors.ts`, plain `Error` subclass with explicit `this.name`) so `CancelOrderService` can report `outcome: 'failed'` while still having committed the cancel. Never let a provider failure roll back TX1 or TX2.
  - Before TX2, short-circuit: if a `payment_refunds` row already exists for this `refundRequestId` with `status: 'succeeded'`, return its result without calling Stripe again.

**`RetryRefundService`** (new file). Input `{ orderId, tenantId, refundRequestId, actorUserId }`. It re-runs only the provider call and TX3 against an existing `payment_refunds` row whose `status` is `'failed'`. It must **not** call `order.cancel()` again and must **not** call `order.refund()` again (the ledger row already records the intended amount). Guard rails, each with its own test: reject when the row's status is not `'failed'` (`RefundNotRetryableError`); reuse the same `refundRequestId` so Stripe's idempotency key is unchanged; re-read `payments.refundedAmount` before applying the outcome so a webhook that already reconciled the refund cannot cause a double-count.

**DTO.** Add `CancelOrderInputSchema` to `payments/application/dto.ts` with `reasonCode: z.enum([...the seven canonical codes...])` and `cancelNote: z.string().max(500).optional()`. Every new free-text field gets a `.max()` cap per `packages/domain/CLAUDE.md`'s hard rule. Do not add a cap to the existing `RefundInputSchema.reason` — that pre-existing gap is out of scope; just do not extend it.

Register `RetryRefundService` in `payments.module.ts` and export what the controller plan (10-08) needs.

Update `cancel-order.service.spec.ts` and `refund-order.service.spec.ts` for the new shapes. These mocked-repository specs are **supplementary only** — the load-bearing proof is Task 3's database read-back, because mocked-repo specs are exactly how the pre-requisite production bug survived.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator → guest's money | A non-owner can now trigger a real Stripe refund |
| API → Stripe Connect | An untrusted, failure-prone external call in the middle of a state change |
| database transaction → external side effect | Money moves outside the transaction; the ledger must reconcile |
| tenant → tenant | Cancel and refund are cross-tenant-sensitive mutations |
