<objective>
Expose the operator order surface over HTTP with the correct guard vocabulary, and make 5-second polling survivable against the shared 60-req/min per-IP bucket.

Purpose: the guard decisions here are the security core of the phase. The tempting fix for the `?location=all` 403 — marking every order route `@LocationNeutral()` — would remove the non-owner scope check and reopen the cross-location privilege escalation that Phase 08.4 was built to close. The correct fix is `@LocationNeutral()` on the aggregate read only, plus a client that always sends the order's own real location on mutations.

Output: two controllers, a per-principal poll rate-limit guard, an allowlist entry, a written route-by-route guard audit, and an authz e2e suite that proves both the permitted and the denied paths.
</objective>

**Root cause of the `?location=all` 403, traced precisely (do not "fix" it the tempting way):**
`LocationScopeGuard.canActivate()` throws `location.context_required` when `getLocationId() === undefined` **before** it reaches the owner-bypass line. An owner in `?location=all` has `apiFetch` omit `x-location-id` entirely (`api-client.ts` guards on `opts.locationId !== 'all'`), so the 403 fires before owner-bypass is evaluated. This reproduces on any route lacking `@BrandNeutral`/`@LocationNeutral` — including every new one.
`@LocationNeutral()` short-circuits the **entire** guard, including the non-owner scope-membership check. Applying it to a mutation route would let a non-owner forge `x-location-id` and act on an order at a location they are not scoped to.

**Existing decorator vocabulary:** `@Permissions({ resource: [verbs] })`, `@RequireActiveTenant()`, `@RequireBrand()`, `@BrandNeutral()`, `@LocationNeutral()`, `@OwnerOnly()`.

`OrdersController` (`ordering/interfaces/http/orders.controller.ts`) is class-level `@Public()` + `@BrandNeutral()`. New operator routes must **not** live on it — put them on new controllers so they cannot inherit `@Public()`.

**Rate limiting today** (`apps/api/src/shared/security.ts`): `@fastify/rate-limit` with `global: false`, invoked from `RateLimitGuard`; a single **per-IP** store shared across all routes; `max` defaults to `env.RATE_LIMIT_PUBLIC_PER_MIN` (60); `allowList: (req) => req.url === '/healthz' || req.url === STRIPE_WEBHOOK_PATH`.
`RateLimitGuard` is registered via `app.useGlobalGuards(...)` in `main.ts`; `AuthGuard` via `{ provide: APP_GUARD, useClass: AuthGuard }` in `identity-http.module.ts`. **RESEARCH Assumption A2** holds that the former runs first, so `req.principal` is unavailable at limiter time — verify this empirically in Task 2 before committing to the design.

**Analog to copy for the new guard:** `apps/api/src/contexts/identity/interfaces/http/guards/brand-slug-rate-limit.guard.ts` — an in-memory `Map<string, Bucket>`, `key = req.principal && 'userId' in req.principal ? req.principal.userId : \`ip:${req.ip}\``, a periodic sweep, and a 429 `HttpException`shaped`{ message: 'Too Many Requests', code: 'rate-limit-exceeded', detail }`so`ProblemDetailsFilter` formats it consistently.

**Arithmetic that makes this mandatory:** one device polling every 5s = 12 req/min. Four operator devices behind one NAT = 48 req/min against a 60/min per-IP bucket shared with `POST /v1/orders` and `GET /v1/menu` — a guest ordering on the restaurant's own WiFi gets 429'd.
