<objective>
Make reject/cancel an order-status capability rather than a financial one (D-06): add a distinct `order:cancel` verb, grant it to `owner`, `admin` and all three staff presets, re-sync the presets onto tenants that were provisioned before this change, and pin by test that widening `order` never reaches `NON_DELEGATABLE` territory.

Also close D-07 explicitly: either wire `LocationPermissionChecker` or record a reasoned third re-defer. This plan records the re-defer, because the global swap would 403 every non-owner on every `@LocationNeutral()` route.

Purpose: today the only person who can refuse an order at 20:40 on a Friday is the owner. That is the bug being fixed.

Output: the new verb across the RBAC surface, a re-sync path for existing tenants, regression specs, and a written decision record.
</objective>

D-07 states the `LocationPermissionChecker` decision "cannot be dodged a third time" — it must be wired or explicitly re-deferred with a reason. This task records the re-defer. **Do not swap the `PERMISSION_CHECKER` binding.**

Create (or append to) `.planning/phases/10-admin-order-intake/deferred-items.md` with a section titled `D-07 — LocationPermissionChecker: third explicit re-defer (Phase 10)` containing, in prose an engineer can act on later:

1. **What is deferred.** Binding `PERMISSION_CHECKER` to `LocationPermissionChecker` instead of `BetterAuthPermissionChecker`.
2. **Why, concretely.** `LocationPermissionChecker.hasPermission()` returns `false` for any non-owner when `activeLocationId` is falsy. Every route decorated `@LocationNeutral()` legitimately runs without a location context. A wholesale swap therefore 403s every non-owner on every `@LocationNeutral()` route across menu, brand, team and settings — a full regression, not a Phase 10 concern. Separately, `PermissionsGuard` calls `hasPermission` with three arguments and never passes `req.activeLocationId` (which `AuthGuard` already populates), so the swap needs a guard-signature change too.
3. **Why the Phase 10 write path is nonetheless safe without it.** Order-mutation routes keep the standard `LocationScopeGuard` non-owner branch, which independently verifies the session-pinned `activeLocationId` against `member_location_scope` via `MemberLocationScopeReader.findLocationScopeForMember` — that check runs regardless of which `PermissionChecker` is bound, so a staff member cannot act on an order at a location they are not scoped to. What `LocationPermissionChecker` additionally offers is a **different role per location for the same person**, a capability the product does not expose anywhere (no assignment UI, `member_location_scope.role` is surfaced nowhere) — so the practical gap is "a staff member has the same role at every location they are scoped to," which is the app's behaviour everywhere else today, not a regression introduced by Phase 10.
4. **What would make this urgent.** The first product surface that lets an owner give one person different roles at different locations. Name it as the trigger condition.
5. **Cost estimate when it is picked up.** Thread `req.activeLocationId` into `PermissionsGuard.canActivate`'s `hasPermission` call (one line), then either make `LocationPermissionChecker` fall back to the tenant-wide check when `@LocationNeutral()` is set on the handler, or bind it per-route rather than globally.

Cross-reference this section from the plan's SUMMARY so the phase verifier can find it.
</action>
