<objective>
Build the order detail Sheet and the deliberately-slow money paths that live inside it: the cancel confirmation that names the refund amount twice, the owner-only discretionary refund control, and the three-level refund-failure surface.

Purpose: reject is one tap on the card face because it happens before any food exists; cancel is buried behind a modal precisely so nobody hits it next to "Готово". That asymmetry is the design, not an inconsistency. And a failed refund is money sitting broken — it must never silently disappear from view.

Output: the detail Sheet, the cancel dialog, the owner-gated refund form, the retry affordance at three zoom levels, and a `me` response that lets the client gate on the same strings the server enforces.
</objective>

<interfaces>
**UI-SPEC Open Question #4 is resolved by this plan.** The spec warns that the client-side visibility check and the server-side enforcement key must be the same string, or the UI shows a button the server then 403s. Today `GET /v1/me` returns only `{ kind, email, baseRole }` — no permission set — so the client cannot gate honestly. `computeEffectivePermissions(memberRoleCsv, customRoleLookup)` already exists at `apps/api/src/contexts/identity/application/effective-permissions.ts` and returns `Record<string, readonly string[]>`. This plan surfaces it on the `me` response.

Server-side enforcement, for reference:
- `POST /v1/orders/:orderId/cancel` and `/refund/retry` → `@Permissions({ order: ['cancel'] })`
- `POST /v1/orders/:orderId/refund` (arbitrary amount) → `@Permissions({ billing: ['update'] })`, and only `owner` holds `billing` in `SYSTEM_ROLES`.

**Backend detail route** (plan 10-07/10-08): `GET /v1/orders/:id/detail` returns the full snapshot plus items, modifiers, the per-state timeline timestamps, and the order's `payment_refunds` rows — including any with `status: 'failed'` and their `refundRequestId` and `failureReason`.

**Retry route:** `POST /v1/orders/:orderId/refund/retry` body `{ refundRequestId }`, gated on `order:cancel`, reusing the original Stripe idempotency key so a retry cannot double-refund.

**Canonical reason codes** are already a single exported `const` array created by plan 10-11's reject popover — import it, do not redefine it.

Installed shadcn components include `sheet`, `alert-dialog`, `select`, `textarea`, `input`, `separator`, `badge`, `button`, `tooltip`. Nothing new is needed.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| principal → own permission set | The client now reads what it is allowed to do |
| cashier → discretionary money decisions | The arbitrary-amount refund must remain unreachable |
| operator-internal failure text → guest | Raw provider errors must stay inside the admin |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-12-01 | Elevation of Privilege | A cashier reaching the arbitrary-amount refund control | mitigate | The section is gated on `can('billing','update')` — the exact string the server enforces — and is **omitted from the DOM**, not disabled; the server's `@Permissions({ billing: ['update'] })` remains the actual boundary and plan 10-08's e2e pins the 403 |
| T-10-12-02 | Elevation of Privilege | Client gating on `baseRole === 'owner'` as a proxy, which silently breaks for custom roles | mitigate | `usePermissions` reads the server-computed effective set; `grep` asserts no `baseRole` gating in the hook |
| T-10-12-03 | Information Disclosure | Surfacing another principal's permissions via the widened `me` response | mitigate | `me` returns only the **caller's own** effective set, derived from their own session; it reveals nothing they could not learn by attempting each action |
| T-10-12-04 | Tampering | Mis-tapping cancel and refunding a guest by accident | mitigate | Cancel exists only in the Sheet footer, spatially separated from the advance button, behind a modal with a required reason and the amount repeated in both the description and the confirm button |
| T-10-12-05 | Tampering | Double-refunding via retry | mitigate | Retry reuses the failed row's `refundRequestId`, which is also Stripe's idempotency key; no client-generated id; plan 10-05's e2e pins that the ledger row count stays 1 |
| T-10-12-06 | Information Disclosure | Raw Stripe failure text leaking to a guest-facing surface | mitigate | `failureReason` renders only inside the admin Sheet; the frozen public status contract (plan 10-06) has no such field |
| T-10-12-07 | Repudiation | A failed refund silently disappearing so nobody resolves it | mitigate | Three simultaneous persistent surfaces, none auto-dismissing, and a failed retry keeps all three visible |
| T-10-12-08 | Information Disclosure | Guest contact details rendered on a counter screen every 5 seconds | accept | Contact details appear only in the detail Sheet, opened deliberately per order, never on the polled feed rows |
