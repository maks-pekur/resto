# Phase 10: Admin Order Intake - Research

**Researched:** 2026-08-13
**Domain:** NestJS ordering/payments bounded contexts + admin SPA (TanStack Router/Query) + Next.js website guest checkout
**Confidence:** HIGH on code facts (all claims below are grounded in a direct read of the current working tree); MEDIUM on a few design recommendations (rate-limit keying, refund-outside-tx restructure) that are net-new patterns with no exact precedent in the repo — flagged inline.

## Summary

Phase 10 is bigger than "extend three aggregate methods." The status-transition **application/interface layer does not exist yet**: `accept()`, `startPreparing()`, `markReady()`, `complete()` on `Order` (`order.aggregate.ts:243-305`) are called from **nowhere** in application code today — no service, no controller, no route. `OrderRepository` (`ordering/domain/ports.ts`) has no list/query method at all. This phase builds the entire operator-facing order-mutation and order-feed surface from scratch, on top of a cancel/refund pair that was just repaired (`642bf8c`/`32016da`) but still has a real correctness bug: **canceling a _paid_ order today ends in `orders.status = 'refunded'`, not `'canceled'`** — pinned by the new regression test itself (`payment-lifecycle.e2e.spec.ts`, the `'operator cancel of a paid order...'` case, `expect(status).toBe('refunded')`). D-09's "one terminal status `canceled`" requires changing that behavior and updating that test's assertion.

Three other load-bearing facts change the shape of the plan: (1) **preset roles (`manager`/`cashier-foh`/`kitchen`) are baked into each tenant's `organization_role` table at provisioning time** (`seed-preset-roles.service.ts`), not read live from `preset-roles.ts` — editing the preset definitions does not retroactively reach already-provisioned tenants; (2) the global per-IP rate limiter runs **before** `AuthGuard` in the request pipeline (`app.useGlobalGuards` vs `APP_GUARD`), so a naive "key the limiter by `principal.userId`" fix cannot work without either reordering guards or adding a second, later guard and exempting the route from the first; (3) `LocationScopeGuard`'s `!locationId` check runs **before** its owner-bypass line, which is the actual, narrow mechanism behind "an owner in `?location=all` mode 403s on `RefundsController`" — the fix is not necessarily "add `@LocationNeutral()`" (that would remove the non-owner scope check entirely and reopen a cross-location privilege escalation); the correct fix is that the admin client must send the **order's own `locationId`** on every mutation call, never the ambient `'all'` sentinel.

**Primary recommendation:** Treat this phase as three build tracks that can mostly run in parallel after one shared migration + one shared RBAC change land: (A) backend order-mutation surface (new services + controller + repository list method), (B) backend refund/cancel restructure (money-safety fixes), (C) admin SPA feed UI + polling, plus a small (D) website/guest-loop track that has almost no backend dependency. See "Recommended plan decomposition" below.

## Project Constraints (from CLAUDE.md)

- **Tenancy double-enforcement**: every new query on `orders`/new tables MUST go through `ScopedTx` AND rely on Postgres RLS — the existing `orders_location_iso`/`orders_brand_iso`/`orders_iso` policies apply automatically to new columns (RLS is row-level, not column-level; no new policy needed for the migration itself, see Landmines).

- **`correlationId` via `buildEnvelope`** — every new outbox append (status-changed, canceled events from the new services) must use `buildEnvelope`, never a hand-built envelope.
- **No raw SQL outside `packages/db`** — the daily-counter atomic upsert (`INSERT ... ON CONFLICT DO UPDATE ... RETURNING`) must be expressed as a Drizzle query in a repository, not inline SQL in `apps/api`.

- **`.service.ts` = single `execute(input)` public method** — `CancelOrderService`/`RefundOrderService` already follow this; new services must too.
- **WHY-comments only** — the existing code in this area already follows this convention well (see `order-drizzle.repository.ts:80`'s one-line ORD-10 comment); match that density, not more.

## Answers to the research agenda

### A. Data model — the one migration (D-04)

**A.1 — Migration authoring workflow (confirmed, not assumed).**

`pnpm --filter @resto/db db:generate` (`drizzle-kit generate`) is **confirmed broken** for this repo, not merely "reportedly" broken: `packages/db/migrations/meta/` only has real Drizzle snapshots up to `0018_snapshot.json` (`ls packages/db/migrations/meta/`) — every migration from `0019` through the current `0072` was hand-written without ever running a snapshot-producing generate. `08.4-01-SUMMARY.md:132-139` documents the concrete failure: running `db:generate` against the current `schema.ts` diffed against the stale `0018` snapshot and produced 300+ lines of destructive `DROP TABLE ... CASCADE` statements duplicating already-applied migrations. **The actual workflow, confirmed across 08.4's 11 plans:**

1. Edit `packages/db/src/schema/*.ts` (Drizzle table definitions) as the schema source of truth.
2. Hand-write the migration SQL file `packages/db/migrations/00NN_description.sql` — sequential 4-digit zero-padded, matching journal `idx`. Use a `-- 00NN_description.sql` header comment describing the phase/plan and any non-obvious data decision (see `0070_orders_location_id.sql` for the house style — cites the plan, decision ID, and the pitfall being guarded against).
3. Manually append one entry to `packages/db/migrations/meta/_journal.json`: `{"idx": NN, "version": "7", "when": <epoch-ms>, "tag": "00NN_description", "breakpoints": true}`. The `when` timestamps in the existing journal increase by exactly `86400000` (1 day) per entry (e.g. idx 70 → 1783814400000, idx 71 → 1783900800000) — follow that convention for the next entries rather than using `Date.now()`, to keep the journal's implied ordering monotonic and match the existing style.
4. Run `pnpm --filter @resto/db db:migrate` (`packages/db/src/cli/migrate.ts`) — applies via `drizzle-orm/postgres-js/migrator`'s `migrate()`, reading `./migrations` and tracking applied migrations in Drizzle's own `__drizzle_migrations` bookkeeping table (keyed by file hash, independent of the journal). Requires `DATABASE_ADMIN_URL` in non-dev (hard-fails without a fallback per `packages/db/CLAUDE.md`).
5. **Next free migration number as of this research: `0073`.** Verify this is still current at plan-execution time (`ls packages/db/migrations/*.sql | tail -1`), since other in-flight work could land migrations first.

Multiple RLS policy migrations exist as the template for any new RESTRICTIVE policy (not needed for this phase's simple column-adds, but needed if a new table like the daily-counter table wants row-level isolation): `0071_orders_location_rls.sql` — `DROP POLICY IF EXISTS` guarded by a `DO $$ ... IF EXISTS ... END $$` block, then `CREATE POLICY <table>_location_iso ON <table> AS RESTRICTIVE USING (is_system_session() OR current_location_id() IS NULL OR location_id = current_location_id()) WITH CHECK (...)` — this is the exact shape to mirror if the new counter table needs location-grain RLS (recommended — see A.2).

**Tradeoff:** hand-authoring is more manual and error-prone than a generator, but it's the only workflow proven to work in this repo since migration ~0019; do not attempt `db:generate` for this phase's migration even for the "just add columns" case — it will re-produce the same destructive diff, because the snapshot baseline never moved off `0018`.

**A.2 — Short daily order number.**

**Recommendation: a dedicated counter table with an atomic `INSERT ... ON CONFLICT (...) DO UPDATE SET counter = counter + 1 RETURNING counter`, keyed `(tenant_id, location_id, business_date)`.**

```
order_daily_sequences (
  tenant_id   uuid NOT NULL,
  location_id uuid NOT NULL,
  business_date date NOT NULL,
  counter     integer NOT NULL DEFAULT 0,
  PRIMARY KEY (tenant_id, location_id, business_date),
  composite FK (location_id, tenant_id) -> locations(id, tenant_id)
)
```

Generation is one Drizzle statement: `db.insert(orderDailySequences).values({tenantId, locationId, businessDate, counter: 1}).onConflictDoUpdate({target: [...], set: {counter: sql\`${orderDailySequences.counter} + 1\`}}).returning({counter: orderDailySequences.counter})`. This is a single round trip, Postgres serializes it atomically per row (no explicit `SELECT ... FOR UPDATE` needed), and it works correctly under the Friday-evening concurrent-checkout scenario PROJECT.md calls out.

Compared against the other three options named in the agenda:

- **Postgres sequence per location** — rejected. Sequences don't reset on a calendar boundary; you'd need to dynamically `CREATE SEQUENCE` per `(location, date)` at runtime, which is both a "no raw SQL outside `packages/db`" violation if done from application code, and operationally ugly (unbounded sequence-object growth, no migration-based provenance).
- **`MAX(shortNumber) + 1` under the existing tx** — rejected, named failure mode: classic read-then-write race. Two simultaneous checkouts at the same location both read `MAX = 41`, both compute `42`, both insert — either a unique-constraint violation (if defended) or a silent duplicate (if not). This is exactly the "Friday-evening simultaneous order spikes" scenario the project's PROJECT.md explicitly flags as a hard constraint to defend against.
- **Date-prefixed with a per-location counter** — this is not a distinct mechanism, it's the _display format_ of the counter-table approach (e.g. render as `#042`, resetting visually each day); adopt the format, reject it as a separate "option."

Coexistence with the existing `orderNumber`: **do not touch `orders.orderNumber`** (`generateOrderNumber()`, `dto.ts:78-88`, format `20260810-A7K2M`). Add a new column, e.g. `shortNumber integer NOT NULL` (or `text` if you want a formatted `#042` string frozen at creation time — recommend storing the raw integer and formatting client-side, so a future rebrand of the display format doesn't require a backfill). `orderNumber` keeps serving as the value already embedded in the idempotency-key uniqueness story and any existing logs/links; `idempotencyKey` (client-supplied UUID, `dto.ts:30`) remains the true dedup key for `ON CONFLICT DO NOTHING` in `order-drizzle.repository.ts:77`. Nothing about the new short number touches idempotency.

**Timezone caveat (flag, not blocker):** `locations.timezone` (`brands.ts:133`) is nullable — `text('timezone')`, no `.notNull()`. "Business date" for the counter reset needs a timezone to compute local midnight; if `timezone` is unset for a location, fall back to UTC explicitly (document the fallback; do not silently use server-local time, which is an unrelated TZ). This does not block the migration itself but the counter-generation service needs an explicit decision here — flagged in Open Questions.

**`NOT NULL` vs backfill:** `channel` and `marketing_consent` are the two genuinely `NOT NULL`-with-default columns (safe on an `ALTER TABLE ... ADD COLUMN ... NOT NULL DEFAULT ...`, no backfill scan needed — Postgres handles a constant default without a table rewrite lock issue for a `text`/`boolean` default in modern PG versions). `short_number` is trickier: it CANNOT have a single static default (each row needs its own value), so **do not add it `NOT NULL` in the same statement as an `ADD COLUMN`** on a non-empty table — mirror the `0070_orders_location_id.sql` precedent exactly: run a row-count check first (`SELECT count(*) FROM orders`), and if non-zero, either backfill with a one-off script assigning ordinal short numbers to existing rows (grouped by location+day) before setting `NOT NULL`, or — matching the established precedent in this exact table (`0070` cleared 5 stale dev-only rows rather than backfilling them) — clear stale dev/test rows if they're smoke-test artifacts, never synthesize/backfill production-shaped data. All the timestamp/reason/actor/eta/consent columns are naturally nullable (historical orders never had them) so they need no backfill decision at all.

**Cancel reason enum (borrowing iiko's shape where sensible, per canonical refs):** propose a fixed set covering the two intents (reject vs. cancel) without conflating them via wording, since D-09 says "the word 'rejected' never reaches the guest" but the reason code itself is an internal analytics field, not guest-facing copy:
`'guest_no_show' | 'kitchen_out_of_stock' | 'kitchen_too_busy' | 'guest_requested' | 'payment_issue' | 'duplicate_order' | 'other'`
This is a reasonable working set (not verified against iiko's actual API taxonomy — flagged `[ASSUMED]`, see Assumptions Log). Land it as a CHECK constraint (`cancel_reason_chk`) matching the existing `orders_status_chk`/`orders_fulfillment_mode_chk` style in `packages/db/src/schema/ordering.ts:64-72`, not a separate lookup table — consistent with how `fulfillmentMode` and `status` are already modeled as CHECK-constrained text, not enums/FKs.

**A.4 — Feed query shape + the missing index.**

Today `OrderRepository` (`ordering/domain/ports.ts`) has **zero list capability** — only `findById`, `findByIdInTx`, `findByIdempotencyKey`. There is no query to extend; this is 100% new. The feed needs, at minimum:

```sql
SELECT * FROM orders
WHERE tenant_id = $1
  AND (location_id = $2 OR $2 IS NULL)  -- 'all' mode omits this predicate, RLS still scopes by tenant/brand
  AND status = ANY($3)                  -- status filter, e.g. ['paid','accepted','preparing','ready'] for the default view
  AND created_at >= $4 AND created_at < $5  -- date filter, default = today
ORDER BY created_at DESC
LIMIT $6 OFFSET $7  -- or, better, keyset pagination on created_at+id for the poll-delta use case (see D.13)
```

**Recommended composite index:** `(tenant_id, location_id, status, created_at DESC)` — leads with `tenant_id` (matches every other index in this schema, e.g. `orders_idempotency_key_uq`), then `location_id` (the feed's primary scoping dimension per D-02), then `status` (every poll filters live orders), then `created_at DESC` (default sort + date-range filter + poll-delta cursor). A single composite index covers the common case (single-location, status-filtered, date-bounded) via index range scans; the `all`-mode aggregate case (location_id omitted) still uses the index's leading `tenant_id` prefix efficiently since Postgres can still use a partial-prefix scan. Do **not** add a separate single-column index on `status` alone — with realistic per-tenant order volumes (a single restaurant, not a marketplace) it adds write overhead for no meaningful read benefit over the composite.

**Pagination:** for the human-browsing list view (with the date/status/channel filters from D-03), offset/limit is fine — feed volumes are small (single-restaurant scale). For the **poll-delta** specifically (D.13), use a keyset cursor (`since=<ISO timestamp>` or `since=<created_at>,<id>` tuple) rather than offset pagination — offset pagination under a live-inserting table has the classic "page 2 skips/duplicates a row that was inserted between page 1 and page 2" bug, which is exactly the kind of silent-data-loss bug D-13/Product MED-18 worry about.

### B. Permissions (D-06, D-07)

**B.5 — New `order:cancel` verb vs. reuse of `order:update-status`.**

**Current permission matrix (verified in code, not CONTEXT.md's paraphrase):**

| Role/preset                          | Source                  | `order` permissions today        |
| ------------------------------------ | ----------------------- | -------------------------------- |
| `owner` (system role)                | `system-roles.ts:6`     | `['read','update-status']`       |
| `admin` (system role)                | `system-roles.ts:20`    | `['read','update-status']`       |
| `staff` (system role, bare fallback) | `system-roles.ts:29-34` | **none** — no `order` key at all |
| `manager` (custom preset)            | `preset-roles.ts:15`    | `['read','update-status']`       |
| `cashier-foh` (custom preset)        | `preset-roles.ts:27`    | `['read','update-status']`       |
| `kitchen` (custom preset)            | `preset-roles.ts:37`    | `['read','update-status']`       |

Important nuance CONTEXT.md's framing slightly overstates: the three **presets** (manager/cashier-foh/kitchen) — the roles an owner actually assigns to real staff — already have `order:update-status`. The literal "staff has no order permission at all" is only true for a member holding _only_ the bare system-role `staff` slug with no preset assigned (an edge case, not the normal onboarded-staff shape). The real gap is narrower: **there is no `order:cancel` verb anywhere yet** — `update-status` and a hypothetical `cancel` are currently the same bucket only if you choose to reuse the verb.

**Recommendation: add a distinct `order: [..., 'cancel']` verb, do not reuse `update-status`.** Cost is three small, well-isolated edits:

1. `packages/domain/src/rbac/permissions.ts` — add `'cancel'` to the `order` array in `PERMISSIONS_STATEMENT` (feeds directly into `createAccessControl(PERMISSIONS_STATEMENT)` in `access-control.ts:4`, no other wiring needed).
2. `packages/domain/src/rbac/system-roles.ts` — add `'cancel'` to `owner` and `admin`'s `order` array.
3. `apps/api/src/contexts/identity/application/preset-roles.ts` — add `'cancel'` to all three presets' `order` array.

**Tradeoff named:** reusing `update-status` is a zero-file-touch option (all three presets already have it) but semantically conflates "move an order forward through the kitchen" with "terminate an order and trigger a refund" — it forecloses ever wanting a role that can progress orders but not cancel them (e.g. a very junior kitchen role), and makes the audit trail ("who has cancel power") unreadable without cross-referencing every status the verb also gates. Given the cost of the alternative is three one-line array edits, take the more future-proof option now while it's cheap.

**`NON_DELEGATABLE` is unaffected either way** — `packages/domain/src/rbac/non-delegatable.ts:4-9` guards only `tenant.delete/transfer`, `billing.update`, `staff.remove`, and all `ac.*`. `order.cancel` (new or reused) is not in that set and does not need to be — it is _supposed_ to be delegatable per D-06. `containsNonDelegatable()` runs in `create-role.service.ts:38` and `update-role.service.ts:42` before any BA write; verify by reading those two call sites that adding `order.cancel` to a custom role payload does not accidentally trip this guard (it won't, since the resource key is `order` not `billing`, but confirm empirically with a unit test at implementation time — this is a good place for a regression test per `packages/domain/CLAUDE.md`'s "pins what admin must NOT receive" testing convention, adapted to "pins what a custom role CAN receive").

**Landmine — preset permission changes do not reach existing tenants.** `SeedPresetRolesService.execute()` (`identity/application/seed-preset-roles.service.ts`) inserts a **snapshot** of `PRESET_ROLES[i].permission` into the BA-owned `organization_role` table (`permission: JSON.stringify(preset.permission)`) at tenant-provisioning time — it does NOT re-sync on every read. Editing `preset-roles.ts` only affects tenants provisioned _after_ the change. Any tenant that already exists in the target environment (dev/demo seed data, per `tools/scripts/seed/commands/seed-demo.ts` which already creates `cashier-foh` etc.) will keep the old JSON blob and NOT gain `order:cancel` until a manual backfill/reseed touches its `organization_role` rows. Given RestOS has no real paying customers yet (target Q1 2027), this is low-risk _now_, but it is exactly the kind of gap that bites post-launch on the next permission change — flag as a landmine, and for THIS phase, plan a one-time dev-environment reseed (or a small idempotent "sync preset permissions for existing orgs" migration/script) rather than assuming `preset-roles.ts` edits are self-propagating.

**B.6 — `LocationPermissionChecker`: wiring cost.**

`PERMISSION_CHECKER` is currently bound to `BetterAuthPermissionChecker` (`identity-core.module.ts:344-347`), which calls BA's tenant-wide `auth.api.hasPermission` — it has **zero location concept** and ignores `activeLocationId` entirely. `LocationPermissionChecker` (`identity/application/location-permission-checker.ts`) exists, is unit-tested, exported from `IdentityCoreModule`, but is **not** the bound `PERMISSION_CHECKER` implementation. Two concrete gaps, not one:

1. `PermissionsGuard.canActivate()` (`identity/interfaces/http/guards/permissions.guard.ts:47`) calls `this.checker.hasPermission(principal, required, headers)` — **3 args**. `LocationPermissionChecker.hasPermission()`'s signature takes a 4th param, `activeLocationId?: string | null`, which nothing ever supplies. This is a one-line fix: `req.activeLocationId` is already populated on every request by `AuthGuard` (`auth.guard.ts:151`, `req.activeLocationId = sessionData.session.activeLocationId ?? null`) — the same field `LocationScopeGuard` already reads. Passing it through is trivial.
2. **The real cost is item 2, and it's not trivial:** if `PERMISSION_CHECKER` is swapped wholesale to `LocationPermissionChecker`, every route decorated `@LocationNeutral()` (tenant/brand-wide permission checks — e.g. `menu:update` under `@LocationNeutral()` in `catalog.controller.ts:130`) would now be checked by a class whose `hasPermission()` **returns `false` for any non-owner when `activeLocationId` is falsy** (`location-permission-checker.ts:31`, `if (!activeLocationId || !principal.tenantId) return false;`). Since `@LocationNeutral()` routes are specifically the ones that legitimately run _without_ a location context, swapping the checker would 403 every non-owner on every `LocationNeutral` route — a full regression across menu, brand, team, and every other permission-gated route that isn't strictly location-scoped. This is precisely why 08.4 and 08.5 both explicitly deferred the swap (`STATE.md:302` item (b); `08.5-03` re-defer).

**Recommendation for Phase 10: do not perform the global swap. Record the third explicit re-defer per D-07's escape hatch**, and close the _specific_ concern D-07 raises ("Phase 10 is the first phase where a per-location role gates a write path on money") through a narrower, already-adequate mechanism: order-mutation routes are (and must stay, see B.7) protected by the **standard `LocationScopeGuard` non-owner branch**, which independently verifies `activeLocationId === req.activeLocationId` (session-pinned, server-controlled) AND `scope.includes(locationId)` via `MemberLocationScopeReader.findLocationScopeForMember` — this already prevents a staff member from acting on an order outside their assigned location, **regardless of which `PermissionChecker` is bound**. What `LocationPermissionChecker` additionally offers — a _different role per location_ for the same person — is not a capability the product currently exposes (there is no UI to assign per-location differing roles, and `member_location_scope.role` is a single nullable text column, not yet surfaced anywhere) — so the practical gap left by not wiring it is "a staff member has the same role at every location they're scoped to," which is the current behavior everywhere else in the app already, not a Phase 10 regression. Document this explicitly as re-defer #3 with this reasoning, distinct from 08.4/08.5's terser re-defers.

**B.7 — `@BrandNeutral()`/`@LocationNeutral()`/`@OwnerOnly()` audit.**

Confirmed: `RefundsController` (`refunds.controller.ts`) has neither `@BrandNeutral()` nor `@LocationNeutral()` at class or method level — only `@Permissions({billing:['update']})` and `@RequireActiveTenant()`. Root cause, traced precisely: `LocationScopeGuard.canActivate()` (`location-scope.guard.ts:39-45`) throws `location.context_required` on `getLocationId() === undefined` **before** it ever reaches the owner-bypass line (`:65`, `if (principal.baseRole === 'owner') return true`). An owner in `?location=all` mode has `apiFetch` omit the `x-location-id` header entirely (`api-client.ts:48-50`, `opts.locationId !== 'all'` guard), so `getLocationId()` resolves to `undefined`, and the 403 fires before owner-bypass logic is ever reached. This reproduces for **any** route lacking `@BrandNeutral`/`@LocationNeutral`, not just refunds — it will reproduce on every new order-mutation route too if left undecorated.

**The tempting fix — mark every order-mutation route `@LocationNeutral()` — is wrong and must not be applied.** `LocationNeutral` short-circuits the _entire_ guard (`:31`, `if (locationNeutral) return true`), including the non-owner scope-membership check. Since staff can hold `order:cancel`/`order:update-status`, blanket-neutralizing these routes would let a non-owner spoof `x-location-id` (a client-controlled header) to act on an order at a location they are not scoped to — a cross-location privilege escalation within the same tenant, undoing exactly what 08.4 built.

**Correct fix, route by route:**

- **`GET` feed/list route** (new, D-02's "one merged list ... labelled with its location" in `all` mode): **does** need `@LocationNeutral()` — this is the one legitimately-aggregate-across-locations read, mirroring the existing `stopListAggregateQuery` pattern (`apps/admin/src/lib/queries/catalog.ts` + `stop-list.tsx`'s `mode === 'all'` branch). Owner-only in `all` mode (staff never see `all`, per D-02/08.5 D-15).
- **Every mutation route** (accept, reject, start-preparing, mark-ready, complete, cancel, refund) — **do not add `@LocationNeutral()`**. Instead, the fix is at the call site: the admin client must always send the **order's own `locationId`** (available on every row already, since D-02 requires each row in `all` mode to display its location) as `opts.locationId` in `apiFetch`, never the ambient `useEffectiveLocation()` value when that value is the `'all'` sentinel. With a concrete, real `locationId` on the request, `getLocationId()` resolves non-null, the guard proceeds past the `!locationId` throw, and the owner-bypass (or non-owner scope check, for staff) behaves exactly as designed. This requires zero guard changes and zero decorator changes on these routes — only correct plumbing in the admin SPA's mutation call sites.
- **`@RequireActiveTenant()`** stays on every order route (all are already tenant-scoped by definition).
- **`@OwnerOnly()`** is correct only on the discretionary arbitrary-refund route if D-10/D-06 end up wanting a stricter gate than `billing:update` alone provides — but `@Permissions({billing:['update']})` already achieves owner-only in practice today (only `owner` has `billing` in `system-roles.ts:10`), so `@OwnerOnly()` would be redundant, not wrong. Recommend leaving `refunds.controller.ts` on `@Permissions({billing:['update']})` alone (no `@OwnerOnly()` needed) and just adding no location-neutral decorator (per the point above — fix the client, not the guard).

**The real bug this diff must fix (not just widen a guard):** `refund()`'s current body (`:334-336`) does:

```
const isFullRefund = amountMinor + alreadyRefundedMinor === capturedMinor;
const newStatus: OrderStatus = isFullRefund ? 'refunded' : 'paid';
```

This **unconditionally overwrites `order.status`** based purely on refund completeness, discarding whatever fulfillment status the order was actually in (a partial refund silently resets a `preparing` order back to `paid`; a full discretionary refund on a `completed` order would silently flip it to `refunded`, erasing "the food was delivered"). **Fix: `refund()` (the discretionary/non-cancel path) must stop touching `order.status` at all.** Refund state belongs on `payments.status`/`payment_refunds` (already modeled, already correctly updated by `RefundOrderService:96-97` `newPaymentStatus`), not on the order's fulfillment status. `cancel()` is the only method that should ever move the order to a terminal state, and it should do so directly (`status = 'canceled'`), independent of whatever `refund()` does to the payment ledger.

This is proven as a live, currently-shipped bug by the very regression test that was supposed to prove the pre-requisite fix worked: `apps/api/test/e2e/payment-lifecycle.e2e.spec.ts`, the test titled `'operator cancel of a paid order persists the auto-refund transition (row no longer stuck at paid)'` (added in `32016da`) **asserts `expect(status).toBe('refunded')`** for a canceled paid order — i.e. it pins exactly the wrong-for-D-09 outcome as correct, because the narrow scope of that pre-requisite fix was only "get it off `paid`," not "land on the semantically correct `canceled`." **This test's assertion must change to `.toBe('canceled')` as part of implementing D-08/D-09** — flagged again in Landmines.

**C.9 — `wasPaid` fix.**

`cancel-order.service.ts:33`: `const wasPaid = snap.status === 'paid';` — once D-08 widens `cancel()` to allow `accepted`/`preparing`/`ready`, this predicate reads `false` for those statuses even though the order is fully paid, silently skipping the refund. **Recommendation: delete the predicate entirely rather than patching it.** `RefundOrderService.executeWithOrder()` already independently determines refundability by looking up the actual payment row (`refund-order.service.ts:61-64`, throws `PaymentNotRefundableError` if `!payment?.paymentIntentId || !payment.stripeAccountId`). `CancelOrderService` should simply **attempt** the refund unconditionally (wrap in try/catch per D-11's restructure below) and let `RefundOrderService`'s own payment lookup be the single source of truth for "was there anything to refund" — this removes a duplicated, now-provably-fragile heuristic instead of patching it into a second fragile heuristic (e.g. `capturedMinor > 0` derived from `snap.total`, which conflates "order total" with "amount actually captured," not equivalent if a discount/partial-capture scenario ever exists).

**C.10 — D-11 refund-outside-the-transaction restructure.**

**No exact existing precedent for "persist, then call external service outside the tx, then record the outcome" was found in this codebase — this is new architecture for Phase 10, not a reuse.** Verified by reading both money-moving call sites: `create-checkout-payment.service.ts:78-139` calls `this.provider.createPaymentIntent(...)` **inside** `this.db.withTenant(async (tx) => {...})`; `refund-order.service.ts:60-140` calls `this.provider.createRefund(...)` **inside** `this.db.withTenant(async (tx) => {...})` too. Both existing patterns are "everything in one transaction," which is exactly what D-11 says must change for cancel. The closest thing to a **reconciliation** pattern (not a "call-then-record" pattern, but adjacent) is `HandleStripeEventService.handleRefund()` (`handle-stripe-event.service.ts`), which uses `PaymentRepository.updateRefundStatus()` (`payment-drizzle.repository.ts:151`) to update a `payment_refunds` row's status **asynchronously**, driven by an inbound Stripe webhook — that method exists and is currently used only in that inbound-reconciliation direction, but it is the right building block to reuse for the outbound direction too.

**Recommended restructure for the auto-refund-on-cancel path:**

1. **TX1 (short):** `order.cancel(reason, actorUserId)` → `orderRepo.update(order, tx)`. Commits regardless of anything downstream — this is what makes "the order still cancels" true even under a Stripe outage (D-11). Emits `OrderCanceled`/`OrderStatusChanged` via the outbox in the same tx (existing `appendToOutbox` pattern).
2. **After TX1 commits**, if there's a payment to refund: insert a `payment_refunds` row with `status = 'pending'` (the CHECK constraint on `payment_refunds.status` already supports `'pending'`, `packages/db/src/schema/ordering.ts` `payment_refunds_status_chk` — this state is modeled but never used as a _pre_-call marker today, only as the table's default) in a short TX2, so there is a durable record that a refund was attempted even if the process crashes before Stripe responds.
3. **Call `provider.createRefund(...)` with no open DB transaction.**
4. **TX3 (short):** on success, `updateRefundStatus(...'succeeded')` + update `payments.refundedAmount`/`status`, append `PaymentOrderRefundedV1`/`OrderRefundedV1` to the outbox. On failure (Stripe exception, timeout, network error), `updateRefundStatus(...'failed')`, and surface a retryable marker (the `status = 'failed'` row itself is enough of a marker; the admin UI's red-flag/retry affordance queries "any `payment_refunds` row for this order with `status = 'failed'`").
5. **Retry** re-invokes only steps 2-4 against the already-`canceled` order — a small, separate `RetryRefundService` or a re-entrant flag on `RefundOrderService` that skips the `order.refund()` domain-status mutation (since, per C.8's fix, `refund()` no longer touches order status anyway) and just re-attempts the Stripe call + ledger update.

**Tradeoff named:** this is more moving parts (3 short transactions instead of 1 long one) and introduces a window where the order is `canceled` but the refund is still `pending`/`failed` — which is precisely D-11's explicit intent ("the order still cancels; the refund is recorded as failed and surfaced ... with a one-click retry"), not an accidental side effect. The alternative — keep everything in one transaction and roll back the cancel if Stripe fails — is simpler but directly violates D-11 ("Refund failure never blocks the kitchen").

**C.11 — Concurrent Accept from two devices.**

No optimistic-concurrency column exists on `orders` (no `version`/`lock_version`, confirmed absent from `packages/db/src/schema/ordering.ts`). `order-drizzle.repository.ts#update()` (`:131-145`) does a plain `UPDATE ... WHERE id = ? AND tenant_id = ?` with no status-guard in the `WHERE` clause and no row-count check beyond "the row exists" — two concurrent `accept()` calls on the same order both succeed at the DB layer today (last write wins on `status`/`updatedAt`; both emit an `OrderStatusChanged` event, so there'd be two events in the outbox for one logical transition).

**Recommendation: adopt Product persona's MED-17 design as-is — it is sound and cheap.** Make transitions idempotent-by-target-state rather than optimistic-locked: a second `accept()` call on an already-`accepted` order returns success (200) with the current state rather than throwing `InvalidOrderTransitionError`. Only genuinely illegal transitions (e.g. `ready → accepted`) return an error. Concretely: in the new accept/status-transition service, before calling the aggregate method, check `if (snap.status === targetStatus) return snap;` (no-op success) — this is a service-layer concern, not an aggregate-layer one, so `order.aggregate.ts`'s existing strict guards (`InvalidOrderTransitionError`) stay untouched and keep protecting against truly invalid transitions. Add `accepted_by_user_id`/reuse `canceled_by_user_id`-style actor columns if the UI wants to show "Accepted by Maria · 12:04" (Product's suggested mitigation for the UX confusion of two devices racing) — this is a nice-to-have, not required for correctness, since the idempotent-response behavior alone prevents the error-toast problem.

### D. Polling & rate limiting (D-13)

**D.12 — Rate limiter fix.**

Confirmed: `apps/api/src/shared/security.ts:144-180` registers `@fastify/rate-limit` with `global: false` (manual invocation via `RateLimitGuard`, `:243`) and a single shared bucket **keyed by `req.ip` by default** (no `keyGenerator` override), `max: () => env.RATE_LIMIT_PUBLIC_PER_MIN` (default **60**, `env.schema.ts:182`) for every route not matching the auth/internal URL-prefix special cases. The comment at `:153-157` explicitly documents this as a known, accepted-for-MVP-1 limitation ("Single per-IP store across all routes ... Acceptable for MVP-1; a future ticket can per-bucket via `keyGenerator`").

**Arithmetic:** one device polling every 5s = `60/5 = 12` requests/min. A restaurant with 3-4 operator devices (tablets/laptops) behind one NAT/WiFi = `36-48` req/min from polling **alone**, against the shared 60/min-per-IP bucket — before counting any other admin traffic (order detail fetches, location switches) or, critically, **any guest device on the same restaurant WiFi placing an order** (`POST /v1/orders`, `GET /v1/menu` share the exact same IP-keyed bucket per the `security.ts:153` comment — "Single per-IP store across all routes"). At 4 polling devices, `48/60 = 80%` of the entire IP's monthly-fair-share is consumed by polling alone, leaving `12` req/min of headroom for everything else sharing that IP — a single guest checkout flow (menu load + a couple of availability checks + order POST) can plausibly exceed that on its own. This directly reproduces D-13's "MUST FIX for polling to work at all," and it's not restricted to the operators 429ing each other — a guest ordering from the same WiFi can 429 too. This also crosses PROJECT.md's "no per-tenant noisy-neighbor" performance constraint, just within-tenant rather than cross-tenant.

**Why a naive `principal.userId`-keyed fix doesn't work:** `RateLimitGuard` is bound via `app.useGlobalGuards(new RateLimitGuard(rateLimitHandler))` in `main.ts:114` (called before `app.listen`, effectively "runs first" in Nest's guard-resolution order), while `AuthGuard` (which populates `req.principal`) is bound via `{ provide: APP_GUARD, useClass: AuthGuard }` in `identity-http.module.ts:95` — a DI-token-based global guard. **[MEDIUM confidence, not empirically verified in this session]:** based on NestJS's guard-composition order (instance guards registered via `useGlobalGuards()` execute before module-registered `APP_GUARD` providers), `RateLimitGuard` almost certainly runs before `AuthGuard`, meaning `req.principal` is not yet populated when the rate limiter's `keyGenerator` would need it. This is consistent with the limiter's evident design intent (protect against pre-auth brute force too). **Recommend the planner verify this ordering empirically** (a quick `console.log`/breakpoint in both guards against one request) before committing to a fix design — flagged in Open Questions since I could not verify guard execution order without running the app.

**Recommended fix (does not require reordering the global guards):** mirror the existing `BrandSlugRateLimitGuard` pattern (`identity/interfaces/http/guards/brand-slug-rate-limit.guard.ts`) — a small, self-contained, per-route `CanActivate` with its own in-memory `Map<string, Bucket>`, keyed `req.principal && 'userId' in req.principal ? req.principal.userId : \`ip:${req.ip}\``, applied via `@UseGuards(OrdersFeedRateLimitGuard)`on the feed's controller/route (this guard runs in Nest's normal per-controller pipeline, safely *after*`AuthGuard`has populated`req.principal`). Then **add the feed's URL path to the existing `allowList`function** in`security.ts:169-170`(which already exempts`/healthz`and the Stripe webhook path) so the global per-IP bucket does not also count feed-poll requests — otherwise the new per-user guard is additive on top of, not a replacement for, the IP bucket, and the IP bucket remains the bottleneck. Give the new per-route bucket a generous, config-driven cap (new env var, e.g.`RATE_LIMIT_ORDERS_FEED_PER_MIN`, default ~30-40 — enough headroom above the `12/min` a single 5s-cadence device needs, covering multiple browser tabs / brief refetch bursts on refocus, without being effectively unlimited).

**D.13 — Polling/delta endpoint contract.**

Adopt Product persona's MED-18 design (`10-PERSONA-PRODUCT.md` MED-18) as the concrete contract — it is well-specified and fits the schema from A.4: **`GET /v1/orders?status=paid,accepted,preparing,ready&since=<ISO timestamp or opaque cursor>`**. Response: the full matching row set with `created_at > since` (or a cursor tuple `(created_at, id)` to break ties safely) — **not a delta/diff format**, a full re-fetch of "everything currently live that changed since `since`," which the client merges into its local list by `id` (upsert semantics: replace if present, insert if new — naturally handles both "new order arrived" and "existing order's status changed" in one response shape). On every mount, refocus, and reconnect-after-error, the client re-issues the query with `since` reset far enough back to safely re-cover any gap (or, simpler: on refocus specifically, drop `since` entirely and refetch the full default-filtered list — feed volumes are small enough that this is cheap and eliminates any edge case in cursor math). This satisfies "backfills missed orders rather than merely resuming" directly — a request that failed to fire while the tab was backgrounded is invisible to the client's local cursor state, so refocus must not trust the cursor blindly.

**Metrics exclusion:** "the polling endpoint must not be counted as normal request traffic in metrics" — verify how OTel HTTP instrumentation currently tags routes (`@opentelemetry/auto-instrumentations-node`, auto-instrumented, likely tags by route template) and either exclude the feed route's span from default dashboards/alerts via a span attribute (e.g. `http.route` already differentiates it structurally — a poll-vs-mutation route is already a distinct route template, `GET /v1/orders` vs `POST /v1/orders/:id/accept`) or explicitly mark it with a custom attribute (`resto.traffic_kind = 'poll'`) that dashboards can filter on. This is a low-risk, low-effort addition (one span-attribute set in the controller method or a small interceptor) — no existing precedent for "excluded from metrics" routes was found in this codebase, so this is new, minor plumbing.

**D.14 — Admin client-side polling pattern.**

`apps/admin/src/lib/query-client.ts` sets `staleTime: 30_000, retry: 0` globally — no existing `refetchInterval` usage anywhere in `apps/admin/src` (confirmed via grep — this is genuinely new territory for the codebase, not an extension of an established pattern). `apps/admin/src/lib/api-client.ts`'s `apiFetch()` already supports an external `AbortSignal` composed via `AbortSignal.any([timeoutSignal, opts.signal])` (`:42-43`) — pass TanStack Query's own per-request `signal` (from the `queryFn`'s `{ signal }` param) straight through as `opts.signal`, which lets Query cancel an in-flight poll cleanly when a newer one supersedes it (Query does this automatically for `refetchInterval`-driven refetches).

**Recommended query config for the feed:**

The error UI ("Try again" affordance, per `apps/CLAUDE.md`) should render when `isError` — since polling failures are expected to be transient, prefer a small persistent "Reconnecting…" indicator (per Product MED-18's "Live / Reconnecting… pill") over a full-page error state, with a manual "Try again" button/link as the required affordance, not just automatic retry-and-hope.

**E.17 — `GET /v1/orders/:id/status` as a capability URL.**

Confirmed: `@Public()` at class level on `OrdersController` (`orders.controller.ts:32`), no override on `getStatus()` — anyone holding the order UUID can call this with no auth, and the response includes `total`, `currency`, `orderNumber` (`:59-65`). **Recommendation: keep it public, narrow the payload, do not add a token.** Reasoning: (1) the UUID itself is already a 122-bit random capability token in all but name — `OrderId` is a standard `randomUUID()` (`order.aggregate.ts:159`), functionally equivalent to a bearer capability URL, and adding a _second_ token achieves little extra security while adding real complexity (token generation, storage, guest-facing URL construction, expiry policy) for a guest-facing feature whose entire value proposition (D-16) is "share this link, watch it update" — friction here directly undercuts the phase's stated demo value. (2) The actual fix is response minimization, which the endpoint mostly already has right (no customer name/phone/email, no item-level breakdown) — but `total`/`currency` are a mild information leak (a stranger holding a leaked/logged URL learns the order's dollar value) that costs nothing to keep. Given the pin-the-contract instruction, this phase should **freeze the response shape explicitly** (status, total, currency, orderNumber, eta, human-readable status label) as the intentional, documented public contract — not silently grow it further as more surfaces consume it, which is the actual risk Skeptic MED-7 is flagging (scope creep on an already-public endpoint), not the current shape being wrong. This recommendation is a judgment call between reasonable options — flagged in Assumptions Log for founder confirmation given it's a security-posture choice, not a pure code fact.

**E.18 — Marketing consent.**

Website checkout: the consent checkbox belongs in the same form step as the existing `checkout.*` fields already present per the ru.json key dump (`checkout.contactNamePlaceholder`, `checkout.contactPhonePlaceholder` — the contact-info step). Write path: `CreateOrderInput`/`CreateOrderInputDto` (`ordering/application/dto.ts`) needs a new optional boolean field, threaded to `Order.create()` and persisted via the same `save()` insert (`order-drizzle.repository.ts:47-76`) that writes every other order field. **GDPR-relevant storage shape:** per PROJECT.md's GDPR constraint (audit log of PII touches, `AUDIT_ERASURE_SALT`-based anonymization) — store `marketing_consent boolean NOT NULL DEFAULT false` + `marketing_consent_at timestamp` (A.3). **A "text version" field (recording exactly what consent copy the guest saw) was not found as an existing pattern anywhere else in the codebase** (no consent-versioning table/column exists for any other consent flow in this repo) — recommend the minimal two-column shape (flag + timestamp) for this phase, consistent with what's actually precedented, and flag "should consent capture record the exact copy/version shown" as an Open Question for the founder rather than inventing a versioning scheme with no established pattern to follow. Given consent data is guest PII-adjacent, it should be included in the erasure pipeline's PII surface if/when a guest requests erasure — verify against `tenancy_erase_tenant`'s scope at implementation time (out of this research's depth to trace the full erasure function here, flagged as a planner TODO).

**E.19 — White-label leak.**

Confirmed: `send-guest-notification.service.ts:59-60`, `const locale = 'ru'; const brandName = brand?.displayName ?? 'RestOS';`. **Minimum fix (per CONTEXT.md's own framing, "fix the fallback at minimum"):** change the `brandName` fallback from `'RestOS'` to something that doesn't leak the platform's own name into a tenant's guest-facing email — e.g. fall back to a generic non-branded phrase, or (better, and cheap) treat a missing `brand.displayName` as a **hard error** logged loudly (this should never happen — every brand has a `displayName` by construction at provisioning) rather than silently degrading to a platform-name leak. The hardcoded `locale = 'ru'` is a separate, larger concern (no locale-detection/selection exists for guest notifications at all) — leave as `'ru'` for this phase per Claude's Discretion framing in CONTEXT.md (not asked to fix), but do not conflate the two fixes; only the `brandName` fallback is in this phase's minimum-fix scope per the CONTEXT.md wording.

### F. Event payloads (D-05)

Confirmed via direct read of `packages/events/src/contracts/ordering.ts` and `apps/api/src/contexts/ordering/domain/events.ts` + `order-drizzle.repository.ts:252-309` (`domainEventToEnvelope`):

- **`locationId` is absent from every `Ordering*DomainEvent` interface and every `Ordering*V1Payload` Zod schema.** Fix requires two coordinated changes: (1) add `locationId: string` to `OrderCreatedDomainEvent`, `OrderPaidDomainEvent`, `OrderCanceledDomainEvent`, `OrderRefundedDomainEvent`, `OrderStatusChangedDomainEvent` (`events.ts`) — the aggregate already has `this.snapshot.locationId` available at every event-push site, so populating it is a one-line addition per `#events.push({...})` call; (2) add `locationId: TenantId`-sibling field (`z.string().uuid()`) to each `*V1Payload` schema in `contracts/ordering.ts`, and thread `event.locationId` into the corresponding case of `domainEventToEnvelope()`.
- **`OrderPaidV1` hardcodes `total: 0, currency: 'USD'`** (`order-drizzle.repository.ts:276-277`) — root cause confirmed: `OrderPaidDomainEvent` (`events.ts:16-22`) simply doesn't carry `total`/`currency` at all; `markPaid(paymentId, now)` (`order.aggregate.ts:208`) never reads `this.snapshot.total`/`this.snapshot.currency` into the pushed event. Fix: add both fields to `OrderPaidDomainEvent`, populate from `this.snapshot` inside `markPaid()`, use `toMinorUnits(this.snapshot.total)` (already imported, `money-utils.ts`) and `this.snapshot.currency` in the envelope construction. The exact same bug pattern exists for `OrderRefundedV1`'s hardcoded `currency: 'USD'` (`:294`) — `OrderRefundedDomainEvent` (`events.ts:32-38`) also lacks a `currency` field; fix identically.
- **`OrderStatusChangedV1` carries no actor.** Add `actorUserId: string | null` to `OrderStatusChangedDomainEvent` and the Zod payload. **Recommendation against literally reusing the 08.3 WeakMap actor-stash pattern here** — that pattern (`identity/infrastructure/better-auth/auth.config.ts:134-160`, `memberRoleUpdateStash`) exists specifically because Better Auth's plugin hook signatures cannot be extended with extra parameters, forcing an out-of-band WeakMap keyed on BA's internal `ctx.context` object. The ordering aggregate's methods are entirely first-party code with no such interception constraint — the idiomatic, already-established style in this exact file (`cancel(reason: string, now: Date = new Date())` — explicit params) is to **thread `actorUserId` as an explicit method parameter** (`accept(actorUserId, now)`, `cancel(reason, actorUserId, now)`, etc.), sourced directly from `req.principal.userId` in the new controller/service layer that this phase is building anyway. Using a WeakMap here would be solving a non-existent constraint with unnecessary indirection.
- **Guest PII stays out** — confirmed by contrast: `OrderCreatedV1Payload` already omits `customerName`/`customerPhone`/`customerEmail` (only `orderId`, `tenantId`, `brandId`, `orderNumber`, `fulfillmentMode`, `total`, `currency`, `itemCount`) — mirror this minimization for every payload touched; `locationId` and `actorUserId` (an operator's internal user id, not guest PII) are both safe additions under this existing bar.
- **Additive, not `v2`.** Every change above is adding optional-at-the-domain-event-level, required-at-the-payload-level new fields to existing contracts. Since `defineEventContract`'s consumers (`nats-guest-notification.subscriber.ts`, `packages/audit`'s cross-cutting subscriber) parse with `.safeParse()`/schema validation and only read specific named fields, adding new required fields to a payload **does** change the schema (a `.parse()` on an old-shaped stored/in-flight envelope without the new field would now fail) — but since these are live domain events (not replayed from long-term storage) and every producer+consumer in the monorepo is deployed together, this is safe as an additive schema change within `v1`, **provided the deploy adds the new required fields as `NOT NULL`-with-default at the Zod level is avoided** — recommend making the new payload fields required in the Zod schema (matching this repo's existing style of few optional payload fields) since producer and consumer ship in the same deploy; no `v2` contract needed.

**G.22 — Sound + tab-title counter (D-14).**

No existing precedent for either: `grep` for `new Audio(`/`HTMLAudioElement`/`document.title` mutation across `apps/admin/src` returned zero hits — both are net-new browser-API integrations.

**Autoplay policy (real constraint, must be designed around, not discovered late):** Chrome/Safari/Firefox all gate programmatic `HTMLAudioElement.play()` behind a "user activation" requirement — an `Audio.play()` call with no prior user gesture on the page returns a rejected promise and plays nothing, silently, unless the rejection is caught and surfaced. **Recommendation:** default the mute toggle to "sound on," but treat the toggle's own first click (or literally any click on the page, since Chrome's activation model persists for the page's lifetime after any gesture) as the point where audio is "unlocked" — always `.catch()` the `play()` promise and, if it rejects, flip the UI into an explicit "click to enable sound" state rather than assuming silent success. This directly serves D-14's own stated risk ("a silent, purely visual flag is how this feature fails in a real restaurant") — the danger is not just a muted-by-choice operator, it's an operator who never triggered a page gesture (e.g. left a kiosk tablet on the page overnight) getting a _silently failed_ chime with no visual indication anything is wrong.

**`document.title` mutation:** straightforward — a small hook/effect that watches the feed's unaccepted-order count and sets `document.title = count > 0 ? \`(${count}) Заказы\` : 'Заказы'\` (or the existing page-title string, if any is already set via a router-level title mechanism — check for one, not found in this research pass) on mount/update, and restores the base title on unmount. Mute-toggle persistence: `localStorage` (per-device, matches D-14's "no browser push notifications" spirit of keeping this a local, per-tablet setting) — no existing localStorage-persisted-setting precedent was found in `apps/admin/src` either, so this is a small new utility, not an extension.

**Browser background-tab timer throttling (a landmine, see below):** `refetchIntervalInBackground: true` keeps polling attempting to fire every 5s even when the tab isn't focused, but modern browsers throttle JS timers in backgrounded tabs (Chrome clamps to roughly one timer firing per minute after a tab has been hidden for some time) — the "backgrounded tab still signals" promise in D-14 will realistically degrade to "within about a minute" for a long-backgrounded tab, not a strict 5s cadence. This is a browser platform constraint, not a code defect — document it as a known limitation rather than something to "fix," since it cannot be fixed from application code (the Page Visibility / backgrounded-timer-throttling API doesn't offer a bypass for ordinary `setInterval`/`fetch` polling short of a Service Worker + `Notification`/Push, which D-14 explicitly rules out).

## Landmines

1. **`refunded` vs `canceled` on a paid-order cancel** (C.8, C.9) — the current, just-shipped behavior sends a canceled paid order to `status='refunded'`, and a brand-new regression test (`32016da`) actively pins this as correct. Implementing D-09 without updating that test's assertion will look like "I broke the test that was just added to prevent regressions" — it's the opposite; the test encoded the pre-Phase-10 interim behavior on purpose (narrow scope of the prerequisite fix) and must be deliberately updated, not treated as untouchable.
2. **`refund()`'s `newStatus` hardcode silently corrupts fulfillment state** (C.8) — today reachable only from `status==='paid'` so it's invisible, but the instant discretionary refunds are allowed from `accepted`/`preparing`/`ready`/`completed` (D-10's own requirement), the existing `isFullRefund ? 'refunded' : 'paid'` logic will silently reset an in-progress or completed order back to `paid`/`refunded` on every refund call unless `refund()` is changed to stop touching `order.status` at all.
3. **RLS is row-level, not column-level — the new migration needs no new RLS policy statements**, but every existing test/seed fixture that does `tx.insert(schema.orders).values({...})` with a fixed field list will fail TypeScript compilation the moment `channel`/`marketing_consent` (the two truly-`NOT NULL` new columns) are added, exactly as happened in 08.4-08 (8+ files touched for one new `NOT NULL` column). Budget for a fixture sweep, not just the schema/migration work.
4. **Rate limiter guard-ordering assumption is unverified** (D.12) — the recommendation to add a second, per-route, post-auth guard rather than reordering the global ones rests on an untested assumption about NestJS's `useGlobalGuards()` vs `APP_GUARD` execution order. Verify empirically before committing engineering time to either approach.
5. **`@LocationNeutral()` is an attractive-looking but wrong fix for order-mutation routes** (B.7) — it is the literal fix the persona reviews' phrasing suggests ("audit `@BrandNeutral`/`@LocationNeutral`... on every new order route"), but blanket-applying it to mutation routes reopens a cross-location privilege-escalation hole for non-owner staff that 08.4 specifically closed. The fix belongs in the admin client (send the order's real location, not `'all'`), not in the guard decorators, for anything that isn't the aggregate list/feed read.
6. **Preset-role permission edits don't reach already-provisioned tenants** (B.5) — `preset-roles.ts` is a seed template, not a live-read source. Any dev/demo tenant already provisioned in the target environment needs a manual reseed/backfill of its `organization_role` rows after this phase's permission change, or the new `order:cancel` verb (or whatever verb is chosen) silently won't work for that tenant's staff despite the code being "correct."
7. **Browser background-tab timer throttling caps how "live" a backgrounded tab can really be** (G.22) — D-14's "backgrounded tab still signals" is a real, buildable requirement, but its latency degrades to roughly a minute for a long-hidden tab due to browser platform throttling, not application code. Don't let acceptance criteria silently assume a strict 5s cadence holds regardless of tab focus.
8. **Autoplay policy can silently swallow the chime** (G.22) — a page left open without any user gesture (e.g. an overnight kiosk tablet, or a tab restored by the OS/browser after a crash) will have `Audio.play()` reject silently unless the promise rejection is explicitly caught and surfaced as a visible "enable sound" prompt.
9. **08.4 test debt sits directly next to this phase's own e2e work** — `STATE.md:292,295-296` documents `set-active-brand.e2e.spec.ts` + `brand-isolation.e2e.spec.ts` (stale `member_brand_scope` fixture model) and `catalog-reads.e2e.spec.ts` + `catalog-brand-read-isolation.e2e.spec.ts` (403 `location.context_required` from missing `x-location-id` in owner fixtures) as pre-existing, unrelated failures. New order e2e specs in this phase should NOT be debugged against a "is the whole suite green" bar — confirm these specific known-bad files are the only pre-existing red before trusting a full-suite run (compounds with Landmine/H.23's 429 false-failure issue — two independent reasons a full-suite run will show red that has nothing to do with this phase's changes).
10. **`GetOrderService.execute()` takes no explicit `tenantId`** (`get-order.service.ts:12`, only `orderId`) — it relies entirely on `requireTenantContext()` ambient state. This is consistent with the rest of the codebase's ALS pattern and not a bug, but any new service reusing this shape (e.g. an admin-facing single-order-detail fetch) must be called from a genuine HTTP-request context (tenant middleware already bound `TenantId`) — do not call it from a background job/NATS handler context, which per `CLAUDE.md`'s "Architectural Constraints" must use `db.withTenant`/`db.withoutTenant` explicitly, never ambient `requireTenantContext()`.

## Open Questions

1. **Business-day timezone for the daily short order number.** `locations.timezone` is nullable. What should the counter-reset boundary be for a location with no timezone set — UTC, or block short-number generation until a timezone is required at location-creation time? Not resolvable from the codebase; needs a founder/product call, low-stakes but blocking a clean implementation of A.2.
2. **NestJS global guard execution order (`useGlobalGuards()` vs `APP_GUARD`).** The D.12 rate-limiter fix design assumes `RateLimitGuard` runs before `AuthGuard` (so `req.principal` is unavailable at rate-limit time). This is inferred from NestJS's documented composition model, not empirically verified against this specific app's boot sequence in this research session. A 10-minute empirical check (log both guards' invocation order for one request) should happen before or during Wave 2 planning — if the assumption is wrong, the simpler "key the existing global limiter by principal when available" fix becomes viable and the per-route-guard-plus-allowlist design in D.12 could be simplified.
3. **Does an `apps/website` Playwright/e2e harness exist for the guest checkout flow?** Not confirmed in this research pass (only `apps/admin`'s harness was verified). If one exists, the H.23 "two-screen demo" smoke should extend it; if not, the guest-side verification for this phase may need to stay manual/browser-smoke rather than automated, which the planner should decide explicitly rather than assume.
4. **Consent copy versioning.** E.18 flags that no existing consent-versioning pattern exists in the repo. Is a flag+timestamp sufficient for this phase's GDPR posture, or does the founder want the exact consent-checkbox copy/version recorded per order (relevant if the checkbox wording changes later and a regulator/guest asks "what did I actually agree to")? Genuinely a product/compliance call, not resolvable from code.
5. **Capability-URL security posture for `GET /v1/orders/:id/status`.** E.17's recommendation (keep public, freeze the payload) is a reasonable default but is a security-posture judgment call with real alternatives (add a short-lived signed token) that the founder may want to weigh in on explicitly, especially since PROJECT.md names GDPR/compliance as a hard constraint area.
