## `refunds.controller.ts` — audited, `@RequireBrand()` added

`BrandScopeGuard.canActivate()` enforces brand-context requirement on **every** route lacking `@BrandNeutral()`, regardless of whether `@RequireBrand()` is present — `REQUIRE_BRAND_KEY` is set by the decorator but is not read anywhere in `BrandScopeGuard`'s logic (confirmed by reading the guard source; the metadata key exists purely for the audit/documentation convention every other brand-scoped route already follows, e.g. `LocationsController`, `CatalogController`). This means `/v1/orders/:orderId/refund` was **already functionally brand-scoped** before this plan touched it — adding `@RequireBrand()` changes no runtime behavior. It was added anyway for audit-trail consistency, so a future reader scanning this controller's decorator list sees the same explicit marker every other brand-scoped mutation route carries, rather than reading its absence as an oversight. `git diff` on this file shows exactly one line added (`@RequireBrand()`) — `@Permissions({ billing: ['update'] })` is untouched and no `@LocationNeutral()` was added.

## Summary

- Exactly one route (`GET /v1/orders/feed`) carries `@LocationNeutral()` — the aggregate feed read, owner-reachable in `all` mode.
- Every mutation route (`accept`, `advance`, `cancel`, `refund/retry`, `refund`) omits `@LocationNeutral()` on purpose — `LocationScopeGuard`'s non-owner scope-membership check (`member_location_scope`) stays live on all of them, so a non-owner cannot forge `x-location-id` to act outside their scoped location(s). This is proven by `order-routes-authz.e2e.spec.ts` case 4 (forged-header denial + unchanged-row read-back).
- No new route on `OperatorOrdersController`/`OrderCancelController` carries `@Public()` or inherits it — both are new controllers with no class-level `@Public()`/`@BrandNeutral()`, so they cannot accidentally inherit `OrdersController`'s guest-facing exemptions.
- `order:cancel` (not `billing:update`) gates both the cancel and the refund-retry route — a cashier-level preset can refuse an order and retry its own already-decided refund; only an owner (via `billing:update`) can issue an arbitrary-amount discretionary refund.
