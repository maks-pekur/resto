Add to `apps/api/src/contexts/ordering/domain/ports.ts` an `OrderSequencePort` interface with a single method `nextShortNumber(input)` taking `{ tenantId: TenantId; locationId: string; businessDate: string }` and returning `Promise<number>`, paired with `export const ORDER_SEQUENCE_PORT = Symbol('ORDER_SEQUENCE_PORT');` — the same token-plus-interface convention `ORDER_REPOSITORY` and `MENU_PRICING_PORT` already use in that file.
`businessDate` is an ISO `YYYY-MM-DD` string — the caller resolves the calendar boundary, the repository just keys on it.

Create `apps/api/src/contexts/ordering/infrastructure/order-sequence-drizzle.repository.ts` implementing it, `@Injectable()`, injecting `TenantAwareDb` the same way `OrderDrizzleRepository` does.

The increment must be a **single atomic statement**, not read-then-write: a Drizzle `insert` into `orderDailySequences` with values `{ tenantId, locationId, businessDate, counter: 1 }`, an `onConflictDoUpdate` whose `target` is the three primary-key columns `[tenantId, locationId, businessDate]` and whose `set` increments `counter` by one via a `sql` template referencing `orderDailySequences.counter`, and a `.returning({ counter: orderDailySequences.counter })` clause.
Postgres serialises this per row, so two simultaneous checkouts at the same location on the same date get distinct values with no explicit `SELECT ... FOR UPDATE`. Do **not** implement `MAX(short_number) + 1` — that is the classic read-then-write race and this project's PROJECT.md names Friday-evening simultaneous order spikes as a hard constraint to defend against. Do **not** create Postgres sequences per location — they do not reset on a calendar boundary and would need runtime DDL.

Run the statement inside `this.db.withTenant(async (tx) => ...)` so the tenant GUC is bound and both RLS policies apply. `ScopedTx.selectFrom()` cannot express an `ON CONFLICT DO UPDATE ... RETURNING`, so use the raw `tx` handle **with an explicit `eq(orderDailySequences.tenantId, tenantId)`-equivalent guarantee** — here that guarantee comes from `tenantId` being part of both the inserted values and the conflict target, so no row outside the tenant can ever be reached. Add a WHY-comment naming this as the same sanctioned raw-`tx` escape hatch that `catalog-drizzle.repository.ts#listStopListAggregateAcrossLocations` uses (ADR-0020 I-1), and state why `ScopedTx` cannot express it.

Throw nothing on a missing counter row — the upsert creates it. Let the composite FK reject a `locationId` that does not belong to the tenant.

Register in `ordering.module.ts` as `{ provide: ORDER_SEQUENCE_PORT, useClass: OrderSequenceDrizzleRepository }` alongside the existing `ORDER_REPOSITORY` / `MENU_PRICING_PORT` providers.
</action>

| guest checkout → order row               | Untrusted client input crosses here; the server is the sole authority on generated values |
