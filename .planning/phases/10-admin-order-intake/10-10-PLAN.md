Build the Orders page: a dedicated `/{brandSlug}/orders` route inside the existing admin shell with a 5-second polled, grouped, filterable feed of order cards, a sidebar entry carrying an unaccepted counter, and deliberate empty and error states.

Purpose: this is the screen a restaurant stares at during a Friday-evening service. Where a decision trades operator speed against developer convenience, operator speed wins.

Output: the feed page, its queries, the card and badge components, the filter bar, the sidebar entry, and full Russian/English copy — everything except the mutation flows, which plan 10-11 adds.

Row fields: `id, shortNumber, status, locationId, locationName, fulfillmentMode, tableIdentifier, total, currency, itemCount, channel, createdAt, acceptedAt, preparingAt, readyAt, completedAt, canceledAt, etaAt, cancelReason, canceledFromStatus, hasFailedRefund`. **Routing is code-based, not file-convention-based.** Routes are declared with `createRoute({ getParentRoute: () => brandSlugLayoutRoute, path: '/orders', ... })` and then registered by hand in `apps/admin/src/main.tsx`'s `brandSlugRouteTree = brandSlugLayoutRoute.addChildren([...])`. A new route file alone does nothing until it is added there.

**`useEffectiveLocation()`** (`apps/admin/src/lib/hooks/use-effective-location.ts`) is the single per-role location authority: owner → `?location` URL search param (`'all'` or a uuid), staff → the server session pin. Returns `{ mode: 'all' | 'single' | 'none', locationId: string | 'all' | undefined }`. Do not invent a parallel location filter.

**`apiFetch`** (`apps/admin/src/lib/api-client.ts`) — `apiFetch<T>(path, { method?, body?, brandSlug?, locationId?, signal? })`. It composes `AbortSignal.timeout` with `opts.signal` via `AbortSignal.any`, retries once only on idempotent GET 5xx, and **omits the `x-location-id` header entirely when `locationId` is `'all'` or absent**.

**Query defaults** (`apps/admin/src/lib/query-client.ts`): `staleTime: 30_000, retry: 0`. There is no `refetchInterval` usage anywhere in `apps/admin/src` today — polling is genuinely new territory here.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| admin browser → API | Client-side filtering and hiding is UX only, never the security boundary |
| operator → order data across locations | The rendered scope must match what the server enforces |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-10-01 | Elevation of Privilege | Treating client-side location filtering as the isolation mechanism | mitigate | The page sends no location id list; `ListOrdersService` server-resolves the active-location set and RLS backs it. The client renders only what the server returned |
| T-10-10-02 | Denial of Service | Client-side polling amplifying into the shared rate-limit bucket | mitigate | One 5-second query for the page, with the sidebar counter derived from the same query rather than a second poll; the route carries its own per-principal bucket (plan 10-08) |
