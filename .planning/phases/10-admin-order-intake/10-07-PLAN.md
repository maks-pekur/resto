<objective>
Build the operator-facing order-mutation and order-feed application layer, which does not exist today: `accept()`, `startPreparing()`, `markReady()` and `complete()` on the aggregate are called from nowhere, and `OrderRepository` has no list capability at all.

Purpose: this is the entire backend behind ORDINT-01, ORDINT-04, ORDINT-07 and ORDINT-08. Without it the admin page has nothing to call.

Output: forward-transition services that are idempotent by target state, an accept path that captures the operator's prep time server-side, a feed read model with the filters D-03 requires and the cursor D-13 requires, and e2e proof read back from Postgres.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator client → order state machine | Client-supplied values must never determine a persisted promise to a guest |
| caller → location scope | The set of locations a feed reads across must be server-derived, never client-supplied |
| tenant → tenant / location → location | Feed reads and transitions are the phase's widest data surface |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-07-01 | Spoofing | Client supplying `etaAt` directly, promising the guest a time the kitchen never chose (or a skewed clock) | mitigate | The API accepts only `prepMinutes` (integer, 5–180); `eta_at` is computed server-side from `now`; e2e case 2 pins it |
