# Skeptic Review — Phase 8: Payments (Stripe Connect)

> Reviewed against the codebase as of `admin-vite-spa` @ 4d967dd (2026-06-26).
> Scope reviewed: ROADMAP Phase 8 + REQUIREMENTS PAY-01..13 / SITE-08 / GNOTIF-01..04,
> the `ordering` and `tenancy` contexts, `payments` schema, outbox/inbox primitives,
> the email port, website checkout, and the founder decisions of 2026-06-26.

## TL;DR

- **The phase is mis-scoped two ways at once.** PAY-12 (leader-health probe) is **already ~80% built and tested** before Phase 8 starts (`apps/api/src/infrastructure/outbox-dispatcher.service.ts`, `apps/api/src/health/health.controller.ts`) — it is mostly planning theater. Meanwhile the *actual* money path is far bigger than "replace the Noop adapter": there is **no Stripe SDK, no PaymentIntent path, no webhook endpoint, no order→paid/refunded caller, no guest-email surface, and the website checkout button is a hard-disabled stub**. The 18 requirements undercount the work by a wide margin.
- **The two highest-bite risks are not in any requirement.** (1) The "retry on the SAME order" flow (founder decision 4) has **no idempotency guard against a late-succeeding first PaymentIntent** → double-charge. (2) **Disputes/chargebacks are out of scope with no acknowledgement** — the one Stripe event class that takes real money *back* from a connected restaurant is unhandled, and your own api-review (`.planning/notes/api-review-2026-06-15.md:277`) already named it a blind spot.
- **`application_fee = 0` is fine for the restaurant but does NOT make payments free for RestOS.** Stripe bills the **platform** for Connect/active-account and (in some regions) cross-border/payout fees regardless of your application fee. "0% to the restaurant" can still be a per-active-account monthly cost to you. This needs to be a written, owned decision, not an assumption.

## Under-engineering / MVP Loopholes

| Thing | Risk to first 10 paying tenants | Evidence |
|---|---|---|
| **No double-charge guard on "retry same order"** | A guest's first PaymentIntent is slow (3DS, bank latency); the UI shows "failed"/timeout; guest retries; a SECOND PaymentIntent is created on the same order; the first then succeeds late. Two charges, one order. Refunding one costs the restaurant a Stripe fee and a confused guest. | Founder decision 4 ("retry on the SAME order — new PaymentIntent"); `order.aggregate.ts:201` `markPaid` only guards `created→paid` state, not "is there already an in-flight PI?"; no requirement addresses concurrent PIs |
| **Disputes / chargebacks entirely out of scope, unacknowledged** | `charge.dispute.created` removes funds from the connected restaurant's balance and (on a destination charge) can claw back from the platform. No webhook handler, no order state, no operator surface, no requirement. Your own api-review already flagged this. First fraudulent or "card not present" dispute = silent money loss + no operator visibility. | `.planning/notes/api-review-2026-06-15.md:277` ("обработка `charge.dispute`/`refund.updated`… слепая зона"); zero PAY-* requirement mentions disputes |
| **Partial refund has no data model** | ORDINT-06 ("refund specific items") and PAY-09 ("partial") cannot be recorded. A manager refunds 1 of 3 items; the system can only flip the whole payment to `refunded` or nothing. Reconciliation against Stripe will not match. | `order.aggregate.ts:293-306` (full-only), `schema/ordering.ts:125-161` (no refunds table / no partial column) |
| **KYC-never-completes has no terminal state** | PAY-13 gates the "Accept payments" switch on KYC, but there is no requirement for what happens if onboarding stalls forever (Stripe requires more docs, restaurant abandons). The tenant aggregate has `stripeAccountId` but **no onboarding-status / charges_enabled / payouts_enabled field** (`tenant.aggregate.ts:29-45`). | **Order currency vs Stripe-account currency mismatch unchecked** | Founder decision 3 fixes currency per tenant at onboarding, but nothing asserts the order's currency == the connected account's settlement currency at PaymentIntent creation. A misconfigured tenant (currency picked at provision ≠ Stripe account country) gets cryptic Stripe errors at the worst moment — the first real sale. | `create-order.service.ts:35` takes currency from menu snapshot; no cross-check against `stripeAccountId` country/currency; `tenant.aggregate.ts:35` `defaultCurrency` set at provision independently of Stripe |
| **Webhook-before-checkout-return ordering** | `payment_intent.succeeded` can arrive at your webhook *before* the guest's browser returns to the confirmation page. | **Refund webhook vs manual refund double-count** | Operator clicks refund → you call Stripe → Stripe sends `charge.refunded`/`refund.updated` webhook → if the webhook handler ALSO transitions the order, you double-apply. inbox-dedup keys on `envelope.id`, not on "this refund was operator-initiated," so the manual path and the webhook path are two different idempotency domains. | `run-deduped.ts:27-31` (no external-effect guard); PAY-09 manual path + PAY-10 webhook path not reconciled in requirements |
| **No webhook-endpoint test strategy with no prod** | ROADMAP:350 defers prod and says webhooks are "covered free by Stripe CLI / Cloudflare Tunnel." ## Top Risks (severity-classified)

1. **[BLOCK] Double-charge on "retry same order".** The founder-chosen retry-on-same-order flow (decision 4) has no guard against a first PaymentIntent that succeeds *after* the guest gave up and retried. Concretely: cancel/replace the prior PI before creating a new one (`PaymentIntent.cancel` on the stale PI, or reuse the same PI and `confirm` again), and make `markPaid` reject a second succeeded-webhook for an already-`paid` order (it currently throws `InvalidOrderTransitionError` — good — but the *second charge* still exists at Stripe and must be auto-refunded). Without this, the first real flaky-network sale double-charges a guest. Evidence: `order.aggregate.ts:201`, founder decision 4.

2. **[BLOCK] `application_fee = 0` does not zero RestOS's per-transaction cost — confirm the charge topology and the platform-fee exposure in writing.** With a destination charge (PAY-06) and `application_fee_amount = 0`, **the platform (you) is the merchant of record for Stripe-fee purposes** and Stripe's processing fees come out of the charge before transfer — but Connect itself bills the platform for active connected accounts and certain payout/cross-border fees regardless of your app fee. Decide explicitly: (a) **direct charge + `on_behalf_of`** (restaurant pays Stripe, restaurant is MoR, you pay only Connect platform fees) vs (b) **destination charge** (you front fees). At fee=0, (a) is usually cheaper for you and cleaner for restaurant tax/reporting. This is a money-on-the-platform decision currently made implicitly by PAY-06's wording. Evidence: PAY-06; founder decision 1.

3. **[BLOCK] Disputes/chargebacks are unhandled and unacknowledged.** `charge.dispute.created` is the only Stripe event that moves money *backward* out of a restaurant (and possibly the platform). No requirement, no state, no operator surface. At minimum: ingest the dispute webhook, mark the order `disputed`, and notify the operator. Silent fund clawbacks with no operator visibility is the fastest way to lose your first customer's trust. Evidence: `.planning/notes/api-review-2026-06-15.md:277`; zero PAY-* coverage.

4. **[HIGH] Partial refund is unrepresentable.** ORDINT-06 / PAY-09 / FIN-03 all promise partial refunds; the domain (`refund()` full-only, `order.aggregate.ts:293-306`) and schema (no `refunds` table, `schema/ordering.ts`) cannot record them. This needs a schema migration (a `refunds` child table keyed to `payments` with amount + Stripe refund id + reason) **before** real payments exist — adding a constraint after data is painful. Evidence: `order.aggregate.ts:293`, `schema/ordering.ts:125-161`.

5. **[HIGH] No server-side "can this tenant accept money?" predicate.** PAY-13 gates the UI switch, but the *authoritative* gate must be server-side at PaymentIntent creation. The tenant aggregate has no onboarding-status / charges_enabled field (`tenant.aggregate.ts:29-45`). A bug or a stale UI must not let an un-KYC'd tenant create a PaymentIntent that Stripe will reject (or worse, accept into a restricted account that can't pay out). Add `stripeChargesEnabled` / onboarding-status to the tenant snapshot, populate from `account.updated`, and check it server-side. Evidence: `tenant.aggregate.ts:36`, PAY-05/PAY-13.

6. **[HIGH] inbox-dedup gives false confidence for external side effects (PAY-10).** The refund call and the four guest emails are external; `runDeduped` only dedups the DB write (`run-deduped.ts:27-31`). Without a Stripe idempotency key on the refund call and a per-`(order, transition, channel)` send-once marker for emails, a redelivered webhook double-sends emails and *can* double-call refund. Make external idempotency explicit per `packages/events/CLAUDE.md` "I-5b". Evidence: `run-deduped.ts:27-31`, `packages/events/CLAUDE.md`.

7. **[HIGH] Confirmation-page consistency at the webhook race.** `payment_intent.succeeded` is async through outbox→inbox; the guest's redirect to SITE-08 can beat the state transition. The status-polling endpoint that would paper over this is in **Phase 10**, which *depends on* Phase 8. SITE-08 needs at least a poll-with-backoff against order status, or it will show "pending" on paid orders to real guests. Evidence: ROADMAP Phase 10 SC-5; PERSONA-REVIEWS:185.

8. **[MED] 30s SLA vs 60s default.** PAY-12 and the env comment say 30s; `OUTBOX_STALL_THRESHOLD_MS` defaults to 60_000 (`env.schema.ts:49`). Either fix the default to 30_000 or fix the requirement text. A leader can be wedged for ~60s (during which `payment_intent.succeeded` outbox events don't publish → no confirmation emails) before the LB drains it. Evidence: `env.schema.ts:49` vs PAY-12.

9. **[MED] Stale-leader probe has a startup blind spot.** `getOutboxLeaderHealth()` keys staleness on `lastDispatchAt` = *last successful publish* (`outbox-dispatcher.service.ts:170`). A leader that wedges at startup with `lastDispatchAt = null` and then accumulates a backlog reports `staleMs = null` → `/readyz` stays OK forever (`health.controller.ts:101-110` treats null as healthy). The probe catches a leader that *was* working and stopped, but not one that *never started* while holding the lock — exactly the case PAY-12 says it closes. Track "last poll attempt" (or backlog age) instead of/in addition to "last successful publish." Evidence: `outbox-dispatcher.service.ts:96-99`, `health.controller.ts:101`.

10. **[MED] Owner-only refund has no break-glass.** Operationally brittle (see loopholes table). Decide a `refund` permission or owner-delegation before launch. Evidence: founder decision 2.

11. **[MED] Website checkout is a disabled stub with no order-placement path.** The "Place order" button is hard `disabled` and `onSubmit` only `preventDefault()` (`checkout-form.tsx:51-53,127-140`); nothing in `apps/website` calls `POST /v1/orders`. Phase 8 must build the entire website → create-order → PaymentIntent → confirmation flow, not just the Stripe adapter. This is uncosted in the "replace Noop" framing. Evidence: `checkout-form.tsx`; `grep` shows no website order call; `markPaid`/`refund` have zero non-test callers.

12. **[LOW] Stale ADR citations in shipping code.** `stripe-connect.adapter.ts:8` and `tenancy/domain/ports.ts:43-47` cite "MVP-2 / ADR-0009 / ADR-0010 / ADR-0012"; payments is MVP-1 Phase 8 and CLAUDE.md says there is no ADR directory. Strip on touch. Evidence: code vs CLAUDE.md "Key Decisions … NOT a separate ADR directory".

## Top 3 Things I Would Cut or Defer

1. **GNOTIF-04 "per-locale" templates → defer to multi-locale tenant #2.** Ship one locale (the tenant's `locale`) with a minimal branded layout for customer #1. The per-locale × 4-template matrix is gold-plating before a single second-language tenant exists. Keep the brand theming (logo + accent) — that one *is* table-stakes.
2. **`outbox.is_leader` OTel gauge → make it a 1-line add, not a phase headline.** On a single-VPS / single-replica deploy (ROADMAP:350) the gauge is a dashboard ornament. The `/readyz` 503 already does the operationally-important thing. Don't let PAY-12 read as meaningful payment scope.
3. **Destination-charge `application_fee_amount` plumbing → reconsider vs direct-charge before building.** If decision 1 (fee=0, restaurant bears Stripe fees) holds, a **direct charge with `on_behalf_of`** likely removes both the app-fee plumbing *and* a chunk of your platform fee exposure. Cutting the destination-charge topology may be cheaper to build *and* run.

## Top 3 Things That Should NOT Be Deferred

1. **Double-charge prevention on retry (BLOCK #1).** This is the single most likely way a real guest gets hurt in week one. Cancel/replace the stale PaymentIntent and auto-refund any late-succeeding orphan charge. Non-negotiable before taking money.
2. **A server-side "tenant can accept payments" predicate + onboarding-status field (HIGH #5).** Add `charges_enabled`/onboarding-status to the tenant snapshot now and gate PaymentIntent creation on it server-side. The UI gate (PAY-13) is not a security control; this is.
3. **Dispute webhook ingest + operator notification (BLOCK #3) and the partial-refund schema (HIGH #4).** Both are "add the constraint/table before the data exists" items. Disputes move money out of a restaurant silently; partial refunds are promised in three requirements and unbuildable as-is. Schema changes after real payment rows are expensive and risky.
