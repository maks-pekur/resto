# CTO Review — Phase 8: Payments (Stripe Connect)

> Lens: operational + technical risk, build-vs-buy. Reviewed against the live codebase
> (seams that Phase 8 must reuse), not against prior internal audits. This is a
> **forward-looking review** — `.planning/phases/08-payments-stripe-connect/` is empty;
> there is no phase plan or design doc yet. Findings below are the things I want
> nailed down in the plan _before_ a line of the real adapter is written.

## TL;DR

- **The charge type contradicts the monetization model.** Founder decision #1 says the _restaurant_ bears Stripe processing fees, but a **destination charge makes RestOS (the platform) the Stripe fee payer by default**. With `application_fee_amount = 0` you'd be paying every restaurant's processing fees out of pocket. This is a **BLOCK** — resolve charge-type semantics (`on_behalf_of` + fee-payer config, or destination-on-behalf-of, or separate charge model) before design freezes.
- **The data model is not ready for the money path.** The `payments` table has one nullable `provider_payment_id` and no `refunded_amount`/`application_fee`/`stripe_account_id`/`payment_intent_id` columns; the `Order` aggregate has no `created → created` retry path and no partial-refund concept; there is **no onboarding/KYC status or capability field anywhere**. These are schema + aggregate changes, not adapter wiring — they must be in the plan as their own slice.
- **The plumbing you need mostly exists and is good.** Inbox-dedup (`run-deduped.ts`), transactional outbox, advisory-lock leader election, the Resend retry/timeout/idempotency-key pattern, and the G-03 readiness probe are all already shipped and directly reusable. PAY-12 is ~70% done already. The risk in this phase is **money-path correctness and state-machine races**, not missing infrastructure.

## Architecture Assessment

The good news first: the seams Phase 8 needs are real and the existing code shows the team already knows how to build idempotent, tenant-safe, retrying integrations. `apps/api/src/contexts/identity/infrastructure/email/resend.adapter.ts` is, in effect, a _reference implementation_ for the Stripe adapter — bounded retry budget with jitter, hard send-timeout via `Promise.race`, idempotency keys threaded into the SDK call, and terminal-failure emission to the transactional outbox via `db.withTenantId(...)`. The webhook handler should be a structural clone of `nats-audit-subscriber.ts:56` — wrap the handler body in `runDeduped(db, envelope, consumer, tx => ...)` keyed on the **Stripe event id**, exactly as the inbox helper intends (`packages/events/src/inbox/run-deduped.ts:35`). Idempotency, dedup, and tenant-scoped writes are solved problems here; do not reinvent them.

The PAY-12 leader-health probe is the single most over-specified item in the phase, because **it is already built**. `apps/api/src/infrastructure/outbox-dispatcher.service.ts` elects a leader via a Postgres session advisory lock (`pg_try_advisory_lock(4815115)`), heartbeats `lastDispatchAt` on every successful publish, and exposes `getOutboxLeaderHealth()`. `apps/api/src/health/health.controller.ts:96` already drains a stalled leader from the LB via 503 (G-03), threshold-driven by `OUTBOX_STALL_THRESHOLD_MS`. The only genuine gap vs. the PAY-12 wording is the **`outbox.is_leader` OTel gauge** — the service emits `outbox.delivered` / `delivery_lag_ms` / `claim_failures` counters but no leader gauge. That's a 10-line `createObservableGauge`. The probe's _design_ has one real flaw worth a finding (false-negative on a never-dispatched leader), covered below.

Now the real concern: **the money path crosses three async boundaries that the current model does not reconcile.** (1) Stripe Checkout return URL fires in the guest's browser; (2) `payment_intent.succeeded` arrives via webhook on an independent connection with no ordering guarantee relative to (1); (3) the `OrderPaid` domain event then flows through the outbox to whatever sends the confirmation email. The `Order` aggregate's `markPaid()` (`order.aggregate.ts:189`) throws `InvalidOrderTransitionError` unless status is exactly `created`. That is correct for idempotency _if and only if_ the webhook is the sole writer of `paid` and the browser-return path never tries to transition — but the phase scope describes both a confirmation page (SITE-08) and webhook-driven `paid`, so the plan must explicitly designate **the webhook as the single source of truth** and make the browser return a _read-only poll_ of `GetOrderService`. If both can write, you get a transition race and a thrown 500 on the loser. This is solvable, but it has to be a stated invariant, not an accident of ordering.

Finally, **the operator surface this phase implicitly depends on does not exist yet.** `OrderRepository` (`contexts/ordering/domain/ports.ts:4`) exposes only `save`, `findById`, `findByIdempotencyKey`. There is no accept/ready/refund service, no operator order controller (`interfaces/http/` has only the guest `orders.controller.ts`). The aggregate has `accept()`/`markReady()`/`refund()` methods but **nothing calls them**. GNOTIF-02/03 (status emails on `accepted` and `ready`) therefore depend on operator transitions that are scheduled for **Phase 10 (Admin Order Intake)**, which the ROADMAP lists _after_ Phase 8. Either GNOTIF-02/03 slip to Phase 10, or Phase 8 grows an operator transition slice. Pick one in the plan — do not discover it mid-build.

## Top Strengths

1. **Idempotency + dedup infrastructure is production-grade and reusable.** `runDeduped` (`packages/events/src/inbox/run-deduped.ts:35`) gives at-most-once handler execution keyed on event id, committing the inbox marker and the handler's DB writes in one transaction. Keyed on the Stripe event id, this _is_ your webhook idempotency story — no new mechanism required. The doc comment even calls out the external-side-effect caveat (ADR-0020 I-5b: use `envelope.id` as the external idempotency key), which is exactly the discipline a payments adapter needs.

2. **The Resend adapter is a ready-made template for the Stripe adapter.** `resend.adapter.ts` already encodes the hard parts of any third-party money/comms integration: bounded retry with jitter (`RETRY_DELAYS_MS`), a 5.5s hard timeout via `Promise.race`, idempotency keys on the SDK call, retryable-vs-terminal classification (`isRetryable`, 4xx terminal / 5xx retry), and terminal-failure emission to the outbox. Clone this shape for `PaymentIntent`/`Refund` creation and you inherit a vetted failure model.

3. **PAY-12 is mostly already shipped.** Leader election (advisory lock on a reserved/direct connection — `outbox-dispatcher.service.ts:113`, with the Neon-PgBouncer footgun already mitigated via `DIRECT_DB_CONNECTION`), heartbeat-on-publish, and the readiness drain (`health.controller.ts:96`, G-03) all exist. The phase only needs the `is_leader` gauge and a small fix to the staleness semantics (see risks).

4. **Defense-in-depth boot assertions set the right precedent for Stripe config.** `main.ts` refuses to start on RLS bypass, missing GUC lock, mis-wired email adapter, and dev-fallback secrets in prod (`assertProdGuardrails`). The same pattern should gate Stripe: fail fast at boot if `STRIPE_WEBHOOK_SECRET` / `STRIPE_SECRET_KEY` are dev-fallback values in a non-dev env, and (like `assertEmailAdapterWired` pings Resend) ping Stripe's `/v1/account` to surface a bad key loudly before the first checkout.

5. **Tenant-safe non-HTTP write path is already defined and enforced.** Webhooks are not HTTP-middleware-tenant-bound, and the codebase already mandates `db.withTenantId(tenantId, ...)` for exactly this case (ADR-0020 I-6, enforced by the `withoutTenant` callsite fence). The Stripe webhook handler has a clear, lint-enforced rule for how to bind tenant context — no new policy decision needed.

## Top Risks (severity-classified)

1. **[BLOCK] Destination charge + `application_fee_amount = 0` makes RestOS pay every restaurant's Stripe fees.** Founder decision #1: the restaurant bears processing fees; RestOS monetizes via flat subscription. But for a **destination charge, the platform is the Stripe fee payer by default** — Stripe debits the platform for processing fees and the application fee is the _only_ thing that flows back to the platform. With the app fee at 0, RestOS eats ~1.5–3.3% of every order across all tenants with zero offsetting revenue. This is a direct contradiction between the chosen charge type (scope) and the business model (founder decision). **Resolution must precede design:** either (a) configure the connected account as fee payer (`on_behalf_of` the connected account + appropriate `transfer_data`, making it effectively the merchant of record so it bears fees and owns the customer relationship), or (b) use **destination charge with `on_behalf_of`** so settlement/fees land on the connected account, or (c) accept that RestOS bears fees and re-price the subscription to cover them (a real margin decision, not a code decision). Note the secondary implication: whoever is "merchant of record" / `on_behalf_of` drives **which entity's name appears on the guest's card statement** and **who carries chargeback/dispute liability** — a restaurant SaaS almost certainly wants the _restaurant_ on the statement and bearing disputes, which also argues against a vanilla platform-liable destination charge. Decide this with a Stripe-savvy read of `on_behalf_of` semantics before writing the adapter.

2. **[BLOCK] The `payments` table cannot represent the required money path.** `packages/db/src/schema/ordering.ts` payments table has: single nullable `provider_payment_id`, status in `{pending,succeeded,failed,refunded}`, unique on `(provider, provider_payment_id)`. Problems: (a) **no `refunded_amount`** — partial refunds (founder decision #2) cannot be tracked; a `refunded` status is binary and loses the "refunded 12.00 of 40.00" state. (b) **No place for both a PaymentIntent id and a Refund id** — a refund creates a _new_ Stripe object; you cannot store its id without overwriting the PI id or adding a row, and the unique index would collide if you reuse the column. (c) **No `stripe_account_id`** on the payment — for reconciliation and dispute handling you need to know which connected account the charge landed on. (d) **No `application_fee` / `stripe_fee`** captured for finance (Phase 14). (e) Status enum has no `partially_refunded`. **This is a schema migration + aggregate redesign**, and it must be its own slice in the plan, sequenced before the adapter. Recommend: add `payment_intent_id`, `latest_charge_id`, `refunded_amount` (money, default 0), `stripe_account_id`, `application_fee_amount`, and either a `payment_refunds` child table (cleanest — one row per Stripe refund, composite-tenant-FK per ADR-0020 I-2) or a `partially_refunded` status. Composite FK + `tenant_id` discipline (CLAUDE.md invariant) applies to any new child table.

3. **[HIGH] Webhook raw-body capture is not configured — signature verification will silently break.** Stripe signature verification (`stripe.webhooks.constructEvent`) requires the **exact raw request bytes**. Fastify pre-parses JSON into `req.body` (`shared/security.ts` registers helmet/cors/rate-limit but no content-type parser carve-out), so by the time a NestJS controller sees the body it has been parsed and re-serialization will not byte-match → every signature check fails, or worse, someone "fixes" it by skipping verification. The plan must add a **per-route raw-body parser** for the webhook path only (Fastify `addContentTypeParser` scoped to the Stripe route, or a dedicated Fastify plugin registered before NestJS routing, mirroring how the BA `preHandler` hook is scoped in `security.ts`). This is a known Fastify+Nest+Stripe footgun and needs an explicit, tested solution. Also: the webhook route must be `@Public()`, exempt from the per-tenant rate-limit bucket, and **exempt from the CORS/Origin allowlist** (Stripe sends no Origin) — verify it lands in the `RATE_LIMIT_INTERNAL`/allowlist path, not the public 429 bucket that could drop a legitimate retry storm.

4. **[HIGH] Webhook ↔ checkout-return race can throw 500s and double-process.** As described in the assessment: `markPaid()` requires status `created` (`order.aggregate.ts:190`) and throws otherwise. If both the browser return and the webhook attempt the transition, the second loses with `InvalidOrderTransitionError` → 500. Mitigation must be explicit in the plan: **webhook is the only writer of `paid`**; the confirmation page (SITE-08) is a read-only poll of `GetOrderService` and shows a "confirming payment…" interstitial until the order flips to `paid`. Additionally, **handle out-of-order / replayed events**: Stripe does not guarantee delivery order, so a `payment_intent.payment_failed` for a stale PI must not clobber a subsequently-`paid` order, and a retried `succeeded` must be a no-op (the `created`-guard gives you that, but only if `markPaid` is reached idempotently inside `runDeduped`). The guest "retry on the same order with a new PaymentIntent" (founder decision #4) means **one order can have multiple PaymentIntents over its lifetime** — the model must tolerate N PIs per order and only the _succeeded_ one drives `paid`. The current single `provider_payment_id` column cannot express this (ties back to risk #2).

5. **[HIGH] No idempotency key on PaymentIntent/Refund _creation_ → duplicate charges/refunds on retry.** The adapter's outbound calls (create PI, create refund) must pass a **Stripe `Idempotency-Key`** derived from a stable order/refund identifier (e.g. the order id + attempt, the refund request id). Without it, a network timeout on `paymentIntents.create` that actually succeeded server-side, followed by the adapter's own retry (per the Resend-style retry budget you'll clone), creates a **second PaymentIntent / second refund** — i.e. double-charge or double-refund. The Resend adapter already models the timeout-then-retry path (`SEND_TIMEOUT_MS` + `RETRY_DELAYS_MS`); that exact pattern, applied to money without an idempotency key, is a double-spend generator. This must be a hard requirement in the adapter contract, with the key deterministic across retries.

6. **[HIGH] KYC / capability state machine is unmodeled — "only the live switch is gated" has no data to gate on.** Success criterion PAY-13 says full product access during KYC, only "Accept payments" gated on completion. But there is **no onboarding-status or capability field**: `tenants` has only `stripe_account_id` (nullable). `account.updated` delivers `charges_enabled`, `payouts_enabled`, `requirements.currently_due`, `requirements.disabled_reason` — none of which has a home. Phase 8 must model an explicit onboarding state (at minimum persist `charges_enabled` and `payouts_enabled`, ideally `requirements_currently_due` for the admin "what's left" UX) on the tenant aggregate, and the "Accept payments" switch + the checkout guard must read `charges_enabled`, **not** `stripe_account_id != null` (an account can exist with charges disabled). Partial-capability handling matters: a connected account can have `charges_enabled: true` but `payouts_enabled: false` (KYC incomplete for payouts) — guests can pay but the restaurant can't get the money, which is a support nightmare if surfaced wrong. Decide the policy (block live switch until both? allow charges, warn on payouts?) and model the states.

7. **[MED] `tenants.stripe_account_id` vs `brands.stripe_account_id` ambiguity — which account does a destination charge route to?** Both `tenants` and `brands` carry `stripe_account_id` (schema confirmed). The scope says "routed to the tenant's Stripe account." Founder decision #3 says single currency per tenant fixed at onboarding. So the tenant is the connected-account owner — but the brand column exists and will tempt a future dev to onboard per-brand. The plan must **declare the tenant as the sole Connect account holder for MVP** and either drop `brands.stripe_account_id` or document it as reserved/unused, otherwise checkout has two candidate accounts and a latent "which one wins" bug. (Cross-ref: the team already shipped cross-brand catalog read leaks recently — CR-04 — so brand-vs-tenant scoping ambiguity is a demonstrated failure mode in this codebase.)

8. **[MED] PAY-12 staleness probe has a false-negative window and a false-positive shutdown risk.** `getOutboxLeaderHealth()` returns `staleMs = null` when `lastDispatchAt` is null (`outbox-dispatcher.service.ts:99`), and `checkOutboxLeader()` treats `staleMs === null` as OK (`health.controller.ts:107`). So a leader that acquired the lock but has **never successfully dispatched** (e.g. NATS publish wedged from the first tick) reports _ready_ forever — the exact failure PAY-12 wants to catch is invisible until _after_ the first success. Fix: treat "leader for > threshold with zero dispatches AND a non-empty outbox" as not-ready, or heartbeat `lastDispatchAt` on lock-acquisition so the clock starts immediately. Conversely, on an **idle queue** the leader legitimately never dispatches; a naive ">30s since last dispatch = unhealthy" would false-positive and drain a perfectly healthy instance. The current code dodges this by only checking staleness once `lastDispatchAt` is set, but that's the same line that creates the false-negative. The correct signal is "leader AND outbox has undelivered rows older than threshold AND no dispatch in that window" — i.e. probe should consult outbox backlog age, not just the in-memory heartbeat. This is a real design refinement, not a cosmetic one.

9. **[MED] Sandbox/test strategy for a money path with no production environment.** Prod is deferred to first-customer + VPS (ROADMAP 2026-06-26); webhooks reach localhost via Stripe CLI / Cloudflare Tunnel during build. That's fine for manual smoke, but the automated test strategy must cover: (a) **signature verification** with a real Stripe-format signature header (use `stripe.webhooks.generateTestHeaderString` against the test secret) — a mock that skips signature checks would hide risk #3; (b) **idempotent replay** — fire the same event twice, assert one state transition (proves `runDeduped` keying on Stripe event id); (c) **out-of-order** — `payment_failed` after `succeeded`, assert order stays `paid`; (d) **partial + full refund accounting** against the new schema. Recommend Stripe's test-mode connected accounts + a recorded set of webhook fixtures committed to the repo, plus one Stripe-CLI-driven e2e in the build harness. Do not ship the money path on unit mocks alone (MEMORY: "tsc + vitest ≠ feature works").

10. **[MED] Refund race + auto-refund-on-cancel double-fire.** Founder decision #2: auto-refund on order cancel/reject, plus manual owner refund. Two paths can request a refund for the same order: the operator clicks "refund" while the auto-refund (triggered by cancel) is in flight. Without an idempotency key (risk #5) and a refund-state guard, that's a double refund. `Order.refund()` (`order.aggregate.ts:309`) requires status `paid` and moves to `refunded`, which gives _some_ protection for full refunds (second call throws), but **partial refunds don't change order status off `paid`**, so the aggregate guard does nothing for the partial case — two partial-refund requests both pass the guard. The refund accounting (refunded_amount + remaining) must live in the `payments`/`payment_refunds` model with its own invariant (sum of refunds ≤ captured amount) enforced in the domain, and the Stripe call must carry a deterministic idempotency key per refund request.

11. **[MED] Currency is fixed per tenant but orders/payments carry their own `currency` column — guard against drift.** Founder decision #3: single currency per tenant, fixed at Stripe onboarding. The `orders`, `order_items`, and `payments` tables each have a `currency` column. If the tenant's Stripe account currency and the order currency ever diverge (e.g. tenant changes locale, or a stale cart), the PaymentIntent will be rejected by Stripe or settle in the wrong currency. The plan should pin the order currency to the tenant's Stripe-account currency at checkout and reject mismatches loudly rather than letting Stripe fail opaquely.

12. **[LOW] Webhook secret management + rotation.** `STRIPE_WEBHOOK_SECRET` is per-endpoint and rotates. Follow the existing pattern: declare in `env.schema.ts` with a prod-guardrail dev-fallback check, never log it (the `packages/db` redact config already covers `token`; ensure the Stripe signature header and secret are on the redact list). For Connect, note there are **two** webhook secrets if you use both the account endpoint and the Connect endpoint — don't conflate them.

13. **[LOW] Application-fee=0 still means RestOS's Stripe account is the platform — Connect platform fees/registration apply.** Even at app-fee 0, RestOS must complete Stripe's platform profile, accept the Connect platform agreement, and (depending on region) handle the platform's own Stripe Connect pricing (e.g. per-active-account fees). This is an operational/legal checklist item, not code, but it belongs in the phase's "definition of done" so go-live isn't blocked by an unsigned platform agreement.

## Top 3 Recommendations (next 90 days)

1. **Resolve charge-model + fee-payer + merchant-of-record BEFORE design freeze (BLOCK #1, #7, #13).** One focused spike: confirm with Stripe's `on_behalf_of`/destination semantics whether the _restaurant_ can be fee-payer and statement descriptor with `application_fee_amount = 0`, and who carries dispute liability. Output a one-page decision: charge type, `on_behalf_of` value, fee payer, dispute owner, and which `stripe_account_id` (tenant) routes the charge. _Impact: prevents RestOS silently subsidizing every tenant's processing fees and de-risks the entire phase. Effort: ~1–2 days, mostly reading + a test-mode spike._

2. **Land the payments schema + aggregate redesign as the first build slice (BLOCK #2, HIGH #4, MED #10).** Add `payment_intent_id`, `latest_charge_id`, `stripe_account_id`, `application_fee_amount`, and a `payment_refunds` child table (composite tenant-FK per ADR-0020 I-2) with a domain invariant `sum(refunds) ≤ captured`. Model N PaymentIntents per order (retry-on-same-order) and an explicit onboarding/capability state on the tenant (`charges_enabled`, `payouts_enabled`, `requirements_currently_due`). Make the checkout guard and "Accept payments" switch read `charges_enabled`. _Impact: every later slice (checkout, refund, webhook) writes into a model that can actually represent the truth; avoids a painful mid-phase migration. Effort: ~3–4 days incl. migration, RLS, tests._

3. **Write the adapter + webhook against the existing seams, with money-path correctness as the test contract (HIGH #3, #5, MED #9).** Clone the Resend adapter's retry/timeout shape but make **every** outbound Stripe call carry a deterministic `Idempotency-Key`; clone `nats-audit-subscriber.ts` for the webhook, keying `runDeduped` on the Stripe event id; configure a per-route raw-body parser for signature verification; emit the `outbox.is_leader` gauge and fix the never-dispatched false-negative in the readiness probe. Gate the slice on an automated suite that proves: valid+invalid signature, idempotent replay, out-of-order succeeded/failed, full+partial refund accounting — driven by Stripe-CLI fixtures, not bare mocks. _Impact: the money path ships with the failure modes that actually bite (double-charge, replay, race) covered by tests. Effort: ~5–7 days._
