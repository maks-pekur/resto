<objective>
Close the operator-facing money path: owner-only, server-enforced refunds (full + partial,
mandatory reason — D-04), an automatic refund on cancel/reject of a paid order via a CANONICAL
`CancelOrderService` (W1 — built unconditionally so there is exactly one cancel→refund path
that Phase 10's operator cancel reuses, avoiding double-refund duplication), and minimal
dispute handling (record + notify — D-11). The refund call carries a deterministic Stripe
idempotency key so the manual refund and the `charge.refunded`/`refund.updated` webhook
reconcile to ONE refund (not two), and the domain invariant `sum(refunds) ≤ captured`
guards partial-refund double-fire (the order status stays `paid` on a partial, so the
aggregate status guard alone is insufficient — the refund-amount accounting from 08-01 is
the real guard). A refund emits `payments.order_refunded.v1` driving the GNOTIF-03 guest
email (08-06). A cross-tenant isolation e2e net proves payment/refund rows are RLS-scoped.

Purpose: make refunds, cancel-with-auto-refund, and disputes correct and non-double-firing on
the money path, with server-side authorization that the UI cannot bypass and a single
canonical cancel path Phase 10 can call.
Output: PAY-09 refund flow + the canonical CancelOrderService + dispute surfacing + the isolation net.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator → refund endpoint | only the owner may refund; the server enforces it, not the UI |
| manual refund + charge.refunded webhook | two paths must reconcile to one refund, not double-refund |
| cancel path (this plan) + Phase 10 cancel | exactly one cancel→refund implementation; Phase 10 reuses it (no second refund path) |
| Stripe → dispute webhook | a dispute moves money out of the restaurant; it must be visible |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-28 | Elevation of privilege | non-owner refunds | mitigate | operator-auth + @Permissions(owner) + @RequireActiveTenant on the refund endpoint; re-asserted server-side (D-04) |
| T-08-29 | Tampering/financial | double-refund (manual + webhook, or partial double-fire, or two cancel paths) | mitigate | deterministic Stripe idempotency key + UPDATE-by-stripe_refund_id reconcile + sum(refunds)≤captured invariant + a single canonical CancelOrderService Phase 10 reuses (W1) (D-09/D-10) |
| T-08-30 | Repudiation | refund without reason | mitigate | RefundReasonRequiredError — reason NOT NULL + non-empty (D-04 audit) |
| T-08-31 | Information disclosure | cross-tenant refund/payment access | mitigate | RLS + ScopedTx on payments/payment_refunds; cross-tenant isolation e2e proves rejection |
| T-08-32 | Denial of service/financial | silent dispute clawback | mitigate | charge.dispute.created recorded + operator-notified (D-11); not a blind spot |
</threat_model>
