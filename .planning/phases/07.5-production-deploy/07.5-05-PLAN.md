<objective>
Replace the `resto_auth` `BYPASSRLS` role attribute with explicit permissive RLS policies so the RestOS schema provisions cleanly on AWS RDS (D-04 LOCKED). RDS PostgreSQL CANNOT grant the `BYPASSRLS` role attribute to a non-superuser: the RDS master is `rds_superuser`, not a true `SUPERUSER`, and conferring `BYPASSRLS` requires superuser. RestOS's Better Auth role `resto_auth` currently relies on the `BYPASSRLS` attribute (set in `provisionAuthRole`) to read/write the Better-Auth-owned RLS tables. Option A (founder-chosen) keeps RDS and removes that dependency: `resto_auth` becomes `NOBYPASSRLS` and instead accesses the RLS-enabled BA tables through explicit `CREATE POLICY ... FOR ALL TO resto_auth USING (true) WITH CHECK (true)` permissive policies, which Postgres OR-combines with the existing tenant-isolation policy FOR `resto_auth` ONLY.

Purpose: This is the change that makes the RDS-locked D-04 decision actually work. Without it, plan 06's role provisioning HARD-STOPS on RDS (BYPASSRLS cannot be conferred) and the whole production data tier is blocked. The scope is strictly `resto_auth`'s access MECHANISM (attribute → policy); `resto_app`'s tenant isolation — the product's core defensibility — is NOT touched.

Output: a new idempotent policy migration (`0054`) + journal entry; `resto_auth` provisioned NOBYPASSRLS with a BYPASSRLS-strip path for existing DBs; updated preflight expectation; updated tests proving resto_auth operates without bypass AND resto_app isolation is intact; revised docs (README, CLAUDE.md) — the ADR-0013 rationale now states permissive-policies, not the BYPASSRLS attribute.
</objective>

The EXACT set of RLS-enabled tables resto_auth operates on (the only tables where BYPASSRLS currently matters), confirmed by cross-referencing the resto_auth GRANTs against every migration that toggles RLS:

  | table              | RLS source                  | resto_auth grant (auth-role.sql)        |
  | ------------------ | --------------------------- | --------------------------------------- |
  | member             | 0005 ENABLE+FORCE           | SELECT, INSERT, UPDATE, DELETE          |
  | invitation         | 0005 ENABLE+FORCE           | SELECT, INSERT, UPDATE, DELETE          |
  | organization_role  | 0005 ENABLE+FORCE           | SELECT, INSERT, UPDATE, DELETE          |
  | tenants            | 0001 ENABLE+FORCE           | SELECT, UPDATE only                     |

  The other tables resto_auth is granted on — "user" (BA singular, quoted), session, account, verification, two_factor — have NO RLS enabled (0005 comment documents this exception), so resto_auth touches them as a plain grantee and needs NO policy. tenants' INSERT/DELETE stay owned by the tenancy context (resto_auth is not granted them).

Existing tenant-isolation policies on those four tables (each created WITHOUT a TO clause → defaults to PUBLIC, applies to all roles incl. resto_auth):
  - member:            member_tenant_isolation            USING(is_system_session() OR organization_id = current_tenant_id()) WITH CHECK(...)
  - invitation:        invitation_tenant_isolation        USING(is_system_session() OR organization_id = current_tenant_id()) WITH CHECK(...)
  - organization_role: organization_role_tenant_isolation USING(is_system_session() OR organization_id = current_tenant_id()) WITH CHECK(...)
  - tenants:           tenants_self_iso                   USING(is_system_session() OR id = current_tenant_id())   [USING only, no WITH CHECK]

Postgres semantics (verified against postgres.org/docs/16/sql-createpolicy.html):
  - Multiple PERMISSIVE policies applicable to a query are combined with OR.
  - A policy with `TO resto_auth` applies ONLY to resto_auth; it is NOT applicable to resto_app or any other role.
  → Adding `FOR ALL TO resto_auth USING(true) WITH CHECK(true)` makes the predicate `true OR <existing>` = true for resto_auth (full access, equivalent to the old BYPASSRLS behaviour on these tables), and changes NOTHING for resto_app (the new policy is not applicable to it; resto_app keeps only the PUBLIC tenant-isolation policy).
  - FORCE ROW LEVEL SECURITY is unchanged; it still applies policies to the owner role. Default-deny still holds for any role with no applicable permissive policy.
