The tenant resolution path the proxy must not break — `apps/api/src/shared/effective-host.ts`:
```typescript
export function effectiveHost(
  headers: Record<string, string | string[] | undefined>,
  trustProxy: boolean,
): string | undefined;
// when trustProxy is on it reads headers['x-forwarded-host'] (first comma-separated
// value) and falls back to headers.host otherwise. A Worker fetch() to
// https://api.<apex>/... sets Host: api.<apex>, so without X-Forwarded-Host every
// guest request resolves to no tenant (Pitfall #3).
```

The edge-cache contract the origin already emits (`docs/runbooks/menu-edge-caching.md`,
`apps/api/src/contexts/catalog/domain/menu-cache.ts`):
```
GET /v1/menu               public, s-maxage=300, stale-while-revalidate=60   ETag "<menuVersion>"
GET /v1/menu/items/:id     public, s-maxage=300, stale-while-revalidate=60   ETag "<menuVersion>"
GET /v1/menu/availability  public, s-maxage=5                                ETag "<stopVersion>"
```
Public menu reads are `Set-Cookie`-free by contract and there is an e2e regression net
holding that. Everything else under `/v1/` is either mutating or tenant-private.

Build-time env the admin bundle reads (`apps/admin/src/env.ts`) — derived from the apex,
so the CD build must pass them (plan 09) and the first manual deploy must too (plan 08):
```typescript
export const VITE_STRIPE_PUBLISHABLE_KEY: string;  // getEnv throws in PROD if unset
export const VITE_ADMIN_HOST_SUFFIX: string;       // e.g. admin.<apex>; dev default admin.localhost
```
`getEnv` also rejects a `http(s)://localhost` value in a production build (G-05).
qr-menu reads only `VITE_STRIPE_PUBLISHABLE_KEY` (`apps/qr-menu/src/env.ts`).

Worker runtime shape to code against (structural, NOT the ambient `Fetcher` type —
see the action for why):
```typescript
export interface Env {
  ASSETS: { fetch(request: Request): Promise<Response> };
  API_ORIGIN: string;
}
export default {
  fetch(request: Request, env: Env, ctx: { waitUntil(p: Promise<unknown>): void }): Promise<Response>
};
```

    Write these tests first; each one names a way the naive version is wrong.
    - A request for `/` or `/assets/app.js` on `pizza.menu.example.invalid` is handed to
      `env.ASSETS.fetch` untouched and no origin fetch happens.
    - `GET /v1/menu` on `pizza.menu.example.invalid` reaches the origin at
      `https://api.example.invalid/v1/menu` carrying
      `X-Forwarded-Host: pizza.menu.example.invalid` and `X-Forwarded-Proto: https`.
    - The `Request` handed to `cache.match` and `cache.put` has
      `url === 'https://pizza.menu.example.invalid/v1/menu'`. It must NOT be the
      rewritten origin URL — that is the Pitfall #2 collapse, and this assertion is the
      whole reason this task exists.
    - **Cross-tenant isolation:** warm the cache with `pizza`'s menu, then request
      `sushi.menu.example.invalid/v1/menu`. The origin is called a second time and the
      response body is sushi's. A stub cache that keys on the origin URL fails here —
      confirm it does by temporarily keying on `originUrl` and watching the test go red
      before keying on the incoming URL.
    - A second identical `pizza` request within the cache lifetime is served from the
      cache and the origin is called exactly once in total.
    - The query string is part of the key: `/v1/menu?location=a` and
      `/v1/menu?location=b` do not share an entry.
    - `POST /v1/orders` is proxied but never read from or written to the cache.
    - An origin response carrying `Set-Cookie` is returned to the client but not cached.
    - A non-2xx origin response (500) is returned and not cached.
    - A path under `/v1/` that is not one of the three cacheable menu routes (e.g.
      `/v1/orders/abc`) is proxied without touching the cache at all.
  </behavior>
  <action>
    Implement `apps/qr-menu/worker/index.ts` from the working code in RESEARCH.md's
    "qr-menu Worker" example, with two deliberate deviations.

    First, type `ASSETS` structurally as `{ fetch(request: Request): Promise<Response> }`
    rather than importing `Fetcher` from `@cloudflare/workers-types`. The ambient
    workers-types package redeclares `Request`/`Response` globally and fights the
    jsdom/node lib set the existing vitest projects use; a structural binding keeps the
    module importable by a plain vitest run with no new test runner and no
    `@cloudflare/vitest-pool-workers` dependency (which is not in RESEARCH.md's package
    legitimacy audit and must not be added on a whim).

    Second, treat cacheability as an explicit allowlist — `/v1/menu`,
    `/v1/menu/availability`, and paths under `/v1/menu/items/` — matching exactly the
    three routes the origin marks `public, s-maxage=...`. Anything else under `/v1/` is
    proxied straight through. Deriving cacheability from the response's `Cache-Control`
    instead would be cleverer and worse: it would silently start caching whatever a
    future route happens to mark public.

    Build the cache key with `new Request(url.toString(), request)` where `url` is the
    incoming request's URL, so the tenant subdomain is inside the key. Read with
    `cache.match(cacheKey)` before going to origin; write with
    `ctx.waitUntil(cache.put(cacheKey, response.clone()))` only when the method is GET,
    the path is on the allowlist, the response is `ok`, and it carries no `Set-Cookie`.
    Do not rely on the Cache API's own `Set-Cookie` refusal as the only guard.

    Add `apps/qr-menu/worker/tsconfig.json` extending the app's config but scoping
    `types` to the workers types, so the Worker source typechecks against the runtime
    it actually runs in while the SPA sources keep their DOM lib.

    In `apps/qr-menu/test/worker.spec.ts`, stub `globalThis.caches` with a Map-backed
    fake whose `match`/`put` record the `Request` they were handed (the tests assert on
    `.url`), stub `globalThis.fetch` with a recorder returning per-tenant bodies, and
    pass a `ctx` whose `waitUntil` awaits synchronously so assertions do not race the
    write. No comments inside test bodies — the `it` names carry the intent.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| guest browser → Worker | untrusted; every tenant's guests hit the same Worker script |
| Worker → API origin | the Worker asserts the tenant identity via `X-Forwarded-Host`; the API trusts it under `TRUST_PROXY` |
| Cloudflare edge cache → guest | a single wrong cache key serves one restaurant's menu to another's guests |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07.5-07-01 | Information Disclosure | qr-menu Worker cache key | mitigate | key on the incoming request URL (carries the tenant subdomain); asserted by the cross-tenant test in Task 1, which is required to have been seen failing against the naive key |
| T-07.5-07-02 | Spoofing | `X-Forwarded-Host` | mitigate | the header is only trustworthy because the origin is unreachable except through Cloudflare — plan 08 owns the `ufw` restriction to Cloudflare IP ranges that makes this true; recorded here so the dependency is not invisible |
| T-07.5-07-03 | Information Disclosure | admin Worker caching an authenticated response | mitigate | admin Worker never touches the Cache API; Task 2 asserts zero cache calls rather than inferring from headers |
| T-07.5-07-04 | Session hijack / loss | Better Auth cookie across the proxy | mitigate | same-origin proxy keeps the cookie inside the `AUTH_COOKIE_DOMAIN` subtree; `Set-Cookie` pass-through asserted in Task 2 (F-41 regression net) |
| T-07.5-07-05 | Tampering | caching a mutating or private `/v1/` route | mitigate | explicit three-route allowlist rather than deriving cacheability from the response |
| T-07.5-07-SC | Tampering | npm installs | mitigate | only `wrangler` and `@cloudflare/workers-types` at pinned versions, both `[VERIFIED]`/Approved in RESEARCH.md's audit; no other package permitted by this plan |
