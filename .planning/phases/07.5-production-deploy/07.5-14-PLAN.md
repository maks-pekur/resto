<objective>
Make the origin route by path, close the forged-host hole while it is finally cheap to close, and
leave one apex parameter behind in every template, guard, rehearsal and instruction file.

Purpose: phase 07.4 deliberately left two handoffs here. Guest checkout now calls `/v1/*`
same-origin with a dev-only Next rewrite that is `NODE_ENV !== 'production'`-gated, so in
production it has no route at all until Caddy grows one — and it will 404 loudly rather than
hairpin, which is the behaviour 07.4 chose on purpose. And with the browser no longer sending
`x-forwarded-host`, the header can finally be pinned at the edge; the research warned against
pinning it while the browser still did.

Output: a Caddyfile that serves three surfaces off two site blocks, a website whose SSR call never
leaves the box, guards and templates that know one apex, a rehearsal whose restore drill can fail,
and infrastructure documentation that describes this decade's stack.
</objective>

**The Caddy path split, measured against `caddy:2.11-alpine` in Docker (M-06).** `handle` blocks
are mutually exclusive and evaluated in written order. `/` reached the website upstream, `/v1/menu`
and `/api/auth/*` reached the api upstream, `/internal/v1/*` was answered 404 without reaching
either, and the upstream saw the real tenant `Host`:

```
{$WEBSITE_HOST}, *.{$WEBSITE_HOST} {
	tls /etc/caddy/certs/origin.crt /etc/caddy/certs/origin.key

	handle /internal* { respond 404 }
	handle /v1/*  { reverse_proxy api:3000     { header_up X-Forwarded-Host {host} } }
	handle /api/* { reverse_proxy api:3000     { header_up X-Forwarded-Host {host} } }
	handle        { reverse_proxy website:3002 { header_up X-Forwarded-Host {host} } }
}
```

**The forgery, measured (M-07), against exactly the committed Caddyfile:**

```
$ curl -H 'Host: pizza.example.invalid' \
       -H 'X-Forwarded-Host: evil.attacker.invalid' http://127.0.0.1:8080/v1/menu
{"who":"api","host":"pizza.example.invalid","xfh":"evil.attacker.invalid",...}
```

The forged value reaches the upstream verbatim. `effectiveHost()`
(`apps/api/src/shared/effective-host.ts:13-18`) honours `x-forwarded-host` whenever `TRUST_PROXY`
is non-empty, which it always is in production by schema requirement. **The fix, measured working
(M-08):** `header_up X-Forwarded-Host {host}` — verified against both a single forged header and
the comma-joined two-value shape, with the `/internal*` `client_ip` gate unaffected.

**What is still unproven and is not this plan's to settle:** whether Cloudflare delivers a
client-supplied `X-Forwarded-Host` to the origin at all (research assumption **A7**, MEDIUM). The
measurement proves Caddy forwards it; it does not prove Cloudflare sends it. Plan 07.5-08 settles
A7 with one curl through the real edge. Apply the pin regardless — it costs one line and removes
the question.

**Why the pin can go on `{$API_HOST}` too now, which it could not before.** Two callers used to set
this header legitimately. `apps/website/lib/checkout-api.ts` — the **browser** — was the dangerous
one and phase 07.4 plan 02 deleted it: guest checkout now calls root-absolute `/v1/...`
same-origin, and a committed source-tree gate (`apps/website/test/no-client-tenant-header.spec.ts`)
fails if the header reappears outside the server-only module. The remaining one is
`apps/website/lib/api-client.ts` (`server-only`), which forwards the real inbound `Host` to
`https://api.<apex>` — hairpinning out through Cloudflare and back on every server-rendered page.
Give it `API_INTERNAL_ORIGIN` and that call never leaves the Compose network, which closes the
latency tradeoff (Pitfall #9) and takes the last legitimate sender off the public path at the same
time. Research changed its own recommendation here from "accept for now" to "do it, in the same
plan as the header pin."

**07.4 plan 02's handoff, verbatim from its summary:** *"before go-live, Caddy's
`{$WEBSITE_HOST}, *.{$WEBSITE_HOST}` site block must add a `handle /v1/*` route to `api:3000`, or
production guest checkout has nothing to route to since the dev-only Next rewrite deliberately does
not run in `NODE_ENV=production`."*

**The two blocks that already exist and must not be disturbed.** The global `servers { trusted_proxies
static 0.0.0.0/0 ::/0 · client_ip_headers CF-Connecting-IP }` block stays exactly as committed: the
blanket range is what lets Caddy read `CF-Connecting-IP` at all, and `client_ip_headers` is what
makes the `/internal*` `client_ip` gate non-bypassable (Round 2 NEW-1, T3/T4 vs C1-C3 against Caddy
2.11.4). `{$API_HOST}`'s `@internal_blocked` matcher and its `respond 404` stay. `InternalTokenGuard`
remains the actual control on `/internal/v1/*`; the IP gate is defence in depth and must never be
described as though it were the control.
