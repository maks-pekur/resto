<objective>
Make the deployed runtime correct under managed Postgres + give the solo founder the two
operational signals that are otherwise missing on the 7.5->8 revenue path:

1. D-05: route the outbox dispatcher's `pg_try_advisory_lock` through a DIRECT (unpooled,
   session-pinned) connection. The lock is session-level; a PgBouncer transaction-mode pooler
   (Neon's default) returns the backend to the pool after each statement, silently losing the
   lock — the outbox would stall with no error. Add `DATABASE_DIRECT_URL`; on RDS it equals
   `DATABASE_URL` (no pooler), on Neon it is the unpooled endpoint.
2. G-03: add a minimal `outbox_leader` readiness check so `/readyz` 503s when no instance holds
   the lock — ALB then replaces the task and a new one re-acquires within ~5s. (The full
   dispatch-lag OTel gauge stays in Phase 8.)
3. G-04: wire Sentry (`@sentry/node`) for unhandled-exception capture in prod.

Purpose: D-05 is a CTO-flagged footgun that makes Neon's pooler safe to use; G-03 turns a
silent outbox stall into a visible 503; G-04 is the difference between "customer told me it's
down" and "I knew first". All three are code-only and independent of which cloud we provision —
proven by unit tests before any infrastructure exists. (Runs Wave 1 only because it imports
@sentry/node, which 07.5-05 installs + legitimacy-verifies in Wave 0; no infra dependency.)
Output: new env vars, a direct-connection dispatcher, an outbox_leader readiness check, Sentry init.
</objective>
