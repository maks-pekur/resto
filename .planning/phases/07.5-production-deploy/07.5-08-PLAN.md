<objective>
Stand the real thing up: one VPS behind Cloudflare serving the API and website over HTTPS
on the founder's apex, with both SPA Workers live on their wildcard hosts and a guest
menu request that actually returns a tenant's menu.

Purpose: this is the plan that spends money and creates state. Everything it does was
rehearsed in plan 06, so what is left are the failure modes only a real network has —
DNS, TLS trust, firewall scope, whether the guardrails pass against real credentials, and
whether the four-hop tenant chain survives contact with Caddy.

That last one is why this plan, and not plan 10, owns the first tenant-resolving request:
plans 06-09 otherwise assert only `/healthz` (tenant-less), stubbed fetches, and SPA
shells that never reach the API. Without it the phase can reach the end of CD — four
hostnames at 200, everything green — with the guest menu completely dead.

Output: two scripts, two runbooks, a repository that no longer documents a cloud it does
not use, and a live production origin serving a real tenant.
</objective>

Read the SCOPE UPDATE banners at the top of `07.5-CONTEXT.md` before the decision bodies.
There is no ECS, no Fargate, no RDS, no ALB, no Terraform, no AWS Secrets Manager and no
Kubernetes anywhere in this plan.

**The apex domain is a parameter.** It comes from the `PUBLIC_APEX_DOMAIN` GitHub variable
set in plan 06 Task 1 and is expanded onto the box by `infra/scripts/render-env.sh`.
Nothing this plan writes into the repository may contain it; `assert-no-domain-literals.sh`
enforces that by searching for the real value. Where a hostname must be named in a runbook,
write the shape: `api.<apex>`, `<apex>` + `*.<apex>`, `admin.<apex>`, `*.admin.<apex>`,
`*.menu.<apex>`.

**The guest and operator surfaces must share a parent domain.** `AUTH_COOKIE_DOMAIN` is
Zod-validated to start with `.` and is set to `.admin.<apex>`; the operator hops from
`admin.<apex>` to `<slug>.admin.<apex>` at sign-in and a host-only cookie does not survive
that. Guest Google sign-in is blocked in dev today for exactly this reason — a tunnel host
offers no shared parent. Any hostname scheme this plan puts into DNS must keep that
subtree intact.

**Provisioning order is migrations FIRST, roles SECOND** (`.github/workflows/ci.yml:253-259`,

    **`infra/scripts/vps-bootstrap.sh`** — runs as root on a fresh Ubuntu 24.04 Docker CE
    box, idempotent, `set -euo pipefail`. Creates an unprivileged `resto` deploy user with
    the deploy public key in `authorized_keys`; creates `/opt/resto`, `/opt/resto/certs`
    (mode 700), `/opt/resto/scripts`, `/opt/resto/backups` owned by that user; installs
    `rclone` from the official installer (floor 1.59 — below it R2 returns spurious 401s);
    confirms the Compose plugin shipped with the image and fails loudly if not; and
    configures `ufw` — default deny incoming, allow SSH (optionally restricted to a
    `--ssh-from` CIDR), and allow 80/443 **only from the ranges fetched live from
    `https://www.cloudflare.com/ips-v4` and `ips-v6`**. Fetch at run time rather than
    hardcoding, and delete the previously generated rules by comment tag before adding the
    new set so a re-run converges instead of accumulating. Print `ufw status numbered`.

    Take the deploy public key path and optional CIDR as arguments — no secrets, no
    hostnames, no apex in this file.

    **`infra/scripts/verify-prod-origin.sh`** — the automated check the founder runs from a
    machine that is not the VPS, taking `PUBLIC_APEX_DOMAIN` and the VPS IP from the
    environment. Two stages, because a checkpoint with no honest pass criterion is a
    checkpoint nobody can fail:

    `--stage network` (everything true before containers exist):
    - `dig +short api.<apex>` resolves and does NOT return the raw VPS IP — proving the
      record is proxied, not grey-clouded.
    - `curl --max-time 5 -k https://<vps-ip>/` fails. A response here means the firewall
      is open to the world and any client can forge `X-Forwarded-Host` straight into the
      API. Hard failure, not a warning.
    - `nc -z -w3 <vps-ip> 5432` and `4222` both fail.

    `--stage full` (the default) adds:
    - `curl -sI https://api.<apex>/healthz` → 200 with a `cf-ray` header, proving the
      request traversed Cloudflare.
    - `curl -sI https://<apex>/` → 200 from the website container via Caddy.
    - `curl -sI https://admin.<apex>/` → 200 from the admin Worker.
    - `curl -sI https://<probe>.menu.<apex>/` → 200 from the qr-menu Worker.
    - **`curl -s https://<probe>.menu.<apex>/v1/menu` → 200 with a JSON body naming that
      tenant.** This single assertion is the only thing in plans 06-09 that exercises the
      whole chain — Worker route binding, `run_worker_first`, the `X-Forwarded-Host` the
      Worker sets, Caddy's `trusted_proxies` preserving it, `effectiveHost()`, and tenant
      resolution. Every one of those can be individually wrong while `/healthz` stays 200.
      Take the probe slug from `PROBE_TENANT_SLUG` and refuse to run `--stage full`
      without it rather than skipping the check.
    - `X-Resto-Cache` is present on that response (plan 07's contract), so a
      silently-bypassed Worker is visible.

    Exit non-zero listing every failed assertion.

    **`docs/runbooks/vps-provisioning.md`** — the founder sequence: create the CX32 from
    the Docker CE marketplace image with the deploy key attached at creation (not added
    later); run `vps-bootstrap.sh`; copy `docker-compose.prod.yml`, the `Caddyfile` and

    only secret store (no AWS Secrets Manager, no Vault, per D-09 as reconciled), they are
    never in an image and never in git, and rotation is "edit the file, then
    `docker compose up -d --no-deps <service>`" because `env_file` is read at container
    creation. State explicitly that `DATABASE_ADMIN_URL` is deliberately not among them.

    **`docs/runbooks/cloudflare-dns-tls-workers.md`** — the six DNS records as a table of
    *shapes*; Origin CA issuance with SANs `<apex>`, `*.<apex>`, `api.<apex>`, 15-year
    validity, no ACME; the zone on Full (strict); the Worker route patterns copied verbatim
    from `docs/runbooks/spa-workers.md` so there is one source; **and the Cache Rule
    setting `api.<apex>/v1/*` to Bypass**, with the one-paragraph reason: the Workers hold
    a tenant-keyed cache of their own and the URL they request upstream is identical for
    every tenant, so a zone cache in front of it is a cross-tenant leak. This is how D-08's
    "CDN cache-rules for the public menu" is settled — the Worker cache replaces them, and
    the zone must be told not to compete. Note that direct access to the VPS IP correctly
