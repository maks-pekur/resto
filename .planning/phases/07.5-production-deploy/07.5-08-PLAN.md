<objective>
Stand up the public production hosting surface for all four apps over HTTPS: ECS/Fargate for `apps/api` (desired-count min 1 — the always-on outbox leader, D-02) and `apps/website` (Next standalone image from plan 07.5-11); Cloudflare Pages/CDN static hosting for `apps/admin` and `apps/qr-menu` (Vite SPA bundles, identical pattern — no admin Dockerfile, no admin ECS service); ALB + ACM in AWS; AWS Secrets Manager for runtime secret injection (D-09); Cloudflare DNS + wildcard TLS for `*.menu.resto.app` + the menu CDN cache-rule + host-routing in front of the ALB (D-08). Keep IaC minimal (D-03 — surface the ECS-Express-Mode vs. AWS-CDK choice and pick the lowest-ops one; explicit "no k8s/EKS, no multi-region, no Terraform sprawl"). AWS Copilot is EXCLUDED — it reached end-of-support on 2026-06-12 (RESEARCH.md §"AWS Copilot CLI: End-of-Life Alert").

Purpose: This is SC#1 (all four surfaces live over HTTPS, 3-role Postgres in place) + SC#2 (object storage wired + runtime secret injection) + the SC#5 precondition (a public HTTPS URL Stripe webhooks can reach in Phase 8). The api MUST never scale to zero or the outbox stops draining (D-02). admin + qr-menu are static like qr-menu always was — this is the key change vs. the archived admin-as-ECS plans. qr-menu fetches `/v1/menu` relative (plan 04), so its Pages host needs a same-origin rewrite to the API, not a CORS path.

Output: ECS api+website services + Pages admin+qr-menu + ALB/ACM + Secrets Manager wiring + Cloudflare DNS/TLS/CDN/routing; three runbooks. This is provisioned manually/console here; plan 09 automates the redeploy on merge.
