**The apex domain is a parameter.** It arrives from the `PUBLIC_APEX_DOMAIN` GitHub
variable set in plan 06 Task 1 and is expanded onto the box by
`infra/scripts/render-env.sh`. Nothing this plan writes into the repository may contain
it. Where a hostname must be named in a runbook, write the shape: `api.<apex>`,
`<apex>` + `*.<apex>`, `admin.<apex>`, `*.admin.<apex>`, `*.menu.<apex>`.

**The guest and operator surfaces must share a parent domain.** `AUTH_COOKIE_DOMAIN` is
Zod-validated to start with `.` and is set to `.admin.<apex>`; the operator hops from
`admin.<apex>` to `<slug>.admin.<apex>` at sign-in and a host-only cookie does not
survive that. This is not cosmetic — guest Google sign-in is blocked in dev today for
exactly this reason (a tunnel host offers no shared parent). Any hostname scheme this
plan puts into DNS must keep that subtree intact.

  <action>
    Write the automatable half of the stand-up, so the founder's manual half is as small
    as it can honestly be and its result is machine-checkable.

    **`infra/scripts/vps-bootstrap.sh`** — runs as root on a fresh Ubuntu 24.04 Docker
    CE box, idempotent, `set -euo pipefail`. It: creates an unprivileged `resto` deploy
    user with the deploy public key in `authorized_keys`; creates `/opt/resto`,
    `/opt/resto/certs`, `/opt/resto/scripts`, `/opt/resto/backups` owned by that user
    with `certs` at mode 700; installs `rclone` from the official install script (the
    version floor is 1.59 — below it R2 returns spurious 401s); confirms the Docker
    Compose plugin shipped with the marketplace image (`docker compose version`) and
    fails loudly if not; and configures `ufw` — default deny incoming, allow SSH
    (optionally restricted to a `--ssh-from` CIDR), and allow 80/443 **only from the
    ranges fetched live from `https://www.cloudflare.com/ips-v4` and `ips-v6`**, then
    enables it. Fetch the ranges at run time rather than hardcoding them, and re-run
    safely: delete the previously generated rules by comment tag before adding the new
    set, so a re-run after Cloudflare changes its ranges converges instead of
    accumulating. Print a summary of the final `ufw status numbered`.

    Do not put secrets, hostnames or the apex in this script — it takes the deploy
    public key path and optional CIDR as arguments.

    **`infra/scripts/verify-prod-origin.sh`** — the automated check the founder runs
    after the manual steps, from a machine that is not the VPS. Takes
    `PUBLIC_APEX_DOMAIN` and the VPS IP from the environment and asserts, each with a
    clear pass/fail line:
    - `dig +short api.<apex>` resolves, and the returned addresses are NOT the raw VPS
      IP — proving the record is proxied (orange-cloud), not a grey-cloud passthrough.
    - `curl -sI https://api.<apex>/healthz` returns 200 and the response carries a
      `cf-ray` header, proving the request actually traversed Cloudflare.
    - `curl --max-time 5 -k https://<vps-ip>/` fails (connection refused or timeout).
      A successful response here means the firewall is open to the world and a client
      can forge `X-Forwarded-Host` straight into the API — treat it as a hard failure,
      not a warning.
    - `nc -z -w3 <vps-ip> 5432` and `nc -z -w3 <vps-ip> 4222` both fail — Postgres and
      NATS are unreachable.
    - `curl -sI https://<probe-slug>.menu.<apex>/` and `curl -sI https://admin.<apex>/`
      both return 200 with `cf-ray`, proving the Worker routes bound to the wildcard and
      apex hosts respectively.
    - `curl -sI https://<apex>/` returns 200, proving the website container is routed by
      Caddy.
    Exit non-zero listing every failed assertion. Accept `--stage network` to run only
    the first four (DNS shape, Cloudflare-only reachability, closed datastore ports),
    which is everything that can be true before Task 3 brings the containers up;
    `--stage full` (the default) runs all of them. Without that split, Task 2 has no
    honest pass criterion. This script is the evidence artifact for Task 2 and gets
    re-run by plan 10's go-live checklist.

    **`docs/runbooks/vps-provisioning.md`** — the founder-facing sequence: create the
    CX32 from the Docker CE marketplace image with the deploy key attached at creation
    (not added later); run `vps-bootstrap.sh`; copy `docker-compose.prod.yml` and the
    `Caddyfile` into `/opt/resto`; render `/opt/resto/.env`, `.env.api` and
    `.env.website` from the plan-06 templates with `render-env.sh`, `chmod 600`, owned
    by the deploy user; place the Origin CA pair in `/opt/resto/certs`. Include the
    secrets-on-the-box section here rather than as a third runbook: the files are the
    only secret store (no AWS Secrets Manager, no Vault, per D-09 as reconciled), they
    are never in an image and never in git, and rotation is "edit the file, then
    `docker compose up -d --no-deps <service>`" because `env_file` is read at container
    creation. State explicitly that `DATABASE_ADMIN_URL` is deliberately not among the
    files on the box.

    **`docs/runbooks/cloudflare-dns-tls-workers.md`** — the six DNS records as a table
    of *shapes* (`api.<apex>` A → VPS IP proxied; `<apex>` A → VPS IP proxied;
    `*.<apex>` CNAME → `<apex>` proxied, which also covers `order.<apex>`;
    `admin.<apex>`, `*.admin.<apex>`, `*.menu.<apex>` as proxied dummy A records to
    `192.0.2.1` whose only job is to let a Worker route bind); Origin CA issuance with
    SANs `<apex>`, `*.<apex>`, `api.<apex>`, 15-year validity, no ACME and no renewal
    cron; the zone set to Full (strict); and the Worker route patterns, copied verbatim
    from `docs/runbooks/spa-workers.md` so there is one source for the invocation. Add
    the note that direct access to the VPS IP correctly shows an untrusted certificate
    and that this is expected, because nothing should reach the origin except through
    Cloudflare.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| internet → VPS | the only legitimate ingress is Cloudflare's edge on 80/443 |
| Cloudflare edge → origin | authenticated by the Origin CA certificate under Full (strict) |
| operator workstation → box | SSH with a deploy-only key; the only path carrying `DATABASE_ADMIN_URL` |
| api container → R2 | a bucket-scoped token, distinct from the backup token |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07.5-08-01 | Spoofing | forged `X-Forwarded-Host` reaching the API directly | mitigate | `ufw` allows 80/443 only from Cloudflare's published ranges; `verify-prod-origin.sh` fails the task if a raw-IP request succeeds |
| T-07.5-08-02 | Information Disclosure | Postgres/NATS on the public interface | mitigate | no `ports:` outside `caddy` (plan 06) plus an outside-in `nc` check on 5432/4222 in the verifier |
| T-07.5-08-03 | Tampering | Cloudflare-to-origin traffic on a Flexible/self-signed setup | mitigate | Origin CA certificate + zone set to Full (strict); the verifier asserts `cf-ray` so a bypassed edge is visible |
| T-07.5-08-04 | Elevation of Privilege | `DATABASE_ADMIN_URL` persisted on the box | mitigate | passed per-invocation to the profile-gated `migrate` service only; absent from every `.env` file and stated as deliberate in the runbook |
| T-07.5-08-05 | Elevation of Privilege | one over-scoped R2 token | mitigate | two buckets, two tokens; the media token cannot read backups and the backup token cannot touch guest media |
| T-07.5-08-06 | Information Disclosure | `.env` files readable by other users on the box | mitigate | mode 600, owned by the deploy user; `certs/` at 700 |
| T-07.5-08-SC | Tampering | npm/pip/cargo installs | accept | this plan installs no packages from those ecosystems; `rclone` comes from its official installer and the Docker images are pinned upstream tags already used in dev |
</threat_model>
