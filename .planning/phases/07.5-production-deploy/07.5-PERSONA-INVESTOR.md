# Phase 7.5 "Production Deploy" — Investor / Business Review

**Lens:** capital efficiency, burn, dependency/lock-in, scalability cost curve, time-to-first-revenue.
**Stage of artifact:** discuss-phase, pre-plan. No plan exists yet — this review shapes the plan.
**Reviewer posture:** Series A B2B-SaaS partner reading the deploy decision as a runway-and-risk question, not a code review.

## TL;DR (IC framing)

- This phase earns **zero revenue** and is **100% plumbing** — it is the gate to revenue (Phase 8 Stripe), not revenue itself. The only correct objective is "cheapest credible public HTTPS prod that won't embarrass us in front of the first paying restaurant," shipped in **days, not weeks**.
- The ROADMAP language is already disciplined ("Fly/Railway/ECS — not full k8s," "pragmatic over ideal"). The CTO review correctly killed the EKS/Terraform stubs. **My job here is to make sure that discipline survives contact with a plan** — the single biggest money-risk in this phase is gold-plating the deploy.
- **Leanest defensible default: a managed-PaaS app host (Railway or Fly) + managed Postgres + Cloudflare R2 + managed/single-node NATS, ~$40–90/month all-in at zero scale.** Two BLOCK-level diligence items before any plan: (1) the 3-role Postgres schema must be validated against the chosen managed Postgres, and (2) automated backups + a tested restore must be in scope before a paying tenant touches it.

## Burn at zero-to-first-customer scale

A sensible default stack, monthly, before any meaningful traffic:

| Line item                                   | Default choice                                                | ~$/mo at zero scale      | Scales painfully when…                                                                  |
| ------------------------------------------- | ------------------------------------------------------------- | ------------------------ | --------------------------------------------------------------------------------------- |
| App hosting (api + admin, +website/qr-menu) | Railway Pro or Fly machines                                   | $20–40                   | per-always-on-VM model; each app a separate service; admin RSC + api = 2+ services      |
| Managed Postgres                            | Neon (scale-to-zero) or Railway/RDS                           | $0–38                    | connection count, not GB; pgbouncer needed early; serverless cold-start on Friday spike |
| Object storage                              | Cloudflare R2                                                 | ~$0–5                    | egress is **free** on R2 — this is the cheap, sticky-in-a-good-way choice               |
| NATS JetStream                              | single small node on the PaaS, or Synadia Cloud free/personal | $0–15                    | HA replication (R3) is paid; single-node = SPOF (see red flags)                         |
| Domain + DNS + TLS                          | Cloudflare                                                    | ~$1–2 (domain amortized) | wildcard cert for `*.menu.resto.app` multi-tenant — confirm host supports it            |
| Email (lands Phase 8, not here)             | Resend                                                        | $0 (free tier)           | out of scope this phase, noted to avoid a surprise                                      |
| **Total**                                   |                                                               | **~$40–90/mo**           |                                                                                         |

This is well inside a bootstrap budget. The cost story at this phase is a non-issue **in absolute terms** — the risk is not the $90, it's the **2–3 weeks of solo-founder time** a k8s/Terraform path would burn. Founder-time is the scarce capital here, not dollars.

**What scales painfully later (not now, but name it):** Postgres connection limits under Friday-evening simultaneous spikes across tenants (the CLAUDE.md peak-load assumption) — a pooled connection layer (pgbouncer/Neon pooler) is the first thing that bites, well before per-tenant compute. NATS HA is the second. Neither needs solving in 7.5; both should be _cheap to add later_, which the current managed choices preserve.

## Capital efficiency / gold-plating risk

- **Good signal:** the phase was explicitly scoped _down_ from EKS to PaaS after CTO review, and the `infra/k8s` + `infra/terraform` stubs are acknowledged as dead weight. That is exactly the call I'd want a capital-efficient founder to make pre-PMF.
- **Where gold-plating creeps back in (watch the plan for these):**
  - Resurrecting Terraform "to do it properly" — **MEDIUM**. At one tenant, click-ops or a 20-line PaaS config file is correct. IaC is a Series-A problem, not a first-customer problem.
  - Multi-region / multi-AZ HA on the revenue path before there's revenue — **HIGH** if it appears. Single-region is fine for the first paying restaurant; DR via backups (below) is the actual requirement, not active-active.
  - A full secrets manager (Vault) when the PaaS-native secret store covers it — **LOW/MEDIUM**. The success criterion only says "runtime secret injection, never baked into images." PaaS secret stores satisfy that. Vault is over-build at this stage.
  - Building observability infra (self-hosted Jaeger/collector) in prod — **MEDIUM**. OTel is already wired; point it at a free-tier hosted backend (or disable in prod initially). Don't run a tracing stack for one tenant.
- **Should be bought, never built here:** Postgres, object storage, NATS, TLS, CD runner. All of these are commodity managed services. Any line in the plan that says "self-host X on a VM we manage" for a core dependency is a red flag for a solo founder's time budget — **the one defensible exception is single-node NATS**, which is cheap to self-host and has no good free managed tier for JetStream HA anyway.

## Lock-in / reversibility (weighted for pre-PMF solo founder)

Reversibility matters _more_ than price here, because the founder may re-platform once after PMF. Rank choices by escape cost:

| Choice                          | Stickiness     | Notes                                                                                                                                                                                                                                              |
| ------------------------------- | -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Cloudflare R2**               | **Low / good** | Free egress means leaving is cheap; S3-API compatible — the `@aws-sdk/client-s3` code already abstracts it. Reversible. **Recommend.**                                                                                                             |
| **PaaS app host (Railway/Fly)** | **Low**        | App is a stock Node/Next container; moving to ECS/another PaaS is a config migration, not a rewrite. The NestJS monolith is deliberately portable. Reversible.                                                                                     |
| **Managed Postgres**            | **Medium**     | Data egress is the friction. Standard Postgres wire protocol keeps logical-dump portability — _as long as you don't adopt vendor-proprietary primitives_ (Neon branching in app logic, Supabase auth/realtime). **Use it as plain Postgres only.** |
| **NATS**                        | **Low**        | Already abstracted behind `@resto/events` publisher/subscriber ports + transactional outbox. Swappable. Good architectural hygiene that a future investor would credit.                                                                            |
| **Better Auth (in-process)**    | n/a this phase | Not a 7.5 decision, but note: self-hosted in-process auth is a _deliberate de-risking_ of the Auth0/Keycloak lock-in — credit it.                                                                                                                  |

**Net:** the abstraction layers already in the codebase (events ports, S3 SDK, Drizzle) mean almost every infra choice here is reversible. The one place to enforce discipline: **treat managed Postgres as commodity Postgres** — no proprietary features in application code — so the DB stays portable.

## Time-to-value (this phase blocks revenue — speed is the KPI)

Fastest credible path to public HTTPS prod, ranked:

1. **Railway** — git-push deploy, managed Postgres + service in the same project, built-in secret store, TLS automatic. **Days.** Best raw time-to-first-HTTPS.
2. **Fly.io** — slightly more config (fly.toml per app, Postgres as a separate managed offering), but better cost control via scale-to-zero and global edge. **Days, with a bit more setup.**
3. **ECS/Fargate** — credible and AWS-native, but more moving parts (ALB, task defs, RDS, Secrets Manager). **1–2 weeks.** Only choose if there's a concrete reason to be on AWS now (there isn't, pre-PMF).
4. **EKS/Terraform** — already correctly rejected. **Weeks.** Would be a capital-efficiency failure here.

**Recommendation: Railway or Fly.** Pick whichever the founder can stand up fastest solo. The decision is reversible (see lock-in), so optimize for shipping speed, not theoretical ceiling. Do **not** let "but AWS is where we'll end up" pull this onto ECS/EKS now — that's pre-optimizing for a scale that doesn't exist and spending the scarcest resource (founder-weeks) to do it.

## Diligence red flags (severity-classified)

1. **BLOCK — 3-role Postgres schema vs managed-Postgres role model.** RestOS requires `resto_app` (NOBYPASSRLS), `resto_admin` (schema owner, DDL), and `resto_auth` (**BYPASSRLS**, owns Better Auth tables). Managed/serverless Postgres restricts superuser, `CREATEROLE`, and `BYPASSRLS` in vendor-specific ways (Neon ties `BYPASSRLS` to `neon_superuser`; Supabase only recently allowed non-superuser `BYPASSRLS`; RDS gates it behind `rds_superuser`). **The plan MUST validate the exact 3-role schema + `FORCE ROW LEVEL SECURITY` + boot preflight (`assertNoRlsBypass`, `assertSetConfigRevoked`) against the chosen provider before committing.** If the provider can't express this role separation, the entire tenant-isolation security model — the product's core defensibility claim — is compromised in prod. This is the one thing I'd want answered before the plan is approved.
2. **BLOCK — no backups / no tested restore on the revenue path.** A paying restaurant's menu, orders, and customer PII will live here. "Managed Postgres has backups" is not sufficient — the success criteria don't mention backup/restore at all. **A tested point-in-time restore (or at least an automated daily snapshot + one rehearsed restore) must be in scope before the first paying tenant.** A seed investor will ask "what happens when the DB is corrupted?" and "no backups before taking money" is a fundability-killer, not a nit.
3. **HIGH — single-node NATS as a SPOF on the order path.** Free/single-node JetStream has no HA. Orders flow through the transactional outbox → NATS. The outbox means a NATS outage doesn't _lose_ events (they queue in Postgres), which is good design — but confirm the plan documents the degraded-mode behavior and that a NATS outage doesn't block order acceptance. Acceptable for first customer _if_ the outbox truly decouples it; must be verified, not assumed.
4. **HIGH — silent env-var routing bug ships to prod.** CONCERNS.md flags `NEXT_PUBLIC_API_ORIGIN` and `ADMIN_WEB_URL` localhost fallbacks: a deploy that forgets the var silently routes real users to a nonexistent local API with no error. **This phase is exactly where that bug goes live.** The plan must include fail-loud env validation for the admin app (mirror the api's `loadEnv` fail-fast) as a deploy gate. A silent prod failure on the customer-facing surface is a revenue leak you can't even see.
5. **MEDIUM — wildcard TLS for multi-tenant subdomains.** Multi-brand domains (`*.menu.resto.app`, custom domains) need wildcard/SNI cert handling. Confirm the chosen host issues wildcard certs and supports per-tenant custom domains, or the multi-tenant story breaks at the first real brand. Cloudflare in front solves this cheaply.
6. **MEDIUM — migrations as a pre-rollout step with no rollback story.** Success criterion 3 runs `pnpm db:migrate` before rollout. Forward-only is fine for now, but the plan should state what happens on a failed migration mid-deploy (does the old version keep serving?). One sentence; cheap to address.
7. **LOW — error tracking absent (no Sentry).** Not a blocker for first customer, but flag it: you will be flying blind on prod exceptions. A free-tier Sentry is a 30-minute add and worth doing here rather than after the first paid order silently 500s.

## Recommended leanest defensible stack

- **App host:** Railway (or Fly) — git-push deploy, native secrets, automatic TLS. ~$20–40/mo.
- **Postgres:** managed (Neon for scale-to-zero economics, _or_ Railway/RDS) — **chosen only after the 3-role schema is validated against it (BLOCK #1).** Use as plain Postgres; no proprietary features. $0–38/mo.
- **Object storage:** Cloudflare R2 — free egress, S3-compatible. ~$0–5/mo.
- **NATS:** single managed/self-hosted node now; HA deferred until post-PMF. $0–15/mo.
- **DNS/TLS/edge:** Cloudflare, wildcard cert for tenant subdomains. ~$1–2/mo.
- **CD:** extend existing nx-affected GitHub Actions → deploy-on-merge-to-`main`. $0.
- **Backups:** automated daily snapshot + **one rehearsed restore** (BLOCK #2).
- **All-in: ~$40–90/month at zero scale.** Founder-time to stand up: target **under one week**.

## Verdict & conditions

**Posture: Pursue — proceed to plan, with two BLOCK gates.** The phase is correctly scoped and capital-efficient in intent; the risk is execution drift toward over-building. Nothing here changes my fundability read of the company — it's the _absence_ of a prod deploy that was the risk, and closing it is strictly positive.

**Conditions I'd want answered before the plan is approved:**

1. Proof the 3-role + RLS + boot-preflight security model works on the chosen managed Postgres (BLOCK #1).
2. Backups + one tested restore in the plan's scope before any paying tenant (BLOCK #2).
3. An explicit "no Terraform/k8s/multi-region in 7.5" line in the plan, so the leanness is a written constraint, not a hope (anti-gold-plating).
4. Fail-loud env validation for the admin app as a deploy gate (HIGH #4).

## What I did NOT review

- Whether the application code is actually deploy-ready (build artifacts, container, health/readiness endpoints) — that's the CTO's lane.
- Stripe Connect availability/terms in target EU markets — a Phase 8 question, not 7.5.
- Market sizing, ARR, valuation — out of scope for a deploy-phase review.
- The 12-month roadmap's plausibility beyond "this phase unblocks Phase 8 revenue."
