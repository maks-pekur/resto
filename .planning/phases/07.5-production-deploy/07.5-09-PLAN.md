<objective>
Make deployment boring: merge to main, and the running system becomes that commit —
with the two failure modes that would be catastrophic here made impossible rather than
documented.

Purpose: the box exists (plan 08) but everything on it was placed by hand. A hand-placed
system drifts from what CI tested within days. The two things this pipeline must never
do are destroy the database volume and run migrations under the wrong role, and both are
easier to do accidentally than deliberately.

Output: `.github/workflows/deploy.yml`, an input-assertion script wired as its first
step and the destructive-command guard wired into CI, a website Dockerfile that can no
longer bake a stale domain, a runbook, and one proven rollback.
</objective>

`packages/db/src/cli/migrate.ts` does NOT fail closed on a missing admin URL:
```typescript
const adminUrl = process.env.DATABASE_ADMIN_URL;
const url = adminUrl ?? process.env.DATABASE_URL;      // silent fallback
if (!adminUrl) logger.warn('DATABASE_ADMIN_URL not set — falling back to DATABASE_URL …');
```
So a misnamed or empty secret does not produce "you forgot the admin URL"; it produces
a confusing Postgres permission error, or worse, a migration attempted under the
runtime role. The workflow must treat a missing `DATABASE_ADMIN_URL` as its own
configuration failure (Pitfall #8).

`apps/website/Dockerfile` currently defaults a domain at build time:
```dockerfile
ARG NEXT_PUBLIC_API_ORIGIN
ARG WEBSITE_URL=https://resto.app        # <- a baked default nobody chose for this deploy
ENV NEXT_PUBLIC_API_ORIGIN=$NEXT_PUBLIC_API_ORIGIN
ENV WEBSITE_URL=$WEBSITE_URL
```
`apps/website/lib/env.ts` validates both with Zod at build time and rejects localhost in
production, so an *absent* value already fails the build loudly — but a *defaulted* one
does not. That default is the same class of bug as G-05.

The compose services the workflow drives (plan 06): `api`, `website` recreated by tag;
`migrate` behind `profiles: ["tools"]` so it never starts with `up -d`; `postgres`,
`nats`, `caddy` never touched by CD.

    **`infra/scripts/assert-deploy-inputs.sh`** — the first thing the deploy job runs.
    It reads the required names from the environment and exits non-zero, listing every
    one that is unset or empty, before the workflow does anything with side effects:
    `PUBLIC_APEX_DOMAIN`, `GHCR_OWNER`, `SSH_HOST`, `SSH_USER`, `SSH_PRIVATE_KEY`,
    `DATABASE_ADMIN_URL`, `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`,
    `VITE_STRIPE_PUBLISHABLE_KEY`. It additionally rejects a `DATABASE_ADMIN_URL` whose
    userinfo names `resto_app` or `resto_auth` — the migration must run as the schema
    owner, and a copy-pasted app connection string is the realistic way that goes wrong.
    It must not echo any value, only names. This exists because `migrate.ts` warns
    rather than refuses; the gate has to live here.

    **`.github/workflows/deploy.yml`** — triggered by `workflow_run` on CI's completion
    for `main`, guarded by `github.event.workflow_run.conclusion == 'success'`, so it
    gates on green CI without duplicating the matrix. Concurrency group on the workflow
    name with `cancel-in-progress: false` — two overlapping deploys running migrations
    against one database is not a race worth having. Steps in order:

    1. Checkout, then `bash infra/scripts/assert-deploy-inputs.sh`.
    2. Log in to `ghcr.io` with `GITHUB_TOKEN`; build and push
       `resto-api` (target `runtime`), `resto-migrate` (target `migrate`) and
       `resto-website`, each tagged with `${{ github.sha }}`. The website build passes
       `NEXT_PUBLIC_API_ORIGIN=https://api.${{ vars.PUBLIC_APEX_DOMAIN }}` and
       `WEBSITE_URL=https://${{ vars.PUBLIC_APEX_DOMAIN }}` as build args. Build the
       migrate image from the same Dockerfile target plan 06 added, so the migration
       always runs the same commit's schema code as the app it precedes.
    3. Build the two SPA bundles with their build-time env derived from the apex
       (`VITE_ADMIN_HOST_SUFFIX=admin.${{ vars.PUBLIC_APEX_DOMAIN }}`,
       `VITE_STRIPE_PUBLISHABLE_KEY`).
    4. **Gated migration over SSH.** Postgres has no public endpoint by design, so this
       cannot run from the runner: `appleboy/ssh-action` with `envs:` carrying
       `DATABASE_ADMIN_URL`, `API_IMAGE_TAG`, `WEBSITE_IMAGE_TAG`, running
       `docker compose -f docker-compose.prod.yml run --rm -e DATABASE_ADMIN_URL migrate`
       in `/opt/resto`. The step's failure stops the job — nothing is recreated and the
       previous version keeps serving.
    5. `docker compose pull api website` then
       `docker compose up -d --no-deps api website`. Never `docker compose down`, with
       or without `-v`, and never a bare `up -d` that would sweep in the other services.
    6. `cloudflare/wrangler-action` twice, once per app, with the `--var`/`--routes`
       invocation recorded in `docs/runbooks/spa-workers.md` (or the rendered-config
       fallback, whichever plan 07 landed on), routes derived from
       `vars.PUBLIC_APEX_DOMAIN`.
    7. Poll `https://api.${{ vars.PUBLIC_APEX_DOMAIN }}/healthz` until 200 with a
       bounded retry, failing the job on timeout, and print the last response body on
       failure so a red deploy says why.

    Every hostname in the file is an expression over `vars.PUBLIC_APEX_DOMAIN`. There
    must be no literal domain anywhere in it.

    **`apps/website/Dockerfile`** — remove the `=https://resto.app` default from the
    `WEBSITE_URL` ARG so the build fails when the arg is missing, exactly as it already
    does for `NEXT_PUBLIC_API_ORIGIN`. Nothing else in that file changes; the standalone
    build shape from plan 07.5-11 stays.

    **`.github/workflows/ci.yml`** — add `bash infra/scripts/assert-no-destructive-compose.sh`
    as a step in an existing fast job (the `format` job is the natural home). Plan 06
    wrote the guard; without a CI step it only runs when someone remembers, which is
    precisely the failure mode Pitfall #7 describes.

    **Do not** write a `docker compose down` anywhere, and do not add a "clean slate"
    convenience step. The compose file's volumes are the production database.

    proved stops working. Add the standing warnings: `DATABASE_ADMIN_URL` never becomes
    a file on the box, and no automation ever runs `docker compose down`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner → VPS | an SSH key with shell access to production lives as a repo secret |
| GitHub Actions runner → production database | `DATABASE_ADMIN_URL` crosses here for the length of one command |
| GHCR → VPS | the box executes whatever image the pipeline pushed |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07.5-09-01 | Elevation of Privilege | migration running under the app role after a silent fallback | mitigate | `assert-deploy-inputs.sh` fails the job on an unset `DATABASE_ADMIN_URL` and on a connection string naming `resto_app`/`resto_auth`; `migrate.ts`'s own warn-and-continue is never relied on |
| T-07.5-09-02 | Denial of Service (self-inflicted) | a `docker compose down -v` reaching the deploy path | mitigate | targeted `up -d --no-deps` only; `assert-no-destructive-compose.sh` wired into CI so the guard runs on every PR; comment lines stripped before matching |
| T-07.5-09-03 | Elevation of Privilege | deploy SSH key compromise | mitigate | a deploy-only key generated for this purpose, stored only as a repo secret, on an unprivileged user; rotation procedure in the runbook |
| T-07.5-09-04 | Tampering | a stale or wrong-domain website bundle | mitigate | build args derived from `vars.PUBLIC_APEX_DOMAIN`; the `WEBSITE_URL` default removed so a missing arg fails the build rather than baking a domain nobody chose |
| T-07.5-09-05 | Tampering | two concurrent deploys migrating the same database | mitigate | workflow-level concurrency group with `cancel-in-progress: false` |
| T-07.5-09-06 | Information Disclosure | secrets echoed into workflow logs | mitigate | the assertion script prints names only; no step echoes a secret; `envs:` passes values into the SSH session rather than interpolating them into the script text |
| T-07.5-09-SC | Tampering | GitHub Actions supply chain | mitigate | pinned major versions of `docker/build-push-action`, `cloudflare/wrangler-action`, `appleboy/ssh-action` per RESEARCH.md's Standard Stack; `docker/build-push-action` is `[ASSUMED]` there — confirm the current major at execution time rather than inheriting the assumption |
