<objective>
Make deployment boring: merge to main, and the running system becomes that commit — including the
parts of it that are not application code.

Purpose: the box exists (plan 07.5-08) but everything on it was placed by hand, and a hand-placed
system drifts from what CI tested within days. The pipeline must never destroy the database volume
and must never run migrations under the wrong role; both are easier to do accidentally than
deliberately, so both get a gate rather than a convention.

Output: `.github/workflows/deploy.yml`, an input-assertion script wired as its first step, all three
repo guards wired into CI, a website Dockerfile that can no longer bake a stale domain, a runbook,
and one rollback proven with evidence a script can read.
</objective>

`packages/db/src/cli/migrate.ts` does NOT fail closed on a missing admin URL:

```typescript
const adminUrl = process.env.DATABASE_ADMIN_URL;
const url = adminUrl ?? process.env.DATABASE_URL;      // silent fallback
if (!adminUrl) logger.warn('DATABASE_ADMIN_URL not set — falling back to DATABASE_URL …');
```

A misnamed or empty secret produces a confusing Postgres permission error, or a migration attempted
under the runtime role — never "you forgot the admin URL". The gate has to live in the workflow
(Pitfall #8).

`apps/website/Dockerfile` defaults a domain at build time:

```dockerfile
ARG NEXT_PUBLIC_API_ORIGIN
ARG WEBSITE_URL=https://resto.app        # a baked default nobody chose for this deploy
```

`apps/website/lib/env.ts` validates both with Zod at build time and rejects localhost in production,
so an *absent* value already fails the build loudly — a *defaulted* one does not. Same class as
G-05.

**`API_INTERNAL_ORIGIN` is not a build arg.** Plan 07.5-14 added it as a server-runtime value read
by the `server-only` `lib/env.ts`, and `infra/docker/env/website.env.example` supplies it as
`http://api:3000`. It reaches the container through `env_file:` on the box, not through
`docker build`. Do not add it to the image build; a build arg would bake a Compose service name
into a bundle.

**The two SPA deploys are assets-only after plan 07.5-12.** No `--var`, no `API_ORIGIN`, one route
pattern each, and each project's `wrangler.jsonc` carries no `routes` and no `vars`:

```bash
wrangler deploy --routes "${{ vars.PUBLIC_APEX_DOMAIN }}/admin*"     # apps/admin
wrangler deploy --routes "*.${{ vars.PUBLIC_APEX_DOMAIN }}/qr*"      # apps/qr-menu
```

Each build must produce the nested asset layout those routes require — `dist/admin/` and `dist/qr/`
with a root `dist/index.html` copy — which both `build` scripts now do. A deploy from a stale
`dist/` is the realistic way `/qr/t/<token>` starts 404ing after a green pipeline, so build in the
same job that deploys.

**Build-time env the two SPA bundles need:** `VITE_STRIPE_PUBLISHABLE_KEY` for both, and
`VITE_PUBLIC_APEX_DOMAIN` for admin (introduced in phase 07.4 plan 04, replacing the deleted
`VITE_ADMIN_HOST_SUFFIX`; it drives the onboarding storefront preview). `VITE_ADMIN_HOST_SUFFIX`
does not exist anywhere in the tree — a repo-wide grep for it returns nothing outside `.planning/`,
per 07.4-04's own verification.

The compose services this workflow drives (plan 06): `api` and `website` recreated by tag; `migrate`
behind `profiles: ["tools"]` so it never starts with `up -d`; `postgres`, `nats` and `caddy` never
touched by CD except when the Caddyfile itself changed. The migrate image is built from the
`migrate` target of `apps/api/Dockerfile`, which exists because the runtime image lacks `pnpm` and
`packages/db/node_modules`.

Provisioning order, everywhere in this phase: migrations first, roles second (`ci.yml:253-259`). CD
only migrates; roles are provisioned once, in plan 07.5-08.

**The three guards, all with `--self-test` modes** (`infra/scripts/`):
`assert-no-destructive-compose.sh`, `assert-no-domain-literals.sh` (one apex after plan 07.5-14),
`assert-hostname-depth.sh` (takes a rendered env file as its argument).
