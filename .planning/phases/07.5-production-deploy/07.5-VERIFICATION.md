# Phase 7.5 plans 06-10 — verification

**Verdict: BLOCK on all five.** 14 blockers, 13 flags. Structure, wave graph and threat models
are sound; execution as written does not produce a working deployment. Four blockers stop
execution outright; three let the phase reach "go-live" with broken email, a live cross-tenant
cache-leak vector, and an unproven rollback.

Wave graph, `depends_on`, and 06/07 file-disjointness were checked and are **correct**.

## Blockers, cheapest-first

### M3 — nothing verifies tenant resolution until go-live
Plans 06-09 assert only `/healthz` (tenant-less), stubbed `fetch` in Worker unit tests, and the
SPA shell from `env.ASSETS` (never reaches the API). Plan 08 Task 3 permits deferring the live
`/v1/menu` check to plan 10, which on a fresh box always applies. The system can reach the end of
plan 09 — CD green, four hostnames at 200 — with the guest menu completely dead.

**Fix:** mandatory assertion in `verify-prod-origin.sh --stage full`:
`GET https://<probe-slug>.menu.<apex>/v1/menu` returns 200 with a JSON body naming that tenant.
One seeded tenant suffices. Cheapest change in the review; converts M2 from a go-live surprise
into a plan-08 failure.

### M1 — role provisioning ordered before migration; hard-fails
Plans say roles-then-migrate (`07.5-06-PLAN.md:377`, `07.5-08-PLAN.md:272-276`). The real order is
the inverse: `.github/workflows/ci.yml:253` migrations → `:257` roles; `packages/db/test/setup.ts:56`
same. **Verified independently.** `packages/db/sql/auth-role.sql:14-24` issues an *unguarded*
`GRANT ... ON "user", session, account, verification, two_factor, member, invitation, tenant_role`
— every other statement in that file is wrapped in an `IF EXISTS` DO-block, this one is not. On a
fresh database it raises `relation "user" does not exist`, the CLI exits 1, `set -euo pipefail`
kills the run. Plan 06 Task 3 fails on the laptop; plan 08 Task 3 fails on the paid box.

**Fix:** swap the order in `07.5-06-PLAN.md:377`, `:363-364` and `07.5-08-PLAN.md:272-276`. Cite
`ci.yml:253-259` in the plan text as the reference order.

### M2 — Caddy discards `X-Forwarded-Host`; breaks every guest menu request
Chain: Worker sets `X-Forwarded-Host: pizza.menu.<apex>` → `fetch https://api.<apex>/v1/menu` →
Cloudflare → **Caddy** → `api:3000`. Caddy's `reverse_proxy` sets `X-Forwarded-Host` from the
request's own Host and preserves an inbound value only when the client IP is in `trusted_proxies`,
which is empty by default. `effectiveHost()` then returns `api.<apex>`;
`NON_GUEST_SECOND_LABELS = new Set(['admin','api','www'])`
(`tenant-resolver.service.ts:13`, **verified**) rejects it; no tenant binds.
`trusted_proxies` appears nowhere in RESEARCH.md or in any of the five plans. Research Pitfall #3
analyses the Worker→origin hop and stops one hop short.

**Fix:** global options block in plan 06's Caddyfile spec with `servers { trusted_proxies ... }`.
Given ufw already restricts 80/443 to Cloudflare ranges, `static 0.0.0.0/0 ::/0` is defensible with
a two-line WHY comment tying it to the firewall — but it must be a written decision, not an
omission. Pin the image tag: `caddy:2-alpine` floats and `trusted_proxies` semantics changed in 2.7.

### B-guard — the destructive-compose guard rejects the plans' own deliverables
Plan 06 Task 2 specifies the guard flags `docker compose down` / `docker-compose down` "in any
form" across `infra/scripts/*.sh`, `infra/docker/*.yml`, `.github/workflows/*.yml` and
`docs/runbooks/*.md`. Then four deliverables contain exactly that: `local-prod-rehearsal.sh`
(`:387`, and Task 3's verify runs the script *and* the guard, `:404`), plus required runbook text in
`07.5-06-PLAN.md:393`, `07.5-09-PLAN.md:283`, `07.5-10-PLAN.md:325`. Markdown `#` is a heading, not
a comment, so the comment-stripping escape does not save the runbooks. Likely outcome: the executor
weakens the guard to make its own artifacts pass — the exact failure Pitfall #7 exists to prevent.

**Fix:** one rule, stated once — flag any compose invocation carrying `-v`/`--volumes` everywhere;
flag bare `docker compose down` in `.github/workflows/` and `infra/scripts/` only; exempt `docs/**`
from the `down` rule. Then drop the `down` from the rehearsal script (it already does
`docker rm -f` + explicit `docker volume rm`) or exempt it deliberately and say why.
Widen the scan to `infra/scripts/*` regardless of extension — plan 10 adds `go-live-smoke.mjs`.

### RESEND_FROM / RESEND_REPLY_TO default to an unowned apex
`apps/api/src/config/env.schema.ts:313,315` default to `RestOS <noreply@resto.app>` /
`support@resto.app`. `ResendEmailAdapter` uses `env.RESEND_FROM` verbatim (`resend.adapter.ts:180`).
They are `.default()`s, so always populated, and `assertProdGuardrails` never inspects them. On any
other apex, Resend rejects every send: **operator invitations, password resets and email
verification all fail silently** while `/healthz` stays 200. Absent from plan 06's
`api.env.example` inventory (`:279-288`) and from RESEARCH.md's secret inventory (`:460`). Plan 06
Task 1 has the founder verify a sending domain *on the apex*, making the mismatch certain.

**Fix:** add both to `api.env.example` as `noreply@${PUBLIC_APEX_DOMAIN}` /
`support@${PUBLIC_APEX_DOMAIN}`, and add them to the dev-default guard set so a forgotten override
fails closed at boot.

### M4 — infra files never reach the box after the first manual copy
Plan 08 Task 2 has the founder hand-copy `docker-compose.prod.yml` and the `Caddyfile` to
`/opt/resto` (`:233`). Plan 09's `deploy.yml` (`:166-192`) never copies them again — it only runs
the migrate service and `up -d --no-deps`. So any later compose/Caddyfile change is committed,
passes CI, and never reaches production: the exact drift plan 09 exists to prevent. Worse,
`backup-nightly.sh` and `restore-drill.sh` are **never** copied by any plan — `vps-bootstrap.sh`
creates `/opt/resto/scripts` (`:150`) and nothing populates it, yet plan 10 Task 1's verify runs
`ssh … 'cd /opt/resto && bash scripts/restore-drill.sh'` (`:197`).

**Fix:** step in `deploy.yml` between GHCR push and migration that rsyncs
`infra/docker/docker-compose.prod.yml`, `infra/docker/Caddyfile` and `infra/scripts/*.sh` to
`/opt/resto` (never `env/` templates, never secrets), then `docker compose config -q` as a syntax
gate before recreate. Add `up -d --no-deps caddy` when the Caddyfile hash changed.

### Cloudflare zone cache can leak across tenants — research's mitigation is incomplete
Plan 07 Task 1's unit tests are the best-specified work in the phase and **pass on their stated
scope** (they assert the key is the incoming URL, warm pizza then request sushi, require a second
origin call, and require the executor to watch the test go red first). But the Worker's Cache API
and Cloudflare's *zone* cache are different caches. The inner
`fetch('https://api.<apex>/v1/menu')` is byte-identical for every tenant, the tenant lives in a
header, and the origin marks the response `public, s-maxage=300` (`menu-cache.ts:5`). If that inner
fetch is ever cached at the `api.<apex>` zone — via a Cache Rule, "Cache Everything", or the CDN
cache-rules CONTEXT D-08 commits to and **no plan ever creates** — tenant B's Worker receives
tenant A's menu before its own correctly-keyed cache is consulted. The tests stub `globalThis.fetch`
and structurally cannot surface this.

**Fix:** issue the subrequest as `fetch(originRequest, { cf: { cacheTtl: 0, cacheEverything: false } })`
and assert the `cf` init option on the recorded call. Belt-and-braces: plan 08's Cloudflare runbook
specifies a Cache Rule setting `api.<apex>/v1/*` to Bypass. Settle D-08 explicitly — the Worker
cache silently replaces those CDN rules and no plan says so.

### Plan 10 assertions 4 and 5 test contracts that do not exist
Assertion 4 (`:285`) requires `cf-cache-status` MISS→HIT. That header is emitted by Cloudflare's own
cache pipeline; a Worker serving from `caches.default` does not produce it, and plan 07 never asks
either Worker to emit any cache signal. Assertion 5 (`:287`) requires tenant B's `ETag` to differ
from tenant A's, but `public-menu.controller.ts:272,298` builds the ETag as `'"' + version + '"'` —
a bare menu-version integer, **not tenant-scoped**. Two freshly published tenants are both at
version 1 and emit identical ETags, so in the exact fresh-production scenario this smoke targets the
assertion fails for a reason unrelated to isolation — which is how an executor ends up deleting the
phase's most important check. Plan 10's interfaces block (`:145`) repeats research's incorrect
"per-tenant ETag" claim.

**Fix:** have both Workers set `X-Resto-Cache: HIT|MISS`, assert it in plan 07's tests and in plan 10
assertion 4; drop the ETag clause from assertion 5 and keep the body comparison, which is the part
that means something.

### Plan 10 assertion 6 is a coin flip described as the highest-value check
`:293-295` asserts a wrong-password `POST /api/auth/sign-in/email` returns 4xx "carrying no
`Access-Control-Allow-Origin`". CORS middleware emits ACAO only when the request carries `Origin`;
a Node script sends none — so the header is absent in a correct same-origin setup *and* in a totally
broken cross-origin one. Conversely if the smoke did send `Origin: https://admin.<apex>`,
`buildOriginMatcher(env.CORS_ALLOWED_ORIGINS)` (`security.ts:171`) would emit ACAO on a correct
setup, because plan 06's `api.env.example` populates `CORS_ALLOWED_ORIGINS`.

**Fix:** assert the 4xx body is Better Auth JSON rather than `text/html` — that proves
`run_worker_first` bound `/api/*`. For the actual F-41 regression net, sign in once with valid
credentials and assert `Set-Cookie` carries `Domain=.admin.<apex>`.

### Plan 09 Task 3 does not verify the rollback it exists to prove

whether or not a rollback happened. The `<done>` claims the prior image served real traffic and the
journal count was identical before/during/after; none of it is checked.

**Fix:** require a machine-checkable rollback-log block appended to `cd-deploy.md` (prior SHA,
current SHA, journal count before/after, elapsed seconds) and assert
`grep -qE 'rollback observed: [0-9]+s'` plus `grep -qE 'journal rows: ([0-9]+) -> \1'`.

### The domain-literal guarantee's own enforcement has a hole
All five plans use `grep -rnoE '[a-z0-9-]+\.(app|com|dev|io|net|org)'` (`06:328`, `07:310`,

The R2-first default (`10:178-180`) and re-provisioning roles through the committed CLIs are right.
Four gaps:

- **Content checks do not check content.** Journal count proves schema version, not data; no table
  is named; no count is compared against the source. Plan 06's variant is weaker still — a

- **`pg_restore` exit code is not evidence.** Without `--exit-on-error` it continues past failures.

## NEW-1 (BLOCKER, plan 06) — the `client_ip` gate is bypassable; proved empirically

Caddy v2.11.4 run in Docker with exactly the configuration plan 06 Task 2 specifies
(`trusted_proxies static 0.0.0.0/0 ::/0`, `not client_ip <allowed>` on `path /internal*`):

| Test | Request | `client_ip` resolved to | `/internal*` |
|---|---|---|---|
| T2 | no XFF | `192.168.215.1` (direct peer) | 404 BLOCKED |
| T3 | `X-Forwarded-For: 203.0.113.7` | `203.0.113.7` | **200 ALLOWED** |
| T4 | `X-Forwarded-For: 203.0.113.7, 198.51.100.9` (the Cloudflare-append shape) | `203.0.113.7` | **200 ALLOWED** |

Caddy's right-to-left walk returns the rightmost address *not* in the trusted set. With
`0.0.0.0/0` nothing is untrusted, the walk finds no candidate, and **the leftmost XFF entry wins**.
T4 is decisive: Cloudflare *appends* the visitor IP to a client-supplied `X-Forwarded-For`, so a
forged value sits leftmost and is what `client_ip` returns.

The gate admits the founder (their genuine request carries their IP leftmost), which is what makes
it look like it works — and simultaneously admits anyone who sends one header. The founder's IP is
not a secret.

Plan 06's justification (`:315-318`) is false in both directions: Cloudflare **appends** to
`X-Forwarded-For` and **overwrites** `CF-Connecting-IP`; and the two decisions do not hold each
other up — the blanket trust that fixes M2 is precisely what breaks the gate. Baseline B2 confirms
it: without `trusted_proxies`, `client_ip` correctly ignored the forged XFF.

`InternalTokenGuard` (`internal-token.guard.ts`) is real and independent — constant-time compare,
throws outside development when unset or mismatched, applied via `@UseGuards` on both internal
controllers. So `/internal*` is not actually exposed and the layer is decorative, not load-bearing.
**That is not the problem.** Plan 08 Task 3 (`:373-374`) and threat `T-07.5-08-04` cite the gate as
the reason the seed path is safe. A plan that tells the founder a surface is IP-restricted when it
is not retires the vigilance that would otherwise apply. That claim must not ship, fixed or not.

**Fix, verified working:** add `client_ip_headers CF-Connecting-IP` to the `servers` block.

| Test | Request | `client_ip` | `/internal*` |
|---|---|---|---|
| C1 | forged `XFF` only | direct peer | 404 BLOCKED |
| C2 | `CF-Connecting-IP: <founder>` | `<founder>` | 200 ALLOWED |
| C3 | forged `XFF` + real `CF-Connecting-IP` | real | 404 BLOCKED |
| C4 | `X-Forwarded-Host` through `reverse_proxy` | — | **preserved** |

C4 matters: the M2 fix survives. Scoping `trusted_proxies` to Cloudflare ranges is also sound and
would fix NEW-5 too, but depends on Docker's published-port DNAT preserving the source IP — which
the test showed it does not on that host. Use `client_ip_headers` as the primary fix, and add an
assertion to `--stage full` that a request carrying `X-Forwarded-For: <allowed-ip>` from an
unlisted source still gets 404, so the gate has a test rather than a paragraph.

## NEW-2 (BLOCKER, plan 09) — the CI domain guard turns CI permanently red on the likeliest apex

`07.5-09-PLAN.md:229` runs `assert-no-domain-literals.sh infra apps .github`. Measured:
`grep -rIF "resto.app" apps` → **264 hits across 30+ files**; `infra .github` → 12. Excluding tests
and build output, ~30 remain in non-test source, including `env.schema.ts` (~15 doc comments),
`exception.filter.ts:91` and `admin-host.ts:6`. If the founder's apex is `resto.app` — the most
likely choice, and the one plan 06 Task 1 explicitly offers — **CI goes red the moment plan 09
lands** and stays red until someone deletes 264 mostly-legitimate occurrences. On any other apex:
zero hits. The guard's behaviour is a coin flip on a decision made two plans earlier, landing on
the failing side for the most probable choice.

Secondary: no exclusions, so `grep -r` traverses `node_modules` and `apps/admin/dist` (gitignored,
so CI is safe, but any developer who has run a production build fails locally on *any* apex,
because `VITE_ADMIN_HOST_SUFFIX` bakes the apex into `dist/assets/*.js.map`). And "fail if the apex
variable is unavailable" turns a missing repository variable into a blocked repository — say what
CI does on fork PRs.

**Fix:** scope the CI invocation to what the guarantee is about — `infra .github`,
`apps/website/Dockerfile`, `apps/*/wrangler.jsonc`, `apps/*/worker` — and hard-exclude
`node_modules`, `dist`, `.next`, `coverage`. For a repo-wide sweep, add an allowlist of accepted
pre-existing occurrences so the check is about *new* literals; that also gives the
`exception.filter.ts:91` namespace follow-up a place to live.

## NEW-3 (BLOCKER, plan 06) — the rehearsal does not need real credentials, and requiring them is a regression

Traced the boot path. `createEmailAdapter` for `production` rejects an empty `RESEND_API_KEY`,
rejects the exact dummy literal, then `createResendClientAdapter(new Resend(key), …)`.
`new Resend(key)` performs **no network call**. So `re_rehearsal_local_only` constructs the adapter,
`adapterName === 'resend'`, and the second `assertProdGuardrails` passes. Stripe is identical —
`tenancy.module.ts:80` is constructor-only, and `prod-guardrails.ts` checks only non-empty /
not-the-dummy / no `replace_me|change_me`. Nothing in Task 3 sends an email or calls Stripe.

So `07.5-06-PLAN.md:464-469` — *"neither can be satisfied synthetically"* — is factually wrong, and
it costs real things: it makes a mechanical task need the founder present with live secrets; it puts
a **live Stripe secret key** into the environment of a script whose transcript is pasted into a
summary (`:496`), against Task 1's own rule at `:252`; it couples Task 3 to Task 1 across a
checkpoint for zero verification value; and it propagates into the founder-facing prerequisites
(`:43`).

**Fix:** treat Stripe and Resend exactly as plan 06 already treats the S3 quartet — synthetic,
non-dev-default, non-placeholder, enumerated in the script, with a one-line WHY that both SDK
constructors are inert and both guardrails are string checks. Keep Task 1's gathering (they *are*
needed at plan 08 Task 3 against the real box); drop the Task 3 dependency.

## NEW-5 (FLAG, borderline BLOCKER, plan 06) — the same header confusion breaks rate limiting

Caddy **appends** its direct peer to the inbound XFF, so the API receives
`XFF: <forged?>, <real-client>, <cf-edge-ip>`. `main.ts:42` uses
`trustProxy: parseTrustProxy(bootEnv.TRUST_PROXY)`; plan 06 specifies `TRUST_PROXY` only as "a CIDR
list" (`:332`) and its rehearsal sets the Docker bridge alone (`:463`) — the natural template for
production. With `TRUST_PROXY=172.16.0.0/12`, `proxy-addr` walks right-to-left, finds the Cloudflare
PoP outside the range and stops: **`req.ip` = the Cloudflare PoP address.**

`rateLimitKeyGenerator` (`security.ts:66-74`) keys on `ip:${req.ip}` for anonymous traffic and
unconditionally for credential routes. So `RATE_LIMIT_AUTH_SIGNIN_PER_MIN` becomes a **per-PoP**
limit — one abusive client locks a whole restaurant's staff out of admin — and credential stuffing
from rotating sources dilutes across PoPs while `req.ip` stops identifying anyone.

**Fix:** `TRUST_PROXY` = compose bridge **plus** Cloudflare's published ranges, stated in
`api.env.example` and the rehearsal. Widening is safe for tenant resolution: `effective-host.ts:13`
gates on `TRUST_PROXY.length > 0`, a boolean, and never evaluates the CIDRs.

## NEW-4 (FLAG, plan 08) — the `--stage full` negative test is vacuous

`07.5-08-PLAN.md:289` runs the negative invocation without `PROBE_TENANT_SLUG`, which `--stage full`
refuses to run without — so it exits non-zero because of the missing variable, not because an
assertion failed. It would pass identically against a script whose menu assertion was `true`.
**Fix:** add `PROBE_TENANT_SLUG=nonexistent`. The `--stage network` negative test is sound.

## NEW-6 (FLAG, plan 06) — the guards miss line continuations and have no test of their own

Comment-stripping cannot smuggle (`docker compose down -v  # cleanup` is still caught), but a
line-oriented matcher misses:

```sh
docker compose \
  down -v
```

and `CMD="docker compose"; $CMD down -v`. The first is a plausible formatting accident. Neither
guard has any test that it fires. **Fix:** join continuations
(`sed -e ':a' -e '/\\$/N; s/\\\n//; ta'`) before matching, and add a `--self-test` mode running
both guards against inline fixtures — `down -v`, bare `down`, a line-continuation form — failing if
any is missed; wire it into the same CI step. A guard nobody has watched fail is in the same
category as a rollback nobody has watched work, a standard this phase otherwise applies rigorously.

## The pattern worth naming

Round 1 found three errors clustered in the edge-cache subsystem, all inherited from research
without re-derivation. Round 2's three new defects cluster the same way: all three are **claims
about what a component does** — Cloudflare's XFF semantics, the Resend/Stripe constructors'
behaviour, the grep's blast radius — asserted confidently and never executed. The remediation's own
standard is the right one and is applied everywhere else in these plans: the observation goes in the
summary, and a script re-checks it. **Any sentence in a plan asserting how a third-party component
behaves needs either a citation or a command.**
