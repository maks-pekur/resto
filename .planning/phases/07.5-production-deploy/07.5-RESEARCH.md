## Summary

The founder's own env.schema.ts, `.env.example`, and the phase-10.2 `10.2-FINDINGS.md` retrospective (F-41/F-42) already fix almost every architectural question this phase would otherwise have to answer from scratch: the four production hostnames are already chosen (`api.resto.app`, `resto.app`+`*.resto.app`, `admin.resto.app`+`*.admin.resto.app`, `*.menu.resto.app`), the cookie-domain scoping is already implemented and Zod-validated (`AUTH_COOKIE_DOMAIN` must start with `.` and is documented as `.admin.resto.app`), and the same-origin-proxy requirement for the SPA surfaces is already proven necessary in code — not just in this research. **What this research adds is the mechanism**: how to actually serve `*.admin.resto.app` and `*.menu.resto.app` as static SPA bundles with a same-origin `/v1/*` (+`/api/*` for admin) rewrite to the VPS, given that classic Cloudflare Pages custom domains — the product CONTEXT.md's prose names — do not support wildcard custom domains as of 2026 and never have. The concrete, current (2026), Cloudflare-documented replacement is **Cloudflare Workers with Static Assets** (`developers.cloudflare.com/workers/static-assets/`), which serves the identical SPA bundle, is still "Cloudflare's free static edge hosting," and additionally lets the *same* Worker script implement the same-origin proxy — collapsing what would have been two separate mechanisms (Pages + a bolt-on Worker route) into one deployable per app.

The second load-bearing finding is a genuine pitfall, not just a mechanism swap: a naive reverse-proxy Worker that does `fetch('https://api.resto.app' + path)` collapses Cloudflare's default host+path cache key across every tenant, because every tenant's qr-menu request ends up targeting the *same* rewritten URL. Left unfixed, this would either silently defeat the existing `docs/runbooks/menu-edge-caching.md` edge-cache design (if Cloudflare doesn't cache it at all) or — worse — serve one tenant's cached menu to another tenant's guests (if it does cache, keyed on the wrong thing). The fix is well-documented Cloudflare Workers Cache API usage: key the cache explicitly on the *original* incoming request URL (which carries the tenant subdomain), not the rewritten outbound one. Full working code is in Pattern 4.

Everything else in this phase is comparatively mechanical: one Hetzner VPS (CX32, €6.80/mo) running Docker Compose with `postgres` + `nats` + `api` + `website` + a `caddy` TLS-terminating reverse proxy (using a free, 15-year Cloudflare Origin CA certificate — no Let's Encrypt renewal cron needed); nightly `pg_dump` to R2 as the initial backup mechanism (WAL-G is the documented, not-yet-needed upgrade for a tighter RPO); GitHub Actions extended with a `deploy.yml` that builds images to GHCR, SSHes into the VPS for a gated migration + service recreate, and separately `wrangler deploy`s the two Worker-hosted SPAs.

**Primary recommendation:** Hetzner CX32 VPS (Docker CE marketplace image) running `docker-compose.prod.yml` (postgres + nats + api + website + caddy, Cloudflare Origin CA cert, no ports published except 80/443) behind Cloudflare (DNS/TLS/CDN) + two Cloudflare Workers-with-Static-Assets projects (admin, qr-menu) each bundling its own same-origin `/v1/*` proxy with tenant-correct edge caching; nightly `pg_dump` → R2 via `rclone`, R2 lifecycle rule for retention; GitHub Actions `deploy.yml` (gated `db:migrate` → SSH service recreate → `wrangler deploy` → `/healthz` poll).

### Pattern 1: `docker-compose.prod.yml` — what differs from the dev compose

**What:** A production sibling of `infra/docker/docker-compose.dev.yml`, reusing its shape (named volumes, healthchecks, `condition: service_healthy` dependency ordering) but diverging on every point that matters for running on a public box.

**Diffs from `docker-compose.dev.yml` (concrete, not general Compose advice):**

1. **No `ports:` on `postgres` or `nats` at all.** Dev maps `5432:5432` and `4222:4222`/`8222:8222` to the host for local tooling access; prod must drop every one of these — the only two things listening on the VPS's public interface are `caddy` (80/443). Anything else reachable from the internet is a direct violation of "self-managed Postgres = superuser" being safe (see Pitfall #6).
2. **Two new services, `api` and `website`**, pulling pre-built images from `ghcr.io/<org>/resto-api:${API_IMAGE_TAG}` / `ghcr.io/<org>/resto-website:${WEBSITE_IMAGE_TAG}` (immutable, commit-SHA-tagged) rather than `image: postgres:16-alpine` style upstream pulls. Dev has no equivalent — dev runs `apps/api`/`apps/website` via `pnpm dev`, not Docker.
3. **A new `caddy` service** terminating TLS with the Cloudflare Origin CA cert and reverse-proxying by `Host` header — dev has no TLS layer at all (plain `http://localhost:*`).
4. **Drop `minio`, `mailhog`, `jaeger`.** MinIO → R2 (external); MailHog → Resend (external, already required by `assertProdGuardrails`); Jaeger → not run in this phase (`OTEL_DISABLED=true` is an acceptable initial choice — Sentry already covers G-04's error-tracking requirement; a hosted OTLP endpoint can be added later without touching the compose shape).
5. **`restart: unless-stopped` on every service** (dev already does this for postgres/nats/mailhog/jaeger but not minio — prod should be uniform: a crash-looping container should keep trying, not sit dead, and Sentry/Caddy's own logs surface the loop for the founder to notice).
6. **`env_file:` per app service** (`api` reads `.env.api`, `website` reads `.env.website`) rather than the inline `environment:` blocks dev uses for infra services — this is what makes "secrets never in the image" concrete: the files live on the VPS filesystem (`chmod 600`), not in the compose file, not in git (Pattern 5).
7. **NATS gets `--user`/`--pass` flags** (or a mounted config file) for the first time — dev's NATS runs with no auth at all, acceptable only because it's not internet-reachable in dev either way. `[CITED: docs.nats.io/running-a-nats-service/introduction/flags]` — `nats-server --user <NATS_USERNAME> --pass <NATS_PASSWORD> --jetstream --store_dir=/data --http_port=8222`.

**How Postgres data survives a `docker compose down`:** The named volume `postgres-data` (declared once at the bottom of the compose file, exactly like dev) is *not* removed by a plain `docker compose down` — only `docker compose down -v` (or an explicit `docker volume rm`) destroys it. **The CD pipeline (Pattern 6) must never issue a blanket `docker compose down` at all** — service updates use `docker compose up -d --no-deps --pull always <service>` to recreate only the changed service(s), leaving `postgres`/`nats`/`caddy` untouched and their volumes never at risk from an automated step. `docker compose down` (without `-v`) is reserved for rare manual maintenance; `-v` must never appear in any script, cron job, or CD step — this is worth a one-line comment directly in the compose file given how easy the two are to conflate.

**Healthchecks:** `postgres` and `nats` keep the exact healthcheck commands already in `docker-compose.dev.yml` (`pg_isready`, `wget … /healthz`). `api` already ships its own `HEALTHCHECK` in `apps/api/Dockerfile` (`wget --quiet --spider http://localhost:3000/healthz`) — no compose-level override needed. `website` likewise (`apps/website/Dockerfile`, hits `/`). `caddy` needs no explicit healthcheck (Docker's own "is the process alive" is sufficient for a stateless proxy; add one later only if a real incident calls for it).

**Restart policy summary:** `unless-stopped` uniformly. This is a single-VPS, single-replica-per-service topology by design — `apps/api/src/shared/security.ts`'s in-process `identityBuckets` rate-limit store is explicitly documented (`.planning/codebase/CONCERNS.md`) as assuming exactly this topology ("no horizontal scale-out planned before a paying customer"). Do not run more than one `api` replica in this compose file without first addressing that in-memory state.

### Pattern 2: Postgres on the box

**What:** PostgreSQL 16 (`postgres:16-alpine`, matching dev) runs as a `postgres` service in the compose stack. Because it is self-managed, the connecting superuser (`POSTGRES_USER`/`POSTGRES_PASSWORD` set at container creation) is a *true* PostgreSQL `SUPERUSER` — not `rds_superuser` or any managed-platform proxy role. This retires the entire category of risk the old AWS research spent its longest section on (whether `rds_superuser` could confer `BYPASSRLS`).

**What this means concretely, checked against `packages/db`:**

- `packages/db/sql/roles.sql` and `packages/db/sql/auth-role.sql` are unchanged — they already run correctly against any standards-compliant Postgres, self-managed or not.
- `07.5-05` (already executed, 2026-06-26) replaced `resto_auth`'s `BYPASSRLS` role attribute with explicit permissive RLS policies (migration `0054_resto_auth_permissive_policies.sql`) specifically to make the app RDS-safe. **On self-managed Postgres this migration is no longer load-bearing for correctness — a true superuser could grant `BYPASSRLS` natively — but it should NOT be reverted.** It is already committed, already tested (71 passing tests per `07.5-05-SUMMARY.md`), portable to any future host, and strictly more auditable (`pg_roles.rolbypassrls = false` for every non-superuser role is a stronger invariant than "trust the policy scoping"). Treat it as free hygiene, not a requirement to re-litigate.
- **Tuning worth doing on a small VPS** (CX32: 8 GB RAM, 4 vCPU shared): Postgres 16's defaults (`shared_buffers=128MB`, `max_connections=100`) are conservative for an 8 GB box. A reasonable, low-risk starting point: `shared_buffers=1GB` (≈25% of an 8 GB VPS with 5 other containers competing for RAM — do not go higher without headroom analysis), `effective_cache_size=3GB`, `max_connections=40` (the app's own connection count is small: one pooled `api` connection group, one dedicated `DATABASE_DIRECT_URL` connection for the outbox advisory lock, migration/backup connections — 40 leaves generous headroom over anything MVP-1 volume needs). These are starting values, not tuned-and-measured numbers — `[ASSUMED]`, flagged for the founder/planner to sanity-check against actual `pg_stat_activity` once real traffic exists, not to accept as gospel.
- **Roles are provisioned the same way as CI does today**, not via a fresh mechanism: `packages/db/src/cli/provision-roles-ci.ts` already shows the exact pattern (`provisionAppRole` + `provisionAuthRole` against a fresh Postgres using admin credentials). The production runbook is this same flow run once against the VPS's `postgres` container instead of a CI service container — no new code, a documentation task.
- **Migrations run under `DATABASE_ADMIN_URL`** via `pnpm --filter @resto/db db:migrate` (`packages/db/src/cli/migrate.ts`). One correction to the AWS-era plans' assumption: **`migrate.ts` does not hard-refuse a `DATABASE_URL` fallback in non-dev** — it logs a `warn` and proceeds if `DATABASE_ADMIN_URL` is unset (verified by reading the current file, 2026-09-04). The old plan 09 claimed a hard refusal that does not exist in the code. This is not a blocker — the CD workflow (Pattern 6) simply must always set `DATABASE_ADMIN_URL` explicitly and should not rely on the script to catch a missing one; document this as a known soft-guard, not a hard gate, so nobody is surprised when a misconfigured secret produces a confusing permission error instead of a clean refusal.
- **Boot preflight dry-check (SC#4):** exactly the same five checks `07.5-02`'s CI job already proves locally (`assertNoRlsBypass`, `assertTenantLockInstalled`, `assertSetConfigRevoked`, plus the two prod-only checks `assertSystemRolesPresent`/`assertProdGuardrails` that only run when `NODE_ENV=production`) — this phase's job is to run them against the *real* VPS Postgres once, before traffic, and capture the transcript. No new preflight code is needed.

### Pattern 3: Backups that are actually restorable

**What:** Nightly `pg_dump` (custom format, `-Fc`) from a host cron job, compressed, uploaded to R2 via `rclone`, retained via an R2 Object Lifecycle Rule — not a hand-rolled retention script.

**Recommendation: `pg_dump`, not WAL-G, for this phase.** WAL-G is the more capable tool (continuous WAL archiving → RPO in minutes rather than up to 24h) and is genuinely R2-compatible (`[CITED: wal-g.readthedocs.io/STORAGES/]` — `AWS_ENDPOINT` + `AWS_S3_FORCE_PATH_STYLE=true` + `AWS_REGION` against any S3-compatible endpoint; the exact combination is not in WAL-G's own official-support matrix as an explicitly named provider, but it is the identical mechanism already proven working for MinIO in this repo's own dev environment, and multiple independent sources confirm the same pattern against R2 specifically — `MEDIUM confidence`, not `HIGH`, because no source is WAL-G's own changelog explicitly saying "R2 supported"). But WAL-G requires real new operational surface — `archive_mode=on`, a custom `archive_command` wired into the `postgres` container, WAL-G credentials, and a `delete retain` policy to reason about — for a benefit (tighter RPO) that does not matter yet at first-customer order volume. `pg_dump` is what the founder can stand up, test-restore, and trust *today*, which is the actual G-02 gate: a **tested** restore, not a theoretically-better RPO nobody has rehearsed.

**Where they land in R2:** a dedicated `resto-backups` R2 bucket (separate from the `menu-photos`/media bucket — different access pattern, different lifecycle, and a scoped API token here should never also be able to touch guest-facing media), object key shape `backups/resto-YYYYMMDD-HHMMSS.dump.gz`.

**Script (`infra/scripts/backup-nightly.sh`, illustrative shape):**
```bash
#!/usr/bin/env bash
set -euo pipefail
TS=$(date -u +%Y%m%d-%H%M%S)
DUMP="/tmp/resto-${TS}.dump"

docker exec resto-postgres pg_dump -U "$POSTGRES_ADMIN_USER" -Fc -d "$POSTGRES_DB" > "$DUMP"
gzip "$DUMP"
rclone copy "${DUMP}.gz" r2:resto-backups/backups/ --config /opt/resto/rclone.conf
rm -f "${DUMP}.gz"
```
Host crontab: `0 3 * * * /opt/resto/scripts/backup-nightly.sh >> /var/log/resto-backup.log 2>&1` — 03:00 UTC is overnight for the EU restaurant timezones this product targets, matching the low-traffic window rationale already used for `RESEND_FROM`/domain choices elsewhere in the codebase.

**Retention:** an R2 lifecycle rule on the `resto-backups` bucket's `backups/` prefix — expire after 14 days (`[CITED: developers.cloudflare.com/r2/buckets/object-lifecycles/]`, dashboard or API-configurable, no custom script). This gives roughly two weeks of nightly recovery points at negligible storage cost (a compressed `pg_dump` of an MVP-1-scale database is low tens of MB at most).

**What the restore drill proves (the deliverable, not a note):** a full, realistic disaster-recovery rehearsal, not just "does the file open":
1. `rclone copy r2:resto-backups/backups/<latest>.dump.gz .` — proves the *actual R2 round-trip*, not just that a local file is valid.
2. Spin up a throwaway `postgres:16-alpine` container (`docker run --rm -d --name resto-restore-drill …`), `pg_restore` the dump into it.
3. **Roles are not part of the dump** (`pg_dump` is database-scoped; roles are cluster-level, captured by `pg_dumpall --roles-only`, which this design deliberately does not use). The drill re-runs the *same committed provisioning CLIs* (`provisionAppRole`/`provisionAuthRole`, `pnpm db:migrate`) against the restored database — this is more realistic than trusting a raw role dump, because it is exactly what a genuine recovery (new VPS, fresh Postgres, restore data, re-provision roles, point the app at it) would actually do.
4. Verify: the drizzle migrations journal (`__drizzle_migrations`) matches the committed migration count; the three roles exist with correct `rolbypassrls`/`rolsuper` attributes; a sample tenant-scoped table is readable and returns the expected row shape.
5. Tear the scratch container down. Record the elapsed wall-clock time as the observed RTO.

**RPO/RTO to record (starting targets, to be replaced with the actually-observed numbers during the real drill):** RPO ≤ 24h (bounded by nightly cadence — tightenable to 6h for free by just changing the cron schedule, before ever reaching for WAL-G). RTO target < 1 hour for a manual-but-scripted recovery (not a fully automated failover — that is out of scope for a bootstrap-budget solo-founder deploy).

### Pattern 4: TLS and DNS

**The headline finding of this research: classic Cloudflare Pages custom domains do not support wildcard subdomains, and never have — as of 2026 this is still an open, unresolved feature request** (`[CITED]`, cross-referenced across Cloudflare's own community forum, including a thread titled "Wildcard subdomains for Pages in 2026?" still active). CONTEXT.md's prose names "Cloudflare Pages" for admin+qr-menu, but the app's own already-committed code requires exactly the wildcard hosts Pages cannot serve: `*.admin.resto.app` (per-tenant admin, D-21/D-40) and `*.menu.resto.app` (per-tenant qr-menu, already live in dev). A plan that provisions classic Pages projects here would work for the apex/demo case and then hard-block the moment a second tenant needs its own admin/menu subdomain — exactly the kind of trap this research exists to catch before it reaches a plan.

**The concrete, current (2026), Cloudflare-official fix: Cloudflare Workers with Static Assets** (`developers.cloudflare.com/workers/static-assets/`) — Cloudflare's own documented successor for exactly this gap (`developers.cloudflare.com/workers/static-assets/migration-guides/migrate-from-pages/`). A Worker's Route pattern natively supports a leading wildcard label (`*.menu.resto.app/*` is valid syntax, confirmed against the official Workers routing docs) and Worker Routes take precedence over anything else bound to the same hostname by pattern specificity. This is still "put the static bundle on Cloudflare's free edge" — the founder's underlying decision is honored; only the specific product name changes, and it changes because the originally-named product cannot do what the app already needs.

**`wrangler.jsonc` — qr-menu:**
```jsonc
{
  "name": "resto-qr-menu",
  "main": "worker/index.ts",
  "compatibility_date": "2026-09-01",
  "assets": {
    "directory": "./dist",
    "binding": "ASSETS",
    "not_found_handling": "single-page-application",
    "run_worker_first": ["/v1/*"]
  },
  "vars": { "API_ORIGIN": "https://api.resto.app" },
  "routes": [{ "pattern": "*.menu.resto.app/*", "zone_name": "resto.app" }]
}
```

**`wrangler.jsonc` — admin:**
```jsonc
{
  "name": "resto-admin",
  "main": "worker/index.ts",
  "compatibility_date": "2026-09-01",
  "assets": {
    "directory": "./dist",
    "binding": "ASSETS",
    "not_found_handling": "single-page-application",
    "run_worker_first": ["/v1/*", "/api/*"]
  },
  "vars": { "API_ORIGIN": "https://api.resto.app" },
  "routes": [
    { "pattern": "admin.resto.app/*", "zone_name": "resto.app" },
    { "pattern": "*.admin.resto.app/*", "zone_name": "resto.app" }
  ]
}
```
`[CITED: developers.cloudflare.com/workers/static-assets/binding/, developers.cloudflare.com/workers/configuration/routing/routes/]` — `run_worker_first` and the wildcard route pattern syntax are both directly confirmed against current official docs, fetched 2026-09-04.

**DNS records required** (one dummy proxied record per Worker-bound wildcard host — Cloudflare requires *some* DNS record to exist for a Worker Route to trigger, even though the Worker never actually contacts whatever IP the record points at):

| Host | Type | Target | Proxied | Serves |
|---|---|---|---|---|
| `api.resto.app` | A | VPS public IP | Yes (orange-cloud) | `api` container via Caddy |
| `resto.app` (apex) | A | VPS public IP | Yes | `website` container via Caddy |
| `*.resto.app` | CNAME | `resto.app` | Yes | `website` container via Caddy (covers every tenant slug **and** `order.resto.app`, since a one-label wildcard already matches it — no separate record needed) |
| `admin.resto.app` | A (dummy) | `192.0.2.1` or any placeholder | Yes | Worker Route (exact match wins over the generic `*.resto.app` wildcard) |
| `*.admin.resto.app` | A (dummy) | `192.0.2.1` | Yes | Worker Route |
| `*.menu.resto.app` | A (dummy) | `192.0.2.1` | Yes | Worker Route |

**TLS for the VPS-hosted surfaces (api, website):** Cloudflare set to **"Full (strict)"** SSL/TLS mode for the zone; Caddy on the VPS presents a **Cloudflare Origin CA certificate** (`[CITED: developers.cloudflare.com/ssl/origin-configuration/origin-ca/]` — dashboard: SSL/TLS → Origin Server → Create Certificate; issued in ~30 seconds, valid up to 15 years, trusted only by Cloudflare's edge — direct access to the VPS's raw IP correctly shows it as untrusted, which is expected and fine since nothing should ever reach the origin except through Cloudflare). One certificate with SANs `resto.app, *.resto.app, api.resto.app` covers both VPS-hosted hostnames. No Let's Encrypt, no `certbot`, no renewal cron.

**TLS for admin/qr-menu:** handled entirely by Cloudflare's edge for the Worker — there is no origin hop, so no origin certificate is needed for these two hosts at all.

**Caddyfile (illustrative shape):**
```
{
  admin off
}

api.resto.app {
  tls /etc/caddy/certs/origin.pem /etc/caddy/certs/origin-key.pem
  reverse_proxy api:3000
}

resto.app, *.resto.app {
  tls /etc/caddy/certs/origin.pem /etc/caddy/certs/origin-key.pem
  reverse_proxy website:3002
}
```

**Why the guest and operator surfaces must share a parent domain — the concrete lesson already paid for in this codebase:** `10.2-FINDINGS.md` (F-41/F-42, phase 10.2, 2026-08-22) found — via a real Chromium browser walkthrough, after 14 plans and a passing e2e suite all missed it — that the operator session cookie is silently dropped once admin is served from a genuinely different host than the API, because `AUTH_COOKIE_DOMAIN=.admin.resto.app` scopes the cookie strictly to that registrable subtree. The fix already shipped: `VITE_API_ORIGIN` was deleted outright (D-39) and admin now issues same-origin relative paths, exactly like qr-menu, relying on a same-origin proxy to reach the API without ever crossing a registrable-domain boundary the browser would refuse to carry the cookie across. **This is why the admin Worker above proxies `/v1/*`+`/api/*` rather than the old AWS-era plan's assumption of `VITE_API_ORIGIN` + CORS + credentials** — that assumption predates the fix and is stale. The proxy's `X-Forwarded-Host` header (Pitfall #3) is what lets the API still resolve the correct tenant despite the request now genuinely terminating at `api.resto.app` behind the scenes. The same rule will bind guest sign-in if/when it ships (`.planning/todos/pending/guest-sign-in-with-google.md`, still pending) — whatever host issues that cookie must share a registrable parent with whatever host the guest's browser is on, exactly as it does today for the operator.

**The four production hostnames (answers SC#5's smoke target directly):**
1. `api.resto.app` — API
2. `resto.app` / `*.resto.app` (marketing apex, tenant storefronts, `order.resto.app` guest order-status) — website
3. `admin.resto.app` / `*.admin.resto.app` — admin (Worker)
4. `*.menu.resto.app` — qr-menu (Worker)

### Pattern 5: Secrets on the box

**What:** Two `.env` files on the VPS (`/opt/resto/.env.api`, `/opt/resto/.env.website`), `chmod 600`, owned by the deploy user, referenced by `env_file:` in `docker-compose.prod.yml` — never `COPY`'d into a Docker build context, never committed.

**How they're delivered without baking them into an image:** the CD workflow's SSH step (Pattern 6) does **not** re-write these files on every deploy — they are seeded once, by hand, during initial VPS setup (a `checkpoint:human-action` task in the plan, same shape as the old AWS plan's "create the RDS instance by hand" task), and only touched again when a secret actually rotates. This is the correct application of "secrets never in the image": the *image* is genuinely secret-free (built once, deployed to any environment), and the *runtime* env is supplied entirely out-of-band by the file already sitting on the box. Contrast with the handful of **build-time, non-secret** values (`NEXT_PUBLIC_API_ORIGIN` for the website Dockerfile) — those remain `ARG`s baked at build time exactly as `07.5-11` already implemented, because they are genuinely public (shipped to every browser anyway) and the repo's own `apps/CLAUDE.md` rule ("`NEXT_PUBLIC_*` must not have a production fallback") is about correctness, not secrecy.

**Rotation:** SSH in, edit the relevant `.env.*` file, `docker compose up -d --no-deps <service>` to pick it up (the container reads `env_file:` at creation, not continuously — a restart is required and is the correct, expected mechanism). No automation is warranted for this at MVP-1 scale; document the manual procedure in `docs/runbooks/secrets-on-the-box.md`.

**Secret inventory (api):** `DATABASE_URL`, `DATABASE_DIRECT_URL` (per D-05', may be identical strings), `DATABASE_ADMIN_URL` (used only by the one-off migration container, not the long-running `api` service — do not put it in `.env.api` at all; inject it only for the migration step), `BETTER_AUTH_DATABASE_URL`, `BETTER_AUTH_SECRET`, `AUDIT_ERASURE_SALT`, `INTERNAL_API_TOKEN`, `NATS_URL`/`NATS_USERNAME`/`NATS_PASSWORD`, `S3_*` (R2), `SENTRY_DSN`, `RESEND_API_KEY`, `STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET`/`STRIPE_CONNECT_CLIENT_ID` (see Pitfall #10 — these are hard-required for boot, not optional in this phase even though Stripe is nominally "Phase 8"), `TRUST_PROXY`, `CORS_ALLOWED_ORIGINS`, `AUTH_COOKIE_DOMAIN=.admin.resto.app`, `ADMIN_WEB_URL=https://admin.resto.app`, `ADMIN_WEB_ORIGIN_WILDCARD=https://*.admin.resto.app`, `WEBSITE_PUBLIC_URL=https://order.resto.app`, `PUBLIC_APEX_DOMAIN=resto.app`.

**Secret inventory (website):** `NEXT_PUBLIC_API_ORIGIN` (build-time ARG, not runtime secret), `WEBSITE_URL`.

**CI-time-only secrets** (GitHub Actions repo/environment secrets, never touch the VPS filesystem): `SSH_PRIVATE_KEY` (deploy-only key, restricted `authorized_keys` command if feasible), `SSH_HOST`, `SSH_USER`, `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `DATABASE_ADMIN_URL` (for the gated migration step — passed over the already-encrypted SSH session, not written to disk on the VPS as a standing file).

### Pattern 6: Deployment on merge

**What:** `.github/workflows/deploy.yml`, triggered via `workflow_run` on `ci.yml`'s completion (gates on green CI without duplicating its matrix), gated on `github.event.workflow_run.conclusion == 'success'` and the branch being `main`.

**Steps, in order:**
1. Build `api` and `website` Docker images, tag with `${{ github.sha }}`, push to `ghcr.io` (`docker/build-push-action`). Website build passes `--build-arg NEXT_PUBLIC_API_ORIGIN=https://api.resto.app` — a real value, never the Dockerfile's own placeholder default, matching the already-closed G-05 principle.
2. Build the admin and qr-menu Vite SPA bundles (`pnpm --filter admin build`, `pnpm --filter qr-menu build`).
3. **Gated pre-rollout migration** — this is the one step that genuinely differs from the AWS-era assumption: **Postgres has no public endpoint** in this topology (Pattern 1, deliberately), so the migration cannot run directly from the GitHub Actions runner the way it could against a (potentially publicly-reachable) RDS endpoint. It must run *from the VPS itself*, over the same SSH connection used for the deploy: `ssh <vps> "cd /opt/resto && DATABASE_ADMIN_URL='...' docker compose -f docker-compose.prod.yml run --rm api pnpm --filter @resto/db db:migrate"`. If this step fails, the job stops — no new image is ever recreated, the previous version keeps serving. `assertTenantLockInstalled` remains the boot-time backstop if a rollout ever races ahead of a migration regardless.
4. SSH deploy: `docker compose pull api website && docker compose up -d --no-deps --pull always api website` (recreates only these two services; `postgres`/`nats`/`caddy` untouched, their volumes never at risk).
5. `wrangler deploy` for admin and qr-menu (`cloudflare/wrangler-action`), each picking up its already-built `dist/` directory.
6. Poll `https://api.resto.app/healthz` until 200 (with a timeout) — fail the job on timeout.

**G-06 rollback (app-only, DB never rolled back):** capture the prior SHA (the tag currently running); to roll back, `ssh <vps> "cd /opt/resto && API_IMAGE_TAG=<prior-sha> docker compose up -d --no-deps api"` (and the equivalent for `website`) — Docker will use the already-locally-cached prior image if it's still present (fast) or re-pull it from GHCR (still fast — small alpine-based images). Migrations are forward-only (hard deletes forbidden by role grant, per the repo's own existing constraint) — expand/contract is the only rollback strategy that makes sense here, unchanged from the AWS-era plan's own correct reasoning, just re-pointed at a Compose command instead of an ECS one. Website's rollback needs no rebuild — the prior image already has the correct `NEXT_PUBLIC_API_ORIGIN` baked in from when it was built.

**What differs from the old (AWS) `deploy.yml` shape besides the target:** no OIDC role assumption (there is no AWS to assume a role into — the credential model is an SSH key instead), no ECR (GHCR), and the migration step's *location* (must run on the VPS, not the runner) is the one genuinely new constraint this stack introduces that the AWS-era plan did not have to solve.

### Pattern 7: The go-live smoke

**What:** the same shape the AWS-era plan 10 already designed — an external, over-HTTPS, four-surface check plus the ported ADM-00 admin Playwright smoke — retargeted at the real hostnames from Pattern 4, reusing `PRE-DEPLOY-VERIFY.md`'s already-verified NATS/outbox-decoupling proofs and the qr-menu same-origin requirement it documented (now additionally proven for admin too, per Pitfall #4/Pattern 4).

1. `GET https://api.resto.app/healthz` → 200.
2. `GET` a tenant host on the website (`<slug>.resto.app` or `order.resto.app`) → 200, body contains a real seeded menu item — proves an actual end-to-end render, not just a shell.
3. `GET https://<slug>.menu.resto.app/` → 200 (SPA shell) **and** `GET https://<slug>.menu.resto.app/v1/menu` → 200 same-origin — proves the qr-menu Worker's proxy AND its tenant-keyed cache (Pitfall #2) are both correct: request the same URL twice, confirm the second response includes whatever cache-hit signal the Worker is configured to surface, and — critically — request a *second, different* tenant's `/v1/menu` and confirm it does **not** return the first tenant's content (this is the one new assertion this research adds beyond the old plan's shape, directly targeting the cache-collision pitfall).
4. `GET https://admin.resto.app/login` → 200 (static shell) **and** confirm the ported ADM-00 Playwright smoke, run against the live host, can complete an operator sign-in — this exercises the admin Worker's `/api/auth/*` proxy end-to-end, which is the one path in this whole stack that both crosses the Worker proxy *and* depends on cookie-domain scoping being correct (Pattern 4's F-41 lesson) — the single highest-value assertion in the whole smoke.
5. Confirm `STRIPE_WEBHOOK_SECRET`-signed test webhook reaches the API over the now-public `api.resto.app` URL (Phase 8's own webhook tests already exist; this smoke just confirms the URL is real and reachable — see Pitfall #10 on why Stripe credentials must already be live at this point, not deferred).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| Same-origin API proxy for a wildcard-hosted SPA | A custom Node/nginx reverse-proxy container | Cloudflare Worker + Static Assets, `run_worker_first` | Already paying for Cloudflare; zero extra compute; officially documented pattern; solves the wildcard-hosting gap and the proxy in one deployable |
| TLS certificate issuance/renewal for the VPS origin | `certbot` + a renewal cron + failure alerting | Cloudflare Origin CA certificate (15-year validity) | Zero renewal surface for the life of the certificate; purpose-built by Cloudflare for exactly this "origin behind our proxy" scenario |
| Backup retention/rotation | A "delete files older than N days" script against R2 | R2 Object Lifecycle Rules | Native, dashboard/API-configurable, cannot be broken by a script bug |
| Edge DDoS/flood protection | `iptables` rate-limiting on the VPS | Cloudflare's always-on L3/4/7 protection (free tier, active on every proxied zone) | The VPS never even sees a volumetric attack when the firewall also restricts inbound to Cloudflare's IP ranges (Pitfall #5) |
| Uploading compressed dumps to an S3-compatible endpoint | Hand-rolled multipart upload + SigV4 signing | `rclone` (officially R2-documented) | Battle-tested, handles multipart/retries/resume; zero reason to reimplement S3 signing by hand |
| Postgres role/schema provisioning for prod | A brand-new "prod setup" script | The already-committed `provisionAppRole`/`provisionAuthRole`/`pnpm db:migrate` CLIs | Identical code path CI already exercises daily; a new script would be an untested second implementation of the same logic |

**Key insight:** almost nothing in this phase is genuinely new engineering — the domain model (hostnames, cookie scoping, RLS roles, outbox leader election, edge-cache headers) was already built and proven correct by earlier phases. This phase's actual job is *wiring*, and every hand-rolled temptation in the table above is a case of reimplementing something Cloudflare or the existing repo already does correctly.

## Common Pitfalls

### Pitfall 1: Assuming "Cloudflare Pages" means the classic product

**What goes wrong:** A plan provisions classic Cloudflare Pages projects for admin and qr-menu with a single custom domain each, works fine in testing against the apex host, then silently cannot add a second tenant's subdomain.
**Why it happens:** CONTEXT.md's locked-decision prose names "Cloudflare Pages" — accurate as a *product family* decision at the time it was written, stale as a *specific product* now that the app requires wildcard hosts.
**How to avoid:** Use Cloudflare Workers with Static Assets (Pattern 4) — same cost, same "static edge hosting" category, supports the wildcard the app needs.
**Warning signs:** Any plan step that says "add a custom domain in the Pages dashboard" for `*.admin.resto.app` or `*.menu.resto.app` specifically (rather than a single exact host) will hit a dashboard error/limitation immediately — catch it at plan-review time, not execution time.

### Pitfall 2: A naive reverse-proxy Worker collapses the per-tenant cache key

**What goes wrong:** The qr-menu Worker's `fetch('https://api.resto.app' + pathname)` targets the identical URL for every tenant's `/v1/menu` request. If Cloudflare's default host+path cache rule ends up applying to that *inner* fetch (targeting the `api.resto.app` zone), every tenant collides on one cache entry — a guest could be served another restaurant's menu.
**Why it happens:** The existing `docs/runbooks/menu-edge-caching.md` design assumed the cache key would naturally include the tenant (because in the AWS-era design, the tenant subdomain *was* the request's actual host all the way to the origin). Inserting a Worker that rewrites the URL breaks that assumption unless the Worker explicitly re-keys the cache.
**How to avoid:** Use the Workers Cache API explicitly, keyed on the *original* incoming request URL (which still carries the tenant subdomain), not the rewritten outbound one — full working pattern in Pattern 4/the qr-menu Worker script above. Skip caching entirely for non-`GET` and for any response carrying `Set-Cookie` (the Cache API already refuses to cache `Set-Cookie` responses by default, but the code should not depend on that alone for the admin proxy, which should not attempt caching at all).
**Warning signs:** During the go-live smoke, request `/v1/menu` for two different seeded tenants back-to-back and diff the bodies — this is exactly why Pattern 7 adds that assertion explicitly.

### Pitfall 3: The proxy loses the tenant `Host` header

**What goes wrong:** A Worker's `fetch()` to `https://api.resto.app/...` naturally sets `Host: api.resto.app` on the outbound request — the original `<slug>.menu.resto.app` is gone by the time the API sees it. `apps/api/src/shared/effective-host.ts`'s `effectiveHost()` then resolves the tenant from the literal `Host` header (`api.resto.app`, not a tenant), and every guest request silently 404s or resolves to no tenant.
**Why it happens:** This is standard `fetch()` behavior, not a bug — the new request genuinely is addressed to `api.resto.app`.
**How to avoid:** The Worker must explicitly set `X-Forwarded-Host: <original hostname>` (and `X-Forwarded-Proto: https`) on the outbound request, and the API's `TRUST_PROXY` must be configured to honor it (already-existing, already-tested code path — `effectiveHost()` reads `x-forwarded-host` exactly when `trustProxy` is true).
**Warning signs:** Every qr-menu/admin request 404s or resolves as tenant-less in the go-live smoke while `api.resto.app/healthz` works fine directly — this signature specifically points at a missing `X-Forwarded-Host`.

### Pitfall 4: Reviving `VITE_API_ORIGIN`/cross-origin CORS for admin

**What goes wrong:** A plan written from the old AWS-era research's assumptions wires admin to talk cross-origin to the API via `VITE_API_ORIGIN` + CORS + `credentials: 'include'`. This variable was **deleted outright** in phase 10.2 (D-39) after F-41 found the cookie transport silently broken exactly this way.
**Why it happens:** The AWS-era plan predates that fix by two months; nothing in the CONTEXT.md decision bodies mentions it (10.2 happened well after 07.5's context was last edited).
**How to avoid:** Admin gets the *same* same-origin Worker proxy treatment as qr-menu (Pattern 4) — no `VITE_API_ORIGIN`, no CORS credentials flow for admin's own auth. Grep for `VITE_API_ORIGIN` in `apps/admin/` before writing any admin-hosting plan — it should return nothing (already true as of this research).
**Warning signs:** Any plan step referencing `VITE_API_ORIGIN` as an admin build-time env var is working from stale assumptions.

### Pitfall 5: The VPS's raw public IP bypasses Cloudflare entirely

**What goes wrong:** Anyone who discovers the VPS's actual IP address (trivial — reverse DNS, historical DNS records, Shodan) can hit Caddy directly, bypassing Cloudflare's WAF, cache, and rate limiting, and — more subtly — can forge an `X-Forwarded-Host` header claiming to be `admin.resto.app`, which the API would trust if `TRUST_PROXY` is configured too permissively.
**Why it happens:** Nothing about DNS or TLS prevents direct-IP access by default; Cloudflare's protections only apply to traffic that actually flows through its edge.
**How to avoid:** `ufw` on the VPS restricts inbound 80/443 to Cloudflare's published IP ranges (`https://www.cloudflare.com/ips-v4`, `/ips-v6`) in addition to the Origin CA cert (which stops *passive* eavesdropping/impersonation but not a direct connection attempt). Optionally layer Cloudflare's "Authenticated Origin Pulls" (mTLS) for a stronger guarantee — noted as a nice-to-have, not required for this phase's scope.
**Warning signs:** none observable from outside — this is a preventive hardening step, not something the go-live smoke can detect by itself.

### Pitfall 6: Copying the dev compose file's port mappings into prod

**What goes wrong:** `docker-compose.dev.yml` publishes `5432:5432` and `4222:4222`/`8222:8222` for local tooling convenience. Copying that shape into `docker-compose.prod.yml` puts a superuser-reachable Postgres and an (initially unauthenticated, if the auth flags are also missed) NATS server directly on the public internet.
**Why it happens:** Compose file reuse is exactly the right instinct for everything *except* `ports:` — it's the one section that must diverge completely.
**How to avoid:** Explicit review checklist item: `docker-compose.prod.yml` must have zero `ports:` entries outside the `caddy` service.
**Warning signs:** `docker compose config` on the prod file, grep for `ports:` — the only match should be under `caddy`.

### Pitfall 7: `docker compose down -v` in any automated path

**What goes wrong:** `-v` destroys the named volumes — `postgres-data` included. A single misplaced `-v` in a deploy script is a full data-loss incident with no warning.
**Why it happens:** `docker compose down` (safe) and `docker compose down -v` (destructive) look nearly identical and are easy to conflate, especially when copy-pasting from a "reset my dev environment" habit (`pnpm dev:reset` in this repo's own dev workflow *does* use `-v`, by design, for dev).
**How to avoid:** The CD pipeline never calls `docker compose down` at all (Pattern 1/6 use targeted `up -d --no-deps <service>` instead); grep the committed workflow files for `-v` near `docker compose` as a review gate.
**Warning signs:** any `docker compose down` appearing anywhere in `.github/workflows/deploy.yml` or `infra/scripts/` should be treated as a red flag during plan review, `-v` or not.

### Pitfall 8: Trusting `migrate.ts`'s fallback as a hard gate

**What goes wrong:** A plan assumes (as the AWS-era plan 09 did) that `migrate.ts` refuses to run without `DATABASE_ADMIN_URL` in non-dev. It does not — it warns and falls back to `DATABASE_URL`. If the CD workflow's `DATABASE_ADMIN_URL` secret is ever missing/misnamed, migrations silently attempt to run under the lower-privileged app role instead of failing closed, and fail with a confusing permission error rather than a clear "you forgot the admin URL" message.
**Why it happens:** The current file (verified 2026-09-04) genuinely only warns; this may have been true at an earlier point in the codebase's history or may simply have been an inaccurate assumption in the original plan.
**How to avoid:** The CD workflow (Pattern 6) must always pass `DATABASE_ADMIN_URL` explicitly and treat its absence as a workflow-level configuration error (fail the job before even attempting the SSH step) rather than relying on the script itself to refuse.
**Warning signs:** a migration step that "succeeds" suspiciously fast, or fails with a Postgres permission-denied error rather than a clean "DATABASE_ADMIN_URL is required" log line.

### Pitfall 9: Website's SSR calls hairpin through the public internet even on the same box

**What goes wrong (not a bug, a documented tradeoff):** `NEXT_PUBLIC_API_ORIGIN` is baked at build time to the public `https://api.resto.app` and used for both server-side (SSR) and client-side fetches (`apps/website/lib/env.ts`/`checkout-api.ts`). Even though `website` and `api` run on the *same* VPS in the *same* Compose network, website's SSR calls leave the box, round-trip through Cloudflare's edge, and come back — adding real (if small) latency to every server-rendered page, purely because one env var serves both contexts.
**Why it happens:** Splitting an "internal" SSR-only origin (`http://api:3000`, the Compose service DNS name) from the "public" client-side origin would require a second env var and a code change to `checkout-api.ts`/wherever SSR fetches happen — out of scope for this deploy phase, which should not touch application code.
**How to avoid (or rather, accept for now):** Ship as-is for the initial go-live — it is correct, just not maximally efficient. Document as a known, deliberate future optimization (an `API_INTERNAL_ORIGIN` env var for SSR-only calls) rather than something this phase's plans need to fix.
**Warning signs:** none that block go-live; revisit only if SSR latency becomes a measured problem.

### Pitfall 10: `assertProdGuardrails` requires real Stripe/Resend credentials to boot at all

**What goes wrong:** `apps/api/src/config/prod-guardrails.ts` refuses to boot in `NODE_ENV=production`/`staging` without a real (non-placeholder) `STRIPE_SECRET_KEY` and `RESEND_API_KEY` — this is unconditional, independent of whether Phase 8 (Payments) is "in scope" for this deploy phase's stated goal. Since Phase 8/8.1 are already complete in this codebase (per `.planning/ROADMAP.md`, both marked "Complete" 2026-06-27/28), this is not a surprise gap to fill — it *is* already-shipped code that this deploy phase must simply satisfy — but a plan that treats "Stripe is Phase 8, not my problem" literally will find the api container refuses to start at all, at the very first go-live smoke attempt, with no partial-success state to debug from.
**Why it happens:** `assertProdGuardrails` was hardened after this deploy phase's CONTEXT.md was first written (2026-06-21/26) but before this research (2026-09-04) — the phase boundary language predates code that now cuts across it.
**How to avoid:** Gather real Stripe (test-mode keys are acceptable for an initial go-live — `assertProdGuardrails` only rejects the *documented placeholder literal*, not test-mode keys generally) and Resend credentials as part of the "founder must provide" checklist (below), before plan 08/the go-live smoke, not after.
**Warning signs:** the `api` container exits immediately on boot with a `ProdGuardrailsError` listing `STRIPE_SECRET_KEY`/`RESEND_API_KEY` — this is the exact, unambiguous failure signature; do not spend time debugging Docker networking or Postgres connectivity first.

## Code Examples

### qr-menu Worker — same-origin proxy with tenant-correct edge caching

```typescript
// apps/qr-menu/worker/index.ts
// Source pattern: developers.cloudflare.com/workers/runtime-apis/cache/
//                 developers.cloudflare.com/workers/static-assets/binding/
export interface Env {
  ASSETS: Fetcher;
  API_ORIGIN: string; // https://api.resto.app
}

const isCacheableMenuPath = (pathname: string): boolean =>
  pathname === '/v1/menu' ||
  pathname === '/v1/menu/availability' ||
  pathname.startsWith('/v1/menu/items/');

export default {
  async fetch(request: Request, env: Env, ctx: ExecutionContext): Promise<Response> {
    const url = new URL(request.url);
    if (!url.pathname.startsWith('/v1/')) {
      return env.ASSETS.fetch(request);
    }

    const cache = caches.default;
    const cacheable = request.method === 'GET' && isCacheableMenuPath(url.pathname);
    // Cache key uses the ORIGINAL request's URL — carries the tenant subdomain.
    // Do NOT key on the rewritten origin URL (Pitfall #2).
    const cacheKey = new Request(url.toString(), request);

    if (cacheable) {
      const cached = await cache.match(cacheKey);
      if (cached) return cached;
    }

    const originUrl = new URL(url.pathname + url.search, env.API_ORIGIN);
    const originRequest = new Request(originUrl, request);
    originRequest.headers.set('X-Forwarded-Host', url.hostname);
    originRequest.headers.set('X-Forwarded-Proto', 'https');

    const originResponse = await fetch(originRequest);

    if (cacheable && originResponse.ok && !originResponse.headers.has('Set-Cookie')) {
      ctx.waitUntil(cache.put(cacheKey, originResponse.clone()));
    }

    return originResponse;
  },
};
```

### admin Worker — same-origin proxy, no caching

```typescript
// apps/admin/worker/index.ts
export interface Env {
  ASSETS: Fetcher;
  API_ORIGIN: string; // https://api.resto.app
}

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const url = new URL(request.url);

      return env.ASSETS.fetch(request);
    }

    const originUrl = new URL(url.pathname + url.search, env.API_ORIGIN);

    return fetch(originRequest);
  },
};
```

## Open Questions

1. **Exact VPS size: CX32 vs. CX22**
   - What we know: CX32 (4 vCPU/8 GB/80 GB, ~€6.80/mo) comfortably fits under the founder's stated ~€8/mo target and leaves headroom for 5 concurrent containers (postgres, nats, api, website, caddy). CX22 (2 vCPU/4 GB, ~€3.79-4.59/mo) is cheaper but tighter, especially once Postgres's own working-set and two Node processes (NestJS + Next.js) are all resident simultaneously.
   - What's unclear: actual MVP-1 traffic/memory profile is unmeasured (no production data exists yet).
   - Recommendation: start on CX32 — the price difference (~€2-3/mo) is immaterial next to the cost of a memory-pressure incident during the very first go-live smoke; Hetzner allows live resizing if it later proves oversized.

2. **Backup cadence: nightly vs. more frequent**
   - What we know: a `pg_dump` at MVP-1 scale is small and fast; running it every 6h instead of nightly costs nothing extra in infra terms and roughly quarters the RPO.
   - What's unclear: whether the founder wants to accept ≤24h RPO for the initial go-live or tighten it immediately.
   - Recommendation: ship nightly first (simplest to reason about and rehearse once), document the cadence as a one-line cron-schedule change if tightened later — this is genuinely Claude's Discretion per CONTEXT.md, not something requiring a hard answer before planning.

3. **Whether to add `Authenticated Origin Pulls` (mTLS) on top of the IP-range firewall**
   - What we know: Cloudflare supports mTLS between its edge and the origin as an additional hardening layer beyond IP allowlisting.
   - What's unclear: whether this is worth the added Caddy config complexity at MVP-1 stage, versus IP-range restriction alone.
   - Recommendation: skip for the initial go-live (IP-range restriction + Origin CA cert is already a strong posture matching D-03's "lowest ops" bias); revisit if a security review flags it later.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---|---|---|
| V2 Authentication | Indirect | Unaffected by hosting — Better Auth's flows are unchanged; only the *transport* (same-origin proxy) changes |
| V3 Session Management | Yes | `AUTH_COOKIE_DOMAIN=.admin.resto.app` cookie scoping (already Zod-enforced) must be preserved exactly through the new Worker proxy layer — Pitfall #3/#4 |
| V4 Access Control | Yes | Postgres 3-role RLS model (`resto_app` NOBYPASSRLS + FORCE RLS) is unchanged by self-hosting; self-managed superuser access (the `POSTGRES_USER` admin credential) is a new *operational* privilege boundary to guard (never used at runtime, only for migrations/provisioning) |
| V5 Input Validation | No | Unaffected — no new HTTP-facing input parsing is introduced by this phase (the Worker proxies are pure pass-through) |
| V6 Cryptography | Yes | TLS via Cloudflare Origin CA cert (never hand-rolled); `BETTER_AUTH_SECRET`/`AUDIT_ERASURE_SALT` generation/rotation procedure documented in Pattern 5, not changed in mechanism |
| V9 Communications | Yes | Two TLS hops (browser↔Cloudflare, Cloudflare↔origin) both enforced "Full (strict)"; internal Compose-network traffic (api↔postgres, api↔nats) is unencrypted but not internet-reachable (no published ports) — an accepted, standard tradeoff for a single-box topology |
| V12 Files and Resources | Yes | Backup integrity — the restore drill (Pattern 3) is the concrete V12 control; R2 bucket access is scoped-token, not account-wide |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---|---|---|
| VPS raw-IP origin bypass | Spoofing / Tampering | `ufw` restricted to Cloudflare's published IP ranges + Origin CA cert (Pitfall #5) |
| Postgres/NATS directly internet-reachable | Information Disclosure | No `ports:` published outside `caddy` in `docker-compose.prod.yml` (Pitfall #6) |
| Secrets baked into a Docker image or committed | Information Disclosure | `.env` files on the VPS filesystem only, `env_file:` reference, never `COPY`'d into a build stage (Pattern 5) |
| Cross-tenant cache poisoning via the reverse-proxy Worker | Tampering / Information Disclosure | Tenant-keyed Cache API usage, not host+path defaults (Pitfall #2) |
| Forged `X-Forwarded-Host` from a client that reached the origin directly | Spoofing | Same fix as the IP-bypass mitigation above — if the origin is genuinely unreachable except via Cloudflare/the Worker, a forged header from an arbitrary client never arrives |
| R2 backup bucket over-scoped token | Elevation of Privilege | A dedicated `resto-backups` R2 API token, scoped to that bucket only, distinct from the `menu-photos` media token (Pattern 3) |
| Automated `docker compose down -v` data loss | Denial of Service (self-inflicted) | No `-v` in any script/CD path; targeted `up -d --no-deps <service>` for all automated updates (Pitfall #7) |
| Deploy-time SSH key compromise | Elevation of Privilege | Dedicated deploy-only key (not a founder's personal key), stored only as a GitHub Actions secret, restricted `authorized_keys` command where feasible |
