## Summary

**Revised 2026-09-05 for the single-apex URL scheme.** The earlier summary described a design in
which two SPAs, hosted on Cloudflare Workers, reverse-proxied `/v1/*` to `api.<apex>` because their
own hostnames had no origin. That design is gone. The founder's decision to collapse to one apex —
`<apex>`, `<apex>/admin`, `<slug>.<apex>`, `<slug>.<apex>/qr`, `api.<apex>` — takes the SPA surfaces
off Worker-only hostnames and puts them on hostnames Caddy already serves. **The consequence is
subtraction, not addition:** same-origin becomes a Caddy routing rule instead of a proxy, and the
tenant-keyed edge cache becomes Cloudflare's default behaviour instead of a hand-rolled Cache API
entry. Roughly 250 lines of Worker source and 440 lines of Worker tests, committed three days ago,
are deleted; three of the defects the four review rounds raised against the edge-cache subsystem
stop existing rather than getting another fix.

The one genuinely new piece of work is **admin tenancy**, and it is smaller than it sounds. The
tenant does not move from the host to the path — it leaves the URL entirely, and the Better Auth
session's `activeOrganizationId` becomes the sole selector. Server-side that is mostly a removal:
`TenantContextMiddleware` has resolved the admin's tenant from the `x-tenant-id` header since
RES-181, with the host as a fallback that this change deletes. `AuthGuard` already cross-checks the
principal's tenant against the bound tenant, and needs one clause dropped so that "must not
disagree" becomes "must agree" — the two-line hardening in Pattern 4b. Client-side it is one deleted
module, one router `basepath`, six call sites, and a single `switchTenant()` helper that is the only
place allowed to POST the switch, enforced by the same `no-restricted-syntax` mechanism the repo
already uses for `runInTenantContext` and `withoutTenant`.

Two things in this revision are corrections to already-committed code rather than new design.
`cf: { cacheTtl: 0 }` in both Workers is documented as *forcing* Cache-Everything with an
immediately-expired entry, not opting out — and combined with a non-tenant-scoped ETag it is a
plausible cross-tenant leak path (Pitfall #2). And Caddy, under the committed
`trusted_proxies static 0.0.0.0/0 ::/0`, passes a **client-supplied** `X-Forwarded-Host` through
verbatim to an API that trusts it as a tenant selector (Pitfall #11, measured). The single-apex
scheme makes the second one cheap to close — nothing upstream needs to set that header any more, so
Caddy can pin it — which is a security improvement the scheme buys, not a cost it imposes.

Everything below the URL layer is unchanged from the 2026-09-04 research: one Hetzner CX32 running
Compose (`postgres` + `nats` + `api` + `website` + `caddy` with a 15-year Origin CA certificate),
nightly `pg_dump` → R2 via `rclone` with a tested restore drill, and a GitHub Actions `deploy.yml`
that builds to GHCR, runs a gated migration over SSH, recreates two services, and deploys two
static asset bundles.

**Primary recommendation:** one Cloudflare zone on `<apex>`; Caddy owns `/v1/*` and `/api/*` on
`<apex>` and `*.<apex>` with `X-Forwarded-Host` pinned to `{host}`; two assets-only Workers on
`<apex>/admin*` and `*.<apex>/qr*` built into `dist/admin/` and `dist/qr/` subdirectories; one Cache
Rule on `/v1/menu*`; the admin's tenant read from `activeOrganizationId` alone with a positive
membership check; the session cookie host-only on `<apex>`; and the admin path-tenancy change
executed as its own small phase **before** deploy plans 08-10.

Rewritten for the single-apex scheme. The load-bearing change: **only two hostnames have an origin
behind them, and both of them are Caddy** — so the two SPAs stop being reverse proxies and go back
to being static bundles.

|------------|-------------|----------------|-----------|

### Pattern 1: `docker-compose.prod.yml` — what differs from the dev compose

**What:** A production sibling of `infra/docker/docker-compose.dev.yml`, reusing its shape (named volumes, healthchecks, `condition: service_healthy` dependency ordering) but diverging on every point that matters for running on a public box.

**Diffs from `docker-compose.dev.yml` (concrete, not general Compose advice):**

1. **No `ports:` on `postgres` or `nats` at all.** Dev maps `5432:5432` and `4222:4222`/`8222:8222` to the host for local tooling access; prod must drop every one of these — the only two things listening on the VPS's public interface are `caddy` (80/443). Anything else reachable from the internet is a direct violation of "self-managed Postgres = superuser" being safe (see Pitfall #6).
2. **Two new services, `api` and `website`**, pulling pre-built images from `ghcr.io/<org>/resto-api:${API_IMAGE_TAG}` / `ghcr.io/<org>/resto-website:${WEBSITE_IMAGE_TAG}` (immutable, commit-SHA-tagged) rather than `image: postgres:16-alpine` style upstream pulls. Dev has no equivalent — dev runs `apps/api`/`apps/website` via `pnpm dev`, not Docker.
3. **A new `caddy` service** terminating TLS with the Cloudflare Origin CA cert and reverse-proxying by `Host` header — dev has no TLS layer at all (plain `http://localhost:*`).
4. **Drop `minio`, `mailhog`, `jaeger`.** MinIO → R2 (external); MailHog → Resend (external, already required by `assertProdGuardrails`); Jaeger → not run in this phase (`OTEL_DISABLED=true` is an acceptable initial choice — Sentry already covers G-04's error-tracking requirement; a hosted OTLP endpoint can be added later without touching the compose shape).
5. **`restart: unless-stopped` on every service** (dev already does this for postgres/nats/mailhog/jaeger but not minio — prod should be uniform: a crash-looping container should keep trying, not sit dead, and Sentry/Caddy's own logs surface the loop for the founder to notice).
6. **`env_file:` per app service** (`api` reads `.env.api`, `website` reads `.env.website`) rather than the inline `environment:` blocks dev uses for infra services — this is what makes "secrets never in the image" concrete: the files live on the VPS filesystem (`chmod 600`), not in the compose file, not in git (Pattern 5).
7. **NATS gets `--user`/`--pass` flags** (or a mounted config file) for the first time — dev's NATS runs with no auth at all, acceptable only because it's not internet-reachable in dev either way. `[CITED: docs.nats.io/running-a-nats-service/introduction/flags]` — `nats-server --user <NATS_USERNAME> --pass <NATS_PASSWORD> --jetstream --store_dir=/data --http_port=8222`.

**How Postgres data survives a `docker compose down`:** The named volume `postgres-data` (declared once at the bottom of the compose file, exactly like dev) is *not* removed by a plain `docker compose down` — only `docker compose down -v` (or an explicit `docker volume rm`) destroys it. **The CD pipeline (Pattern 6) must never issue a blanket `docker compose down` at all** — service updates use `docker compose up -d --no-deps --pull always <service>` to recreate only the changed service(s), leaving `postgres`/`nats`/`caddy` untouched and their volumes never at risk from an automated step. `docker compose down` (without `-v`) is reserved for rare manual maintenance; `-v` must never appear in any script, cron job, or CD step — this is worth a one-line comment directly in the compose file given how easy the two are to conflate.

**Healthchecks:** `postgres` and `nats` keep the exact healthcheck commands already in `docker-compose.dev.yml` (`pg_isready`, `wget … /healthz`). `api` already ships its own `HEALTHCHECK` in `apps/api/Dockerfile` (`wget --quiet --spider http://localhost:3000/healthz`) — no compose-level override needed. `website` likewise (`apps/website/Dockerfile`, hits `/`). `caddy` needs no explicit healthcheck (Docker's own "is the process alive" is sufficient for a stateless proxy; add one later only if a real incident calls for it).

**Restart policy summary:** `unless-stopped` uniformly. This is a single-VPS, single-replica-per-service topology by design — `apps/api/src/shared/security.ts`'s in-process `identityBuckets` rate-limit store is explicitly documented (`.planning/codebase/CONCERNS.md`) as assuming exactly this topology ("no horizontal scale-out planned before a paying customer"). Do not run more than one `api` replica in this compose file without first addressing that in-memory state.

### Pattern 2: Postgres on the box

**What:** PostgreSQL 16 (`postgres:16-alpine`, matching dev) runs as a `postgres` service in the compose stack. Because it is self-managed, the connecting superuser (`POSTGRES_USER`/`POSTGRES_PASSWORD` set at container creation) is a *true* PostgreSQL `SUPERUSER` — not `rds_superuser` or any managed-platform proxy role. This retires the entire category of risk the old AWS research spent its longest section on (whether `rds_superuser` could confer `BYPASSRLS`).

**What this means concretely, checked against `packages/db`:**

- `packages/db/sql/roles.sql` and `packages/db/sql/auth-role.sql` are unchanged — they already run correctly against any standards-compliant Postgres, self-managed or not.
- `07.5-05` (already executed, 2026-06-26) replaced `resto_auth`'s `BYPASSRLS` role attribute with explicit permissive RLS policies (migration `0054_resto_auth_permissive_policies.sql`) specifically to make the app RDS-safe. **On self-managed Postgres this migration is no longer load-bearing for correctness — a true superuser could grant `BYPASSRLS` natively — but it should NOT be reverted.** It is already committed, already tested (71 passing tests per `07.5-05-SUMMARY.md`), portable to any future host, and strictly more auditable (`pg_roles.rolbypassrls = false` for every non-superuser role is a stronger invariant than "trust the policy scoping"). Treat it as free hygiene, not a requirement to re-litigate.
- **Tuning worth doing on a small VPS** (CX32: 8 GB RAM, 4 vCPU shared): Postgres 16's defaults (`shared_buffers=128MB`, `max_connections=100`) are conservative for an 8 GB box. A reasonable, low-risk starting point: `shared_buffers=1GB` (≈25% of an 8 GB VPS with 5 other containers competing for RAM — do not go higher without headroom analysis), `effective_cache_size=3GB`, `max_connections=40` (the app's own connection count is small: one pooled `api` connection group, one dedicated `DATABASE_DIRECT_URL` connection for the outbox advisory lock, migration/backup connections — 40 leaves generous headroom over anything MVP-1 volume needs). These are starting values, not tuned-and-measured numbers — `[ASSUMED]`, flagged for the founder/planner to sanity-check against actual `pg_stat_activity` once real traffic exists, not to accept as gospel.
- **Roles are provisioned the same way as CI does today**, not via a fresh mechanism: `packages/db/src/cli/provision-roles-ci.ts` already shows the exact pattern (`provisionAppRole` + `provisionAuthRole` against a fresh Postgres using admin credentials). The production runbook is this same flow run once against the VPS's `postgres` container instead of a CI service container — no new code, a documentation task.
- **Migrations run under `DATABASE_ADMIN_URL`** via `pnpm --filter @resto/db db:migrate` (`packages/db/src/cli/migrate.ts`). One correction to the AWS-era plans' assumption: **`migrate.ts` does not hard-refuse a `DATABASE_URL` fallback in non-dev** — it logs a `warn` and proceeds if `DATABASE_ADMIN_URL` is unset (verified by reading the current file, 2026-09-04). The old plan 09 claimed a hard refusal that does not exist in the code. This is not a blocker — the CD workflow (Pattern 6) simply must always set `DATABASE_ADMIN_URL` explicitly and should not rely on the script to catch a missing one; document this as a known soft-guard, not a hard gate, so nobody is surprised when a misconfigured secret produces a confusing permission error instead of a clean refusal.
- **Boot preflight dry-check (SC#4):** exactly the same five checks `07.5-02`'s CI job already proves locally (`assertNoRlsBypass`, `assertTenantLockInstalled`, `assertSetConfigRevoked`, plus the two prod-only checks `assertSystemRolesPresent`/`assertProdGuardrails` that only run when `NODE_ENV=production`) — this phase's job is to run them against the *real* VPS Postgres once, before traffic, and capture the transcript. No new preflight code is needed.

### Pattern 3: Backups that are actually restorable

**What:** Nightly `pg_dump` (custom format, `-Fc`) from a host cron job, compressed, uploaded to R2 via `rclone`, retained via an R2 Object Lifecycle Rule — not a hand-rolled retention script.

**Recommendation: `pg_dump`, not WAL-G, for this phase.** WAL-G is the more capable tool (continuous WAL archiving → RPO in minutes rather than up to 24h) and is genuinely R2-compatible (`[CITED: wal-g.readthedocs.io/STORAGES/]` — `AWS_ENDPOINT` + `AWS_S3_FORCE_PATH_STYLE=true` + `AWS_REGION` against any S3-compatible endpoint; the exact combination is not in WAL-G's own official-support matrix as an explicitly named provider, but it is the identical mechanism already proven working for MinIO in this repo's own dev environment, and multiple independent sources confirm the same pattern against R2 specifically — `MEDIUM confidence`, not `HIGH`, because no source is WAL-G's own changelog explicitly saying "R2 supported"). But WAL-G requires real new operational surface — `archive_mode=on`, a custom `archive_command` wired into the `postgres` container, WAL-G credentials, and a `delete retain` policy to reason about — for a benefit (tighter RPO) that does not matter yet at first-customer order volume. `pg_dump` is what the founder can stand up, test-restore, and trust *today*, which is the actual G-02 gate: a **tested** restore, not a theoretically-better RPO nobody has rehearsed.

**Where they land in R2:** a dedicated `resto-backups` R2 bucket (separate from the `menu-photos`/media bucket — different access pattern, different lifecycle, and a scoped API token here should never also be able to touch guest-facing media), object key shape `backups/resto-YYYYMMDD-HHMMSS.dump.gz`.

**Script (`infra/scripts/backup-nightly.sh`, illustrative shape):**
```bash
#!/usr/bin/env bash
set -euo pipefail
TS=$(date -u +%Y%m%d-%H%M%S)
DUMP="/tmp/resto-${TS}.dump"

docker exec resto-postgres pg_dump -U "$POSTGRES_ADMIN_USER" -Fc -d "$POSTGRES_DB" > "$DUMP"
gzip "$DUMP"
rclone copy "${DUMP}.gz" r2:resto-backups/backups/ --config /opt/resto/rclone.conf
rm -f "${DUMP}.gz"
```
Host crontab: `0 3 * * * /opt/resto/scripts/backup-nightly.sh >> /var/log/resto-backup.log 2>&1` — 03:00 UTC is overnight for the EU restaurant timezones this product targets, matching the low-traffic window rationale already used for `RESEND_FROM`/domain choices elsewhere in the codebase.

**Retention:** an R2 lifecycle rule on the `resto-backups` bucket's `backups/` prefix — expire after 14 days (`[CITED: developers.cloudflare.com/r2/buckets/object-lifecycles/]`, dashboard or API-configurable, no custom script). This gives roughly two weeks of nightly recovery points at negligible storage cost (a compressed `pg_dump` of an MVP-1-scale database is low tens of MB at most).

**What the restore drill proves (the deliverable, not a note):** a full, realistic disaster-recovery rehearsal, not just "does the file open":
1. `rclone copy r2:resto-backups/backups/<latest>.dump.gz .` — proves the *actual R2 round-trip*, not just that a local file is valid.
2. Spin up a throwaway `postgres:16-alpine` container (`docker run --rm -d --name resto-restore-drill …`), `pg_restore` the dump into it.
3. **Roles are not part of the dump** (`pg_dump` is database-scoped; roles are cluster-level, captured by `pg_dumpall --roles-only`, which this design deliberately does not use). The drill re-runs the *same committed provisioning CLIs* (`provisionAppRole`/`provisionAuthRole`, `pnpm db:migrate`) against the restored database — this is more realistic than trusting a raw role dump, because it is exactly what a genuine recovery (new VPS, fresh Postgres, restore data, re-provision roles, point the app at it) would actually do.
4. Verify: the drizzle migrations journal (`__drizzle_migrations`) matches the committed migration count; the three roles exist with correct `rolbypassrls`/`rolsuper` attributes; a sample tenant-scoped table is readable and returns the expected row shape.
5. Tear the scratch container down. Record the elapsed wall-clock time as the observed RTO.

**RPO/RTO to record (starting targets, to be replaced with the actually-observed numbers during the real drill):** RPO ≤ 24h (bounded by nightly cadence — tightenable to 6h for free by just changing the cron schedule, before ever reaching for WAL-G). RTO target < 1 hour for a manual-but-scripted recovery (not a fully automated failover — that is out of scope for a bootstrap-budget solo-founder deploy).

**The certificate, measured on the founder's own live zone rather than reasoned about** (M-03/M-04/M-05):

```
$ openssl s_client -connect restos.pp.ua:443 -servername restos.pp.ua </dev/null 2>/dev/null \
    | openssl x509 -noout -subject -issuer -ext subjectAltName -dates

    DNS:restos.pp.ua, DNS:*.restos.pp.ua
```

Two SANs. That is the whole scheme in one line: **the apex and exactly one wildcard level.** The
entire three-apex design existed to buy those two SANs three times over; one domain buys them once.

**DNS records (five, on one zone):**

| Host | Type | Target | Proxied | Serves |
|---|---|---|---|---|
| `<apex>` | A | VPS public IP | Yes | `website` container via Caddy; Worker Route intercepts `/admin*` |
| `*.<apex>` | A (or CNAME → `<apex>`) | VPS public IP | Yes | `website` container via Caddy; Worker Route intercepts `/qr*` |
| `api.<apex>` | A | VPS public IP | Yes | `api` container via Caddy |
| `media.<apex>` | CNAME | R2 public bucket / custom domain | Yes | `MEDIA_PUBLIC_BASE_URL` (unchanged) |
| `www.<apex>` | CNAME → `<apex>` | — | Yes | Optional redirect. Note `www` is already in `RESERVED_HOSTS` and `NON_GUEST_SECOND_LABELS` (`tenant-resolver.service.ts:8,12`), so it can never resolve as a tenant |

Note `*.<apex>` covers `api.<apex>` in DNS terms, but an explicit A record for `api` is still worth
having so the record is visible in the dashboard and can be repointed independently.

**Worker Routes — two, plus one negation. All three rules below are quoted from the current
official routing doc** (`[CITED: developers.cloudflare.com/workers/configuration/routing/routes/]`,
fetched 2026-09-05):

- *"The only supported operator is the wildcard (`*`), which matches zero or more of any character."*
- *"When more than one route pattern could match a request URL, the most specific route pattern wins."*
- *"A route can be specified without being associated with a Worker. This will act to negate any less specific patterns."*
- *"`*.example.com/` matches `https://www.example.com/` but not `https://example.com/`."* — so a
  `*.<apex>/…` route never touches the apex, and an apex route never touches a tenant host. The two
  Workers cannot collide.

| Pattern | Worker | Why |
|---|---|---|
| `<apex>/admin*` | `resto-admin` | Serves the admin SPA. Does **not** match `<slug>.<apex>/admin*` (wildcard-hostname rule above), which is correct — an operator's admin lives on the apex only |
| `*.<apex>/qr*` | `resto-qr-menu` | Serves the QR-menu SPA on every tenant host |
| `api.<apex>/*` | *(none — negation)* | Belt and braces. Neither route above matches `api.<apex>`, but leaving an explicit no-Worker route documents the intent and survives someone later broadening a pattern to `*.<apex>/*` |

**Everything else — `/`, `/v1/*`, `/api/*`, `/checkout`, `/internal*` — reaches Caddy, on both the
apex and every tenant host.** That is the design's biggest simplification: *no Worker proxies
anything.* Under the three-apex scheme the two SPAs had to be reverse proxies because their
hostnames had no origin at all. Under one apex, `<apex>` and `<slug>.<apex>` are ordinary
origin-backed hostnames that Caddy already serves, so the API is reachable same-origin by simply
routing a path.

**Caddyfile — measured working (M-06/M-08), Caddy 2.11-alpine:**

```
{
	admin off
	servers {
		# Unchanged from the committed file, and still load-bearing for
		# client_ip: Caddy must trust the peer before it will read
		# CF-Connecting-IP at all. ufw admits 80/443 from Cloudflare ranges
		# only, which is what makes the blanket range defensible.
		trusted_proxies static 0.0.0.0/0 ::/0
		client_ip_headers CF-Connecting-IP
	}
}

{$API_HOST} {
	tls /etc/caddy/certs/origin.crt /etc/caddy/certs/origin.key
	@internal_blocked {
		path /internal*
		not client_ip {$INTERNAL_ALLOWED_IPS:192.0.2.1/32}
	}
	respond @internal_blocked 404
	# NOTE: no `header_up X-Forwarded-Host` here — see Pitfall #11. This block
	# is the one place an inbound X-Forwarded-Host is still meaningful, and it
	# must stop being so before the pin can be applied uniformly.
	reverse_proxy api:3000
}

{$WEBSITE_HOST}, *.{$WEBSITE_HOST} {
	tls /etc/caddy/certs/origin.crt /etc/caddy/certs/origin.key

	# `handle` blocks are mutually exclusive and evaluated in written order.
	# Measured: /internal* 404s without reaching any upstream; /v1/* and
	# /api/* reach api:3000; everything else reaches website:3002.
	handle /internal* {
		respond 404
	}
	handle /v1/* {
		reverse_proxy api:3000 {
			header_up X-Forwarded-Host {host}
		}
	}
	handle /api/* {
		reverse_proxy api:3000 {
			header_up X-Forwarded-Host {host}
		}
	}
	handle {
		reverse_proxy website:3002 {
			header_up X-Forwarded-Host {host}
		}
	}
}
```

Three things about this block are not cosmetic:

1. **`handle /internal*` → 404 comes first.** The `client_ip` gate exists only in the `{$API_HOST}`
   block. Without this, `<apex>/internal/v1/*` would reach the API past a gate the runbooks claim
   protects it. `InternalTokenGuard` is still the real control (constant-time compare, throws
   outside development); this keeps the *claim* honest, which is the standard Round 2 set.
2. **`header_up X-Forwarded-Host {host}`** overwrites any client-supplied value with the request's
   own `Host`. Measured against both a single forged header and the comma-joined two-value shape
   (M-08). Under the old scheme this pin was impossible — the Worker's legitimate `X-Forwarded-Host`
   was the only thing carrying the tenant, which is exactly why `trusted_proxies static 0.0.0.0/0`
   was introduced to preserve it. Under this scheme nothing upstream needs to set it, so the pin is
   free. See Pitfall #11.
3. **`{$WEBSITE_HOST}, *.{$WEBSITE_HOST}` already exists in the committed Caddyfile** and needs only
   the three `handle` blocks added. `{$API_HOST}` is unchanged.

**Origin CA certificate:** one certificate, SANs `<apex>, *.<apex>, api.<apex>`, on the single zone.
Cloudflare SSL/TLS mode "Full (strict)". No Let's Encrypt, no renewal cron. (Unchanged mechanism,
one zone instead of three.)

**Cache Rule (settles D-08, which no plan ever created):** one Cache Rule on the zone —
expression `starts_with(http.request.uri.path, "/v1/menu")`, action *Eligible for cache*, respect
origin TTL. The origin already emits `public, s-maxage=300` + ETag
(`apps/api/src/contexts/catalog/domain/menu-cache.ts`, `docs/runbooks/menu-edge-caching.md`). The
zone cache key is the full request URL, which now carries the tenant in its host — so the
tenant-keyed cache the qr-menu Worker was hand-rolling is what Cloudflare does by default. See
Pattern 4c.

### Pattern 4a: Two apps on one hostname — the `/qr` and `/admin` base paths

Cloudflare documents this exactly (`[CITED: developers.cloudflare.com/workers/static-assets/routing/advanced/serving-a-subdirectory/]`,
requires Wrangler ≥ 3.98.0; we are on 4.129.0):

> *"Assets defined for a Worker must be nested in a directory structure that mirrors the desired
> path. For example, to serve assets from `example.com/blog/*`, create a `blog` directory in your
> asset directory."*

So the build changes are two lines per app:

| App | Vite `base` | Vite `build.outDir` | wrangler `assets.directory` | Route |
|---|---|---|---|---|
| qr-menu | `/qr/` | `dist/qr` | `./dist` | `*.<apex>/qr*` |
| admin | `/admin/` | `dist/admin` | `./dist` | `<apex>/admin*` |

**The trap, and it is not in the docs — measured with `wrangler 4.129.0 dev --local` (M-09).**
`not_found_handling: "single-page-application"` serves *`/index.html` at the asset root*, not the
subdirectory's index. With assets nested under `dist/qr/` and nothing at `dist/index.html`:

| Request | Result |
|---|---|
| `/qr/` | 200, the shell |
| `/qr/assets/app.js` | 200, the real file |
| `/qr/items/abc` | **404** ← every deep link is dead |

Two configurations fix it. Both were run; the difference between them is a free-tier billing cliff,
not taste.

**Recommended — assets-only, no Worker script:**

```jsonc
// apps/qr-menu/wrangler.jsonc
{
  "name": "resto-qr-menu",
  "compatibility_date": "2026-09-01",
  "assets": {
    "directory": "./dist",
    "not_found_handling": "single-page-application"
  }
}
```

with one line added to the build: `cp dist/qr/index.html dist/index.html`. Measured result:

| Request | Result |
|---|---|
| `/qr` | 307 → `/qr/` (Cloudflare's own HTML URL normalisation) |
| `/qr/` | 200, shell |
| `/qr/t/<token>` | 200, shell — **the QR sticker path works** |
| `/qr/items/abc` | 200, shell |
| `/qr/assets/app.js` | 200, real file |

Why this one is recommended, and it is a cost argument with a citation
(`[CITED: developers.cloudflare.com/workers/static-assets/billing-and-limitations/]`):

> *"Requests to static assets are free and unlimited. Requests to the Worker script … are billed
> according to Workers pricing."*
>
> *"**Important note for free tier users**: When using `run_worker_first`, requests matching the
> specified patterns will always invoke your Worker script. If you exceed your free tier request
> limits, these requests will receive a 429 (Too Many Requests) response instead of falling back to
> static asset serving."*

On the free plan, an assets-only project has **no** request ceiling. A project using
`run_worker_first: ["/qr/*"]` puts every JavaScript and CSS file of the menu behind the 100k/day
Worker limit, and the failure mode past the limit is a 429 on the bundle — a white screen at a
restaurant table, on the busiest day.

**Alternative — Worker script with an explicit fallback** (keep only if a plan needs Worker logic on
these paths for some other reason):

```jsonc
{
  "main": "worker/index.ts",
  "assets": {
    "directory": "./dist",
    "binding": "ASSETS",
    "not_found_handling": "none",
    "run_worker_first": ["/qr/*"]
  }
}
```

```typescript
const res = await env.ASSETS.fetch(request);
if (res.status === 404 || res.status === 307) {
  // Measured: fetching '/qr/index.html' returns 307 -> '/qr/', so a naive
  // fallback to the .html path turns every deep link into a redirect to the
  // menu root — which silently breaks /qr/t/<token>. Target the directory URL.
  const shell = await env.ASSETS.fetch(new Request(new URL('/qr/', url), request));
  return new Response(shell.body, { status: 200, headers: shell.headers });
}
return res;
```

**SPA source changes for the base path — the complete list:**

*qr-menu* (`apps/qr-menu/src/App.tsx:39-41`, `:139,143,226,231,236`): the four route regexes
(`/items/<id>`, `/info/<key>`, `/t/<token>`, and the implicit `/`) and every `history.pushState` /

API paths (`/v1/…` in `apps/qr-menu/src/api/client.ts`, 13 call sites) are **unchanged** — they are
root-absolute and Caddy owns `/v1/*` on that host.

*admin*: `createRouter({ basepath: '/admin', … })` — verified present in the installed
`@tanstack/router-core@1.171.13` (`dist/esm/router.d.ts:198`, *"The basepath for then entire router.
This is useful for mounting a router instance at a subpath."*). One line. `apiFetch` paths
(`/v1/…`, `/api/auth/…`) are unchanged and must stay root-absolute. The Better Auth client already
has no `baseURL` and derives `window.location.origin + '/api/auth'`
(`apps/admin/src/lib/auth-client.ts:4-7`) — correct on the apex with no change.
`apps/admin/src/routes/(auth)/forgot-password.tsx:43` builds

**How the storefront's SSR is reached:** it is not reached through any Worker. `<slug>.<apex>` DNS
points at the VPS; Cloudflare proxies; the Worker Route matches only `/qr*`; every other path goes
to Caddy's `{$WEBSITE_HOST}, *.{$WEBSITE_HOST}` block → `website:3002`. The Next.js app resolves its

construction rather than by a Worker's cooperation.

### Pattern 4b: Admin tenancy without a tenant host — what the new trusted input is

This is the only part of the scheme that is not deployment configuration, and it touches the code
that decides whose data a request may reach. State the answer plainly first:

> **The new trusted input is the Better Auth session's `activeOrganizationId`. Nothing else.
> The URL carries no tenant at all.**

**Not a slug in the path.** The founder's map is `<apex>/admin`, with no `<slug>` segment, and that
is the right reading: phase 10.2's D-20 deliberately *removed* `/{brandSlug}` from admin paths, and
D-21 chose a host over a path precisely because *"a path segment changes on every navigation, so
reconciling it against the session costs a check in all 18 route files."* Re-adding a slug segment
would reintroduce exactly what D-20 deleted and buy nothing: the "two tabs on two tenants" property
is lost either way, because `activeOrganizationId` is per-session, not per-tab.

**The reassuring part: this is already how it works in production.** The tenant has not been read
from the admin host on the server side for some time. `TenantContextMiddleware.resolveTenantOnly`
(`tenant-context.middleware.ts:89-120`) tries, in order:

1. `x-tenant-id` — the BA `activeOrganizationId` UUID, which `apps/admin/src/lib/api-client.ts:55,63`
   attaches to **every** `/v1/*` request today (RES-181);
2. `x-tenant-slug` — gated by `shouldAcceptTenantSlugHeader` (`:122-131`) to dev/test or
   `/internal/v1/*` + a constant-time internal-token compare;
3. the host.

So today, in production, the admin's tenant already arrives as a **header**, and the host branch is
a fallback that only fires when the header is missing. Removing the tenant from the host removes
the fallback, not the mechanism.

**What validates it.** `AuthGuard.canActivate`
(`identity/interfaces/http/guards/auth.guard.ts:119-136`) resolves the BA session, builds the
principal with `tenantId = session.activeOrganizationId`, and refuses when the request's bound
tenant and the principal's tenant disagree:

```typescript
if (principal.kind !== 'anonymous' && 'tenantId' in principal && principal.tenantId
    && alsTenantId && principal.tenantId !== alsTenantId) {
  throw new ForbiddenException({ code: 'auth.tenant_mismatch', ... });
}
```

Under this scheme `alsTenantId` is derived *from* `activeOrganizationId`, so the two are the same
value by construction and the check becomes tautological on the admin path — it stays as the guard
for every other path (a forged host, a stale header, `/internal/*`).

`ScopedTx` and RLS are then bound to `alsTenantId` exactly as before. The chain is:
**session cookie → BA session row → `activeOrganizationId` → ALS tenant → `ScopedTx` + RLS.**
Every link is server-side except the cookie, which is `httpOnly`. That is a *stronger* chain than
the host-based one it replaces, because a host is attacker-nameable (see Pitfall #11) and a session
row is not.

**The one hole to close, and it exists today.** `buildPrincipal` (`auth.guard.ts:239-253`) only sets
`operator.tenantId` when `activeOrganizationId` is present. If a session has **no** active
organization, `principal.tenantId` is `undefined`, the mismatch check is skipped by its own
`principal.tenantId &&` guard, and whatever `x-tenant-id` the client sent binds the ALS tenant
unchecked. Downstream this mostly fails closed — `lookupBaseRole` is likewise guarded by
`principal.tenantId`, so `PermissionsGuard` rejects any `@Permissions(...)` route — but "mostly"
is not a security argument, and the set of routes that carry `@RequiresTenantContext` **without**
`@Permissions` has never been enumerated.

**Recommended fix, one condition:** in `AuthGuard`, when `alsTenantId` is bound and the principal is
an operator, require membership rather than merely require non-contradiction:

```typescript
// Deny by default: an operator request that binds a tenant must be a member of it.
if (principal.kind === 'operator' && alsTenantId && principal.tenantId !== alsTenantId) {
  throw new ForbiddenException({ code: 'auth.tenant_mismatch', ... });
}
```

Dropping the `principal.tenantId &&` clause turns "they must not disagree" into "they must agree",
which is the property the scheme actually relies on. `member`-table membership is already looked up
by `lookupBaseRole` (`:166-184`) if a second layer is wanted. This is a two-line change and a test;
it should be executed as part of the same plan as the path move, not deferred.

### Pattern 4c: Preserving phase 10.2's stale-cache property under one origin

T-10.2-14-02 and T-10.2-16-02 both closed *"a stale query cache serving another organization's data
after a switch"* with the same mitigation: *"the organization switch is a hard cross-origin
navigation (D-21) that discards the in-memory cache."* Under a path scheme the origin no longer
changes, so the question is whether a same-origin hard navigation still discards it, and what stops
a later refactor from quietly downgrading it.

**Does it still discard? Measured, Chromium via Playwright 1.60.0 (M-10).** A module-scope object
carrying a `performance.now()` stamp, in a page that then navigates:

| Action | `location.pathname` after | Module-scope object survived? |
|---|---|---|
| `window.location.assign('/dashboard/')` | `/dashboard/` | **No** — stamp changed 40 → 4.7. New document, new realm |
| `history.pushState(null, '', '/dashboard/')` | `/dashboard/` | **Yes** — stamp unchanged |

So the property holds, and the "cross-origin" part of 10.2's reasoning was never the load-bearing
part — "cross-**document**" was. Two supporting facts, both read from the repo rather than assumed:
`apps/admin/src/lib/query-client.ts` creates the `QueryClient` at module scope, and a grep for
`persistQueryClient` / `createSyncStoragePersister` across `apps/admin/src` returns nothing — the
cache has no storage backing that could survive the document.

**But the same measurement is the threat model.** `history.pushState` is exactly what TanStack
Router's `navigate()` does. Under the host scheme a client-side route change *could not* reach
another tenant, because `navigate()` cannot cross an origin — the impossibility was structural.
Under the path scheme `navigate({ to: '/dashboard' })` after a switch is a perfectly ordinary call
that compiles, type-checks, passes review, and silently keeps tenant A's cache. **The property stops
being enforced by physics and starts needing to be enforced by the codebase.**

**Recommended enforcement — three layers, cheapest first, all modelled on patterns this repo already
uses:**

1. **One helper, one call site each.** `apps/admin/src/lib/switch-tenant.ts`:

   ```typescript
   export const switchTenant = async (organizationId: string, next = '/dashboard'): Promise<void> => {
     const res = await apiFetch<SwitchTenantResponse>('/api/auth/switch-organization', {
       method: 'POST', body: { organizationId },
     });
     if (!res.ok || !res.data) throw new TenantSwitchFailedError();
     // Belt: the reload below is what actually discards the cache (measured), but
     // clearing explicitly is the part a test can assert. Braces: apiFetch's 2s
     // session cache still holds the previous activeOrganizationId.
     queryClient.clear();
     window.location.assign(next);
   };
   ```

2. **An ESLint `no-restricted-syntax` rule** in `apps/admin/eslint.config.mjs` forbidding the string
   literal `'/api/auth/switch-organization'` anywhere except `src/lib/switch-tenant.ts`. This is the
   same shape as the two rules the repo already enforces for exactly this class of invariant —
   `runInTenantContext` restricted to `tenant-context.middleware.ts` (ADR-0020 I-6) and
   `withoutTenant` allowlisted by file path (RES-252 I-1) — so it needs no new machinery and no new
   argument, only a new entry and an ADR/ticket citation in the rule's `message`.

3. **A test that fails if the navigation is downgraded.** Assert that `switchTenant` calls
   `queryClient.clear()` and that it assigns `window.location`, not that it calls `navigate`. A
   Playwright assertion is stronger still and is now cheap to express: after a switch, assert
   `performance.getEntriesByType('navigation')[0].type === 'navigate'` on the landing page — a
   pushState route change produces no navigation entry at all.

Layer 2 is the answer to *"what enforces it so a later refactor cannot quietly turn it into a
client-side route change"*. Layers 1 and 3 make the failure loud rather than silent; layer 2 makes
it not compile.

**A related module-scope cache the plan must not miss:** `apps/admin/src/lib/api-client.ts:20-39`
holds a 2-second `sessionCache` of the BA session, which is where `x-tenant-id` comes from. On a
client-side switch it would send the *previous* `activeOrganizationId` with a session bound to the
new one — which `AuthGuard` rejects as `auth.tenant_mismatch` (403), so it fails closed rather than
leaking. Worth stating in the plan so an executor who sees that 403 during testing does not
"fix" it by weakening the guard.

**Edge cache, for completeness:** unaffected and simplified. The tenant is still in the host for
every guest surface, so the Cloudflare zone cache keys `https://<slug>.<apex>/v1/menu` per tenant
with no code at all. The admin path caches nothing (`<apex>/v1/*` and `<apex>/api/*` responses are
authenticated and carry `Set-Cookie` or `Cache-Control: private`).

### Pattern 4d: Cookie scoping — better isolation than the design it replaces

**What `AUTH_COOKIE_DOMAIN` does when unset — read from the installed package, not assumed
(M-11).** `identity-core.module.ts:283` spreads `cookieDomain` only when set, and
`auth.config.ts:559-566` spreads the whole `advanced.crossSubDomainCookies` block only when
`opts.cookieDomain` is truthy. In `better-auth@1.6.30`, `dist/cookies/index.mjs:22-23,36`:

```javascript
const crossSubdomainEnabled = !!options.advanced?.crossSubDomainCookies?.enabled;
const domain = crossSubdomainEnabled ? (… ) : void 0;
…
...crossSubdomainEnabled ? { domain } : {},
```

With the option absent the `Domain` attribute is **omitted entirely**, so the browser stores a
**host-only** cookie: it is sent to `<apex>` and to nothing else — not `<slug>.<apex>`, not
`api.<apex>`. Remaining attributes are `Path=/`, `SameSite=lax`, `HttpOnly`, and `Secure` with the
`__Secure-` name prefix under https.

**This is strictly better isolation than the current design achieves.** `.<admin-apex>` is a
*domain* cookie: it reaches every subdomain of the admin apex, including any that might be added
later, and the leading-dot rule was introduced (D-24) precisely because the sign-in flow had to hop
`admin.<domain>` → `<slug>.admin.<domain>`. With admin on a path there is no hop, so the cookie
never needs to leave one host. A host-only cookie is the narrowest scope the platform offers, and
the guest surfaces are on *different hosts of the same registrable domain*, which a host-only cookie
does not reach.

**Two schema changes, both required, both small:**

1. **`AUTH_COOKIE_DOMAIN` must stop being required outside dev/test.** It is currently in the
   `superRefine` required list (`env.schema.ts:361`) and in `prod-guardrails.ts`. Remove it from
   the required list. Leaving it required would force a value, and every legal value is now wrong.
2. **The "must start with a dot" rule (`env.schema.ts:389-395`) does not need to change** — it is
   conditioned on `env.AUTH_COOKIE_DOMAIN &&`, so an unset value skips it. Keep the rule for the
   case where a future deployment genuinely wants cross-subdomain cookies; **update the message and
   the field comment**, both of which currently instruct the reader to set `.admin.resto.app` and
   explain a hop that no longer exists. A stale instruction here is worse than none: it would talk a
   future operator into re-widening the cookie to `.{apex}`, which would deliver the operator
   session to every tenant storefront.

**One public-suffix note, because the apex has three labels.** `pp.ua` is on the Public Suffix List
(M-02, ICANN section, alongside `biz.ua`/`co.ua`). That is benign here — `restos.pp.ua` is the
registrable domain, so `Domain=.restos.pp.ua` would be legal if ever needed — but it is a live
tripwire for any "just drop a label off the apex" rule: `Domain=.pp.ua` is rejected by every
browser. Another reason the leading-dot rule should stay a *shape* check and the scope should stay
unset.

**Dev parity:** `.env.example` currently sets `AUTH_COOKIE_DOMAIN=.admin.localhost` and carries a
long comment (lines 46-53) explaining why dev needs the dotted value. Both come out; dev becomes
`http://localhost:4000/admin/` with a host-only cookie, which is the same shape as production for
the first time.

### Pattern 5: Secrets on the box

**What:** Two `.env` files on the VPS (`/opt/resto/.env.api`, `/opt/resto/.env.website`), `chmod 600`, owned by the deploy user, referenced by `env_file:` in `docker-compose.prod.yml` — never `COPY`'d into a Docker build context, never committed.

**How they're delivered without baking them into an image:** the CD workflow's SSH step (Pattern 6) does **not** re-write these files on every deploy — they are seeded once, by hand, during initial VPS setup (a `checkpoint:human-action` task in the plan, same shape as the old AWS plan's "create the RDS instance by hand" task), and only touched again when a secret actually rotates. This is the correct application of "secrets never in the image": the *image* is genuinely secret-free (built once, deployed to any environment), and the *runtime* env is supplied entirely out-of-band by the file already sitting on the box. Contrast with the handful of **build-time, non-secret** values (`NEXT_PUBLIC_API_ORIGIN` for the website Dockerfile) — those remain `ARG`s baked at build time exactly as `07.5-11` already implemented, because they are genuinely public (shipped to every browser anyway) and the repo's own `apps/CLAUDE.md` rule ("`NEXT_PUBLIC_*` must not have a production fallback") is about correctness, not secrecy.

**Rotation:** SSH in, edit the relevant `.env.*` file, `docker compose up -d --no-deps <service>` to pick it up (the container reads `env_file:` at creation, not continuously — a restart is required and is the correct, expected mechanism). No automation is warranted for this at MVP-1 scale; document the manual procedure in `docs/runbooks/secrets-on-the-box.md`.

**Secret inventory (api):** `DATABASE_URL`, `DATABASE_DIRECT_URL` (per D-05', may be identical strings), `DATABASE_ADMIN_URL` (used only by the one-off migration container, not the long-running `api` service — do not put it in `.env.api` at all; inject it only for the migration step), `BETTER_AUTH_DATABASE_URL`, `BETTER_AUTH_SECRET`, `AUDIT_ERASURE_SALT`, `INTERNAL_API_TOKEN`, `NATS_URL`/`NATS_USERNAME`/`NATS_PASSWORD`, `S3_*` (R2), `SENTRY_DSN`, `RESEND_API_KEY`, `RESEND_FROM`/`RESEND_REPLY_TO` (both `.default()` to an unowned apex — already in the dev-default guard set as of plan 07), `STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET`/`STRIPE_CONNECT_CLIENT_ID` (see Pitfall #10), `TRUST_PROXY`, `CORS_ALLOWED_ORIGINS`, `ADMIN_WEB_URL=https://${PUBLIC_APEX_DOMAIN}/admin`, `WEBSITE_PUBLIC_URL`, `PUBLIC_APEX_DOMAIN`. **Removed by the single-apex scheme:** `AUTH_COOKIE_DOMAIN` (now unset — Pattern 4d), `ADMIN_WEB_ORIGIN_WILDCARD` (no per-tenant admin origins), `GUEST_APEX_DOMAIN` and `ADMIN_APEX_DOMAIN` (collapsed into `PUBLIC_APEX_DOMAIN`). Optionally added: `API_INTERNAL_ORIGIN` for the website container — see Pitfall #11.

**Secret inventory (website):** `NEXT_PUBLIC_API_ORIGIN` (build-time ARG, not runtime secret), `WEBSITE_URL`.

**CI-time-only secrets** (GitHub Actions repo/environment secrets, never touch the VPS filesystem): `SSH_PRIVATE_KEY` (deploy-only key, restricted `authorized_keys` command if feasible), `SSH_HOST`, `SSH_USER`, `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `DATABASE_ADMIN_URL` (for the gated migration step — passed over the already-encrypted SSH session, not written to disk on the VPS as a standing file).

### Pattern 6: Deployment on merge

**What:** `.github/workflows/deploy.yml`, triggered via `workflow_run` on `ci.yml`'s completion (gates on green CI without duplicating its matrix), gated on `github.event.workflow_run.conclusion == 'success'` and the branch being `main`.

**Steps, in order:**
1. Build `api` and `website` Docker images, tag with `${{ github.sha }}`, push to `ghcr.io` (`docker/build-push-action`). Website build passes `--build-arg NEXT_PUBLIC_API_ORIGIN=https://api.${{ vars.PUBLIC_APEX_DOMAIN }}` — a real value, never the Dockerfile's own placeholder default, matching the already-closed G-05 principle. **2026-09-05:** if Pitfall #11's second fix lands (storefront checkout on same-origin relative paths), this build arg stops being needed by the client and the website gains a server-only `API_INTERNAL_ORIGIN=http://api:3000` instead.
2. Build the admin and qr-menu Vite SPA bundles (`pnpm --filter admin build`, `pnpm --filter qr-menu build`).
3. **Gated pre-rollout migration** — this is the one step that genuinely differs from the AWS-era assumption: **Postgres has no public endpoint** in this topology (Pattern 1, deliberately), so the migration cannot run directly from the GitHub Actions runner the way it could against a (potentially publicly-reachable) RDS endpoint. It must run *from the VPS itself*, over the same SSH connection used for the deploy: `ssh <vps> "cd /opt/resto && DATABASE_ADMIN_URL='...' docker compose -f docker-compose.prod.yml run --rm api pnpm --filter @resto/db db:migrate"`. If this step fails, the job stops — no new image is ever recreated, the previous version keeps serving. `assertTenantLockInstalled` remains the boot-time backstop if a rollout ever races ahead of a migration regardless.
4. SSH deploy: `docker compose pull api website && docker compose up -d --no-deps --pull always api website` (recreates only these two services; `postgres`/`nats`/`caddy` untouched, their volumes never at risk).
5. `wrangler deploy` for admin and qr-menu (`cloudflare/wrangler-action`), each picking up its already-built `dist/` directory and supplying its route on the CLI so no hostname is committed:
   `--routes "$PUBLIC_APEX_DOMAIN/admin*"` and `--routes "*.$PUBLIC_APEX_DOMAIN/qr*"`. Neither needs `--var API_ORIGIN` any more — the assets-only Workers have no `env`.
6. Poll `https://api.${PUBLIC_APEX_DOMAIN}/healthz` until 200 (with a timeout) — fail the job on timeout.

**G-06 rollback (app-only, DB never rolled back):** capture the prior SHA (the tag currently running); to roll back, `ssh <vps> "cd /opt/resto && API_IMAGE_TAG=<prior-sha> docker compose up -d --no-deps api"` (and the equivalent for `website`) — Docker will use the already-locally-cached prior image if it's still present (fast) or re-pull it from GHCR (still fast — small alpine-based images). Migrations are forward-only (hard deletes forbidden by role grant, per the repo's own existing constraint) — expand/contract is the only rollback strategy that makes sense here, unchanged from the AWS-era plan's own correct reasoning, just re-pointed at a Compose command instead of an ECS one. Website's rollback needs no rebuild — the prior image already has the correct `NEXT_PUBLIC_API_ORIGIN` baked in from when it was built.

**What differs from the old (AWS) `deploy.yml` shape besides the target:** no OIDC role assumption (there is no AWS to assume a role into — the credential model is an SSH key instead), no ECR (GHCR), and the migration step's *location* (must run on the VPS, not the runner) is the one genuinely new constraint this stack introduces that the AWS-era plan did not have to solve.

### Pattern 7: The go-live smoke

Retargeted at the single-apex map. Five hostnames become **three** (`<apex>`, `<slug>.<apex>`,
`api.<apex>`), and two of the old assertions become both cheaper and more meaningful because the
cache signal is now Cloudflare's own header rather than one the Workers had to invent.

1. `GET https://api.<apex>/healthz` → 200.
2. `GET https://<slug>.<apex>/` → 200, body contains a real seeded menu item. Proves the storefront
   SSR path end-to-end: Cloudflare → Caddy → `website` → API → Postgres, with the tenant resolved
   from the real `Host`.
3. `GET https://<slug>.<apex>/v1/menu` → 200, JSON naming that tenant. **This is the M3 assertion
   from Round 1 and it must stay mandatory** — it is the only check that proves tenant resolution
   before go-live day. Under this scheme it also proves the Caddy `handle /v1/*` split.
4. **Edge cache, tenant-keyed:** request `/v1/menu` on tenant A twice and assert `cf-cache-status`
   goes `MISS` → `HIT`; then request tenant B's `/v1/menu` and assert the body differs from A's.
   Round 1 correctly rejected `cf-cache-status` as untestable when a Worker served the response from
   `caches.default`; with the zone cache serving it, the header is emitted by Cloudflare's own
   pipeline and the assertion is real. **Do not assert that the two tenants' `ETag`s differ** —
   `public-menu.controller.ts:272,298` builds the ETag as a bare menu-version integer, so two
   freshly published tenants are both `"1"`. The body comparison is the part that means something.
5. `GET https://<slug>.<apex>/qr/` → 200 HTML shell, and `GET https://<slug>.<apex>/qr/t/anything`
   → 200 HTML shell (not 404). The second one is the deep-link assertion that catches the
   subdirectory SPA-fallback trap in Pattern 4a, which is a silent 404 that only the sticker path
   would ever hit.
6. `GET https://<apex>/admin/` → 200 HTML shell; `GET https://<apex>/admin/anything` → 200 shell.
7. **The highest-value assertion:** sign in with valid credentials against `https://<apex>` and
   assert the `Set-Cookie` on the response carries **no `Domain=` attribute** (host-only — Pattern
   4d) and that a follow-up authenticated `GET https://<apex>/v1/me` returns 200 with the expected
   tenant. This is the F-41 regression net, and unlike the Round-1 version it does not depend on
   CORS header presence, which was a coin flip.
8. `GET https://<apex>/internal/v1/anything` → 404 and `GET https://<slug>.<apex>/internal/v1/anything`
   → 404, from an address that is *not* in `INTERNAL_ALLOWED_IPS`. Proves the `handle /internal*`
   block, which is new in this scheme.
9. **Negative control for the header pin (Pitfall #11):** `GET https://<slug-a>.<apex>/v1/menu`
   with `-H 'X-Forwarded-Host: <slug-b>.<apex>'` must return **tenant A's** menu. This is the
   assertion that proves `header_up X-Forwarded-Host {host}` is actually deployed, and it is the
   kind of check the Round-2 review asked for when it said a gate needs a test rather than a
   paragraph.
10. Confirm a `STRIPE_WEBHOOK_SECRET`-signed test webhook reaches `https://api.<apex>/webhook/stripe`.

There is currently **no `apps/*/e2e` directory and no Playwright config in `apps/admin`** — the
"ported ADM-00 admin Playwright smoke" this section used to name has no artifact. Assertion 7 above
is the curl-level replacement; if a plan wants the browser-level version it must first re-create the
harness, which is a separate piece of work and should be scoped as such.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| Same-origin API access for an SPA on a tenant host | A reverse-proxy Worker (what plans 06-07 built) or a Node/nginx sidecar | **Caddy `handle /v1/*` on the hostname the SPA already lives on** | Under one apex the SPA's hostname has a real origin, so "same-origin" is a routing rule, not a proxy. Deletes the proxy, its `X-Forwarded-Host` handling, its cache-key logic and its `cf` options in one move |
| Per-tenant edge cache for the public menu | A Worker Cache API entry keyed on the incoming URL | **The Cloudflare zone cache + one Cache Rule on `/v1/menu*`** | The zone cache key already *is* the full request URL, which carries the tenant in its host. Also tiered-cache-compatible, which the Cache API is not (`[CITED: developers.cloudflare.com/workers/reference/how-the-cache-works/]`) |
| SPA deep-link fallback under a base path | A Worker script with `run_worker_first` | **`not_found_handling: single-page-application` + a root `index.html` copy** | Assets-only projects have no free-tier request ceiling; `run_worker_first` puts every JS/CSS file behind the 100k/day limit and 429s past it (`[CITED: …/static-assets/billing-and-limitations/]`) |
| TLS certificate issuance/renewal for the VPS origin | `certbot` + a renewal cron + failure alerting | Cloudflare Origin CA certificate (15-year validity) | Zero renewal surface for the life of the certificate; purpose-built by Cloudflare for exactly this "origin behind our proxy" scenario |
| Backup retention/rotation | A "delete files older than N days" script against R2 | R2 Object Lifecycle Rules | Native, dashboard/API-configurable, cannot be broken by a script bug |
| Edge DDoS/flood protection | `iptables` rate-limiting on the VPS | Cloudflare's always-on L3/4/7 protection (free tier, active on every proxied zone) | The VPS never even sees a volumetric attack when the firewall also restricts inbound to Cloudflare's IP ranges (Pitfall #5) |
| Uploading compressed dumps to an S3-compatible endpoint | Hand-rolled multipart upload + SigV4 signing | `rclone` (officially R2-documented) | Battle-tested, handles multipart/retries/resume; zero reason to reimplement S3 signing by hand |
| Postgres role/schema provisioning for prod | A brand-new "prod setup" script | The already-committed `provisionAppRole`/`provisionAuthRole`/`pnpm db:migrate` CLIs | Identical code path CI already exercises daily; a new script would be an untested second implementation of the same logic |

**Key insight, sharpened by the single-apex revision:** almost nothing in this phase is new engineering, and the last revision proved the point the hard way — the two Workers built in plan 07 were a careful, well-tested reimplementation of same-origin routing and per-tenant edge caching, both of which Caddy and the Cloudflare zone cache already do. They were not built carelessly; they were built because the three-apex hostname map made them necessary. **When a plan finds itself writing infrastructure logic in application code, the first question is whether a hostname or routing decision upstream made it necessary — and whether that decision is the thing to change.**

## Common Pitfalls

### Pitfall 1: Building a reverse-proxy Worker for a hostname that already has an origin

**What goes wrong:** A plan carries forward the three-apex design and gives each SPA a Worker that
proxies `/v1/*` (and `/api/*`) to `api.<apex>`. It works, and then every one of its own hazards has
to be re-solved: the cache key must be re-derived from the incoming URL, `X-Forwarded-Host` must be
set and preserved through Caddy, the origin subrequest must be kept out of the zone cache, and on
the free plan `run_worker_first` puts the SPA's own bundle behind a request ceiling.
**Why it happens:** under three apexes the SPA hostnames genuinely had no origin — `<slug>.menu.<guest-apex>`
resolved to a dummy `192.0.2.1` record whose only purpose was to make a Worker Route fire. Proxying
was not a design choice, it was the only way to reach the API same-origin. That constraint is gone.
**How to avoid:** `<apex>` and `<slug>.<apex>` are ordinary origin-backed hostnames served by Caddy.
Route `/v1/*` and `/api/*` there with `handle` blocks (Pattern 4, measured M-06). The Workers keep
only their static-asset half.
**Warning signs:** any plan step that mentions `API_ORIGIN` as a Worker `var`, `X-Forwarded-Host` set
inside a Worker, or `caches.default` in this phase.

### Pitfall 2: `cf: { cacheTtl: 0 }` does not mean "do not cache" — it forces caching

**This is a live defect in committed code** (`apps/qr-menu/worker/index.ts:53-56`,
`apps/admin/worker/index.ts:25-26`, both landed in `6ff9de4f`/`4f60a08a`), introduced as the fix for
a Round-1 blocker and never executed against the documentation.

Cloudflare's Request docs, verbatim
(`[CITED: developers.cloudflare.com/workers/runtime-apis/request/]`, fetched 2026-09-05):

> **`cacheTtl`** — *"This option **forces Cloudflare to cache the response** for this request,
> regardless of what headers are seen on the response. This is equivalent to setting two Page Rules:
> Edge Cache TTL and **Cache Level (to Cache Everything)**. The value must be zero or a positive
> number. A value of 0 indicates that the cache asset **expires immediately**."*
>
> **`cacheTtlByStatus`** — *"…The value can be any integer, including zero and negative integers. A
> value of 0 indicates that the cache asset expires immediately. **Any negative value instructs
> Cloudflare not to cache at all.**"*

So `cacheTtl: 0` is `Cache Everything` with a zero TTL — the opposite of an opt-out — and the
`cacheEverything: false` sitting beside it is contradicted by `cacheTtl`'s own documented
equivalence. The documented "do not cache" is a **negative** `cacheTtlByStatus`.

**Why this matters more than a wasted line:** the entry `cacheTtl: 0` creates is keyed on the
*tenant-blind* inner URL `https://api.<apex>/v1/menu`, and it is created **expired**, so the next
same-zone subrequest revalidates it. `public-menu.controller.ts:272,298` builds the ETag as a bare
menu-version integer, **not tenant-scoped** — two freshly published tenants both emit `"1"`. A
revalidation of tenant A's expired entry, carrying `If-None-Match: "1"`, against an origin that
resolves tenant B and is also at version 1, is answered `304 Not Modified`, and Cloudflare serves
**tenant A's body**. Every step of that chain is separately documented or separately verified in
this repo; the combination is the cross-tenant leak the `cf` option was added to prevent.

**How to avoid:** delete the proxy (Pitfall 1) and the option disappears with it. If a Worker
subrequest survives anywhere, the opt-out is
`cf: { cacheTtlByStatus: { '200-299': -1, '300-399': -1, '400-499': -1, '500-599': -1 } }`.
**Warning signs:** `cacheTtl: 0` anywhere; a `cf` object whose only assertion in tests is that it was
passed (which is what `apps/qr-menu/test/worker.spec.ts` asserts — the test is correct about the call
shape and silent about the semantics).

### Pitfall 3: Same-zone subrequests read through your own zone's cache

**What goes wrong:** a Worker on `*.<apex>` fetches `https://api.<apex>/…`. Under three apexes those
were different zones; under one apex they are the same zone, and Cloudflare's own reference is
explicit (`[CITED: developers.cloudflare.com/workers/reference/how-the-cache-works/]`):

> *"First, `fetch` checks to see if the URL matches a different zone. If it does, it reads through
> that zone's cache (or Worker). **Otherwise, it reads through its own zone's cache**, even if the
> URL is for a non-Cloudflare site."*

and, from the same-zone side (`[CITED: …/workers/configuration/routing/routes/]`):

> *"Note that Routes cannot be the target of a same-zone `fetch()` call."*

Two consequences a plan must not get backwards. **(a)** the zone cache is unavoidably in the path of
any surviving Worker subrequest — Pitfall 2 is therefore not theoretical. **(b)** a Worker's
subrequest to a same-zone hostname will *not* invoke another Worker, so there is no route loop even
without the `api.<apex>/*` negation route — the negation is documentation and future-proofing, not
the loop fix.

**The one thing that gets easier:** custom cache keys. *"You can only override cache keys when making
requests within your own zone"* (`[CITED: …/workers/examples/cache-using-fetch/]`). Under three
apexes a `cf.cacheKey` override on the cross-zone subrequest would have been ignored; under one apex
it would work. **This research does not recommend relying on it** — the plan-availability of
`cf.cacheKey` on the free plan is not stated on any page fetched in this session, and the
Cache-Rules custom-key table lists Host/Header/Query keys as Enterprise-only. Marked `[ASSUMED]`;
irrelevant if Pitfall 1's advice is taken.

### Pitfall 4: Assuming the tenant still arrives in the admin host

**What goes wrong:** a plan (or a later refactor) preserves `parseTenantSlugFromHost`, or adds a
`/admin/<slug>` path segment, or leaves `reconcileHostWithSession()` in place, on the theory that
"the tenant moved from the host to the path".
**Why it happens:** the phrase "admin tenancy moves from the host to the path" reads as a relocation.
It is not. The tenant leaves the URL entirely; `activeOrganizationId` on the Better Auth session
becomes the sole selector (Pattern 4b). D-20 already deleted the slug path segment once, in phase
10.2, and D-21 chose a host over a path specifically to avoid a per-navigation reconciliation check
in 18 route files.
**How to avoid:** delete `admin-host.ts` outright and let the type checker find the five call sites.
Grep for `VITE_ADMIN_HOST_SUFFIX` and `ADMIN_WEB_ORIGIN_WILDCARD` afterwards — both should return
nothing outside `.planning/`.
**Warning signs:** any plan step that keeps `VITE_ADMIN_HOST_SUFFIX` "for dev", or that introduces a
`$tenantSlug` route param in `apps/admin/src/routes/`.

### Pitfall 5: The VPS's raw public IP bypasses Cloudflare entirely

**What goes wrong:** Anyone who discovers the VPS's actual IP address (trivial — reverse DNS, historical DNS records, Shodan) can hit Caddy directly, bypassing Cloudflare's WAF, cache, and rate limiting, and — more subtly — can forge an `X-Forwarded-Host` header naming any tenant, which the API trusts whenever `TRUST_PROXY` is non-empty. **2026-09-05: that forgery does not require reaching the origin directly — it works through Cloudflare too. See Pitfall #11, where it is measured, and where the one-line Caddy fix is.**
**Why it happens:** Nothing about DNS or TLS prevents direct-IP access by default; Cloudflare's protections only apply to traffic that actually flows through its edge.
**How to avoid:** `ufw` on the VPS restricts inbound 80/443 to Cloudflare's published IP ranges (`https://www.cloudflare.com/ips-v4`, `/ips-v6`) in addition to the Origin CA cert (which stops *passive* eavesdropping/impersonation but not a direct connection attempt). Optionally layer Cloudflare's "Authenticated Origin Pulls" (mTLS) for a stronger guarantee — noted as a nice-to-have, not required for this phase's scope.
**Warning signs:** none observable from outside — this is a preventive hardening step, not something the go-live smoke can detect by itself.

### Pitfall 6: Copying the dev compose file's port mappings into prod

**What goes wrong:** `docker-compose.dev.yml` publishes `5432:5432` and `4222:4222`/`8222:8222` for local tooling convenience. Copying that shape into `docker-compose.prod.yml` puts a superuser-reachable Postgres and an (initially unauthenticated, if the auth flags are also missed) NATS server directly on the public internet.
**Why it happens:** Compose file reuse is exactly the right instinct for everything *except* `ports:` — it's the one section that must diverge completely.
**How to avoid:** Explicit review checklist item: `docker-compose.prod.yml` must have zero `ports:` entries outside the `caddy` service.
**Warning signs:** `docker compose config` on the prod file, grep for `ports:` — the only match should be under `caddy`.

### Pitfall 7: `docker compose down -v` in any automated path

**What goes wrong:** `-v` destroys the named volumes — `postgres-data` included. A single misplaced `-v` in a deploy script is a full data-loss incident with no warning.
**Why it happens:** `docker compose down` (safe) and `docker compose down -v` (destructive) look nearly identical and are easy to conflate, especially when copy-pasting from a "reset my dev environment" habit (`pnpm dev:reset` in this repo's own dev workflow *does* use `-v`, by design, for dev).
**How to avoid:** The CD pipeline never calls `docker compose down` at all (Pattern 1/6 use targeted `up -d --no-deps <service>` instead); grep the committed workflow files for `-v` near `docker compose` as a review gate.
**Warning signs:** any `docker compose down` appearing anywhere in `.github/workflows/deploy.yml` or `infra/scripts/` should be treated as a red flag during plan review, `-v` or not.

### Pitfall 8: Trusting `migrate.ts`'s fallback as a hard gate

**What goes wrong:** A plan assumes (as the AWS-era plan 09 did) that `migrate.ts` refuses to run without `DATABASE_ADMIN_URL` in non-dev. It does not — it warns and falls back to `DATABASE_URL`. If the CD workflow's `DATABASE_ADMIN_URL` secret is ever missing/misnamed, migrations silently attempt to run under the lower-privileged app role instead of failing closed, and fail with a confusing permission error rather than a clear "you forgot the admin URL" message.
**Why it happens:** The current file (verified 2026-09-04) genuinely only warns; this may have been true at an earlier point in the codebase's history or may simply have been an inaccurate assumption in the original plan.
**How to avoid:** The CD workflow (Pattern 6) must always pass `DATABASE_ADMIN_URL` explicitly and treat its absence as a workflow-level configuration error (fail the job before even attempting the SSH step) rather than relying on the script itself to refuse.
**Warning signs:** a migration step that "succeeds" suspiciously fast, or fails with a Postgres permission-denied error rather than a clean "DATABASE_ADMIN_URL is required" log line.

### Pitfall 9: Website's SSR calls hairpin through the public internet even on the same box

**What goes wrong (not a bug, a documented tradeoff):** `NEXT_PUBLIC_API_ORIGIN` is baked at build time to the public `https://api.<apex>` and used for both server-side (SSR) and client-side fetches (`apps/website/lib/env.ts`/`checkout-api.ts`). Even though `website` and `api` run on the *same* VPS in the *same* Compose network, website's SSR calls leave the box, round-trip through Cloudflare's edge, and come back — adding real (if small) latency to every server-rendered page, purely because one env var serves both contexts.
**Why it happens:** Splitting an "internal" SSR-only origin (`http://api:3000`, the Compose service DNS name) from the "public" client-side origin would require a second env var and a code change to `checkout-api.ts`/wherever SSR fetches happen — out of scope for this deploy phase, which should not touch application code.
**How to avoid (or rather, accept for now):** Ship as-is for the initial go-live — it is correct, just not maximally efficient. Document as a known, deliberate future optimization (an `API_INTERNAL_ORIGIN` env var for SSR-only calls) rather than something this phase's plans need to fix.
**Warning signs:** none that block go-live; revisit only if SSR latency becomes a measured problem.
**2026-09-05 update — this is no longer only a latency question.** The same SSR call is what forces `{$API_HOST}` to keep accepting an inbound `X-Forwarded-Host`, which is the header Pitfall #11 shows is client-forgeable. Adding a server-only `API_INTERNAL_ORIGIN=http://api:3000` closes both at once: the hairpin disappears *and* the header stops crossing the public internet. Recommendation changed from "accept for now" to **"do it, in the same plan as the Caddy header pin."**


### Pitfall 10: `assertProdGuardrails` requires real Stripe/Resend credentials to boot at all

**What goes wrong:** `apps/api/src/config/prod-guardrails.ts` refuses to boot in `NODE_ENV=production`/`staging` without a real (non-placeholder) `STRIPE_SECRET_KEY` and `RESEND_API_KEY` — this is unconditional, independent of whether Phase 8 (Payments) is "in scope" for this deploy phase's stated goal. Since Phase 8/8.1 are already complete in this codebase (per `.planning/ROADMAP.md`, both marked "Complete" 2026-06-27/28), this is not a surprise gap to fill — it *is* already-shipped code that this deploy phase must simply satisfy — but a plan that treats "Stripe is Phase 8, not my problem" literally will find the api container refuses to start at all, at the very first go-live smoke attempt, with no partial-success state to debug from.
**Why it happens:** `assertProdGuardrails` was hardened after this deploy phase's CONTEXT.md was first written (2026-06-21/26) but before this research (2026-09-04) — the phase boundary language predates code that now cuts across it.
**How to avoid:** Gather real Stripe (test-mode keys are acceptable for an initial go-live — `assertProdGuardrails` only rejects the *documented placeholder literal*, not test-mode keys generally) and Resend credentials as part of the "founder must provide" checklist (below), before plan 08/the go-live smoke, not after.
**Warning signs:** the `api` container exits immediately on boot with a `ProdGuardrailsError` listing `STRIPE_SECRET_KEY`/`RESEND_API_KEY` — this is the exact, unambiguous failure signature; do not spend time debugging Docker networking or Postgres connectivity first.

### Pitfall 11 (NEW, and it is a defect in already-committed code): `X-Forwarded-Host` is client-forgeable today

**Measured, not reasoned** (M-07). Caddy 2.11-alpine, with exactly the committed
`infra/docker/Caddyfile`'s `trusted_proxies static 0.0.0.0/0 ::/0`:

```
$ curl -H 'Host: pizza.example.invalid' \
       -H 'X-Forwarded-Host: evil.attacker.invalid' http://127.0.0.1:8080/v1/menu
{"who":"api","host":"pizza.example.invalid","xfh":"evil.attacker.invalid",...}
```

The forged value reaches the upstream verbatim. `effectiveHost()`
(`apps/api/src/shared/effective-host.ts:13-18`) honours `x-forwarded-host` whenever `TRUST_PROXY` is
non-empty — which it always is in production, by schema requirement. Cloudflare does not strip
`X-Forwarded-Host`; it manages `X-Forwarded-For` and `CF-Connecting-IP` and forwards everything else.
So **any client that can reach the origin through Cloudflare can name any tenant host.**

This is not introduced by the new scheme — it exists in the committed Caddyfile now, and four review
rounds did not catch it, because `trusted_proxies static 0.0.0.0/0` was introduced deliberately (to
fix blocker M2, "Caddy discards `X-Forwarded-Host`") and its side effect on *inbound* forgery was
only ever analysed for `client_ip`, never for the host.

**What it is worth to an attacker, stated honestly rather than dramatically:** on `/v1/menu` the
data is public anyway. On the operator path `AuthGuard`'s cross-check rejects a forged tenant with
`auth.tenant_mismatch` — *unless* the session has no `activeOrganizationId`, in which case the check
is skipped by its own guard clause (Pattern 4b). On `/v1/orders` it means a guest can place an order
against a tenant they are not browsing. The set of routes carrying `@RequiresTenantContext` without
`@Permissions` has never been enumerated, so the residual blast radius is **unknown**, and that is
the finding: not "this is catastrophic", but "nobody can currently say it isn't."

**The fix, measured working (M-08):** `header_up X-Forwarded-Host {host}` on the
`{$WEBSITE_HOST}, *.{$WEBSITE_HOST}` reverse_proxy blocks. Verified against both a single forged
header and the comma-joined two-value shape; the `/internal*` `client_ip` gate was unaffected.

**Two callers must be dealt with before the pin can also be applied to `{$API_HOST}`**, and both are
worth doing in the same plan:

1. `apps/website/lib/api-client.ts:22-25` — SSR sends `x-forwarded-host: <the request's own Host>` to
   `https://api.<apex>`, hairpinning out through Cloudflare and back (the phase's own Pitfall #9).
   Give the website an `API_INTERNAL_ORIGIN` (server-only, defaults to `NEXT_PUBLIC_API_ORIGIN`) of
   `http://api:3000` so the call never leaves the Compose network. This closes Pitfall #9 *and*
   removes the header from the public path — the latency win was the parked reason, the security
   property is the real one.
2. `apps/website/lib/checkout-api.ts:73-81` — the **browser** sends
   `x-forwarded-host: window.location.host` cross-origin to `api.<apex>` on `/v1/orders`,
   `/v1/checkout/payment-intent` and order-status reads. That is a client-controlled tenant selector
   on the order-creation path, in production, today. Under one apex the fix is the D-39 move applied
   to the third surface: make these calls **same-origin relative paths** (`/v1/orders` on
   `<slug>.<apex>`, which Caddy already routes), delete the header, and `NEXT_PUBLIC_API_ORIGIN`
   stops being needed by the client at all.

With both done, `header_up X-Forwarded-Host {host}` can go on every block, no browser and no
container sets the header, and the tenant becomes a function of the URL the user actually visited.
**If the planner descopes (2), say so explicitly and leave `{$API_HOST}` unpinned** — do not pin it
and discover at the go-live smoke that guest checkout 404s.

### Pitfall 12 (NEW): the storefront and the QR menu now share an origin, and a `sessionStorage` cart

`packages/cart/src/cart.ts:150-152` persists the whole store under the key `resto-cart` in
`sessionStorage`, with no `partialize`. `sessionStorage` is per-origin. Under three apexes
`<slug>.<guest-apex>` (QR menu) and `<slug>.<public-apex>` (storefront) were different registrable
domains and therefore different stores; under one apex they are the **same origin** and share one
cart — items, `mode`, and `tableId`/`tableZoneName`/`tableNumber`.

Not a security issue (`apps/website/components/checkout/checkout-form.tsx:44-45` reads only `mode`
and `items`, never `tableId`), but a real behaviour change: a guest who builds a cart on the
storefront and then scans a code at the table sees the home cart, and vice versa; a table set at
`/qr` persists into a storefront delivery order's state. Decide it deliberately rather than discover
it — either give the two apps distinct persist keys (`resto-cart` / `resto-cart-qr`, one line each)
or declare the sharing a feature and add a test that pins it. The `resto.table` cookie is unaffected:
`apps/api/src/shared/table-session.ts:24-35` sets it `Path=/`, `HttpOnly`, host-only, so it is
correctly scoped and unreadable by either app's JavaScript.

### Plan 07 — the tenant-keyed cache logic does **not** survive, and that is the right outcome

The tenant **is** still in the host. That is precisely why the hand-rolled cache is no longer needed:
with `<slug>.<apex>/v1/menu` served by Caddy, the Cloudflare **zone** cache keys on the full request

has.

## Where the admin path-tenancy work belongs

**Recommendation: its own small phase, numbered ahead of the remaining deploy plans — not a plan
inside 7.5.**

The founder's note left this open. Three arguments, in order of weight:

1. **It is application code with a security-relevant trust boundary, and 7.5 is a deployment phase.**
   Every other plan in 7.5 changes infrastructure, configuration or CI. This one changes which input
   the server trusts to select a tenant, plus a two-line hardening of `AuthGuard`'s membership check
   (Pattern 4b). Phase 7.5's own CONTEXT and its four review rounds are calibrated for deployment
   risk — "does the box come up", "does the cert cover the host". They are not calibrated to review
   a tenancy change, and the reviewers said as much when they observed that the three defects each
   round found clustered in whichever subsystem the plans treated as incidental.
2. **It is a prerequisite for plans 08-10, not a peer of them.** Plan 08 stands up the box and runs
   `verify-prod-origin.sh --stage full`; that script's mandatory tenant assertion cannot pass until
   the admin and the API agree on where the tenant comes from. Anything that must be *finished*
   before the next plan starts is a phase boundary, not a wave inside one.
3. **It has its own rollback story and its own blast radius.** If the path move is wrong, the fix is
   a revert of a frontend/API commit with no infrastructure implication. Entangling it with the box
   bring-up means a single bad go-live has two unrelated suspects.

**Proposed shape — phase 7.4 (or 07.5.5 if numbering must stay contiguous), four waves, one plan
each, ~1 day:**

| Wave | Content |
|---|---|
| 1 | `AuthGuard` membership tightening (drop the `principal.tenantId &&` clause) + tests. Independently correct, ships even if the rest slips |
| 2 | Delete `admin-host.ts` / `VITE_ADMIN_HOST_SUFFIX` / `reconcileHostWithSession`; add `basepath`, `base`, `outDir`; rewrite the six call sites; `switch-tenant.ts` + the ESLint rule + the cache test (Pattern 4c) |
| 3 | Env collapse: delete `GUEST_APEX_DOMAIN` / `ADMIN_WEB_ORIGIN_WILDCARD`; `AUTH_COOKIE_DOMAIN` unset + schema change; `ADMIN_WEB_URL` origin-vs-path split (M-12); `guest-menu-url.service.ts` `/qr` suffix; `.env.example` and the e2e fixtures |
| 4 | qr-menu `/qr` base path: route regexes, `pushState`/`replaceState` targets, `wrangler.jsonc`, the `index.html` copy, and a test that `/qr/t/<token>` still parses the token |

Waves 2 and 4 are file-disjoint and can run in parallel. Then 7.5 plans 08-10 are re-planned against
a settled URL scheme, and the only Cloudflare work left in them is DNS records, two Worker routes,
one negation route, one Cache Rule and the Origin CA certificate — all founder-console actions with
a `verify-prod-origin.sh` assertion behind each.

**The counter-argument, stated fairly:** the change is genuinely small (roughly 8 files in `apps/admin`,
4 in `apps/api`, 6 test files) and a new phase carries its own overhead — a CONTEXT, a research pass,
a verification round. If the founder prefers to keep it inside 7.5, the workable compromise is a
single plan `07.5-07.5` executed *before* 08, with its own verification round scoped to tenancy
rather than deployment. What must **not** happen is folding it into plan 08 as a task: that is how a
tenancy change gets reviewed by a checklist written for a Docker host.

## Open Questions

1. **Exact VPS size: CX32 vs CX22** — unchanged from 2026-09-04. CX32 (4 vCPU/8 GB, ~€6.80/mo) leaves
   headroom for 5 containers; CX22 is ~€3/mo cheaper and tighter. Recommendation: CX32, resize down
   later if measurement says so.

2. **Backup cadence: nightly vs 6-hourly** — unchanged. Recommendation: nightly first, documented as
   a one-line cron change.

3. **`Authenticated Origin Pulls` (mTLS) on top of the IP-range firewall** — unchanged.
   Recommendation: skip for the initial go-live. **Note it interacts with Pitfall #11:** if the
   `X-Forwarded-Host` pin is descoped, mTLS becomes the fallback control that stops a non-Cloudflare
   client reaching Caddy at all, and its priority rises accordingly.

4. **NEW — the marketing landing does not exist.** The founder's map assigns `<apex>` to a marketing
   landing. `apps/website/app/page.tsx` is a **tenant storefront**: it calls `fetchMenuPublic()`,
   resolves the tenant from the `Host`, and at the bare apex throws `TenantNotFoundError` → `notFound()`
   → "Restaurant not found". There is no marketing route, no locale-prefixed route tree, and no
   `app/api` route.
   - What we know: the apex will serve a 404 page at go-live unless something is done, on the same
     domain that appears in every invitation and password-reset email.
   - What's unclear: whether the founder wants a real landing page now (a content/design task well
     outside a deploy phase) or a placeholder.
   - **Recommendation:** ship a deliberate placeholder — a static `apps/website/app/(marketing)/page.tsx`
     rendered only when the host equals `PUBLIC_APEX_DOMAIN`, or a Caddy `redir / /admin/` on the exact
     apex host with the tenant path untouched. Decide it in the phase's CONTEXT, not at the smoke.
     Do **not** let the default "Restaurant not found" stand: it is the first thing a prospect sees.

5. **NEW — `WEBSITE_PUBLIC_URL` is apex-scoped but the storefront is per-tenant.**
   `send-guest-notification.service.ts:117-118` builds the guest order-confirmation link as
   `${WEBSITE_PUBLIC_URL}/checkout/confirmation/${orderId}`. On a single apex that is
   `https://<apex>/checkout/confirmation/…` — a URL that resolves no tenant and renders the same
   404 as Open Question 4. It should be `https://<slug>.<apex>/checkout/confirmation/…`, composed
   from the order's tenant.
   - Recommendation: fold into the same plan as `guest-menu-url.service.ts`'s `/qr` suffix — both are
     "compose a guest URL from the tenant and the apex", and there should be one helper doing it.
     Pre-existing (the three-apex map had the same bug); newly visible because the map is now simple
     enough to notice it.

6. **NEW — the residual blast radius of Pitfall #11 is unmeasured.** Nobody has enumerated the routes
   carrying `@RequiresTenantContext` without `@Permissions`, which is the set an attacker could reach
   with a forged host on a session with no `activeOrganizationId`.
   - Recommendation: a 20-minute grep-and-tabulate as a task in the tenancy phase's wave 1, alongside
     the `AuthGuard` tightening that closes the hole regardless. Do the fix even if the table comes
     back empty; an empty table today is not an invariant.

7. **NEW — `.pp.ua` as the production apex.** It works (M-01…M-05) and it is free. Two things it is
   not: memorable to a restaurant owner, and neutral in a customer's address bar. This is a
   go-to-market question, not a technical one, and the technical work is apex-parameterised
   throughout — swapping the apex later is an env change plus DNS, not a re-plan.
   - Recommendation: proceed on `restos.pp.ua` for go-live; treat a paid apex as a marketing decision
     with a known, cheap migration path. Say so in the CONTEXT so it is a decision rather than a drift.

|---|---|---|
