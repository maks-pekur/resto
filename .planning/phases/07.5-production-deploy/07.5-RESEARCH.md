## Summary

**The decisive finding of this research is that Neon's BYPASSRLS support for non-`neon_superuser` custom roles is unverified and likely blocked in their managed environment.** The `neondb_owner` / roles created via the Neon Console inherit `neon_superuser` (which has BYPASSRLS), but the ability to delegate `BYPASSRLS` via `ALTER ROLE custom_role BYPASSRLS` from that role is not documented as permitted by Neon's managed platform. Because `packages/db/src/auth-role.ts` provisions `resto_auth` with explicit `BYPASSRLS` via `CREATE ROLE resto_auth WITH LOGIN NOSUPERUSER BYPASSRLS` — and `assertRoleAttributes` then verifies the attribute actually landed — a failure here produces a hard boot rejection. This cannot be bypassed. The plan MUST include a mandatory "Neon BYPASSRLS spike" task (15-minute psql test, details below) before any Neon plan tasks are scheduled; if the spike fails, the plan pivots to AWS RDS. Both paths are fully specced in this document.

AWS Copilot CLI — previously considered the "minimal ECS tool" — reached end-of-support on **June 12, 2026** (already past). The recommended replacement is **AWS CDK L3 constructs** (`aws-ecs-patterns.ApplicationLoadBalancedFargateService`) or the new **Amazon ECS Express Mode** (`aws-actions/amazon-ecs-deploy-express-service` GitHub Action). Either satisfies D-03 and is the established AWS-native path forward.

NATS JetStream on ECS Fargate with EFS is **explicitly not recommended by Synadia** (the NATS authors): EFS latency and consistency properties are unsuited for a durable messaging store. The resolution is to run the single NATS node on a small EC2 instance with an EBS volume — still one node, but correct storage — rather than as a Fargate task.

**Primary recommendation:** Spike Neon BYPASSRLS first (30 min). If viable: Neon (pooled + direct) + ECS Fargate (ECS Express Mode) + NATS on EC2/EBS + R2 + Cloudflare + GitHub Actions with `amazon-ecs-deploy-express-service`. If Neon BYPASSRLS fails: swap to RDS PostgreSQL 16 where `rds_superuser` can delegate BYPASSRLS. Everything else in the stack is identical.

## D-04 HARD GATE: Neon 3-Role + BYPASSRLS Feasibility

### What the codebase requires (confirmed from source)

The 3-role model in `packages/db/src/`:

1. **`resto_app`** — `NOSUPERUSER NOBYPASSRLS LOGIN`; runtime app role (`DATABASE_URL`). Created by `provisionAppRole()` in `roles.ts` with `ALTER ROLE resto_app WITH LOGIN NOSUPERUSER NOBYPASSRLS`. Verified by `assertRoleAttributes(..., { rolbypassrls: false })`.

2. **`resto_auth`** — `NOSUPERUSER BYPASSRLS LOGIN`; Better Auth's drizzle client (`BETTER_AUTH_DATABASE_URL`). Created by `provisionAuthRole()` in `auth-role.ts` with `CREATE ROLE resto_auth WITH LOGIN NOSUPERUSER BYPASSRLS`. Verified by `assertRoleAttributes(..., { rolbypassrls: true })`. This is the role that must have BYPASSRLS.

3. **Admin/migration role** — the connection used to call `provisionAppRole` and `provisionAuthRole` must have CREATEROLE + DDL privileges. On Neon this is `neondb_owner` (`DATABASE_ADMIN_URL`); on RDS this is the `postgres` master user.

Required extensions (from `01-extensions.sql`): `pgcrypto`, `citext`, `pg_trgm`.

Boot preflight assertions that hard-fail if wrong (from `main.ts` — 8 total, not "six" as mentioned in CONTEXT):

1. `assertNoRlsBypass(DATABASE_URL)` — `resto_app` NOBYPASSRLS, NOSUPERUSER
2. `assertTenantLockInstalled(DATABASE_URL)` — `app_bind_tenant` GUC wrapper exists (migration 0022+)
3. `assertSetConfigRevoked(DATABASE_URL)` — `set_config` revoked from `resto_app`
4. `assertNoBaCredentialAccess(DATABASE_URL)` — `resto_app` cannot read auth credential tables
5. `assertInboxProcessedDeletable(DATABASE_URL)` — `resto_app` has DELETE on `inbox_processed`
6. `assertWithoutTenantCallsiteRegistered()` — allowlist entries point to existing source files
7. `assertSystemRolesPresent()` — BA org plugin access-control map matches SYSTEM_ROLES
8. `assertProdGuardrails(env)` — dev defaults / placeholder secrets rejected in non-dev (with email adapter name check at step 2 of the double call)

### Neon capabilities (researched)

- Extensions `pgcrypto`, `citext`, `pg_trgm` are all available on Neon [VERIFIED: neon.com/docs/extensions/pg-extensions]
- `neondb_owner` (and roles created via Console/CLI/API) hold `neon_superuser` membership, which includes `BYPASSRLS`, `CREATEDB`, and `CREATEROLE` [CITED: neon.com/docs/manage/roles]
- Roles created **via SQL** from a `neon_superuser` member start with standard Postgres defaults (no inherited `neon_superuser`)
- **THE UNRESOLVED QUESTION:** Can a `neon_superuser` member (`neondb_owner`) issue `ALTER ROLE resto_auth BYPASSRLS`? In standard Postgres 16, only roles with BYPASSRLS can grant BYPASSRLS to others. `neondb_owner` has BYPASSRLS. But Neon's managed layer may intercept this DDL. Neon docs do NOT explicitly state this is permitted or blocked. [ASSUMED — cannot be confirmed without a live psql test]
- What IS documented as blocked on Neon: "Altering the `neon_superuser` role itself is not permitted." This is about the role as an object, not about delegating attributes.

**Research verdict: [ASSUMED] Neon BYPASSRLS delegation is PLAUSIBLE but UNVERIFIED. Probability ~60% based on Postgres 16 semantics; Neon may not have blocked this. Cannot confirm without a live test.**

### Mandatory spike (Wave 0 — must complete before any provider-specific tasks)


Decision tree:

- **Success:** Proceed with Neon path. `DATABASE_URL` = Neon pooled; `DATABASE_DIRECT_URL` = Neon direct (unpooled); `DATABASE_ADMIN_URL` = neondb_owner.
- **Failure:** Pivot to RDS Postgres 16. Spike takes 15 minutes. Do it first.

1. Create Neon project; get `neondb_owner` connection string → `DATABASE_ADMIN_URL`

## D-05: Neon Pooled vs Direct Connection Wiring

### The problem (confirmed from code)

`OutboxDispatcherService.tryAcquireLeadership()` at line 85:

```typescript
reserved = await this.db.connection.raw.reserve();
await reserved`SELECT pg_try_advisory_lock(${ADVISORY_LOCK_KEY}) AS got`;
```

`postgres.js` `.reserve()` acquires a single dedicated connection from the pool. `pg_try_advisory_lock` is a **session-level** lock — it persists as long as the physical backend connection lives.

Neon's pooler runs PgBouncer in **transaction mode**: each transaction may land on a different backend. A session-level lock acquired on backend A may be on a backend that PgBouncer returns to the pool after the lock query finishes. Next time the `reserved` connection is used, it may be a different backend — and the advisory lock is gone from that connection's session.

**Conclusion:** The outbox dispatcher MUST use a direct (non-pooled) connection. [VERIFIED from code: `outbox-dispatcher.service.ts:85-89`]

### Required changes

1. Add `DATABASE_DIRECT_URL` to `env.schema.ts`:

   ```typescript
   DATABASE_DIRECT_URL: z.string().url().optional(),
   // superRefine: required outside dev when DATABASE_URL is a pooled URL
   ```

2. `OutboxDispatcherModule` creates a second `postgres()` client from `DATABASE_DIRECT_URL` and injects it into `OutboxDispatcherService` separately from the shared `TenantAwareDb`. The dispatcher uses this client's `.reserve()` for the lock; tick queries go through the regular `TenantAwareDb` (which can use the pooled connection for scan).

   This is the safer option: the lock-holding connection is isolated. The `leaderConn` stays pinned for the lifetime of leadership.

3. On RDS (fallback): `DATABASE_DIRECT_URL` = same as `DATABASE_URL` (no pooler). Both `postgres()` clients point to the same RDS endpoint. The `reserve()` call on the direct client pins one physical connection (max: 1 for that client), which is fine.

## G-01: Docker Production Boot Bug

### Root cause (confirmed from Dockerfile + build.mjs + roles.ts)

`build.mjs` produces `apps/api/dist/main.cjs`. When esbuild bundles `@resto/db` inline (workspace packages are NOT external), it processes `packages/db/src/roles.ts:7`:

```typescript
const GRANTS_SQL_PATH = resolve(import.meta.dirname, '..', 'sql', 'roles.sql');
```

esbuild converts `import.meta.dirname` → `__dirname` in CJS output. In the bundled file, `__dirname` = `/app/apps/api/dist/`. The resolved path becomes:

```
/app/apps/api/dist/../sql/roles.sql
= /app/apps/api/sql/roles.sql   ← DOES NOT EXIST
```

The actual file is at `/app/packages/db/sql/roles.sql` (copied by the Dockerfile's `COPY --from=build /workspace/packages ./packages`).

The same issue affects `packages/db/src/auth-role.ts:7` (`auth-role.sql`).

`openapi.ts` does NOT use `import.meta.dirname` for file reads at runtime — its `emitOpenApi` function is only called from the CLI emit script, not from `main.ts` boot. So openapi.ts is not a boot blocker.

### Fix (recommended)

Use esbuild's `loader` option to inline the SQL files as strings at build time, eliminating the runtime file path dependency:

In `build.mjs`, add to the `build()` call:

```js
loader: { '.sql': 'text' }
```

In `packages/db/src/roles.ts` and `auth-role.ts`, change from:

```typescript
// Before (runtime file read — broken in bundle)
const GRANTS_SQL_PATH = resolve(import.meta.dirname, '..', 'sql', 'roles.sql');
// ...used as: readFileSync(GRANTS_SQL_PATH, 'utf8')
```

to:

```typescript
// After (build-time string inline — works in bundle)
import GRANTS_SQL from '../sql/roles.sql';
// ...used as: await client.unsafe(GRANTS_SQL)
```

esbuild's text loader inlines the file content as a JS string at build time. No runtime file system dependency. No path math.

[ASSUMED: esbuild text loader syntax; based on training data. Must verify against current esbuild docs before implementing.]

## D-06: NATS JetStream on EC2 + EBS

### Recommendation (confirmed from Synadia docs)

Run NATS as a single node on **EC2 t3.micro** (or `t4g.micro` ARM for ~10% lower cost) with an **EBS gp3 volume** (20GB, 3000 IOPS). [CITED: synadia.com/blog/running-nats-on-aws-ec2-ebs-fargate-efs]

Fargate + EFS is explicitly not recommended by Synadia for JetStream. EFS NFS has latency and file-handle consistency issues that cause JetStream stream corruption (nats-io/nats-server#2792). EBS is block storage — appropriate for a durable message store.

### Setup

1. Launch EC2 in same VPC as ECS cluster (same AZ for lowest latency)
2. Attach EBS gp3 volume at `/data/nats` — format on first boot, persist across EC2 restarts
3. Install NATS server binary as a systemd service (single binary, no Docker needed):
   ```ini
   [Unit]
   Description=NATS Server
   [Service]
   ExecStart=/usr/local/bin/nats-server -c /etc/nats/nats.conf
   Restart=always
   [Install]
   WantedBy=multi-user.target
   ```
4. `nats.conf`:
   ```
   port: 4222
   http_port: 8222
   jetstream {
     store_dir: /data/nats
   }
   authorization {
     user: nats_user
     password: $NATS_PASSWORD
   }
   ```
5. Security group: inbound 4222 from VPC CIDR only; 8222 (monitoring) from VPC CIDR only
6. Store EC2 private IP in SSM Parameter Store `/restos/prod/NATS_URL` → `nats://nats_user:password@<private-ip>:4222`

### Outbox decoupling confirmed

`OutboxDispatcherService.onApplicationBootstrap()` checks `if (this.publisher === null) return` — when NATS is down at boot, the publisher is null, the dispatcher logs a warn and does not start. No crash. [VERIFIED from code: `outbox-dispatcher.service.ts:60-65`]

The transactional outbox (Postgres `outbox_events` table) accumulates events while NATS is unavailable. Order creation still completes normally. When NATS recovers, the dispatcher retries acquisition and drains the backlog. This is the intended degraded-mode behavior.

### NATS `max_deliver` / DLQ gap

CONCERNS.md confirms NATS consumers still lack `max_deliver` and dead-letter configuration. The plan must include a task to add `max_deliver: 5` and `dead_letter: 'dlq.<subject>'` to `packages/events/src/infrastructure/nats-subscriber.ts` consumer config. Without it, one malformed envelope stalls the audit consumer indefinitely (poison-message SPOF). [VERIFIED: CONCERNS.md — NATS consumer missing max_deliver and DLQ config]

## G-03: Outbox-Stall Detector (Minimal Pull-Forward)

Current `/readyz` checks: `database` (ping) + `broker` (null publisher check — not actual connection test).

The `checkBroker()` method at `health.controller.ts:74-82` returns `ok: true` if `this.publisher !== null` — meaning it returns ok if NATS connected at boot, even if the broker went down later. This is a known gap.

**Minimal addition for 7.5 (G-03):**

Add a third health check: `outbox_leader`. `OutboxDispatcherService` exposes `isLeader(): boolean` returning `this.leaderConn !== null`. The readiness check:

```typescript
private checkOutboxLeader(): CheckResult {
  const isLeader = this.outboxDispatcherService.isLeader();
  // ok if this instance holds the lock, or if NATS is disabled (publisher null = dev/test mode)
  const ok = isLeader || this.publisher === null;
  return { name: 'outbox_leader', ok, detail: ok ? undefined : 'no instance holds the outbox leader lock' };
}
```

Why this helps: If all replicas lose the advisory lock (e.g., Postgres briefly went away and connections dropped), `/readyz` returns `503` → ALB marks all tasks unhealthy → ECS replaces them → new tasks retry lock acquisition within 5 seconds. Without this check, the silent outbox stall is invisible until a customer reports a missing confirmation email.

This is not the full dispatch-lag gauge (Phase 8 SC#5). The dispatch-lag OTel gauge (`outbox.is_leader` gauge + >30s since last dispatch → not-ready) stays in Phase 8.

## Common Pitfalls

### Pitfall 1: PgBouncer kills advisory lock (D-05)

**What goes wrong:** Outbox dispatcher acquires `pg_try_advisory_lock` on connection A; PgBouncer returns A to pool; next query from the same client gets connection B; advisory lock is gone.
**How to avoid:** `DATABASE_DIRECT_URL` → unpooled Neon endpoint or direct RDS endpoint; used exclusively by `OutboxDispatcherService`.
**Warning signs:** Outbox stalls silently; `/readyz` outbox_leader check returns false.

### Pitfall 2: `import.meta.dirname` resolves to `dist/` not `packages/`

**What goes wrong:** `__dirname` in bundled CJS = `/app/apps/api/dist/`; `resolve(__dirname, '..', 'sql', 'roles.sql')` = `/app/apps/api/sql/roles.sql` — does not exist → `readFileSync` throws → API crashes before preflights.
**How to avoid:** esbuild text loader inlines SQL at build time, eliminating runtime file reads.
**Warning signs:** Container exits non-zero immediately; `Error: ENOENT: no such file or directory, open '/app/apps/api/sql/roles.sql'`

### Pitfall 3: NATS JetStream on Fargate + EFS

**What goes wrong:** EFS NFS file handle staleness causes JetStream stream corruption; messages lost.
**How to avoid:** EC2 t3.micro + EBS gp3 for NATS. Not Fargate + EFS.

### Pitfall 4: Cloudflare SSL mode "Flexible"

**What goes wrong:** CF sends HTTP to the ALB; ALB HTTPS listener rejects it; 502/504 from CF.
**How to avoid:** CF SSL mode = "Full (strict)"; ALB has ACM cert.

### Pitfall 5: `TRUST_PROXY=true` in prod

**What goes wrong:** `env.schema.ts` superRefine rejects `TRUST_PROXY=true` in non-dev; boot fails.
**How to avoid:** Use `TRUST_PROXY=1` (one hop) or ALB CIDR.

### Pitfall 6: New image rolls before migration completes

**What goes wrong:** ECS rolls new image before `pnpm db:migrate` exits; `assertTenantLockInstalled` fires (or new columns missing) → boot fails.
**How to avoid:** Migration ECS task runs as a gated step BEFORE deploy; CD waits for exit code 0. The preflight is also a safety net.

### Pitfall 7: `AUDIT_ERASURE_SALT` treated as rotatable

**What goes wrong:** Rotating the salt after first paying tenant's GDPR erasure makes historical anonymized IDs non-linkable to future anonymized IDs.
**How to avoid:** Generate once, document as immutable, never rotate.

### Pitfall 8: NATS `max_deliver` not set → poison-message stall

**What goes wrong:** A malformed envelope NAK-loops indefinitely, blocking all events on that consumer. Audit trail halts; email dispatch halts.
**How to avoid:** Configure `max_deliver: 5` + `dead_letter: 'dlq.<subject>'` in `nats-subscriber.ts`.
