# Phase 7.5 Production Deploy — CTO Review (discuss-phase, pre-plan)

## TL;DR
- **Recommended default stack: Fly.io (api + Next apps) + Neon (3-role Postgres, RLS) + Cloudflare R2 (storage) + a single self-hosted NATS JetStream node on a Fly volume.** It is the only option that satisfies all four locked constraints at once: scale-to-near-zero cost, a stable long-running process for the advisory-lock leader, Docker-native deploy, and wildcard + custom-domain TLS without a separate edge layer.
- **The non-negotiable architectural fact driving this phase is the outbox leader.** `OutboxDispatcherService` elects via `pg_try_advisory_lock(4815115)` on a *reserved* Postgres connection (`outbox-dispatcher.service.ts:88`). This rules out any platform that scale-to-zeros the API to 0 replicas (Railway/Render/Cloud Run idle-stop), because with no live process the outbox never drains — paid-order and email events silently queue. The api must keep **≥1 always-on instance**.
- **Two latent BLOCKERs sit in the code today, not in the infra choice**: (1) the Docker production bundle has a known `import.meta.dirname`-undefined-in-CJS bug (`ci.yml:176`, `packages/db/src/roles.ts`, `auth-role.ts`, `apps/api/src/openapi.ts`) that the CI deliberately does *not* catch because the docker job was removed; (2) NATS consumers still ship without `max_deliver`/DLQ (`CONCERNS.md` — flagged, Phase 3 was supposed to close it). Both must be verified green before a public URL exists, or the first webhook will land on a broken process.

## Hosting platform — assessment

The decisive requirement is the leader-elected outbox. It is a single long-lived process holding a session advisory lock; if its connection dies the lock auto-releases and another replica's 5s retry loop (`ACQUIRE_RETRY_MS = 5000`) takes over (`outbox-dispatcher.service.ts:20,81-109`). This is correct and cheap — but it means the platform must guarantee at least one warm instance and must not "pause" a process while keeping its DB connection alive (a zombie that holds the lock but stops ticking is the worst case; only the DB connection dying frees it).

| Platform | Fit | Verdict |
|---|---|---|
| **Fly.io** | Stable Firecracker VMs, `min_machines_running=1`, Docker-native, **per-app wildcard + custom-domain certs built in**, internal NATS over private 6PN networking, volumes for NATS persistence. SSR Next apps deploy as separate Fly apps. | **DEFAULT.** Best leader fit + cheapest path to wildcard TLS. |
| **Railway** | Great DX, Docker-native, but **idle-stops** services by default and wildcard/custom-domain TLS is weaker. Idle-stop + advisory-lock leader = silent outbox stall. | Acceptable only with sleep disabled; loses its cost edge then. |
| **Render** | Solid, stable instances, native Postgres. But background-worker model nudges you to split the dispatcher out (the code runs it *in-process*), and wildcard custom domains are fiddlier. | Viable runner-up; more config for `*.menu.resto.app`. |
| **AWS ECS/Fargate** | Matches the old ADR-0011 "AWS/EKS" intent and scales furthest. But it is the **highest ops surface for a solo founder** — ALB + ACM wildcard + Route53 + Secrets Manager + task defs + a migration task. Weeks of yak-shaving for one customer. | **Defer.** This is the org-of-50 answer; revisit at MVP-2 scale, not now. The ROADMAP already says "Fly/Railway/ECS — not full k8s" — honor that. |

**[MEDIUM] The repo still encodes the abandoned AWS/EKS direction** (`infra/CLAUDE.md`, `STACK.md:132`, ADR-0011 references, `terraform/` for "EKS, RDS, ElastiCache"). Phase 7.5 must explicitly supersede ADR-0011, or the next engineer (or you in 6 months) builds the wrong thing. Write the decision down.

## NATS JetStream in prod — [HIGH]
The outbox dispatcher and inbox dedup hard-depend on JetStream; `NATS_DISABLED` is a test-only escape and silently drops events in prod (`CONCERNS.md` "fragile areas"). Options:
- **Single self-hosted node on a Fly volume — RECOMMENDED for first customer.** File-backed JetStream persistence survives restarts; one node is acceptable at first-customer scale (single-digit tenants, Friday spikes measured in hundreds of orders, not thousands). It is on the bootstrap-budget side of the ledger and avoids a third vendor. **Risk to accept consciously:** a single node is a single point of failure — if it is down, the outbox keeps the events durably in Postgres (no data loss, that is the whole point of the outbox), but downstream audit/email projections lag until it recovers. That is tolerable for MVP-1.
- **Synadia Cloud** — removes the ops burden and gives HA, but adds a paid vendor and egress dependency for marginal benefit at this scale. Buy this at MVP-2, not now.
- **Do NOT defer/remove NATS.** Audit trail (GDPR PII-touch log), role-change events, and the entire Phase 8 Stripe webhook → inbox-dedup path run through it. It is load-bearing.

**Precondition:** the `max_deliver`/DLQ + `#run()` try/catch fixes from the events CLAUDE.md must be confirmed live before prod, or one malformed envelope stalls a consumer indefinitely (the classic poison-message outage).

## Managed Postgres — [HIGH on provider capability]
The 3-role model is the gating requirement, and it is more demanding than a typical managed-PG happy path:
- `resto_admin`/`resto` owner must run `CREATE EXTENSION pgcrypto, citext, pg_trgm` (`infra/docker/postgres/init/01-extensions.sql`) and `CREATE ROLE` for `resto_app` + `resto_auth`.
- `resto_auth` needs **BYPASSRLS**; `resto_app` must be **NOBYPASSRLS** with `FORCE ROW LEVEL SECURITY` honored. Boot refuses to start otherwise (`main.ts:52-64` → `assertNoRlsBypass`, `assertSetConfigRevoked`).

| Provider | Fit |
|---|---|
| **Neon — RECOMMENDED** | Supports custom roles, all three extensions, `BYPASSRLS` on roles you create, branching for safe migration dry-runs, scale-to-zero compute (fits bootstrap budget), and a built-in pooler. The one thing to verify in the plan: whether the role you create can be granted `BYPASSRLS` (Neon allows it on non-`neon_superuser` roles — confirm during spike). |
| **Supabase** | Works, but its own RLS/`authenticated` role conventions collide conceptually with our hand-rolled 3-role model; you fight the platform. |
| **Fly Postgres** | It is unmanaged Postgres-in-a-VM (you own backups/failover). Full role control, but the backup/PITR burden lands on a solo founder. Avoid unless you want that responsibility. |
| **RDS** | Capable, but pairs with the ECS path you are deferring; over-heavy now. |

**[MEDIUM] Connection model.** Fastify opens many short-lived connections and you will run ≥1 api replica + the reserved leader connection + Next SSR. Neon's pooler (PgBouncer transaction mode) handles this — **but the leader's advisory lock requires a session-pinned connection** (`db.connection.raw.reserve()`), which transaction-pooling breaks. Plan must route the leader connection through a **direct (non-pooled) connection string** and only pool the request-path queries. This is a real footgun; call it out in the plan.

## Object storage — [LOW] R2 over S3
The codebase is S3-SDK + path-style + presigned URLs already (`s3-signed-image-url.adapter.ts`, `INTEGRATIONS.md`), so R2 is a drop-in (`S3_ENDPOINT` swap). **R2 wins decisively on the bootstrap-budget lens: zero egress fees**, which matters because every public menu image is served to guests. CLAUDE.md already states "R2 over S3 if neutral" — it is better than neutral here. Verify presigned-PUT CORS (the Phase 4b photo-upload flow uses direct-to-bucket PUT) against R2; that is the only compat item to spike.

## CD + migrations — [MEDIUM]
- The migration step is `pnpm db:migrate` → `tsx src/cli/migrate.ts` run with the **admin/owner role**, never the runtime role. Run it as a **separate gated step before the new image goes live** (Fly: a release-command or a one-off `fly machine run`; not inline in app start — `infra/CLAUDE.md` rule, and boot asserts the lock is already installed at `main.ts:57`). Good: boot preflight (`assertTenantLockInstalled`) means a rollout that races ahead of migration **fails closed** rather than serving corrupt isolation. That is a real safety net — lean on it.
- **[HIGH] Rollback story is the weak point, and it is a code gap, not an infra gap.** Drizzle migrations here are forward-only; there is no `down` path and **hard deletes are forbidden by role grant**. So the rollback strategy must be **expand/contract (additive migrations only) + roll the app image back**, never "roll the DB back." The plan must state this explicitly and the first migration-bearing deploy must prove an app-only rollback works. Do not discover this at 2am.
- **Zero-downtime is not required for the first customer.** A brief maintenance window is fine and far simpler than blue-green. Don't build orchestration you don't need yet. Single instance + `enableShutdownHooks()` (`main.ts:110`) drains in-flight work; accept ~30s of 503s on deploy.
- **CI has no deploy job and the docker build is unverified** (`ci.yml:173-179`). Phase 7.5 must (a) re-add a docker-build check that actually boots the bundle far enough to hit the `import.meta.dirname` bug, and (b) add the deploy-on-merge-to-main job. Until (a) is green, the deploy target does not exist.

## Biggest operational risks for a solo founder (2am lens)
1. **[BLOCK] Unverified production bundle.** The `import.meta.dirname` CJS bug is documented as latent and CI was *deliberately* configured to not catch it. A public URL on a binary that crashes on boot is the single highest risk in this phase. Gate the phase on a green container that passes all six boot preflights against real managed Postgres.
2. **[HIGH] Silent outbox stall.** If the leader process is alive-but-wedged, or NATS is down, paid-order/email/audit events queue invisibly. Readiness (`/readyz`) checks DB + broker reachability but **not** leader liveness or dispatch lag (`health.controller.ts:51-59`). The `outbox.is_leader` gauge and the ">30s since last dispatch ⇒ not-ready" probe are scoped to **Phase 8** (ROADMAP Phase 8 SC#5) — meaning during 7.5→8 you are flying blind on the most important background process. **Recommendation:** pull a minimal version of that readiness check forward into 7.5, or you will not know the outbox died until a customer reports a missing confirmation email.
3. **[HIGH] No error tracker.** `INTEGRATIONS.md` confirms no Sentry/equivalent. OTel traces go to a dev Jaeger. In prod, a solo founder needs push alerts (Sentry/Better Stack/Grafana Cloud free tier) — not a dashboard you have to remember to open. Add this in 7.5; it is the difference between "customer told me it's down" and "I knew before they did."
4. **[MEDIUM] Secret sprawl across vendors.** Fly secrets + Neon string + R2 keys + NATS creds + `BETTER_AUTH_SECRET` + `AUDIT_ERASURE_SALT` (immutable — rotating it breaks anonymization linkage, `env.schema.ts:84`) + `INTERNAL_API_TOKEN`. Use the platform secret store (Fly secrets) as the single injection point; do **not** stand up Vault for one customer (the infra/CLAUDE.md Vault assumption is over-built for now — say so). Document every secret and its rotation rule in a runbook.
5. **[MEDIUM] Web-layer localhost fallbacks become prod 404s.** `NEXT_PUBLIC_API_ORIGIN ?? 'http://localhost:3000'` and `ADMIN_WEB_URL ?? 'http://localhost:3001'` (`CONCERNS.md`) silently route real users/reset-emails to localhost if a deploy env var is missing. These must fail loud before the first deploy.
6. **[LOW] Lock-in.** R2 (S3 API) and Neon (standard Postgres) are portable. Fly is the stickiest piece, but a Dockerized NestJS app moves to ECS/Render in a day if needed. NATS self-host is fully portable. Lock-in is acceptably low — don't over-engineer for exit.

## Recommended default (write this as the phase decision)
- **api + admin + website + qr-menu:** Fly.io, api with `min_machines_running=1`.
- **Postgres:** Neon (3 roles, RLS, pgcrypto/citext/pg_trgm); leader connection on a direct (unpooled) string, request path on the pooler.
- **Object storage:** Cloudflare R2.
- **Broker:** single self-hosted NATS JetStream node on a Fly volume (Synadia Cloud at MVP-2).
- **Secrets:** Fly secrets (no Vault yet).
- **CD:** GitHub Actions on merge to main → docker build (must boot-verify) → gated `pnpm db:migrate` (admin role) → rollout; expand/contract migrations + app-only rollback; brief maintenance window accepted.
- **Observability:** add Sentry (or Grafana Cloud free) in this phase; pull a minimal outbox-leader readiness signal forward from Phase 8.
