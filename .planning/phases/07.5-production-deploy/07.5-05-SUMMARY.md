## What Was Built

**Migration 0054** adds four idempotent `DO $$` blocks — one per RLS-enabled BA-owned table (`member`, `invitation`, `organization_role`, `tenants`) — each creating a `FOR ALL TO resto_auth USING(true) WITH CHECK(true)` permissive policy. Postgres OR-combines this with the existing PUBLIC tenant-isolation policy: `true OR <tenant_iso>` = `true` for `resto_auth` only. The `TO resto_auth` scoping ensures `resto_app`'s isolation is untouched.

**provisionAuthRole** now creates/alters `resto_auth` as `LOGIN NOSUPERUSER NOBYPASSRLS` and asserts `rolbypassrls: false`. The `NOBYPASSRLS` keyword in the ALTER branch explicitly strips a pre-existing `BYPASSRLS` attribute from any DB provisioned before this plan.

**auth-role.sql** includes the same four idempotent policy DO $$ blocks (without the role-existence guard, since the role is guaranteed to exist when this script runs). This handles the `migrate() → provisionAuthRole()` order used in testcontainers where the migration runs before the role exists.

**assertAuthRoleNoBypass(adminUrl)** exported from `src/preflight.ts` — connects as admin, checks `pg_roles.rolbypassrls` for `resto_auth`, throws `AuthRoleBypassRlsError` if set. Exported for plan-06 dry-checks; not wired into the API boot path (API connects as `resto_app`).

**New test suites in auth-role-grants.spec.ts:**

- `D-04: resto_auth operates on RLS-enabled BA tables WITHOUT BYPASSRLS` — proves `rolbypassrls=false`, full CRUD on member/invitation/organization_role, SELECT+UPDATE on tenants, all without setting `app.current_tenant`; control asserts `member_brand_scope` still 42501.
- `D-04: resto_app isolation is intact after the resto_auth permissive-policy change` — 42501 on account/session/two_factor/verification; cross-tenant SELECT on member returns 0 rows; cross-tenant SELECT on tenants returns 0 rows.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] policy-creation skip when migrate() runs before provisionAuthRole()**

- **Found during:** Task 3 (auth-role-grants test run)
- **Issue:** Migration 0054's DO $$ blocks guard on `IF EXISTS (pg_roles WHERE rolname='resto_auth')`. In test setup, `migrate()` runs first, role doesn't exist yet → policies skipped. Then `provisionAuthRole()` creates the role but doesn't apply policies. `resto_auth` connected without `app.current_tenant` set → USING(is_system_session() OR id=current_tenant_id()) = false → 0 rows returned.
- **Fix:** Added the same four idempotent policy DO $$ blocks to `sql/auth-role.sql` (without the role-existence guard). This script runs AFTER the role is created, so policies are guaranteed to be applied regardless of `migrate()` → `provisionAuthRole()` order.
- **Files modified:** packages/db/sql/auth-role.sql
- **Commit:** 9926774

**2. [Rule 1 - Bug] Wrong column name in organization_role insert**

- **Found during:** Task 3 (D-04 test suite beforeAll)
- **Issue:** Test inserted `(id, organization_id, name)` into `organization_role` but schema has `(id, organization_id, role, permission)` — `name` column does not exist.
- **Fix:** Updated test inserts and UPDATE statements to use correct columns `role` and `permission`.
- **Files modified:** packages/db/test/integration/auth-role-grants.spec.ts
- **Commit:** 9926774
