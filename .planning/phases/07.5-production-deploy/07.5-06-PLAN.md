    **`infra/docker/Caddyfile`** — uses Caddy's env placeholders so no hostname is

    Two things beyond the research's shape, both load-bearing:

    1. **A global options block setting `servers { trusted_proxies static 0.0.0.0/0 ::/0 }`.**
       Without it Caddy's `reverse_proxy` overwrites `X-Forwarded-Host` with the request's
       own Host, so the tenant hostname the Worker forwards is replaced by `api.<apex>`;
       `effectiveHost()` returns that, and `NON_GUEST_SECOND_LABELS = new Set(['admin','api','www'])`
       in `tenant-resolver.service.ts:13` rejects it — **no tenant ever binds and every
       guest menu request dies.** Research Pitfall #3 analyses the Worker→origin hop and
       stops one hop short. The blanket range is acceptable only because `ufw` (plan 08)
       admits 80/443 exclusively from Cloudflare's published ranges, so the only client
       Caddy can ever see is already a trusted proxy. Put exactly that reasoning in a
       two-line WHY comment above the block — it is a deliberate decision that reads as a
       mistake without it, and it is void the moment the firewall rule changes.
    2. **`client_ip_headers CF-Connecting-IP` in the same `servers` block.** This is not
       optional once (1) is in place, and the reason is the opposite of intuitive: with
       every address trusted, Caddy's right-to-left walk over `X-Forwarded-For` finds
       nothing untrusted, gives up, and returns the **leftmost** XFF entry — which is
       whatever the client sent. Cloudflare **appends** the visitor address to a
       client-supplied `X-Forwarded-For` rather than replacing the header, so a forged
       value stays leftmost and wins. Cloudflare does overwrite `CF-Connecting-IP`, so
       reading that header instead is what makes `client_ip` mean anything here.
       Verified empirically against Caddy 2.11.4 in Docker (`07.5-VERIFICATION.md` Round 2
       NEW-1, tables T3/T4 and C1-C4): a forged `X-Forwarded-For` alone is admitted
       without this directive and rejected with it, and `X-Forwarded-Host` preservation —
       the whole point of (1) — is unaffected. Record in the WHY comment that (1) is what
       makes (2) necessary; they do not hold each other up.
    3. **A `client_ip` gate on `/internal*` as defence in depth.** The seed CLI
       (`pnpm resto:seed`) is the documented onboarding path for design-partner
       restaurants and talks to `/internal/v1/*`. **What actually protects that surface is
       `InternalTokenGuard`** (`apps/api/src/shared/api/internal-token.guard.ts`): it
       constant-time compares `X-Internal-Token` against `INTERNAL_API_TOKEN` and throws
       `UnauthorizedException` whenever the token is unset or mismatched outside
       `NODE_ENV=development`. The Caddy matcher — `path /internal*` with
       `not client_ip {$INTERNAL_ALLOWED_IPS}` and `respond 404` — narrows who can reach
       the guard at all; it is a second layer, not the control. Write it that way in the
       runbook too. Give the placeholder a Caddyfile default that matches nothing —
       `not client_ip {$INTERNAL_ALLOWED_IPS:192.0.2.1/32}` (TEST-NET-1, RFC 5737).

       closed. Task 3's rehearsal catches it locally, which is where you want to find it.
       Plan 08's `--stage full` proves the gate fires rather than asserting that it does.

    peer to the inbound `X-Forwarded-For`, so the api receives

    `RATE_LIMIT_AUTH_SIGNIN_PER_MIN` would become a per-PoP limit — one abusive client
