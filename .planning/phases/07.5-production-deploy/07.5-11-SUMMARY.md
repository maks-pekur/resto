## Decisions Made

1. **WORKDIR switch before pnpm build:** Next.js 16 Turbopack infers the workspace root from the working directory. Running `pnpm --filter @resto/admin build` from /workspace triggers a bug where Turbopack can't find next/package.json. Switching `WORKDIR /workspace/apps/admin` then `pnpm build` runs Next.js from the app directory, where it resolves correctly.

2. **turbopack.root dynamic resolution:** Even with WORKDIR in the app dir, Turbopack needs to know the monorepo root to resolve `@resto/*` workspace packages (e.g., packages/domain imports `zod` from the hoisted root node_modules). `turbopack: { root: resolve(__dirname, '../..') }` where `__dirname = fileURLToPath(new URL('.', import.meta.url))` resolves correctly in both Docker (/workspace) and local dev (the actual monorepo root).

3. **Server-only env build-time placeholders:** `apps/admin/lib/env.ts` calls `loadAdminEnv()` at module load time (line 67). During `next build`'s page-data-collection phase, Next.js SSRs pages in a Node worker — triggering the env validation. Passing placeholder build ARGs (with production-safe non-secret values for `ADMIN_WEB_URL`, and placeholder strings meeting minimum-length requirements for `INTERNAL_API_TOKEN` and `ACTIVE_BRAND_COOKIE_SECRET`) satisfies the validator during build. Real values override these at ECS task launch via Secrets Manager — they are never shipped to clients (server-only import guard is in place).

4. **Package-level node_modules in build stage:** Workspace packages that have their own `node_modules` in the local tree (domain, ui, cart, api-client) must have those `COPY --from=deps`'d explicitly in the build stage. Without this, Turbopack's module resolution from within each package's source fails to find hoisted deps (e.g., `zod` for domain, `zustand` for cart, `react` for ui/cart).
