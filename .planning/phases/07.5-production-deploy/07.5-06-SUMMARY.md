**1. [Rule 3 — blocking] GitHub repository variables were Secrets, not Variables**
- **Found during:** Task 1 checkpoint verification
- **Issue:** The founder had stored `PUBLIC_APEX_DOMAIN`/`ADMIN_APEX_DOMAIN`/`GUEST_APEX_DOMAIN` as GitHub Secrets. Secrets are write-only (no API/CLI can read them back), so every `gh variable get` in this plan's scripts and every `${{ vars.* }}` expression in plan 09's `deploy.yml` would have resolved to empty.
- **Fix:** Set the same three values as GitHub repository Variables (`gh variable set`, run with the founder's explicit, out-of-band authorization after the sandbox's own permission classifier correctly blocked my first attempt as a remote-visible action). Left the redundant Secrets in place — deleting them is the founder's call.
- **Verification:** `gh variable get` for all three now echoes back the real values; Task 1's full automated verify block (apex distinctness, Cloudflare NS delegation, SSH keypair) passes.
- **Committed in:** N/A (GitHub account state, not a repo file)

**2. [Rule 1 — bug] `docker manifest inspect` used to confirm the Caddy tag exists needed a substitute in this sandbox**
- **Found during:** Task 2 verification
- **Issue:** `docker manifest inspect caddy:2.11-alpine` hangs indefinitely in this session — traced to `docker-credential-osxkeychain get` blocking on a macOS Keychain prompt with no interactive session to approve it (confirmed: killing the stuck helper process immediately surfaces `error getting credentials - err: signal: killed`, and a fake credential helper printing the documented `credentials not found in native keychain` sentinel to stdout resolves it in 3.4s).
- **Fix:** Verified tag existence by two independent, stronger means instead: the Docker Hub Registry HTTP API (`GET /v2/library/caddy/manifests/2.11-alpine` → 200) and an actual successful `docker pull` + `docker run` of that exact tag (used for the live Caddyfile behavior tests below). This is an environment-local finding, not a script defect — CI runners without a GUI keychain (the normal case) would not hit this.
- **Verification:** both checks above, re-run at the end of the session.
- **Committed in:** N/A (verification method substitution, not a file change)

**3. [Rule 1 — bug] Compose `env_file:` interpolation claim was wrong for the installed Compose version**
- **Found during:** authoring `render-env.sh` (Task 2), per the plan's own instruction to confirm rather than assume
- **Issue:** The plan states "Compose's `env_file:` does not expand `${...}` inside the referenced file." Docker Compose v5.1.2 (installed here) *does* interpolate `env_file:` contents against the invoking shell's environment — confirmed twice, with two different variable names, including the `"variable is not set, defaulting to blank string"` warning that is the interpolation engine's own signature.
- **Fix:** Corrected the WHY-comment in `render-env.sh` to state the real justification (a self-contained, mode-600, placeholder-refusing file that doesn't depend on ambient shell state at `docker compose up` time) rather than the plan's incorrect claim. The script's actual behavior and the surrounding architecture are unaffected — pre-rendering remains the right design regardless of which Compose behavior is true.
- **Verification:** the exact scratch-file reproduction the plan asked for, both with and without the variable exported.
- **Committed in:** `f7593977`

**4. [Rule 1 — bug, PRE-EXISTING] `apps/api` cannot boot: `Cannot find module 'pino'`**
- **Found during:** Task 3, first `local-prod-rehearsal.sh` run — the api container crash-looped
- **Issue:** `pino` is declared only by `packages/db`, never by `apps/api`. `build.mjs` bundles `@resto/*` source but leaves third-party deps external; the runtime image links only `apps/api`'s own declared dependencies into `apps/api/node_modules`, so `packages/db/src/logger.ts`'s `require('pino')` had no resolvable path from `apps/api/dist/main.cjs`. **This predates this plan** — `apps/api/Dockerfile`'s runtime stage and `build.mjs` are both unchanged by plan 06 (confirmed: `git diff main..HEAD -- apps/api/Dockerfile` before this fix showed only the new `migrate` stage). Without this rehearsal, the same failure would have first appeared as a dead container on the paid box in plan 08.
- **Fix:** Added `"pino": "^9.5.0"` to `apps/api/package.json` (matching `packages/db`'s range) and ran `pnpm install` to update `pnpm-lock.yaml`.
- **Verification:** `require('pino')` now resolves via `apps/api/node_modules/pino` (a real symlink, not hoisted); the built runtime image progresses past module resolution to `EnvValidationError` (expected, no env supplied) rather than `MODULE_NOT_FOUND`; the full rehearsal subsequently boots the api container to `healthy`.
- **Committed in:** `d5b53a47`

**5. [Rule 1 — bug, PRE-EXISTING] Docker `HEALTHCHECK` used `localhost`, which resolves to `::1` first and always fails**
- **Found during:** Task 3 rehearsal — api process was demonstrably alive and serving `200` on `/healthz`, yet Docker reported the container `unhealthy`
- **Issue:** `HEALTHCHECK CMD wget --quiet --spider http://localhost:3000/healthz` — inside the Alpine/musl runtime image, `getent hosts localhost` returns `::1` before `127.0.0.1`, and Node's `app.listen({ host: '0.0.0.0' })` binds IPv4 only (confirmed via `netstat` inside the container: only `tcp 0.0.0.0:3000`, no `tcp6`). `wget http://localhost:3000/...` connects to `[::1]:3000`, finds nothing listening, and the healthcheck fails every time regardless of app health. This is also pre-existing — the runtime stage's `HEALTHCHECK` line is untouched by plan 06 apart from this fix.
- **Fix:** Changed the healthcheck target to `http://127.0.0.1:3000/healthz`.
- **Verification:** `docker exec <container> wget -O- http://127.0.0.1:3000/healthz` → `{"status":"ok"}`; the rehearsal's api container subsequently reaches Docker's own `healthy` state.
- **Committed in:** `d5b53a47`

**6. [Rule 1 — bug] `verifyTransport()` makes a real network call to Resend even with a syntactically-valid dummy key — the plan's Round-2-derived claim that "nothing here sends an email or calls Stripe" understated this**
- **Found during:** Task 3 rehearsal, after fixing #4 and #5
- **Issue:** `assertEmailAdapterWired` (`identity-core.module.ts`) unconditionally calls `adapter.verifyTransport()` in `NODE_ENV=production`/`staging`; the Resend adapter's `verifyTransport()` calls the real `domains.list()` endpoint (`resend.adapter.ts`). This is a genuine network call — neither the constructor-inertness check (which only tests `new Resend(key)`) nor `assertProdGuardrails`'s string comparisons cover it. `re_rehearsal_local_only` failed it with a real `400` from Resend's API (`API key is invalid`). This gap survived four rounds of adversarial review because Round 2's NEW-3 examined only the adapter *constructor*, not this separate boot-time verification call in a different file.
- **Fix:** Confirmed the Resend SDK reads `process.env.RESEND_BASE_URL` as an override (`node_modules/resend/dist/index.mjs`: `process.env.RESEND_BASE_URL || defaultBaseUrl`) — not a workaround invented for this, a documented SDK escape hatch. `local-prod-rehearsal.sh` now stands up a throwaway `caddy:2.11-alpine` container (`resend-mock`, added via a compose file override the script generates itself, never committed) that answers any request with `{"data":[],"error":null}`, and points `RESEND_BASE_URL` at it. No production code changed; the boot guard (`assertEmailAdapterWired`) is fully exercised, not bypassed.
- **Verification:** shown failing (`Resend verifyTransport failed: API key is invalid (status 400)`) before the fix; shown passing (api reaches `healthy`, `/readyz` reports `outbox_leader` ok) after.
- **Committed in:** `d5b53a47`

**7. [Rule 1 — bug, own artifact] Caddy cert directory name mismatch crash-looped Caddy in the rehearsal**
- **Found during:** Task 3 rehearsal, while diagnosing #6
- **Issue:** `local-prod-rehearsal.sh` generated its self-signed cert at `infra/docker/certs.rehearsal/`, but `docker-compose.prod.yml`'s `caddy` service mounts `./certs` (resolved relative to `infra/docker/`) — a name I introduced, not specified by the plan. Caddy crash-looped on `open /etc/caddy/certs/origin.crt: no such file or directory`, and the mismatched bind mount had silently auto-vivified an empty `infra/docker/certs/`.
- **Fix:** Generate the rehearsal's self-signed pair at `infra/docker/certs/` (matching the compose file exactly, matching where plan 08 places the real Origin CA pair on the box) and added `infra/docker/certs/` to `.gitignore`.
- **Verification:** Caddy boots cleanly, no ACME/cert errors in logs; `/healthz` and `/readyz` both reachable through it.
- **Committed in:** `d5b53a47`

**8. [Rule 1 — bug, own artifact] Restore-drill's cleanup trap silently inverted a passing result to a failing exit code**
- **Found during:** Task 3, first successful `restore-drill.sh` run under `--dump-file`
- **Issue:** `cleanup() { ...; [ -n "$CLEANUP_DIR" ] && rm -rf "$CLEANUP_DIR"; }` under `set -e`: when `--dump-file` is used, `$CLEANUP_DIR` stays empty, `[ -n "" ]` evaluates false, and that false status — being the trap's last command — became the script's own exit code, even though the drill had printed `PASSED` and every check had succeeded. Reproduced deliberately (`bash -c` minimal repro) before fixing.
- **Fix:** Replaced the `&&`-chained one-liner with an explicit `if [ -n "$CLEANUP_DIR" ]; then rm -rf "$CLEANUP_DIR"; fi`.
- **Verification:** shown failing (exit 1 despite a printed `PASSED`) before the fix, shown passing (exit 0) after, on the same successful drill.
- **Committed in:** `d5b53a47`

**9. [Rule 1 — bug, own artifact] Two smaller script bugs caught during the same debugging pass**
- Missing `-i` on the `docker exec` reading the resto_app-scoped counts caused a silent no-op (no stdin attached, psql received nothing, exited 0 with no output) — fixed by adding `-i`.
- Positional line-parsing of psql's `resto_app` count output was off by one (a void-returning `app_bind_tenant()` call and the `BEGIN` command tag both emit lines even under `-t`), which silently shifted every count by one row. Replaced with `\gset` + a single tagged `\echo` line, the same technique already used by `backup-nightly.sh`.
- **Committed in:** `d5b53a47`

**10. [Rule 1 — bug, own artifact] `SENTRY_DSN=` (empty string) crashes api boot; committed templates had the same bug**
- **Found during:** Task 3 rehearsal
- **Issue:** `SENTRY_DSN: z.string().url().optional()` accepts an absent key but rejects an empty string. `SENTRY_DSN=` in a dotenv file sets the key to `""`, not "unset" — `EnvValidationError: SENTRY_DSN: Invalid url`. The already-committed `api.env.example`/`website.env.example` (Task 2) had this exact line, so a founder filling in the templates as-is and leaving Sentry unconfigured would hit the identical failure on the real box.
- **Fix:** Commented out `SENTRY_DSN=` (with a WHY note) in both committed templates and in the rehearsal script's own heredocs.
- **Verification:** rehearsal boot proceeds past env validation with the line commented out; confirmed the website side is unaffected either way (`instrumentation.ts` checks truthiness, so an empty string was already harmless there).
- **Committed in:** `d5b53a47`
