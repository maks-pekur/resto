<objective>
Provision the production managed Postgres on the provider chosen by 07.5-01 (Neon if the
BYPASSRLS spike passed, RDS otherwise), expressing the full 3-role + FORCE-RLS + extensions model
that the boot preflights demand, and confirm automated backups/PITR are on. This is success
criterion 1's database half ("the 3-role Postgres schema is provisioned on managed Postgres") and
the investor's BLOCK #1 (security model expressible on the chosen provider).

Purpose: The 3-role/RLS double-enforcement is the product's core tenant-isolation defensibility.
If the roles, extensions, or RLS forcing are wrong, the API refuses to boot (assertNoRlsBypass,
assertSetConfigRevoked, assertNoBaCredentialAccess) — better caught here than at the first
customer request.
Output: a live prod DB with the three roles + three extensions + backups, migrations applied, and
a repeatable provisioning runbook.
</objective>

## Trust Boundaries

| Boundary                                               | Description                                                              |
| ------------------------------------------------------ | ------------------------------------------------------------------------ |
| resto_app connection -> tenant-scoped tables           | Must be NOBYPASSRLS so RLS is the safety net under the repo-layer filter |
| resto_auth connection -> Better Auth credential tables | BYPASSRLS by design; resto_app must have zero access to these            |
| admin/migration role -> schema DDL                     | Powerful; used only for migration + provisioning, never at runtime       |
