**What plans 06 and 07.5-14 already built, so this plan runs it rather than rewriting it.**
`infra/scripts/backup-nightly.sh` writes a `-Fc` dump plus a manifest carrying `SELECT count(*)` for
`tenants`, `orders`, `menu_items` and `tenant_domains` taken inside one `REPEATABLE READ`
transaction with the dump. `infra/scripts/restore-drill.sh` already refuses an object older than 26
hours, restores with `pg_restore --exit-on-error --no-owner --no-acl` into a throwaway
`postgres:16-alpine`, creates the roles before restoring, runs `migrate.ts` then
`provision-roles-ci.ts` in `ci.yml` order, re-reads the four counts **as `resto_app`** rather than as
the scratch superuser, checks `__drizzle_migrations` against `_journal.json`, asserts
`rolsuper`/`rolbypassrls` are false on both app roles, and prints an elapsed RTO. Plan 07.5-14 gave
the local rehearsal seeded rows so this machinery is exercised against non-zero counts on every run.
This plan's job is to install the cron, run the drill against a **real R2 object**, and record it.

**The ETag is NOT tenant-scoped.** `public-menu.controller.ts:272,298` builds it as
`'"' + version + '"'` — a bare menu-version integer. Two freshly published tenants both sit at
version 1 and emit identical ETags. An isolation assertion built on an ETag difference fails in
exactly the fresh-production case this smoke targets, for a reason unrelated to isolation — which is
how an executor talks themself into deleting the phase's most important check. **Compare bodies.**

**`cf-cache-status` is observable now, and was not before.** Round 1 correctly rejected it while a
Worker served the response from `caches.default` — a Worker does not produce that header. Plan
07.5-12 deleted both Workers; the Cloudflare zone cache is the mechanism again, and the header is
emitted by Cloudflare's own pipeline. The zone cache key is the full request URL, which carries the
tenant in its host, so it is tenant-correct with no code. What is **not** yet known is whether the
Cache Rule produces a hit at all on this route: research assumption **A9**, rated MEDIUM, notes that
Cloudflare does not cache JSON content types by default — which is why the rule is needed — but that
the rule's interaction with `Vary` and with `Set-Cookie` on `/v1/menu` has never been executed. The
origin already emits `public, s-maxage=300` plus an ETag
(`apps/api/src/contexts/catalog/domain/menu-cache.ts`, `docs/runbooks/menu-edge-caching.md`).

**`X-Resto-Cache` does not exist.** Plan 07 invented it, plan 07.5-12 deleted it with the Workers.
An assertion on it could only ever fail.

**CORS cannot prove same-origin.** `security.ts:171`'s `buildOriginMatcher` emits
`Access-Control-Allow-Origin` only when the request carries `Origin`. A Node script sends none, so
the header is absent both in a correct setup and in a completely broken one; and if the script did
send an `Origin` the API would emit ACAO on a correct setup because `CORS_ALLOWED_ORIGINS` lists it.
Assert the response *shape* instead.

**The session cookie is host-only, and that is the assertion.** Phase 07.4 plan 06 removed
`AUTH_COOKIE_DOMAIN` from the required-outside-dev list; with the option absent Better Auth omits
the `Domain` attribute entirely — read from `better-auth@1.6.30 dist/cookies/index.mjs:22-42`, where
`domain` is `undefined` and the attribute is spread in only under `...crossSubdomainEnabled ? { domain } : {}`.
The remaining attributes are `Path=/`, `SameSite=lax`, `HttpOnly`, and `Secure` with the `__Secure-`
name prefix under https. So the smoke asserts the **absence** of `Domain=` — not the presence of
`Domain=.<something>`, which was the previous version's assertion and is now the failure signature.

**Guest sticker host precedence — `GuestMenuUrlService.#resolveGuestHost`**, after plan 07.5-13:

```typescript
const primaryVerifiedCustom = domains.find(
  (d) => d.kind === 'custom' && d.isPrimary && d.verifiedAt !== null,
);
if (primaryVerifiedCustom) return primaryVerifiedCustom.domain;   // outranks the apex
return `${tenant.slug}.${env.PUBLIC_APEX_DOMAIN}`;
```

One `tenant_domains` row decides what every printed QR code says, and a row left from a dev tunnel
looks legitimate — "verified custom domain" is a production concept, not a dev flag.
`prod-guardrails.ts` inspects env, not rows, and cannot see it.

**`tenant_domains` shape** (`packages/db/src/schema/tenants.ts`): `domain` (citext, globally unique),
`kind` in `('subdomain','custom')`, `is_primary` under the partial unique index
`tenant_domains_one_primary_per_tenant_uq WHERE is_primary = true`. Clear the old primary before
setting a new one, or the write is rejected — or, under `ON CONFLICT DO NOTHING`, silently dropped.

**The writers are already fixed and are not this plan's to touch.** Plan 07.5-13 moved
`provision-tenant.service.ts` and `finalize-tenant-onboarding.service.ts` onto
`PUBLIC_APEX_DOMAIN` through `apps/api/src/shared/guest-links.ts` and closed
`tenant-primary-domain-ignores-configured-apex.md`. What that plan explicitly did **not** do, and
left named for this one: rows written by the old `menu.resto.app` constant already exist in any
database that has provisioned a tenant. Clearing them is this audit's job.
