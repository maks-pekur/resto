# Phase 07.5 Plan 07: Cloudflare Workers for admin and qr-menu, and the three-apex hostname scheme Summary

**Two Cloudflare Worker modules (admin, qr-menu) each serving a SPA plus a same-origin API proxy, with a tenant-keyed Worker cache and a zone-cache opt-out proven by tests at both cache layers, and the guest-menu hostname promoted from a hardcoded "menu" label to `GUEST_APEX_DOMAIN` configuration.**

## Accomplishments

- `apps/qr-menu/worker/index.ts` — same-origin `/v1/*` proxy, cache key built from the incoming request URL (not the rewritten origin URL), zone-cache opt-out (`cf: { cacheTtl: 0, cacheEverything: false }`) on the subrequest, `X-Resto-Cache: MISS|HIT|BYPASS` on every response. 12 tests, including the cross-tenant isolation test observed red-then-green against the naive (origin-URL-keyed) implementation.
- `apps/admin/worker/index.ts` — same-origin `/v1/*` + `/api/*` proxy, zero Cache API interaction (asserted by call count, not inference), `Set-Cookie` pass-through unmodified (F-41 regression net), zone-cache opt-out, `X-Resto-Cache: BYPASS` always. 10 tests. `apps/admin/Dockerfile` (a Next.js/ECS-era artifact baking `ADMIN_WEB_URL=https://admin.resto.app`) deleted with no dangling references.
- `GUEST_APEX_DOMAIN` added to `env.schema.ts` and `prod-guardrails.ts` (ephemeral-host guard); `RESEND_FROM`/`RESEND_REPLY_TO` added to the dev-default guard set. `guest-menu-url.service.ts` composes `${slug}.${GUEST_APEX_DOMAIN}`. `tenant-resolver.service.ts`'s `guestSlugLabel` replaces its old shape test (`second === 'menu'`, no apex gate) with an apex-equality test on both branches — `GUEST_HOST_LABEL` no longer exists anywhere in `apps/api/src`.
- `wrangler.jsonc` for both apps: `assets` block with `run_worker_first`, no `routes`/`vars` committed. `wrangler@4.129.0` + `@cloudflare/workers-types@5.20260904.1` added as devDependencies. Both `worker:dry-run` scripts (`vite build && wrangler deploy --dry-run` with the three apexes as CLI flags) succeed.
- `docs/runbooks/spa-workers.md` — three-apex map with citation, deploy invocations, build-time env, DNS records, cache-key rule, `X-Resto-Cache` contract, and the statement that these Workers' own cache replaces the CDN cache rules D-08 contemplated.

## Decisions Made

See `key-decisions` in the frontmatter. In short: keep the Worker runtime modules dependency-free of `@cloudflare/workers-types` (structural `Env` typing + a 6-line `CacheStorage` augmentation) while still adding the package as a devDependency per Task 3; run both Worker test suites under `@vitest-environment node` (an existing repo pattern) because jsdom's own `AbortController` collides with Node's native `fetch`/`Request` internals; and guard `apps/admin/test/setup.ts`'s DOM stubs behind `typeof window !== 'undefined'`, mirroring qr-menu's pre-existing guard.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 — blocking] Worker unit tests cannot run under the app's default jsdom environment**
- **Found during:** Task 1, first `vitest run` of the naive (red-baseline) implementation
- **Issue:** `new Request(url, existingRequest)` — the plan's own mandated cache-key/proxy-request construction, and RESEARCH.md's own example code — throws `TypeError: RequestInit: Expected signal ("AbortSignal {}") to be an instance of AbortSignal` under `apps/qr-menu`'s default `environment: 'jsdom'`. Root-caused with a command, not assumed: `new JSDOM('').window.AbortController !== globalThis.AbortController` — jsdom implements its own `AbortController`/`AbortSignal`, distinct from the one Node's native `fetch`/`Request` internals validate against, even though `instanceof`/prototype reflection from *inside* the same jsdom-provided global scope reports them as consistent.
- **Fix:** Added `// @vitest-environment node` as the first line of both `apps/qr-menu/test/worker.spec.ts` and `apps/admin/test/worker.spec.ts` — an existing, precedented pattern in this repo (`apps/qr-menu/test/bundle-no-dev-leak.spec.ts` already does this for the same class of reason). No production code changed; the Worker modules keep the plan-mandated `new Request(url, request)` shape.
- **Verification:** shown failing with the exact error above before the fix; shown passing after, in the same file, no other change.
- **Committed in:** `6ff9de4f`

**2. [Rule 3 — blocking] admin's shared `test/setup.ts` crashes under the node-environment worker suite**
- **Found during:** Task 2, first `vitest run test/worker.spec.ts`
- **Issue:** `ReferenceError: window is not defined` — `apps/admin/test/setup.ts` unconditionally references `window`/`Element.prototype` (unlike `apps/qr-menu/test/setup.ts`, which already guards this exact case with a `typeof window !== 'undefined'` check and the comment "The prod-bundle suite runs in the node environment, where none of this exists").
- **Fix:** Wrapped the DOM-dependent block (`matchMedia`, `ResizeObserver` stub, pointer-capture/`scrollIntoView` shims, `window.scrollTo`) in the same `typeof window !== 'undefined'` guard qr-menu already uses.
- **Verification:** worker suite passes (10/10); full admin suite re-run afterward — 50 test files / 270 tests, all green, confirming the guard changes nothing for jsdom-environment tests.
- **Committed in:** `4f60a08a`

**3. [Rule 1 — bug, own artifact / pre-commit gate] `worker/tsconfig.json`'s `types: ["@cloudflare/workers-types"]` cannot resolve before Task 3 installs the package**
- **Found during:** Task 1, `git commit` — the repo's `lint-staged` pre-commit hook runs type-aware ESLint (`projectService: true`) against `apps/qr-menu/worker/index.ts` using the not-yet-existent `@cloudflare/workers-types` types field, producing 46 `no-unsafe-*` errors (every expression involving `Request`/`Response`/`caches` resolves to `any`) and blocking the commit.
- **Fix:** Scoped `worker/tsconfig.json`'s `types` to `[]` (drop the package reference entirely) and added a 6-line local ambient augmentation in `worker/index.ts` (`declare global { interface CacheStorage { readonly default: Cache } }`) extending the standard `lib.dom` `CacheStorage`/`Cache` types already in scope. `Request`/`Response`/`Headers`/`URL`/`fetch` keep their standard DOM-lib types; only the one Cloudflare-specific extension (`caches.default`) needed filling in. Confirmed `tsc -p worker/tsconfig.json --noEmit` and `eslint worker/index.ts` both clean, with zero new dependencies. Applied identically to `apps/admin/worker/tsconfig.json` (which never needed `caches` at all, so it just has `types: []`).
- **Verification:** `pnpm exec eslint worker/index.ts` — 0 problems (was 46); `pnpm exec tsc -p worker/tsconfig.json --noEmit` — clean; `vitest run test/worker.spec.ts` unaffected (12/12 still passing).
- **Committed in:** `6ff9de4f`, `4f60a08a`

**4. [Rule 1 — bug, direct regression] `GuestMenuUrlService`'s co-located spec and two e2e fixtures still assumed `PUBLIC_APEX_DOMAIN`**
- **Found during:** Task 3, after switching `guest-menu-url.service.ts` from `PUBLIC_APEX_DOMAIN`+hardcoded label to `GUEST_APEX_DOMAIN`
- **Issue:** `apps/api/src/contexts/tenancy/application/guest-menu-url.service.spec.ts` (co-located with the source file, not listed in the plan's `<files>` but directly broken by the required code change) set `env = { PUBLIC_APEX_DOMAIN: 'resto.app' }`, which would make every "falls back to the slug formula" test throw instead of returning a URL. `test/e2e/table-zones.e2e.spec.ts` and `table-location-availability.e2e.spec.ts` set `process.env.PUBLIC_APEX_DOMAIN = 'resto.app'` specifically so `GuestMenuUrlService` could build a table's `qrUrl` for a tenant with no verified custom domain (documented in both files' own comments) — after the switch, `GuestMenuUrlService` would throw `GUEST_APEX_DOMAIN is not set` in both e2e runs.
- **Fix:** Updated the co-located spec's env fixture and one test name/body to `GUEST_APEX_DOMAIN`. Added `process.env.GUEST_APEX_DOMAIN = 'menu.resto.app'` alongside the existing `PUBLIC_APEX_DOMAIN` line in both e2e files — reusing the exact same literal (`menu.resto.app`) the old hardcoded-label code produced, so `table-zones.e2e.spec.ts`'s existing exact-string assertion (`qrUrl` toBe `https://${tenantSlug}.menu.resto.app/?t=${table.id}`) needed no further change.
- **Verification:** co-located spec re-run (5/5 passing). The two e2e files require Docker and were not executed in this sandbox (consistent with plan 06's own noted Docker-credential-helper constraint in this environment) — verified by static trace instead: `GuestMenuUrlService` only reads `GUEST_APEX_DOMAIN` now, both files set it to the exact string the prior hardcoded-label formula produced, and no other line in either file depends on the removed formula.
- **Committed in:** `5f381ba7`

**5. [Rule 1 — bug, direct regression] The "dev tunnel fallback" describe block in `tenant-resolver.service.spec.ts` needed `GUEST_APEX_DOMAIN` to keep its own claim true**

- **Fix:** Added `GUEST_APEX_DOMAIN: 'guest.invalid'` to the block's `envFor` helper.

- **Committed in:** `5f381ba7`
