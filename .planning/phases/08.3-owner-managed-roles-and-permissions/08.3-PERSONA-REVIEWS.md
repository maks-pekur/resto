## CTO (technical correctness) — CRITICAL / HIGH

- **C-1 (CRITICAL) — Role *assignment* has no subset check.** BA's `updateMemberRole` gates
  only on `{member:['update']}`; the creator-subset guard runs on role create/update/delete
  only. An admin (or over-broad custom-role holder) could assign a
  `tenant:delete`/`billing:update` role to a peer or **to themselves**. → Wire
  `beforeUpdateMemberRole` with assigned-⊆-assigner effective-perms + self-escalation guard;
  e2e. **→ CONTEXT D-02, D-06.**
- **C-2 (CRITICAL) — No `ac` resource → role-CRUD gate authorizes nobody.** BA checks
  `{ac:['create']}`; RestOS encodes it as `staff:['role:create','role:update']`, which BA
  never consults. → Add `ac:['create','read','update','delete']`, grant owner, re-seed,
  retire `staff:role:*`. **→ CONTEXT D-13.**
- **C-3 (CRITICAL) — Pure creator-subset insufficient; add non-delegatable allowlist.**
  owner holds `tenant:delete`/`tenant:transfer`/`billing:update`; those can be minted into a
  custom role and leak via C-1. → `NON_DELEGATABLE` allowlist, enforced on create + assign.
  **→ CONTEXT D-04.**
- **H-1 — `AuthGuard.lookupBaseRole` returns `undefined` for custom/multi-role members**,
  breaking `BrandScopeGuard` owner-bypass. → parse role, derive highest system role.
  **→ CONTEXT D-15.**
- **H-2 — Role-definition changes emit no audit.** → new
  `identity.role_created/permissions_changed/deleted.v1` + `role` target kind.
  **→ CONTEXT D-16.**
- **H-3 — `maximumRolesPerOrganization` defaults `Infinity`**; confirm `cacheAllRoles`
  invalidation for "effect on next request". → cap it. **→ CONTEXT D-17, D-11.**
- **M-1 — `staff:role:create` violates the domain no-`:` rule** — becomes a live bug when
  the UI serializes permissions. → resolve with C-2. **→ CONTEXT D-13.**
