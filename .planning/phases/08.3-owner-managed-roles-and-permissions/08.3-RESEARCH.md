## Summary

Phase 08.3 turns on better-auth's `dynamicAccessControl` plugin and builds the privilege-escalation guards that justify enabling it. The good news: **this is a build-on-BA phase, not a build-your-own-RBAC phase.** The permission resolution engine (`hasPermission`, DB-backed custom-role lookup, subset checking in `checkIfMemberHasPermission`) is already correct and in place. The work divides into five areas:

1. **Platform prerequisites** (D-13/D-15): add the `ac` resource to `PERMISSIONS_STATEMENT`, rename colon-actions, grant to `owner`, flip the flag, fix `lookupBaseRole` CSV parsing. These are small but boot-critical changes.
2. **Privilege-escalation guards** (D-02/D-04/D-06): BA's `createOrgRole`/`updateOrgRole` already enforce a creator-subset check (`checkIfMemberHasPermission`, verified against installed source). The CRITICAL gap is the **assignment path** (`updateMemberRole`) — BA only checks `{ member: ['update'] }` and the creator-role special case; there is NO permission-set subset check on assignment. This gap is closed by wiring `beforeUpdateMemberRole` with custom RestOS logic.
3. **RestOS NestJS wrapper controllers** (D-14): the single leverage point for subset guard, NON_DELEGATABLE, assignment guard, audit emission, cross-tenant pinning, and rate-limiting. BA's native endpoints must NOT be reached directly by the browser.
4. **Audit** (D-16): BA has no create/update/delete-role hooks — only `afterUpdateMemberRole` (already wired). New role-definition events (`identity.role_created.v1` etc.) must be emitted from the D-14 wrappers.
5. **Admin UI** (D-07/D-08/D-10): presets-first role builder (duplicate & tweak), grouped permission catalog, minimal active-member assignment surface.

**Primary recommendation:** Implement in strict wave order — platform prerequisites → privilege-escalation guards → NestJS wrappers → audit events → UI. The guards are not a bolt-on; they are the condition under which `dynamicAccessControl: { enabled: true }` is safe to ship.

## Priority Research Findings (by Decision)

### D-13 — `ac` Resource + Re-seed [VERIFIED: installed source]

**Confirmed:** BA's `createOrgRole` endpoint gates on `{ ac: ['create'] }` (line 81-86 in `crud-access-control.mjs`). `updateOrgRole` gates on `{ ac: ['update'] }` (line 486-492). `deleteOrgRole` gates on `{ ac: ['delete'] }` (line 188-193). `listOrgRoles` and `getOrgRole` gate on `{ ac: ['read'] }`.

**Current state:** `PERMISSIONS_STATEMENT` has NO `ac` resource (confirmed at `packages/domain/src/rbac/permissions.ts:10-19`). `ownerRole = ac.newRole(SYSTEM_ROLES.owner)` — since `SYSTEM_ROLES.owner` has no `ac` key, the owner has no `ac` permissions. `ac.authorize({ ac: ['create'] })` returns `{ success: false, error: 'You are not allowed to access resource: ac' }`.

**Required changes (in sequence):**

1. `packages/domain/src/rbac/permissions.ts` — add `ac: ['create','read','update','delete']` to `PERMISSIONS_STATEMENT`; rename `staff: ['invite','remove','roleCreate','roleUpdate']` (drop the colon).

2. `packages/domain/src/rbac/system-roles.ts` — add `ac: ['create','read','update','delete']` to `SYSTEM_ROLES.owner`; rename `staff.roleCreate`/`staff.roleUpdate` in both `owner` and `admin`. Do NOT add `ac` to `admin` or `staff` (owner-only authoring per D-01).

3. `apps/api/src/contexts/identity/infrastructure/better-auth/access-control.ts` — `ownerRole = ac.newRole(SYSTEM_ROLES.owner)` will automatically pick up the `ac` key once D-13 is applied to `SYSTEM_ROLES`. No change to this file's shape, but the re-computed `ownerRole.statements` must include `ac`.

4. `apps/api/src/contexts/identity/infrastructure/better-auth/auth.config.ts` — flip `dynamicAccessControl: { enabled: true }` and set `maximumRolesPerOrganization` (D-17, see below).

5. **Re-seed mechanism:** There is no `pnpm db:rbac:sync` script yet — it is a `permissions.ts` comment referencing a future Phase E script. System roles are not stored in the `organization_role` DB table; they are wired at BA boot time via `organization({ roles: { owner: ownerRole, admin: adminRole, staff: staffRole } })`. The "re-seed" is simply: update `permissions.ts` + `system-roles.ts` → restart the API → `assertSystemRolesPresent()` runs at boot and validates the drift is zero. **No DB migration needed for the system roles themselves.** The preset custom roles (Manager/Cashier-FoH/Kitchen) DO need to be inserted into `organization_role` — this is done by a seed script at tenant provisioning time, not by the re-seed of system roles.

6. **Retire `staff:role:create` / `staff:role:update`:** After renaming, update the regression test in `apps/api/test/unit/identity/system-roles-presets.spec.ts` (currently checks `'role:create'` on line 73+). The test comment says "stays in admin per current design" — with D-01 (owner-only authoring) and D-13, `roleCreate`/`roleUpdate` become `ac:create/update` semantics for owner and are explicitly NOT granted to admin.

**Property test:** `ac.authorize({ ac: ['create'] })` on `ownerRole` must return `{ success: true }`. `ac.authorize({ ac: ['create'] })` on `adminRole` must return `{ success: false }`.

### D-14 — Wrapping BA Role Endpoints [VERIFIED: installed source]

**BA server API surface confirmed in `organization.mjs:88-139`:**

```typescript
auth.api.createOrgRole({ body: { organizationId?, role: string, permission: Record<string,string[]> }, headers })
```

**Call pattern (mirror `BetterAuthPermissionChecker`):**

```typescript
const api = this.auth.api as unknown as {
  createOrgRole: (opts: {
    body: CreateOrgRoleBody;
```

**Critical:** always pin `organizationId` from `getTenantContext()` (ALS), never from the client request body. The RestOS tenant cross-check in `AuthGuard` (lines 109-123) validates session `activeOrganizationId` matches ALS — trust that, not a client-supplied `organizationId`.

### D-06 — Creator/Assigner Subset Algorithm [VERIFIED: installed source]

**BA's built-in creator-subset check (for role CREATE/UPDATE):**

`checkIfMemberHasPermission` in `crud-access-control.mjs:600-636` iterates every `[resource, [action]]` pair in the proposed permission, calls `hasPermission({ ..., useMemoryCache: true })` for each, collects missing ones, and throws 403 with `missingPermissions` list if any are absent.

This runs on the actor's `member.role` CSV (system role + custom role if multi). Since D-05 mandates one-role-per-member, the CSV will be either `"owner"` or `"<custom-slug>"` — no composition edge cases.

**BA does NOT have this check on the ASSIGNMENT path.** Confirmed: `updateMemberRole` in `crud-members.mjs:246-318` checks only: (a) role exists, (b) `{ member: ['update'] }` permission, (c) creator-role protection (nobody can demote the owner unless they're the owner). Zero subset check.

**Concrete algorithm for the RestOS assignment-subset guard:**

```typescript
async function validateAssignmentSubset(
  actorUserId: string,
  organizationId: string,
  targetRoleSlug: string,
  auth: Auth,
  headers: Headers,
): Promise<void> {
  // 1. Actor's effective permission set
  // For each resource in PERMISSIONS_STATEMENT, check hasPermission.
  // Build actor's effective set by probing what BA returns.
  // Alternative: read organization_role for actor's custom role directly + merge with system role.
  // 2. Target role's permission set
  // Fetch via auth.api.getOrgRole({ query: { roleName: targetRoleSlug }, headers })
  // If system role, look up SYSTEM_ROLES[targetRoleSlug].
  // 3. NON_DELEGATABLE filter on target role
  // If target role permission ∩ NON_DELEGATABLE ≠ ∅ → reject 403.
  // 4. Subset check: every (resource, action) in targetRole.perms
  //    must exist in actor's effective perms.
  // 5. Self-escalation check: actor.userId === target.userId AND
  //    targetRole effective perms ⊃ actor's current effective perms → reject 403.
}
```

**Effective set computation:** The fastest approach is to call `auth.api.hasPermission` per resource/action pair (mirrors BA's own pattern). This makes N calls where N = |proposedPermissions| pairs. For a 25-action cap and per-role max of 20 permissions, this is at most 20 calls — acceptable.

**Alternative (cheaper):** Read the actor's `member.role` CSV directly from the `member` table (via `AuthDrizzle`), resolve system role permissions from `SYSTEM_ROLES`, resolve custom role permissions from `organization_role`, union them, then do an in-process subset check against `PERMISSIONS_STATEMENT`. This avoids the N round-trips. This is what `checkIfMemberHasPermission` does internally via `useMemoryCache:true`.

**Recommendation:** Use the in-process approach for the RestOS guard (read member.role, resolve permissions from SYSTEM_ROLES + organization_role, union, subset check). Keep `auth.api.hasPermission` for the primary per-request permission check in `PermissionsGuard`.

### D-11 — `cacheAllRoles` Invalidation [VERIFIED: installed source]

**Confirmed cache behavior in `has-permission.mjs`:**

- `cacheAllRoles` is a **module-level `Map`** (line 12 in `permission.mjs`): `const cacheAllRoles = new Map()`.
- On every `hasPermission(input, ctx)` call WITHOUT `useMemoryCache: true`, it: (1) reads from DB, (2) calls `cacheAllRoles.set(organizationId, acRoles)` after the DB read (line 29). So the cache is **always updated** on normal (non-cached) calls.
- On calls WITH `useMemoryCache: true` (only used in `checkIfMemberHasPermission` during role create/update subset check), it reads the cache first.
- **No explicit cache invalidation on `updateOrgRole` or `deleteOrgRole`.** The cache is NOT cleared when a role's permissions change.

**Security impact:** This means:

- Normal `hasPermission` calls (from `BetterAuthPermissionChecker`, which does NOT set `useMemoryCache`) ALWAYS re-read from DB first. The cache is populated as a side effect but is not consumed by the primary path.
- The `useMemoryCache:true` path is only used during the creator-subset batch check (a short internal loop, not across requests). This cache is process-scoped.
- **Critical:** there is NO per-request staleness issue for the primary `hasPermission` path, because it always hits the DB when `dynamicAccessControl.enabled && !useMemoryCache`. This is the behavior that matters for D-11 ("edits apply on next request").

**Conclusion:** When a role's permissions are edited, the very next request from any member with that role will re-read from DB (because `BetterAuthPermissionChecker.hasPermission` calls BA's `hasPermission` without `useMemoryCache`). The cacheAllRoles map will be written with fresh data on that read. **D-11 is satisfied by the existing BA implementation — no additional invalidation logic needed.** The "stale cache" concern applies only to the short `useMemoryCache:true` batch within a single create/update-role operation, which is process-internal and inconsequential.

**Caveat (multi-process):** In a multi-pod deployment, the `cacheAllRoles` Map is per-process. This does not affect the primary check (always DB) but could affect `checkIfMemberHasPermission`'s batch loop on role create/update if the Map has stale data from a previous request. Impact: the creator-subset check might use a slightly stale snapshot of the actor's roles — this is LOW risk because (a) it only affects the subset check, not the actual permission enforcement, and (b) owner-only authoring means the actor's permissions are the full owner set (never stale in a way that matters).

**Fix:**

```typescript
private async lookupBaseRole(userId: string, organizationId: string) {
  const rows = await this.authDb.db.select({ role: memberTable.role })...
  const role = rows[0]?.role;
  if (!role) return undefined;
  const parts = role.split(',').map(r => r.trim());
  // Derive highest system role from the CSV parts
  if (parts.includes('owner')) return 'owner';
  if (parts.includes('admin')) return 'admin';
  if (parts.includes('staff')) return 'staff';

}
```

**New test:** `lookupBaseRole` on `"staff,gm"` returns `'staff'`; on `"custom-manager"` returns `undefined`; on `"admin"` returns `'admin'`.

### D-03 — Brand-Scope Reconciliation [VERIFIED: source]

**Confirmed orthogonality:** `BrandScopeGuard` (`brand-scope.guard.ts:26-78`) checks:

1. `brandNeutral` decorator → bypass
2. ALS brand context from `getBrandId()` → required

### HIGH-7 / Cross-Tenant Isolation Spike [VERIFIED: installed source + migration audit]

**Risk vector:** BA's `organization_role` reads in `has-permission.mjs` use the `resto_auth` connection (NOBYPASSRLS, but with `USING(true)` permissive policy per migration `0054_resto_auth_permissive_policies.sql`). The application-level isolation is: `findMany({ model: 'organizationRole', where: [{ field: 'organizationId', value: organizationId }] })`.

**Isolation guarantee:** If `organizationId` is always the session-validated tenant (`session.activeOrganizationId`, cross-checked against ALS by `AuthGuard`), then `hasPermission` can ONLY read roles for the caller's own organization. The BA code never uses a user-supplied `organizationId` without first validating membership via `adapter.findOne({ model:'member', where:[organizationId, userId] })` (lines 60-79 in `createOrgRole`). Cross-tenant reads are not possible via the normal path because:

1. The RestOS D-14 wrapper always pins `organizationId` from ALS (server-resolved) and never from the client body.
2. BA's own membership check (`findOne member where organizationId=X AND userId=Y`) gates before any role operation.
3. `AuthGuard` cross-checks `principal.tenantId === alsTenantId` (lines 112-123).

**Residual risk:** The `as unknown as BetterAuthPlugin` cast in `auth.config.ts:261` and `as unknown` in `permission-checker.adapter.ts:36` mean TypeScript cannot catch a future BA API shape change that exposes a new cross-tenant path. Runtime testing (the cross-tenant e2e) is the regression net.

**Go/No-go verdict:** Cross-tenant isolation for `dynamicAccessControl` in 1.4.22 is **safe to enable** when D-14 (wrapper controller pinning `organizationId` from ALS) is implemented. The risk is not from the plugin itself but from direct browser access to BA's `/api/auth/organization/*-role` routes — which D-14 prevents by routing everything through RestOS controllers.

**CVE migration tie-in (from `.planning/notes/dependency-cve-deferral.md`):** The deferred `better-auth 1.4→1.6` migration addresses the transitive `vitest` advisory (dev-tool only) and targets a pre-launch milestone. Enabling `dynamicAccessControl` in 1.4.22 does NOT add a new CVE surface. The existing org plugin surface (membership, invitations) is already active; `dynamicAccessControl` adds role-CRUD endpoints which are wrapped by RestOS controllers and gated behind auth. The deferred CVE migration schedule is unaffected.

```typescript
import type { Permission } from './permissions';

export const NON_DELEGATABLE: Permission = {
  tenant: ['delete', 'transfer'],
  billing: ['update'],
  staff: ['remove'],
  ac: ['create', 'read', 'update', 'delete'],
} as const;

export function containsNonDelegatable(
  permission: Record<string, string[]>,
): boolean {
  for (const [resource, actions] of Object.entries(NON_DELEGATABLE) as [
    keyof typeof NON_DELEGATABLE,
    string[],
  ][]) {
    const requested = permission[resource] ?? [];
    if (actions.some((a) => requested.includes(a))) return true;
  }
  return false;
}
```

### D-12 — Soft-Delete of Occupied Roles [VERIFIED: installed source]

**BA's native behavior:** `deleteOrgRole` in `crud-access-control.mjs:152-283` already BLOCKS deletion of roles with members (lines 252-271). It does `findMany({ model:'member', where:[organizationId, role contains slug] })` and throws `BAD_REQUEST ROLE_IS_ASSIGNED_TO_MEMBERS` if any member has the role. It also BLOCKS deletion of pre-defined (system) roles (lines 201-214).

**Soft-delete requirement (D-12):** BA's `deleteOrgRole` performs a hard DELETE (`adapter.delete` line 273). To implement soft-delete:

1. Add `archived_at timestamp with time zone` column to `organization_role` via a new migration.
2. Do NOT call `auth.api.deleteOrgRole` for the soft-archive path. Instead, the RestOS `archive-role.service.ts` wrapper:
   a. Checks occupied (query `member` table — same as BA does)
   b. Updates `organization_role.archived_at = NOW()` via `AuthDrizzle` (direct Drizzle update, not through BA's endpoint)
   c. Emits `identity.role_deleted.v1` (tombstone semantics — the role is logically deleted)
3. The `listOrgRoles` wrapper filters out `archived_at IS NOT NULL` rows.
4. `hasPermission` must not resolve archived roles — add `archived_at IS NULL` filter to the `findMany` in `hasPermission` is impossible without patching BA source. **Alternative:** because `listOrgRoles` returns only non-archived roles, the archive prevents re-use. But the `hasPermission` call still uses BA's `findMany` which has no archived_at filter.

**Problem:** BA's `hasPermission` (`has-permission.mjs:11-17`) uses `ctx.context.adapter.findMany({ model:'organizationRole', where:[organizationId] })` — no `archived_at` filter. A soft-archived role will still be resolved.

**Resolution options:**

- **Option A (recommended):** When archiving, also unassign all members from the role (force member reassignment before allowing archive, enforcing "no members" guard same as D-12 states). This ensures no member ever has an archived role slug in their `member.role` field. The archive then becomes a "name reservation" — the slug exists in the DB but no one is on it. BA's `hasPermission` will find the role entry but since no member has that slug in `member.role`, it's never resolved.
- **Option B:** Patch the `hasPermission` adapter call by adding a custom `adapter.findMany` override that adds `archived_at IS NULL`. Complex.

**Recommendation: Option A.** Enforce "must reassign all members before archiving" (the D-12 requirement already implies this — "a role with assigned members cannot be deleted"). After members are off the role, archive is safe because BA never resolves it (no member.role matches).

## Common Pitfalls

### Pitfall 1: `ac` Resource — `checkForInvalidResources` Validation

**What goes wrong:** When `dynamicAccessControl.enabled`, `createOrgRole` and `updateOrgRole` call `checkForInvalidResources` which validates that every resource key in the proposed permission is in `ac.statements` (the keys of `PERMISSIONS_STATEMENT`). After adding `ac` to `PERMISSIONS_STATEMENT`, the `ac` resource becomes a valid resource key. This means an owner could technically propose a custom role with `{ ac: ['create'] }` — which would pass `checkForInvalidResources` but MUST be blocked by the RestOS NON_DELEGATABLE filter (D-04) before reaching BA.

**How to avoid:** NON_DELEGATABLE check MUST run in the D-14 wrapper BEFORE calling `auth.api.createOrgRole`, not after.

**Warning sign:** Unit test for `containsNonDelegatable({ ac: ['create'] })` returns `false` — means the filter is missing `ac`.

### Pitfall 2: BA Role Storage Format — JSON String in `permission` Column

**What goes wrong:** `organization_role.permission` is stored as a JSON string (`TEXT` column). BA serializes via `JSON.stringify(permission)` on create and parses via `JSON.parse(permission)` on read. If the D-14 wrapper validates the permission with a Zod schema before passing to BA, the Zod schema must accept the pre-parsed form (`Record<string,string[]>`), not the serialized string.

**How to avoid:** The D-14 wrapper receives a `Record<string,string[]>` from the client, validates it with Zod against `PERMISSIONS_STATEMENT` (check each resource/action is valid), then passes it to `auth.api.createOrgRole`. BA handles the `JSON.stringify`.

**Warning sign:** BA logs `[hasPermission] Invalid permissions for role X` at runtime — means a malformed JSON string is in the DB.

### Pitfall 3: CSV in `member.role` + Custom Roles + Single Role per Member

**What goes wrong:** BA's `parseRoles` in `organization.mjs:20-22` joins arrays with `,`: `Array.isArray(roles) ? roles.join(',') : roles`. If D-05 (one role per member) is enforced at the RestOS layer but NOT at the BA layer, a BA client SDK call that passes `role: ['staff', 'custom-manager']` would create a CSV. `lookupBaseRole` returns `'staff'` for the CSV — correct after D-15 fix. But `PermissionsGuard` would call `hasPermission` which resolves BOTH roles' perms (BA's `hasPermissionFn` splits by `,` and checks each role).

**How to avoid:** The D-14 `assign-role` wrapper must accept only a single role string (not an array), validate it is either a system role slug or an existing `organization_role.role` slug, and reject arrays. Also validate the target is NOT a system role assignment (system roles are assigned at invitation time; 08.3 only manages custom role assignment).

### Pitfall 4: `updateMemberRole` — Creator-Role Protection Blocks Owner Self-Demotion

**What goes wrong:** `crud-members.mjs:265-276` has: if the caller IS the `owner` and is updating themselves AND there's only 1 owner AND the new role is NOT `owner` → throws `BAD_REQUEST YOU_CANNOT_LEAVE_THE_ORGANIZATION_WITHOUT_AN_OWNER`. This is BA's last-owner-lockout protection.

**Impact on 08.3:** If an owner tries to assign themselves a custom role (effectively self-demoting), BA blocks it. This is CORRECT behavior that RestOS inherits for free. The D-06 self-escalation guard in the wrapper should also explicitly block self-demotion attempts (belt-and-suspenders: reject if `actor.userId === targetMemberId AND targetRole.effectivePerms ⊂ actor.currentEffectivePerms`).

**Warning sign:** Test: owner tries to assign themselves the `staff` role → should get 400 (BA blocks). Owner tries to assign themselves `manager` (custom role with fewer perms than owner) → should get 400 from RestOS D-06 guard.

### Pitfall 5: `RLS` Does Not Protect `organization_role` for `resto_auth`

**What goes wrong:** Migration `0054_resto_auth_permissive_policies.sql` gives `resto_auth` a `USING(true)` policy on `organization_role`. This means BA's Drizzle adapter (`buildBetterAuthDrizzleAdapter`) can read/write any org's roles without RLS restrictions. The only isolation is application-level `WHERE organization_id = ?`.

**How to avoid:** NEVER pass a client-supplied `organizationId` to BA endpoints. Always resolve `organizationId` from the server-side ALS (`getTenantContext()?.tenantId`). The D-14 wrapper enforces this — it pins `organizationId` from ALS and ignores any `organizationId` in the request body. This is the same pattern as the existing auth tenant_mismatch check.

### Pitfall 6: `pnpm db:rbac:sync` Does Not Exist

**What goes wrong:** `permissions.ts` comment says "Run `pnpm db:rbac:sync` (added in Phase E) to seed BA." This script does not exist. A planner might create a Wave 0 task to "run this script" that will fail.

**Reality:** System roles (owner/admin/staff) are wired at BA boot via `access-control.ts`, not stored in `organization_role`. The "re-seed" for D-13 means: update the TypeScript files → restart the API → `assertSystemRolesPresent()` validates alignment. No DB seed needed for system roles.
