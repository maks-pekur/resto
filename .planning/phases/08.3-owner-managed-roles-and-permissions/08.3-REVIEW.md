# Phase 08.3: Code Review Report

**Reviewed:** 2026-07-06T00:00:00Z
**Depth:** standard
**Files Reviewed:** 27
**Status:** issues_found

## Summary

Phase 08.3 delivers owner-managed custom roles and permissions on top of better-auth's `dynamicAccessControl`. The core privilege-escalation and cross-tenant isolation invariants hold: `containsNonDelegatable` runs before the BA call on create, update, and assign paths; `organizationId` derives exclusively from `requireTenantContext()` ALS, never from client body; `listActiveCustomRoles` enforces `archivedAt IS NULL`; and the `isSubsetOf` subset check correctly gates assignment authority.

Two security/correctness blockers were found: `archive-role.service` emits a phantom audit event and returns HTTP 204 for non-existent role slugs because there is no pre-update existence check; and the `beforeUpdateMemberRole` defense-in-depth hook permits assignment of roles that exist in BA's routing but are absent from `organization_role` (unknown role slug path returns `null` permission and skips the non-delegatable check). Four warnings cover: the hook also does not filter archived roles, the `permission` DTO has no allowlist or size bounds, the admin client calls a `GET /v1/roles/:roleSlug` endpoint that does not exist on the server, and `archive-role` has no system-slug guard (relying implicitly on member occupation). Four info items are noted.

## Critical Issues

### CR-01: `archive-role.service` silently succeeds for non-existent (and already-archived) role slugs

**File:** `apps/api/src/contexts/identity/application/archive-role.service.ts:46-72`

**Issue:** `ArchiveRoleService.execute` fetches all members (line 32-35), runs an occupation check (line 37-43), then unconditionally issues a Drizzle `UPDATE … SET archivedAt = now() WHERE (organizationId = X AND role = Y)` (line 47-55). When the slug `Y` does not exist in `organization_role` or is already archived, the `UPDATE` matches zero rows and is a silent no-op. Execution continues: `TenantId.parse` runs, `buildEnvelope(IdentityRoleDeletedV1, …)` is called, and the service emits a false `identity.role_deleted.v1` audit event (line 58-70). The HTTP handler returns `204 No Content`.

This produces a lying audit trail for any caller (operator, script, or test) that invokes `DELETE /v1/roles/:someNonExistentSlug`. In contrast, `update-role.service` correctly throws `RoleNotFoundError` when the target slug is absent from `listActiveCustomRoles` (line 35-39) before proceeding.

**Fix:** Add an existence check before the `UPDATE`, mirroring the pattern in `update-role.service`:

```typescript
async execute(input: ArchiveRoleServiceInput): Promise<void> {
  const activeRoles = await listActiveCustomRoles(this.authDb, input.organizationId);
  const target = activeRoles.find((r) => r.role === input.roleSlug);
  if (!target) {
    throw new RoleNotFoundError(input.roleSlug);
  }

  // existing member-occupation check ...
  const memberRows = await this.authDb.db ...
```

`listActiveCustomRoles` is already imported transitively via `update-role.service`; the import just needs to be added to `archive-role.service`. This also makes `archive-role` consistent with the rest of the services.

### CR-02: `beforeUpdateMemberRole` hook silently allows assignment of unknown role slugs

**File:** `apps/api/src/contexts/identity/infrastructure/better-auth/auth.config.ts:259-288`

**Issue:** The hook is the defense-in-depth backstop when a caller bypasses `assign-role.service` and hits BA's `/api/auth/organization/update-member-role` directly (e.g., a scripted call authenticated as the owner). Its logic (lines 252-288) has two branches:

1. If `newRole` is a system slug → `targetPermission` is populated from `SYSTEM_ROLES`.
2. Otherwise → DB query for `organization_role` WHERE `(organizationId = orgId AND role = newRole)`.

When the DB query finds no row (because the role slug is unrecognised, was never created, or is from a different org), `rows[0]?.permission` is `undefined`, the `if (typeof raw === 'string')` branch is skipped, and `targetPermission` remains `null`. The `try/catch` only throws on actual DB errors — zero rows is not an error. Execution falls through to `if (targetPermission && containsNonDelegatable(targetPermission))` which evaluates to `false`, and the hook returns without blocking the assignment.

BA itself may or may not validate role existence in `organization_role` before writing. If it does not (or in future versions changes this behaviour), an actor can assign any arbitrary string slug through the BA endpoint, bypassing the non-delegatable check entirely.

**Fix:** Treat an unknown role (non-system, not in `organization_role`) as a denial, not a pass:

```typescript
const raw = rows[0]?.permission;
if (typeof raw === 'string') {
  targetPermission = JSON.parse(raw) as Record<string, string[]>;
} else {
  // Role slug not found in this org — deny assignment (fail closed)
  throw new ForbiddenException({
    code: 'role.not_found',
    message: 'Target role does not exist in this organisation.',
  });
}
```

Move this inside the `try` block (before the `catch`). The `catch` then continues to cover genuine DB errors with the existing deny message.

## Warnings

### WR-01: `beforeUpdateMemberRole` hook does not filter archived roles

**File:** `apps/api/src/contexts/identity/infrastructure/better-auth/auth.config.ts:261-274`

**Issue:** The DB query in the hook selects from `organization_role` without adding `isNull(organizationRole.archivedAt)` to the WHERE clause. An archived role's row still exists in the table with its `permission` column intact. If a caller hits the BA endpoint directly and requests assignment of an archived role slug, the hook finds the row, reads the (valid) permissions, passes the non-delegatable check if clean, and allows the assignment. The member's `role` column would then reference an archived slug — an inconsistent state.

The primary service path (`assign-role.service`) correctly uses `listActiveCustomRoles` (which filters `archivedAt IS NULL`), so this is not reachable through the normal API. But since the hook is explicitly labelled "defense-in-depth backstop for direct BA endpoint calls", it should close this path too.

**Fix:** Add `isNull(organizationRoleTable.archivedAt)` to the hook's WHERE clause:

```typescript
.where(
  and(
    eq(organizationRoleTable.organizationId, orgId),
    eq(organizationRoleTable.role, newRole),
    isNull(organizationRoleTable.archivedAt),
  ),
)
```

### WR-02: `permission` DTO accepts unbounded arbitrary resource/action strings

**File:** `apps/api/src/contexts/identity/application/dto.ts:14,20`

**Issue:** Both `CreateRoleInputSchema` and `UpdateRoleInputSchema` declare `permission: z.record(z.string(), z.array(z.string()))` with no constraints on key names, action names, or cardinality. This means:

- A client can POST `{ menu: [...10000 actions...] }` — no size cap on the array.
- Unknown resource keys (e.g., `"__admin__"`, `"billing-v2"`) pass straight through and are stored verbatim in `organization_role.permission`, then re-parsed via `JSON.parse` in `listActiveCustomRoles`. BA's `hasPermission` call would evaluate them as real permissions if ever supported.
- `containsNonDelegatable` only checks the known `NON_DELEGATABLE` resources; novel resource names are unchecked.

The `packages/domain/CLAUDE.md` "free-text fields MUST have a max length" rule applies here.

**Fix:** Validate that keys are from `PERMISSIONS_STATEMENT` and actions are within the declared action list for that resource:

```typescript
import { PERMISSIONS_STATEMENT } from '@resto/domain';

const PermissionSchema = z.object(
  Object.fromEntries(
    Object.entries(PERMISSIONS_STATEMENT).map(([resource, actions]) => [
      resource,
      z.array(z.enum(actions as [string, ...string[]])).optional(),
    ]),
  ),
);
```

At minimum, add a `z.record(z.string().max(64), z.array(z.string().max(64)).max(32)).max(16)` to cap cardinality if the strict allowlist approach is too breaking for the current BA integration.

### WR-03: `GET /v1/roles/:roleSlug` is called by the admin UI but does not exist on the server

**File:** `apps/admin/src/lib/queries/roles.ts:30-33` / `apps/api/src/contexts/identity/interfaces/http/roles.controller.ts`

**Issue:** `roleQuery(roleSlug)` in the admin client makes a `GET /v1/roles/${roleSlug}` request. `roles.$roleId.tsx` calls this for every existing role detail page (line 19 — when `roleId !== 'new'`). `RolesController` has only `@Get()` (list all) at line 130; there is no `@Get(':roleSlug')` handler. The server will return 404 for every single-role fetch.

`apiFetch` returns `{ status: 404, ok: false, data: null }` without throwing, so the UI does not crash. Instead, `roleResult?.data` is `null`, and `existingRole` falls back to `undefined` (same as the new-role state). The role edit form renders empty — all permissions appear unchecked — rather than showing the existing role's permissions. An owner attempting to edit a custom role sees a blank form and would inadvertently clear all permissions on save.

This is a data-loss risk (silently blanking permissions on edit) masked behind a graceful-degradation fallback.

**Fix:** Add the missing handler to `RolesController`:

```typescript
@Get(':roleSlug')
@RequiresTenantContext()
@Permissions({ ac: ['read'] })
getRoleHandler(@Param('roleSlug') roleSlug: string) {
  const ctx = requireTenantContext();
  const organizationId = TenantId.parse(ctx.tenantId);
  return wrap(async () => {
    const { roles } = await this.listRoles.execute({ organizationId, headers: new Headers() });
    const role = roles.find((r) => r.role === roleSlug);
    if (!role) throw new RoleNotFoundError(roleSlug);
    return role;
  });
}
```

Or alternatively, change the admin client's `roleQuery` to pull from the already-loaded `rolesQuery` cache instead of issuing a separate HTTP request.

### WR-04: `archive-role.service` has no system-slug guard — relies on member-occupation side-effect for protection

**File:** `apps/api/src/contexts/identity/application/archive-role.service.ts:30-44`

**Issue:** `create-role.service` (line 34) and `assign-role.service` (line 36) both maintain a `RESERVED_SYSTEM_SLUGS = new Set(['owner', 'admin', 'staff'])` guard that rejects system slugs early with a typed domain error. `archive-role.service` has no such check.

For `DELETE /v1/roles/owner`, the service proceeds to fetch all members, finds that the owner member's `role` CSV includes `'owner'`, and throws `RoleOccupiedError`. This provides incidental protection — but it depends on the org always having an owner member. In a corrupted state (owner member row missing), the service would proceed to the `UPDATE` on `organization_role WHERE role='owner'`, match zero rows (since system roles are not in that table), and silently succeed with a false audit event. The missing existence check from CR-01 amplifies this.

**Fix:** Add the system-slug guard identically to `create-role.service`:

```typescript
const SYSTEM_ROLE_SLUGS = new Set(['owner', 'admin', 'staff']);

async execute(input: ArchiveRoleServiceInput): Promise<void> {
  if (SYSTEM_ROLE_SLUGS.has(input.roleSlug)) {
    throw new RoleNotFoundError(input.roleSlug);
  }
  // ...
}
```

This also correctly communicates to the caller that the slug was not found as an archiveable custom role, rather than leaking that `owner` is a special name.

### IN-01: `toWebHeaders` is duplicated four times across the identity context

**File:** `apps/api/src/contexts/identity/interfaces/http/roles.controller.ts:37-52`, `member-roles.controller.ts:28-45`, `guards/auth.guard.ts:174-195`, `guards/permissions.guard.ts:59-71`

**Issue:** The same `toWebHeaders` helper is copy-pasted into four files. The `auth.guard.ts` version correctly collapses the `cookie` header (lines 181-185) to prevent BA session resolution from failing behind a proxy that splits cookies into multiple values. The `permissions.guard.ts` version (line 59-71) is missing this cookie-collapsing logic — it uses `headers.append` for arrays instead of `headers.set` with joined values. Since `PermissionsGuard` calls `auth.api.hasPermission` (which reads the session cookie), this difference could cause session-lookup failures on multi-value cookie headers behind a proxy.

**Fix:** Extract the cookie-aware `toWebHeaders` into a shared module (e.g., `apps/api/src/shared/api/to-web-headers.ts`) and import it from all four sites. The `permissions.guard.ts` copy should be updated to match the cookie-collapsing behaviour from `auth.guard.ts`.

### IN-02: `seed-preset-roles.service` reads archived roles when checking existing slugs

**File:** `apps/api/src/contexts/identity/application/seed-preset-roles.service.ts:20-26`

**Issue:** The existence check query (lines 20-24) selects from `organization_role` with no `archivedAt IS NULL` filter. If an owner archives a preset role (e.g., `'manager'`), the archived slug still appears in `existingSlugs`, and re-seeding (e.g., on subsequent tenant provisioning retries) will not restore it. This is probably intentional (the owner made a deliberate choice to archive), but the code reads as if it's checking for active roles, not all-time slugs.

**Fix:** Document this intention with a WHY comment on the query, or explicitly include `isNull(organizationRoleTable.archivedAt)` in the filter if re-seeding of archived presets is desired. As-is the behaviour is defensible but silently surprising.

### IN-04: `role.cap_reached` error code in admin client has no server-side mapping

**File:** `apps/admin/src/lib/queries/roles.ts:78-80` / `apps/api/src/contexts/identity/interfaces/http/error-mapping.ts`

**Issue:** The admin client's `friendlyRoleError` (lines 78-80) handles a `role.cap_reached` error code for HTTP 400 responses. BA emits this when `maximumRolesPerOrganization: 25` is hit (configured in `auth.config.ts:226`). However, `mapIdentityError` in `error-mapping.ts` has no entry for this BA-generated error body. BA's error will surface as an unmapped response through `ProblemDetailsFilter`, likely as a `BadGatewayException` or raw BA body, rather than the `400 { code: 'role.cap_reached' }` the client expects. The admin UI's friendly message for this case will never display.

**Fix:** Catch BA's cap error in `createOrgRole` call (likely a specific BA error type or response code) and translate it to a `ConflictException` or `BadRequestException` with `code: 'role.cap_reached'` in `error-mapping.ts` or `create-role.service.ts`.
