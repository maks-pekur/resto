# Phase 08.3: Owner-managed Roles & Permissions - Context

**Gathered:** 2026-07-04
**Status:** Ready for planning
**Security review:** REQUIRED before code — re-enabling dynamic access control is a privilege-escalation surface; the creator-subset + assignment-subset guards ARE the gate that kept it disabled.

<domain>
## Phase Boundary

Phase 08.3 turns on **owner-authored custom roles (dynamic RBAC)** — the founder's
headline access feature — and nothing beyond it. Concretely it delivers:

1. **Enable better-auth `dynamicAccessControl`** (currently `enabled: false` at
   `auth.config.ts:212`), which is a no-op until the platform prerequisites (D-13/D-14)
   land.
2. **A creator-subset privilege-escalation guard on BOTH the create/update AND the
   assignment paths** (a role's creator may grant only permissions they themselves hold;
   an assigner may assign only a role whose effective permissions are a subset of their
   own; a member cannot self-escalate).
3. **Owner-facing admin UI** to create/edit a role from a permission catalog, plus a
   **minimal assignment surface** (active-member list + per-member role picker) so a role
   can actually be attached to a human end-to-end.
4. **Persist tenant-defined roles** (better-auth `organization_role` table) and reuse the
   existing `@resto/domain` `PERMISSIONS_STATEMENT` + `SYSTEM_ROLES` + permission-checker.

**Explicitly OUT of scope** (belongs to other phases — see Deferred):
- The full team-management page (pending invitations, revoke, bulk in-place role change,
  2FA lost-device reset for subordinates) → **Phase 17**.
- Per-brand / per-location roles ("manager of brand X") → closer to **Phase 08.4**.
- Multi-role composition per member → post-MVP.
- The immutable system roles (`owner`/`admin`/`staff`) stay unchanged and are not weakened.

</domain>

<decisions>
## Implementation Decisions

### Authoring & assignment authority

- **D-01 — Owner-only authoring.** Only the `owner` may create / edit / delete custom
  roles in this phase. `SYSTEM_ROLES` currently grants role-management to `admin` too
  (`system-roles.ts` — `staff:['role:create','role:update']`); admin-authoring is
  deferred (fits Phase 17). Owner-only collapses the create-side subset check to
  near-trivial but the guard MUST still exist (see D-06) for the assignment path and
  future admin-authoring.
- **D-02 — Owner-only assignment.** Only the `owner` may assign a role to a member in this
  phase. This directly contains CTO **C-1** (better-auth's `updateMemberRole` gates only
  on `{member:['update']}` and never runs the role-subset check). Even with owner-only
  assignment, the assignment path MUST enforce the subset + self-escalation guard so the
  invariant holds when admin-assignment is later enabled.

### Permission model

- **D-03 — Role = tenant-wide permission set; brand access stays orthogonal.** A custom
  role is org(=tenant)-scoped in better-auth: it defines WHAT actions are allowed, across
  all brands. WHICH brands a member can reach remains governed by 08.2's
  `member_brand_scope` + `BrandScopeGuard`. **This interaction MUST be explicitly
  reconciled and tested** — a custom role does not (and must not) widen brand reach; a
  member's effective access = (their brand scope from 08.2) ∩ (their role's permissions).
  Skeptic **CRITICAL-2**: custom roles today bypass everything 08.2 shipped because
  `BrandScopeGuard` keys only on `baseRole==='owner'` + the scope table and has zero
  awareness of `organization_role`.
- **D-04 — NON_DELEGATABLE allowlist.** A fixed set of permissions NEVER enters a custom
  role, even if the authoring owner holds them: `tenant:delete`, `tenant:transfer`,
  `billing:update`, the role-management permission (the new `ac:*` per D-13),
  `staff:remove`. Enforced on BOTH the create/update path AND the assignment path. Bound
  in `@resto/domain`. (CTO **C-3**; prior `AUDIT.md:129`; founder choice.)
- **D-05 — One role per member.** A member holds exactly one role — a system role XOR a
  custom role. No multi-role composition this phase (avoids better-auth CSV `member.role`
  ambiguity that already broke base-role lookup — CTO **H-1**).
- **D-06 — Creator/assigner subset rule.** A creator may grant only permissions within
  their own EFFECTIVE permission set (system role ∪ assigned custom role) minus
  NON_DELEGATABLE. An assigner may assign only a role whose effective permissions ⊆ their
  own effective set. A member can never assign themselves a role stronger than they
  currently hold. Prove with an e2e that an `admin`-tier actor cannot mint/assign a
  `tenant:delete`/`billing:update`-bearing role. (CTO **C-1/C-3**.)

### Role-builder UX (presets-first)

- **D-07 — Presets-first, not blank-matrix-first.** Seed 2–3 ready-to-assign preset roles
  (working names, RU/EN job language: **Менеджер / Manager**, **Кассир-зал / Cashier-FoH**,
  **Кухня / Kitchen**). The custom-role flow is **"duplicate a preset/system role and
  tweak"**, not an empty 20+ checkbox grid. Owners think in job titles, not `menu:update`.
  (Product **H-2**; Toast's "Jobs" model.)
- **D-08 — Catalog UI grouped by resource, dangerous perms hidden.** Present the permission
  catalog grouped by resource (`menu / order / staff / reports / settings / billing /
  brand / …`) with progressive disclosure / tri-state toggles. The NON_DELEGATABLE
  permissions (D-04) are hidden from the custom-role editor entirely, not merely disabled.
  (Product **M-1**.)
- **D-09 — Role naming.** Per-tenant unique role names; the reserved system slugs
  (`owner`/`admin`/`staff`) cannot be used for a custom role (better-auth
  `organization_role.role` is free-text — guard server-side). (Product **M-4**; skeptic
  shadow-name omission.)

### Assignment surface

- **D-10 — Minimal assignment surface ships in 08.3.** Include an active-member list with a
  per-member role picker (owner-only) so SC#2 ("assign a role to staff") works end-to-end.
  Without it the feature dead-ends (owner authors a role, no human to attach it to —
  Product **H-1**; today `team.tsx` shows pending invitations only, member-role control was
  deferred to Phase 17). Show "who's on this role" member counts where cheap (Product
  **M-2**). The FULL team page stays in Phase 17.

### Role lifecycle

- **D-11 — Edits apply on next request.** Permission changes to a role take effect on the
  member's next request (better-auth resolves per-request). MUST confirm better-auth role
  cache (`cacheAllRoles`) invalidation so a *removed* permission actually stops working
  immediately (CTO **H-3**). A confirm dialog surfacing blast radius (N members affected)
  on edit is desirable (Product **M-3**).
- **D-12 — Deleting an occupied role is blocked.** A role with assigned members cannot be
  deleted until those members are reassigned; deletion is soft (archive), consistent with
  the project's no-hard-delete rule. No silent fallback-to-`staff` (avoids surprising a
  member mid-shift).

### Platform prerequisites (locked constraints — verified, not open questions)

> These are not "gray areas" — they are must-do groundwork the reviewers verified against
> better-auth 1.4.22 source. Recorded here so the planner treats them as in-scope.

- **D-13 — The "flip the flag" premise is incomplete; add an `ac` resource + re-seed.**
  Enabling `dynamicAccessControl` as-is returns 403 for everyone, including the owner:
  better-auth's role-CRUD gate checks `{ ac: ['create'] }`, but `PERMISSIONS_STATEMENT`
  has no `ac` resource — it encodes role management as `staff:['role:create','role:update']`,
  a vocabulary better-auth never consults (CTO **C-2**, verified; skeptic **CRITICAL-1** /
  `AUDIT.md:128` "dynamicAccessControl фактически мёртв"). Add
  `ac: ['create','read','update','delete']` to the statement, grant it to `owner`, re-seed
  better-auth, and retire the parallel `staff:role:*` scheme. Resolve the
  **`:`-in-action-name** violation at the same time — rename `role:create`/`role:update`
  (domain rule: "Action names MUST NOT contain `:`"; CTO **M-1** / skeptic **HIGH-6**).
- **D-14 — Wrap better-auth role endpoints in RestOS operator controllers.** Do NOT expose
  `/api/auth/organization/*-role` (create/update/delete role, updateMemberRole) directly to
  the browser. A RestOS wrapper controller is the single leverage point for: the subset
  guard (D-06), NON_DELEGATABLE (D-04), the assignment guard (D-02), audit emission (D-16),
  cross-tenant pinning, and rate-limiting. (CTO top-2.)
- **D-15 — Fix base-role resolution for custom-role members.** `AuthGuard.lookupBaseRole`
  returns `undefined` for a member whose `member.role` is a custom slug (not a system
  role), which breaks `BrandScopeGuard`'s owner-bypass branch. Resolve custom-role members
  to a non-owner base-role floor derived from their system membership. (CTO **H-1**;
  applies even under one-role-per-member D-05.)
- **D-16 — Audit role-definition changes.** Emit `identity.role_created.v1` /
  `identity.role_permissions_changed.v1` / `identity.role_deleted.v1` from the D-14 wrapper
  (better-auth has no create/update/delete-role hooks; only `afterUpdateMemberRole`, which
  already covers assignment via `identity.role_changed.v1`). Add a `role` target kind to
  `ACTION_TARGET_KIND`. "Who granted `billing:update` to which role" must be answerable.
  (CTO **H-2**.)
- **D-17 — Cap roles per tenant.** better-auth `maximumRolesPerOrganization` defaults to
  `Infinity` (abuse/DoS + per-request `findMany` cost). Set a sane per-tenant limit. (CTO
  **H-3**.)

<specifics>
## Specific Ideas

- Founder's headline vision (this phase's core): **the owner creates roles themselves,
  configures each role's permissions from the catalog, and assigns roles to staff** —
  owner-authored dynamic RBAC on top of better-auth's `dynamicAccessControl`.
- Presets named in restaurant job language, RU/EN both (Менеджер/Manager,
  Кассир-зал/Cashier-FoH, Кухня/Kitchen); the custom path is "duplicate & tweak", not a
  blank grid.
- Founder wants tamper-resistant, server-enforced guards (consistent with 08.2's rejection
  of client-forgeable state) — which is why the subset + assignment + self-escalation
  guards and the D-14 server-side wrapper are non-negotiable.

</specifics>
