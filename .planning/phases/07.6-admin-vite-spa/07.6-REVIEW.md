## Summary

Phase 7.6 re-platformed `apps/admin` from Next.js to a Vite+React+TanStack SPA. The security-critical INTERNAL_API_TOKEN data path is gone — no references survive into the new SPA. The auth re-platform to better-auth session cookies is structurally sound: `credentials: 'include'`, `AbortSignal.timeout`, the `x-tenant-id` derived from `activeOrganizationId`, and the open-redirect guard in `safe-next.ts` are all correctly implemented. The server-side tenant cross-check in `AuthGuard` (RES-172) means a forged `x-tenant-id` still cannot read another tenant's data.

Four critical bugs were found, all on the client side. Three are call-to-nonexistent-API-endpoint bugs (dead network calls that will always 404/500), and one is a forgeable `x-tenant-id` production path that leaks identity security to a header the middleware doesn't accept on operator routes in production. Five warnings cover mutation retry unsafety, a race in `useDebouncedAutosave`, a status filter mismatch, the `draft-diff` missing brand scope, and a stale `timingSafeEqualString` length short-circuit that leaks token length.

## Critical Issues

### CR-01: `x-tenant-id` not accepted on operator routes in production — tenant context silently unbound

**File:** `apps/admin/src/lib/api-client.ts:38` + `apps/api/src/shared/tenant-context.middleware.ts:121-130`

**Issue:** The SPA sends `x-tenant-id: <activeOrganizationId>` on every request. `TenantContextMiddleware.shouldAcceptTenantSlugHeader` only honors that header when: (a) `NODE_ENV === 'development' | 'test'`, OR (b) the URL starts with `/internal/v1/` AND has a valid `x-internal-token`. In production, operator calls to `/v1/catalog/*`, `/v1/tenants/*`, etc. will never hit branch (b) — those URLs do not start with `/internal/v1/`. The middleware falls through to host-based resolution. If the API is deployed on a generic host (not a per-tenant hostname), `tenantId` is never bound to ALS, every `@RequiresTenantContext()` route returns 403 `auth.tenant_context_missing`, and every catalog/tenancy read is broken.

This is a production-only failure (dev works because of the `NODE_ENV === 'development'` gate), which makes it easy to miss in local testing.

**Fix:** The middleware must accept `x-tenant-id` from a session-authenticated request on all operator routes, not only internal ones. The cross-check in `AuthGuard` (`auth.tenant_mismatch`) already enforces that the header value must match the session's `activeOrganizationId`, so accepting it on operator routes does not open a new escalation path. Change `shouldAcceptTenantSlugHeader` to return `true` when the request carries a valid bearer/session (or add a separate resolution path that runs after the session is available). Alternatively, resolve tenant from `session.activeOrganizationId` directly inside `AuthGuard` rather than relying on the middleware header path.

### CR-02: `reorderCategories` calls wrong endpoint — loops `POST /v1/catalog/categories` instead of `POST /v1/catalog/categories/reorder`

**File:** `apps/admin/src/lib/queries/catalog.ts:208-219`

**Issue:** The client `reorderCategories` function iterates over moves and calls `POST /v1/catalog/categories` (the upsert endpoint) for each move. The correct endpoint is `POST /v1/catalog/categories/reorder` (which expects a `ReorderCategoriesInputDto` with the full moves array in one call). The upsert endpoint has a different schema — it expects a `UpsertCategoryInputDto` — so sending a raw `{ id, parentId, sortOrder }` object hits the wrong handler, will fail schema validation, and the API will return 400. Even if it happened to succeed, it would loop N HTTP round-trips where one is intended and would mutate the category (not just its order).

**Fix:**

```typescript
export const reorderCategories = (
  brandSlug: string,
  moves: { id: string; parentId: string | null; sortOrder: number }[],
) =>
  apiFetch('/v1/catalog/categories/reorder', {
    method: 'POST',
    body: { moves },
    brandSlug,
  });
```

### CR-03: `resetStopList` and `upsertItemModifierGroups` call endpoints that do not exist in the controller

**File:** `apps/admin/src/lib/queries/catalog.ts:260-263` and `281-284`

**Issue:**

- `upsertItemModifierGroups` calls `POST /v1/catalog/items/modifier-groups`. No such route exists in `CatalogController`. The controller has `/v1/catalog/items` (upsert item) and `/v1/catalog/modifier-groups` (upsert modifier group), but no endpoint for associating modifier groups to items by a separate call.
- `resetStopList` calls `POST /v1/catalog/stop-list/reset`. No such route exists in `CatalogController`. The only stop-list endpoints are `POST /v1/catalog/stop-list` (add) and `DELETE /v1/catalog/stop-list/:itemId` (remove one).

Both calls will receive 404 responses from the API at runtime. Any UI code path that calls these functions is silently broken.

**Fix:** Either implement the missing endpoints on the API side, or remove the client stubs and implement the functionality using the existing endpoints (e.g., `resetStopList` can be composed from individual `DELETE` calls; `upsertItemModifierGroups` likely belongs in the item upsert payload).

### CR-04: `draft-diff` endpoint lacks `@RequireBrand()` but client passes `brandSlug` — brand-scoped data can be read without a bound brand

**File:** `apps/api/src/contexts/catalog/interfaces/http/catalog.controller.ts:368-375` + `apps/admin/src/lib/queries/catalog.ts:195-199`

**Issue:** `GET /v1/catalog/draft-diff` is decorated with `@Permissions({ menu: ['read'] })` and `@RequiresTenantContext()` but has **no `@RequireBrand()`** decorator. All other catalog read endpoints carry `@RequireBrand()`. The client does pass `brandSlug` in the `x-brand-slug` header, but the service executing the query may operate without a resolved brand context (depending on how `GetDraftDiffService` consumes brand scope). If `GetDraftDiffService` reads draft data tenant-wide instead of brand-scoped, an operator with access to one brand can see unpublished draft changes across all brands in the tenant. Conversely, if the service does require brand context but `@RequireBrand()` is absent, the guard that would reject requests without a resolved brand never fires, making the behavior undefined.

**Fix:** Add `@RequireBrand()` to `getDraftDiff()` to match the rest of the catalog read endpoints:

```typescript
@Get('draft-diff')
@HttpCode(HttpStatus.OK)
@Permissions({ menu: ['read'] })
@RequireBrand()          // add this
@ApiOkResponse({ type: DraftDiffResponseDto })
@ApiForbiddenResponse({ type: ProblemDetailsDto })
getDraftDiff(): Promise<DraftDiffResponseDto> {
  return wrap(() => this.getDraftDiffService.execute());
}
```

## Warnings

### WR-01: TanStack Query client retries GETs — double-fires mutation side-effects if a query is also a mutating call

**File:** `apps/admin/src/lib/query-client.ts:6-8`

**Issue:** `defaultOptions.queries` has `retry: 1`. The `apiFetch` function in `api-client.ts` already implements its own GET retry (up to 2 attempts on 5xx). TanStack Query will then retry the query function again on error, resulting in up to **4 total attempts** for a GET (2 from `apiFetch` inner loop × 2 from TQ retry). For true read queries this is an annoyance; for any query function that has side effects (e.g., a `queryFn` that calls an endpoint that happens to mutate), it creates unsafe amplification. More practically, after a network error the UI may already be showing stale data while TQ fires a second round of retries, creating confusing double-refresh jitter. The `apps/CLAUDE.md` rule is "one retry, only on idempotent GET 5xx" — having retry logic in two places violates the single-point-of-truth intent.

**Fix:** Set `retry: 0` on `defaultOptions.queries` and rely solely on the retry logic already in `apiFetch`, which is purpose-built for this codebase's rules.

### WR-02: `useDebouncedAutosave` — `runSave` closure captured from outer scope is stale after re-renders that change `onPersist`/`onState`

**File:** `apps/admin/src/lib/menu/use-auto-save.ts:27-43`

**Issue:** `runSave` is defined inside the `useEffect` body (line 27) and references `onStateRef.current` and `onPersistRef.current` correctly — those are stable ref reads. However `runSave` passes itself as `retry: runSave` (line 42) to `onState({ kind: 'failed', retry: runSave })`. If the consuming component replaces the `onState` callback between the first failure and the retry click, the new `onState` will be called with a `retry` that points back to the `runSave` closure created in the original effect. This `runSave` still reads `onStateRef.current` (updated correctly) but the _retry function identity itself_ is the old one. While harmless in most cases, it means the retry path cannot be rebound by effect re-runs — if form or `onPersist` changes between failure and retry, the retry fires the correct `onPersist` (via ref) but the caller cannot swap in a new retry handler via a fresh effect because the stale retry identity is already stored in caller state. This is a latent correctness issue when auto-save is used in a component that reconstructs `onPersist` each render (e.g. a render that captures a new item ID after first-save creation).

**Fix:** Expose `retry` as a stable callback that reads from refs rather than the closure:

```typescript
const runSaveRef = useRef<() => void>(() => {});
// define runSave and assign runSaveRef.current = runSave after definition
// then use: retry: () => runSaveRef.current()
```

### WR-03: `ItemListStatusFilter` client-side enum includes `'paused'` and `'all-except-archived'` which are not valid API values

**File:** `apps/admin/src/lib/menu/zod-schemas.ts:28-33` + `apps/admin/src/lib/queries/catalog.ts:147-156` + `apps/api/src/contexts/catalog/domain/ports.ts:166`

**Issue:** The client defines `ItemListStatusFilter` as `'all-except-archived' | 'draft' | 'published' | 'paused' | 'archived'`. The server's `ItemStatusFilter` is `'all' | 'draft' | 'published' | 'archived' | 'active'`. Two values are mismatched:

- `'paused'` (client) — not a recognized server filter; will be silently dropped by the controller (falls through the `allowed` check, treated as `undefined`, returns all-status items instead of paused-only).
- `'all-except-archived'` — filtered out in `buildItemsQueryString` (line 147) before being sent, so the API receives no `status` parameter and returns `all` status items. This is an implicit convention that is not visible from either end's type definition.

When `status === 'paused'` the user expects to see only stopped items; instead they see everything. This is a silent data display bug.

**Fix:** Align the client enum to the server's type. If "paused" is a display concept that maps to a server-side filter, make the mapping explicit:

```typescript
// In buildItemsQueryString:
const serverStatusMap: Record<ItemListStatusFilter, string | undefined> = {
  'all-except-archived': undefined, // no param → server returns all
  paused: 'active', // or handle via stop-list overlay
  draft: 'draft',
  published: 'published',
  archived: 'archived',
};
```

Or add `'paused'` as a valid value on the server side if it has distinct semantics.

### WR-04: `timingSafeEqualString` leaks token length via early-exit on length mismatch

**File:** `apps/api/src/shared/tenant-context.middleware.ts:133-139`

**Issue:** The custom `timingSafeEqualString` returns `false` immediately when `a.length !== b.length` (line 134). This makes the comparison non-constant-time in the length dimension: an attacker probing `x-internal-token` with values of varying lengths can distinguish "wrong length" (fast return) from "right length, wrong bytes" (full XOR loop). For a token of unknown length, this halves the brute-force search space by confirming the correct length in O(len) probes. Node.js's `crypto.timingSafeEqual` operates on `Buffer`/`TypedArray` of equal length; the idiomatic safe approach is to HMAC both sides with a random key and compare the HMACs, which are always the same length.

**Fix:**

```typescript
import { timingSafeEqual, createHmac, randomBytes } from 'node:crypto';

const HMAC_KEY = randomBytes(32);

const timingSafeEqualString = (a: string, b: string): boolean => {
  const ha = createHmac('sha256', HMAC_KEY).update(a).digest();
  const hb = createHmac('sha256', HMAC_KEY).update(b).digest();
  return timingSafeEqual(ha, hb);
};
```

### WR-05: `DangerZoneCard` — `isOwner` derived from `/v1/me` `baseRole` field, not from a server-enforced ownership check

**File:** `apps/admin/src/routes/(protected)/dashboard/settings.tsx:32` + `apps/admin/src/components/danger-zone-card.tsx:83`

**Issue:** `isOwner` is computed as `me.baseRole === 'owner'` from the `/v1/me` response. The `MeResponse.baseRole` field is populated server-side and comes from `AuthGuard.lookupBaseRole` via `principal.baseRole`, so it is not forgeable by the client. The UI gating is therefore correct as a UX guard. However, `scheduleOffboard` / `cancelOffboard` are both called without passing the `isOwner` flag to the API — the API must enforce the owner-only restriction independently. Checking the API: `POST /v1/tenants/me/offboard` is decorated with `@Permissions({ tenant: ['delete'] })`. Whether `tenant:delete` is restricted to `owner` role only (vs. `admin`) determines whether this is a genuine enforcement gap. If `admin` also has `tenant:delete` permission in the RBAC table, the server-side check does not enforce owner-only, and an admin could initiate offboarding despite the UI hiding the button. This is a defense-in-depth gap if the RBAC config is ever loosened.

**Fix:** Verify that `tenant:delete` is only granted to the `owner` role in the RBAC policy. If not, add an explicit role check in `OffboardTenantService.schedule` that reads `principal.baseRole` and throws if it is not `'owner'`.
