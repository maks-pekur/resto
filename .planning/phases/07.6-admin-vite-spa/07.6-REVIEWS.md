# Cross-Lens Plan Review — Phase 07.6 / CR-04 (per-brand publish rework)

Both lenses independently returned **FIX-THEN-EXECUTE**. Two blockers, one HIGH security gap, several MEDIUM hardening items, and one founder-level scope decision.

## CTO Review (correctness / migration safety) — verdict: FIX-THEN-EXECUTE

### HIGH (blocking)

- **H1 — Migration 0054 has no `meta/_journal.json` entry → `pnpm db:migrate` skips it.** `packages/db/src/cli/migrate.ts:38` runs Drizzle `migrate(db, {migrationsFolder:'./migrations'})`, which applies migrations from `_journal.json`, not by globbing `*.sql`. 54 sql files == 54 journal entries today. Plan 08 `files_modified` lists only `0054_*.sql` + schema; the journal is never edited → Task 4 applies nothing, the four shape checks fail. **[VERIFIED against migrate.ts + journal count.]** Fix: add the idx-54 journal entry (`{idx:54, version:"7", when:<epoch_ms>, tag:"0054_<name>", breakpoints:true}`) and add `packages/db/migrations/meta/_journal.json` to `files_modified`; `tag` must equal the filename minus `.sql`.
- **H2 — `packages/db/test/integration/catalog-menu-versions.spec.ts` breaks and is in neither plan.** Lines 49/71-72/96 `db.insert(catalogMenuVersion)` with no `brandId`; after schema gains `brandId notNull` → compile error + NOT-NULL violation. Task 1 verify only runs `typecheck` over `src/`, so it surfaces later as red CI. Fix: add the spec to plan 08 Task 1 `files_modified`, give inserts a real `brandId`, brand-scope the assertions, run `pnpm --filter @resto/db test` in Task 1 verify.

### MEDIUM

- **M1 — The 08→09 compile seam has no commit boundary.** After wave 1, `@resto/api` does not typecheck (3 `current()` arity errors at `get-published-menu.service.ts:21`, `public-menu.controller.ts:174,196`) until wave 2 Task 2. Fine within one PR, but nothing states 08+09 are a single mergeable unit — a halt between waves or an 08-only merge leaves `main` red, with the **blocking** Task 4 checkpoint sitting inside the broken window. Fix: declare 08+09 one PR, or move the 3 call-site fixes into wave 1 so every wave compiles.
- **M2 — Backfill is non-atomic with the PK swap.** If interrupted after `DELETE … WHERE brand_id IS NULL` but before the composite PK, a re-run's `COALESCE(…,1)` finds no null row and resets **every** brand to version 1 → CDN ETag poisoning (the highest-risk thing). Also the old PK is Postgres-implicit `catalog_menu_version_pkey` (not `_pk`). Fix: wrap migration in a transaction (verify Drizzle does this for mixed DDL+DML), or compute COALESCE before the null-row delete; assert "no brand's version is 1 if its tenant had version>1 pre-migration."
- **M3 — Delayed-publish timer is in-memory + per-pod.** Per-brand keying (`${tenantId}:${brandId}`) is correct and not a regression, but makes per-brand publish a first-class guarantee on a best-effort single-instance mechanism (loses timers on restart; cross-pod cancel impossible). Acceptable at single-replica MVP-1 — but say so in the threat model; the in-process e2e gives false multi-pod confidence.
- **M4 — `doPublish(tenantId, brandId)` must use the brandId param, not `requireBrandContext()`.** Verified the timer `setTimeout` callback runs outside the HTTP ALS; `finalizeMenuPublish` binds tenant but not brand. Add an acceptance check that the v2 UPSERT + envelope use the **parameter**.

### LOW

- L1 — `catalog.e2e.spec.ts:754` "bumps by exactly 1" survives by luck (single-brand fixture, `rows[0]`); make the Task-3 helper refactor touch it too.
- L2 — keep v1 contract exports in `packages/events/src/index.ts` (harmless for in-flight outbox rows; plan says keep — good).
- L3 — the new composite brand FK `onDelete('cascade')` is **load-bearing for erasure** (`0051:69` `DELETE FROM brands` now cascades into version rows, closing a latent orphan gap). Keep exactly as specified.
- L4 — brand isolation is application-only (ScopedTx `eq(brandId)`), RLS enforces tenant only — matches `catalog_brand_stop_version` precedent. Don't claim DB-level brand isolation.

### Verified fine (no action)

No FK points at `catalog_menu_version` (PK swap not blocked); no `catalog.>` NATS consumer (clean v2 cut-over); outbox `type` constraint accepts `.v2`; public path always has a brandId before the ETag (`requireBrandOr404` first); brands get a version row lazily via the publish UPSERT (`?? 1` until first publish); ScopedTx UPSERT conflict target matches the new composite PK; `menuFirstPublishedAt` tenant-wide (Option A) internally consistent.

## Skeptic Review (assumptions / scope / edge-cases) — verdict: FIX-THEN-EXECUTE

- **#1 [HIGH] — Two sibling cross-brand leaks of the EXACT CR-04 class are left untouched.** `GET /v1/catalog/modifier-groups` → `listModifierGroups()` reads `scoped.selectFrom(menuModifierGroups)` with **no brand filter** (`catalog-drizzle.repository.ts:1143`, route `catalog.controller.ts:357` `@RequireBrand`). `GET /v1/catalog/stop-list` → `listStopListWithStoppedAt()` same, **no brand filter** (`:1206`, route `:379`). Both tables carry `brand_id`. **[VERIFIED — both reads are tenant-scoped only.]** The rework closes one leak and ships two of the same class. Fix the brandId filter in plan 08 Task 3 + e2e, or explicitly carve out with written justification.
- **#2 [HIGH] — Migration breaks two existing e2e tests the plans don't list.** `catalog.e2e.spec.ts:761` and `:841` read `menu_version … WHERE tenant_id` with no brand filter / no LIMIT → arbitrary/multi-row after 0054. Plan 09 Task 3's conditional ("_If_ the helper is scoped to a single brand today, parameterise it") is wrong — it's **tenant**-scoped, so an executor reading literally skips the fix. Make it an explicit requirement; list both tests as modified.
- **#3 [MEDIUM] — "full rework now" vs "leak-fix now, rework later" was never weighed in writing.** Original CR-04 was a 2-line `@RequireBrand`+`eq(brandId)` on draft-diff; the founder expanded it to migration + event-v2 + ETag + timer-rekey, folded into a phase that's otherwise code-complete (only Cloudflare deploy 07.6-07 pending). A first paying tenant is overwhelmingly single-brand, where tenant-wide ≡ per-brand. Record the rejected split option + rationale, or split: ship the leak fixes (draft-diff + #1 siblings) as a quick task to close 7.6, and schedule per-brand publish as its own small phase before Phase 8 (Payments) — where publish semantics first meet money.
- **#4 [MEDIUM] — Two inaccurate backfill/ETag claims.** (a) Post-migration brands get **no** row — ETag `"1"` comes from the adapter `?? 1` fallback, not backfill; the "one row per brand" truth/Task-4 check is fragile. (b) RESEARCH:455 "ETag diverges only after first independent publish" is wrong — divergence is baked at backfill for any multi-brand tenant with version>1. Harmless (CDN key is per brand host) but correct the claims.
- **#5 [MEDIUM] — Cross-brand e2e proves the integer, not the content.** Asserts Brand B's `catalog_menu_version` + ETag unchanged, never that Brand B's `GET /v1/menu` **body** is byte-identical. Add a content-isolation assertion. Confirm the `menu-brand-response` fixture (currently single-brand, `:111`) is actually extended to two brand hosts.
- **#6 [MEDIUM] — PK drop hardcodes a name; no rollback.** Drop the PK by querying `information_schema.table_constraints` (type=PRIMARY KEY), not assuming `_pkey`. Forward-only (ADR-0003, no down-migration) → add a pre-migration `pg_dump` of `catalog_menu_version` in Task 4 so a botched backfill is recoverable.
- #7 [LOW] — concurrent publish to two brands is fine; note restart-mid-window (pre-existing Pitfall 1) still drops the timer.
- #8 [LOW] — `menuFirstPublishedAt` tenant-wide means a multi-brand tenant sees every other brand's published items as "modified" in draft-diff (`computeDraftDiff:1268`) — directly contradicts the per-brand purpose. Surface in the user-facing decision log, not buried in a research-resolution block.
- #9 [LOW] — over-engineering check mostly passes; event v2 for a zero-consumer feature is mild ceremony (~6 lines), not worth fighting; no port/adapter over-abstraction.

## Consensus Summary

- Research is accurate; the load-bearing claims (no inbound FK, no `catalog.>` consumer, lazy brand-row UPSERT, public path always brand-resolved, ScopedTx UPSERT mechanics) were independently verified true.
- The change faithfully mirrors the `catalog_brand_stop_version` precedent; no new abstraction.
- The actual CR-04 leak (draft-diff) is correctly closed.

### Agreed concerns (highest priority first)

1. **BLOCKER — migration journal (CTO H1):** add `meta/_journal.json` idx-54 entry + to `files_modified`, else `db:migrate` no-ops. [VERIFIED]
2. **BLOCKER — breaking tests (CTO H2 + Skeptic #2):** `db` integration spec + two `catalog.e2e` helpers (`:761`, `:841`) break on the schema change and aren't owned by any plan; plan 09's conditional wording will be skipped. Make them explicit, list as modified, run `pnpm --filter @resto/db test`.
3. **HIGH security — sibling leaks (Skeptic #1):** `listModifierGroups` (`repo:1143`) + `listStopListWithStoppedAt` (`repo:1206`) leak across brands, same class as CR-04. [VERIFIED] Fold the brand filter in, or explicitly defer in writing. **Founder call.**
4. **MEDIUM — migration robustness (CTO M2 + Skeptic #6, agree):** name-agnostic PK drop, atomic/transactional backfill (no silent reset-to-1 → CDN poisoning), pre-migration `pg_dump`, "no version reset to 1" assertion.
5. **MEDIUM — atomic merge unit (CTO M1):** 08+09 one PR, or move the 3 public-read call-site fixes into wave 1 so every wave compiles (the blocking Task 4 must not sit in a red window).
6. **MEDIUM — test honesty (Skeptic #5 + CTO M4):** assert Brand B's menu **body** unchanged; assert finalize uses the `brandId` param; confirm the 2-brand fixture.
7. **MEDIUM — correct two research claims (Skeptic #4).**
