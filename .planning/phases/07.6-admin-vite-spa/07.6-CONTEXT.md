# Phase 7.6: Admin → Vite SPA - Context

**Gathered:** 2026-06-21
**Status:** Ready for planning

<domain>
## Phase Boundary

Re-platform `apps/admin` from **Next.js 16 (App Router / RSC / server-actions)** to a **static Vite + React + shadcn SPA**, deployed static like qr-menu (Cloudflare Pages/R2 + CDN). Retire the server-only `INTERNAL_API_TOKEN` data path: all admin→API calls move to **operator-authenticated** endpoints (better-auth session + RBAC), closing review **HIGH-7** (per-operator RBAC/attribution).

**No product/feature change.** The existing operator UI surface — menu item/category/modifier-group editors, item-sizes, stop-list, publish/cancel-publish flow, photo upload, draft-diff, brands/domains/payouts/theme, settings, team, onboarding/brand, sidebar nav, dashboard — is **preserved by porting framework-agnostic React components**. Only routing, the data layer, the auth layer, i18n, and deploy are rewritten.

**In scope:**

- Fresh Vite scaffold in `apps/admin`; port `components/` + framework-agnostic `lib/`; big-bang cutover (admin has **zero prod exposure** today — no live migration risk).
- Auth rewrite: `better-auth/react` client, cross-subdomain cookie session, client-side route guard.
- Data layer rewrite: TanStack Router + TanStack Query; all server-actions become client mutations.
- API parity: relocate the 7 catalog **read** endpoints from `internal/v1/catalog` to operator `v1/catalog`, then delete `internal/v1/catalog`.
- i18n rewrite: next-intl → react-i18next (port ru+en JSON, default ru); next-themes → lightweight theme.
- Static deploy (folds the deferred admin slice of Phase 7.5): Cloudflare static + CDN, admin host + TLS, CD on merge; four-surface smoke passes (Phase 7.5 SC#5).

**Out of scope:**

- New operator features / UI redesign (this is a re-platform — visual parity, not new surface).
- Removing `INTERNAL_API_TOKEN` from the system (it still guards `internal/v1/tenants` bootstrap/provisioning — only the admin browser stops using it).
- website (stays Next SSR — it is public/SEO-relevant) and qr-menu (already Vite).
- Per-tenant custom-domain onboarding UX (Phase 7.5 deferred item; wildcard/apex is enough).

</domain>

<decisions>
## Implementation Decisions

### Auth & session

- **D-01: Cross-subdomain httpOnly cookie session.** Admin authenticates to the API via the better-auth session **cookie** with `Domain=.resto.app`, `SameSite=Lax`, `Secure`, `httpOnly`. `admin.resto.app` and `api.resto.app` share the registrable domain → requests are **same-site**, so the cookie is sent normally under `SameSite=Lax`. Fetches use `credentials: 'include'`; the API enables CORS with an explicit allowed origin (not `*`) + `Access-Control-Allow-Credentials: true`. Chosen over a bearer-token-in-storage model: the token stays unreachable from JS (XSS cannot exfiltrate it), and it matches the already-provisioned `AUTH_COOKIE_DOMAIN` env. Dev (`localhost:3000` ↔ `:3001`) is also same-site, so the same model works without env branching.
- **D-02: `better-auth/react` client (`createAuthClient`).** Replaces the current hand-rolled server-actions (`sign-in-and-bind-org.ts`, `sign-out.ts`) wholesale. Use `useSession`, `signIn.email`, `organization.list` / `organization.setActive`, `signOut`. The current 3-call sign-in fan-out (sign-in → list orgs → set-active) is re-expressed through the client. No SDK calls to `/api/auth/*` are hand-written.
- **D-03: Tenant context from session; brand as client state.** The active **tenant/org** is read from the better-auth active organization in the session — the API derives tenant server-side from the session, so the forgeable `x-tenant-id` header (currently injected by `apiFetchInternal`) is **gone**. The active **brand** becomes client state (reflected in the route and/or persisted in localStorage), sent as an explicit request param; access is authorized server-side by the existing **BrandScopeGuard**. The Phase 02 HMAC-signed `resto.active_brand` cookie (02-CONTEXT D-03) is **removed** — a static SPA has no server to sign it, and per D-03 it was only ever a UX hint, never the security boundary.
- **D-04: Client-side route guard replaces `proxy.ts`.** The Next `proxy.ts` cookie-gate (flash-prevention redirect to `/login`) disappears. The SPA guards protected routes client-side: on load / route change, resolve the session (better-auth client); on unauthenticated/401, redirect to `/login`. The open-redirect `next`-param safety (same-origin `/` only, reject `//`) and the 401→`/login?expired=1` behaviour (02-CONTEXT D-10) are re-established client-side.

### Frontend stack

- **D-05: TanStack Router.** Typed routes/params/search-params, native integration with TanStack Query (route loaders + prefetch), culturally aligned with the strict-TS/zod/branded-types codebase. Handles the admin's nested layouts, dynamic params (`:slug`, `:id`), route groups, and brand-in-URL cleanly.
- **D-06: TanStack Query.** Server-state for reads, mutations, cache invalidation, optimistic publish, and the existing debounced auto-save (`lib/menu/use-auto-save.ts`). Subsumes the hand-written `executeWithRetry` retry/timeout logic from `api-server.ts` / `api-server-internal.ts`. Chosen over SWR (weaker mutations/optimistic) and plain fetch (reinventing cache).

### Migration strategy & API parity

- **D-07: Fresh Vite scaffold in `apps/admin`, big-bang.** Build a clean Vite + React 19 + Tailwind 4 + shadcn app; port `components/` (incl. `components/ui/`, `components/menu/`) and framework-agnostic `lib/` (forms, zod schemas, dnd-kit reorder, sonner helpers, localized helpers, slugify, format-age, pluralize). Rewrite only routing + data/auth + i18n. Single cutover — **no Next+Vite coexistence**. Keep the `apps/admin` directory name (downstream CD/host refs depend on it). Justification: admin has **never deployed to prod**, so there is no live-traffic migration — this is "rebuild before first deploy."
- **D-08: Relocate 7 catalog reads to operator, delete `internal/v1/catalog`.** Operator `v1/catalog` already exposes every **write** (POST categories/items/modifier-groups/modifier-options/item-sizes/stop-list/photo-upload-url/publish, DELETE stop-list+publish, PATCH archive). The gap is exactly the 7 **GET reads** on `internal/v1/catalog`: `categories`, `items`, `items/:id`, `modifier-groups`, `modifier-groups/:id`, `stop-list`, `draft-diff`. Move those handlers to `catalog.controller.ts` (`v1/catalog`) with operator guard + tenant-from-session / brand-from-param (instead of token + injected header) reusing the **same application services**, then **delete `internal-catalog.controller.ts`** (admin is its only caller — website/qr-menu use public `/v1/menu`). `INTERNAL_API_TOKEN` / `InternalTokenGuard` **stay** in the system for `internal/v1/tenants` (identity bootstrap + tenancy provisioning). End state: no duplicate internal read-surface, no dead code.

### i18n & framework-coupled bits

- **D-09: react-i18next.** Closest migration from next-intl: keeps the namespaced JSON resources, interpolation, and pluralization; language detection via cookie/localStorage; lazy-load. Port `lib/i18n/messages/{en,ru}.json` with minimal reshaping; default locale **ru** (matches `DEFAULT_LOCALE='ru'` pinned in 04b). Chosen over react-intl (ICU would require reformatting all messages) and a hand-rolled helper (i18next is low-risk for 2 locales with existing infra).
- **D-10: `next-themes` → lightweight theme.** Replace with a small localStorage + `class` toggle (or a tiny lib); light/dark parity with the current `theme-provider.tsx` / `theme-toggle.tsx`. Mechanical.

### Deploy

- **D-11: Mirror the qr-menu static deploy.** Static build → Cloudflare Pages or R2 + CDN (per Phase 7.5 stack, 07.5-CONTEXT D-07/D-08), served at the admin host with TLS, SPA fallback to `index.html` for client-side routing, CD publishes on merge to main. This **folds the deferred admin slice of Phase 7.5** (07.5-CONTEXT scope-change note). Pages-vs-R2 choice and exact host wiring left to planning.

### Claude's Discretion

The following are mine to settle during planning/execution; the founder does not need to weigh in:

- Exact CORS config (allowed-origins list, preflight handling) and dev-port specifics for the cookie/credentials model (D-01).
- Brand-in-URL vs localStorage-only for active-brand state (D-03) — leaning brand-in-URL (shareable, survives refresh, deep-linkable); planner decides with the route tree.
- Theme implementation details (D-10).
- TanStack Router route-tree organization (file-based vs code-based), Query client config (stale times, retry/timeout parity with old wrappers).
- Which `lib/` modules port verbatim vs need a thin rewrite once their server-only imports (`server-only`, `next/headers`) are stripped.
- Cloudflare Pages vs R2+CDN, and whether the static build lands via a temp dir + swap or in-place (D-07/D-11).
