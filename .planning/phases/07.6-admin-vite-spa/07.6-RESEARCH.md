## Summary

Phase 7.6 replaces `apps/admin` (Next.js 16 App Router + RSC + server-actions) with a pure client-side Vite + React 19 SPA. The re-platform has four interlocking pieces: (1) a fresh Vite scaffold with Tailwind 4 + shadcn, (2) an auth layer rewrite to `better-auth/react` SPA client over a cross-subdomain httpOnly cookie, (3) an API-side endpoint relocation that moves the 7 catalog read GETs from the internal token-protected surface to the operator-auth surface (closing HIGH-7), and (4) static deployment on Cloudflare Pages mirroring qr-menu.

The main execution risk is the auth plumbing: the API already has `crossSubDomainCookies` + `trustedOrigins` in `auth.config.ts` and `CORS_ALLOWED_ORIGINS` in `security.ts`, but the admin host (`admin.resto.app`) must be added to both lists at deploy time, and the SPA client must pass `fetchOptions: { credentials: 'include' }` and an explicit `baseURL` pointing at the API host. The endpoint relocation is a well-scoped add-GET-routes-to-existing-controller task because every application service already exists; the only delta is swapping `InternalTokenGuard` for `AuthGuard`+`PermissionsGuard`+`BrandScopeGuard` and deriving tenant/brand from session instead of injected headers.

**Primary recommendation:** Execute as three parallel work-streams — Scaffold+Port, API relocation, and Auth/Deploy — with the Scaffold wave starting first (it unblocks component porting and the route tree, both of which the Auth stream depends on).

### Pattern 1: better-auth SPA Client Setup

**What:** Single auth client instance with organizationClient plugin. `baseURL` must point at the API host (not the SPA host). `fetchOptions.credentials = 'include'` is how the httpOnly cookie is sent cross-origin. [CITED: better-auth.com/docs/concepts/client]

```typescript
// src/lib/auth-client.ts
import { createAuthClient } from 'better-auth/react';
import { organizationClient } from 'better-auth/client/plugins';
import { getEnv } from './env';

export const authClient = createAuthClient({
  baseURL: getEnv('VITE_API_ORIGIN'), // e.g. https://api.resto.app
  fetchOptions: {
    credentials: 'include', // sends the httpOnly session cookie cross-origin
  },
  plugins: [organizationClient()],
});
```

Usage in components:

```typescript
// Session read (reactive)
const { data: session, isPending } = authClient.useSession();

// Organization list (reactive hook added by organizationClient plugin)
const { data: orgs } = authClient.useListOrganizations();

// Active org (from session — persisted in BA session row)
const { data: activeOrg } = authClient.useActiveOrganization();

// Sign in
await authClient.signIn.email({ email, password });

// Set active org (= tenant switch)
await authClient.organization.setActive({ organizationId: org.id });

// Sign out
await authClient.signOut();
```

Note: `useSession` data shape: `{ session: { activeOrganizationId, ... }, user: { id, email, ... } }`. The `activeOrganizationId` is what the SPA must forward as `x-tenant-id`. [CITED: better-auth.com/docs/plugins/organization]

### Pattern 3: TanStack Router Auth Guard

**What:** A pathless route group `(protected)` with `beforeLoad` that checks the session before rendering any child route. [CITED: tanstack.com/router/v1/docs/framework/react/guide/authenticated-routes]

```typescript
// src/routes/(protected)/_layout.tsx
import { createFileRoute, redirect } from '@tanstack/react-router';
import { authClient } from '../../lib/auth-client';

export const Route = createFileRoute('/(protected)/_layout')({
  beforeLoad: async ({ location }) => {
    const session = await authClient.getSession();
    if (!session?.data?.session) {
      const rawNext = `${location.pathname}${location.search}`;
      // apps/CLAUDE.md open-redirect rule: same-origin path, reject //
      const safeNext =
        rawNext.startsWith('/') && !rawNext.startsWith('//')
          ? rawNext
          : '/dashboard';
      throw redirect({ to: '/login', search: { next: safeNext } });
    }
  },
});
```

**401 → /login?expired=1 (D-04):** In the `apiFetch` wrapper, on HTTP 401:

```typescript
if (res.status === 401) {
  // invalidate session cache, then redirect
  void authClient.signOut();
  window.location.href = '/login?expired=1';
}
```

**Open-redirect safety on login `next` param (apps/CLAUDE.md + 02-CONTEXT D-10):**

```typescript
const rawNext = searchParams.get('next') ?? '/dashboard';
const safeDest =
  rawNext.startsWith('/') && !/^\/[\\/]/.test(rawNext) ? rawNext : '/dashboard';
// after signIn success:
navigate({ to: safeDest });
```

### Pattern 4: apiFetch Client Wrapper

**What:** Replaces the server-only `apiFetch` + `apiFetchInternal` with a client-side wrapper that forwards the session cookie and brand header. Must comply with `apps/CLAUDE.md` network rules. [VERIFIED: codebase read]

```typescript
// src/lib/api-client.ts
import { getEnv } from './env';
import { authClient } from './auth-client';

const API_ORIGIN = getEnv('VITE_API_ORIGIN');
const TIMEOUT_GET_MS = 10_000; // apps/CLAUDE.md: 10s reads
const TIMEOUT_MUTATION_MS = 30_000; // apps/CLAUDE.md: 30s mutations

export const apiFetch = async <T>(
  path: string,
  opts: {
    method?: 'GET' | 'POST' | 'PUT' | 'PATCH' | 'DELETE';
    body?: unknown;
    brandSlug?: string;
    signal?: AbortSignal;
  } = {},
): Promise<{ status: number; ok: boolean; data: T | null }> => {
  const session = authClient.getSession(); // sync accessor for current cached value
  const tenantId = session?.data?.session?.activeOrganizationId;
  const isGet = (opts.method ?? 'GET') === 'GET';
  const timeoutMs = isGet ? TIMEOUT_GET_MS : TIMEOUT_MUTATION_MS;
  // compose signals: caller's signal + timeout
  const signal = AbortSignal.any
    ? AbortSignal.any([
        AbortSignal.timeout(timeoutMs),
        ...(opts.signal ? [opts.signal] : []),
      ])
    : AbortSignal.timeout(timeoutMs);

  const headers: Record<string, string> = {
    accept: 'application/json',
    ...(tenantId ? { 'x-tenant-id': tenantId } : {}),
    ...(opts.brandSlug ? { 'x-brand-slug': opts.brandSlug } : {}),
    ...(opts.body !== undefined ? { 'content-type': 'application/json' } : {}),
  };

  const maxAttempts = isGet ? 2 : 1;
  for (let attempt = 1; ; attempt++) {
    const res = await fetch(`${API_ORIGIN}${path}`, {
      method: opts.method ?? 'GET',
      headers,
      body: opts.body !== undefined ? JSON.stringify(opts.body) : undefined,
      credentials: 'include', // D-01: send session cookie
      signal,
    });
    if (
      !isGet ||
      !(res.status >= 500 && res.status <= 504) ||
      attempt >= maxAttempts
    ) {
      // ... parse JSON, return { status, ok, data }
      return parseResponse<T>(res);
    }
    await sleep(500); // one retry on idempotent GET 5xx
  }
};
```

### Pattern 6: D-08 — Operator Catalog GET Handlers (API side)

**What:** Add 7 GET routes to `catalog.controller.ts`. Each handler is identical to its `internal-catalog.controller.ts` counterpart, but guarded with `AuthGuard` (implicit, global), `PermissionsGuard` (`menu:read`), and `@RequireBrand()` where brand context is needed. [VERIFIED: codebase read of both controllers]

### Pattern 7: i18n Migration (next-intl → react-i18next)

**What:** JSON messages port is largely mechanical because `next-intl` and `react-i18next` both use namespaced flat/nested JSON. The interpolation syntax difference is the only non-trivial delta. [CITED: react.i18next.com, multiple sources]

**Interpolation format difference:**

- `next-intl`: `{count}` (ICU style, bare braces)
- `react-i18next`: `{{count}}` (double braces by default)

**Action required:** All 22 interpolated strings in `ru.json` and their `en.json` equivalents must have `{var}` replaced with `{{var}}`. Mechanically done with a find-replace across the two JSON files.

**ICU plurals:** One ICU plural exists (`menu.publishBar.unpublishedChanges`). i18next supports ICU format via `i18next-icu` plugin, OR you can rewrite the single plural in i18next `_plural` key convention:

```json
// Option A: use i18next-icu plugin (keep ICU format verbatim)
// Option B: rewrite to i18next plural convention (simpler, no extra plugin)
"unpublishedChanges_one": "{{count}} неопубликованное изменение",
"unpublishedChanges_few": "{{count}} неопубликованных изменения",
"unpublishedChanges_other": "{{count}} неопубликованных изменений"
```

Option B (i18next native plurals) is recommended — avoids an extra dependency. [ASSUMED]

**Call-site migration:** 77 `useTranslations`/`getTranslations` call-sites. Pattern:

```typescript
// Before (next-intl):
const t = useTranslations('menu.items');
t('addItem'); // → 'menu.items.addItem'
t('fromPrice', { price: '100' }); // → interpolation

// After (react-i18next):
const { t } = useTranslation('menu.items'); // namespace = 'menu.items'
t('addItem');
t('fromPrice', { price: '100' }); // same shape, double-brace in JSON
```

**i18n init:**

```typescript
// src/lib/i18n/index.ts
import i18n from 'i18next';
import { initReactI18next } from 'react-i18next';
import LanguageDetector from 'i18next-browser-languagedetector';
import ru from './messages/ru.json';
import en from './messages/en.json';

i18n
  .use(LanguageDetector)
  .use(initReactI18next)
  .init({
    resources: { ru: { translation: ru }, en: { translation: en } },
    fallbackLng: 'ru', // D-09: default ru
    detection: {
      order: ['cookie', 'localStorage', 'navigator'],
      caches: ['cookie', 'localStorage'],
    },
    interpolation: { escapeValue: false },
    ns: ['translation'],
    defaultNS: 'translation',
  });
```

Note: `next-intl` uses dotted namespace paths as the argument to `useTranslations('menu.items')` which returns a scoped `t`. With react-i18next, you pass the full dotted key or use the `ns` parameter. The cleanest port keeps full key paths: `t('menu.items.addItem')` or scopes via `keyPrefix`:

```typescript
const { t } = useTranslation('translation', { keyPrefix: 'menu.items' });
t('addItem'); // resolves to 'menu.items.addItem'
```

The `keyPrefix` approach preserves the namespace-scoping idiom from `next-intl` with minimal refactoring. [CITED: react.i18next.com/latest/usetranslation-hook]

### Pattern 9: D-10 Theme Toggle

**What:** Replace `next-themes` with a small hook that reads/writes `localStorage` and toggles a `dark` class on `document.documentElement`. Pattern used by many shadcn apps. [ASSUMED]

```typescript
// src/hooks/use-theme.ts
type Theme = 'light' | 'dark' | 'system';
const STORAGE_KEY = 'resto-theme';

export const useTheme = () => {
  const [theme, setTheme] = useState<Theme>(
    () => (localStorage.getItem(STORAGE_KEY) as Theme) ?? 'system',
  );

  useEffect(() => {
    const root = document.documentElement;
    const isDark =
      theme === 'dark' ||
      (theme === 'system' &&
        window.matchMedia('(prefers-color-scheme: dark)').matches);
    root.classList.toggle('dark', isDark);
    localStorage.setItem(STORAGE_KEY, theme);
  }, [theme]);

  return { theme, setTheme };
};
```

**What:** Cloudflare Pages automatically routes all unmatched paths to the root when no top-level `404.html` exists. This is the native SPA fallback behavior. No `_redirects` file needed for a pure SPA. [CITED: developers.cloudflare.com/pages/configuration/serving-pages/]

- Build output: `apps/admin/dist/`
- Pages project root: `apps/admin/dist`
- No `404.html` in dist → all paths fallback to `index.html`

- TLS: Cloudflare provisioned (automatic via Pages)
- CD: GitHub Actions → `wrangler pages deploy apps/admin/dist --project-name resto-admin` on merge to `main`

### Anti-Patterns to Avoid

- **Server-only imports in client code:** `'server-only'`, `next/headers`, `next/cache`, `next/navigation`, `cookies()` from `next/headers`. All must be stripped before porting files.
- **`useTranslations` from `next-intl`:** Will fail at runtime in a non-Next app. Replace with `useTranslation` from `react-i18next`.
- **`redirect()` from `next/navigation`:** Replace with TanStack Router's `throw redirect(...)` in loaders or `navigate(...)` in components.
- **VITE\_\* fallbacks in production:** `import.meta.env.VITE_API_ORIGIN ?? 'http://localhost:3000'` silently breaks prod. Use `getEnv()` that throws.
- **Forwarding `activeOrganizationId` as `x-tenant-id` from stale state:** The SPA must read `activeOrganizationId` from the live session (not a cached prop from a previous render) before each API call. Use `authClient.useSession().data?.session?.activeOrganizationId`.
- **`SameSite=None` for dev:** Do not set `SameSite=None` to "fix" dev — `localhost` is same-site, and `SameSite=None` requires `Secure` (breaks HTTP). The current `SameSite=Lax` works correctly.

## Don't Hand-Roll

| Problem                            | Don't Build                        | Use Instead                                     | Why                                                                                                                                      |
| ---------------------------------- | ---------------------------------- | ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Client-side routing + typed params | Custom router                      | TanStack Router                                 | Type-safe params, search params, loaders, `beforeLoad`, nested layouts — built-in                                                        |
| Server-state cache + mutations     | `useState` + useEffect fetch       | TanStack Query                                  | Cache invalidation, background refetch, optimistic updates, devtools — ~200 edge cases                                                   |
| Auth session state                 | `useState` with manual cookie read | `better-auth/react` `useSession`                | Reactive, syncs across tabs, handles refresh                                                                                             |
| Locale detection                   | Manual `navigator.language` read   | `i18next-browser-languagedetector`              | Handles cookie, localStorage, navigator, htmlTag — priority ordering                                                                     |
| CSRF protection                    | Custom token                       | `SameSite=Lax` + explicit CORS origin allowlist | SameSite=Lax prevents cross-site form submission attacks; CORS prevents cross-origin XHR. No separate token needed for same-site cookie. |

**Key insight:** The most dangerous area for hand-rolling is auth — specifically the open-redirect check and the 401 re-authentication flow. These must use the patterns in Pattern 3 above exactly.

## Common Pitfalls

### Pitfall 1: `apiFetch` forwarding stale `activeOrganizationId`

**What goes wrong:** The SPA caches session data and passes `tenantId` from component props rather than reading fresh from `authClient`. After an org switch, some requests still carry the old tenant ID.
**Why it happens:** TanStack Query's `staleTime` may serve the old value.
**How to avoid:** Read `activeOrganizationId` directly from `authClient.useSession()` (not a memoized component prop) inside the query function.
**Warning signs:** 403 errors from `AuthGuard.tenant_mismatch` cross-check after org switch.

### Pitfall 2: Brand state out of sync with route

**What goes wrong:** User navigates directly to `/dashboard/menu/items` without a `brandSlug` in the route; `x-brand-slug` header is missing; API returns 403 `brand.context_required`.
**Why it happens:** Brand-in-URL requires every route transition to include the brand slug.
**How to avoid:** On `/dashboard` render, if no brand in route, read from `localStorage` and redirect to `/:brandSlug/dashboard/...`; if no stored brand, prompt brand selection. The `BrandScopeGuard` short-circuits when brand header is absent.
**Warning signs:** Intermittent 403 on menu routes after page refresh.

### Pitfall 3: `crossSubDomainCookies` domain format

**What goes wrong:** Cookie domain set to `resto.app` (no leading dot) instead of `.resto.app` — the cookie is only sent to the exact host, not subdomains.
**Why it happens:** Browser cookie domain spec requires leading dot for subdomain sharing.
**How to avoid:** Confirm `AUTH_COOKIE_DOMAIN=.resto.app` in prod env. The existing `env.schema.ts` already validates this (line 255: `'AUTH_COOKIE_DOMAIN must start with "."'`).
**Warning signs:** Login succeeds on `api.resto.app` but session not visible on `admin.resto.app`.

### Pitfall 4: TanStack Router file-based route naming conventions

**What goes wrong:** File named `items.index.tsx` instead of `items.tsx` creates a nested route at `/items/` not `/items`.
**Why it happens:** TanStack Router file-based routing has specific conventions for index routes, pathless groups, and parameter segments.
**How to avoid:** Pathless groups use `_layout.tsx`; index routes use `index.tsx`; params use `$param` prefix; path segments use `.` as separator for nesting.
**Warning signs:** Routes rendering at unexpected paths.

### Pitfall 5: `next-intl` server-side `getTranslations` in server actions

**What goes wrong:** `app/dashboard/.../page.tsx` files currently call `await getTranslations('...')` — this is a server-side call. In the SPA all translation calls become synchronous client-side `useTranslation`.
**Why it happens:** 77 call-sites mix `getTranslations` (server async) and `useTranslations` (client hook). Both become `useTranslation` in the SPA.
**How to avoid:** During port, grep for `getTranslations` and convert every instance to `useTranslation` (hook). Any `await getTranslations` in a file that becomes a React component → refactor to hook call.
**Warning signs:** TypeScript error "cannot call hook in async function".

### Pitfall 6: settings offboard endpoints use `internal/v1/tenants` (NOT catalog)

**What goes wrong:** Planner assumes all `apiFetchInternal` calls are catalog reads. `apps/admin/app/dashboard/(workspace)/settings/actions.ts` calls `/internal/v1/tenants/:id/offboard` (POST and DELETE) — these are NOT in D-08 scope and do not have operator-auth equivalents yet.
**Why it happens:** `apiFetchInternal` is used for both catalog reads AND tenant lifecycle.
**How to avoid:** Identify and separate the two uses (see Open Questions #1). The 7 catalog GETs are safe to relocate; the settings tenant actions need separate treatment.

### Pitfall 7: Cloudflare Pages `_redirects` SPA fallback loop

**What goes wrong:** Adding `/* /index.html 200` to `_redirects` triggers Cloudflare's "infinite loop" detection and the rule is silently ignored.
**Why it happens:** Cloudflare detects redirect-to-self patterns.
**How to avoid:** Do NOT add a `_redirects` file. Cloudflare Pages' native behavior (no `404.html` → SPA mode) handles all routes automatically. [CITED: developers.cloudflare.com/pages/configuration/serving-pages/]

```typescript
// src/routes/(protected)/_layout.tsx
import { createFileRoute, redirect } from '@tanstack/react-router';
import { authClient } from '../../lib/auth-client';

export const Route = createFileRoute('/(protected)/_layout')({

    const session = await authClient.getSession();
    if (!session?.data?.session) {
      const rawNext = `${location.pathname}${location.search}`;
      // apps/CLAUDE.md: reject protocol-relative open redirect
      const safe =
        rawNext.startsWith('/') && !/^\/[\\/]/.test(rawNext)
          ? rawNext
          : '/dashboard';
      throw redirect({ to: '/login', search: { next: safe } });
    }
  },
});
```

| Pattern                                         | STRIDE          | Standard Mitigation                                                                                                                        |

## Open Questions

1. **Settings tenant offboard actions use `internal/v1/tenants` — what replaces them in the SPA?**
   - What we know: `settings/actions.ts` calls `POST/DELETE /internal/v1/tenants/:id/offboard` via `apiFetchInternal`. This is NOT part of D-08 (only catalog GETs). `INTERNAL_API_TOKEN` stays for `internal/v1/tenants`. The static SPA cannot hold the token.
   - What's unclear: Should (a) operator offboard endpoints be added to the regular `v1/tenancy` surface behind operator auth, or (b) the settings danger-zone be deferred to a later phase, or (c) the settings page calls a platform-admin flow?
   - Recommendation: **Add `POST/DELETE /v1/tenancy/me/offboard` operator-auth endpoints** (the tenant derives from session, not an injected ID — safer). This is a small extension to the tenancy context consistent with the operator-auth model. Planner should add this as a task in Wave 1 (API side) alongside D-08.

2. **TanStack Router: file-based vs code-based route tree?**
   - What we know: File-based routing generates the route tree from filesystem conventions; code-based is manual `createRootRoute`/`createRoute` composition.
   - What's unclear: Monorepo Nx build may have opinions about generated file locations (`routeTree.gen.ts`).
   - Recommendation: Use **code-based routing** for the initial scaffold (simpler in a fresh repo, no codegen step, easier for Nx to track). Switch to file-based if the route count grows past ~30 routes.
