# Phase 7.6 Plan 08: CR-04 Per-Brand Publish Rework — Research

**Researched:** 2026-06-26
**Domain:** Catalog publish cycle — schema, services, delayed timer, event contracts, public ETag path
**Confidence:** HIGH (all findings grounded in actual source files)

---

## Summary

CR-04 requires making the entire menu-publish cycle brand-scoped. This research reveals that the work is **asymmetric**: the stop-version side is already brand-keyed (`catalog_brand_stop_version` PK = `(brand_id, tenant_id)`), but the menu-version side is **tenant-wide** (`catalog_menu_version` PK = `tenant_id` only). The delayed-publish timer is also keyed by `tenantId` string throughout. The public ETag for `/v1/menu` derives directly from `catalogMenuVersion.menuVersion`, so making that version per-brand is a **CDN-visible wire change** that affects the cache invalidation key shape. The qr-menu and website currently hit the public menu endpoint against a brand-resolved host (brand's subdomain → `brandId` in ALS), so per-brand ETag behaviour is already the right design — but the ETag value itself must change.

The `computeDraftDiff` method is tenant-wide too (scans all `menuItems` for the tenant); it needs a `brandId` filter to become brand-scoped.

The `tenants.menuFirstPublishedAt` timestamp is shared tenant-wide. Per-brand publish requires either a per-brand equivalent or an accepted semantics decision (first publish = first brand publish). This is a **design decision for the planner**.

**Primary recommendation:** Add `brand_id` to `catalog_menu_version` (new PK `(brand_id, tenant_id)`, composite FK), update all services, the delayed timer, the event payloads (v2), and the public ETag derivation path. This is a 5-layer change: schema migration → port interfaces → repo adapter → services → controller decorators.

### 2. Migration shape (VERIFIED: source + precedent)

**What must change in `catalog_menu_version`:**

The current single-column PK `(tenant_id)` must become a composite PK `(brand_id, tenant_id)` matching the pattern of `catalog_brand_stop_version`.

**Concrete migration — `0054_catalog_brand_menu_version.sql`:**

```sql
-- Step 1: drop existing PK + FK
ALTER TABLE "catalog_menu_version" DROP CONSTRAINT "catalog_menu_version_pkey";
ALTER TABLE "catalog_menu_version" DROP CONSTRAINT "catalog_menu_version_tenant_fk";

-- Step 2: add brand_id column
ALTER TABLE "catalog_menu_version" ADD COLUMN "brand_id" uuid NOT NULL DEFAULT gen_random_uuid();
-- Note: DEFAULT is a migration-only trick; column becomes NOT NULL with real values after backfill.
-- Better approach: add nullable, backfill, then set NOT NULL:

-- Correct approach:
ALTER TABLE "catalog_menu_version" ADD COLUMN "brand_id" uuid;

-- Step 3: backfill — one row per brand, inheriting the tenant's existing version
-- (best: copy current menu_version per tenant to each of its brands)
INSERT INTO catalog_menu_version (brand_id, tenant_id, menu_version)
  SELECT b.id, b.tenant_id,
    COALESCE((SELECT menu_version FROM catalog_menu_version WHERE tenant_id = b.tenant_id LIMIT 1), 1)
  FROM brands b
  ON CONFLICT DO NOTHING;

-- Step 4: delete old tenant-only rows (those without brand_id — i.e., brand_id IS NULL)
DELETE FROM catalog_menu_version WHERE brand_id IS NULL;

-- Step 5: set NOT NULL
ALTER TABLE "catalog_menu_version" ALTER COLUMN "brand_id" SET NOT NULL;

-- Step 6: add composite PK
ALTER TABLE "catalog_menu_version" ADD CONSTRAINT "catalog_menu_version_pk"
  PRIMARY KEY ("brand_id", "tenant_id");

-- Step 7: re-add tenant FK
ALTER TABLE "catalog_menu_version" ADD CONSTRAINT "catalog_menu_version_tenant_fk"
  FOREIGN KEY ("tenant_id") REFERENCES "public"."tenants"("id") ON DELETE no action ON UPDATE no action;

-- Step 8: composite brand FK (ADR-0020 I-2)
ALTER TABLE "catalog_menu_version" ADD CONSTRAINT "catalog_menu_version_brand_fk"
  FOREIGN KEY ("brand_id", "tenant_id") REFERENCES "public"."brands"("id", "tenant_id")
  ON DELETE cascade ON UPDATE no action;

-- Step 9: RLS policies must be re-applied (they survive ALTER TABLE but must be verified)
-- The existing policy uses tenant_id which is still present — it will still work.
```

**Idempotent DO-block wrapping pattern** (from migration `0040` and `0053`): if this migration may run in environments where `catalog_menu_version` already has a `brand_id` column (after a failed partial run), wrap `ADD COLUMN` in `IF NOT EXISTS`:

```sql
DO $$ BEGIN
  IF NOT EXISTS (
    SELECT 1 FROM information_schema.columns
    WHERE table_name = 'catalog_menu_version' AND column_name = 'brand_id'
  ) THEN
    ALTER TABLE "catalog_menu_version" ADD COLUMN "brand_id" uuid;
  END IF;
END $$;
```

**Drizzle schema change** — `packages/db/src/schema/menu.ts`: replace the current `pgTable` definition's `primaryKey` from `tenantId` alone to `(brandId, tenantId)`:

```typescript
export const catalogMenuVersion = pgTable(
  'catalog_menu_version',
  {
    brandId: uuid('brand_id').notNull(),
    tenantId: tenantIdColumn(),
    menuVersion: bigint('menu_version', { mode: 'number' })
      .notNull()
      .default(1),
  },
  (table) => [
    primaryKey({
      name: 'catalog_menu_version_pk',
      columns: [table.brandId, table.tenantId],
    }),
    foreignKey({
      name: 'catalog_menu_version_tenant_fk',
      columns: [table.tenantId],
      foreignColumns: [tenants.id],
    }),
    compositeTenantFk({
      name: 'catalog_menu_version_brand_fk',
      child: { id: table.brandId, tenantId: table.tenantId },
      parent: { id: brands.id, tenantId: brands.tenantId },
    }).onDelete('cascade'),
  ],
);
```

**First-publish timestamp:** `tenants.menuFirstPublishedAt` is currently shared across all brands of the tenant (set on the first `finalizeMenuPublish` call). With per-brand publish, the semantics must be decided:

- **Option A (recommended):** Keep `menuFirstPublishedAt` as "any brand first published" — no schema change. The v1 events remain per-tenant semantics for first-publish detection.
- **Option B:** Add `brands.menuFirstPublishedAt` column — requires additional migration and logic in `finalizeMenuPublish`.

Option A is simpler and appropriate for MVP-1; the planner should confirm.

### 3. Publish/cancel/draft-diff services (VERIFIED: source)

**Current scope resolution in each service:**

`PublishMenuService.execute()` (`publish-menu.service.ts:12-17`):

```typescript
async execute(): Promise<{ tenantId: string; version: number }> {
  const ctx = requireTenantContext();      // reads ALS
  const tenantId = TenantId.parse(ctx.tenantId);
  const { version } = await this.doPublish(tenantId);
  return { tenantId, version };
}
```

No brand context read — `doPublish` calls `repo.finalizeMenuPublish({ tenantId })`.

`DelayedPublishService.schedule(tenantId: string)` — keyed by `tenantId` string (`#pending` Map key is tenantId, `doPublish(tenantId)` takes only tenantId).

`GetDraftDiffService.execute()` (`get-draft-diff.service.ts:11-26`):

```typescript
const ctx = requireTenantContext();
const tenantId = TenantId.parse(ctx.tenantId);
const { items, totalCount } = await this.repo.computeDraftDiff({ tenantId });
```

No brand filter at all — `computeDraftDiff` scans all `menuItems` across brands for the tenant.

**What must change:**

`PublishMenuService.execute()`:

- Call `requireBrandContext()` (from `@resto/db`) to get `brandId`.
- Pass `{ tenantId, brandId }` to `repo.finalizeMenuPublish`.
- Return `{ tenantId, brandId, version }`.

`PublishMenuService.doPublish(tenantId, brandId)`:

- Signature: `async doPublish(tenantId: TenantId | string, brandId: string)`.
- Used by `DelayedPublishService` callback — must accept both params.

`GetDraftDiffService.execute()`:

- Call `requireBrandContext()` to get `brandId`.
- Pass `{ tenantId, brandId }` to `repo.computeDraftDiff`.

**How brand context arrives:** `TenantContextMiddleware` already reads `x-brand-slug` header, resolves via `brands.resolveBrandBySlug(tenantId, slug)`, and stores `brandId` in ALS (`context.ts:73-86`, `withBrand` function). When a route has `@RequireBrand()`, `BrandScopeGuard` checks the resolved brand is in the operator's scope. `requireBrandContext()` then succeeds in any service called from that route.

**`@RequireBrand()` decorator** is `SetMetadata(REQUIRE_BRAND_KEY, true)` (`require-brand.decorator.ts:12`). Adding it to `publishMenu`, `cancelPublishMenu`, and `getDraftDiff` routes will: (1) ensure `BrandScopeGuard` fires, (2) ensure `brandId` is in ALS when the service runs.

### 4. Delayed-publish rework (VERIFIED: source)

**Current implementation** (`delayed-publish.service.ts`):

```typescript
readonly #pending = new Map<string, { timerId: NodeJS.Timeout }>();

schedule(tenantId: string): { cancel: () => boolean } {
  this.#cancel(tenantId);
  // key = tenantId string
  ...
  this.#pending.set(tenantId, { timerId });
  ...
}

cancelPending(tenantId: string): boolean {
  if (!this.#pending.has(tenantId)) return false;
  this.#cancel(tenantId);
  return true;
}
```

The comment in `delayed-publish.service.ts:47-49` explicitly notes that the `setTimeout` callback cannot use `requireTenantContext()` (ADR-0020 I-6) and already uses `publisher.doPublish(tenantId)` with explicit `tenantId`.

**What must change:**

- Map key becomes a brand-scoped composite key: `${tenantId}:${brandId}`.
- `schedule(tenantId, brandId)` signature — pass both.
- `cancelPending(tenantId, brandId)` signature.
- `doPublish(tenantId, brandId)` called in the timer callback.
- `#cancel(key: string)` private method works unchanged (key is now composite string).

**Controller call sites** (`catalog.controller.ts:252-260`, `267-273`):

```typescript
publishMenu(): Promise<PublishScheduledResponseDto> {
  return wrap(() => {
    const ctx = requireTenantContext();
    const tenantId = TenantId.parse(ctx.tenantId);
    this.delayed.schedule(tenantId);   // must also pass brandId
    ...
  });
}

cancelPublishMenu(): Promise<PublishCancelResponseDto> {
  return wrap(() => {
    const ctx = requireTenantContext();
    const tenantId = TenantId.parse(ctx.tenantId);
    const cancelled = this.delayed.cancelPending(tenantId);  // must also pass brandId
    ...
  });
}
```

Both routes lack `@RequireBrand()` today; adding the decorator means `requireBrandContext()` is safe to call in the route handler (ALS already has `brandId`). The concrete brand context is read via `requireBrandContext()` inside the `wrap()` callback (same pattern as `GetPublishedMenuService`).

### 6. Public ETag knock-on — HIGHEST RISK (VERIFIED: source)

This is the most dangerous part of the change.

**Current ETag derivation** (`public-menu.controller.ts:174-175`):

```typescript
const version = await wrap(() =>
  this.menuVersions.current(TenantId.parse(ctx.tenantId)),
);
const etag = '"' + version.toString() + '"';
```

`menuVersions.current(tenantId)` → `PostgresMenuVersionAdapter.current(_tenantId)` which **ignores the tenantId argument** and just `selectFrom(schema.catalogMenuVersion).limit(1)` using ScopedTx.

After rework, `MenuVersionPort.current(tenantId)` becomes `MenuVersionPort.current(tenantId, brandId)` — the port interface signature changes. The adapter must query by both `tenant_id` and `brand_id`.

**ETag value shape:** Currently `"<number>"` (e.g., `"3"`). This is keyed per-tenant. After rework it will still be `"<number>"` but the number is per-brand. Because the CDN caches at the URL+host level, and the public menu URL is already brand-resolved (the qr-menu hits the brand's own subdomain, which routes to the specific brand), the ETag semantics are correct once the version is per-brand — the CDN's cache key is `(brand host, /v1/menu)` which already discriminates brands. **No CDN cache rule change needed.**

**Brand resolution in the public path:** Already brand-aware. `TenantContextMiddleware` calls `brands.resolveByCustomerHost(host)` for the qr-menu subdomain (`brandSlug.menu.resto.app`), which populates `brandId` in ALS. The controller already calls `requireBrandOr404()` (`getBrandId()`) before serving. `GetPublishedMenuService` calls `requireBrandContext()` to get `brandId`.

**Files affected in the public read path:**

1. `apps/api/src/contexts/catalog/domain/ports.ts` — `MenuVersionPort.current(tenantId, brandId)` signature.
2. `apps/api/src/contexts/catalog/infrastructure/postgres-menu-version.adapter.ts` — `current(tenantId, brandId)` reads from per-brand row; `currentStop(brandId)` is already brand-keyed and unchanged.
3. `apps/api/src/contexts/catalog/interfaces/http/public-menu.controller.ts` — passes `brandId` from ALS to `menuVersions.current(tenantId, brandId)`.
4. `apps/api/src/contexts/catalog/application/get-published-menu.service.ts` — `execute` already calls `this.versions.current(tenantId)` and then `requireBrandContext()`. After rework: call `this.versions.current(tenantId, brandId)` passing the brand id.

**qr-menu / website change needed:** None. They call `/v1/menu` against the brand host. Brand is resolved by the middleware from the host. The ETag they receive will correctly be the brand-specific version. No client change.

**Cache-Control headers:** Unchanged — `s-maxage=300, stale-while-revalidate=60` for `/v1/menu`, `s-maxage=5` for `/v1/menu/availability`.

**No-`Set-Cookie` contract:** The `menu-brand-response.e2e` test verifies this. It will continue to pass — nothing in the ETag change touches cookie headers.

### 7. RLS / isolation (VERIFIED: source)

**Existing RLS policy on `catalog_menu_version`** (migration 0048):

```sql
CREATE POLICY "catalog_menu_version_iso" ON "catalog_menu_version"
  USING (is_system_session() OR tenant_id = current_tenant_id())
  WITH CHECK (is_system_session() OR tenant_id = current_tenant_id());
```

The policy uses `tenant_id`. After adding `brand_id` to the PK, the `tenant_id` column is still present and the policy still holds — tenant isolation is maintained. A `resto_app` session can only see/write rows for `current_tenant_id()`.

**Brand-level isolation within the tenant:** RLS does not filter by brand (that is by design — all brands of a tenant share one Postgres role session). The ScopedTx `withTenant` callback ensures queries include `tenant_id` filter. The new `brand_id` filter in UPSERT and SELECT is enforced at the application layer (both in the adapter and ScopedTx's extra `eq()` argument).

**`ScopedTx` call sites for `catalog_menu_version`:** The UPSERT in `finalizeMenuPublish` goes through `scoped.insertInto(schema.catalogMenuVersion, ...)` which ScopedTx auto-injects `tenantId` on INSERT. With the new composite PK `(brand_id, tenant_id)`, ScopedTx's auto-inject of `tenant_id` still applies — the caller must also supply `brand_id` explicitly (same pattern as `catalog_brand_stop_version`).

**`PostgresMenuVersionAdapter.current()` after rework** must use the extra-filter pattern:

```typescript
async current(tenantId: TenantId, brandId: string): Promise<number> {
  return this.db.withTenant(async (_tx, scoped) => {
    const rows = await scoped
      .selectFrom(schema.catalogMenuVersion,
        eq(schema.catalogMenuVersion.brandId, brandId))
      .limit(1);
    return rows[0]?.menuVersion ?? 1;
  });
}
```

This matches the existing pattern in `currentStop(brandId)` (line 18-27 of the adapter).

**No new RLS policy change needed** — existing tenant-isolation policy suffices. Brand-level isolation is application-enforced, consistent with all other brand-scoped tables.

### 9. Landmines / Sequencing

**Migration-before-code ordering:** The migration `0054` must be applied before the new service/adapter code goes live. The planner's Wave 0 must be: migration → Drizzle types regenerated → application code changes.

**Backfill correctness:** The migration must correctly copy each tenant's current `menu_version` into each of the tenant's brands' rows. If a tenant has 3 brands, all 3 should get the same current version (so no brand incorrectly starts at 1). The INSERT…SELECT in the migration handles this.

**ETag cache invalidation on deploy:** On first deploy after the version-per-brand migration, every brand's `catalog_menu_version` row has the tenant's old version value (backfilled). The ETag shape is unchanged (`"<number>"`). Existing CDN cache entries keyed by brand host + `/v1/menu` with the old ETag will still match the ETag from the new per-brand rows (because they have the same integer value). **This is safe — no cache poisoning.** The ETag value will only diverge between brands after their first independent publish post-migration.

**`computeDraftDiff` brand filter vs. `menuFirstPublishedAt`:** The `computeDraftDiff` query uses `tenants.menuFirstPublishedAt` as the reference timestamp for "modified" status detection. This field is per-tenant. After rework, if brand A has been published but brand B has not, brand B's items will appear as "modified" (not "draft") once `menuFirstPublishedAt` is set. This is an edge case — documenting it as a known limitation is sufficient for MVP-1.

**`DelayedPublishService.onModuleDestroy()`:** Clears all pending timers on shutdown. With composite key, this is unchanged — all entries in `#pending` are cleared regardless of key shape.

**`@RequireBrand()` on `cancelPublishMenu`:** When an operator clicks Undo within the 5s window, they must send the same brand header as the publish. If the cancel request doesn't include `x-brand-slug`, it will 403. The admin client (`apps/admin/src/lib/queries/catalog.ts:322-326`) already passes `brandSlug` on cancel — no admin change needed. But the 403 behaviour is new (currently cancel succeeds even without a brand header). This is correct per the founder's decision.

**Port interface signature change is a compile-time break:** `MenuVersionPort.current(tenantId: TenantId): Promise<number>` is exported and consumed in `GetPublishedMenuService` and `PostgresMenuVersionAdapter`. Changing to `current(tenantId: TenantId, brandId: string): Promise<number>` will cause a TypeScript compile error in all implementors and callers — this is the desired behaviour (fail-fast; no silent miss).

## Architecture Patterns

### Per-Brand UPSERT Pattern (follow `catalog_brand_stop_version`)

The stop-version adapter (`postgres-menu-version.adapter.ts:18-27`) is the blueprint:

```typescript
async currentStop(brandId: string): Promise<number> {
  return this.db.withTenant(async (_tx, scoped) => {
    const rows = await scoped
      .selectFrom(
        schema.catalogBrandStopVersion,
        eq(schema.catalogBrandStopVersion.brandId, brandId),  // extra filter
      )
      .limit(1);
    return rows[0]?.stopVersion ?? 1;
  });
}
```

Replicate this exact pattern for `current(tenantId, brandId)`.

### UPSERT with Brand Scope (from `finalizeMenuPublish`)

Currently (tenant-scoped):

```typescript
const bumped = await scoped
  .insertInto(schema.catalogMenuVersion, { menuVersion: 2 })
  .onConflictDoUpdate({
    target: [schema.catalogMenuVersion.tenantId],
    set: { menuVersion: sql`${schema.catalogMenuVersion.menuVersion} + 1` },
  })
  .returning({ menuVersion: schema.catalogMenuVersion.menuVersion });
```

After rework (brand-scoped):

```typescript
const bumped = await scoped
  .insertInto(schema.catalogMenuVersion, { brandId, menuVersion: 2 })
  .onConflictDoUpdate({
    target: [
      schema.catalogMenuVersion.brandId,
      schema.catalogMenuVersion.tenantId,
    ],
    set: { menuVersion: sql`${schema.catalogMenuVersion.menuVersion} + 1` },
  })
  .returning({ menuVersion: schema.catalogMenuVersion.menuVersion });
```

ScopedTx auto-injects `tenantId` on INSERT; `brandId` must be passed explicitly.

## Open Questions

1. **`menuFirstPublishedAt` semantics with per-brand publish:** Currently a single tenant-wide timestamp. Should it become per-brand (add `brands.menuFirstPublishedAt`)? Or keep as "any brand first published" (tenant-wide)? Recommend keeping tenant-wide for MVP-1 to minimise scope.

2. **Audit subscriber subject update:** Does the `audit` context subscribe to `catalog.menu_first_published.v1` and `catalog.menu_republished.v1` explicitly, or via wildcard? If explicit, the subscriber must be updated (or kept) for v2.

3. **Event versioning policy:** Should v1 events be emitted in parallel with v2 during a transition, or is a clean cut-over acceptable (since no external consumers exist yet)?

## Security Domain

No new security surface introduced. The change narrows scope (requires brand resolution before publish — stricter, not looser). `@RequireBrand()` on `publishMenu`/`cancelPublishMenu`/`getDraftDiff` adds the `BrandScopeGuard` check, which is an improvement.

ASVS V4 (Access Control): Adding `@RequireBrand()` to publish routes closes the gap identified in CR-04 — a route that read brand-scoped data without the brand guard is now guarded.
