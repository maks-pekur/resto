## Accomplishments

- `LocationId` branded type added to `packages/domain/src/ids.ts`, mirroring the existing `BrandId` pattern (`z.string().uuid().brand<'LocationId'>()`), re-exported from the package barrel (`index.ts`)

- Dedicated admin-escalation regression spec (`packages/domain/test/rbac/system-roles.spec.ts`) pins: admin lacks `ac`, admin/staff `location` is read-only, and only `owner` holds `ac` across all three system roles

## Decisions Made

- **admin.location grain = `['read']`** — plan left this at "planner discretion, default `['read']`"; kept admin read-only on locations so location create/update/delete stays owner-exclusive, consistent with D-15's owner-only assignment-matrix gate for this phase.
- **NON_DELEGATABLE regression check narrowed to `tenant`/`billing`/`ac`** — a literal loop over every `NON_DELEGATABLE` resource (including `staff: ['remove']`) fails against the codebase's actual, pre-existing, and intentional state: `SYSTEM_ROLES.admin.staff` already includes `'remove'` (shipped in 08.3, and explicitly excluded from `packages/domain/CLAUDE.md`'s own canonical "must NOT receive" example, which lists only `tenant:delete`/`tenant:transfer`). `NON_DELEGATABLE` governs what's delegatable to tenant-created custom roles, not the hardcoded admin system role's fixed grants. Scoped the regression to the resources actually relevant to this phase's escalation threat (T-084-04): the new `location` resource and the `ac` gate.
