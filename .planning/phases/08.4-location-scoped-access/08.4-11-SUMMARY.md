## Accomplishments

- `location-isolation.e2e.spec.ts` — сеет один tenant, owner, два бренда (brand1 с двумя локациями A/B, brand2 с одной локацией C) и non-owner (`admin`), scoped только на локацию A через `member_location_scope` (актуальная D-04-модель, не устаревшая `member_brand_scope`).
- Доказано через реальные HTTP-запросы к `GET /v1/catalog/stop-list` (единственный default-on, не-`@LocationNeutral()` роут в приложении):
  - D-05: подделанный `x-location-id` (B вместо запиненной A) → 404, а не 403 (session-vs-request mismatch, скрытие существования).
  - D-04: бренд без scoped-локаций для non-owner → 404 (та же existence-hiding логика на уровне `BrandScopeGuard`, отрабатывает раньше `LocationScopeGuard`).
  - Позитивный контроль: staff на своей локации A → 200.
  - Owner-bypass: owner достаёт все 3 локации в обоих брендах без единой scope-строки.
  - `GET /v1/me/locations` для staff возвращает ровно `[locationA]`.
  - D-11: staff, уже запиненный на A, не может сам переключиться на B (`403 location.already_pinned`) без релогина; owner переключается свободно (A→B, оба 200).
  - D-17: после архивации owner'ом локации A staff теряет доступ на следующем же запросе — поскольку A была ЕДИНСТВЕННОЙ scoped-локацией staff И единственным доступным брендом, guard-цепочка отбивает уже на `BrandScopeGuard` (`403 brand.access_denied`), что является даже более полным доказательством blast-radius предупреждения D-17, чем узкий location-only отказ.
- Попутно найден и исправлен реальный prod-баг (Rule 1): `InitialLocationDrizzleRepository.resolveForUserInBrand` использовал `db.withTenantId(...)` безусловно — этот метод по дизайну **бросает исключение**, если вызван изнутри уже ALS-bound контекста (HTTP-запрос). `SetActiveBrandService.resetActiveLocation()` вызывает этот репозиторий именно из HTTP-обработчика `POST /v1/me/set-active-brand` — исключение перехватывалось собственным `try/catch` метода и тихо возвращало `null`, из-за чего `activeLocationId` **всегда** обнулялся при явном переключении бренда в проде (юнит-тесты этого не ловили, так как мокают репозиторий). Исправлено: метод теперь проверяет `getTenantContext()` и использует `db.withTenant()` (ALS-aware) для HTTP-вызова, оставляя bootstrap-цепочку `withoutTenant`+`withTenantId` только для non-ALS вызова из BA-хука. Заодно добавлен отсутствовавший явный фильтр `eq(memberLocationScope.tenantId, tenantId)` в scope-join запросе (ADR-0020 I-1 требует явный tenant-фильтр поверх RLS, не полагаясь только на RLS).

## Decisions Made

- Non-owner фикстура использует базовую роль `admin`, а не `staff` — у `SYSTEM_ROLES.staff` нет ни одного `menu`-разрешения, а единственные default-on (не `@LocationNeutral()`) HTTP-роуты во всём приложении — это 3 catalog stop-list эндпоинта (`menu:read`/`update`). Фикстура с ролью `staff` физически не могла бы дойти до реального location-scoped роута для сквозного HTTP-доказательства. `admin` — тот же паттерн, что уже используется в `brand-isolation.e2e.spec.ts`, и полностью эквивалентен `staff` с точки зрения `LocationScopeGuard`/`BrandScopeGuard` (bypass только у `baseRole==='owner'`, для non-owner логика mismatch/scope идентична).
- Проверка D-17 (архивация → потеря доступа) утверждает `403 brand.access_denied`, а не `location.access_denied` — так как единственная scoped-локация staff (A) была одновременно единственным достижимым брендом, после архивации первым отбивает `BrandScopeGuard` (раньше в цепочке guard'ов, чем `LocationScopeGuard`). Это более сильное и полное доказательство blast-radius предупреждения D-17, чем узкий location-only отказ.
- Единый файл спека разбит на 2 коммита по числу задач плана: сначала написан и провёрен подмножество Task 1 (фикстура + 7 кейсов), закоммичено; затем добавлено подмножество Task 2 (3 кейса) вторым коммитом — вместо одного объединённого коммита.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `InitialLocationDrizzleRepository.resolveForUserInBrand` тихо ломался при вызове из HTTP-запроса**
- **Found during:** Task 1, тест "positive control" (staff обращается к своей же scoped-локации) неожиданно вернул 404 вместо 200.
- **Issue:** Non-owner ветка метода использовала `db.withTenantId(tenantId, ...)` — по дизайну (`packages/db/src/client.ts`) этот метод **бросает** `Error`, если вызван изнутри уже ALS-bound контекста (зарезервирован для non-HTTP вызывающих: BA-хуки, NATS-подписчики, CLI). `SetActiveBrandService.resetActiveLocation()` вызывает этот репозиторий из `POST /v1/me/set-active-brand` — HTTP-обработчика, уже ALS-bound через `TenantContextMiddleware`. Исключение перехватывалось собственным `catch` метода (`this.logger.error(...)`, легко потерять в логах) и тихо возвращало `null` — то есть `activeLocationId` **всегда** обнулялся при explicit-переключении бренда в проде, полностью ломая D-08 (авто-resolve единственной scoped-локации при смене бренда). Юнит-тесты (`set-active-brand.service.spec.ts`) мокают репозиторий и не могли это поймать.
- **Fix:** Метод теперь читает `getTenantContext()`; если ALS-контекст уже связан (HTTP-вызов), использует `db.withTenant()` (ALS-aware) напрямую; иначе — прежнюю цепочку `withoutTenant` (резолв tenantId по brandId) → `withTenantId` (для non-ALS BA-хука). Общая scoped-логика вынесена в приватный `#resolveScoped(tx, userId, brandId, tenantId)`. Заодно добавлен отсутствовавший explicit-фильтр `eq(memberLocationScope.tenantId, tenantId)` на scope-join запрос (ADR-0020 I-1: explicit tenant-фильтр обязателен поверх RLS, RLS — не единственный барьер).
