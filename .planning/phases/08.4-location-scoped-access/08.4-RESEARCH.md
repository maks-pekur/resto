## User Constraints (from CONTEXT.md)

### Locked Decisions (verbatim, D-01..D-17)

- **D-01 — Location = real org unit, not a label.** Fields: name, address, timezone, contacts, status. Composite FK `(brand_id, tenant_id) → brands(id, tenant_id)` + tenant FK; RLS enabled + FORCED at brand/location grain (mirror the ScopedTx + RLS double-enforcement). No hard delete — soft-archive via `status`/`archived_at`.
- **D-02 — Menu stays brand-level; stop-list/availability goes location-level.** Items, categories, modifiers, prices remain per-brand (shared across a brand's locations — unchanged). **Availability / stop-list becomes per-location** — each kitchen 86's its own items. The existing availability subsystem (currently brand-scoped: `/v1/menu/availability`, `get-menu-availability.service.ts`, `postgres-menu-version.adapter.ts`, menu/stop versions in Postgres) is re-grained to location. The guest sees availability for their **default/resolved location** (single-location brand → that one).
- **D-03 — Orders are per-location.** Add `location_id` to `orders` (composite FK + location-level isolation). Admin order access is location-scoped (Phase 10's incoming-orders feed will be per-location). **Boundary:** guest checkout binds the order to a default/resolved location automatically this phase (single location → it); qr-menu / site are NOT reworked for guest location-selection here.
- **D-04 — Locations supersede brand scope.** Member access is defined by a set of **locations** (`member_location_scope`); the brands a member can reach are **derived** from the brands of those locations. `member_brand_scope` is replaced. Single source of truth — no dual brand+location scope tables. Invariant: because access derives from locations, a brand with **zero** locations is reachable only by the owner until the owner creates locations there.
- **D-05 — Owner stays unrestricted.** As in 08.2/08.3, the owner (`canViewAllBrands` / base-role `owner`) bypasses location scope entirely. Default-deny + existence-hiding 404/403 extend to location grain for non-owners (out-of-scope location/brand → 404/403, mirroring 08.2 D-10).
- **D-06 — Role is per-location.** The role a member holds lives on the `member_location_scope` row (like the existing nullable `role` column on `member_brand_scope`). A member can be e.g. Manager at location A and Cashier at location B. This **refines 08.3's D-05 "one tenant-wide role per member"** down to one role _per location_. The role value references a system role (`owner`/`admin`/`staff`) or an 08.3 tenant-defined custom role.
- **D-07 — 08.3 guards apply to location-role assignment.** Assigning a per-location role MUST still enforce 08.3's subset / self-escalation guards (08.3 D-06) and NON_DELEGATABLE allowlist (08.3 D-04). Base-role resolution for custom-role members (08.3 D-15) must keep working at location grain so owner-bypass is not broken.
- **D-08 — Effective permissions = role at the active location.** Because menu is brand-level but roles are per-location, a member operates "as" one active location; their effective permission set is the role attached to that active location. Active brand = the brand of the active location.
- **D-09 — Owner: silent, two-level.** The owner works within one brand at a time and switches brands via a **global switcher (modal brand picker)**; within a brand the owner sees data **both brand-global (all locations) and per-location** via a `locationSwitcher`. All owner switches are **silent (no re-login)**.
- **D-10 — Staff (non-owner): login-pinned to one location.** A staff member **logs in to a specific location** they have access to (if scoped to several, they pick at login); they see only that location's data, bounded by the location role. Switching to another location requires **re-login**. One active location at a time. (Forward-looking: an open _shift_ will also be one-location-at-a-time — noted, not built.)
- **D-11 — Staff active-location/brand is fixed at session creation.** This is **stricter than 08.2 D-13** (which downgraded SEED-001's "re-login to switch" to a silent server-side re-pin at _brand_ grain). At _location_ grain the founder re-asserts login-pinning for staff. Stricter = safer; the security review must reconcile the two (the per-request scope check remains the real boundary either way). The silent re-pin remains **owner-only** (D-09). Mechanism (extend `session.activeBrandId` additionalField with an `activeLocationId`, vs a separate session-bound field) is a research/plan decision — it MUST be server-managed and not forgeable, mirroring 08.2's active-brand pin.
- **D-12 — No auto-created first location.** A brand starts with **zero** locations; the owner creates them manually. (Do NOT auto-seed a default location on brand create.) Consequence: a non-owner cannot be scoped to a brand that has no locations yet — acceptable and consistent with default-deny.
- **D-13 — Migration is near-empty; no auto-default.** No production data (first customer not live, likely single-location). No default location is synthesized. Existing `member_brand_scope` grants are re-established by the owner assigning members to locations after creating them. Legacy `orders` needing `location_id`: planner decides a one-time backfill vs nullable-for-legacy given the near-zero data — do not block on a data-migration design.
- **D-14 — Locations CRUD at `/{brand}/locations`.** New admin page under the brand-first shell (create / list / archive). (Claude's discretion on exact layout; a UI-phase may follow — UI hint = yes.)
- **D-15 — Assignment via a matrix on the Team page.** Extend 08.3's Team page: per member, a list of **(location → role)** pairs (add/remove). Owner-only (as 08.3 D-01/D-02/D-10). This keeps the assignment surface consolidated rather than adding a separate screen.
- **D-16 — Switcher becomes a `locationSwitcher` within a brand.** For staff there is no in-session switcher (pinned at login, D-10). For the owner: `locationSwitcher` within the active brand + a brand-global view + a cross-brand modal (D-09). Planner groups locations by brand for owners with many brands.
- **D-17 — Archiving a location with scoped staff is ALLOWED.** Archive is not blocked; members scoped only to that location lose access (default-deny). Planner adds a blast-radius warning ("N staff will lose access") before archive — mirrors 08.3 D-11/M-3, but does not block. (Chosen over the block-until-reassigned alternative.)

## Summary

08.4 extends the brand-level access core shipped in 08.2 (`BrandScopeGuard`, session-pinned `activeBrandId`, brand-grain RLS) and the role model shipped in 08.3 (`AssignRoleService`, subset/NON_DELEGATABLE guards, `computeEffectivePermissions`) down one grain, to **location**. The 08.2/08.3 code is a nearly complete architectural template — every mechanism this phase needs (session-managed active-scope pin, per-request scope reconciliation guard, existence-hiding 404, RESTRICTIVE RLS policy stacked on a GUC bound inside `TenantAwareDb.withTenant`) already exists and has a working, tested implementation to copy. The work is 80% "re-grain an existing pattern," 20% genuinely new: (a) a **stricter, asymmetric pin** for staff vs owner that the current `SetActiveBrandService` does not support (it treats owner and non-owner identically), and (b) a **permission-resolution path that bypasses Better Auth entirely** for non-owner operators, because BA's `auth.api.hasPermission` only ever knows the tenant-wide `member.role` — it has zero concept of location scope. The `member_brand_scope.role` column already exists in the schema (added by 08.3) but is **never read anywhere in application code today** — the per-location-role mechanism has to be built from scratch on top of it, not merely "extended."

The clearest concrete risk in this phase is the CDN edge-cache key for `/v1/menu/availability`: it is currently `host + path` (per `docs/runbooks/menu-edge-caching.md`), with **no location dimension**. The moment a brand has 2+ active locations, a shared per-host cache entry cannot correctly represent two different per-location stop-lists — this is fine for a single-location brand (matches the current near-empty-data reality per D-13) but is a silent correctness bug waiting for the second location of any brand to go live, and is not something the ETag alone fixes (ETags change what invalidates the cache, not what key partitions it).

**Primary recommendation:** Reuse the exact 08.2 pin/guard/RLS architecture at location grain (new `app.current_location` GUC, `app_bind_location()`, RESTRICTIVE location-iso policies, `LocationScopeGuard` mirroring `BrandScopeGuard`, `session.activeLocationId` additionalField mirroring `activeBrandId`), but make the write path (`SetActiveLocationService`) asymmetric: owners may re-pin freely (mirrors `SetActiveBrandService` unrestricted today); non-owners may set `activeLocationId` **only once per session** (first-pin, enforced server-side by rejecting a re-pin attempt when the session already has a non-null value) — this is what actually implements "re-login to switch" without adding new re-login-detection machinery. Build a new, location-aware `PermissionChecker` that resolves effective permissions from `member_location_scope.role` (via the existing `computeEffectivePermissions`/`isSubsetOf` helpers from 08.3) for non-owner operators, and only falls back to BA's `hasPermission` for the owner's tenant-wide bypass.

## Project Constraints (from CLAUDE.md)

Directives the plan MUST honor, extracted from root + package-level `CLAUDE.md` files:

- Every tenant-scoped query goes through `ScopedTx` **AND** Postgres RLS (double enforcement) — RLS alone is insufficient (`CLAUDE.md` "Tenancy Enforcement Pattern"; `packages/db/CLAUDE.md` "Repo-layer tenant filter is mandatory ON TOP of RLS").
- Composite FK `(parent_id, tenant_id) → parent(id, tenant_id)` on every tenant-scoped child table — `locations` (child of `brands`), `member_location_scope` (child of `brands` + `member`), `orders.location_id` (child of `locations`) all need this (`packages/db/CLAUDE.md` "Schema").
- Every tenant-scoped table: `ENABLE ROW LEVEL SECURITY` + `FORCE ROW LEVEL SECURITY` in the migration (`packages/db/CLAUDE.md`).
- Hard deletes forbidden — `resto_app` has no DELETE privilege; `locations` archive is `status`/`archived_at` only (`CLAUDE.md` "Architectural Constraints").
- `runInTenantContext` is HTTP-middleware-only; anything outside HTTP middleware uses `db.withTenant`/`db.withoutTenant` (ADR-0020 I-6) — relevant if any location-pin logic runs in a NATS subscriber or background job (none currently planned, but the guard applies to future outbox/notification consumers of location events).
- `withoutTenant(reason, op)` requires a non-empty reason string, logged at WARN.
- No raw SQL outside `packages/db` — the `app_bind_location`/`current_location_id()` SQL functions and RLS policies belong in `packages/db/migrations/`, mirroring 0058/0060/0061.
- `test/integration/tenant-isolation.spec.ts` needs a new entry for every new tenant-scoped table: `locations`, `member_location_scope`, and the re-graining of `orders` (location dimension) and the stop-list/stop-version tables.
- `_columns.ts` helpers (`pkUuid`, `tenantIdColumn`, `compositeTenantFk`, `tenantParentUniqueIndex`, `timestampsColumns`) are the only sanctioned way to build these columns — do not hand-roll FK syntax.
- System roles (`owner`/`admin`/`staff`) are immutable in code; adding a permission requires a regression test pinning what `admin` must NOT receive.
- Action names must not contain `:` (RBAC permission catalogue convention — relevant if a `location` resource is added to `PERMISSIONS_STATEMENT`).
- Free-text fields (location `name`, `address`, `contacts`) need `.max()` bounds; URL-ish fields need scheme restriction (none expected for `locations` unless a location-level logo/photo is added — out of scope here).
- Apps only import `@resto/*` packages; `apps/admin` never reaches into `apps/api` source.
- Server-side `fetch`/`apiFetch` calls need `AbortSignal.timeout(...)`; no exceptions for the new locations/team endpoints.
- Comments: default NO comments; only WHY-comments for hidden constraints/invariants/ADR references — this applies to the new location-pin/guard code exactly as it applied to the 08.2/08.3 code being mirrored.

### Focus Area 1: Active-location session pin mechanism

**Recommendation: extend the existing `activeBrandId` additionalField pattern with a sibling `activeLocationId` field — do NOT invent a separate mechanism.**

Evidence for the existing brand mechanism (the template to copy):

- `session.additionalFields.activeBrandId` — `{ type: 'string', defaultValue: null, input: false, returned: true }` (`apps/api/src/contexts/identity/infrastructure/better-auth/auth.config.ts:348-355`). `input: false` is what makes it non-forgeable — BA rejects any client-supplied value in the sign-up/sign-in body; the only way to set it is `internalAdapter.updateSession(token, { activeBrandId })` from trusted server code.
- Migration `0059_session_active_brand.sql` adds the `active_brand_id` column to BA's `session` table (confirmed by file existence; the location equivalent is `0067_session_active_location.sql` in the structure above).
- **Initial pin**: `databaseHooks.session.update.after` fires whenever `activeOrganizationId` changes (i.e., on `organization.setActive` — the login flow calls this, `apps/admin/src/routes/(auth)/login.tsx:52-53`) and `activeBrandId` is still null. **CDN edge-cache landmine (flag prominently, do not silently fix in scope, do not ignore):**

### Focus Area 7: 08.3 guard interplay (subset / self-escalation / NON_DELEGATABLE / base-role floor)

**Recommendation:** Location-role assignment reuses `computeEffectivePermissions`/`isSubsetOf`/`containsNonDelegatable` verbatim; the "actor's effective permissions" input to the subset check must be computed **at the actor's own active location**, not their tenant-wide `member.role`, to keep D-07's guard meaningful once roles are per-location.

The subset check still matters for the **target** role (can't grant a NON_DELEGATABLE-bearing custom role to a location-scope row, exactly mirroring `assign-role.service.ts:70-72`), but the actor-authority computation collapses to "is this operator the owner" (already checked by the endpoint's `@Permissions({ ac: ['update'] })` gate, since only `owner` has any `ac` permission in `SYSTEM_ROLES` — `packages/domain/src/rbac/system-roles.ts:4-15` has `ac` under `owner` only; `admin` (`:16-24`) has no `ac` key at all, so `admin` is automatically excluded by the BA permission check, this is the exact mechanism `MemberRolesController.assignRole` already uses at `member-roles.controller.ts:59`).
- **`SYSTEM_ROLE_SLUGS` constant** (`assign-role.service.ts:18`, `= new Set(['owner', 'admin', 'staff'])`) rejecting system-role assignment applies equally to location-role assignment — a `member_location_scope.role` value should be allowed to be a system-role slug OR a custom-role slug (D-06: "references a system role... or an 08.3 tenant-defined custom role"), which is a **different** constraint than `AssignRoleService`'s current rejection of system-role assignment via the `/v1/roles/:roleSlug/assign` endpoint (that endpoint is specifically for CUSTOM role assignment; location-role assignment is broader — it must accept `owner`/`admin`/`staff` too, since D-06's example is "Manager at location A and Cashier at location B" where Manager/Cashier are 08.3-seeded preset custom roles, but the mechanism must also support plain system roles). This means `AssignLocationRoleService` is not a thin wrapper around `AssignRoleService` — it needs its own validation path that permits system-role slugs, still enforces NON_DELEGATABLE + subset for custom roles, and (unlike `AssignRoleService`) does NOT call BA's `updateMemberRole` at all (that mutates the tenant-wide `member.role`; location-role assignment mutates `member_location_scope.role` directly via a Drizzle upsert, since `member_location_scope` is fully RestOS-owned, not a BA-managed table).
- **Base-role floor (D-15/08.3, D-07 interplay):** `AuthGuard.lookupBaseRole` (`auth.guard.ts:153-171`) reads the tenant-wide `member.role` CSV and returns the highest system-role token present (owner > admin > staff), used purely for **owner-bypass detection** in `BrandScopeGuard`/`LocationScopeGuard` (`principal.baseRole === 'owner'`). This is UNCHANGED by 08.4 — `principal.baseRole` continues to answer "is this operator globally unrestricted," and `member_location_scope.role` answers a completely separate question ("what permissions does this operator have while acting at their pinned location"). D-07's "base-role resolution... must keep working" is satisfied automatically as long as `lookupBaseRole` is left untouched and the new `LocationPermissionChecker` (Focus Area 5/8) checks `principal.baseRole === 'owner'` first, before ever consulting `member_location_scope`.

**Confidence:** HIGH for the mechanical reuse of `computeEffectivePermissions`/`isSubsetOf`/`containsNonDelegatable`; HIGH for the owner-only simplification (directly follows from D-15's explicit constraint + the existing `ac`-resource gating trick already proven in `member-roles.controller.ts`).

## Common Pitfalls

### Pitfall 1: Assuming `member_brand_scope.role` already does something

**What goes wrong:** A planner or implementer sees the `role` column on `member_brand_scope` (`packages/db/src/schema/brands.ts:131`) and assumes 08.4 is "just" reading a column that 08.3 already wired up.
**Why it happens:** The column exists, is nullable, and its comment in `08.4-CONTEXT.md`'s code_context section literally says "note it already carries a nullable role column — the per-location-role pattern of D-06," which reads as if the pattern is proven, not merely scaffolded.
**How to avoid:** Grep confirms zero application-code reads of `memberBrandScope.role` anywhere. Treat this as new logic end-to-end (permission resolution, assignment service, subset guard wiring) — see Focus Area 5/7.
**Warning signs:** A plan task that says "wire up the existing role column" without also specifying a new `PermissionChecker`/guard change is under-scoped.

### Pitfall 2: Reusing BA's `hasPermission` for location-grain checks

**What goes wrong:** `PermissionsGuard` → `BetterAuthPermissionChecker.hasPermission` (`permission-checker.adapter.ts:23-58`) calls `auth.api.hasPermission`, which BA evaluates purely against the session's tenant-wide `member.role` (plus BA's own dynamicAccessControl custom-role lookup, itself keyed by `member.role`, not by any location). There is no way to pass "evaluate as if this member's role were X" into BA's API — it always resolves from the authenticated session's actual stored role.
**Why it happens:** It's the existing, working permission-check path for everything else in the codebase; it's easy to assume it "just needs a location parameter."
**How to avoid:** Build the new `LocationPermissionChecker` (Focus Area 5/8) as a genuinely separate `PermissionChecker` implementation (or a composed one that branches on `principal.baseRole === 'owner'`) used specifically for location-scoped routes, bypassing `auth.api.hasPermission` entirely for non-owners.
**Warning signs:** Any code path that calls `this.auth.api.hasPermission` while also trying to reason about `activeLocationId` — those two facts cannot be reconciled through BA's API surface.

### Pitfall 3: CDN edge-cache correctness silently breaking on the second location

**What goes wrong:** `/v1/menu/availability`'s edge-cache key is `host + path` with no location dimension (`docs/runbooks/menu-edge-caching.md:24`). Once a brand has 2+ active locations, guests resolved to different locations sharing the same host can receive a cached response computed for a different location's stop-list.
**Why it happens:** The caching design (Phases 1-5 of `docs/superpowers/plans/2026-06-14-public-menu-caching.md`) was built and reviewed entirely under the brand-is-the-smallest-unit assumption; nothing in that design anticipated a sub-brand dimension.
**How to avoid:** This phase's D-03 boundary (guest location-selection deferred) makes it a **latent** bug, not an active one, as long as brands stay single-location. Document it explicitly in the runbook (task, not optional) so the next phase that touches guest-facing location selection inherits a known gap, not a silent one. Do not let it block 08.4.
**Warning signs:** Any customer support report of "wrong items shown as available/unavailable" for a multi-location brand post-launch is very likely this bug, not a data bug.

### Pitfall 4: `@RequireBrand()`/`@RequireLocation()` decorator is a no-op

**What goes wrong:** Copying the existing `@RequireBrand()` decorator pattern for a new `@RequireLocation()` decorator, assuming it does something, when `BrandScopeGuard.canActivate` (`brand-scope.guard.ts`) never actually reads `REQUIRE_BRAND_KEY` — only `BRAND_NEUTRAL_KEY` (the opt-out) is consulted; the guard is default-on globally (`identity-http.module.ts:81`, `APP_GUARD`).
**Why it happens:** The decorator's own doc comment (`require-brand.decorator.ts:5-11`) describes stale pre-08.2 default-allow semantics ("Empty scope rows mean the operator sees all brands... default-allow per ADR-0019 §5.3") that D-08 explicitly flipped — the comment was never updated after the default-on guard shipped, so it actively misleads a reader into thinking `@RequireBrand()` is load-bearing.
**How to avoid:** For location, implement only the opt-out decorator (`@LocationNeutral()`, mirroring `@BrandNeutral()`) and skip the vestigial opt-in one entirely. Optionally fix or delete `@RequireBrand()`'s stale comment while in the area (small, low-risk cleanup, not required for phase scope).
**Warning signs:** Any new decorator whose only consumer is a doc comment, not a guard's `reflector.getAllAndOverride` call.

### Pitfall 5: Synthesizing a location during migration or seed to "fix" D-12

**What goes wrong:** Under schema-migration pressure (e.g., to satisfy `orders.location_id NOT NULL`, or to make existing e2e/seed fixtures pass), a migration or seed script auto-creates a "Default Location" row for every existing brand.
**Why it happens:** It's the path of least resistance for making NOT NULL constraints and existing tests pass without touching every test fixture.
**How to avoid:** D-12 is explicit and founder-confirmed: "Do NOT auto-seed a default location on brand create." A migration silently doing the same thing for _existing_ brands is the same violation in spirit even if it's not literally "on brand create." Fix seed/test fixtures explicitly (create a location, then reference it) rather than auto-synthesizing in a migration.
**Warning signs:** A migration file that does `INSERT INTO locations (...) SELECT id, tenant_id, 'Default' FROM brands` — this is the exact pattern to reject in review.

## Open Questions

1. **Does the admin API client (`apps/admin/src/lib/api-client.ts`) need a new `x-location-id` header analogous to `x-brand-slug`/`x-tenant-id`, or should `TenantContextMiddleware` derive `locationId` purely from the session (requiring the middleware to resolve the BA session itself, which it currently does not do)?**
   - What we know: `x-tenant-id` is read directly from a request header inside `TenantContextMiddleware` (before `AuthGuard` resolves the session) and is later cross-checked by `AuthGuard`'s `auth.tenant_mismatch` check (`tenant-context.middleware.ts:80-84`, `auth.guard.ts:112-123`). `x-brand-slug` is explicitly passed by the admin API client caller, not auto-derived from session (`api-client.ts:38-39`). Neither pattern has a location precedent yet.
   - What's unclear: Whether the planner should follow the `x-tenant-id` pattern (header value derived from the session client-side, echoed back, guard cross-checks) — which is the recommendation in Focus Area 1/Architecture Diagram — or invent a session-resolved-in-middleware approach instead (more invasive, requires calling BA's session API twice per request).
   - Recommendation: Follow the `x-tenant-id` echo pattern (header set from the last-known `session.activeLocationId`, cross-checked by the new `LocationScopeGuard` exactly as `BrandScopeGuard` does today) — it requires zero changes to `TenantContextMiddleware`'s session-resolution boundary and reuses 100% of the existing guard-based reconciliation. Flagged as an open question rather than a locked decision because it's a genuine implementation-detail fork the planner should confirm, not something CONTEXT.md dictates.

2. **What is the exact default-location resolution algorithm for guest-facing reads (D-02/D-03 "default/resolved location")?**
   - What we know: D-13's "single-location brand → that one" covers the only case that matters near-term. `InitialBrandDrizzleRepository` (Focus Area 1) already establishes a precedent — "earliest by `createdAt`, then by `id`" — for an analogous "pick one deterministically" problem.
   - What's unclear: Whether a brand should carry an explicit `isDefaultLocation`/`isPrimary` flag (mirroring `brand_domains.isPrimary`, `packages/db/src/schema/brands.ts:101,118-120`) once a brand has 2+ locations, versus always falling back to "earliest created."
   - Recommendation: Ship "earliest active location by `createdAt`, then `id`" for this phase (matches the `InitialBrandDrizzleRepository` precedent exactly, needs no new schema field) and leave an explicit primary-location flag as a follow-up if multi-location brands become common before guest-facing location selection ships.
