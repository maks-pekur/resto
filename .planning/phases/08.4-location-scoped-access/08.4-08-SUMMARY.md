### Auto-fixed Issues

**1. [Rule 1 - Bug] Row-count check нашёл непустую `orders` (5 строк) при D-13's предположении «near-empty»**

- **Found during:** Task 1, перед ADD COLUMN NOT NULL
- **Issue:** План предполагал (D-13) практически пустую таблицу `orders`. Фактически в dev-БД было 5 заказов (артефакты платёжной live-smoke-сессии 2026-06-20/28), а таблица `locations` при этом была полностью пустой (0 строк) — ни одной локации, к которой можно было бы легитимно привязать существующие заказы.
- **Fix:** Строки очищены (`DELETE FROM payment_refunds/payments/order_modifiers/order_items/orders` в правильном FK-порядке) внутри той же миграции, перед `ADD COLUMN ... NOT NULL` — не забэкфиллены, локация не синтезирована (D-12/Pitfall 5). Точное зеркалирование прецедента `0068_stop_list_location_regrain.sql`.
- **Files modified:** `packages/db/migrations/0070_orders_location_id.sql`
- **Verification:** `pnpm db:migrate` exit 0, дважды подряд (идемпотентно); `docker exec ... psql` подтвердил 0 строк до/после и корректную схему.
- **Committed in:** `8364fac`

**2. [Rule 3 - Blocking] `tenancy_erase_tenant` никогда не erased `locations`/`member_location_scope`/`catalog_location_stop_version`**

- **Found during:** Task 1, после обновления фикстуры `erase-includes-ordering.spec.ts` (потребовалась `locations` seed для NOT NULL инсерта заказа) — тест начал падать на `DELETE FROM brands` с FK-violation.
- **Issue:** План 06 переключил `catalog_location_stop_version`'s FK с brand-cascade на location-RESTRICT (миграция 0068), но не обновил `tenancy_erase_tenant`, который никогда явно не удалял ни `locations`, ни `catalog_location_stop_version`. До этого плана это было тихой (без ошибок) незавершённостью erasure-пайплайна — просто orphaned строки оставались навсегда. Как только эта задача добавила первый `DELETE FROM locations` (нужный, чтобы фикстура-тест смог пройти brand-erasure), это превратилось в жёсткий сбой для ЛЮБОГО тенанта со stop-list данными на локации.
- **Fix:** Новая миграция `0072_tenancy_erase_locations.sql` — `CREATE OR REPLACE FUNCTION tenancy_erase_tenant` добавляет `DELETE FROM catalog_location_stop_version`, `DELETE FROM member_location_scope` (явно, зеркалит уже существующую явную строку для `member_brand_scope`, хотя technically избыточно поверх cascade от `member`), `DELETE FROM locations` — все три перед блоком `brands`.
- **Files modified:** `packages/db/migrations/0072_tenancy_erase_locations.sql`, `packages/db/migrations/meta/_journal.json`
- **Verification:** `pnpm db:migrate` exit 0 (трижды подряд, идемпотентно); `erase-includes-ordering.spec.ts` зелёный; полный `packages/db` тест-сьют (27 файлов / 214 тестов) зелёный, без регрессий.
- **Committed in:** `8364fac`

**3. [Rule 3 - Blocking] Обязательный `orders.location_id` разорвал всю ordering/payments write-path поверхность (typecheck + фикстуры)**

- **Found during:** Task 1/2, при первой попытке коммита — pre-commit хук прогоняет typecheck по всему монорепо независимо от staged-файлов; `OrderSnapshot`/`Order.create`'s новый обязательный `locationId` сломал компиляцию в 8 файлах (`order-drizzle.repository.ts`, 3 e2e-фикстуры, 5 unit-спеков в payments, включая прямые литералы `Order.fromSnapshot({...})`).
- **Fix:** `Order.aggregate.ts`/`order-drizzle.repository.ts` прокинули `locationId` сквозным образом; `create-order.service.ts` резолвит и передаёт его (полная реализация Task 2, не только заглушка); все затронутые unit/integration/e2e фикстуры получили `locationId`/`schema.locations` seed.
- **Files modified:** см. полный список в frontmatter `key-files.modified`.
