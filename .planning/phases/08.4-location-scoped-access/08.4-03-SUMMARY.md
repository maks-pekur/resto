## Accomplishments

- `session.activeLocationId` — sibling `additionalField` к `activeBrandId` (`input: false`), единственный путь записи — `internalAdapter.updateSession` из доверенного серверного кода (`SessionActiveLocationWriter`/`BetterAuthSessionActiveLocationWriter`).
- `SetActiveLocationService` — асимметричная запись: owner валидирует цель против `findPinnableLocations(isOwner=true)` и пишет безусловно (включая `null` — сброс в brand-global вид, D-09); non-owner СНАЧАЛА читает текущий пин через новый `readActiveLocationId`, и если он не `null` — `LocationAlreadyPinnedError` (403 `location.already_pinned`); переход разрешён только `null → value`, ровно один раз за сессию (D-11).
- `MemberLocationScopeDrizzleReader` — 4 метода (`findLocationScopeForMember`, `findReachableBrandsForMember`, `findRoleForMemberAtLocation`, `findPinnableLocations`), ВСЕ джойнят `locations` с фильтром `status='active'` — архивная локация перестаёт давать доступ на следующем же запросе (D-17), без удаления scope-строк.
- `findReachableBrandsForMember` — джойн `member_location_scope → locations → brands`, `DISTINCT brandId`; бренд без активных локаций недостижим никем, кроме owner (D-04).
- `InitialLocationDrizzleRepository.resolveForUserInBrand` — owner всегда `null` (brand-global по умолчанию); non-owner — "самая ранняя активная локация по `createdAt`" с трёхвариантной веткой: 0 кандидатов → `null`, ровно 1 → авто-пин, 2+ → `null` (требуется явный первый выбор).
- `auth.config.ts` — `onInitialLocationPin` подключён в ТОТ ЖЕ хук `databaseHooks.session.update.after`, что и `onInitialBrandPin`, использует существующий `brandPinDone`-гейт (без отдельного `locationPinDone` WeakMap) и срабатывает только когда бренд был реально запинен в этом же вызове.
- `initial-brand-drizzle.repository.ts` — non-owner ветка переведена с `member_brand_scope` на `member_location_scope → locations (status='active') → brands` (D-04 single source of truth; таблица `member_brand_scope` НЕ удалена — суперseded-in-code).
- `POST /v1/me/set-active-location` + `GET /v1/me/locations` — второй эндпоинт на том же контроллере, owner видит все активные локации бренда, non-owner — только свои scoped активные локации.
- `req.activeLocationId` теперь прокидывается в `AuthGuard` рядом с `activeBrandId`; заголовок `x-location-id` (валидный uuid) биндится как `locationId` в `runInTenantContext` через `TenantContextMiddleware` (echo-паттерн, реальная проверка — будущий `LocationScopeGuard` в плане 05).
- `SetActiveBrandService` реконcилирован под D-04: non-owner-валидация переключения бренда теперь идёт через `findReachableBrandsForMember` (а не суперседед `findBrandScopeForMember`), и КАЖДОЕ успешное переключение бренда (и owner, и non-owner) пересчитывает и записывает `activeLocationId` для нового бренда — `activeLocationId` больше никогда не может указывать на локацию из предыдущего бренда (D-08).

## Decisions Made

- `InitialLocationDrizzleRepository.resolveForUserInBrand(userId, brandId)` без `tenantId`-параметра (зафиксировано в PLAN/RESEARCH) — tenantId буутстрапится через `db.withoutTenant` по глобально-уникальному `brandId`, затем реальный scoped-запрос идёт через `db.withTenantId`. Безопасно: `brandId → tenantId` — жёсткая 1:1 связь через composite FK.
- `GET /v1/me/locations` — на том же `SetActiveLocationController`, читает `MEMBER_LOCATION_SCOPE_READER` напрямую, без промежуточного application-сервиса (так в плане).
- `findReachableBrandsForMember` явно джойнит `member_location_scope → locations → brands` (не просто `DISTINCT locations.brandId`) — под зафиксированный в acceptance criteria join-chain.
- non-owner `locationId=null` трактуется единообразно как out-of-scope (`LocationOutOfScopeError`) — у non-owner нет brand-global clear семантики (D-10), только owner может передать `null`.
- `InitialLocationDrizzleRepository` экспортирован из `IdentityCoreModule` уже в Task 3 (хотя в файл-листе плана числится за Task 4) — Task 3 всё равно требовал его для `buildAuthFromEnv`; Task 4 использовал готовую проводку без дополнительных правок модулей.
