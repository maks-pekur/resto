# Phase 08.4 Plan 06: Локационный уровень stop-list и доступности меню Summary

**`menu_stop_list` и `catalog_location_stop_version` перекованы с brand_id на location_id с location-grain RESTRICTIVE RLS; оператор стопит/расстопливает позиции через активную локацию (пин сессии), гость читает доступность через дефолтную локацию бренда (самая ранняя активная по createdAt) — плюс попутно закрыта критическая брешь rollout'а `LocationScopeGuard` из плана 05, из-за которой гостевое чтение меню и провижининг тенант/бренд/локация были полностью недоступны (403).**

- **Найдена и частично закрыта критическая брешь плана 05**: `LocationScopeGuard` (уже задеплоен как default-on `APP_GUARD`) кидает 403 `location.context_required` ДО проверки owner-bypass на любом роуте без `@LocationNeutral()` — гостевые `/v1/menu*`, `POST /internal/v1/tenants`, `POST /v1/me/brands`, `POST /v1/tenancy/locations` были полностью сломаны. ## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `get-stop-list.service.ts` re-grain (not in files_modified, same port method)**

- **Found during:** Task 2
- **Issue:** `listStopListWithStoppedAt`'s only other caller besides `stop-list.service.ts` is `GetStopListService` (the `GET /stop-list` listing) — changing the port signature to `locationId` without updating this caller breaks the build.
- **Fix:** Swapped `requireBrandContext()` -> `requireLocationContext()`, same as `StopListService`.
- **Files modified:** `apps/api/src/contexts/catalog/application/get-stop-list.service.ts`
- **Verification:** `pnpm nx run api:typecheck` green; catalog.e2e's `GET /stop-list` assertions pass.
- **Committed in:** `3343768`

**2. [Rule 3 - Blocking] `CatalogMenuPricingAdapter` (ordering context) re-grain**

- **Found during:** Task 2
- **Issue:** `listStoppedItemIds` is also called from `apps/api/src/contexts/ordering/infrastructure/catalog-menu-pricing.adapter.ts` (guest checkout's pricing snapshot). No ordering test in this repo exercises this adapter with real DI (all existing create-order tests use a hand-rolled fake `MenuPricingPort`), so this is a genuine compile-time-only blocker today, not a behavior regression caught by any test — but leaving it broken would silently regress checkout's stopped-item filtering in production.
- **Fix:** Injected `DefaultLocationResolverService`, resolves a default location from `brandId` before calling `listStoppedItemIds(locationId)`. `CatalogModule` now exports the resolver for `OrderingModule` to consume.
- **Files modified:** `apps/api/src/contexts/ordering/infrastructure/catalog-menu-pricing.adapter.ts`, `apps/api/src/contexts/catalog/catalog.module.ts`
- **Verification:** `pnpm nx run api:typecheck` green; confirmed via code inspection no ordering test currently exercises real DI for this adapter (`grep` across `apps/api/test` for `CatalogMenuPricingAdapter`/`MENU_PRICING_PORT` usage).
- **Committed in:** `3343768`

**3. [Rule 3 - Blocking] `packages/db/src/schema/auth.ts` `session` table missing `activeLocationId`**

- **Found during:** Task 3, first e2e run attempt
- **Issue:** Plan 03 (`08.4-03`) added `session.active_location_id` via migration `0066` and wired Better Auth's `additionalFields` config to read/write it, but never added the Drizzle column to `packages/db/src/schema/auth.ts`'s `session` table — the table BA's own `drizzleAdapter` uses. Every BA `signUpEmail` call threw `BetterAuthBootstrapFailureError: The field "activeLocationId" does not exist in the "session" Drizzle schema`, i.e. the entire owner-bootstrap flow was broken, blocking every e2e test in the repository.
- **Fix:** Added `activeLocationId: text('active_location_id')` to the `session` table definition, mirroring the pre-existing `activeBrandId` column 1:1.
- **Files modified:** `packages/db/src/schema/auth.ts`
- **Verification:** `pnpm nx run api:typecheck` + `pnpm nx run db:typecheck` green; `runBootstrap` (owner sign-up) succeeds in all subsequently-run e2e suites.
- **Committed in:** `ee73aa5`

**4. [Rule 1 - Bug] `PublicMenuController` missing `@LocationNeutral()` — guest menu reads were 403ing**

- **Found during:** Task 3, e2e debugging
- **Issue:** `LocationScopeGuard` (default-on `APP_GUARD` since plan 05) throws `403 location.context_required` whenever `getLocationId()` is unbound and the route lacks `@LocationNeutral()` — before ever reaching the owner-bypass check. Guests never send `x-location-id`, so `/v1/menu`, `/v1/menu/availability`, `/v1/menu/items/:id` were unconditionally 403ing for every guest request. This directly blocks the exact feature this plan ships (guest availability reads).
- **Fix:** Added `@LocationNeutral()` to `PublicMenuController`.
- **Files modified:** `apps/api/src/contexts/catalog/interfaces/http/public-menu.controller.ts`
- **Verification:** `menu-availability.e2e.spec.ts` (4/4) and `menu-brand-response.e2e.spec.ts` (6/6), including the guest availability assertions, pass.
- **Committed in:** `d329c27`

**5. [Rule 3 - Blocking] `InternalTenantsController`/`MeBrandsController`/`LocationsController` missing `@LocationNeutral()`**

- **Found during:** Task 3, e2e debugging
- **Issue:** Same root cause as #4. `POST /internal/v1/tenants` (tenant provisioning, used by every e2e fixture), `POST /v1/me/brands` (brand creation), and `POST/GET/PATCH /v1/tenancy/locations` (this plan's own newly-added e2e location-creation calls) were all 403ing — no e2e test in the whole repository could even set up its fixtures.
- **Fix:** Added `@LocationNeutral()` to all three controllers. Did NOT touch the other ~12 controllers discovered with the same gap (payments, ordering `orders.controller.ts` guest checkout, several identity controllers, health) — out of scope for this plan, each needs individual domain review rather than a blind decorator copy; documented in `deferred-items.md` as a CRITICAL follow-up.
- **Files modified:** `apps/api/src/contexts/tenancy/interfaces/http/internal-tenants.controller.ts`, `apps/api/src/contexts/identity/interfaces/http/me-brands.controller.ts`, `apps/api/src/contexts/tenancy/interfaces/http/locations.controller.ts`
- **Verification:** `catalog.e2e.spec.ts` (26/26), `cross-tenant-isolation.e2e.spec.ts` (12/13, the 1 remaining failure is the pre-existing unrelated `tenants.controller.ts` gap — see Issues Encountered).
- **Committed in:** `d329c27`
