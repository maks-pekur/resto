# Phase 08.4: Location-scoped Access - Context

**Gathered:** 2026-07-10
**Status:** Ready for planning
**Security review:** REQUIRED before code — locations are a new data-isolation boundary. Extend the default-deny + existence-hiding-404 pattern (08.2) to location grain; per-location role resolution + active-location session pin are privilege-surface changes that must be reconciled with 08.2 D-13 and 08.3's subset guards.

<domain>
## Phase Boundary

Introduce the **location** entity (none exists today — brand is currently the smallest unit) and move member scope + operational data isolation from **brand** grain to **location** grain.

**Domain hierarchy (founder-confirmed 2026-07-10):** `Tenant → Brand(s) → Location(s)`. One tenant = one entrepreneur who may own several brands (dark-kitchen example: 1 tenant, 3 brands). Each brand has one or more **locations** (kitchens / points of sale). A location is a concrete point of sale with its **own stop-lists** and (future) its **own load/capacity**. This matches the `Brand → Location → Menu / Zones / Staff` hierarchy already stated in `CLAUDE.md`.

**This phase delivers:**

1. **`locations` entity** — per-brand org unit (name, address, timezone, contacts, status). Composite FK `(brand_id, tenant_id)` + brand/location-level RLS per the tenancy invariants. Locations admin CRUD (create / list / archive) under the brand-first `/{brand}/...` shell.
2. **Location-level member scope (supersedes brand scope)** — `member_location_scope` replaces `member_brand_scope`; a member's reachable brands are **derived** from the brands of their scoped locations.
3. **Role-per-location** — a member may hold a different role at different locations; the role lives on the location-scope row.
4. **Active-location session model** — extends 08.2's single-active-brand pin down to location grain (owner switches silently; staff is pinned at login, switch = re-login).
5. **Stop-list / availability moves to location grain** — menu items/categories/prices stay per-brand; **availability/stop-list becomes per-location**.
6. **Orders move to location grain** — orders carry `location_id`; admin order visibility/management is location-scoped.

**Explicitly OUT of scope (deferred — see Deferred Ideas):**

- Per-location **menu / prices** (items, categories, modifiers stay brand-level; only availability is per-location).
- Guest-facing **location selection** at checkout in qr-menu / site (guest order binds to a default/resolved location this phase; the guest "pick a branch" UX is a later concern).
- Per-location **load/capacity** and the **shift** concept (forward-looking framing only; no capacity or shift system exists yet).
- Delivery **zones** per location (Phase 9, MVP-2 — attaches to location later).
- A "whole-brand (all locations incl. future)" convenience grant — staff are assigned to explicit locations this phase.

</domain>

<decisions>
## Implementation Decisions

### Location entity & catalog boundary

- **D-01 — Location = real org unit, not a label.** Fields: name, address, timezone, contacts, status. Composite FK `(brand_id, tenant_id) → brands(id, tenant_id)` + tenant FK; RLS enabled + FORCED at brand/location grain (mirror the ScopedTx + RLS double-enforcement). No hard delete — soft-archive via `status`/`archived_at`.
- **D-02 — Menu stays brand-level; stop-list/availability goes location-level.** Items, categories, modifiers, prices remain per-brand (shared across a brand's locations — unchanged). **Availability / stop-list becomes per-location** — each kitchen 86's its own items. The existing availability subsystem (currently brand-scoped: `/v1/menu/availability`, `get-menu-availability.service.ts`, `postgres-menu-version.adapter.ts`, menu/stop versions in Postgres) is re-grained to location. The guest sees availability for their **default/resolved location** (single-location brand → that one).
- **D-03 — Orders are per-location.** Add `location_id` to `orders` (composite FK + location-level isolation). Admin order access is location-scoped (Phase 10's incoming-orders feed will be per-location). **Boundary:** guest checkout binds the order to a default/resolved location automatically this phase (single location → it); qr-menu / site are NOT reworked for guest location-selection here.

### Access model

- **D-04 — Locations supersede brand scope.** Member access is defined by a set of **locations** (`member_location_scope`); the brands a member can reach are **derived** from the brands of those locations. `member_brand_scope` is replaced. Single source of truth — no dual brand+location scope tables. Invariant: because access derives from locations, a brand with **zero** locations is reachable only by the owner until the owner creates locations there.
- **D-05 — Owner stays unrestricted.** As in 08.2/08.3, the owner (`canViewAllBrands` / base-role `owner`) bypasses location scope entirely. Default-deny + existence-hiding 404/403 extend to location grain for non-owners (out-of-scope location/brand → 404/403, mirroring 08.2 D-10).

### Roles × location

- **D-06 — Role is per-location.** The role a member holds lives on the `member_location_scope` row (like the existing nullable `role` column on `member_brand_scope`). A member can be e.g. Manager at location A and Cashier at location B. This **refines 08.3's D-05 "one tenant-wide role per member"** down to one role *per location*. The role value references a system role (`owner`/`admin`/`staff`) or an 08.3 tenant-defined custom role.
- **D-07 — 08.3 guards apply to location-role assignment.** Assigning a per-location role MUST still enforce 08.3's subset / self-escalation guards (08.3 D-06) and NON_DELEGATABLE allowlist (08.3 D-04). Base-role resolution for custom-role members (08.3 D-15) must keep working at location grain so owner-bypass is not broken.

### Session & switching (the nuanced part — founder-designed)

- **D-08 — Effective permissions = role at the active location.** Because menu is brand-level but roles are per-location, a member operates "as" one active location; their effective permission set is the role attached to that active location. Active brand = the brand of the active location.
- **D-09 — Owner: silent, two-level.** The owner works within one brand at a time and switches brands via a **global switcher (modal brand picker)**; within a brand the owner sees data **both brand-global (all locations) and per-location** via a `locationSwitcher`. All owner switches are **silent (no re-login)**.
- **D-10 — Staff (non-owner): login-pinned to one location.** A staff member **logs in to a specific location** they have access to (if scoped to several, they pick at login); they see only that location's data, bounded by the location role. Switching to another location requires **re-login**. One active location at a time. (Forward-looking: an open *shift* will also be one-location-at-a-time — noted, not built.)
- **D-11 — Staff active-location/brand is fixed at session creation.** This is **stricter than 08.2 D-13** (which downgraded SEED-001's "re-login to switch" to a silent server-side re-pin at *brand* grain). At *location* grain the founder re-asserts login-pinning for staff. Stricter = safer; the security review must reconcile the two (the per-request scope check remains the real boundary either way). The silent re-pin remains **owner-only** (D-09). Mechanism (extend `session.activeBrandId` additionalField with an `activeLocationId`, vs a separate session-bound field) is a research/plan decision — it MUST be server-managed and not forgeable, mirroring 08.2's active-brand pin.

### Bootstrapping & migration

- **D-12 — No auto-created first location.** A brand starts with **zero** locations; the owner creates them manually. (Do NOT auto-seed a default location on brand create.) Consequence: a non-owner cannot be scoped to a brand that has no locations yet — acceptable and consistent with default-deny.
- **D-13 — Migration is near-empty; no auto-default.** No production data (first customer not live, likely single-location). No default location is synthesized. Existing `member_brand_scope` grants are re-established by the owner assigning members to locations after creating them. Legacy `orders` needing `location_id`: planner decides a one-time backfill vs nullable-for-legacy given the near-zero data — do not block on a data-migration design.

### Admin UX

- **D-14 — Locations CRUD at `/{brand}/locations`.** New admin page under the brand-first shell (create / list / archive). (Claude's discretion on exact layout; a UI-phase may follow — UI hint = yes.)
- **D-15 — Assignment via a matrix on the Team page.** Extend 08.3's Team page: per member, a list of **(location → role)** pairs (add/remove). Owner-only (as 08.3 D-01/D-02/D-10). This keeps the assignment surface consolidated rather than adding a separate screen.
- **D-16 — Switcher becomes a `locationSwitcher` within a brand.** For staff there is no in-session switcher (pinned at login, D-10). For the owner: `locationSwitcher` within the active brand + a brand-global view + a cross-brand modal (D-09). Planner groups locations by brand for owners with many brands.

### Lifecycle

- **D-17 — Archiving a location with scoped staff is ALLOWED.** Archive is not blocked; members scoped only to that location lose access (default-deny). Planner adds a blast-radius warning ("N staff will lose access") before archive — mirrors 08.3 D-11/M-3, but does not block. (Chosen over the block-until-reassigned alternative.)

### Claude's Discretion (research / planner)

- Exact server mechanism for the active-location pin (extend `activeBrandId` additionalField vs a new field) and the base-role-floor contract for custom-role members at location grain (08.3 D-15 interplay).
- Whether `orders.location_id` is NOT NULL with a one-time backfill or nullable-for-legacy (D-13).
- Re-graining the availability/stop-version mechanism to location (schema shape of per-location stop versions; ETag/cache-key impact — see `docs/runbooks/menu-edge-caching.md`).
- Exact `locations` field set and iiko entity-shape alignment (see canonical refs) to ease MVP-3 partner integration.
- Whether brand/location RLS extends beyond orders + availability (e.g. to the scope tables themselves) — planner / security pass.

</decisions>

<specifics>
## Specific Ideas

- **Dark-kitchen mental model (founder):** one tenant = one entrepreneur owning several brands; each brand has locations (kitchens / points of sale); a location has its own load and its own stop-lists. This is the canonical example to design against.
- **Founder's session model (D-08–D-11), verbatim intent:** the owner sees info globally at brand level and per-location by switching, and moves between brands via a global (modal) switcher — always silently. A staff member logs in to the one location they have access to, sees only that location within their permissions, and to switch must re-login; they work in only one location at a time, and (later) will have an open shift in only one location at a time.
- Consistent with 08.2/08.3: the founder wants tamper-resistant, server-enforced boundaries — active-location must be server-managed, not client-forgeable.

</specifics>

- **Per-location load / capacity** — a location's occupancy/throughput; ties to Phase 10 (Admin Order Intake) and order pacing.
- **Shift concept** — an "open shift" bound to one location at a time (the founder's forward hook on D-10); no shift system exists yet.
- **Delivery zones per location** — Phase 9 (MVP-2) attaches polygon zones + fees to a location.
- **"Whole-brand" convenience grant** — assign a member to all current+future locations of a brand in one action (brand-manager). This phase uses explicit per-location assignment.
- **Admin-authored / admin-assigned location roles** — owner-only in this phase (mirrors 08.3 D-01/D-02); enabling admin authorship later is a policy flip since the subset guards (D-07) are built now.
