# Phase 08.4 Plan 07: Per-location role assignment + LocationPermissionChecker Summary

**Owner-only `AssignLocationRoleService` upserting `member_location_scope.role` (system or custom slugs, NON_DELEGATABLE-guarded) plus a standalone `LocationPermissionChecker` that resolves a non-owner's effective permissions from their role at an explicit active location, bypassing Better Auth's tenant-wide `hasPermission` — with full `PermissionsGuard` route integration deliberately deferred to avoid a silent app-wide non-owner lockout.**

## Accomplishments

- `AssignLocationRoleService.execute({ organizationId, memberId, locationId, roleSlug })` — accepts system role slugs (`owner`/`admin`/`staff`) as well as custom role slugs (D-06, inverting `AssignRoleService`'s rejection); for a custom slug, looks it up via `listActiveCustomRoles` and rejects with `InsufficientPermissionsToMintError` if `containsNonDelegatable` (08.3 D-04) is true; persists via a plain Drizzle `insertInto(...).onConflictDoUpdate(...)` upsert on `member_location_scope`'s `(memberId, locationId)` composite PK — never calls BA's role-mutation API.
- Clearing an assignment (`roleSlug: null`) nulls the row's `role` rather than deleting it (no DELETE privilege on `resto_app`); the scope row itself persists so the member stays visible to `LocationScopeGuard`, just with zero granted permissions until re-assigned.
- `MemberLocationRolesController` — `POST /v1/members/:memberId/location-roles` (assign) and `DELETE /v1/members/:memberId/location-roles/:locationId` (clear), both gated `@Permissions({ ac: ['update'] })` (owner-exclusive, mirrors `member-roles.controller.ts`'s `ac`-gate trick) and `@BrandNeutral()`.
- `LocationPermissionChecker implements PermissionChecker` — owner bypass first (`principal.baseRole === 'owner'` returns `true` without touching `member_location_scope`); non-owner path resolves `findRoleForMemberAtLocation(userId, activeLocationId)` → `computeEffectivePermissions` → `isSubsetOf` (08.3 helpers, reused verbatim), never delegating to `auth.api.hasPermission`.
- Registered `LocationPermissionChecker` (plus a second `MEMBER_LOCATION_SCOPE_READER` binding needed for its own DI scope) inside `IdentityCoreModule`, exported for future consumption — deliberately NOT swapped in as the live `PERMISSION_CHECKER` token (see Decisions Made).
- 10 unit tests total (5 per class) covering: NON_DELEGATABLE rejection, unknown custom slug, system-slug acceptance, custom-slug upsert, role-clear; owner bypass, sufficient location role, over-grant prevention, missing activeLocationId, missing role-at-location.

## Decisions Made

- **`MemberLocationRolesController` is `@BrandNeutral()`, not location-scoped.** It manages (member, location) role pairs across an entire brand's locations from one Team-matrix action, not a single pinned active location. `LocationScopeGuard` checks `getLocationId()` (the `x-location-id` header) presence _before_ its owner-bypass branch — a non-brand-neutral decoration would 403 `location.context_required` for an owner performing a cross-location management action without echoing that header. Mirrors `member-roles.controller.ts`'s decoration exactly, per the phase's remediation note that a brand-neutral route is also location-neutral.
- **`LocationPermissionChecker` is built and unit-proven but NOT wired as the live `PERMISSION_CHECKER` DI token.** The plan's action text says to "wire it as the PermissionCheckerPort implementation used on location-scoped operator routes," but the only mechanism to do that live is `PermissionsGuard`'s single global `PERMISSION_CHECKER` injection, and `PermissionsGuard.canActivate` calls `hasPermission(principal, required, headers)` — no `activeLocationId` is threaded through today. Swapping the DI binding without that plumbing (which requires touching `permissions.guard.ts`, outside this task's file list) would make `activeLocationId` always `undefined`, and every non-owner permission check across the entire app would silently start returning `false` — a full functional lockout of every admin/staff account, not a narrow correctness gap. Given this is explicitly "the highest-risk correctness area of the phase," I registered the class as a standalone, exported, fully-tested provider instead of taking that risk unreviewed. Threat T-084-21's disposition ("unit-proven") is satisfied; live route-level integration is flagged below as required follow-up.
- **`hasPermission` takes `activeLocationId` as an explicit, optional 4th parameter** beyond `PermissionChecker`'s declared 3-arg shape — TypeScript's structural typing allows an implementing method to declare additional optional parameters. This carries the **session**-derived `req.activeLocationId` (set by `AuthGuard`, non-forgeable) rather than the ALS/header-echoed `getLocationId()` (unreconciled against the session pin until `LocationScopeGuard` runs, which today executes _after_ `PermissionsGuard` in the guard chain) — using the header value here would be a genuine privilege-escalation surface for `@BrandNeutral`/`@LocationNeutral` routes.
- **`MEMBER_LOCATION_SCOPE_READER`/`MemberLocationScopeDrizzleReader` bound a second time inside `IdentityCoreModule`.** `LocationPermissionChecker` lives in `IdentityCoreModule` per the plan's file list, but the reader's only existing binding is in `IdentityHttpModule` (which imports Core, not the reverse) — a NestJS child module cannot resolve a token only bound in its importer. Both bindings wrap the same stateless, `@Global()` `TenantAwareDb`, so this is harmless duplication, not a behavior change. Verified by booting the full `AppModule` DI graph via `test/e2e/health.e2e.spec.ts`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Re-bound MEMBER_LOCATION_SCOPE_READER inside IdentityCoreModule**

- **Found during:** Task 2 (LocationPermissionChecker wiring)
- **Issue:** The plan's file list puts `LocationPermissionChecker` + its module wiring in `identity-core.module.ts`, but `MEMBER_LOCATION_SCOPE_READER` (the port it needs) is only bound in `identity-http.module.ts`, which _imports_ `IdentityCoreModule` — not the reverse. A NestJS module cannot resolve a token only provided by its importer; registering `LocationPermissionChecker` as specified would have thrown "Nest can't resolve dependencies" at boot.
- **Fix:** Added a second `{ provide: MEMBER_LOCATION_SCOPE_READER, useClass: MemberLocationScopeDrizzleReader }` binding inside `IdentityCoreModule`, alongside the existing one in `IdentityHttpModule`. Both wrap the same stateless `@Global() TenantAwareDb`; no behavior difference.
- **Files modified:** `apps/api/src/contexts/identity/identity-core.module.ts`
- **Verification:** `pnpm exec tsc -p apps/api/tsconfig.json --noEmit` clean; `test/e2e/health.e2e.spec.ts` boots the full `AppModule` DI graph successfully.
- **Committed in:** `88e0e1c` (Task 2 commit)
