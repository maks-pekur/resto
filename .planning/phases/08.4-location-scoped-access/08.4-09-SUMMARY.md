## Accomplishments

- `api-client.ts` echoes `x-location-id` from the current Better Auth session's `activeLocationId` additionalField on every request, mirroring the existing `x-tenant-id`/`x-brand-slug` attachment — single cast covers both `activeOrganizationId` and `activeLocationId` reads.
- `lib/queries/locations.ts` — `brandLocationsQuery`, `meLocationsQuery`, `activeLocationIdQuery`, `createLocationMutation`, `archiveLocationMutation`, `friendlyLocationError`.
- `/{brand}/locations` route (owner-only, `EmptyState variant="forbidden"` otherwise) — react-hook-form + zod create form (name/address/timezone/contacts, client `.max` bounds mirror the backend `LocationName`/`LocationAddress`/`LocationTimezone`/`LocationContactsSchema` constants) + a status table; archive shows a confirm dialog then a post-archive toast with the real `scopedMemberCount` ("N staff member(s) lost access") — never blocks (D-17).
- `location-switcher.tsx` — owner-only (`if (!isOwner) return null`), lists the active brand's locations via `meLocationsQuery`, includes a "Brand-global (all locations)" item that POSTs `set-active-location` with `locationId: null`, reloads the page on switch so every loader picks up the new `x-location-id` header (D-09/D-16).
- `pick-location.tsx` — new `(auth)` route listing the operator's pinnable locations (`meLocationsQuery`), POSTs `set-active-location` on pick, then navigates to `safeNext(next ?? '/dashboard')` (D-10).
- `login.tsx` — after `organization.setActive`, reads `baseRole` (`GET /v1/me`) and `activeLocationId` (raw session cast); non-owner + still-null `activeLocationId` routes to `/pick-location` instead of `/dashboard`; owners and auto-pinned single-location staff proceed straight through.
- `app-sidebar.tsx` — new "Locations" nav entry (`scope: 'brand'`), mounts `LocationSwitcher` next to `BrandSwitcher`, self-fetches both location queries gated on `isOwner && activeBrandSlug !== null`.

### Bug found + fixed during checkpoint verification (not part of this plan's task list)

**`fix(admin): guard dashboard against location-less stop-list 403 crash`** — `3590cd0`

- **Symptom:** the brand dashboard (`$brandSlug/index.tsx`) white-screened for an owner in brand-global view (no active location pinned).
- **Root cause:** `GET /v1/catalog/stop-list` is location-grain since 08.4-06 and returns `403 location.context_required` when no `x-location-id` is bound; the dashboard's "today's 86 widget" queried it unconditionally and then read `.data?.items.length` on the 403 problem-details body, which has no `items` field — a `TypeError` on undefined, crashing the route. This is the same guard-ordering gap already tracked in `.planning/phases/08.4-location-scoped-access/deferred-items.md` (`LocationScopeGuard`'s owner-bypass runs _after_ the location-binding check) surfacing in a new controller this plan's owner brand-global flow newly exercises.
- **Fix:** `$brandSlug/index.tsx` now guards the stop-list query with `enabled: ... && activeLocationId != null` (consuming this plan's `activeLocationIdQuery`) and defensively reads `(stopListResult?.data?.items ?? []).length` instead of an unguarded `.items.length`.
- **Not committed by this agent** — surfaced and fixed in the same verification session, on top of this plan's `activeLocationIdQuery` export. Included here only for accurate traceability; do not attribute Task 1-3 authorship of `3590cd0` to this plan's own commit list above.
