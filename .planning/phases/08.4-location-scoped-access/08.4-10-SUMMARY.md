## Accomplishments

- **Backend deviation (not in original plan file list, see Decisions Made):** `GET /v1/members/:memberId/location-roles` — `ListMemberLocationRolesService` + `MemberLocationScopeReader.listLocationRolesForMember` (joins `member_location_scope` to active `locations`, filters null roles) + controller handler, gated `ac: ['update']` (owner-only, brand-neutral, mirrors the existing POST/DELETE handlers on the same controller).

- `MemberLocationRoleMatrix` — for each member: a list of `(location name, role <Select>, remove button)` rows sourced from `memberLocationRolesQuery` (query disabled for non-owners), plus an inline "add location" row (location `<Select>` limited to the brand's not-yet-assigned locations + role `<Select>` covering `SYSTEM_ROLES` + tenant's custom roles + "Add" button). Reuses `member-role-row.tsx`'s `useMutation`/`toast`/`invalidateQueries` idiom verbatim, invalidating `['team','location-roles',memberId]`, `['team','members']`, and `['roles','members']` on every mutation.

A member's brand access is derived from the brands of the locations they are scoped to — there is no separate brand-scope setting."` — grep-verified zero remaining matches of the old phrase.
- `member-role-row.tsx` deleted (fully superseded, zero remaining references after the swap).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing Critical Functionality] Added GET /v1/members/:memberId/location-roles**

- **Found during:** Task 1 planning — before writing `memberLocationRolesQuery`, checked what backend read path it would call and found plan 07 shipped only `POST`/`DELETE` on `member-location-roles.controller.ts`, no `GET`. No other endpoint in the codebase exposes a member's full set of `(location, role)` pairs (`findRoleForMemberAtLocation` only resolves one location at a time, for internal session-bootstrap use).
- **Issue:** Without this, `MemberLocationRoleMatrix` cannot render "current pairs" — the plan's central must-have ("The Team page shows, per member, a matrix of (location -> role) pairs") is unsatisfiable.
- **Fix:** Added `listLocationRolesForMember` to the `MemberLocationScopeReader` port + Drizzle reader (joins active `locations`, filters null roles), a new `ListMemberLocationRolesService` (`.execute(input)` pattern, mirrors `ListMembersService`), and a `GET :memberId/location-roles` handler on the existing `MemberLocationRolesController`, gated `@Permissions({ ac: ['update'] })` — same gate as the write endpoints, matching the plan's own stated intent ("matching the server-side ac:['update'] gate").
- **Files modified:** see key-files above (backend section).
- **Verification:** `pnpm nx run api:typecheck` and `pnpm nx run api:lint` clean; `pnpm nx run api:test` for `test/unit/identity` — all relevant specs green (272/273; the 1 pre-existing failure is `identity-boot-integration.spec.ts`'s unrelated Stripe Connect env-guardrail check, documented as pre-existing in plan 04's SUMMARY, not touched by this plan). Live-verified against the seeded `demo` tenant via direct `curl` calls (sign-in, set-active-org, GET returns the manager's 2 pizza-location pairs correctly) and confirmed 403 for a non-owner (`manager@demo.local`) attempting the same GET.
- **Committed in:** `bb532c0`

## Issues Encountered

- During browser smoke-testing, an early run crashed with `TypeError: (locationsResult?.data ?? []).filter is not a function` — traced to my own test script navigating to an invalid brand-slug URL (`/demo/team`, using the tenant slug instead of a real brand slug like `/pizza/team`), which returns a 403 problem-details body instead of an array. The exact same `data ?? []` pattern already exists, unguarded, in the already-shipped `locations.tsx` (`locationsResult?.data ?? []`) — not a defect introduced by this plan, and out of scope per the deviation rules' scope boundary (pre-existing pattern, not touched by this plan's file list). Re-ran with the correct brand-slug URL; page rendered cleanly with zero console/page errors.
- Hit the login rate limiter (429) after several scripted sign-ins while probing the non-owner-visibility case in the browser. Not pursued further since the same guarantee was already independently confirmed three ways: (1) `team.tsx`'s `{isOwner && ...}` JSX conditional means the column is never in the DOM for non-owners, deterministically; (2) `MemberLocationRoleMatrix` has its own `if (!isOwner) return null` defense-in-depth; (3) direct `curl` as `manager@demo.local` against the GET endpoint returned a hard 403.
