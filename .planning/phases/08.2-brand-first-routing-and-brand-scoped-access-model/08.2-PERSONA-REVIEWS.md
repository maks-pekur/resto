# Phase 08.2 — Persona Reviews

## Skeptic Review (persona-skeptic)

**Reviewer stance:** hired to disagree. Every finding below is grounded in `path:line` from the
current `admin-vite-spa` tree. The headline: **the founder chose FULL scope, but ~70% of the
"server-enforced access model" the seed describes already exists and ships today.** The genuinely
new work is small and security-positive; the genuinely _risky_ new work (single-active-brand
re-login + location scope) defends against a threat the existing per-request guard already covers,
and hangs off a `locations` table **that does not exist**. This phase as written is a cosmetic IA
refactor with a security-phase costume on top.

---

### CRITICAL — The `locations` table does not exist; "move member scope to location level" is a hidden net-new feature

**Hidden assumption:** SEED-001 §Access model and ROADMAP SC#6 both say "move `member_brand_scope`
from brand-level to **location-level**" as if `locations` were an existing entity to re-point a FK at.

**Reality:** there is no locations model anywhere in the codebase.

- `packages/db/src/schema/` contains: `audit, auth, brands, customer-profiles, inbox, menu, ordering, outbox, tenants` — **no `locations.ts`** (`ls packages/db/src/schema/`).
- `grep -rln "location" packages/db/` returns **zero** schema/migration hits.
- The hierarchy CLAUDE.md advertises (`Brand → Location → Menu / Zones / Staff`) is aspirational; `Location` is not implemented. `member_brand_scope` is keyed on `(member_id, brand_id)` with a brand FK — `packages/db/src/schema/brands.ts:125-157`.

**Why it bites:** "extend member scope to location level" silently grows a whole `locations` feature —
table, composite-FK wiring (ADR-0020 I-2), RLS enable/force + isolation policies, an admin CRUD
surface to _create_ locations, association of menus/orders/zones to a location, seed data, and a
migration. That is a multi-day sub-phase masquerading as a one-line FK change. **And the first
paying customer is single-brand, single-owner** — they will never create a second location, let
alone a member scoped to one.

**Recommendation:** **CUT location-scope entirely from 08.2.** Do not introduce `locations` in this
phase. If member scoping must be touched at all, keep it at the existing brand level (already
shipped — see next finding). Location is a Phase 17 / MVP-2 concern at the earliest, and only once
a real multi-location tenant exists to validate the shape against.

### CRITICAL — The "server-enforced brand-scoped access model" already exists and ships today

**Hidden assumption:** the seed frames the access model as _not yet implemented_ ("the intended
access model is not yet implemented", SEED-001:24). The founder picked FULL scope partly on that
premise.

**Reality — already in `main`:**

- **Per-request server-side brand-scope authz:** `BrandScopeGuard` (`apps/api/src/contexts/identity/interfaces/http/guards/brand-scope.guard.ts:39-85`) reads the active brand from ALS, looks up `member_brand_scope` for `(userId, tenantId)`, and throws `403 brand.access_denied` when the brand is not in scope. **Owner `baseRole` bypasses** (`:70`) — exactly the "owner sees all brands" rule.
- **Tamper resistance:** the brand is resolved from `x-brand-slug` **server-side** against the tenant's brands in `TenantContextMiddleware` (`apps/api/src/shared/tenant-context.middleware.ts:68-72`), and `AuthGuard`'s `auth.tenant_mismatch` (RES-172) rejects any `x-tenant-id` diverging from the session (`:78`). A member editing the URL or a cookie cannot reach an out-of-scope brand — the guard reads scope from the DB, not from the client. **This is SC#4, already true.**
- **Owner free-switch, no re-login:** `brand-switcher.tsx` already switches brand on click with zero re-login (`apps/admin/src/components/brand-switcher.tsx:34-37`). **This is SC#3, already true** (for everyone, in fact).
- **Existing proof:** `apps/api/test/e2e/catalog-brand-scope.e2e.spec.ts:143-156` already asserts "scoped operator writes in-scope = ok", "out-of-scope = 403", "owner writes anywhere". `brand-scope-guard.e2e.spec.ts` asserts no cross-tenant scope leak.
- **api-client already sends the active-brand header** (`apps/admin/src/lib/api-client.ts:39`) — the seed's "add active-brand header" is already done.

**Verdict:** SC#3, SC#4, and the entire "server-side tamper-proof per-request brand authz" are
**already shipped**. The phase's draft success criteria are ~50% testing-what-already-works.

**Recommendation:** Rewrite the phase brief to acknowledge the existing guard. The _only_ honest
net-new authz delta is whatever today's "empty scope rows = default-allow" (`brand-scope.guard.ts:77`)
doesn't cover. Decide consciously whether default-allow is the intended posture; if not, that's a
1-line change + a test, not a phase.

### HIGH — "Re-login to switch brand" defends against nothing the per-request guard doesn't already cover; it is pure friction

**The claim:** a member must be "active in exactly one brand per session" and **re-login** to switch
to another permitted brand, because single-active-brand pinning is "security-sensitive"
(SEED-001:24-25, ROADMAP SC#5).

**Probe — what concrete threat does single-active-brand-session stop that per-request brand-scope
authz does not?** I can't find one.

- Authorization is already evaluated **per request** against the DB scope (`brand-scope.guard.ts:72-83`). Whether the member "switched" brand in-session or re-logged in, every single request is independently checked. A member with scope `{A}` gets 403 on brand B's endpoints **regardless of session state**.
- "Single active brand" is a _session-shape_ constraint, not an authorization boundary. It defends against… a member seeing two brands' data in two tabs? But if both brands are in their scope, that's _authorized_ — there's no threat. If a brand is _not_ in scope, the guard already blocks it.
- Worse, the mechanism is incoherent with the actual session model: Better Auth's `setActive` sets the active **organization (= tenant)**, not brand (`brand-switcher.tsx:35`). Brand is a per-request header, not a session property. "Re-login to switch brand" would require _inventing_ a brand-pinned-session concept that doesn't exist, then forcing a logout/login cycle to mutate it — building friction machinery from scratch to constrain something that isn't currently a security boundary.

**Why it bites:** this is the single most expensive and most user-hostile item in the phase, and it
buys no security. It also corrupts the multi-brand UX for the _exact_ persona it targets (a trusted
member working two of the tenant's brands now has to log out and back in to move between them).

**Recommendation:** **CUT "re-login to switch brand" (SC#5) entirely.** Keep per-request
brand-scope authz (already shipped). If product wants members defaulted into one brand on login,
that's a UI default (land on their first scoped brand), not a re-auth wall. Do not build a
brand-pinned session.

### HIGH — Reserved-word slug guard already ships; the only real risk is the maintenance landmine the phase is about to formalize

**The claim (SC#2):** "Brand-slug creation rejects reserved root words server-side."

**Reality:** already implemented. `packages/domain/src/brand-slug.ts:21-23` refines `BrandSlugValue`
against `RESERVED_SLUG_SET`, and `packages/domain/src/reserved-slugs.ts:7-33` already lists
`admin, api, app, assets, auth, dashboard, login, menu, signup, …`. `provision-brand.service.ts`
takes a `BrandSlug` (`:11`), so the refine runs at creation. **SC#2 is already true.**

**The real (unaddressed) risk — the brittle coupling the phase introduces:** today brand slugs live
on **subdomains** (`<slug>.menu.resto.app`, `provision-brand.service.ts:48`), so the reserved list
guards against _subdomain_ collisions — a stable, rarely-changing set. The moment 08.2 makes the
slug the **first path segment of the admin app** (`/{brand}/...`), the reserved list must now also
mirror **every admin root route** (`login, signup, onboarding, accept-invitation, reset-password,
forgot-password, …` — all real route files in `apps/admin/src/routes/(auth)/`). **Every new root
route silently becomes a new reserved word**, and forgetting to add it means a brand slug can shadow
a real route. The reserved list and the route tree become two sources of truth that must be kept in
lockstep by hand — a classic drift landmine. The phase plans to _grow_ this coupling, not avoid it.

**Simpler structural alternative the phase does not consider:** keep a one-segment namespace prefix
for the brand workspace — `/b/{brand}/...` (or `/app/{brand}/...`). Then `login`, `onboarding`,
etc. live at the root, brand pages live under `/b/`, and **the two namespaces can never collide** —
no reserved-word list maintenance, ever. The founder's stated motivation was "drop the ugly
`/dashboard` middle segment"; `/b/` is one short, honest segment that removes the ambiguity
_without_ coupling slug validation to the route tree. This deserves an explicit decision in
discuss-phase, not a silent default to root-level brand slugs.

**Recommendation:** Either (a) adopt a `/b/{brand}` prefix and drop the reserved-route coupling
entirely, or (b) if root-level brand slugs are chosen, add a **CI test that diffs the admin root
route names against `RESERVED_SLUGS`** so drift fails the build. Do not rely on a human remembering.

### HIGH — This is a Phase-17-class refactor pulled forward by an aesthetic itch, mislabeled as a security phase

**The tension the seed itself names:** SEED-001:56 explicitly recommends **"URL-first,
data-scope-later"** — move the URLs now, defer the data-scope (team/settings still tenant-scoped).
The founder **overrode** this to FULL scope. The override is worth surfacing honestly.

**Evidence of cosmetic origin:** SEED-001:18-22 — the trigger was _local hand-testing during Phase
08.1_ and annoyance at `/dashboard/{brand}/brands/{brand}/payouts`-class URLs ("dashboard is
overloaded"). That is a legitimate IA complaint. But the access-model half rides in on its
coattails labeled "security-sensitive", when the security it describes **already exists** (see the
two CRITICALs).

**Why it bites:** the founder is single-owner-customer-bound until Q1 2027 (CLAUDE.md Timeline).
The member/location enforcement only activates "before onboarding the first multi-member tenant"
(SEED-001:30) — which **is literally the Phase 17 trigger** (ROADMAP:531, "first paying tenant adds
a 2nd member with role ≠ owner"). Building member-pinning + location scope now means writing,
testing, and securing an enforcement model **with no user who can exercise it**, no UI to create the
members or locations it governs, and a real chance the shape is wrong by the time a multi-member
tenant actually appears (the canonical "build it before you have the requirement" miss). Meanwhile
the cosmetic URL win — the thing that actually annoyed the founder — is cheap and available now.

**Recommendation:** **Split the phase.** Ship the IA/routing + owner-switch + slug-CI-guard now
(days, low risk, scratches the real itch). **Defer member single-active-brand + location scope to
Phase 17**, where it belongs, with a real multi-member tenant to validate against. Do not let the
genuinely-cheap cosmetic work drag the genuinely-premature security work into MVP-1.

**Recommendation:** gate the routing refactor behind an explicit redirect-map test + the ported
ADM-00 Playwright smoke (login → land on brand → deep-link → payouts return). Treat the Stripe
return URL as a named regression checkpoint, not an afterthought.

## Top 3 things the founder must consciously decide

1. **Root-level `/{brand}` vs prefixed `/b/{brand}`.** Root-level permanently couples brand-slug
   validation to the admin route tree (every new root route = new reserved word; drift = a slug can
   shadow a route). `/b/{brand}` removes the coupling forever for one extra honest segment. This is
   the single most consequential IA decision in the phase and is currently a silent default.

2. **Does "re-login to switch brand" survive contact with the question "what threat does it stop
   that the per-request guard doesn't?"** I claim: none. If the founder can't name a concrete threat
   beyond what `BrandScopeGuard` already enforces per request, **cut it** — it's friction, not
   security, and it requires inventing a brand-pinned session that doesn't exist today.

3. **Build location-scoped membership now, or wait for a tenant who has locations?** There is no
   `locations` table, no multi-location tenant, and no member to scope — the first customer is
   single-owner. Building the enforcement before the entity, the UI, or the user exists is the
   textbook premature-abstraction risk. Defer to Phase 17 (its own trigger already covers this) and
   keep member scope at the existing, already-enforced brand level — or consciously accept building
   a feature months before anyone can use it.

I agree with the skeptic's two big cuts (locations YAGNI; re-login friction) and won't re-argue them
at length — I reach them from the architecture angle below. My distinct contribution is on the three
things the skeptic underweights: **where the brand pin must live to be tamper-proof at all**, **the
brand-RLS gap underneath the guards**, and **the default-allow → default-deny flip that is the actual
security delta**.

### TL;DR (decision-grade)

- The phase **conflates two changes of very different risk**: a low-risk cosmetic URL refactor and a
  **net-new security control**. Ship them as two slices, gated differently. (Converges with skeptic.)
- The hardest requirement — "member re-login to switch brand" — **fights the grain of the auth
  model**. Brand ≠ org; the brand is a URL/header value with **no server-side pin and no RLS
  binding**. A tamper-proof pin is a new primitive, not an extension of `setActive`.
- The genuine, shippable security win hiding in this phase is **flipping member scope from

  which is modeling for zero users.

### CRITICAL-1 — A tamper-proof "active brand" has no server-side home today; it is a new auth primitive, and `setActive` does not provide it

**What/why.** SC#3/#5 require a server-pinned active brand (owner free-switch; member single-brand,
re-login to change). Nothing in the stack can host that pin as-is:

- The active **tenant** (org) is pinned server-side on `session.activeOrganizationId` and mutated by
  `authClient.organization.setActive` (`brand-switcher.tsx:34`, read at `auth.guard.ts:99,215`). Per
  the BA 1.4.22 org-plugin docs, `setActive` switches the active org **in-session, with no re-login**.
  So even the tenant pin is not a "re-login to switch" primitive — and brand is a level below.
- The active **brand** is not server state at all. In the live SPA it is `brands[0]?.slug`
  (`dashboard/_layout.tsx:34`) and reaches the API as the per-call `x-brand-slug` header derived from
  the URL (`api-client.ts:39`). `TenantContextMiddleware` resolves the brand purely from that header
  (`tenant-context.middleware.ts:68-72`). **There is no signed active-brand cookie in the Vite SPA** —
  the Phase-2 `resto.active_brand` HMAC cookie is dead, surviving only in `apps/admin/Dockerfile`,
  `playwright.config.ts`, `.env.example`, and an e2e stub (a Next server-action artifact). The
  brand-switcher only calls `setActive` (changes the _tenant_) then navigates by slug.

Consequence: to enforce "members pinned to one brand per session" you must introduce a **server-side
per-session active-brand field** that is (a) set at login/scope-resolution, (b) the _only_ source the
API trusts, and (c) makes `x-brand-slug` advisory — a member presenting any other brand via
header/URL/cookie gets an existence-hiding 404 regardless. Two clean options:

1. **Map brand → BA team** and pin via the plugin-managed `activeTeamId` session field. BA already
   stores this server-side and (per docs) `/update-session` _rejects_ client writes to plugin-managed
   fields — so it is tamper-resistant by construction, and "set active brand" becomes a first-class BA
   mutation you can authorize (members can't `setActiveTeam`). Lowest-NIH path **if** brand⊆org maps
   to team⊆org cleanly. **Open question:** are we willing to take a structural dependency on the BA
   team plugin for the brand concept?
2. **Custom session-bound active-brand** (signed cookie validated server-side against a session-stored
   `active_brand_id`, never trusting the cookie value). More code; hand-rolls what the team plugin
   gives you.

**Recommendation.** Decide the pin location **before any code** — this is exactly what the seed's
mandated security pass is for. Lean: evaluate brand-as-team first. Whatever you pick, the invariant
is: **the API derives the active brand from server-side session state, never from a client-supplied
value**, and `x-brand-slug` is downgraded to "must equal the pinned brand or 404." (Note: if you cut
re-login per the skeptic's HIGH, you still want a _cookie-persisted_ active brand for owner UX — but
that one needn't be a security pin, only the member case needs the server pin.)

### CRITICAL-2 — Brand isolation today is application-layer only (no brand GUC, no brand RLS); the access model is being hardened on a fence with a structural gap

**What/why.** The platform's headline invariant is **RLS + ScopedTx double-enforcement at the
tenant level**. Brand has **no equivalent**. `withBrand`/`getBrandId` (`packages/db/src/context.ts:71-97`)
only place `brandId` into ALS; there is **no `app.current_brand` GUC and no brand RLS policy**. Brand
authz is enforced solely in app code — `BrandScopeGuard` reads `getBrandId()` and compares against
`member_brand_scope` (`brand-scope.guard.ts:46-83`), opt-in per route via `@RequireBrand`.

Consequence: SC#4's promise ("a member cannot reach an out-of-scope brand by editing URL/cookie") is
only as strong as the weakest controller. The moment one tenant-scoped query reads brand-owned rows
without `@RequireBrand` + an explicit brand filter, a **cross-brand read within the same tenant** is
possible — RLS will not catch it, because RLS scopes by tenant only. This is the same bug class
CLAUDE.md's tenancy invariant exists to prevent, one level down (brand inside tenant). The skeptic is
right that the _guard_ ships and works; my point is the _defense-in-depth layer the rest of the
platform mandates is absent for brand_, and this is the phase that should decide whether that's
acceptable.

**Recommendation.** Treat brand isolation as a first-class boundary for this phase, not a guard-only
convention. Minimum bar: (1) a cross-**brand** regression matrix over every brand-scoped table
(mirroring the existing cross-tenant matrix the project already runs — SC#4 already asks for one
isolation e2e; make it a matrix); (2) an audit of which controllers read brand-owned data _without_
`@RequireBrand` (catalog uses it; check payouts/theme/domains). **Founder decision:** add a brand GUC

- RLS policy now (real defense-in-depth, ~1 migration per brand-scoped table) or accept app-layer-only
  brand isolation as documented debt? A phase whose purpose is hardening brand access is internally
  inconsistent if it leaves this gap. Lean: add the GUC + policy at least on the highest-value
  brand-owned tables (payments/payouts, catalog) this phase; full coverage can follow.

### CRITICAL-3 — Current member scope is DEFAULT-ALLOW; the model needs DEFAULT-DENY, and that flip is the real security delta

**What/why.** Both `BrandScopeGuard` (`brand-scope.guard.ts:77`) and `ListMyBrandsService`
(`list-my-brands.service.ts:35`) treat **`null`/empty scope rows as "access ALL brands"**
(`canViewAllBrands`). The port doc states it: "`null` means the member has no scope rows … the
UX-friendly default that grants access to ALL brands" (`member-brand-scope-reader.port.ts:6-11`).
That is the inverse of what SEED-001 requires: a member with no scope should reach **nothing**; only
the **owner** (`baseRole === 'owner'`) is unrestricted. Today the code conflates two "unrestricted"
notions — owner→all (correct, `brand-scope.guard.ts:70`) and member-with-no-scope→all (a UX
convenience that becomes a **privilege-escalation hole** under the new model). This is the same
default-allow the skeptic flags at `:77`; I'm elevating it from "1-line decision" to **the central
security objective of the phase**, because flipping it correctly (without breaking the owner path or
the freshly-onboarded-owner-with-no-scope-rows case) is the part that actually needs a security pass
and tests.

**Recommendation.** Make semantics explicit and role-aware: `owner` ⇒ unrestricted; any non-owner ⇒
scope is a strict allow-list and **empty scope = no access**. Add a regression test that a
freshly-invited member with zero scope rows gets 403 on every brand-scoped route, _and_ that a
brand-new owner with zero scope rows still gets all brands. Shippable independently of granularity.

### HIGH-1 — Location granularity is net-new modeling for zero users; cut it (converges with skeptic CRITICAL-1)

**What/why.** Grep across `packages/db/src/schema`, `packages/domain/src`, `apps/api/src/contexts`
finds **no `locations`/`Location` entity**. `member_brand_scope` is brand-keyed
(`schema/brands.ts:125-157`). "Move scope to location-level" therefore means: new `locations`
aggregate + table (with `tenant_id` + composite FK `(brand_id, tenant_id) → brands(id, tenant_id)`,

of brand-level scopes to "all locations of that brand," plus propagation through resolver/guard/
reader/`list-my-brands`. Multi-table migration + a new bounded concept — for a single-brand,
owner-only first customer with no non-owner members (multi-member is the Phase-17 trigger).

**Recommendation (the cleanest cut in the phase).** Split the access model: **now (08.2)** ship the
security-correct core at **brand level** — default-deny flip (CRITICAL-3) + tamper-proof server-side
pin (CRITICAL-1) + brand-isolation net (CRITICAL-2); **defer** `locations` + `member_location_scope`
to the first multi-member/multi-location tenant. **Open question:** is there a concrete first-customer
requirement for _location_-level (not brand-level) member scoping in MVP-1? If not, defer.

### HIGH-2 — Reserved-word guard exists but is incomplete for path-based routing; derive it from the route table

**What/why.** The guard SC#2 asks for **already exists**: `BrandSlugValue` refines against
`RESERVED_SLUG_SET` (`brand-slug.ts:21-23`), enforced at create (`me-brands.controller.ts:113`). But
the set was built for **subdomain** collisions and is missing root route words the new IA introduces —
notably `onboarding` (a real sibling of `/{brand}` at the root: the no-brands redirect target,
`dashboard/_layout.tsx:37`), plus `accept-invitation`, `forgot-password`, `reset-password`. `menu` is
reserved (good); `team/settings/payouts/theme/domains` are not (lower risk as depth-2 child paths).
The deeper issue (the skeptic and I agree): a hand-maintained list that must mirror the router is a
drift landmine.

**Recommendation.** Either adopt a `/b/{brand}` prefix (kills the coupling — the skeptic's structural
alternative, which I endorse), **or** if root-level slugs are chosen, **derive the reserved set from
the router's root route table** (or a unit test that fails if a root segment isn't reserved) so they
can't drift. Either way: before shipping the stricter guard, confirm **no existing brand in any env
has a now-reserved slug** — existing rows bypass the create-time refine. **Open question:** do any
seeded/dev/first-customer brands already use a now-reserved slug?

### HIGH-3 — Sequencing vs Phase 10: the URL half must land first; the access-model half does not gate Phase 10

**What/why.** Placing 08.2 before Phase 10 is right for the **cosmetic IA** — Phase 10 adds admin
surfaces (orders feed, order detail) you don't want to build under `/dashboard/...` then move. But
the _access model_ has **no dependency from Phase 10** (operator-facing, single-brand owner-only first
customer). So only the URL half gates Phase 10. Compounding the risk: this lands on `admin-vite-spa`

### MEDIUM-1 — When the brand pin lands, reconcile the `x-brand-slug` header against it (mirror the existing `tenant_mismatch` cross-check)

**What/why.** The API trusts client-sent `x-tenant-id` only because `AuthGuard` cross-checks it
against the session active org (`auth.guard.ts:108-119`, `auth.tenant_mismatch`) — a sound design.
The brand header has **no equivalent cross-check**: middleware resolves the brand from `x-brand-slug`
and binds it; the guard then authorizes. If a server-side active-brand pin is added (CRITICAL-1), the
middleware/guard must reconcile the header against the pin the same way, or the pin is decorative.

**Recommendation.** Add a `brand_mismatch` cross-check mirroring `tenant_mismatch`: for a **member**,
resolved brand MUST equal the session-pinned brand or reject (existence-hiding 404 per SC#4); for an
**owner**, the header/URL brand is free but must be a brand of the active tenant.

### MEDIUM-2 — "URL-first, data-scope-later" for team/settings creates a UX lie the URL shouldn't tell

**What/why.** SEED-001 moves `team`/`settings` under `/{brand}/...` now but keeps the **data
tenant-scoped** until later. For a single-brand tenant this is invisible; for a multi-brand owner the
URL implies per-brand team/settings while editing one edits the tenant's. Acceptable deferral, bad
URL promise.

**Recommendation.** Keep `team`/`settings` at a brand-neutral path (`/settings`, `/team`) until the
data is actually brand-scoped, and only brand-path the genuinely brand-scoped pages (menu, payouts,
theme, domains). Cheapest correct option; avoids the lie. **Open question:** does the founder want the
URL to _promise_ per-brand team/settings before the data supports it?

### LOW-1 — Exit the security pass with named, testable invariants (not prose SCs)

**What/why.** ROADMAP §08.2 Requirements are "TBD." Given three CRITICALs around enforcement
semantics, the discuss/security pass should emit named invariants — "members are default-deny,"
"active brand is server-derived only," "brand header is advisory and reconciled" — each mapping 1:1
to an e2e test, the way ADR-0020 invariants map to the isolation spec. Don't ship the security half on
prose-only success criteria.

### Top 3 decisions the founder must make

1. **Where does the tamper-proof active-brand pin live? (CRITICAL-1)** — Brand-as-BA-team
   (`activeTeamId`, server-managed, lowest NIH) vs a custom session-bound signed active-brand. This is
   the load-bearing decision of the phase; re-login-to-switch and 404-on-tamper are impossible to
   enforce cleanly without it, and `setActive` does **not** provide it (brand ≠ org; BA switches orgs
   without re-login anyway). _(If you also cut re-login per the skeptic, the member case still needs a
   server pin; only the owner case can stay a plain cookie.)_

2. **Cut location-granularity and ship the security core at brand-level? (HIGH-1 / CRITICAL-3)** — The
   `locations` table doesn't exist and no MVP-1 customer needs location-level scope. The real,
   shippable security win is the **default-allow → default-deny flip** at brand level — small, testable,
   high-value. Recommended: ship that now, defer `locations`/`member_location_scope` to the first
   multi-member tenant.

3. **Add brand-level RLS now, or accept app-layer-only brand isolation as documented debt?
   (CRITICAL-2)** — Today brand isolation has no GUC/RLS underneath the guards, so one forgetful
   controller can leak cross-brand-within-tenant. A phase whose purpose is hardening brand access is
   internally inconsistent leaving this open. Recommended: at minimum add brand GUC + policy on the
   highest-value brand-owned tables (payments/payouts, catalog) this phase.
