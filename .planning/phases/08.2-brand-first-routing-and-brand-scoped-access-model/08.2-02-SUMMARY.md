## Decisions Made

1. **Tables covered by brand RLS (9 total):** `menu_categories`, `menu_items`, `menu_item_sizes`, `menu_modifier_groups`, `menu_modifier_options`, `menu_item_modifier_groups`, `menu_stop_list`, `catalog_brand_stop_version`, `orders`. All have `brand_id NOT NULL`.

2. **Tables excluded from brand RLS:** `menu_item_slug_aliases` (no `brand_id` column; only `tenantId` + `itemId`) and `catalog_menu_version` (no `brand_id`; tenant-level version counter). These tables are covered by tenant RLS only.

3. **Pass-through clause is mandatory:** `current_brand_id() IS NULL OR brand_id = current_brand_id()` — the `IS NULL` branch ensures tenant-level queries (no brand bound) still return all rows for the tenant.

4. **Bind order in withTenant:** `app_bind_tenant` first, then `app_bind_brand` (RESEARCH Pitfall 2 — brand context presupposes tenant context).

5. **Preflight location:** `apps/api/src/shared/preflight/assert-brand-rls.ts` — `apps/api` already depends on `postgres` directly, so this mirrors the pattern without an arch violation.

## Accepted Debt

### payments / payment_refunds — No Brand-Level DB Isolation (SC-6 Escape Hatch)

**Issue:** `payments` and `payment_refunds` tables have NO `brand_id` column — they reach a brand only via `orders.brand_id`. Brand RLS on these tables would require adding a `brand_id` column + data backfill.

**Resolution (SC-6 escape hatch):** Brand isolation for payments/payment_refunds is **app-layer-only**:

- Tenant RLS already filters to the correct tenant
- BrandScopeGuard on the payouts controller restricts to the active brand's orders at the application layer

This is tracked in the migration header as `-- D-14 SCOPE NOTE` and is the documented acceptable residual risk per ROADMAP SC-6. No guest or operator can reach another brand's payment rows because:

1. The query path always goes through payouts/orders join, filtered by brand at the application layer
2. Tenant RLS prevents cross-tenant leakage regardless

**Future resolution:** When brand_id is eventually added to payments (e.g. for reporting/multi-brand analytics), add a companion migration adding brand policy to both tables.
