# Phase 08.2: Brand-first Routing & Access-Control Core - Context

**Gathered:** 2026-06-29
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 08.2 delivers TWO things and nothing more:

1. **Brand-first routing / admin IA refactor** — drop the `/dashboard` prefix; every admin
   page lives under `/{brand}/...`; `/` redirects to the active brand; brand slugs are
   protected from colliding with root routes.
2. **Brand-level access-control core** — flip member brand-scope from default-allow to
   default-deny; move the "active brand" from a forgeable cookie into the server session;
   reconcile every request's brand against the session pin + the member's scope; owner
   free-switches in-session, a non-owner session is pinned to one brand at a time; add
   brand-level Postgres RLS on the most sensitive tables.

This phase operates entirely at the **brand** level using the existing fixed system roles
(`owner` / `admin` / `staff`). Explicitly **out of scope** (split into their own follow-on
phases per founder decision 2026-06-29 — see Deferred Ideas):

- **Owner-managed custom roles** (enable better-auth `dynamicAccessControl` + creator-subset
  privilege-escalation guard + owner role-builder UI).
- **Location-level scoping** (new `locations` entity + `member_location_scope` + locations
  admin UI).

</domain>

<decisions>
## Implementation Decisions

### Scope & Sequencing
- **D-01:** SEED-001's full vision is delivered as a SEQUENCE, not one phase (founder,
  2026-06-29). 08.2 = routing + brand-level access core only. Owner-managed roles and
  location scoping are separate follow-on phases. Nothing is dropped from the roadmap.
- **D-02:** Access enforcement in this phase is **brand-level**. Location granularity is out.
  Custom/owner-authored roles are out — keep the existing fixed `owner`/`admin`/`staff`
  system roles unchanged here.

### Routing / Information Architecture
- **D-03:** Brand-first URLs with **no prefix**: `/{brand}/...` (founder chose clean form over
  `/b/{brand}`). Drop the `/dashboard` segment entirely. Pages move under the brand:
  dashboard, menu, payouts, theme, domains, team, settings.
- **D-04:** `/` redirects to the active brand. Owner with multiple brands lands on the
  **last-active** brand (from the server-session pin / hint); fallback to a deterministic
  first brand. **No brand-picker screen** in this phase.
- **D-05:** `team` and `settings` move under the brand path but their DATA stays
  **tenant-scoped** for now (URL-first, data-scope-later). Keep these two pages
  brand-neutral in copy so the URL doesn't imply per-brand data (CTO MEDIUM-2).

### Reserved slugs / collision protection
- **D-06:** The reserved-word list for brand slugs is **derived automatically from the admin
  route table** — a new root route is automatically reserved, no hand-maintained list.
  Enforced **server-side** at brand-slug create/rename (extends the existing
  `packages/domain/src/brand-slug.ts` + `reserved-slugs.ts` validation). This is the agreed
  answer to the CTO/skeptic "maintenance landmine" concern for the clean `/{brand}` form.
- **D-07:** Detect and handle any EXISTING brand whose slug already collides with a reserved
  root word (migration-time check; forced-rename path if found). Verify none exist before
  shipping.

### Access-control core
- **D-08:** Flip member brand-scope from default-**allow** to default-**deny**. Today an
  empty/unset `member_brand_scope` grants ALL brands; after this phase, empty scope = NO
  brand. Owner (`canViewAllBrands` / null scope) stays unrestricted. **This is the primary,
  shippable security delta** (CTO CRITICAL-3).
- **D-09:** The "active brand" lives in the **server session** (server-managed source of
  truth), not a forgeable cookie. The exact mechanism — better-auth team `activeTeamId` vs a
  custom session-bound field — is a research/plan decision, but it MUST be server-managed and
  not forgeable from client input (CTO top-decision #1).
- **D-10:** Every request reconciles the request's brand (URL / `x-brand-slug`) against BOTH
  (a) the member's allowed scope AND (b) the session's active-brand pin. Mismatch returns an
  **existence-hiding 404/403**, mirroring the existing `auth.tenant_mismatch` cross-check in
  `tenant-context.middleware.ts`.
- **D-11:** Extend the existing `BrandScopeGuard` so brand-scoped routes are guarded by
  default rather than per-controller `@RequireBrand` opt-in (close the opt-in gap; CTO
  CRITICAL-2).

### Switching UX (owner vs non-owner)
- **D-12:** Owner switches between all tenant brands freely in-session — no re-login.
- **D-13:** A non-owner session is pinned to exactly ONE active brand at a time. Switching to
  another permitted brand is a **silent server-side session re-pin (re-issue), NOT a password
  re-entry**. SEED-001's "re-login to switch" is downgraded: single-active-brand is a
  UX/operational rule, not a security barrier (the per-request scope check is the real
  boundary — skeptic HIGH).

### Brand-level RLS (defense-in-depth)
- **D-14:** Add brand-level Postgres RLS **now** (GUC + policy) on at least the most sensitive
  tables — **payments/payouts + catalog** (founder choice). Mirrors the established tenant
  RLS double-enforcement pattern (ScopedTx + RLS). Closes CTO CRITICAL-2's "app-layer-only
  brand isolation" gap rather than carrying it as debt.

### Claude's Discretion
- Exact server-session active-brand pin mechanism (BA `activeTeamId` vs custom session field) — research/plan.
- Deterministic ordering for the owner `/` first-brand fallback — planner.
- Whether brand RLS extends beyond payments/payouts + catalog (e.g., to `orders`) — planner / security pass.
- Old `/dashboard/...` link handling: prefer a redirect to the new brand path where resolvable, else existence-hiding 404 — planner to confirm during the route refactor (watch the Stripe Connect return URL, already cleaned to `/{slug}/payouts` in a44239a — skeptic MEDIUM regression note).

</decisions>

<specifics>
## Specific Ideas

- Founder's headline product vision (captured for the follow-on phase, NOT this one): **the
  owner creates roles themselves, configures each role's permissions, and assigns roles to
  staff** — i.e. owner-authored dynamic RBAC. This maps directly onto better-auth's
  `dynamicAccessControl` (already integrated, gated off behind the creator-subset guard).
- Founder explicitly wants tamper-resistant enforcement (rejected the cookie-as-source-of-truth
  approach), which is why D-09 (server-session pin) and D-14 (brand RLS) are in scope.
- Employees should be limited to one or several **locations** of a brand, and may belong to
  several brands but work in only one at a time — the location half lands in the locations phase;
  08.2 establishes the brand-level single-active-brand session that it will refine.

</specifics>
