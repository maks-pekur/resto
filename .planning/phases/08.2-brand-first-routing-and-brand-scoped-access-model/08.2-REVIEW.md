# Phase 08.2: Code Review Report

**Reviewed:** 2026-07-03
**Depth:** deep
**Files Reviewed:** 19
**Status:** issues_found

## Summary

This phase introduces brand-first routing, a default-deny brand-scope authorization guard, brand-level Postgres RLS (fixed from PERMISSIVE to RESTRICTIVE in 0060), and admin-side brand switching. The architecture is well-reasoned and the audit doc (D-11) is accurate for the NestJS layer. Four blockers were found: a runtime crash in `resolveInitialBrandId` caused by the `resto_auth` role lacking table grants on `brands` and `member_brand_scope`; a `null` scope bypass in `SetActiveBrandService` that allows non-owners with no scope rows to pin any brand in their tenant; an unvalidated open redirect in the legacy `/dashboard/*` splat redirect; and a missing `p_is_system` effect in `app_bind_brand` that silently ignores the parameter, leaving the system-session bypass reliant solely on tenant-level `app.is_system` rather than a brand-level equivalent. Three warnings cover missing nonce cookie TTL, unguarded localhost Stripe Connect return URLs in production, and a `scope === null` semantic inconsistency between `SetActiveBrandService` and `BrandScopeGuard`.

## Critical Issues

### CR-01: `resolveInitialBrandId` queries `brands` and `member_brand_scope` under `resto_auth` — both tables have no grant to that role

**File:** `apps/api/src/contexts/identity/infrastructure/better-auth/auth.config.ts:162-198`

**Issue:** `resolveInitialBrandId` runs in a BA `databaseHooks.session.update.after` callback and therefore executes as `authDb.db` — the Drizzle client that connects under the `resto_auth` Postgres role. `resto_auth` is granted only: `user`, `session`, `account`, `verification`, `two_factor`, `member`, `invitation`, `organization_role` (SELECT/INSERT/UPDATE/DELETE), and `tenants` (SELECT/UPDATE) — per `packages/db/sql/auth-role.sql`. Neither `brands` nor `member_brand_scope` appear in those grants. Postgres will return `ERROR: permission denied for table brands` (or `member_brand_scope`) the first time any user sets an active organization after login. The bare `catch { return null; }` swallows this error silently, so `activeBrandId` is never written to the session. All brand-scoped operators will appear to have no active brand after org-switch, leaving them unable to reach any brand-scoped route without a manual `POST /v1/me/set-active-brand` call. This is a silent runtime regression.

**Fix:** Either grant `resto_auth` `SELECT` on `brands` and `member_brand_scope` (add to `packages/db/sql/auth-role.sql` and the idempotent boot provisioner) and add matching RLS permissive policies scoped `TO resto_auth`, OR move `resolveInitialBrandId` to a callback that runs under `resto_app` (e.g., use the `onActiveOrganizationSet` callback already wired into `buildAuth` opts, which fires in a separate transaction under the app role).

The cleaner fix is the second option — move brand resolution into the `onActiveOrganizationSet` callback in the identity module, where the `TenantAwareDb` (running as `resto_app` with RLS correctly bound via `withTenantId`) already has all required grants:

```typescript
// In identity-core.module.ts (or the wiring site):
onActiveOrganizationSet: async (session) => {
  if (!session.activeOrganizationId) return;
  const brandId = await resolveInitialBrandIdViaAppRole(
    db, // TenantAwareDb (resto_app role)
    session.userId,
    session.activeOrganizationId,
  );
  if (brandId !== null) {
    await sessionActiveBrandWriter.writeActiveBrand({
      sessionToken: session.token, // pass token through onActiveOrganizationSet opts
      activeBrandId: brandId,
    });
  }
};
```

### CR-02: `SetActiveBrandService` non-owner path allows brand-pin when `scope === null` (no scope rows)

**File:** `apps/api/src/contexts/identity/application/set-active-brand.service.ts:53-66`

**Issue:** The non-owner branch reads:

```typescript
if (scope !== null && !scope.includes(input.brandId))
  throw new BrandOutOfScopeError();
if (scope !== null && scope.length === 0) throw new BrandOutOfScopeError();
const tenantBrands = await this.brands.listForTenant(
  input.tenantId,
  scope ?? undefined,
);
```

When `scope === null` (member has zero rows in `member_brand_scope`) neither guard fires. `scope ?? undefined` becomes `undefined`, so `listForTenant` returns ALL brands for the tenant, and `find` succeeds for any brand in the tenant. A non-owner staff member who has no scope rows can therefore pin any brand in the tenant by calling `POST /v1/me/set-active-brand`. This directly contradicts D-08 (default-deny for non-owners: `null` means no-access, not all-access).

The audit doc section "MemberBrandScopeReader Contract" explicitly states: "non-owners treat `null` as no-access per D-08." `BrandScopeGuard` correctly handles this (lines 60–73 throw 404 / 403 when scope is null for non-owners). The service does not.

**Fix:**

```typescript
// Non-owner branch in set-active-brand.service.ts
const scope = await this.scopeReader.findBrandScopeForMember({
  userId: input.userId,
  tenantId: input.tenantId,
});
if (scope === null || !scope.includes(input.brandId)) {
  throw new BrandOutOfScopeError();
}
const tenantBrands = await this.brands.listForTenant(input.tenantId, scope);
const match = tenantBrands.find((b) => b.id === input.brandId);
if (!match) throw new BrandOutOfScopeError();
```

### CR-03: Open redirect in `/dashboard/$` splat route — unsanitized splat forwarded directly as `to:`

**File:** `apps/admin/src/routes/(protected)/dashboard-redirect.$.tsx:6-11`

**Issue:**

```typescript
const splat = (params as Record<string, string>)['*'] ?? '';
const target = splat.length > 0 ? `/${splat}` : '/';
throw redirect({ to: target, replace: true });
```

`splat` is the raw URL path component captured by TanStack Router's splat pattern. A URL like `/dashboard/%2F%2Fevil.com/anything` URL-decodes in the browser to `//evil.com/anything`; after prepending `/` the target becomes `///evil.com/anything` — a protocol-relative URL treated as `https://evil.com/anything` by the browser's `window.location`. Even without percent-encoding, `/dashboard//evil.com` produces `target = `//evil.com``.

The `safeNext` helper in `apps/admin/src/lib/auth/safe-next.ts` (which correctly rejects `//`-relative paths via `/^\/[\\/]/`) is not applied here.

This route is protected (inside `/_layout` which requires a session), so an attacker must trick an authenticated operator. The phishing vector is: send operator a link to `/dashboard//evil.com/fake-login` → operator's session redirects them to `//evil.com` still logged in.

**Fix:** Apply the same sanitization as `safeNext`:

```typescript
beforeLoad: ({ params }) => {
  const splat = (params as Record<string, string>)['*'] ?? '';
  const raw = splat.length > 0 ? `/${splat}` : '/';
  // Reject protocol-relative paths (//host) to prevent open redirect
  const target = /^\/[\\/]/.test(raw) ? '/' : raw;
  throw redirect({ to: target, replace: true });
},
```

### CR-04: `app_bind_brand` ignores its `p_is_system` parameter — brand-level `is_system_session()` bypass is inoperative

**File:** `packages/db/migrations/0058_brand_rls.sql:43-60`

**Issue:** The `app_bind_brand` function signature accepts `p_is_system BOOLEAN` mirroring `app_bind_tenant`, but the body never uses it:

```sql
CREATE OR REPLACE FUNCTION app_bind_brand(p_brand TEXT, p_is_system BOOLEAN)
...
BEGIN
  -- Only sets app.current_brand; p_is_system is silently ignored
  PERFORM set_config('app.current_brand', p_brand, true);
END
```

`app_bind_tenant` correctly sets `app.is_system` when `p_is_system = TRUE` (migration 0022). The brand-level restrictive policies in 0060 include `is_system_session()` as a bypass clause:

```sql
USING (is_system_session() OR current_brand_id() IS NULL OR brand_id = current_brand_id())
```

The `is_system_session()` predicate reads `app.is_system`, which is only set by `app_bind_tenant`. So for `withoutTenant('reason', op)` calls (which call `app_bind_tenant('', true)` and therefore set `app.is_system = 'true'`), the brand-level restrictive policy DOES fire the `is_system_session()` arm correctly — there is no isolation breach today.

However, the dead `p_is_system` parameter is a latent defect: anyone calling `app_bind_brand(brand_id, true)` expecting a system bypass at the brand level will be silently denied by the restrictive brand policy (because `is_system_session()` checks `app.is_system`, not any brand-level flag, and `app.is_system` may be `'false'` at that point). The parameter's existence is misleading — it matches the function signature of `app_bind_tenant` but has no effect, creating a future maintenance trap.

**Fix:** Either (a) remove the `p_is_system` parameter from `app_bind_brand` (and update callers in `client.ts`) since the brand bypass is correctly handled via the tenant-level `app.is_system`, or (b) add the missing `set_config('app.is_system', ...)` call if independent brand-level system-session control is intended:

```sql
-- Option a (recommended): drop the unused parameter
CREATE OR REPLACE FUNCTION app_bind_brand(p_brand TEXT)
RETURNS VOID LANGUAGE plpgsql SECURITY DEFINER SET search_path = pg_catalog, public
AS $$
DECLARE v_current TEXT := current_setting('app.current_brand', true);
BEGIN
  IF v_current IS NOT NULL AND v_current <> '' AND v_current <> p_brand THEN
    RAISE EXCEPTION 'app.current_brand already bound to % — refusing to rebind to %',
      v_current, p_brand USING ERRCODE = 'insufficient_privilege';
  END IF;
  PERFORM set_config('app.current_brand', p_brand, true);
END
$$;
```

Update `packages/db/src/client.ts` line 256 accordingly:

```typescript
await tx.execute(sql`SELECT app_bind_brand(${ctx.brandId})`);
```

## Warnings

### WR-01: OAuth nonce cookie has no `Max-Age` expiry — nonce persists until browser session ends

**File:** `apps/api/src/contexts/tenancy/interfaces/http/brand-onboarding.controller.ts:56-67`

**Issue:** `buildNonceCookieHeader` does not include a `Max-Age` attribute:

```typescript
const attrs = [
  `${OAUTH_NONCE_COOKIE}=${nonce}`,
  'HttpOnly',
  IS_PROD ? 'Secure' : '',
  'SameSite=Lax',
  'Path=/',
]
  .filter((a) => a !== '')
  .join('; ');
```

Without `Max-Age`, the nonce cookie is a session cookie. If the operator opens the OAuth flow, navigates away, and reopens the same browser session days later, the nonce cookie may still be present. An attacker who can replay the original state (before verification) could still pass the nonce check. Standard practice is to limit nonce cookies to 10-15 minutes.

**Fix:**

```typescript
const attrs = [
  `${OAUTH_NONCE_COOKIE}=${nonce}`,
  'HttpOnly',
  IS_PROD ? 'Secure' : '',
  'SameSite=Lax',
  'Path=/',
  'Max-Age=900', // 15 minutes
]
  .filter((a) => a !== '')
  .join('; ');
```

### WR-02: `STRIPE_CONNECT_RETURN_URL` and `STRIPE_CONNECT_REFRESH_URL` default to `localhost` with no production guardrail

**File:** `apps/api/src/config/env.schema.ts:247-248`

**Issue:**

```typescript
STRIPE_CONNECT_RETURN_URL: z.string().url().default('http://localhost:3001/stripe/return'),
STRIPE_CONNECT_REFRESH_URL: z.string().url().default('http://localhost:3001/stripe/refresh'),
```

`assertProdGuardrails` (in `prod-guardrails.ts`) only covers `S3_*`, `INTERNAL_API_TOKEN`, `BETTER_AUTH_SECRET`, `AUDIT_ERASURE_SALT`, `RESEND_API_KEY`, and `STRIPE_SECRET_KEY`. The two Stripe Connect URL defaults are not in `DEV_DEFAULTS` and are not checked by `assertProdGuardrails`. A production deploy that omits these env vars will silently send Stripe's return/refresh redirects to `http://localhost:3001`, causing Stripe Connect onboarding to appear to hang or fail with no operator-visible error.

**Fix:** Add both keys to `DEV_DEFAULTS` in `prod-guardrails.ts`:

```typescript
const DEV_DEFAULTS = {
  S3_SECRET_KEY: 'minio_dev_password',
  S3_ACCESS_KEY: 'minio',
  S3_ENDPOINT: 'http://localhost:9000',
  INTERNAL_API_TOKEN: 'internal_dev_token_change_me',
  STRIPE_CONNECT_RETURN_URL: 'http://localhost:3001/stripe/return',
  STRIPE_CONNECT_REFRESH_URL: 'http://localhost:3001/stripe/refresh',
} as const;
```

### WR-03: `MemberBrandScopeDrizzleReader` uses raw `tx.select()` instead of `ScopedTx` — violates ADR-0020 I-1

**File:** `apps/api/src/contexts/identity/infrastructure/member-brand-scope-drizzle.reader.ts:15-28`

**Issue:**

```typescript
const rows = await this.db.withTenant(async (tx) =>
  tx
    .select({ brandId: schema.memberBrandScope.brandId })
    .from(schema.memberBrandScope)
    .innerJoin(
      schema.member,
      eq(schema.memberBrandScope.memberId, schema.member.id),
    )
    .where(
      and(
        eq(schema.member.userId, input.userId),
        eq(schema.member.organizationId, input.tenantId),
      ),
    ),
);
```

The callback uses the raw Drizzle `tx` handle rather than the `ScopedTx` second argument. ADR-0020 I-1 and the CLAUDE.md "Repo-layer tenant filter is mandatory ON TOP of RLS" require every tenant-scoped table read to include an application-layer `tenantId` filter. Here, `memberBrandScope.tenantId` is never filtered in the application layer — only `member.organizationId` on the joined table carries the tenant check. RLS (0017_member_brand_scope_rls) is the only isolation fence.

While RLS does protect this query, the "I-1" invariant exists precisely because RLS alone has been identified as insufficient (one fence per the architectural constraints). The filter on `member.organizationId` is not the same as a direct `memberBrandScope.tenantId` filter.

**Fix:** Use the `ScopedTx` argument and `scoped.selectFrom()`:

```typescript
const rows = await this.db.withTenant(async (_tx, scoped) =>
  scoped.selectFrom(
    schema.memberBrandScope,
    and(
      eq(schema.member.userId, input.userId),
      // join to member is expressed via extraWhere or a raw tx join
    ),
  ),
);
```

Since `selectFrom` does not support `innerJoin`, the recommended fix is to keep `tx` for the join but add an explicit `eq(schema.memberBrandScope.tenantId, input.tenantId)` predicate:

```typescript
const rows = await this.db.withTenant(async (tx) =>
  tx
    .select({ brandId: schema.memberBrandScope.brandId })
    .from(schema.memberBrandScope)
    .innerJoin(
      schema.member,
      eq(schema.memberBrandScope.memberId, schema.member.id),
    )
    .where(
      and(
        eq(schema.memberBrandScope.tenantId, input.tenantId), // I-1: explicit app-layer filter
        eq(schema.member.userId, input.userId),
        eq(schema.member.organizationId, input.tenantId),
      ),
    ),
);
```

### IN-01: `BrandSwitcher` falls back to `brands[0]` when `activeBrandSlug` doesn't match — silently incorrect brand shown

**File:** `apps/admin/src/components/brand-switcher.tsx:27-31`

**Issue:**

```typescript
const activeBrand =
  (activeBrandSlug
    ? brands.find((b) => b.slug === activeBrandSlug)
    : undefined) ??
  brands[0] ??
  null;
```

If `activeBrandSlug` is set but no brand in the list matches (stale session, brand deleted after list loaded), the component silently displays `brands[0]` as the "active" brand. The header label will show a different brand than what the session has pinned. This can confuse an operator who is looking at brand-A data but sees brand-B in the header. The condition should render `null` / a placeholder instead of a stale first brand.

**Fix:**

```typescript
const activeBrand = activeBrandSlug
  ? (brands.find((b) => b.slug === activeBrandSlug) ?? null)
  : (brands[0] ?? null);
```

And handle `activeBrand === null` with a neutral placeholder label (e.g. "Select brand") rather than `'—'` for the sub-label to prompt the user to switch.
