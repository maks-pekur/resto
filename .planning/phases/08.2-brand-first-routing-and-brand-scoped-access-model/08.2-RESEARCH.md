## Summary

Phase 08.2 has two independent slices with different risk profiles. The routing refactor is
mechanical but wide-blast-radius: ~25 route files, every nav URL, every redirect, and one
money-path string in the API (`start-brand-onboarding.service.ts:207`). The access-control core
is a security change with real scope but the project already ships ~70% of the model — the
genuine net-new work is (a) the default-deny flip, (b) the server-session active-brand pin,
(c) BrandScopeGuard default-on, and (d) brand-level Postgres RLS.

The three open unknowns have been resolved by code investigation:

1. **Session pin:** No BA teams plugin exists in v1.4.22 (the org plugin has an OPTIONAL teams
   feature requiring new tables). The recommended mechanism is `session.additionalFields.activeBrandId`
   — same API as the existing `user.additionalFields.requiresPasswordChange`, zero new tables, and
   BA's `internalAdapter.updateSession` is the server-side write path the org plugin already uses
   for `activeOrganizationId`. [VERIFIED: source code]

2. **Brand RLS:** The tenant RLS pattern uses GUC `app.current_tenant` set via SECURITY DEFINER
   function `app_bind_tenant`. Payments and paymentRefunds tables have NO `brand_id` column —
   brand isolation here is achievable only indirectly (via `orders.brand_id`, which they FK into).
   The directly brand-owned tables that CAN have brand-level RLS added are: all `menu_*` tables
   and `orders`. A new GUC (`app.current_brand`) + SECURITY DEFINER wrapper (`app_bind_brand`) +
   policy on `menu_*` + `orders` is the clean path. [VERIFIED: source code]

3. **Reserved-slug derivation:** `RESERVED_SLUGS` in `packages/domain/src/reserved-slugs.ts` is
   a plain array. After the routing move, the admin root route segments (`login`, `signup`,
   `forgot-password`, `reset-password`, `accept-invitation`, `onboarding`) must be in that array
   OR a CI test must diff route names against the set. The recommended approach: add the missing
   root words to `RESERVED_SLUGS` AND add a Vitest unit test that imports both the TanStack router
   root route list and `RESERVED_SLUG_SET` and asserts every root segment is reserved. [VERIFIED: source code]

**Primary recommendation:** Implement as two sequenced PRs — PR-A (route rename + redirect + reserved
slug + Stripe URL fix) before PR-B (default-deny flip + session pin + BrandScopeGuard default-on +
brand RLS). PR-B must not land until PR-A is merged and verified, because the brand mismatch
cross-check in PR-B requires the URL shape from PR-A.

## Open Unknown 1: Server-Session Active-Brand Pin (D-09)

### Current state of the codebase

[VERIFIED: source code] The admin SPA active brand is **not server state today**. In
`dashboard/_layout.tsx:34` it is simply `brands[0]?.slug`. In `brand-switcher.tsx:34` the
`switchTo` function calls `authClient.organization.setActive({ organizationId: brand.id })` —
this sets the active **tenant** (org), not brand. The `x-brand-slug` header is derived from
the URL in `api-client.ts:39`. No signed cookie, no session field for brand.

The session table (`packages/db/src/schema/auth.ts`) has:

- `activeOrganizationId text` — managed by BA organization plugin, holds the tenant UUID
- No `activeBrandId` or equivalent column

The `TenantContextMiddleware` reads `x-brand-slug` and resolves the brand by slug via
`TenantAndBrandResolverService`, binding `brandId` into ALS (`TenantContext`). There is no
check that this brand matches anything server-authoritative — brand is purely header-derived.

### Why BA teams plugin is NOT the right path

[VERIFIED: better-auth dist/plugins/organization/organization.mjs] The BA organization plugin
in v1.4.22 has an OPTIONAL `teams` feature gated on `opts.teams?.enabled`. When enabled, it:

- Requires two NEW tables: `team` (id, organizationId, name, createdAt, updatedAt) and
  `teamMember` (teamId, userId, createdAt)
- Adds `activeTeamId` to the session table
- Exposes `POST /api/auth/organization/set-active-team` endpoint

Using this for brand pinning would require: provisioning a BA team row for each brand on brand
creation, a `teamMember` row for each `member_brand_scope` row, and keeping them in sync.
That is 2 new tables and a dual-write maintenance burden for a concept (brand) that already
has first-class schema. **Do not adopt the teams plugin for brand pinning.**

### Recommended mechanism: `session.additionalFields.activeBrandId`

[VERIFIED: better-auth dist/db/field.d.mts] BA supports `session.additionalFields` with the
same API as `user.additionalFields`. The existing codebase already uses `user.additionalFields`
for `requiresPasswordChange` (`auth.config.ts:260-267` + `auth.ts:16`).

**Implementation steps:**

**Step 1 — DB migration.** Add `active_brand_id text` (nullable, no FK enforced by BA — add a
soft FK comment) to the `session` table in `packages/db/src/schema/auth.ts`. Generate migration
with `pnpm db:generate`.

**Step 2 — BA config (`auth.config.ts`).** Add to the `betterAuth({...})` call:

```typescript
session: {
  expiresIn: 60 * 60 * 24 * 7,
  updateAge: 60 * 60 * 24,
  additionalFields: {
    activeBrandId: {
      type: 'string',
      defaultValue: null,
      input: false,   // client cannot write this via /update-session
      returned: true, // surface on session so guards can read it
    },
  },
},
```

Setting `input: false` makes BA's `/update-session` endpoint reject client writes to this field —
it is tamper-resistant by construction, identical to how `requiresPasswordChange` (`input: false`)
works. [VERIFIED: auth.config.ts:264]

**Step 3 — Server-side write path.** The only way to set `activeBrandId` is via
`ctx.context.internalAdapter.updateSession(sessionToken, { activeBrandId: brandId })` called
from a server-side BA hook or a custom NestJS endpoint. Two write occasions:

- **On login / set-active-org:** Add to the existing `databaseHooks.session.update` hook in
  `auth.config.ts` (which already fires on `POST /api/auth/organization/set-active`, line 285).
  When `activeOrganizationId` is being set, resolve the member's first scoped brand (or first
  brand for owner) and set `activeBrandId` in the same update.
- **On brand switch (D-12/D-13):** Add a new NestJS API endpoint
  `POST /v1/identity/me/set-active-brand` (protected by `AuthGuard`). For owner: accept any
  brand of the active tenant, call `internalAdapter.updateSession` to set `activeBrandId`. For
  non-owner: validate brand is in member's `member_brand_scope`, then same update. Return
  `{ slug }` so the SPA can navigate.

**Step 4 — Per-request read.** In `AuthGuard.canActivate`, after `this.auth.api.getSession()`,
cast the session to expose `activeBrandId`:

```typescript
const activeBrandId =
  (session as { session: { activeBrandId?: string | null } }).session
    .activeBrandId ?? null;
```

Pass `activeBrandId` into the guard chain via the request or ALS.

**Step 5 — Brand mismatch cross-check (D-10).** In `TenantContextMiddleware` or at the start of
`BrandScopeGuard`, after resolving the brand from `x-brand-slug`, compare it against the session's
`activeBrandId`. For a non-owner with a pinned brand: if `brandId !== activeBrandId`, throw a
404 (`NotFoundException` — existence-hiding per D-10). For an owner: skip the pin check but still
validate the brand belongs to the active tenant. Mirror the existing `auth.tenant_mismatch` pattern
in `auth.guard.ts:108-119`. [VERIFIED: auth.guard.ts]

**File and symbol citations:**

- Session table schema: `packages/db/src/schema/auth.ts` — add `activeBrandId text`
- BA config: `apps/api/src/contexts/identity/infrastructure/better-auth/auth.config.ts:269` —
  add to `session:` object
- Set-active hook: `auth.config.ts:276-309` — extend existing `databaseHooks.session.update`
- New endpoint: `apps/api/src/contexts/identity/interfaces/http/me.controller.ts` — add
  `POST /v1/identity/me/set-active-brand`
- Mismatch cross-check: `apps/api/src/contexts/identity/interfaces/http/guards/brand-scope.guard.ts`
  or `apps/api/src/shared/tenant-context.middleware.ts`

## Open Unknown 2: Brand-level Postgres RLS (D-14)

### Existing tenant RLS pattern (the template)

[VERIFIED: packages/db/migrations/0022_tenant_guc_lock.sql]

- GUC name: `app.current_tenant`
- Read function: `current_tenant_id() RETURNS uuid` — `nullif(current_setting('app.current_tenant', true), '')::uuid`
- Set via: `app_bind_tenant(p_tenant TEXT, p_is_system BOOLEAN)` — SECURITY DEFINER, raises on
  rebind to a different tenant
- Client call: `SELECT app_bind_tenant(${ctx.tenantId}, false)` at start of every
  `db.withTenant()` transaction (`packages/db/src/client.ts:232`)
- Policy expression: `is_system_session() OR tenant_id = current_tenant_id()`
- All tenant-scoped tables: `ENABLE ROW LEVEL SECURITY` + `FORCE ROW LEVEL SECURITY`

[VERIFIED: packages/db/src/context.ts] The `brandId` already lives in `TenantContext` as an
optional field and is accessible via `getBrandId()`. `withBrand(brandId, op)` layers a brand
context on top of the existing tenant context in ALS.

### Critical finding: payments/paymentRefunds have NO brand_id column

[VERIFIED: packages/db/src/schema/ordering.ts:126-202]

```
payments table columns: id, tenantId, orderId, status, amount, currency, provider,
providerPaymentId, paymentIntentId, latestChargeId, refundedAmount, stripeAccountId,
applicationFeeAmount, createdAt, updatedAt
```

No `brand_id`. Payment rows are linked to brands ONLY via `orders.brand_id` (the FK chain is
`payments → orders → brands`). Same for `paymentRefunds` (FK: `payment_refunds → payments →
orders → brands`).

**Consequence for D-14:** You cannot add `WHERE brand_id = current_brand_id()` to `payments`
or `paymentRefunds` RLS policies because the column does not exist.

**Two options:**

**Option A (preferred for this phase):** Add brand RLS only where a `brand_id` column already
exists. Those are: all `menu_*` tables, `orders`, `member_brand_scope`, `brand_domains`.
Document that `payments`/`paymentRefunds` are isolated only at the tenant level + app layer
(`BrandScopeGuard` on the payouts controller), and add `brand_id` to payments/paymentRefunds
as a follow-on migration if needed. The `orders` table has `brand_id NOT NULL` and composite FK
— it is the cleanest target for brand RLS.

**Option B (broader but adds scope):** Add `brand_id NOT NULL` to `payments` and `paymentRefunds`
via a migration, then add RLS. This requires a data migration (fill `brand_id` from the linked
`orders.brand_id`), schema changes to Drizzle, and verifying the `PaymentDrizzleRepository` passes
`brandId` correctly. This is out of phase scope per D-02 (no new schema bloat beyond what's needed).

**Recommendation: Option A.** Add brand-level RLS to `menu_*` tables and `orders` this phase.
For payments/payouts, the existing tenant RLS + `BrandScopeGuard` enforcement on the payouts
controller is the defense. Document this explicitly. CTO CRITICAL-2's "app-layer-only brand
isolation" gap is materially closed for the highest-value catalog+orders surface.

### Concrete brand RLS implementation

**New migration: `0058_brand_rls.sql`**

```sql
-- Function to read the current brand GUC
CREATE OR REPLACE FUNCTION current_brand_id() RETURNS uuid
  LANGUAGE sql STABLE PARALLEL SAFE
AS $$
  SELECT nullif(current_setting('app.current_brand', true), '')::uuid;
$$;

-- SECURITY DEFINER wrapper (mirrors app_bind_tenant)
CREATE OR REPLACE FUNCTION app_bind_brand(p_brand TEXT, p_is_system BOOLEAN)
RETURNS VOID
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = pg_catalog, public
AS $$
DECLARE
  v_current TEXT := current_setting('app.current_brand', true);
BEGIN
  IF v_current IS NOT NULL AND v_current <> '' AND v_current <> p_brand THEN
    RAISE EXCEPTION
      'app.current_brand already bound to % — refusing to rebind to %',
      v_current, p_brand
      USING ERRCODE = 'insufficient_privilege';
  END IF;
  PERFORM set_config('app.current_brand', p_brand, true);
END
$$;
REVOKE EXECUTE ON FUNCTION app_bind_brand(text, boolean) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION app_bind_brand(text, boolean) TO resto_app;

-- Apply brand-level RLS to menu tables and orders
-- Policy: pass when system session OR no brand bound (tenant-only request) OR brand matches
-- The 'no brand bound' pass is critical: many tenant-level ops don't supply a brand
-- (e.g., listing all brands for a tenant); they must still succeed.
ALTER TABLE menu_categories ADD POLICY menu_categories_brand_iso ON menu_categories
  USING (is_system_session() OR current_brand_id() IS NULL OR brand_id = current_brand_id());
-- ... repeat for menu_items, menu_variants/modifiers (now renamed), menu_stop_list,
--     menu_item_modifier_groups, catalog_menu_version, catalog_brand_stop_version, orders
```

**TenantAwareDb changes (`packages/db/src/client.ts`):**

Add a `withBrand()` method that calls `SELECT app_bind_brand(${brandId}, false)` inside
the existing `withTenant()` transaction. This is layered: tenant GUC is always bound first,
brand GUC is bound additionally when a brand context is available. The ALS `withBrand()` in
`context.ts` already stacks brand on top of tenant (`storage.run({ ...parent, brandId }, op)`).
The DB client must also call `app_bind_brand` when `ctx.brandId` is present.

**Modified `withTenant` flow:**

```typescript
async withTenant<T>(op: (tx: RestoTx, scoped: ScopedTx) => Promise<T>): Promise<T> {
  const ctx = requireTenantContext();
  return this.#db.transaction(async (tx) => {
    await tx.execute(sql`SELECT app_bind_tenant(${ctx.tenantId}, false)`);
    if (ctx.brandId) {
      await tx.execute(sql`SELECT app_bind_brand(${ctx.brandId}, false)`);
    }
    const result = await op(tx, new ScopedTx(tx, ctx.tenantId));
    await this.#assertGucUnchanged(tx, ctx.tenantId, 'withTenant');
    return result;
  });
}
```

**File and symbol citations:**

- New migration: `packages/db/migrations/0058_brand_rls.sql`
- GUC bind: `packages/db/src/client.ts` — `TenantAwareDb.withTenant` (add `app_bind_brand` call)
- New function: `current_brand_id()` alongside `current_tenant_id()` in migration
- Tables to add brand policy: `menu_categories`, `menu_items`, `menu_item_sizes`,
  `menu_modifier_groups`, `menu_modifier_options`, `menu_item_modifier_groups`,
  `menu_stop_list`, `catalog_menu_version`, `catalog_brand_stop_version`, `orders`
- Tables that CANNOT get brand RLS without a migration: `payments`, `payment_refunds`

## Secondary Research: Default-Allow → Default-Deny Flip (D-08)

### Exact code locations

[VERIFIED: source code]

**`brand-scope.guard.ts:77`** — the default-allow line:

```typescript
if (scope === null) return true; // LINE 77 — THIS IS DEFAULT-ALLOW
```

`scope === null` means `findBrandScopeForMember` returned null, which per the port docs
(`member-brand-scope-reader.port.ts:6-11`) means "member has no scope rows."

**`member-brand-scope-drizzle.reader.ts:27`** — returns null when zero rows:

```typescript
if (rows.length === 0) return null; // null = "no scope rows"
```

**`list-my-brands.service.ts:35`** — owner bypass:

```typescript
const canViewAllBrands = scopeRows === null; // null scope = owner unrestricted
```

**The minimal default-deny change (D-08):**

The `owner` bypass is at `brand-scope.guard.ts:70` (checked BEFORE the scope lookup). The
default-deny flip only affects non-owner paths. Change line 77:

```typescript
// BEFORE (default-allow):
if (scope === null) return true;

// AFTER (default-deny):
if (scope === null) {
  throw new ForbiddenException({
    code: 'brand.access_denied',
    message: 'Operator is not scoped to any brand.',
  });
}
```

**The `canViewAllBrands` semantic in `list-my-brands.service.ts` needs updating:**
The owner path calls `canViewAllBrands = scopeRows === null`. This is correct for owners
(owner never has scope rows, always gets all brands). The danger is if a non-owner also has
no scope rows — after the flip, the guard blocks them from accessing any brand, but
`list-my-brands.service.ts` still returns their brands list as "all brands" (confusing). The
service should be aware of role:

```typescript
// After: only owners get canViewAllBrands = true when scope is null
// The service needs baseRole passed in, or a separate is-owner check
```

**Recommended:** The service should receive `isOwner: boolean` from the controller, and
`canViewAllBrands = isOwner && scopeRows === null`.

**Regression test that MUST pass after the flip:**

- Owner with zero scope rows: passes guard → all brands
- Non-owner with zero scope rows: fails guard with `brand.access_denied`
- Non-owner with scope rows matching the brand: passes guard
- Non-owner with scope rows NOT matching: fails guard with `brand.access_denied`

[VERIFIED: apps/api/test/unit/identity/brand-scope-guard.spec.ts:91-94] — existing test
"passes for non-owner when scope is empty (default-allow)" MUST be inverted.

## Secondary Research: BrandScopeGuard Default-On (D-11)

### Current opt-in mechanism

[VERIFIED: brand-scope.guard.ts:40-44]

```typescript
const required = this.reflector.getAllAndOverride<boolean | undefined>(
  REQUIRE_BRAND_KEY,
  [ctx.getHandler(), ctx.getClass()],
);
if (!required) return true; // passes without annotation
```

`@RequireBrand` is the opt-in decorator. Routes without it skip the guard entirely.

### Making it default-on

**Approach:** Invert the logic so the guard passes by default ONLY for routes explicitly marked
as brand-neutral (`@BrandNeutral`). Mirror how `AuthGuard` uses `@Public` (`IS_PUBLIC_KEY`).

New decorator: `@BrandNeutral()` sets a key `BRAND_NEUTRAL_KEY` via `SetMetadata`.

## Common Pitfalls

### Pitfall 1: `authClient.organization.setActive` accepts a brand ID — it does not

**What goes wrong:** `brand-switcher.tsx:34` currently calls `setActive({ organizationId: brand.id })`.
`brand.id` is a BRAND UUID, not a tenant UUID. BA will try to look up this ID as an organization
and may return null or set wrong state.
**Why it happens:** Brand and org (tenant) were conflated in early code — org plugin is used for
tenant switching only.
**How to avoid:** Remove the `setActive` call from `brand-switcher.tsx`. Use the new
`POST /v1/identity/me/set-active-brand` endpoint instead.

### Pitfall 2: `withTenant` transaction binds tenant GUC before brand GUC — order matters

**What goes wrong:** `app_bind_tenant` raises if already bound. If `app_bind_brand` is called
before `app_bind_tenant`, subsequent calls to `app_bind_tenant` would fail.
**Why it happens:** Both are `SET LOCAL` in the same transaction; call order is strict.
**How to avoid:** Always call `app_bind_tenant` first, then `app_bind_brand`. In `withTenant`,
add the brand bind AFTER the tenant bind.

### Pitfall 3: Brand RLS policy `current_brand_id() IS NULL` pass-through is required

**What goes wrong:** Many API operations (list brands for tenant, get tenant settings, create
brand) do not supply a `x-brand-slug` header. Without the IS NULL pass-through, every
tenant-level query against a brand-RLS-enabled table would return zero rows.
**Why it happens:** `app.current_brand` GUC is unset for tenant-level requests.
**How to avoid:** Policy must be: `is_system_session() OR current_brand_id() IS NULL OR brand_id = current_brand_id()`. The IS NULL condition ensures tenant-level queries still work.

### Pitfall 4: The Stripe return URL is the single highest-regression-risk line

**What goes wrong:** `start-brand-onboarding.service.ts:207` has `/dashboard/${slug}/payouts`
hardcoded. If this line is not updated in PR-A, Stripe Connect Standard OAuth return will
redirect to a 404 after the route rename.
**Why it happens:** The URL is constructed server-side from `ADMIN_WEB_URL + path`.
**Warning signs:** Stripe onboarding redirect lands on 404 page. Test by checking that
`STRIPE_CONNECT_RETURN_URL` env var and the OAuth redirect URL both end with `/${slug}/payouts`.

### Pitfall 5: Default-deny flip breaks freshly-provisioned owner with no scope rows

**What goes wrong:** A new owner has no rows in `member_brand_scope` (they are unrestricted by
role, not by scope rows). If the default-deny flip is applied without the owner bypass check,
new owners get 403 immediately after signup.
**Why it happens:** `scope === null` is the overlap between "owner, no scope rows" and "non-owner,
no scope rows."
**How to avoid:** The owner bypass at `brand-scope.guard.ts:70` runs BEFORE the scope lookup —
this is correct. The owner never reaches the `if (scope === null)` check. Verify this is still
true after the guard refactor for default-on.

### Pitfall 6: TanStack Router navigation to `/` loops if active brand is unknown

**What goes wrong:** `routes/index.tsx` redirects to `/dashboard` today. After rename it must
redirect to `/${activeBrandSlug}`. If the SPA doesn't know the active brand (first load, no
cookie), it may loop or redirect to `/undefined`.
**How to avoid:** Have the index route load the brand list first (suspense query), then redirect.
Or store a plain non-security `active-brand-hint` cookie in the `set-active-brand` endpoint
response that the SPA can read for the initial redirect.
