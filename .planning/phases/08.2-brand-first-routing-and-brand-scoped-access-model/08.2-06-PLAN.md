policy (Plan 02's BLOCKING apply must have run). This is the SC-4 named isolation test: forge a

and `/update-session` cannot move the active-brand pin (input:false). And — newly — a POSITIVE

customer routes.

the code typechecks — AND that it did not regress the customer order/menu path. It is the final
gate; it depends on the default-deny flip + D-10 reconciliation + the @BrandNeutral opt-out on the
customer controllers (Plan 05), the session pin (Plan 03), the flattened Stripe return URL (Plan 04),
and the applied brand RLS migration (Plan 02).

PRECONDITION (BLOCKING, from Plan 02 Task 3): migration 0058 is applied to the live test DB and
the boot preflight `assertBrandRlsInstalled` passes. If the policy is not live, this e2e would
false-positive. The e2e harness MUST run against the migrated DB.

Output: the brand-isolation e2e matrix (incl. the public-traffic survival case), an extension to
the cross-tenant isolation spec covering the new brand-owned tables, and the Stripe-URL unit
regression test.

Scope guard (D-01/D-02): tests cover brand-level isolation only. No location-level fixtures, no
dynamic-AC. Payments brand isolation is NOT asserted at the RLS layer (accepted debt, Plan 02);
the payouts controller's app-layer BrandScopeGuard is the boundary tested instead.
