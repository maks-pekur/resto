<objective>
Give the "active brand" a tamper-resistant server-side home (D-09): add
`session.activeBrandId` as a better-auth `additionalField` with `input:false` (client cannot
forge it via `/update-session`, identical to the existing `requiresPasswordChange` field).
Add the server-side write paths: re-pin on `organization/set-active` (login/org-switch) and a
new `POST /v1/identity/me/set-active-brand` endpoint that owners use to free-switch (D-12) and
non-owners use to silently re-pin within their scope (D-13). The server-side write goes through a
dedicated injectable adapter (`SessionActiveBrandWriter`) wrapping `internalAdapter.updateSession`
— application code never reaches into the better-auth config closure. Surface `activeBrandId`
onto the request in `AuthGuard` so Plan 05's reconciliation cross-check can read it.

Purpose: the founder explicitly rejected the forgeable-cookie approach; this is the server pin
the whole anti-tamper model (D-10) hangs off. Plan 05 (reconciliation) and Plan 04 (the
brand-switcher API wire) both depend on this endpoint + the request-surfaced field. The pin MUST
be set DETERMINISTICALLY at login/org-switch for non-owners (including non-owners with multiple
allowed brands) so a non-owner brand-scoped request is never null-pinned — Plan 05's
reconciliation treats a null pin on a non-owner brand-scoped route as existence-hiding 404, so the
login path must guarantee the pin is populated.

Output: schema column + migration 0059, BA config field + hook (deterministic initial pin),
the SessionActiveBrandWriter port + adapter, set-active-brand service+controller, AuthGuard
surfacing, and an integration spec proving `input:false` tamper-resistance + owner/non-owner
re-pin semantics + the deterministic-initial-pin-for-multi-brand-non-owner case.

Scope guard (D-01/D-02): brand-level only. No BA teams plugin (RESEARCH: 2 new tables, wrong
tool). No `dynamicAccessControl`. `member_brand_scope.role` left untouched (skeptic LOW).
</objective>
