<domain>
## Phase Boundary

A guest signs in with Google from the QR menu or the storefront **without leaving the page**, and
gets two things: their name and phone already filled in at checkout, and a list of their own orders
for the restaurant whose site they are on. "Continue without an account" stays available on every
screen that offers sign-in.

The phase also carries the trust-boundary fix that signing in exposes: on a restaurant's own site,
**an operator is someone who holds a membership there** — not merely someone without a phone number.

**Not in this phase:** marketing consent, offers, loyalty, a `customers` table or any other Phase 12
CRM surface beyond one column on `orders`; phone/OTP login; providers other than Google; claiming
orders placed before signing in; cross-restaurant order history; anything in `apps/admin`.

</domain>

<decisions>
## Implementation Decisions

### How the guest signs in

- **D-01: Google One Tap, not the redirect flow.** Load the `one-tap` plugin (present in
  better-auth 1.6.30, not currently registered). The guest app obtains a Google ID token in the
  browser and `POST`s it to `/api/auth/one-tap/callback`; the response body carries the session
  token. **The redirect flow cannot work here:** it ends in a 302 the browser follows as a top-level
  navigation, and JavaScript on the destination page cannot read the headers of a redirect it did
  not fetch — so `set-auth-token` would be emitted and unreachable.
- **D-02: No new Google credential and no new redirect URI.** One-tap reuses
  `socialProviders.google.clientId`, already configured (`auth.config.ts:204`). Nothing is
  registered in Google Cloud Console for this phase.
- **D-03: The ID token is verified server-side.** One-tap calls `verifyGoogleIdToken` against our
  own client id as the audience and rejects a mismatched `hd`. The client supplies an ID token, not
  a session. Do not add a code path that trusts a client-supplied session token.

### How the session travels

> **Corrected 2026-09-06 after reading `infra/docker/Caddyfile`.** An earlier draft of this section
> called for a bearer token in `localStorage` because it assumed a tenant host cannot reach the API.
> It can. The correction removes work and removes risk; the superseded reasoning is not preserved
> because following it would be strictly worse.

- **D-04: The guest's session is an ordinary host-only cookie, set on the restaurant's own host.**
  `infra/docker/Caddyfile` serves `{$WEBSITE_HOST}, *.{$WEBSITE_HOST}` from one block, and inside it
  `handle /v1/*` and `handle /api/*` both proxy to the api — its own comment says 07.4 made "guest
  checkout and operator auth same-origin on these two paths". So `pizza.<apex>/api/auth/...` is
  **same-origin for the guest**, and the `Set-Cookie` it returns carries no `Domain`, binding it to
  `pizza.<apex>` and nothing else.
- **D-05: No bearer token, no token in JavaScript, no `localStorage`.** The session cookie is
  `httpOnly`, so an XSS on a tenant storefront cannot read it. This is a smaller attack surface than
  the alternative, not merely a simpler one.
- **D-06: `AUTH_COOKIE_DOMAIN` stays unset — and that is now load-bearing, not merely preserved.**
  Host-only cookies are what keep a guest's session on `pizza.<apex>` from reaching `burger.<apex>`,
  and the operator's session on `<apex>` from reaching either. Setting it would merge all three into
  one session scope. 07.4-06's narrowing is the mechanism this phase runs on.
- **D-07: Better Auth's `trustedOrigins` gains `https://*.<apex>`.** A same-origin POST from a tenant
  host still sends an `Origin` header, and Better Auth rejects a mutating request whose origin is not
  trusted. Wildcards are supported — `trusted-origins.mjs:18-22` routes any pattern containing `*`
  through `wildcardMatch`. `trustedOrigins` is assembled in `identity-core.module.ts:232`.
- **D-08: `CORS_ALLOWED_ORIGINS` does not need to change for sign-in.** The auth calls are
  same-origin. Touch it only if a plan finds a genuinely cross-origin call, and say which.
- **D-09: The dev environment is where the gap is.** Production has the Caddy route; dev does not.
  `apps/website/next.config.mjs` rewrites `/v1/:path*` only, and it is `NODE_ENV !== 'production'`
  gated; `apps/qr-menu/vite.config.ts` proxies `/v1`, `/internal` and `/media` — neither covers
  `/api/*`. Both need it, or one-tap 404s locally while working in production. That asymmetry is
  exactly the kind this project has been bitten by; close it in the same plan that adds the plugin.

### Who the request is from

- **D-10: On a guest host, an operator is someone who holds a membership in that tenant. Off a
  guest host, signed in still means operator.** The plain version of this rule — "operator = holds a
  membership" — **breaks registration**: `me-tenants.controller.ts`'s `/me/tenants`,
  `/me/tenants/slug-availability` and `/me/tenants/onboarding` sit behind `@CurrentOperator`, and a
  freshly-registered person holds no membership anywhere until they have created their first
  restaurant through exactly those routes. `alsTenantId` is set only when the tenant middleware
  resolved a tenant from the host, which is a guest surface; the admin lives at `<apex>/admin` where
  the apex resolves none. Keying off that keeps onboarding working and still makes a Google guest a
  customer. See `10.7-01-PLAN.md` for the full decision table.

  *What is wrong today:* `auth.guard.ts:238` decides by `if (session.user.phoneNumber)` → customer,
  else → **operator**. A Google account carries an email and no phone, so a signed-in guest is
  classified as an operator with no tenant. RBAC refuses them, so it is not an open door — but the
  classification is wrong, and safety then rests on RBAC catching it rather than on the identity
  being right. The guard already queries `member` in `lookupMembership` (line 177); the query moves
  earlier and runs once.
- **D-11: Keep the phone branch.** It stays correct and the deferred OTP login needs it. Off a
  guest host it still yields `anonymous`, exactly as today.
- **D-12: This is its own plan with its own review.** Phase 7.4 was made a separate phase for this
  one file. It does not get folded into a UI plan.

### The order ↔ guest link

- **D-13: One nullable column on `orders`, not a `customers` table.** `orders.customer_user_id`
  referencing the Better Auth user id. A `customers` table is Phase 12's job and is not needed to
  answer "show me my orders".
- **D-14: The link is written at placement only.** An order placed while signed in carries the id;
  an order placed anonymously never gains one. **Claiming past orders by matching email or phone is
  out of scope** — it is an identity-matching problem with real abuse potential (anyone who knows a
  phone number would inherit someone's history) and it deserves its own decision.
- **D-15: History is scoped to the tenant whose site the guest is on.** `WHERE tenant_id = ? AND
  customer_user_id = ?` — RLS already constrains the first half. A guest on `pizza.<apex>` must not
  see their `burger.<apex>` orders; the storefront belongs to the restaurant, not to RestOS.
- **D-16: The existing loose columns stay.** `customer_name` / `customer_phone` / `customer_email`
  on `orders` are the snapshot the kitchen reads; they are not replaced by the link. A signed-in
  guest's checkout **prefills** them and may edit them, and what they submit is what is stored.

### What the guest sees

- **D-17: Two entry points, both dismissible.** The account drawer (`AccountSheet.tsx`, today a
  stub) and an unobtrusive offer at checkout. "Continue without an account" is present on both and
  is never a second-class path.
- **D-18: The benefits copy names exactly what D-13..D-16 deliver** — find your orders, and your
  details filled in next time. Not offers, not loyalty, not "faster" in the abstract. Copy that
  promises what the phase does not build is the defect this project keeps meeting.
- **D-19: `AccountSheet`'s current copy is wrong after this phase** and must be rewritten. It
  promises the order is found "by the number you give at checkout"; after this phase the *account*
  finds the order, and QR checkout still asks only for an optional name.

### Migration and data

- **D-20: One migration, additive.** A nullable `customer_user_id` on `orders` plus its index. No
  backfill — D-14 means historical orders have no owner, and inventing one is exactly what D-14 forbids.
- **D-21: Composite-FK rules do not apply.** `customer_user_id` points at a Better Auth user, which
  is not tenant-scoped. It is a plain nullable column with no FK to a tenant-scoped parent, so
  ADR-0020 I-2 has nothing to say about it. State this in the migration so a later reader does not
  "fix" it.

### Claude's Discretion

- **D-22 — what the same-origin cookie does and does not buy.** It is `httpOnly`, so an XSS on a
  tenant storefront cannot read it; and it is host-only, so a guest session on `pizza.<apex>` never
  reaches `burger.<apex>` or the operator's `<apex>`. What it does **not** stop is an XSS making
  requests *as* that guest on the page it already runs on — the ordinary limit of cookie auth, and
  the reason `trustedOrigins` and Better Auth's CSRF handling still matter. Do not add a
  JavaScript-readable copy of the session "for convenience"; that would give back exactly the
  property this choice buys.
- Session lifetime is Better Auth's default unless the planner finds a reason to shorten it; a guest
  session is not an operator session and does not need the same discipline.
- Where the order-history list lives in the guest UI (its own screen vs a section of the account
  drawer) is a layout decision for the plan; both entry points already exist.
- Whether the storefront (`apps/website`) gets sign-in in this phase or only the QR menu
  (`apps/qr-menu`) — the planner should size this. Both are named in the phase boundary, but the QR
  menu is where the founder's original ask started and it has the account drawer already.

</decisions>

### A trap this phase will meet

`OrderDrizzleRepository`'s UPDATE set-clause silently omitted `payment_status`/`paid_at` until
`0d97ed5b` — the insert wrote them and the update did not, so every payment transition was lost.
Any new column on `orders` must be added to **both** write paths, and the plan's verification must
read the column back after an update, not only after an insert.
