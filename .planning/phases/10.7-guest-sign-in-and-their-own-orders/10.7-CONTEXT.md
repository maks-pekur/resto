<domain>
## Phase Boundary

A guest signs in with Google from the QR menu or the storefront **without leaving the page**, and
gets two things: their name and phone already filled in at checkout, and a list of their own orders
for the restaurant whose site they are on. "Continue without an account" stays available on every
screen that offers sign-in.

The phase also carries the trust-boundary fix that signing in exposes: **an operator is someone who
holds a membership**, not someone without a phone number.

**Not in this phase:** marketing consent, offers, loyalty, a `customers` table or any other Phase 12
CRM surface beyond one column on `orders`; phone/OTP login; providers other than Google; claiming
orders placed before signing in; cross-restaurant order history; anything in `apps/admin`.

</domain>

<decisions>
## Implementation Decisions

### How the guest signs in

- **D-01: Google One Tap, not the redirect flow.** Load the `one-tap` plugin (present in
  better-auth 1.6.30, not currently registered). The guest app obtains a Google ID token in the
  browser and `POST`s it to `/api/auth/one-tap/callback`; the response body carries the session
  token. **The redirect flow cannot work here:** it ends in a 302 the browser follows as a top-level
  navigation, and JavaScript on the destination page cannot read the headers of a redirect it did
  not fetch — so `set-auth-token` would be emitted and unreachable.
- **D-02: No new Google credential and no new redirect URI.** One-tap reuses
  `socialProviders.google.clientId`, already configured (`auth.config.ts:204`). Nothing is
  registered in Google Cloud Console for this phase.
- **D-03: The ID token is verified server-side.** One-tap calls `verifyGoogleIdToken` against our
  own client id as the audience and rejects a mismatched `hd`. The client supplies an ID token, not
  a session. Do not add a code path that trusts a client-supplied session token.

### How the session travels

- **D-04: Bearer token for the guest apps. `AUTH_COOKIE_DOMAIN` stays unset.** The guest is on
  `<slug>.<apex>`, the API on the bare `<apex>` — two origins. Phase 07.4-06 made the operator's
  session cookie host-only **on purpose** so it never reaches a tenant storefront; widening it to
  `.<apex>` would undo a narrowing made on a trust boundary and put the operator session on every
  restaurant's page. The `bearer` plugin is already loaded (`auth.config.ts:312`) and converts
  `Authorization: Bearer <token>` into a session server-side.
- **D-05: No same-origin proxy, no tunnel or Caddy route for `/api/auth/*` on tenant hosts.** Bearer
  transport is cross-origin by design; CORS is the mechanism. Adding a proxy would be work that buys
  nothing.
- **D-06: Tenant origins enter both allowlists in the `https://*.<apex>` shape** —
  `CORS_ALLOWED_ORIGINS` (`env.schema.ts:188`) and Better Auth's `trustedOrigins`
  (`identity-core.module.ts`). The CORS wildcard matches exactly one label and never spans dots
  (`security.ts:17-18`), which is the shape needed; it will not match `a.b.<apex>`.
- **D-07: The token lives in `localStorage`, not memory.** A guest who closes the tab and comes back
  to check their order is the case this phase exists for; a memory-only token loses the session on
  every reload and makes the feature useless. The cost is stated in D-20.

### Who the request is from

- **D-08: On a guest host, an operator is someone who holds a membership in that tenant. Off a
  guest host, signed in still means operator.** The plain version of this rule — "operator = holds a
  membership" — **breaks registration**: `me-tenants.controller.ts`'s `/me/tenants`,
  `/me/tenants/slug-availability` and `/me/tenants/onboarding` sit behind `@CurrentOperator`, and a
  freshly-registered person holds no membership anywhere until they have created their first
  restaurant through exactly those routes. `alsTenantId` is set only when the tenant middleware
  resolved a tenant from the host, which is a guest surface; the admin lives at `<apex>/admin` where
  the apex resolves none. Keying off that keeps onboarding working and still makes a Google guest a
  customer. See `10.7-01-PLAN.md` for the full decision table. The original wording follows: `auth.guard.ts:238` currently decides by
  `if (session.user.phoneNumber)` → customer, else → **operator**. A Google account carries an email
  and no phone, so a signed-in guest would be classified as an operator with no tenant. RBAC refuses
  them, so it is not an open door — but the classification is wrong, and safety then rests on RBAC
  catching it rather than on the identity being right. The guard already queries `member` in
  `lookupMembership` (line 177); the query moves earlier and runs once.
- **D-09: Keep the phone branch.** It stays correct and the deferred OTP login needs it. The new
  rule is *membership first*, phone second, anonymous last.
- **D-10: This is its own plan with its own review.** Phase 7.4 was made a separate phase for this
  one file. It does not get folded into a UI plan.

### The order ↔ guest link

- **D-11: One nullable column on `orders`, not a `customers` table.** `orders.customer_user_id`
  referencing the Better Auth user id. A `customers` table is Phase 12's job and is not needed to
  answer "show me my orders".
- **D-12: The link is written at placement only.** An order placed while signed in carries the id;
  an order placed anonymously never gains one. **Claiming past orders by matching email or phone is
  out of scope** — it is an identity-matching problem with real abuse potential (anyone who knows a
  phone number would inherit someone's history) and it deserves its own decision.
- **D-13: History is scoped to the tenant whose site the guest is on.** `WHERE tenant_id = ? AND
  customer_user_id = ?` — RLS already constrains the first half. A guest on `pizza.<apex>` must not
  see their `burger.<apex>` orders; the storefront belongs to the restaurant, not to RestOS.
- **D-14: The existing loose columns stay.** `customer_name` / `customer_phone` / `customer_email`
  on `orders` are the snapshot the kitchen reads; they are not replaced by the link. A signed-in
  guest's checkout **prefills** them and may edit them, and what they submit is what is stored.

### What the guest sees

- **D-15: Two entry points, both dismissible.** The account drawer (`AccountSheet.tsx`, today a
  stub) and an unobtrusive offer at checkout. "Continue without an account" is present on both and
  is never a second-class path.
- **D-16: The benefits copy names exactly what D-11..D-14 deliver** — find your orders, and your
  details filled in next time. Not offers, not loyalty, not "faster" in the abstract. Copy that
  promises what the phase does not build is the defect this project keeps meeting.
- **D-17: `AccountSheet`'s current copy is wrong after this phase** and must be rewritten. It
  promises the order is found "by the number you give at checkout"; after this phase the *account*
  finds the order, and QR checkout still asks only for an optional name.

### Migration and data

- **D-18: One migration, additive.** A nullable `customer_user_id` on `orders` plus its index. No
  backfill — D-12 means historical orders have no owner, and inventing one is exactly what D-12
  forbids.
- **D-19: Composite-FK rules do not apply.** `customer_user_id` points at a Better Auth user, which
  is not tenant-scoped. It is a plain nullable column with no FK to a tenant-scoped parent, so
  ADR-0020 I-2 has nothing to say about it. State this in the migration so a later reader does not
  "fix" it.

### Claude's Discretion

- **D-20 — the cost, stated once so the plan does not have to re-argue it:** a bearer token in
  `localStorage` can be stolen by an XSS on a tenant storefront. The blast radius is **one guest's
  own account** — their order history and their name on a checkout form. The alternative, widening
  the cookie, would put the *operator's* cross-tenant session on the same page. The bearer choice is
  the smaller loss, not a free one.
- Session lifetime is Better Auth's default unless the planner finds a reason to shorten it; a guest
  session is not an operator session and does not need the same discipline.
- Where the order-history list lives in the guest UI (its own screen vs a section of the account
  drawer) is a layout decision for the plan; both entry points already exist.
- Whether the storefront (`apps/website`) gets sign-in in this phase or only the QR menu
  (`apps/qr-menu`) — the planner should size this. Both are named in the phase boundary, but the QR
  menu is where the founder's original ask started and it has the account drawer already.

</decisions>

## Existing Code Insights

### Reusable assets

- `bearer()` is already registered (`auth.config.ts:312`); nothing to add for transport.
- `socialProviders.google` is already registered and env-gated (`auth.config.ts:204`,
  `identity-core.module.ts:265`).
- Wildcard CORS matching already exists and is already tested (`security.e2e.spec.ts`).
- `AccountSheet.tsx` and the guest drawer already exist as the entry point — this phase fills a
  stub rather than inventing a surface.

### Integration points

- `apps/api/src/contexts/identity/interfaces/http/guards/auth.guard.ts` — D-08/D-09, the trust
  boundary.
- `apps/api/src/contexts/identity/infrastructure/better-auth/auth.config.ts` — the one-tap plugin.
- `apps/api/src/contexts/ordering/` — the order↔guest link on the write path, and a read for
  history.
- `apps/qr-menu/src/components/AccountSheet.tsx` and `CheckoutSheet.tsx` — the guest surfaces.
- `apps/qr-menu` has **no** Better Auth client today (`grep -rn better-auth apps/qr-menu` is empty);
  one is added here.

### A trap this phase will meet

`OrderDrizzleRepository`'s UPDATE set-clause silently omitted `payment_status`/`paid_at` until
`0d97ed5b` — the insert wrote them and the update did not, so every payment transition was lost.
Any new column on `orders` must be added to **both** write paths, and the plan's verification must
read the column back after an update, not only after an insert.

## Deferred Ideas

- **Claiming orders placed before sign-in** (D-12). Needs its own decision about identity matching
  and abuse.
- **Cross-restaurant history** ("everywhere I have ordered"). Contradicts D-13's tenancy stance;
  belongs to a RestOS-level account surface that does not exist.
- **Phone/OTP login.** Dropped 2026-09-04 on cost; the phone branch in the guard is kept for it.
- **Providers beyond Google.** `oauth-popup` is the plugin to look at when a redirect-flow provider
  is needed.
- **Marketing consent, offers, loyalty.** Phases 11 and 12. The founder explicitly did not choose
  them when asked on 2026-09-06.
- **A `customers` table.** Phase 12.
