<context>
`orders` carries `customer_name`, `customer_phone`, `customer_email` as loose snapshot columns for
the kitchen. They stay (D-16). What is missing is a link to an identity.

`CreateOrderService` builds the order from `CreateOrderInput`. The guest order route
(`orders.controller.ts:67`) is `@Public()`, so today it has no principal at all — **plan 01 adds
`@OptionalAuth()` for exactly this**, and this plan is the first user of it.

**The trap, stated because this repository has already been bitten by it.**
`OrderDrizzleRepository` has two write paths: `save` (INSERT, line ~55) and `#runUpdate` (UPDATE,
line ~145). Until `0d97ed5b`, `payment_status` and `paid_at` were written by the first and silently
omitted by the second, so every payment transition was lost and revenue read zero. A new column
that only lands in the INSERT repeats that defect exactly.
</context>

<tasks>

### Task 1 — the column

**Action.** Add `customer_user_id` to `orders`: nullable `text`, no default. Write migration
`0021_order_customer_user.sql` adding the column and an index on `(tenant_id, customer_user_id)` —
that pair is the only way it is ever queried (D-15). No backfill (D-20).

State in the migration comment **why there is no composite FK**: the column points at a Better Auth
user, which is not tenant-scoped, so ADR-0020 I-2 does not apply. Without that note a later reader
will "fix" it.

**Verification.**
- `pnpm -C packages/db exec pnpm db:migrate` applies cleanly and is a no-op on a second run.
- `psql -c "\d orders"` shows the column nullable and the index present — output pasted into the
  SUMMARY.
- `grep -c "compositeTenantFk" packages/db/src/schema/ordering.ts` is unchanged from before this task.

### Task 2 — both write paths, and a test that would have caught the old defect

**Action.** Thread `customerUserId` through the order snapshot and **both** repository paths:
`save`'s INSERT and `#runUpdate`'s `.set({...})`.

Write `apps/api/test/integration/order-customer-link.spec.ts` that inserts an order with a user id,
**updates it through the repository**, reads the row back, and asserts the id survived. Then flip
the assertion's expectation and confirm the test fails — a test that has never been seen red proves
nothing.

**Verification.**
- The integration spec passes.
- Deliberately remove `customerUserId` from `#runUpdate`'s set-clause and confirm the spec fails.
  Record the failure text in the SUMMARY, then restore.

### Task 3 — the id comes from the session, never from the body

**Action.** `CreateOrderService` takes the user id from the resolved principal, not from
`CreateOrderInput`. Put `@OptionalAuth()` on the guest order route and read
`principal.kind === 'customer' ? principal.userId : null`.

**Do not add `customerUserId` to `CreateOrderInputSchema`.** A client-supplied owner id would let
anyone attach their order to someone else's history — or read a stranger's orders by claiming their
id. If a reviewer suggests it "for the operator case", the answer is no: an operator creating an
order on a guest's behalf is not that guest.

**Verification.**
- `grep -n "customerUserId" apps/api/src/contexts/ordering/application/dto.ts` returns nothing.
- An e2e test: a signed-in guest places an order and the row carries their id; an anonymous guest
  places one and the row carries null; a request that *puts* `customerUserId` in its body is
  ignored, not honoured.

### Task 4 — reading them back, scoped

**Action.** Add a read that answers "my orders here": filtered by the resolved user id, inside the
tenant the request resolved. Go through `ScopedTx` — the tenant half is RLS's job and the user half
is the query's, and neither substitutes for the other.

Return only what a guest needs to recognise their order: number, when, status, payment status,
total, currency. **Not** the modifier detail, not the customer snapshot columns, not internal ids.

**Verification.**
- An e2e test seeding two tenants and two guests: each guest sees exactly their own orders for the
  tenant they are on, and nothing from the other tenant even when the same user placed orders there.
- The response shape is asserted field-by-field, so a later widening is a test failure rather than a
  silent leak.

</tasks>

<threat_model>
## Trust Boundaries

The order-creation route accepts a body from an untrusted browser and now also attributes ownership.
The history route returns one person's data.

## STRIDE Threat Register

- **T-01 (Spoofing) — a client claiming another guest's id.** Prevented by Task 3: the id is never
  read from the body. The `grep` in that task's verification is the regression guard.
- **T-02 (Information disclosure) — reading a stranger's orders.** The history query filters on the
  session's own user id inside a tenant-scoped transaction. Task 4's two-tenant, two-guest test is
  the proof.
- **T-03 (Information disclosure) — cross-tenant leakage.** A guest signed in on `pizza.<apex>` must
  not see `burger.<apex>` orders even though it is one Better Auth user. RLS plus the explicit
  `tenant_id` filter; tested.
- **T-04 (Tampering) — an operator reassigning an order's owner.** No route writes the column after
  creation. If a later phase adds one, it is a separate decision, not an implementation detail.
- **T-05 (Information disclosure) — an over-wide response.** Task 4 pins the field list. A guest's
  order status is not an excuse to return the whole aggregate.
</threat_model>
