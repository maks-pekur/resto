<objective>
Make the guard decide **who someone is** from whether they hold a membership in the tenant the
request is about, instead of from the absence of a phone number. This is the file phase 7.4 was
made its own phase for; it changes the code that decides who may do what, and it ships alone.
</objective>

<context>
`toPrincipal` (`auth.guard.ts:~236`) is a pure function over the session. Today:

```ts
if (session.user.phoneNumber) { ...customer... }
const operator: OperatorPrincipal = { kind: 'operator', ... };
```

A Google account has an email and no phone, so a signed-in guest becomes an **operator with no
tenant**. RBAC refuses them, so this is not an open door — but the identity is wrong and safety
rests on a later check rather than on the classification.

**The tenant a request is about** is `alsTenantId` when the host resolved one (guest surfaces), and
`session.activeOrganizationId` otherwise (the admin, since 07.4 moved the tenant into the session).

**Two edge cases decide the rule, and both kill the obvious version.**

*The lunch case.* "Operator = holds *any* membership" makes a restaurant owner ordering lunch on
another restaurant's storefront an operator with no membership there, and `canActivate`'s existing
check refuses them with `auth.tenant_membership_missing` — a real person walled off a public page.

*The onboarding case, which is worse.* "Operator = holds a membership **in this request's tenant**"
breaks registration outright. `me-tenants.controller.ts` exposes `GET /me/tenants`,
`GET /me/tenants/slug-availability` and `POST /me/tenants/onboarding`, all behind `@CurrentOperator`
— and they are exactly the routes a freshly-registered person with **no membership anywhere** must
call to create their first restaurant. Under a membership-only rule they classify as a customer and
are refused. Nobody could sign up.

**The rule that survives both** keys off whether the request arrived on a tenant host at all.
`alsTenantId` is set precisely when the tenant middleware resolved a tenant from the host — that is
a guest surface. The admin lives at `<apex>/admin`, the apex resolves no tenant, and 07.4 moved the
operator's tenant into the session for exactly that reason. So:

- **On a guest host** (`alsTenantId` set): a membership in *that* tenant makes an operator;
  otherwise a customer. The lunch case lands correctly.
- **Off a guest host** (admin, apex): signed in makes an operator, exactly as today. Authority is
  still gated by the membership checks already in `canActivate`. Onboarding is untouched.

`lookupMembership` already exists (line ~177) and already distinguishes **no row** (`null`) from **a
row with no system role** (`{ role: undefined }`). Do not collapse that distinction — it is what
keeps a custom-role-only operator from being locked out.
</context>

<tasks>

### Task 1 — the membership lookup moves ahead of the classification

**Action.** In `canActivate`, resolve the request's tenant once:

```ts
const requestTenantId = alsTenantId ?? sessionData.session.activeOrganizationId ?? undefined;
```

When there is a signed-in session **and** a `requestTenantId`, call `lookupMembership` once, before
`toPrincipal`, and pass the result in. When there is no `requestTenantId`, there is no tenant to
hold a membership in — pass `null`.

Change `toPrincipal`'s signature to take that membership as its third argument. Keep it pure and
synchronous; it must stay unit-testable without a database.

**Do not** add a second query. The existing per-tenant lookups further down `canActivate` must be
replaced by this one result, not run again — today the operator branch queries the same row.

### Task 2 — the rule itself

**Action.** `toPrincipal(session, alsTenantId, membership)` decides in this order:

1. **No session** → `anonymous`.
2. **`alsTenantId` is undefined** (the admin and the apex — no tenant host):
   - phone present → `anonymous`, unchanged from today;
   - otherwise → `operator`, exactly as today, `tenantId` from `activeOrganizationId` when set.
     **Onboarding depends on this branch** — do not gate it on membership.
3. **`alsTenantId` is set** (a guest host):
   - `membership !== null` → `operator` for that tenant, `baseRole` from `membership.role`;
   - otherwise → `customer` for that tenant. **This is the new branch**, and it is what both a
     Google guest and a phone customer hit.

A `CustomerPrincipal` requires a `phone` today. A Google guest has none. Widen it to
`phone: string | null` rather than inventing a value; audit every reader of `principal.phone` and
make the `null` case explicit.

**Verification.**
- `grep -n "principal.phone" apps/api/src -r` — every hit handles `null`.

<threat_model>
## Trust Boundaries

The guard is the boundary. Everything downstream — RBAC, `ScopedTx`, RLS — assumes
`req.principal` is right.

## STRIDE Threat Register

- **T-01 (Elevation of privilege) — a customer classified as an operator.** Cannot happen under the
  new rule: `operator` now requires a membership row, which is strictly more evidence than today's
  "no phone number". The change moves in the safe direction.
- **T-02 (Elevation) — an operator classified as a customer, then reaching guest routes with an
  operator's session.** Possible on another tenant's storefront by design (the lunch case). The
  guest surface is public and grants nothing an anonymous visitor lacks, so the customer principal
  carries no privilege to abuse. What must be verified is that no *operator* route accepts a
  customer principal — Task 4's authz specs cover exactly this.
- **T-03 (Spoofing) — forging `alsTenantId` to claim membership elsewhere.** `alsTenantId` comes
  from the tenant middleware, which resolves it from the host; `X-Forwarded-Host` is set by Caddy
  and not accepted from a client (07.5-14). Unchanged by this plan, and the membership query is
  scoped to that same tenant, so a forged value would find no row and yield a *customer*, not an
  operator.
- **T-04 (Information disclosure) — the extra query leaking membership existence.** The result never
  reaches a response body; it only selects a branch. No new surface.
- **T-05 (Denial of service) — a query added to every authenticated request.** It replaces an
  existing query rather than adding one (Task 1's grep proves the count). `member` is indexed on
  `(user_id, tenant_id)`.
</threat_model>
