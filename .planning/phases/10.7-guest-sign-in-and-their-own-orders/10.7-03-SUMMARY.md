# 10.7-03 — an order remembers who placed it

## What shipped

- **`orders.customer_user_id`**, nullable, plus a partial index on `(tenant_id, customer_user_id)
  WHERE customer_user_id IS NOT NULL` — the only shape it is ever queried in. Migration
  `0021_order_customer_user.sql`, no backfill (D-14).
- **Three write paths, not two**: the repository's INSERT, its UPDATE, and its snapshot read.
- **The owner comes from the resolved session**, never the body. `@OptionalAuth()` (plan 01) is on
  the orders controller; `customerUserId` is absent from `CreateOrderInputSchema` — verified by grep.
- **`GET /v1/orders/mine`**: a guest's own orders inside the tenant the request resolved, newest
  first, capped at 50, with the response field list pinned by a Zod schema.

## Two of my own tests failed the "must be able to fail" bar

**First: the update-path test could not fail.** The plan asked for a test that would have caught the
`payment_status` defect. I wrote one that loads an order, calls `accept()`, updates, and asserts the
owner survived. **Measured: with `customerUserId` deleted from `#runUpdate`'s set-clause, it still
passed.**

The reason is structural, and worth carrying forward: **omitting a column from an UPDATE only loses
data when something changes that column.** Nothing changes the owner after placement — by design —
so the row simply keeps its inserted value either way.

Rewritten to rebuild the snapshot with a *different* owner and assert the write follows. That
version fails correctly: `Expected "guest-…-moved", Received "guest-…"`. The reasoning is in a
comment on the test so nobody "simplifies" it back.

**Honest scope of what the column-in-UPDATE buys:** today it is defence, not necessity — nothing
writes a different owner. It is there so that a future change to the owner cannot vanish the way
`payment_status` did.

**Second: the isolation test does not prove what it looks like it proves.** It seeds two
restaurants and the *same* guest identity in both, then asserts each list matches exactly. It
passes. But **with `eq(orders.tenantId, ctx.tenantId)` removed from the query, it still passes** —
RLS alone provides the isolation in this harness.

So: *the test proves the isolation holds. It does not prove that my query's filter provides it.*
The explicit filter stays because ADR-0020 I-1 mandates both layers precisely so neither is a single
point of failure — not because a test here demands it. Strengthening the test would mean bypassing
RLS, which is a path the application never takes.

## A fixture mistake worth naming

The isolation test first failed with two orders where one was expected. **Not a leak** — both
belonged to the same tenant; earlier tests in the file had placed orders for the same guest.

The one-character fix was to loosen `toEqual` into "contains mine". That would have passed while
leaking a stranger's order, which is the exact thing the test exists to catch. Gave the test its own
guest id instead, and wrote the reason into the file.

## `as never` in a fixture cost three round trips

The aggregate input was cast rather than typed, so instead of one compiler error listing every
missing field I got them one at a time from Postgres: `short_number` NOT NULL, then
`order_items.currency` NOT NULL — each a fresh container start. Suppressing types in a fixture moves
errors from compile time to run time, where they cost minutes instead of seconds.

## Making the snapshot field required did the sweep for me

`customerUserId: string | null` (not optional) on `OrderSnapshot` turned every construction site
into a compile error — **seven**, including the repository's own read path, which I would otherwise
have missed. Adding `listForCustomer` to the port then broke five repository mocks and one
controller spec. Six more places that each had to be looked at.

## Deviations from the plan

- **The plan said the update-path test "would have caught the old defect".** As first written it
  would not have. Corrected, and the measurement recorded rather than the intention.
- **The plan asked for an e2e for the read.** Covered at the integration layer against the real
  repository instead, which exercises the same query and the same RLS. An HTTP-level test adds the
  controller's `principal.kind !== 'customer'` branch, which is not yet reachable without plan 04's
  client — worth adding there.

## Handoff

- `GET /v1/orders/mine` returns `{ orders: [] }` for anyone not signed in, deliberately: a refusal
  would tell a stranger whether an account has orders. Plan 05 renders this.
- The response shape is pinned in `MyOrderSummarySchema`. Widening it is a schema change, not an
  accident.
- **Not done:** the OpenAPI artifacts are not regenerated. Plan 05 owns that, and CI's
  `openapi-drift` job will be red until it runs.
