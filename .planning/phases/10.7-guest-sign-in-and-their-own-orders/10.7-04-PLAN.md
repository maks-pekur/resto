<context>
`apps/qr-menu` has no Better Auth client at all — `grep -rn better-auth apps/qr-menu` is empty. It
calls the API with **relative paths** (`fetch('/v1/menu')` in `src/api/client.ts`), which is exactly
right and is what makes the same-origin cookie work: `/api/auth/*` resolves to the guest's own host,
Caddy proxies it to the api in production, and plan 02 makes the dev proxies match.

`AccountSheet.tsx` is a stub: it takes a phone number, sets a flag, and renders `account.soon`. Its
copy promises the order is found "by the number you give at checkout" — which QR checkout never
asks for. After this phase the **account** finds the order, so that copy must go (D-19).

**This plan is `autonomous: false`** because it needs two things only the founder can do in Google
Cloud Console and the environment. Do not guess them; ask, and stop until they are done.
</context>

<tasks>

### Task 1 — an auth client for the guest app

**Action.** Add `better-auth` to `apps/qr-menu` and create `src/auth/client.ts` exporting a client
built with `createAuthClient` and the `oneTapClient` plugin, pointed at the **relative** base
`/api/auth` — never an absolute host. An absolute URL would send the guest cross-origin and put the
cookie on the wrong host, which is the whole failure this design avoids.

Add `src/auth/use-session.ts`: a thin hook exposing `{ user, isPending }` and nothing else. Do not
build a store, a context, or a token cache — the session is a cookie the browser sends on its own.

**The one thing not to do.** Do not copy the session into `localStorage`, a Zustand store, or any
JavaScript-reachable place "so the UI can read it". That gives back the property the same-origin
`httpOnly` cookie buys (D-22).

**Verification.**
- `grep -rn "localStorage\|sessionStorage" apps/qr-menu/src/auth/` returns nothing.
- `grep -n "baseURL" apps/qr-menu/src/auth/client.ts` shows a relative path.
- `pnpm exec nx run qr-menu:typecheck --skip-nx-cache` — 0 errors.

### Task 2 — the account drawer signs in for real

**Action.** Replace `AccountSheet`'s phone stub with One Tap. Signed out: the benefits and the
Google button. Signed in: who they are and a sign-out. Delete `account.soon` and every string that
promises the phone number finds the order.

**Copy (D-18) — say only what is true after this phase:** find your orders here, and your details
filled in next time. Not offers, not loyalty, not points. All three locales.

**Verification.**
- `grep -rn "account.soon" apps/qr-menu` returns nothing.
- `grep -rn "по номеру\|by the number" apps/qr-menu/src/i18n` returns nothing.
- The three locale files parse and carry the same key set — a missing key in one locale is a blank
  screen for that guest.

### Task 3 — checkout prefills, and offers without nagging

**Action.** When a session exists, prefill the checkout name and phone from it, **editable**; what
the guest submits is what is stored (D-16). When there is none, show a one-line offer to sign in
with "continue without an account" beside it — same visual weight, not a greyed-out afterthought.

Dismissing the offer must persist for the visit. A prompt that returns on every checkout is the
"unobtrusive" the founder asked for, inverted.

**Verification.**
- A component test: with a session, the fields are prefilled and editable, and an edited value is
  what reaches the submit handler.
- A component test: with no session, both the offer and the continue-without path are present and
  the continue path submits successfully.
- A component test: dismissing the offer hides it, and it stays hidden on a second open.

### Task 4 — signing out leaves nothing behind

**Action.** Sign-out calls the server and clears any client state derived from the session. The cart
is **not** cleared — a guest signing out mid-order has not abandoned it.

**Verification.**
- A component test asserting the cart survives sign-out.
- A component test asserting a signed-out guest sees the signed-out drawer, not a stale name.

</tasks>

<threat_model>
## Trust Boundaries

The browser holds the session. Everything here is client code; the server-side checks are plan 02's.

## STRIDE Threat Register

- **T-01 (Information disclosure) — session readable by an XSS on a tenant storefront.** The cookie
  is `httpOnly`; Task 1's grep is the guard that keeps it that way. What remains is an XSS acting
  *as* the guest on that page — the ordinary limit of cookie auth, not something this plan can fix.
- **T-02 (Spoofing) — a fake sign-in UI harvesting Google credentials.** One Tap renders in a
  Google-controlled iframe; the page never sees the password. This is a reason to use One Tap rather
  than a hand-built form, and a reason not to "simplify" it into one later.
- **T-03 (Information disclosure) — prefilled details leaking to the wrong guest.** The prefill
  comes from the session, and the session is host-only, so a shared device shows the last signed-in
  guest until they sign out. Sign-out must therefore actually work — Task 4.
- **T-04 (Tampering) — an edited prefill.** Intended: D-16 says the guest may correct their own
  details and what they submit is stored. It is a snapshot for the kitchen, not an identity claim.
</threat_model>
