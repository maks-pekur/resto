<context>
Plan 03 built the read and pinned its response shape. Plan 04 built the session and the drawer. This
plan is the screen between them, and the contract regeneration that publishes the read.

The guest already has an order-status view (`OrderStatusSheet.tsx`) for the order they just placed.
This is the list of the ones before it — reuse that sheet's visual language rather than inventing a
second way to show an order.

**Why the empty state matters more than usual here.** D-14 says an order placed anonymously never
gains an owner. A guest who ordered last week, then signed in today, will see an empty list and
conclude the feature is broken. The screen has to say what is actually true: orders are remembered
from the moment you sign in.
</context>

<tasks>

### Task 1 — publish the contract

**Action.** Regenerate `docs/api/openapi.yaml` and `packages/api-client/src/generated/api.ts` from
plan 03's route. Both are committed artifacts and CI has an `openapi-drift` job that fails when they
disagree with the code.

**Never hand-edit the generated client** — `packages/api-client/CLAUDE.md` forbids it, and a
hand-edit that does not byte-match real codegen trips the drift job anyway. Regeneration needs a
bootable `AppModule`; if it fails, stop and report rather than patching by hand. A phase-10.6 plan
lost a correct fix to exactly this and was right to revert rather than fake it.

**Verification.**
- `pnpm exec nx run api:openapi:emit && pnpm exec nx run api-client:gen` both succeed.
- `git diff --stat docs/api/openapi.yaml packages/api-client/src/generated/api.ts` shows only the
  new route.

### Task 2 — the screen

**Action.** `MyOrdersSheet.tsx`: newest first, each row showing number, when, status, total. Opening
a row shows what `OrderStatusSheet` already shows. Reached from the account drawer, and only when
signed in.

Three states, all designed, none an afterthought:
- **loading** — the app's existing skeleton, not a bare spinner;
- **empty** — "orders are remembered from the moment you sign in", so last week's absence reads as
  expected rather than broken;
- **error** — a retry, not a dead end.

**Verification.**
- A component test per state.
- The empty state's copy exists in all three locales and says what D-14 actually guarantees.

### Task 3 — it is offered, never teased

**Action.** A signed-out guest sees no entry point to this screen — no greyed row, no "sign in to
see". The offer to sign in already lives in the drawer and at checkout (plan 04); a third nag is
noise.

**Verification.**
- A component test: signed out, the drawer renders no my-orders entry at all.
- A component test: signed in, it does.

### Task 4 — prove the isolation from the client's side too

**Action.** Plan 03 proved cross-tenant isolation server-side. Add one component test that the
screen renders exactly what the API returned and never merges in anything from cart or local state
— a client that "helpfully" appends the current order would show an order the server did not
attribute.

**Verification.**
- A component test with a stubbed response asserting the rendered rows match it one-for-one.

</tasks>
