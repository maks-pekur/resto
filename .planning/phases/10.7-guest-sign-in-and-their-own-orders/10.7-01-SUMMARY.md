# 10.7-01 — the principal rule, and `@OptionalAuth`

Executed by the orchestrator. The headline is not the feature: **07.4's tests caught a real security
regression I wrote**, and the plan I had written a few hours earlier was wrong about the design.

## What shipped

`buildPrincipal` now takes the membership row and decides in this order:

1. **phone present** → customer on a tenant host, anonymous off one. **07.4's branch, untouched, and
   still first.**
2. **no phone, on a tenant host, no member row, no `activeOrganizationId`** → **customer**. The new
   branch; it is what a Google guest hits.
3. otherwise → operator, `tenantId` from `activeOrganizationId`, `baseRole` from the membership.

`lookupMembership` runs **once** per request (`grep -c` returns 2: one definition, one call), against
`alsTenantId ?? activeOrganizationId`.

`@OptionalAuth()` pairs with `@Public()`: the route stays open, but a valid session yields a real
principal. It **never refuses** — every failure path ends in `anonymous`.

## The regression 07.4 caught

My first implementation set the operator's `tenantId` from **`alsTenantId`** — the host. 07.4-06's
own summary describes the hole that closes: *"a session with no activeOrganizationId used to skip
this check entirely, binding whatever x-tenant-id the request carried."*

The mismatch check below it still ran, and still compared — the host against itself. It agreed every
time. **The guard looked intact and guarded nothing.**

Six specs went red. I twice explained them as tests written for the old rule, and was wrong twice.
The corrected rule is smaller than the one I planned: an operator's tenant comes from their session's
positive choice; only a *customer* takes it from the host, which is correct because a guest's tenant
**is** the site they are standing on.

Also restored: the `auth.tenant_membership_missing` refusal, which I had deleted as unreachable. It
is reachable — a session claiming a tenant whose member row was revoked — and it is what stops a
stale `activeOrganizationId` outliving a revoked membership.

**Net: zero of 07.4's guarantees relaxed.**

## Two of the six failures were a test-harness artifact, not a guarantee

`auth-guard.spec.ts`'s shared `authDb` stub answers `[{ role: 'owner' }]` for every lookup. Two
*customer* scenarios therefore appeared to hold a membership. Reading the stub rather than the test
names is what stopped me rewriting two settled 07.4 behaviours to satisfy a fixture.

## Three wrong expectations were my own

`auth-guard-principal.spec.ts` asserted the operator's `tenantId` came from the host — the same
mistake as the implementation. I had written it into the code *and* the test, and only somebody
else's tests caught it. A row asserting "membership outranks a phone number" was also wrong and now
asserts the opposite, naming 07.4 as the reason.

## RED before GREEN, both times

- **The rule.** 8 rows run against the unchanged implementation: `4 failed | 4 passed`. The four
  failures were the membership-dependent rows; the three onboarding rows passed already, which is
  what made it clear they must not break.
- **`@OptionalAuth`.** Made the catch rethrow `UnauthorizedException` and re-ran: exactly one
  failure — *"treats a broken session as anonymous instead of throwing"*, `1 failed | 11 passed`.
  Restored, 12/12.

Lint caught six violations I introduced, in two rounds, and **the second round is the lesson**:

- `nx run api:lint` found four — a `type` where this repo requires an `interface`, and three `async`
  arrows with no `await`. I only saw them because I ran lint on its own; the combined command had
  swallowed its output.
- After fixing those, `nx run api:lint` reported **0 errors — and the pre-commit hook then rejected
  the commit twice**, on an unsafe `any` return and a redundant assertion in the new spec. The hook
  runs `eslint` directly on the changed files; the Nx target did not reach this one.

So "lint is clean" was written into this summary once on the strength of a command that never
looked at the file. This is the same failure as 07.4-06's — verifying with a sibling command instead
of the one that covers the change. **The check that matters is `npx eslint <the changed file>`,
which is what the hook does.**

## An honest note on two e2e specs

`organization-switch` and `tenant-onboarding` are red on `main` in CI and **green here**. I did not
claim a fix. Stashing this plan's changes and running the same two specs on the base gives
`2 passed (2) / 8 passed (8)` — they pass there too. So they fail only in CI's full-suite run,
matching the recorded gotcha that the whole `apps/api` suite in one process produces false
rate-limit failures. Nothing in this plan touched them.

## Known limitation, accepted deliberately

An operator of restaurant A visiting restaurant B's storefront is **not** a guest there. They stay
an operator bound to A, meet 07.4's mismatch refusal, and must sign out to order.

The plan intended to solve this ("the lunch case"). Solving it requires weakening the check that
protects against a stale organization binding — the revoked-membership case. Between "an owner
cannot buy lunch without signing out" and "revoked access outlives the revocation", there is no
contest. Logged rather than fixed.

This does not affect the phase's goal: an ordinary Google guest carries no operator identity at all
and takes the new branch as designed.

## Deviations from the plan

- **The plan named `toPrincipal`; the function is `buildPrincipal`.** It also placed the decorators
  in `apps/api/src/shared/auth.ts`; they live in a directory. Both corrected in the plan before
  execution, per the founder's standing rule that a changed fact updates every source.
- **`buildPrincipal` had to be exported** to be unit-testable. The plan did not mention it.
- **The plan's decision table was wrong in two rows** (operator tenant from the host; membership
  outranking a phone). Corrected in the plan file, not only in the tests.

## Handoff

- Nothing yet carries `@OptionalAuth()`. Plan 03 puts it on the guest order route and is its first
  user.
- `CustomerPrincipal.phone` is now `string | null`. Nothing in `apps/api/src` reads it today —
  verified by grep — so no call site needed updating, but the next reader must handle `null`.
