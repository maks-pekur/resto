<objective>
Register the `one-tap` plugin, trust the tenant origins, and close the dev/production asymmetry on
`/api/*` so the guest sign-in that works on a server also works on the Mac.
</objective>

<context>
Google is already registered (`auth.config.ts:204`), gated on both credentials being present. The
`one-tap` plugin ships with better-auth 1.6.30 and is not loaded. It reuses
`socialProviders.google.clientId` as the ID token's audience, so it needs no second credential and
no new redirect URI in Google Cloud Console.

`trustedOrigins` is assembled in `identity-core.module.ts:232` as a plain array. Better Auth routes
any pattern containing `*` through `wildcardMatch` (`dist/auth/trusted-origins.mjs:18-22`), so
`https://*.<apex>` is a supported shape.

**The asymmetry this plan must close.** In production `infra/docker/Caddyfile` proxies `/api/*` to
the api from the apex **and every tenant subdomain**. Locally nothing does:
`apps/website/next.config.mjs:17-24` rewrites `/v1/:path*` only, and `apps/qr-menu/vite.config.ts`
proxies `/v1`, `/internal` and `/media`. Ship the plugin without this and sign-in works on a server
and 404s on the Mac — the exact class of gap that cost this project a day already.
</context>

<tasks>

### Task 1 — register one-tap, gated exactly as Google is

**Action.** Import `oneTap` from `better-auth/plugins` and add it to the `plugins` array **only when
`opts.google` is present**, mirroring how `socialProviders` is already conditional. Pass no
`clientId` of its own — let it fall through to `socialProviders.google.clientId`, so there is one
credential and one place to change it.

**Verification.**
- `pnpm exec nx run api:typecheck --skip-nx-cache` — 0 errors.
- A unit test builds the auth instance **without** Google credentials and asserts the app still
  constructs and no one-tap route is exposed.
- A unit test builds it **with** credentials and asserts the `one-tap/callback` route exists.

### Task 2 — trust the tenant origins

**Action.** In `identity-core.module.ts`, push `https://*.${PUBLIC_APEX_DOMAIN}` onto
`trustedOrigins` when the apex is set. Keep the existing admin origin entry.

**Do not** touch `CORS_ALLOWED_ORIGINS`. The auth calls are same-origin (D-08); a CORS change here
would be cargo-culted from the superseded bearer design.

**Verification.**
- A unit test asserting the built `trustedOrigins` contains the wildcard entry when the apex is set,
  and does not when it is unset.
- `grep -n "CORS_ALLOWED_ORIGINS" apps/api/src/contexts/identity/` returns nothing.

### Task 3 — the dev proxies learn `/api/*`

**Action.** Add `/api/:path*` to `apps/website/next.config.mjs`'s dev-only `rewrites()`, next to the
existing `/v1/:path*` and gated the same way. Add `'/api'` to `apps/qr-menu/vite.config.ts`'s
`proxy`, with the same `changeOrigin: false` the `/v1` entry uses — the api must see the tenant host,
not the proxy's.

**Why `changeOrigin: false` matters here.** The tenant is resolved from the host; rewriting it would
make every proxied guest request tenant-less. The existing `/v1` entry already gets this right —
copy it, do not invent.

**Verification.**
- With the dev stack up, `curl -sS -o /dev/null -w '%{http_code}' http://localhost:3003/api/auth/ok`
  returns a status the api produced, not Vite's 404 page.
- The same through the website's dev port.
- `grep -c "'/v1'" apps/qr-menu/vite.config.ts` still returns 1 — the existing entry is untouched.

### Task 4 — prove the audience check is real

**Action.** This is the one security property the plan adds, and it comes from a dependency. Do not
take it on trust: write a test that posts an ID token whose `aud` is some other client id and assert
the callback refuses it.

If minting a signed token in a test is impractical, assert the *wiring* instead and say so plainly
in the SUMMARY: that `audience` resolves to our own `GOOGLE_CLIENT_ID`, read back from the built
auth instance. An honest smaller claim beats a comfortable unverified one.

**Verification.**
- The test exists and fails if `audience` is wired to anything but our client id.

</tasks>

<threat_model>
## Trust Boundaries

`/api/auth/one-tap/callback` accepts a token from an untrusted browser and, on success, mints a
session.

## STRIDE Threat Register

- **T-01 (Spoofing) — a forged or replayed ID token.** Mitigated by the plugin's own
  `verifyGoogleIdToken`, which checks Google's signature and the audience. Task 4 exists because
  this mitigation lives in a dependency and the plan must not assume it.
- **T-02 (Spoofing) — a token minted for a different Google application.** Same mitigation: the
  audience is our client id, not any client id.
- **T-03 (Elevation) — a guest session reaching the admin.** Prevented by the cookie being
  host-only: a cookie set on `pizza.<apex>` is never sent to `<apex>`. This is D-06, and it is why
  `AUTH_COOKIE_DOMAIN` must stay unset.
- **T-04 (Elevation) — a guest session on one restaurant reaching another.** Same mechanism, same
  reason.
- **T-05 (CSRF) — a mutating auth call from an attacker's page.** `trustedOrigins` is the control;
  Task 2 widens it to tenant hosts and no further. `https://*.<apex>` matches one label and never
  spans dots, so `evil.com/#.<apex>` and `a.b.<apex>` both fail.
- **T-06 (Denial of service) — unbounded sign-in attempts.** The existing per-tenant sign-in rate
  limit (`per-tenant-signin-rate-limit.e2e.spec.ts`) covers Better Auth's routes; confirm one-tap's
  callback is inside that scope and say so in the SUMMARY. If it is not, log it — do not widen the
  limiter as a side effect of this plan.
</threat_model>
