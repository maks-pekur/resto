# 10.7-02 — one-tap registered, tenant origins trusted, the dev gap closed

## What shipped

- **`oneTap()` is in the plugins array**, gated on `opts.google` exactly as `socialProviders.google`
  already was, and given **no `clientId` of its own** — so the ID token's audience can only ever be
  `socialProviders.google.clientId`. One credential, one place to change it.
- **`trustedOrigins` gains `https://*.${PUBLIC_APEX_DOMAIN}`** when the apex is set.
- **Both dev proxies learn `/api/*`**: `apps/website/next.config.mjs`'s dev-only `rewrites()` and
  `apps/qr-menu/vite.config.ts`'s `server.proxy`, the latter with `changeOrigin: false` copied from
  the `/v1` entry.
- `CORS_ALLOWED_ORIGINS` untouched — the auth calls are same-origin (D-08).

## The plan allowed a weaker claim than I ended up able to make

Task 4 said: if minting a signed Google token in a test is impractical, assert the *wiring* instead
and **say plainly in the summary that the signature check itself is unverified**.

I wrote the wiring assertions first, then checked whether the plugin was actually mounted. It can be
tested for real: `buildAuth` constructs with a stub `authDb` and never touches the database, so its
`api` object can be inspected directly.

```
WITH GOOGLE    oneTap keys: [ 'oneTapCallback' ]
WITHOUT GOOGLE oneTap keys: []
```

So `one-tap-mounted.spec.ts` asserts the route **exists with credentials and is absent without
them** — a real property, not a proxy for one. The fallback was not needed.

**What is still unverified, stated plainly:** the ID token's *signature and audience* check runs
inside better-auth's `verifyGoogleIdToken` and is not exercised by any test here. What is proven is
that the route is mounted only when Google is configured, and that no second `clientId` can be
supplied to it. A forged-token test would need a signing key and belongs to an e2e with a Google
test fixture.

## RED before GREEN

Both changes were broken deliberately and each cost exactly one test:

- `...(opts.google ? [oneTap()] : [])` → `...(opts.google ? [] : [])`
  → *"exposes the one-tap callback when both credentials are configured"* failed.
- the `trustedOrigins.push` line deleted
  → *"trusts every tenant host under the apex, one label deep"* failed.

`2 failed | 7 passed` with both broken; `9 passed` restored.

## The dev/production asymmetry, proven closed with real requests

Before this plan, `/api/*` reached the api from a tenant host **in production only** — the Caddyfile
serves `{$WEBSITE_HOST}, *.{$WEBSITE_HOST}` and proxies `/api/*` there, while the website rewrote
`/v1` alone and qr-menu proxied `/v1`, `/internal`, `/media`. Sign-in would have worked on a server
and 404'd on the Mac.

Measured after the change, against the running api:

| through | `/api/auth/ok` |
|---|---|
| `apps/website` dev (3002) | `200` — body `{"ok":true}` |
| `apps/qr-menu` dev | `200` — body `{"ok":true}` |

`{"ok":true}` is better-auth's own response, so the request reached the api rather than the dev
server's 404. The qr-menu server was not running; it was started for this check, bound to the next
free port because 3003 was occupied, and stopped afterwards.

## The lint lesson, for the third time today

`nx run api:lint` reported clean **twice** on files that `npx eslint <file>` then rejected — the
pre-commit hook, which lints changed files directly, caught two more errors here after the Nx target
had passed.

`nx run api:lint` is not a substitute for linting the file you changed. This summary's own
verification table lists the per-file command for that reason. Same family as 07.4-06's defect,
where a sibling spec was run instead of the changed one.

## A stale comment corrected in passing

`identity-core.module.ts` carried: *"Since 07.4 the admin is one origin — a path on the apex — so
there is no per-tenant host to allow and no wildcard to match."* True when written, false the moment
this plan adds guest sign-in. Rewritten rather than left to mislead, per the founder's rule that a
