## Findings (severity-classified)

### BLOCK-1 — Decision 4's guard premise is inverted: the "session-pin-vs-request 404" is a STAFF defense, not the owner path. A literal implementation deletes staff isolation.

- **Decision touched:** 4 (guard rework).
- **Evidence:** In `location-scope.guard.ts`, the owner bypass returns at **line 65** (`if (principal.baseRole === 'owner') return true;`) — this executes **before** the pin comparison at **lines 67-70** (`activeLocationId !== locationId → NotFoundException()`). An owner **never reaches** that 404 today. The comparison at 67-70, and the scope check at 72-82, are reached **only by non-owners (staff)**. They are the core of staff BOLA defense: they enforce both "one active location at a time" (D-10/D-11) and existence-hiding.
- **Risk:** The locked decision says "on the owner filter path this session-pin-vs-request comparison must be dropped." That comparison is not on the owner path at all. A planner/implementer taking the text literally will edit the guard and remove lines 67-70 — **weakening staff isolation**: a multi-location staff member could then forge `x-location-id` (or a stale session pin) and read a location they are not currently pinned to. The scope check at 77-82 still blocks locations outside their `member_location_scope`, so this is not a cross-tenant breach — but the "one active location per session" business boundary (D-10/D-11) collapses and the existence-hiding 404 is lost. Security-sensitive phase; this is the exact class of regression the persona review exists to catch.
- **Recommendation:** Rewrite decision 4 to state the real change set before planning:
  1. The guard's **owner branch needs no change** — owner already bypasses the pin comparison.
  2. The `all`/brand-global fix is to mark the **new aggregate endpoints `@LocationNeutral()`** so an owner with no `x-location-id` does not hit the `location.context_required` 403 at guard lines 39-45 (that 403 — not a pin 404 — is the documented 08.4 "owner-brand-global stop-list" gap; confirmed: the admin `GET stop-list` is `@RequireBrand()` and NOT `@LocationNeutral()`, `catalog.controller.ts:401-408`).
  3. Guard lines **67-82 stay untouched** for staff.
  4. Add a guard unit test that pins: staff with `x-location-id ≠ session pin → 404`, and staff out-of-scope → 403. Make it a regression net so nobody "simplifies" the guard later.

### HIGH-1 — The new aggregate endpoints are "owner-only" by decision, but `@LocationNeutral` + brand scope does NOT enforce owner-only. A brand-scoped staff member would read sibling locations they aren't scoped to (OWASP API1 BOLA).

- **Decision touched:** 2 (owner-only), 3 (aggregate endpoints).
- **Evidence:** `BrandScopeGuard` (`brand-scope.guard.ts:57-76`) admits any member whose scope includes the brand; `@RequireBrand` is documented default-allow ("empty scope rows mean the operator sees all brands of their tenant", `require-brand.decorator.ts:6-11`). A staff member scoped to **location A** of brand B — where B has locations A, C, D — passes brand scope for B. If an aggregate endpoint is protected only by `@RequireBrand()` + `@LocationNeutral()`, that staff member receives the **A+C+D merged aggregate**, i.e. data for C and D which they cannot otherwise reach. `member_location_scope` is bypassed precisely because the endpoint is location-neutral.
- **Risk:** Silent horizontal privilege escalation for any multi-location brand with scoped-down staff. This is the single most dangerous NEW surface in 08.5.
- **Recommendation:** Aggregate endpoints MUST enforce `baseRole === 'owner'` explicitly — a dedicated `@OwnerOnly()` guard or an in-handler owner check — **not** rely on brand scope. Add an e2e: brand-scoped staff → 403 on every aggregate endpoint. Treat this as a hard acceptance criterion for the phase.

### HIGH-2 — Owner single-location path is not validated `location ∈ active-brand` (and not `not-archived`) server-side. The "silent fallback" of decision 8 is client-only.

- **Decision touched:** 4 (owner bypass), 8 (invalid/archived/foreign fallback).
- **Evidence:** Owner returns true at `location-scope.guard.ts:65` with **no check** that the resolved `x-location-id` belongs to the route's active brand or is active. Tenant isolation still holds (RLS + `auth.tenant_mismatch`, `tenant-context.middleware.ts:92-98`), but cross-brand-within-tenant and archived-location reads are not gated at the server. Decision 8 places the "fallback to first location" for invalid/foreign/archived `?location` in the **client only** (`location-switcher` / route loader).
- **Risk:** An owner (via a bug, a stale tab, a hand-crafted request, or a future copy-paste of this location-neutral pattern onto a staff-reachable surface) can render **brand B1's dashboard populated with B2's location data**, or query an **archived** location. For an owner this is own-tenant data — not a breach — but it is a data-coherence defect and a latent hole the moment the pattern is reused. Never let a security-adjacent invariant depend solely on client behavior.
- **Recommendation:** Add server-side validation on the single-location path: the resolved `x-location-id` must belong to the active brand and must not be archived; return existence-hiding **404** otherwise (mirror 08.2 D-10 / the existing 404 idiom). This makes decision 8's fallback defense-in-depth rather than the only line.

### HIGH-3 — Aggregate fan-out cost under Friday-night spike must be a single grouped query, not a per-location loop.

- **Decision touched:** 3 (aggregate across all brand locations).
- **Evidence / risk:** RestOS perf constraint forbids per-tenant noisy-neighbor patterns and assumes simultaneous Friday-evening order spikes. A naive `for (location of brandLocations) { queryStopList(location) }` implementation is an N+1: a 20-location brand = 20 round-trips per dashboard/stop-list render. The "stopped at N of M locations" badge invites exactly this shape. Mitigant that lowers severity: the aggregate is **owner-only and opt-in** (`all` is not the default per decision 6), so cardinality is bounded by owner admin sessions, not guest traffic.
- **Recommendation:** Enforce a single set-based query in the plan: `WHERE location_id IN (<brand locations>) GROUP BY item_id`, with the N/M badge computed as `COUNT(DISTINCT location_id)` per item versus the brand's total location count. Add/confirm an index on the per-location stop table `(brand_id, location_id, item_id)`. Paginate the aggregate stop-list. Add a test asserting the endpoint issues O(1) queries regardless of location count.

### MED-1 — Keep the `all` aggregate OFF the public edge-cached availability path.

- **Decision touched:** 3 (aggregate endpoints + ETag interaction).
- **Evidence:** The public availability endpoint is `Cache-Control: public, s-maxage=5` with a `stopVersion` ETag and is Set-Cookie-free (`public-menu.controller.ts:160-167`); the `menu-brand-response.e2e` no-`Set-Cookie` test and `apps/CLAUDE.md` lock this as an invariant. The admin `all` aggregate is **owner-authenticated, cookie-bearing, per-owner**.
- **Risk:** Reusing the cached guest availability path for the admin aggregate would either leak per-owner data into a shared edge cache or force `private/no-store` onto an endpoint whose public-cacheability is a hard invariant. Either way regresses the caching contract.
- **Recommendation:** New admin aggregate endpoints emit `Cache-Control: private, no-store`, never `public`, and do **not** route through the guest availability handler. Leave the guest per-location availability endpoint (single resolved location) untouched — the `all` case has no guest surface. If admin-side caching is ever wanted, derive a private ETag from `max(per-location stopVersion)`; that is a later optimization, not MVP.

### MED-2 — Two sources of truth (owner=URL, staff=session pin) must branch on server-trusted role, and the `x-location-id` echo needs a coherent rework.

- **Decision touched:** 1 (URL param), 5 (owner=URL, staff=session pin).
- **Evidence:** `api-client.ts:35,45` currently derives `x-location-id` from `sessionData.activeLocationId` for **everyone**. Under 08.5 the owner header must derive from `?location`, staff from the session pin. Also note `?location=all` is not a UUID — if sent as `x-location-id` it fails `LocationId.safeParse` and is silently dropped (`tenant-context.middleware.ts:85-89`), so an owner in `all` mode on a non-neutral route lands on `location.context_required`.
- **Risk:** If the client keeps echoing the session pin for owners, the URL filter silently no-ops or fights the pin; the state model becomes ambiguous and untestable.
- **Recommendation:** Make the client branch on the server-provided `isOwner` (already available in the switcher props, `location-switcher.tsx:20-26`) — but remember the **guard**, not the client, is the boundary for staff, so a mis-derived client role is only a UX bug. Codify the state model: `?location=all` ⇒ omit `x-location-id` **and** call the aggregate endpoints; `?location=<id>` ⇒ `x-location-id=<id>` on location-scoped endpoints; staff ⇒ header comes from the server pin, ignore any URL param. Unit-test both branches.

### MED-3 — Dead-code / regression surface from removing owner pin writes; do not half-delete shared reset logic.

- **Decision touched:** 5 (owner `session.activeLocationId` no longer written/used).
- **Evidence:** Owner pin is written in several places today: `set-active-location.service.ts:34-54` (owner branch), `set-active-brand.service.ts:56,74` calling `resetActiveLocation` (`:78-88`, writes an initial location on brand switch — invoked for **both** owner and non-owner branches), and `auth.config.ts:422` (initial pin on org-switch). `location-permission-checker.ts:28-35` reads the role at `activeLocationId` — the known "LocationPermissionChecker-not-wired" gap.
- **Risk:** A partial removal leaves inconsistent owner-pin state. The `resetActiveLocation` helper is **shared with the staff path**, so a careless "remove owner pin" edit can break staff login-pinning. Removing the owner pin also interacts with 08.4 D-08 ("effective permissions = role at active location"): under the URL model the owner has no server pin to read, so any future wiring of `LocationPermissionChecker` must explicitly treat owner as base-role `owner` (all permissions), not "role at active location."
- **Recommendation:** Keep the `set-active-location` endpoint **and** its staff branch (`set-active-location.service.ts:57-72`) intact — that is how staff set their login pin. Make owner pin writes an explicit no-op rather than a scattered deletion. Verify the staff path through `resetActiveLocation` still behaves (or is genuinely unreachable given login-to-brand — see MED-4). Add a one-line decision that owner effective-permissions derive from base-role, so the deferred `LocationPermissionChecker` wiring skips owners.

### MED-4 — Staff "login-to-brand" (decision 7) contradicts the still-present non-owner `set-active-brand` path.

- **Decision touched:** 7 (staff session bound to one brand; switch brand = re-login), 5.
- **Evidence:** `set-active-brand.service.ts:62-77` has a live **non-owner** branch that validates reachable brands and resets active-location — i.e. an in-session staff brand switch — which decision 7 forbids.
- **Risk:** Contradictory model. Either staff can switch brand in-session (violates the re-login story and the D-11 tamper-resistance intent) or they cannot (then this scope-changing endpoint is dead code that needlessly widens the attack surface).
- **Recommendation:** In discuss, decide explicitly: under login-to-brand, disable the non-owner `set-active-brand` path (return 403) rather than leaving a reachable brand-switch endpoint for staff. Shrinking a reachable scope-mutation endpoint is a security win, not just cleanup.

### LOW-1 — Alphabetical-first-location default (decision 6) is unstable.

- **Decision touched:** 6.
- **Risk:** "First location alphabetical by name" means creating a location named "AAA" silently changes every owner's default landing location; renames shuffle it. Minor surprise, but avoidable.
- **Recommendation:** Use a stable default — oldest-created, or an explicit `brand.defaultLocationId` the owner can set. Optionally persist last-used-location per session as a convenience. Low effort, removes a footgun.

### LOW-2 — `?location` is user-controlled; validate as `all | uuid` at the edge.

- **Decision touched:** 1, 8.
- **Recommendation:** Parse `?location` with `z.union([z.literal('all'), z.string().uuid()])`; anything else → default. Trivial with Zod + Drizzle (no SQL-injection surface given parameterized queries), but make it explicit so an invalid value can never propagate into a header or query builder. Low.

### NOTE-1 — Pay down the two 08.4 gaps this phase re-opens.

08.4 left "LocationPermissionChecker-not-wired" and "brand-scope e2e fixture debt." 08.5 touches exactly these surfaces. Required e2e coverage for this phase: (1) staff `x-location-id ≠ pin → 404`; (2) staff → aggregate endpoint `403`; (3) owner `?location=<foreign-brand location>` → 404 (per HIGH-2) or documented fallback; (4) owner `all` aggregate returns merged totals + correct N/M badge; (5) non-owner out-of-scope location → 404. Either wire `LocationPermissionChecker` or record an explicit re-defer decision — don't leave it dangling a third phase.

### NOTE-2 — Build-vs-buy / scope: aggregate is genuinely new and correctly minimal; hold the line.

Grep confirms **no** existing dashboard/summary/aggregate endpoint — the aggregate is net-new, not a rebuild (the current dashboard is client-side stop-count + brand-count, `$brandSlug/index.tsx`). The phase reuses `BrandScopeGuard`, `member-location-scope-reader`, and `@LocationNeutral` — good leverage, no NIH. Decision 3's "read-only in `all`, writes require a concrete location" is the right call and already matches the code: the stop-list **write** endpoints are `@RequireBrand()` (location-scoped), not `@LocationNeutral()` (`catalog.controller.ts:223,236`), so they will keep forcing a concrete `x-location-id` through the full guard — do not accidentally make them location-neutral. Resist scope creep into per-location breakdown tables or trend analytics here; that is Phase 13.

## Verdict

**Safe to PLAN against — NOT safe to implement as literally worded.** The direction (URL-as-source-of-truth for owners, session pin for staff, `all`-aggregate endpoints) is architecturally sound because the server guard remains the boundary. Three items must be corrected in the plan before any code: **(BLOCK-1)** rewrite decision 4 — the owner path already bypasses the pin; do not touch the staff pin comparison at `location-scope.guard.ts:67-82`; the real fix is `@LocationNeutral()` on the new aggregate endpoints; **(HIGH-1)** enforce owner-only on the aggregate endpoints explicitly, never via brand scope; **(HIGH-2)** validate `location ∈ active-brand` (and not-archived) server-side instead of trusting the client fallback. Fix MED-2/MED-3/MED-4 to keep the state model coherent and the pin-removal clean.
