# Phase 08.5 Plan 05: Owner location filter UX — switcher, all-mode aggregate, browser smoke Summary

**The location switcher is now a pure client-side URL filter (no server round-trip, no full-page reload); the dashboard and dedicated stop-list page both render an aggregate branch with a read-only N/M badge in `?location=all`, closing the 08.4 white-screen gap; and a real (non-mocked) Playwright browser smoke — seeded against a live api+admin dev server — proves zero 403/`location.context_required` responses across the whole owner walk, catching and fixing a genuine cross-page navigation bug along the way.**

## Accomplishments

- `location-switcher.tsx` is a pure URL filter: `switchTo(value)` calls `navigate({ to: <current pathname>, search: (prev) => ({...prev, location: value}) })` — zero `apiFetch`, zero `window.location.reload`, zero `set-active-location` reference (D-01/D-04)
- Dashboard (`index.tsx`) and `menu/stop-list.tsx` both branch on `useEffectiveLocation()`: `all` → `stopListAggregateQuery`, `single` → `stopListQuery(brandSlug, locationId)`, `none` → empty state — closing the exact 08.4 gap (owner-brand-global stop-list 403) on **both** surfaces, not just the previously-patched dashboard
- `stop-list.tsx` declares `loaderDeps: ({ search }) => ({ location: search.location })` so the loader re-runs on `?location` changes; in `all` it renders the new `StopListAggregateTable` (per-item "N/M locations" badge, no stop/unstop control, a visible read-only hint) instead of the single-location `StopListTable` (D-05/D-06)
- Zero-locations owner sees an `EmptyState` + "Create a location" CTA on the dashboard, no default-location redirect (D-19)
- Restored single-location stop/unstop end-to-end: `toggleStopList`/`resetStopList` now require an explicit `locationId` (threaded through `StopListTable`, `TodaysWidgetResetButton`, and `ItemsTable`'s inline toggle) — without this, every owner stop/unstop write would 403 today since `apiFetch` no longer falls back to a session pin (08.5-04)
- A real (non-mocked) Playwright browser smoke (`apps/admin/e2e/adm-01-all-mode-smoke.spec.ts`) seeds a tenant/brand/2 locations/item via the live `apps/api`, signs in through the actual `/login` form, and walks `?location=all` on the dashboard + stop-list page, then switches to a concrete location — asserting **zero** 403/`location.context_required` responses the entire way, and that the stop/unstop switch reappears once a concrete location is selected
- **Found and fixed a real bug via that browser smoke** (not caught by any unit test): `useNavigate({ from: <static layout route> })` + `navigate({ search })` with no `to` resolves the destination _path_ relative to `from`, not the current page — so the switcher (and the pre-existing D-18 fallback redirect in `use-effective-location.ts`, inherited from plan 04) silently bounced the owner back to the brand dashboard on every location switch, discarding whatever sub-page they were on

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Fixed the switcher (and the pre-existing D-18 fallback hook) navigating to the brand dashboard instead of staying on the current page**

- **Found during:** Task 3, the real browser smoke (Step 3 — switching from the stop-list page to a concrete location)
- **Issue:** `useNavigate({ from: brandSlugLayoutRoute.fullPath })` followed by `navigate({ search: (prev) => ... })` with no `to` resolves the destination path relative to `from` (verified by reading `@tanstack/router-core`'s `buildLocation`: `defaultedFromPath = dest.from ?? currentFullPath`, and `nextTo` defaults to that path when `to` is absent) — not the browser's actual current pathname. Any component using this pattern from somewhere other than the `from` route itself gets silently redirected. `use-effective-location.ts`'s D-18 fallback effect (built in plan 04) has the identical pattern and the identical latent bug, exercised on every page whenever `?location` needs a default substituted.
- **Fix:** Kept `from` (needed only for the search-updater's TypeScript narrowing) and added an explicit `to: useRouterState({ select: (s) => s.location.pathname })` so the navigation target is always the real current page.
- **Files modified:** `apps/admin/src/components/location-switcher.tsx`, `apps/admin/src/lib/hooks/use-effective-location.ts`
- **Verification:** Playwright smoke's Step 3/4 (switch location from the stop-list page, assert the URL updates and the page stays on `/menu/stop-list`) — green after the fix, red before it (a hard failure with the pre-fix code, not a flaky pass).
- **Committed in:** `866d5ba` (Task 3 commit, alongside the smoke that found it)

**2. [Rule 3 - Blocking] Threaded `locationId` through `toggleStopList`/`resetStopList` and their call sites**

- **Found during:** Task 2, while wiring the single-location `StopListTable` path
- **Issue:** 08.5-04-SUMMARY explicitly flagged this as deferred to plan 05: after `apiFetch` stopped reading the session pin, `toggleStopList`/`resetStopList` sent no `x-location-id` at all, which the location-scoped write endpoints require — an owner's stop/unstop action would 403 today.
- **Fix:** `toggleStopList(brandSlug, itemId, next, locationId)` and `resetStopList(brandSlug, locationId)` now require `locationId`; `StopListTable`, `TodaysWidgetResetButton`, and `ItemsTable` (a call site not in this plan's file list, broken by the same signature change) all thread it through, disabling/hiding the action when not in single mode.
- **Files modified:** `apps/admin/src/lib/queries/catalog.ts`, `apps/admin/src/components/menu/stop-list-table.tsx`, `apps/admin/src/components/menu/todays-86-reset-button.tsx`, `apps/admin/src/components/menu/items-table.tsx`, `apps/admin/src/routes/(protected)/$brandSlug/menu/items.tsx`
- **Verification:** `tsc -p tsconfig.json --noEmit` exits 0; full admin vitest suite 44/44 green; the browser smoke exercises the single-location switch's stop/unstop affordance directly.
- **Committed in:** `47ed84c` (Task 2 commit)

**3. [Rule 3 - Blocking] Fixed `apps/admin/playwright.config.ts`'s stale Next.js-era webServer config**

- **Found during:** Task 3, attempting to run the browser smoke
- **Issue:** The config (unchanged since Phase 02, pre-Vite-migration) launched admin on `:3001` with `NEXT_PUBLIC_API_ORIGIN`/`ADMIN_WEB_URL`/`ACTIVE_BRAND_COOKIE_SECRET` env vars — none of which the current Vite SPA reads. The real dev topology (confirmed by reading `vite.config.ts`, root `.env`, and `env.schema.ts`'s `CORS_ALLOWED_ORIGINS`/`ADMIN_WEB_URL` defaults) is admin `:4000` / api `:5001`, with no server-side env overrides needed.
- **Fix:** `adminPort` → `4000`; `apiOrigin` default → `http://localhost:5001`; `webServer.command` now launches `vite --port 4000` directly (bypassing the package.json `dev` script's own `--port 3001` override); dropped the four dead env vars, kept only `VITE_API_ORIGIN`.
- **Files modified:** `apps/admin/playwright.config.ts`
- **Verification:** `pnpm --filter @resto/admin exec playwright test e2e/adm-01-all-mode-smoke.spec.ts` — 3 consecutive green runs from a cold port (no manually pre-started admin server).
- **Committed in:** `866d5ba` (Task 3 commit)
