# Phase 08.5: Owner location filter UX (URL-param + all-aggregate) - Research

**Researched:** 2026-07-12
**Domain:** NestJS guard-chain security primitive (owner-only gate) + Drizzle/Postgres cross-location aggregate query + TanStack Router typed search params
**Confidence:** HIGH (every claim below is grounded in a direct code/migration read in this repo, not training-data recall; two document-vs-code corrections are flagged explicitly)

## Summary

08.5 is a rework of an already-implemented, already-tested security boundary (`LocationScopeGuard`, `BrandScopeGuard`, the active-location session pin). The CONTEXT.md's 19 decisions are locked; this research does not revisit them. Its job is to firm up six open technical shapes, and it found the code matches the CONTEXT.md's claims closely, with two corrections load-bearing enough for the planner to know before writing tasks:

1. **The owner-only gate should be a new opt-in decorator + guard (`@OwnerOnly()` / `OwnerOnlyGuard`)**, registered as a fifth global `APP_GUARD` in `identity-http.module.ts` after `LocationScopeGuard`. This is the only shape that fits the codebase's existing metadata-driven guard convention (`@Permissions`, `@BrandNeutral`, `@LocationNeutral` are all `Reflector`-read opt-in/opt-out metadata consumed by global guards) rather than a scattered inline check duplicated per new aggregate endpoint.
2. **D-16's literal index target `(brand_id, location_id, item_id)` does not exist as a single table** — `menu_stop_list` had its `brand_id` column *dropped* in migration `0068_stop_list_location_regrain.sql` (08.4). The existing unique index `menu_stop_list_location_item_tenant_uq (tenant_id, location_id, item_id)` already serves the aggregate's `location_id IN (...)` shape. No new migration is required for the stop-list table. Brand→location-list resolution should reuse `LOCATION_REPOSITORY.listForBrand(brandId, tenantId)` — already exported by `TenancyModule`, already imported by `CatalogModule` — filtered to `status === 'active'` app-side, rather than inventing a new query or a phantom index.
3. **The dashboard (`index.tsx`) already silently degrades in brand-global mode** (`enabled: activeLocationId != null` on `stopListQuery`) — it does not crash today, it just never shows a number. The dedicated **`menu/stop-list.tsx` page has no such guard** — its `loader` calls `ensureQueryData(stopListQuery(brandSlug))` unconditionally, so an owner navigating there while brand-global almost certainly reproduces the white-screen (403) live today. Both call sites need the new aggregate branch; enumerated exhaustively below.
4. **`@BrandNeutral()` transitively bypasses `LocationScopeGuard` too**, not just `BrandScopeGuard` — the guard's own code checks `BRAND_NEUTRAL_KEY` before its location check. This explains why `/v1/me/*` endpoints work today regardless of location-pin state and matters for the D-17 enumeration (anything already `@BrandNeutral()` needs no additional `@LocationNeutral()`).
5. **`afterUpdateMemberRole` (Phase 3) does NOT reset `activeLocationId`/`activeBrandId` on role change** — verified by reading the hook; it only emits the `identity.role_changed.v1` audit event. The persona's LOW-11 concern is real and unresolved in the codebase today.
6. **TanStack Router 1.170's `loader` does not automatically re-run when a search param changes** — the route needs `loaderDeps: ({ search }) => ({ location: search.location })` or the aggregate/single-location branch will silently serve stale data after the owner changes `?location`.

**Primary recommendation:** Add `@OwnerOnly()` + `OwnerOnlyGuard` as a new APP_GUARD; add one new sibling read endpoint (`GET /v1/catalog/stop-list/aggregate`) marked `@LocationNeutral() @OwnerOnly()`; resolve the brand's active locations via the existing `LOCATION_REPOSITORY.listForBrand` port (no new migration); lift `?location` to a `validateSearch` on `$brandSlug/_layout.tsx` so it is available to every descendant route via `Route.useSearch()`; replace `apiFetch`'s unconditional session-read of `activeLocationId` with an explicit `locationId` parameter that callers resolve via one shared hook branching on `isOwner`.

### Pattern 1: Opt-in metadata guard (the established convention to extend)

**What:** Every cross-cutting authorization concern in this codebase is a `SetMetadata` key + a `Reflector.getAllAndOverride` read inside a global `APP_GUARD`. `@Permissions(spec)` (opt-in, no-op if absent), `@BrandNeutral()` / `@LocationNeutral()` (opt-out, no-op if absent) are the two existing shapes.
**When to use:** Any new cross-cutting authz check that must be declaratively visible on the controller/handler, unit-testable in isolation, and enforced even if a future developer adds a new endpoint and forgets a manual `if` check.
**Recommendation:** `@OwnerOnly()` should be the **opt-in** shape (like `@Permissions`), because it only applies to the 1-2 new aggregate endpoints, not the whole surface:

```typescript
// apps/api/src/shared/auth/owner-only.decorator.ts (NEW — mirrors location-neutral.decorator.ts)
import { SetMetadata } from '@nestjs/common';
export const OWNER_ONLY_KEY = 'identity:owner-only';
export const OwnerOnly = () => SetMetadata(OWNER_ONLY_KEY, true);
```

```typescript
// apps/api/src/contexts/identity/interfaces/http/guards/owner-only.guard.ts (NEW)
@Injectable()
export class OwnerOnlyGuard implements CanActivate {
  constructor(@Inject(Reflector) private readonly reflector: Reflector) {}

  canActivate(ctx: ExecutionContext): boolean {
    const required = this.reflector.getAllAndOverride<boolean | undefined>(OWNER_ONLY_KEY, [
      ctx.getHandler(),
      ctx.getClass(),
    ]);
    if (!required) return true; // no-op, same as PermissionsGuard when @Permissions absent

    const req = ctx.switchToHttp().getRequest<FastifyRequest>();
    const principal = req.principal;
    if (principal?.kind !== 'operator' || principal.baseRole !== 'owner') {
      // Bare NotFoundException() — no code/message body — matches the existing
      // existence-hiding precedent at location-scope.guard.ts:69, not the
      // {code, message} shape used for informative 403s elsewhere in this file.
      throw new NotFoundException();
    }
    return true;
  }
}
```

Register as a **fifth** `APP_GUARD` in `identity-http.module.ts`, after `LocationScopeGuard` (order matters only in that it should run after `AuthGuard` has populated `req.principal.baseRole` — any position after `AuthGuard` is technically correct, but appending it last keeps the guard list's "most general → most specific" ordering intact and keeps the diff minimal — a single new line):

```typescript
{ provide: APP_GUARD, useClass: AuthGuard },
{ provide: APP_GUARD, useClass: PermissionsGuard },
{ provide: APP_GUARD, useClass: BrandScopeGuard },
{ provide: APP_GUARD, useClass: LocationScopeGuard },
{ provide: APP_GUARD, useClass: OwnerOnlyGuard },   // NEW
```

**Rejected alternative — inline check in the service:** `if (principal.baseRole !== 'owner') throw new NotFoundException()` inside `GetStopListAggregateService.execute()`. Works, but (a) breaks the pattern every other cross-cutting concern in this codebase follows, (b) is invisible on the controller signature next to `@LocationNeutral()` — a reviewer scanning decorators would not see the owner-only property declared, (c) must be copy-pasted into every future aggregate endpoint (a second dashboard-summary endpoint, say) with no compiler/lint signal if someone forgets. The guard+decorator form fails closed by default (`OWNER_ONLY_KEY` absent = pass, matching `PermissionsGuard`'s convention) and is unit-testable exactly like `location-scope.guard.spec.ts` already tests `LocationScopeGuard`.

**One correction to CONTEXT.md's framing:** `@RequireBrand()` (`require-brand.decorator.ts`) is currently **dead metadata** — `SetMetadata(REQUIRE_BRAND_KEY, true)` is set but no guard anywhere reads `REQUIRE_BRAND_KEY` (grepped the whole `apps/api/src` tree; only the decorator file and its own export reference it). `BrandScopeGuard` is default-on for every route except `@BrandNeutral()` — `@RequireBrand()` is purely a documentation/readability marker on existing catalog/tenancy endpoints. Do not rely on it for any enforcement claim in the plan; keep adding it to the new aggregate endpoint for stylistic consistency with its siblings, but know it does nothing at runtime.

### Pattern 2: Aggregate query — resolve locations via the existing tenancy port, not a new query

**What:** `LOCATION_REPOSITORY.listForBrand(brandId, tenantId): Promise<readonly LocationSnapshot[]>` (`apps/api/src/contexts/tenancy/domain/ports.ts:38`, implemented in `location-drizzle.repository.ts:48`) already returns every location for a brand (both `active` and `archived` — filter client-side). It is **already exported by `TenancyModule`** and **`CatalogModule` already imports `TenancyModule`** (for `RequireActiveTenantGuard`) — no new provider wiring beyond injecting the token.

```typescript
// Source: apps/api/src/contexts/tenancy/domain/ports.ts:38-44 (verified read)
export interface LocationRepository {
  findById(id: LocationId): Promise<LocationSnapshot | null>;
  listForBrand(brandId: BrandId, tenantId: TenantId): Promise<readonly LocationSnapshot[]>;
  save(snapshot: LocationSnapshot): Promise<void>;
  countScopedMembers(locationId: LocationId): Promise<number>;
}
```

```typescript
// New service — apps/api/src/contexts/catalog/application/get-stop-list-aggregate.service.ts
@Injectable()
export class GetStopListAggregateService {
  constructor(
    @Inject(CATALOG_REPOSITORY) private readonly repo: CatalogRepository,
    @Inject(LOCATION_REPOSITORY) private readonly locations: LocationRepository,
  ) {}

  async execute(): Promise<StopListAggregateResponse> {
    const ctx = requireTenantContext();
    const tenantId = TenantId.parse(ctx.tenantId);
    const brandId = requireBrandContext(); // @resto/db — already bound by TenantContextMiddleware
    const all = await this.locations.listForBrand(brandId as BrandId, tenantId);
    const active = all.filter((l) => l.status === 'active');
    const rows = await this.repo.listStopListAggregateAcrossLocations(
      tenantId,
      active.map((l) => l.id),
    );
    return { items: rows, totalActiveLocations: active.length };
  }
}
```

**Aggregate SQL shape (`CatalogRepository.listStopListAggregateAcrossLocations`):** `ScopedTx.selectFrom()` does not expose `.groupBy()` — the repository already drops to the raw `tx` handle with an explicit `eq(table.tenantId, ...)` filter when the fluent builder can't express the query (see `removeFromStopList`'s raw DELETE and `finalizeMenuPublish`'s raw SELECT, both in `catalog-drizzle.repository.ts`). This is the sanctioned escape hatch, not a violation of ADR-0020 I-1, as long as the tenant `eq()` is explicit:

```typescript
// Source: pattern verified against catalog-drizzle.repository.ts:840-905 (raw tx + explicit tenant filter)
async listStopListAggregateAcrossLocations(
  tenantId: TenantId,
  activeLocationIds: readonly string[],
): Promise<AggregateStopListRow[]> {
  if (activeLocationIds.length === 0) return [];
  return this.db.withTenant(async (tx) => {
    const grouped = await tx
      .select({
        itemId: schema.menuStopList.itemId,
        stoppedLocationCount: sql<number>`count(distinct ${schema.menuStopList.locationId})`,
        lastStoppedAt: sql<Date>`max(${schema.menuStopList.stoppedAt})`,
      })
      .from(schema.menuStopList)
      .where(
        and(
          eq(schema.menuStopList.tenantId, tenantId),       // ADR-0020 I-1 mandatory app-level filter
          inArray(schema.menuStopList.locationId, activeLocationIds),
        ),
      )
      .groupBy(schema.menuStopList.itemId)
      .orderBy(desc(sql`max(${schema.menuStopList.stoppedAt})`))
      .limit(/* page size */ 50)
      .offset(/* page offset */ 0);
    // then batch-fetch item/category names exactly like listStopListWithStoppedAt does today
    return grouped;
  });
}
```

**Index:** `menu_stop_list_location_item_tenant_uq` — `UNIQUE (tenant_id, location_id, item_id)`, created in migration `0068_stop_list_location_regrain.sql` — already covers `WHERE tenant_id = X AND location_id IN (...)` efficiently (tenant_id is the fixed leading column; Postgres can do an index range/bitmap scan on the `IN` over the second column). **D-16's literal instruction to "add/confirm index `(brand_id, location_id, item_id)`" describes a column combination that cannot exist** — `menu_stop_list` has no `brand_id` column (dropped in `0068`, confirmed by reading the migration and the current `menu.ts` schema). No new migration is needed for this table.

Optional, not required at MVP scale: `locations` has no index beyond `locations_id_tenant_uq (id, tenant_id)` — resolving `listForBrand(brandId, tenantId)` does a filtered scan over the tenant's locations (bounded by the tenant's total location count across all brands, expected to be small — dozens, not thousands, for a solo-founder-scale restaurant SaaS). If this becomes measurably hot, add `index('locations_tenant_brand_status_idx').on(tenantId, brandId, status)` via `pnpm db:generate` — flag as planner discretion, not a blocking requirement.

**RLS double-enforcement, precisely:** `locations` carries a brand-grain RESTRICTIVE policy (`locations_brand_iso`, migration `0063`): `current_brand_id() IS NULL OR brand_id = current_brand_id()`. Because `ctx.brandId` **is** bound for this request (resolved from `x-brand-slug` by `TenantContextMiddleware`, same as every other brand-scoped catalog read today), `app_bind_brand()` runs inside `withTenant()` and this RLS policy actively filters — the `listForBrand` call is RLS-protected even though it doesn't explicitly `WHERE brand_id = ...` beyond what the app already does. `menu_stop_list` carries a **location-grain** RESTRICTIVE policy (`menu_stop_list_location_iso`, migration `0069`): `current_location_id() IS NULL OR location_id = current_location_id()`. Since `?location=all` sends no `x-location-id` header, `ctx.locationId` is `undefined`, `app_bind_location()` is never called, `current_location_id()` returns `NULL`, and this policy **passes through** (does not filter) — meaning the app-level `location_id IN (activeLocationIds)` predicate is the *only* fence at that table for the aggregate read. This is exactly why D-10's "never trust a caller-supplied location list" matters: `activeLocationIds` must always be server-resolved from the brand-RLS-protected `locations` table, never accepted as a request parameter.

### Pattern 3: `?location` as a shared TanStack Router search param

**What:** TanStack Router (`^1.170.16`) merges a parent route's `validateSearch` output into every descendant route's `useSearch()` result automatically — this is the mechanism to make `?location` visible to the dashboard, menu pages, and stop-list page without each one re-declaring it. [Confirmed via TanStack docs.]
**Where to declare it:** `$brandSlug/_layout.tsx` (the parent of `index.tsx`, `menu/*`, `locations.tsx`) — the existing per-page `validateSearch` pattern already exists at `menu/items.tsx:19-24` (a Zod schema for `page`/`status`/`categoryId`/`q`) to model from.

```typescript
// apps/admin/src/routes/(protected)/$brandSlug/_layout.tsx — ADD
const locationSearchSchema = z.object({
  location: z.union([z.literal('all'), z.string().uuid()]).optional(), // D-01
});
export const Route = createRoute({
  getParentRoute: () => protectedLayoutRoute,
  path: '/$brandSlug',
  validateSearch: locationSearchSchema,
  component: BrandLayout,
});
```

```typescript
// any descendant route, e.g. index.tsx or menu/stop-list.tsx
const search = Route.useSearch({ from: brandSlugLayoutRoute.id }); // or via strict:false — planner picks one convention
```

**Navigation must preserve other search params** — `navigate({ search: (prev) => ({ ...prev, location: nextValue }) })`, not `navigate({ search: { location: nextValue } })` (the latter drops `page`/`status`/etc. on menu pages). [Confirmed via TanStack docs — "Preserving Parameters During Navigation."]

**Loader reactivity — the pitfall that will silently break refetch-on-select:** TanStack Router's `loader` (used by `menu/stop-list.tsx`'s `ensureQueryData` today) does **not** re-run when a search param changes unless the route declares `loaderDeps`:

```typescript
// menu/stop-list.tsx — REQUIRED addition, not currently present anywhere in this codebase
export const Route = createRoute({
  // ...
  loaderDeps: ({ search }) => ({ location: search.location }),
  loader: ({ context: { queryClient }, params: { brandSlug }, deps }) =>
    queryClient.ensureQueryData(
      deps.location === 'all' ? stopListAggregateQuery(brandSlug) : stopListQuery(brandSlug, deps.location),
    ),
});
```
Without `loaderDeps`, switching `?location` via the URL (e.g. browser back/forward, or a shared link) would serve a stale loader result until an unrelated navigation forces a re-run. [MEDIUM confidence — confirmed by official docs + a corroborating GitHub issue thread; no first-party test written in this session.]

### Anti-Patterns to Avoid
- **Duplicating the "brand's active locations" query in `catalog-drizzle.repository.ts`.** `LOCATION_REPOSITORY.listForBrand` already exists, is already exported, is already reachable from `CatalogModule`. A second, catalog-local implementation of the same query is exactly the kind of drift ADR-0020 warns about (two sources of truth for the same brand-location relationship).
- **Editing `location-scope.guard.ts` lines 67-82 to "fix" the `all` 403.** This is BLOCK-2 verbatim — the 403 at lines 39-45 (`location.context_required`) is a *different* code path than the pin-mismatch 404 at lines 67-70; the fix is `@LocationNeutral()` on the new endpoint, full stop.
- **Trusting a client-supplied `x-location-id` list for the aggregate.** There is no such list today (the aggregate takes zero location input), but if a future "compare two specific locations" feature is ever added, the location set must always be re-derived server-side from `LOCATION_REPOSITORY`/`MemberLocationScopeReader`, never accepted as an array in the request body/query.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Owner-only backend check | A new domain error class + `mapDomainError` case, or a scattered `if (baseRole !== 'owner')` per endpoint | `@OwnerOnly()` decorator + `OwnerOnlyGuard` throwing a bare `NotFoundException()` directly (guards in this codebase never route through `error-mapping.ts` — they throw NestJS exceptions directly, matching `location-scope.guard.ts`/`brand-scope.guard.ts`) | Guards are a different layer than services; domain-error mapping is for service-thrown errors caught in controllers, not guard-thrown HTTP exceptions |
| Brand's active-location list | A new SQL query in `catalog-drizzle.repository.ts` | `LOCATION_REPOSITORY.listForBrand(brandId, tenantId)` (tenancy context, already exported/imported) | Same data, same brand-RLS protection, zero new code |
| `?location` cross-page availability | Prop-drilling the search param through every route's loader args manually | TanStack Router's parent `validateSearch` + child `useSearch()` inheritance | Built-in mechanism for exactly this; already used once in this codebase (`menu/items.tsx`) for a smaller case |
| Cache-Control header on the aggregate | A new interceptor/middleware | `reply.header('Cache-Control', 'private, no-store')` inline in the controller, mirroring the exact call already used (with `'public, ...'`) in `public-menu.controller.ts:166-167` | One-line, existing pattern, no new abstraction needed for two routes |

**Key insight:** Every piece this phase needs (owner-only gate shape, brand-location resolution, search-param sharing, cache-header emission) has a near-identical existing pattern somewhere in this codebase or its direct dependencies. The main risk is inventing a parallel mechanism instead of finding and reusing the existing one — which is what BLOCK-1/BLOCK-2 already caught once for the guard itself.

## Common Pitfalls

### Pitfall 1: Guard execution order hides the real 403 cause
**What goes wrong:** `LocationScopeGuard`'s `location.context_required` 403 (lines 39-45) fires *before* the owner-bypass check (line 65) and *before* the staff-pin check (lines 67-70). A dev "fixing" the owner brand-global gap by touching the owner-bypass line will not even reach the code they're editing in a request that has no location context at all — the 403 already threw three lines earlier.
**Why it happens:** The guard's early-return order is neutral-checks → context-required-check → principal-checks → owner-bypass → staff-pin-check. Only `@LocationNeutral()`/`@BrandNeutral()` skip the context-required check; nothing else does.
**How to avoid:** Any endpoint that must work with no location context bound (aggregate reads, `all` mode) MUST be marked `@LocationNeutral()`. There is no guard-internal code path that exempts owners from the context-required check.
**Warning signs:** A 403 with `code: 'location.context_required'` in an e2e/manual test where the owner-bypass "should" apply — this is that same guard, wrong assumption about check order.

### Pitfall 2: `@BrandNeutral()` is a stronger bypass than its name implies
**What goes wrong:** Assuming `@BrandNeutral()` only exempts `BrandScopeGuard`, and that a `@BrandNeutral()`-only endpoint still needs `@LocationNeutral()` to avoid the location-context-required 403.
**Why it happens:** `LocationScopeGuard.canActivate` itself checks `BRAND_NEUTRAL_KEY` (line 32-37) and returns `true` immediately if present — brand-neutral implies location-neutral in this codebase's guard logic, by design (you cannot be location-scoped if you are not even brand-scoped).
**How to avoid:** When enumerating D-17's "every `all`-mode read," check for `@BrandNeutral()` at the class OR handler level first — if present, the endpoint is already safe and needs no `@LocationNeutral()` addition.
**Warning signs:** Adding `@LocationNeutral()` to an endpoint that already has `@BrandNeutral()` is harmless but redundant — a plan-checker reviewing decorator combinations should flag it as a signal the enumeration wasn't done carefully.

### Pitfall 3: `menu/stop-list.tsx`'s loader has no brand-global guard today
**What goes wrong:** Unlike the dashboard (`index.tsx`, which conditionally `enabled: activeLocationId != null`s its query), `menu/stop-list.tsx`'s `loader: ({ context, params }) => queryClient.ensureQueryData(stopListQuery(brandSlug))` runs unconditionally. An owner navigating directly to `/{brand}/menu/stop-list` while brand-global almost certainly hits the exact same `location.context_required` 403 as the dashboard bug, just via a code path STATE.md's "front-end gates the request off" note does not mention (it only describes the dashboard fix).
**Why it happens:** The 08.4 fix (commit 3590cd0) addressed the dashboard specifically; the dedicated stop-list page was not part of that fix's blast radius.
**How to avoid:** Both call sites (dashboard `TodaysWidget` + the dedicated stop-list page/table) need the `all`-branch treatment, not just one.
**Warning signs:** A browser smoke that only visits `/{brand}` (dashboard) in `all` mode and calls it done — the sibling `/menu/stop-list` route needs its own visit in the same smoke.

### Pitfall 4: `apiFetch` currently has no way to express "omit the header" vs "use this specific id" vs "use the session pin" as three distinct states
**What goes wrong:** `apiFetch` (api-client.ts:35,45) unconditionally reads `session.activeLocationId` and echoes it as `x-location-id` if it's a non-null string, for every caller, every role. There is no parameter today to override this. A naive fix that adds an optional `locationId` param but keeps the session-read as a fallback re-creates a two-source-of-truth bug identical to the one 08.4 already had for the owner pin (HIGH "two-source-of-truth" finding in the persona review).
**Why it happens:** `apiFetch` was written before location filtering existed as a client-side concept; it only ever needed to reflect the server-managed pin.
**How to avoid:** Make the caller (a single shared hook, not each query file) always pass the fully-resolved value; `apiFetch` becomes a dumb passthrough — `opts.locationId === 'all-or-undefined' → omit header`, `opts.locationId === <uuid> → set header`, and it should stop reading `session.activeLocationId` itself entirely once every call site is migrated. A staged migration risk: `catalog.ts`, `locations.ts`, `identity.ts`, `roles.ts`, `team.ts`, `tenancy.ts` all route through `apiFetch` — grep confirms it's the sole HTTP entry point for the admin app, so the blast radius is "every query/mutation function," but the change itself (add a parameter, stop reading session inside `apiFetch`) is mechanical.
**Warning signs:** Any code path where `x-location-id` is set from session AND a `?location` URL value exists but disagrees — that disagreement should be structurally impossible after the refactor (only one code path produces the header value), not "impossible in practice."

### Pitfall 5: Role-change mid-session leaves stale server-side pin state (persona LOW-11, now verified)
**What goes wrong:** `organizationHooks.afterUpdateMemberRole` (Better Auth, wired in Phase 3, `auth.config.ts:298-330`) fires on every role change but **only emits `identity.role_changed.v1` for audit** — it does not call `SessionActiveLocationWriter`/`SessionActiveBrandWriter` to reset or revalidate the session's pinned `activeLocationId`/`activeBrandId`. Verified by reading the hook body directly — no session/pin side effect exists.
**Why it happens:** The hook was built in Phase 3 purely for the audit trail (`IdentityRoleChangedV1` event); pin invalidation was never in that phase's scope.
**How to avoid (if 08.5 chooses to close this — it is Claude's Discretion per CONTEXT.md, not a locked decision):** Extend the hook to detect a demotion (`previousRole` included `owner`, `data.member.role` does not) and call the location/brand pin writers to reset to a safe default. This is a small, isolated addition to an existing hook, not a new mechanism.
**Consequence if left open:** A demoted owner→staff retains `activeLocationId: null` (owners never auto-pin) and hits the 404 wall (`activeLocationId === null` at `location-scope.guard.ts:68`) until they re-login and pick a location — annoying but fails closed (safe, not a security hole). A promoted staff→owner keeps their stale staff pin in session, but since 08.5 makes the owner's location authority the URL (not the session pin) and owners bypass the guard entirely, **the promoted-staff→owner case is actually neutralized as a side effect of 08.5's own design** — worth noting in the plan so it isn't mistaken for a new gap.
**Warning signs:** A support report of "I got demoted and now I see a blank dashboard until I log out and back in" — expected, not a bug, given the current fail-closed behavior; a report of a promoted user retaining their old location's data would be the actual regression to watch for.
