# Phase 08.5 Plan 03: Owner-only aggregate stop-list endpoint Summary

**GET /v1/catalog/stop-list/aggregate merges stop-list state across a brand's active locations behind @LocationNeutral + @OwnerOnly, with a single tenant-bound GROUP BY query and no new migration; GET /v1/catalog/stop-list now server-validates the resolved location against the active brand (D-10 existence-hiding 404).**

## Accomplishments

- Closed the documented 08.4 gap (c): an owner in brand-global (`all`) mode can now read a merged stop-list instead of 403'ing on `location.context_required`
- The new aggregate endpoint is backend-owner-only-gated (`@OwnerOnly()` from plan 01) on top of `@LocationNeutral()` — proved by e2e that a non-owner scoped to one location gets a bare 404 with zero other-location data in the response body (BLOCK-1 / D-09)

## Decisions Made

- Aggregate row type deliberately drops `reason` (present on the single-location `StopListEntryRow`) since per-location stop reasons can differ and a merged view has no single correct value to surface.
- Used `sql<string>` (not `sql<number>`) for the `COUNT(DISTINCT ...)` projection because postgres.js returns Postgres `bigint` as a JS string at runtime; typing it as `number` would have made the `Number()` conversion at the mapping boundary a silent no-op (caught by `@typescript-eslint/no-unnecessary-type-conversion` during commit, not by tsc).
- D-10's validation logic is shared conceptually (not code-shared) between `GetStopListService` and `GetStopListAggregateService` — both independently call `LOCATION_REPOSITORY.listForBrand` and filter to `status === 'active'`, since the aggregate needs the full active list (for M) while the single-location read only needs a membership check.
