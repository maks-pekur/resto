<domain>
## Phase Boundary

Rework admin **location selection** from the 08.4 server-session pin + relogin model into an **owner-only URL search-param filter** (`?location=all|<locationId>`) on the brand-scoped admin routes. Selecting a location is a client-side filter (update the search param + refetch), not a server pin round-trip.

**This phase delivers:**

1. **Owner URL filter** — `?location` drives what the owner sees; `x-location-id` on owner requests is derived from the URL, not the session pin.
2. **`all` aggregate** — when `location=all`, admin surfaces show a **merged summary across all of the brand's locations** (dashboard counters + today's stop-list). Requires **new backend aggregate endpoints** — this resolves the documented 08.4 gap (owner in brand-global mode currently 403s on the location-grain stop-list). A specific `?location=<id>` filters every surface to that location.
3. **Backend owner-only gate (NEW security primitive)** — the aggregate endpoints are `@LocationNeutral` and therefore bypass `LocationScopeGuard`; a real backend owner-only gate enforces decision D-02, because UI-only "owner-only" is a BOLA hole.
4. **Session-pin cleanup** — the owner's `session.activeLocationId` pin is retired (URL is the single source of truth for owners); the staff pin is preserved intact.

**Explicitly OUT of scope (deferred):**

- Staff free location switching — staff stay login-pinned to one location (08.4 D-10/D-11), change via re-login. The URL filter is owner-only.
- Per-location breakdown tables, cross-brand aggregate, trend analytics, an aggregate edge-ETag — not this phase (Phase 13 territory / YAGNI).
- Wiring `LocationPermissionChecker` as the live location-aware permission checker (08.4 gap) — 08.5 must NOT depend on it; wire-or-re-defer is a planner call (D-11).
- The admin order-feed itself (Phase 10). Order-based `all` counters exist only if/when there is a per-location order counter to aggregate (D-07).

</domain>

<decisions>
## Implementation Decisions

> Numbering note: these supersede the pre-discuss `08.5-DECISIONS-SEED.md`. Seed decisions 1/2/3/5 are preserved; **seed decision 4 is CORRECTED here (D-08)** after the persona reviews showed it mis-read the guard.

### Location filter model (product)

- **D-01 — Location = URL search param.** `?location=all|<locationId>` on the brand-scoped `/{brandSlug}/...` routes. Selecting a location updates the search param + refetches; no server pin round-trip. Parse `?location` with `z.union([z.literal('all'), z.string().uuid()])` at the edge — any other value falls back to the default (D-03).
- **D-02 — Owner-only.** The filter is exposed only to the owner. Staff do not get free location switching. **Enforcement is backend, not just UI (see D-09).**
- **D-03 — Default when `?location` absent → first location, alphabetical by name.** Fresh entry / deep-link without the param / refresh → the brand's first location by name (A→Я); `all` is opt-in for the owner. **FLAG (persona MED-9):** alphabetical is a _mutable_ home view — renaming a location moves the default. Founder chose alphabetical; personas recommend a stable key (oldest `created_at` or an explicit primary-location flag). Kept as founder chose; planner surfaces this if a real multi-location tenant appears. **Also document:** this is a behavior change from 08.4, where the owner landed brand-global (`activeLocationId = null` = all) — now a single location is the default and `all` is opt-in.
- **D-04 — Owner: URL is the single source of truth.** Server-side `session.activeLocationId` is no longer written/read for owners; the owner's `x-location-id` derives from `?location`. Between sessions the view resets to the default (no cross-session memory). Staff pin unchanged.

### `all` aggregate (product + scope)

- **D-05 — `all` = merged totals only, stop-list read-only.** Dashboard counters = one combined number across the brand's locations (no per-location breakdown). Stop-list = items stopped at _any_ location, each with a **"stopped at N of M locations"** badge. In `all` the stop-list is **read-only** — stop/unstop requires selecting a concrete location. The stop/unstop **write** endpoints stay location-scoped (`@RequireBrand`, full guard) — do NOT make them `@LocationNeutral`.
- **D-06 — N/M badge semantics.** M = **active (non-archived) locations at read time**; archived locations are excluded from both N and M; a stop row on an archived location does not count (archiving mid-day is allowed per 08.4 D-17).
- **D-07 — Aggregate scope at THIS phase = stop-list + existing catalog/stop-derived counters only.** The admin order feed is Phase 10; there is no per-location order counter to aggregate yet. Planner MUST state exactly what the `all` dashboard summarizes at MVP: if the dashboard renders order counts, either build an orders aggregate too OR render only stop-list-derived counters in `all` this phase — do NOT ship an `all` dashboard whose order counters silently render empty. No per-location drill-down, no cross-brand aggregate, no aggregate edge-ETag (YAGNI).

### Guard & backend security (CORRECTS seed D-4 — persona BLOCKs; MUST honor)

- **D-08 (CORRECTS seed D-4) — The owner filter change is PURELY CLIENT-SIDE; the guard's non-owner path is UNTOUCHED.** Owners already bypass at `location-scope.guard.ts:65` _before_ the pin-vs-request 404 at lines 67-70; that comparison is reached only by non-owners and is the STAFF isolation control (existence-hiding 404 + one-active-location, D-10/D-11). It MUST stay. The 08.4 owner-brand-global stop-list gap is a `location.context_required` **403** (guard lines 40-45), NOT a pin 404 — fixed by marking the new aggregate endpoints `@LocationNeutral()`, never by editing the guard's non-owner branch. Add/keep a guard regression test: staff `x-location-id ≠ pin → 404`; staff out-of-scope → 403.
- **D-09 (NEW — BLOCK-1) — Aggregate endpoints get an explicit backend owner-only gate.** Because `@LocationNeutral` bypasses `LocationScopeGuard`, and `BrandScopeGuard` admits any member reachable to the brand, owner-only MUST be enforced by a new backend primitive (an `@OwnerOnly()` guard/decorator, or an inline `if (principal.baseRole !== 'owner') throw new NotFoundException()` — 404 to preserve existence-hiding). NOT via brand scope. Hard acceptance criterion: e2e — non-owner (`menu:read`, scoped to location A) hitting `?location=all` gets 403/404 and **no other-location data** in the body.
- **D-10 (HIGH) — Owner single-location path validated server-side.** On a specific `?location=<id>`, the server validates that the resolved `x-location-id` belongs to the active brand and is not archived; existence-hiding **404** otherwise. The client-side fallback (D-18) is defense-in-depth, not the only line. The aggregate query MUST be ScopedTx/RLS tenant+brand-bound (ADR-0020 I-1) and filter to the resolved brand's locations only — never trust a caller-supplied location list.
- **D-11 (HIGH) — 08.5 does NOT depend on location-aware RBAC.** `PermissionsGuard` does not thread `activeLocationId`; the wired checker is tenant-wide; `LocationPermissionChecker` is built but not wired. All location confinement is `LocationScopeGuard` + the new owner-only gate (D-09). Do NOT design the aggregate assuming `@Permissions` is location-scoped. Planner: wire `LocationPermissionChecker` OR record an explicit re-defer decision — do not dangle it a third phase.

### Session-pin cleanup (HIGH-4 / MED-3 / MED-4)

- **D-12 — Exactly one location authority per role in `api-client.ts`.** Owner → URL (`?location`); staff → session pin; NO fallback between them. `?location=all` ⇒ omit `x-location-id` **and** call the aggregate endpoints; `?location=<id>` ⇒ `x-location-id=<id>` on location-scoped endpoints; staff ⇒ header comes from the server pin, ignore any URL param. Branch on the server-provided `isOwner` (already in the switcher props). (The guard, not the client, is the boundary for staff — a mis-derived client role is only a UX bug.)
- **D-13 — Retire the owner pin cleanly; keep the staff pin.** Remove only the _owner_ pin read/write; keep the staff login-pin write and the `set-active-location` staff branch intact. `resetActiveLocation` is shared owner+staff and is the exact code the 08.4-11 bug #2 fix repaired — do not regress it. Make owner pin writes an explicit no-op (or mark the owner `set-active-location` path staff-only) rather than a scattered deletion. Owner effective permissions derive from base-role `owner` (all permissions), so any future `LocationPermissionChecker` wiring skips owners.
- **D-14 (MED-4) — Disable the non-owner in-session brand switch.** Under staff login-to-brand (D-15), the non-owner `set-active-brand` path returns 403 rather than remaining a reachable staff brand-switch endpoint. Shrinking a reachable scope-mutation endpoint is a security win.

### Staff model (preserved from 08.4)

- **D-15 — Staff unchanged.** Login-pick-location interstitial → brand derived from the picked location → one active location → switch = re-login. Multi-brand staff scope is allowed; the pick-location interstitial **groups locations by brand**. Seed decision 6 ("session bound to one brand") is already satisfied by this model — no new mechanism.

### Caching & performance (MED-1 / MED-7)

- **D-16 — Aggregate off the edge cache; single query.** Aggregate endpoints emit `Cache-Control: private, no-store`, never `public`, and never route through the guest edge-cached availability handler (public, `stopVersion` ETag, `s-maxage=5` — a locked invariant per `apps/CLAUDE.md`). Implement the aggregate as a single set-based query (`WHERE location_id IN (<brand locations>) GROUP BY item_id`), not a per-location loop; add/confirm index `(brand_id, location_id, item_id)`; paginate the aggregate stop-list; O(1) queries regardless of location count.

### `all`-mode completeness (HIGH-5)

- **D-17 — No `location.context_required` white-screens in `all`.** Enumerate every read each dashboard/menu/stop-list page issues in `all` mode; each must have an aggregate or `@BrandNeutral`/`@LocationNeutral` variant. Mandatory: a **real browser/e2e smoke in `all` mode** asserting no request 403s (mocked-repo unit tests missed this exact bug class in 08.4 — see project memory "verify feature, not call shape").

### Silent fallback (MED-10)

- **D-18 — Invalid `?location` fallback is CLIENT-ONLY.** Invalid/archived/foreign `?location` → the client resets to the default (D-03), optionally a light toast. The server MUST still 403/404 an out-of-scope/cross-tenant location (default-deny + existence-hiding); never substitute the default server-side to soften the UI.

### Zero-locations

- **D-19 — Brand with zero locations (owner) → empty state + "create location" CTA.** Owner already has Locations CRUD from 08.4; the switcher is hidden; no default-location redirect. (Layout is Claude's discretion.)

### Claude's Discretion (research / planner)

- Exact form of the owner-only backend primitive (`@OwnerOnly()` decorator+guard vs inline check) — but it MUST return existence-hiding 404 and be unit- + e2e-tested (D-09).
- Exact SQL/Drizzle shape of the aggregate query, the index, and pagination (D-16).
- Whether to add a stable `brand.defaultLocationId` / primary-location flag now vs keep alphabetical (D-03 FLAG).
- Whether the owner `set-active-location` endpoint is removed vs marked staff-only (D-13).
- Whether to wire `LocationPermissionChecker` this phase or record a re-defer (D-11).
- Zero-locations empty-state layout (D-19).
- **Role-change mid-session (persona LOW-11):** confirm the Phase 3 `afterUpdateMemberRole` hook invalidates the session on role change (a demoted owner→staff has null `activeLocationId` → 404 until re-login; a promoted staff→owner leaves a stale pin). Verify, don't assume.

## Specific Ideas

- **Founder framing:** location becomes "just a dashboard filter" (URL search-param) for the owner — clean, shareable, no server round-trip. Staff stay tamper-proof and server-pinned (08.4 model), because the owner filter is client-side and the _guard_ remains the boundary.
- **This phase closes the documented 08.4 gap (c):** owner in brand-global mode currently 403s on the location-grain stop-list — resolved by the `@LocationNeutral` aggregate endpoints (D-08), not by touching the guard.
- **Security-first (matches 08.2/08.3/08.4 posture):** the owner-only property is enforced on the backend (D-09), not just the UI; the persona reviews are load-bearing acceptance criteria, not advisory.
