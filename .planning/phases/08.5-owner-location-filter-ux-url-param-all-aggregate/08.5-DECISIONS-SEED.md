# Phase 08.5 — Decisions Seed (pre-discuss)

Captured live with the founder on 2026-07-12, right after phase 08.4 completed.
These are LOCKED going into `/gsd-discuss-phase 08.5` — do not re-litigate; expand the rest.

## Motivation

The 08.4 model made the operator's active location a **server-managed session pin** changed
via `set-active-location` + reload (owner) or re-login (staff). The founder wants a cleaner
UX: location as a **URL search-param filter**, like any dashboard filter.

## Locked decisions

1. **Location → URL search param.** `?location=all|<locationId>` on the brand-scoped admin
   routes. Selecting a location is a client-side filter (updates the search param + refetches),
   not a server pin round-trip.

2. **Owner-only.** The location filter is exposed **only to the owner**. Staff do NOT get free
   location switching.

3. **`all` = aggregate.** When `location=all`, surfaces show a **summary across all of the
   brand's locations** (dashboard counters + today's stop-list). When a specific location is
   selected, dashboard / menu / stop-list / everything filters to that location.
   - Requires NEW backend **aggregate endpoints** for the `all` case (dashboard summary +
     stop-list across all locations). This directly **resolves the documented 08.4 gap**:
     an owner in brand-global mode currently 403s on the location-grain stop-list.
   - Brand-level data (menu items/categories/prices) is already brand-grain — `all` is a no-op
     filter for those; only location-grain data (stop-list, order/dashboard counters) needs
     the aggregate.

4. **Guard rework.** `LocationScopeGuard` currently throws existence-hiding 404 when the request
   `x-location-id` ≠ the session `activeLocationId` pin. On the **owner filter path** this
   session-pin-vs-request comparison must be **dropped** — the pure `member_location_scope`
   check (owner-bypass) remains the real gate. Security invariant unchanged: a non-owner still
   cannot reach a location outside their scope (403/404). SECURITY-SENSITIVE — persona-cto +
   persona-skeptic review required.

5. **Staff model preserved (08.4 D-10/D-11).** Staff stay **pinned to a single location**
   (pick-location at login, change only via re-login). No filter, no free switching for staff.

6. **Staff session scoped to one brand (login-to-brand).** A staff member's session is bounded
   to a single brand — "log in to a brand". (Founder addition 2026-07-12; flesh out the exact
   mechanism — brand chosen at login vs derived from their single scoped brand — in discuss.)

## Open questions for discuss

- `all`-aggregate: exact shape of the aggregate endpoints (per-location breakdown vs merged
  totals; how stop-list "stopped at N of M locations" reads).
- Search-param source of truth vs the existing `session.activeLocationId` — does the pin stay
  (owner) as a convenience default, or is it fully replaced by the URL for owners?
- `x-location-id` header now derived from the URL param on owner requests — how it coexists
  with the existing header-echo in `api-client.ts`.
- Staff single-brand-session mechanism (decision 6) — how brand is fixed for a staff session.
- Deep-link / refresh behavior; default when `?location` absent (→ `all`? → last used?).
