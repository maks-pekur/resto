# Phase 08.5 — Skeptic Review (pre-code)

**Reviewer:** persona-skeptic (adversarial)
**Date:** 2026-07-12
**Scope:** Owner location filter UX — URL search-param + `all`-aggregate. Security-sensitive (reworks `LocationScopeGuard` + the location-selection session model).
**Judged against:** OWASP API Security Top 10 (API1 BOLA, API3 BOPLA, API5 BFLA), the project's own existence-hiding-404 + ScopedTx/RLS double-enforcement invariants (`CLAUDE.md`), and the documented 08.4 known gaps (`STATE.md:270-275`).

I am not re-litigating the six locked decisions. I am attacking their **hidden assumptions and failure modes**. Two findings are BLOCK: the phase as framed introduces a cross-location read leak on the new aggregate, and the guard-rework instruction mis-describes the code in a way that invites a real security regression.

---

## BLOCK findings

### BLOCK-1 — The `all` aggregate endpoint has **zero location enforcement**; "owner-only" is a UI assumption, not a backend gate (OWASP API1/API5, BOLA/BFLA)

**Hidden assumption:** that "filter is owner-only" (decision 2) protects the aggregate data. It does not — that is a client-side affordance. The _endpoint_ must enforce it.

**Why it bites — the enforcement chain collapses for an aggregate:**

- Location isolation in this codebase rests on **exactly one** control: `LocationScopeGuard`. It gates on a _single_ `x-location-id` resolved into ALS (`location-scope.guard.ts:39`). An aggregate spans many locations, so it has no single `locationId` and **must** be marked `@LocationNeutral()` — at which point the guard short-circuits to `return true` (`location-scope.guard.ts:27-31`). The aggregate is, by construction, invisible to the only location gate that exists.
- The other guards do **not** fill the gap:
  - `PermissionsGuard` delegates to the **wired** `BetterAuthPermissionChecker` (`identity-core.module.ts:344-345`), which evaluates the member's **tenant-wide** BA role with **zero location concept** (`permission-checker.adapter.ts:23-50`; the location-aware `LocationPermissionChecker` is built but **NOT** wired — `STATE.md:274` gap (b)). A non-owner holding `menu:read` at their role passes.
  - `BrandScopeGuard` only checks brand reachability (`brand-scope.guard.ts:64-74`). A staff member scoped to location A of brand X **is reachable to brand X** (brands are derived from scoped locations, 08.4 D-04). So brand scope passes.
- Net result: a **non-owner** staff member scoped only to location A, holding `menu:read`, can call `GET /…/stop-list?location=all` (or the dashboard-summary aggregate) and receive stop-list / counter data for **locations B and C they have no scope to**. That is textbook **BOLA (API1)** + **BFLA (API5)**. Today the non-aggregate stop-list read is protected precisely because it is **not** `@LocationNeutral` (`catalog.controller.ts:401-403` has `@Permissions` but no `@LocationNeutral`, so `LocationScopeGuard` runs). The aggregate removes that protection.

**There is no reusable owner-only primitive to lean on** — a repo-wide search finds only inline `baseRole === 'owner'` checks (`location-scope.guard.ts:65`, `brand-scope.guard.ts:57`, services). No `@OwnerOnly` guard/decorator exists.

**Guardrail:**

1. Introduce an explicit backend **owner-only gate** for every aggregate endpoint (new `@OwnerOnly()` + guard, or an early `if (principal.baseRole !== 'owner') throw new NotFoundException()` — 404 to preserve existence-hiding). This is a **net-new security primitive** and must be unit- + e2e-tested; it is not "already there."
2. Belt-and-suspenders: the aggregate **query** must still be tenant+brand-bound under ScopedTx (see BLOCK-2 / HIGH-6) so RLS backs the app-layer check.
3. Add an e2e case: _non-owner (menu:read, scoped to A) → `?location=all` → 403/404, body contains no B/C data._ The 08.4 suite has no such case (`location-isolation.e2e.spec.ts:175-249` covers single-location scope only).

### BLOCK-2 — "Drop the session-pin-vs-request 404 comparison on the owner path" **mis-describes the guard**; a literal implementation is a security regression

**Hidden assumption:** decision 4 assumes there is an owner code path in `LocationScopeGuard` that performs the pin-vs-request comparison. **There isn't.** Owners `return true` at `location-scope.guard.ts:65`, _before_ the comparison. The comparison at lines **67-70** is reachable **only by non-owners**.

**Why it bites — deleting lines 67-70 (the only literal reading of "drop the comparison") regresses two invariants, both for staff:**

1. **Existence-hiding 404 → 403 leak.** Today, a non-owner sending an out-of-scope `x-location-id` hits `activeLocationId !== locationId → 404` at line 68 (the primary existence-hider). Remove it and the request falls through to the scope check, which returns **403** (`location-scope.guard.ts:77-82`) — leaking that the location _exists_. This violates 08.2 D-10 / the `CLAUDE.md` "existence-hiding 404 for out-of-scope reads" invariant, and directly breaks the pinned e2e assertion _"staff pinned to A requesting B … returns 404 (not 403)"_ (`location-isolation.e2e.spec.ts:177`).
2. **D-10/D-11 "one active location, switch = re-login" breaks.** For a **multi-location** staff member (scoped to A and B, pinned to A at login), lines 67-70 are what forbid reaching B without re-login. Remove them and staff can free-switch by editing `x-location-id` to any in-scope location — exactly the "staff no free switching" property decision 2/5 claims to preserve. The self-switch e2e (`location-isolation.e2e.spec.ts:230`) guards the `set-active-location` path but **not** a direct header swap, so this regression would pass CI.

**Guardrail:** The specific-location owner behavior needs **no guard change at all** — owners already bypass at line 65, and the client simply sources `x-location-id` from `?location` instead of the session pin. **Leave lines 67-70 intact for non-owners.** If the plan literally edits the guard, require: (a) the change be gated so it can never affect the non-owner branch, and (b) both e2e assertions above stay green. Re-word decision 4 in the plan to say "owner `x-location-id` moves from session-pin to URL **client-side**; guard non-owner path unchanged" — the current wording is an implementation trap.

## HIGH findings

### HIGH-3 — The phase silently depends on location-aware permissions that are **not wired**

`PermissionsGuard.canActivate` calls `hasPermission(principal, required, headers)` with **no `activeLocationId`** (`permissions.guard.ts:47`), and the wired checker ignores location entirely (`permission-checker.adapter.ts`). So **no** `@Permissions()` check in the system is location-scoped today. If any 08.5 design note assumes "the permission check will confine the aggregate/filtered read to the caller's location," that assumption is **false**. All location confinement is `LocationScopeGuard`-only. Make this explicit in the plan; do **not** design the aggregate on the belief that RBAC is location-aware. (Wiring `LocationPermissionChecker` is out of this phase's scope — and per `STATE.md:274` a blind swap would block all non-owner checks — so 08.5 must not quietly take a dependency on it.)

### HIGH-4 — Two-source-of-truth: the owner session pin is still **written and read** after decision 5 says it's dead

Decision 5 says `session.activeLocationId` is "no longer written/used for owners." But the code still:

- **writes** it on every brand switch for owner _and_ staff (`set-active-brand.service.ts:78-88`, shared `resetActiveLocation`), and on org-switch login (`auth.config.ts:414-431`); and
- **reads** it in the client for everyone and echoes it as `x-location-id` (`api-client.ts:35,45`).

If 08.5 changes only the _reader_ on the owner UI but leaves these writes/reads, a **stale pin can win over the URL**, silently showing/acting on the wrong location — the failure class the founder explicitly wants to avoid ("tamper-resistant, server-enforced… not client-forgeable," 08.4 specifics). Worse, `resetActiveLocation` is the exact code the 08.4-11 bug #2 fix repaired (`STATE.md:273`, commit db3624d); it is **shared** owner+staff, so naive surgery here can re-break the staff login-pin.

**Guardrail:** (1) exactly **one** authority per role in `api-client.ts` — owner → URL, staff → session pin — with **no fallback** between them; (2) keep the staff login-pin write (`auth.config.ts` hook) untouched; remove only the _owner_ read; (3) add a client test: an owner request carries the **URL's** location, never a stale `session.activeLocationId`; (4) decide explicitly whether owner brand-switch still calls `resetActiveLocation` (if the pin is dead for owners, that write is now dead code — see LOW-12).

### HIGH-5 — `all` mode + any location-required endpoint = white-screen 403 (repeat of the 08.4 bug that unit tests missed)

In `all` mode the client sends no single `x-location-id`; any endpoint that is **not** aggregate/brand-neutral throws `location.context_required` (`location-scope.guard.ts:40-45`). This is the **same failure class** as 08.4 prod bug #1 — "owner brand-global dashboard white-screen (location-less stop-list 403 crash)" (`STATE.md:273`) — which **unit tests missed because repos were mocked** (a recurring lesson in project memory: `tsc + vitest ≠ feature works`).

**Guardrail:** enumerate **every** read each dashboard/menu/stop-list page issues in `all` mode; each must have an aggregate or `@BrandNeutral` variant. Add a **browser/e2e smoke in `all` mode** (not mocked-repo unit tests) that asserts no request 403s. Without this, `all` ships broken the same way brand-global did.

### HIGH-6 — Owner-bypass forwards an **unvalidated** location into the query; the aggregate must stay ScopedTx-bound

`location-scope.guard.ts:65` returns `true` for **any** parseable `x-location-id` with no check that it belongs to the owner's tenant/brand (the header is a "client-echoed hint," `tenant-context.middleware.ts:83-84`). For single-location reads, RLS + composite FK catch cross-tenant. But the **aggregate is `@LocationNeutral`** — `getLocationId()` is undefined, so the guard never even looks at a location. If the aggregate service builds its own query, it **must** bind tenant + brand via ALS/`ScopedTx` (per the `CLAUDE.md` "no raw SQL outside packages/db" + double-enforcement invariants) and filter to the resolved brand's locations only. An aggregate that trusts a caller-supplied brand/location list, or drops the tenant filter, re-opens the exact hole 08.4 bug #2 exposed (a missing ADR-0020 I-1 tenant filter, `STATE.md:273`).

## MED findings

### MED-7 — Aggregate fan-out under the Friday spike; do NOT reuse the edge-cached availability path

The public availability read is cookie-free, `Cache-Control: public`, `stopVersion` ETag, `s-maxage=5` (`apps/CLAUDE.md` menu-caching rule). The owner aggregate is **authenticated and per-owner** — it must be `private`/`no-store` and must **not** be served from, or pollute, that edge-cached path (leaking one owner's aggregate to a CDN key). Also: implement the aggregate as a **single set-based query** (`GROUP BY location_id`), not a per-location loop — a fan-out of N queries per owner poll on a Friday spike is the "no per-tenant noisy-neighbor" violation the perf constraint forbids. Do **not** over-build an edge ETag for the aggregate (YAGNI at MVP; short client staleness is fine).

### MED-8 — "N of M" badge is under-specified when M changes

"Stopped at N of M locations" — define M as **active (non-archived) locations at read time**, and exclude archived locations from both N and M. Otherwise archiving a location mid-day (allowed, 08.4 D-17) makes M drift, and a stop row on an archived location can produce `N > M` or a stale badge. Decide explicitly: does a stop at an archived location count? (Recommend: no.)

### MED-9 — "Alphabetical first location" default is a **mutable** home view

Decision 6 defaults to the first location by name. Renaming a location silently **moves the owner's default landing view** — and any action taken there (dashboard counters, future order actions). Use a **stable** key (oldest `created_at`, or an explicit "primary location" flag), not mutable display name. Also note this is a **behavior change from 08.4**, where the owner landed **brand-global** (`activeLocationId = null` = all locations); 08.5 makes a _single_ location the default and `all` opt-in. Confirm that flip is intended and document it — it changes owner muscle memory and is the kind of silent UX drift that surprises the first real operator.

### MED-10 — Silent fallback must be **client-only**; it must never mask a server authorization decision

Decision 8 ("invalid/archived/foreign `?location` → silent fallback to default") is safe **only** as a client UX behavior. The **server must never** substitute the default for an out-of-scope location — that would mask a 403/404 and defeat default-deny + existence-hiding. Concretely: the guard/aggregate must still 403/404 a non-owner (or cross-tenant) location; the _client_ may then navigate to the default. Owner vs non-owner fallback should differ: for an owner a foreign/archived id is genuinely just "reset to default"; for a non-owner a silent client fallback that hides a real permission error is acceptable **only** because the server already denied — never move the fallback server-side to make the UI "nicer."

## LOW / NOTE

- **LOW-11 — Role change mid-session.** `baseRole` is looked up live per request (`auth.guard.ts:144-147`, `156-174`), but the session pin persists. A demoted owner→staff has a null `activeLocationId` (never written for owners) → `404` on every location route until re-login (`location-scope.guard.ts:67-70`). A promoted staff→owner leaves a stale pin. Verify the Phase 3 `afterUpdateMemberRole` hook invalidates the session on role change; if it does, this is moot — confirm it, don't assume it.

- **LOW-12 — Dead code / latent inconsistency.** If owners no longer use the pin, the owner branch of `SetActiveLocationService` (`set-active-location.service.ts:34-55`), the `POST /v1/me/set-active-location` owner path, and `location-switcher.tsx:36-47` become dead for owners — yet the endpoint still **mutates** a session field that is now "not used." Either remove the owner path or explicitly mark the endpoint staff-only; leaving a live, writable, "unused" session pin is exactly the ambiguity that produced HIGH-4.

- **NOTE-13 — Scope clarity on the dashboard aggregate.** No dashboard/counters endpoint exists yet, and orders currently expose only create + public status (`orders.controller.ts:41,52`) — the location-scoped **admin order feed is Phase 10**. So "dashboard counters aggregate" (decision 3) may have **no per-location non-aggregate counterpart** to aggregate over yet. Clarify precisely what the `all` dashboard summarizes at MVP: if the counters are meant to include order counts (order data is location-grain, 08.4 D-03), an **orders aggregate must be built too** — do not ship a stop-list-only aggregate while the dashboard's order counters silently render empty in `all`. If counters are only stop-list-derived at this phase, say so in the plan.

- **NOTE-14 — Over-engineering check (the aggregate is justified).** The aggregate is **not** over-built: it directly resolves the documented 08.4 gap (c) owner-brand-global stop-list 403 (`STATE.md:274`), and merged totals are the minimum needed. Keep it minimal: **no** per-location drill-down breakdown, **no** cross-brand aggregate, **no** edge ETag this phase. The only thing that must be _added_ beyond the happy path is the owner-only backend gate (BLOCK-1) — that is not gold-plating, it is the load-bearing control.

---

## Verdict

**CONDITIONAL — proceed only after the plan (a) adds an explicit owner-only backend gate on every `all`/aggregate endpoint with a non-owner `?location=all` 403/404 e2e (BLOCK-1), and (b) re-frames the guard rework as a client-side header-source change, leaving the non-owner pin-vs-request 404 comparison intact, with the two existing existence-hiding/self-switch invariants pinned by test (BLOCK-2).** HIGH-3/4/5/6 must have named owners and tests before code; the aggregate itself is the right call, but as currently framed it converts the system's single location-isolation control into an opt-out and would ship a cross-location read leak.
