## Summary

Reviewed the diff between `1431681` and `HEAD` for the owner-only guard, the new cross-location
stop-list aggregate read, the retirement of the owner server-side location pin (D-13/D-14), and the
admin client's location-authority split (D-12).

**The core BFLA/BOLA boundary holds up under adversarial tracing.** `OwnerOnlyGuard` runs after
`AuthGuard → PermissionsGuard → BrandScopeGuard → LocationScopeGuard` (declaration order in
`identity-http.module.ts`, which is also NestJS's execution order for `APP_GUARD` providers
registered in a single array), fails closed on a missing/non-owner/anonymous/customer principal, and
throws a bare `NotFoundException` (no `{code,message}` body) — verified against
`owner-only.guard.spec.ts`. The aggregate query (`listStopListAggregateAcrossLocations`) is driven
exclusively by `tenantId` (from `requireTenantContext()`) and a server-resolved active-location-id
list (`LocationRepository.listForBrand(brandId, tenantId)` filtered to `status === 'active'`), never
by client input, and every raw-`tx` query in the new repository method carries an explicit
`eq(table.tenantId, tenantId)` filter on top of the `withTenant` RLS binding, per ADR-0020 I-1. The
aggregate route sets `Cache-Control: private, no-store` and is confirmed off the public edge cache
(`stop-list-aggregate.e2e.spec.ts` D-16). Client-side, a non-owner's `useEffectiveLocation()` ignores
the `?location` search param entirely (mode is derived solely from the server session pin), so a
malicious `?location=all` in a staff member's address bar never even triggers the aggregate query
client-side, and would 404 server-side regardless.

No Critical or High findings on the primary threat model. The findings below are Warning-level:
one deliberate-but-underspecified layering/consistency defect, one silent-truncation correctness bug,
one functional lock-in regression caused by the interaction of this phase's D-14 change with
pre-existing (08.4) session-pin resolution logic, and three lower-impact client-side robustness gaps.

## Warnings

### WR-01 ✅ RESOLVED (80529b8): Aggregate stop-list query silently truncates at 50 items with no total/pagination signal

**File:** `apps/api/src/contexts/catalog/infrastructure/catalog-drizzle.repository.ts:1291-1293`
**Issue:** `listStopListAggregateAcrossLocations` hardcodes `.limit(50).offset(0)` on the
`GROUP BY item_id` query, and neither `AggregateStopListResponseSchema` (`dto.ts`) nor
`GetStopListAggregateService.execute()` surfaces a `total`/`hasMore` field. The per-location sibling,
`listStopListWithStoppedAt` (same file, line 1220), is unbounded — it returns every stopped item for
a single location with no cap. Once a brand's combined stop list across all active locations exceeds
50 distinct items, the owner's `all`-mode dashboard/stop-list page silently drops entries: the
"today's 86 count" widget (`aggregateResult.data.items.length`) undercounts, and items stopped beyond
the 50th (ordered by `max(stoppedAt) DESC`, so the *oldest* stops are the ones dropped) simply vanish
from the view with no indication anything was cut.
**Fix:** Either return `total` (a `count(distinct item_id)` alongside the paged rows) and wire
pagination through the controller/DTO/FE the same way `listItemsService` already paginates, or, if 50
is judged sufficient for MVP scale, document the cap as an explicit product decision and expose an
"and N more" affordance in `StopListAggregateTable` instead of a silent drop:
```ts
// dto.ts
export const AggregateStopListResponseSchema = z.object({
  items: z.array(AggregateStopListEntrySchema),
  totalActiveLocations: z.number().int().nonnegative(),
  totalStoppedItems: z.number().int().nonnegative(), // NEW
});
```

### WR-02: D-14's blanket non-owner `set-active-brand` 403 removes the only self-service fix for a pre-existing brand/location pin mismatch, locking multi-brand staff out of their second brand

**File:** `apps/api/src/contexts/identity/application/set-active-brand.service.ts:42-44`
**Issue:** `SetActiveBrandService.execute()` now throws `NonOwnerBrandSwitchForbiddenError` for every
non-owner call, unconditionally — the previous `findReachableBrandsForMember` scope check (which let
a legitimately-scoped staff/admin member switch to a brand they hold `member_location_scope` rows in)
is gone entirely. Tracing the chain this closes off:
- `onInitialBrandPin` (`identity-core.module.ts:302`) deterministically resolves a non-owner's
  session `activeBrandId` at sign-in to the **earliest-created** brand they have any active-location
  scope in (`initial-brand-drizzle.repository.ts:29-50`, `orderBy(asc(brands.createdAt))`,
  `.limit(1)`) — independent of which brand the member actually intends to work in.
- `GET /v1/me/locations` (`set-active-location.controller.ts:112-139`, used by both the admin's
  `pick-location.tsx` login interstitial and `use-effective-location.ts`'s `meLocationsQuery()`) is
  scoped to `req.activeBrandId` — i.e. that same auto-picked brand.
- `BrandScopeGuard` (`brand-scope.guard.ts:59-62`) 404s any non-owner request whose
  `x-brand-slug`-resolved brand doesn't match `req.activeBrandId`, regardless of whether the member's
  `member_location_scope` actually covers that brand.

For a staff/admin member whose location scope spans two brands (explicitly called "allowed" by this
phase's own D-15 decision), `pick-location.tsx` can therefore never surface, and the member can never
select, a location belonging to any brand other than the one `onInitialBrandPin` happened to pick —
and since `set-active-brand` now 403s unconditionally for non-owners, there is no client-driven
recovery. Re-login re-runs the identical deterministic resolution and lands on the same brand every
time. This contradicts D-15's stated behavior ("the pick-location interstitial groups locations by
brand") — the interstitial's data source is single-brand-scoped, not grouped-by-brand. This is a
fail-closed functional lockout (not a data leak), but it makes a documented-as-supported scenario
unreachable with no operator-facing error message explaining why, and no admin-side remedy short of
manually editing `member_location_scope`/re-provisioning the member.
**Fix:** Either (a) make `GET /v1/me/locations` (or a new endpoint) tenant-wide for the
pick-location flow specifically, grouped by brand as D-15 claims, and have `pick-location.tsx`'s
selection also correct `activeBrandId` to match the chosen location's brand (a small, scoped write
path distinct from the general-purpose `set-active-brand` endpoint D-14 intentionally closed); or
(b) if multi-brand staff scoping is not actually meant to be supported yet, correct the D-15 record
and add a guard rail (e.g. reject `member_location_scope` writes across >1 brand for non-owners) so
the inconsistency can't be silently created in the first place.

### WR-03: Application-layer `NotFoundException` in `GetStopListService` bypasses the domain-error/`error-mapping.ts` convention

**File:** `apps/api/src/contexts/catalog/application/get-stop-list.service.ts:29-31`
**Issue:** Per this codebase's documented error-handling convention, application-layer services throw
typed domain errors from `domain/errors.ts`, and `interfaces/http/error-mapping.ts`'s
`mapDomainError`/`mapCatalogError` translates them to `HttpException` subclasses — `mapCatalogError`
here explicitly returns `unknown` errors unchanged (`error-mapping.ts:118-121`), so a bare
`NotFoundException` thrown from the application layer "happens to work" only because it's already an
`HttpException`. This is the exact pattern the plan-checker flagged for plan 03. Functionally this is
fine as an existence-hiding check (equivalent intent to `OwnerOnlyGuard`'s bare 404), and there is one
pre-existing precedent elsewhere (`start-brand-onboarding.service.ts`), but it is inconsistent with
the sibling `LocationOutOfScopeError` pattern already used one file over
(`identity/domain/errors.ts:29-36`) for the identical "location not in caller's scope" concept, and it
couples the catalog application layer to `@nestjs/common`, which the rest of `catalog/application/*`
avoids.
**Fix:** Add a catalog-context domain error (e.g. `LocationOutOfBrandScopeError extends
CatalogDomainError`) and map it in `mapCatalogError` to `NotFoundException` with no body, mirroring
`OwnerOnlyGuard`'s existence-hiding contract:
```ts
// catalog/domain/errors.ts
export class LocationOutOfBrandScopeError extends CatalogDomainError {
  constructor() { super('catalog.location_out_of_brand_scope', 'Location is not in scope.'); }
}
// error-mapping.ts
case 'LocationOutOfBrandScopeError':
  return new NotFoundException();
```

### WR-04 ✅ RESOLVED (d074288): `?location` search schema throws instead of gracefully degrading on invalid values, contradicting its own comment

**File:** `apps/admin/src/routes/(protected)/$brandSlug/_layout.tsx:17-22`
**Issue:** The comment states "Any value outside this union is dropped by zod at the edge, leaving
`location` undefined." That is not what happens: `locationSearchSchema` is passed directly as
`validateSearch`, and the installed `@tanstack/router-core` (`router.js:1066-1075`) calls the zod
schema's Standard-Schema `~standard.validate`, which throws `SearchParamError` on any value that
isn't `'all'` or a UUID (verified in `node_modules/.pnpm/@tanstack+router-core@.../router.js:297-298,
871-888` — on failure the router sets `strictMatchSearch = {}` and attaches `searchError` to the
match rather than silently coercing to `undefined`). A stale bookmark, a shared link with a typo, or a
bot probing `/$brandSlug?location=garbage` gets a router error state instead of the intended D-03
default-location fallback. This also deviates from this codebase's own established tolerant
search-param pattern used one file over for the identical problem
(`apps/admin/src/lib/menu/zod-schemas.ts:37-42`, `coerceStatusFilter`, which defaults on any
unrecognized value instead of throwing).
**Fix:** Match the established pattern — use `.catch(undefined)` (zod) or a manual coerce function:
```ts
const locationSearchSchema = z.object({
  location: z.union([z.literal('all'), z.string().uuid()]).optional().catch(undefined),
});
```

### WR-05: `useEffectiveLocation()` reports `mode: 'none'` for an owner while `meLocationsQuery()` is still loading, not only when locations are actually empty

**File:** `apps/admin/src/lib/hooks/use-effective-location.ts:38,52,89`
**Issue:** `meLocationsQuery()` is a plain `useQuery` (not suspense), so on first render for an owner
its `data` is `undefined`. `activeLocations` then defaults to `[]` (line 38) and `defaultLocation` is
`undefined` (line 52), so `needsFallback` is `false` and the function falls through to the final
`return { mode: 'none', locationId: undefined }` (line 89) — the same terminal state used for a
confirmed zero-location owner (D-19). This is indistinguishable from "no locations exist," so every
cold load of `$brandSlug`, `$brandSlug/menu/items`, and `$brandSlug/menu/stop-list` for an owner who
does have locations briefly renders the D-19 empty state (`index.tsx`) or disables the stop/unstop
toggle (`items.tsx`) until the query resolves.
**Fix:** Distinguish "loading" from "confirmed empty" using the query's status, e.g.:
```ts
const { data: locationsResult, isPending: locationsPending } = useQuery({ ...meLocationsQuery(), enabled: isOwner });
// ...
if (isOwner && locationsPending) return { mode: 'single', locationId: undefined }; // or a dedicated 'loading' mode
```

### WR-06: Empty-string `x-location-id` header is reachable in principle from `ItemsTable`'s stop/unstop mutation

**File:** `apps/admin/src/components/menu/items-table.tsx:92`
**Issue:** `toggleMutation`'s `mutationFn` always evaluates `stopListLocationId ?? ''`, so if
`toggleMutation.mutate(...)` were ever invoked without going through `handleToggleStop`'s
`!canToggleStopList` guard (e.g. a future refactor that adds another call site, or a
programmatically-triggered `Switch.onCheckedChange` bypassing the `disabled` prop via testing
utilities/automation), `apiFetch` would receive `locationId: ''`. Since `'' !== undefined && '' !==
'all'`, `apiFetch` (`api-client.ts:48-50`) would attach `x-location-id: ''` to the request. The
backend's `resolveLocationHeader`/`TenantContextMiddleware` treats a falsy header value as absent
(`locationId ? { locationId } : {}`), so this is currently harmless (fails to `location.context_required`,
not an information leak), but the safety property lives entirely in the *caller* disabling the UI, not
in the mutation itself refusing to run.
**Fix:** Guard at the mutation boundary, not only the click handler:
```ts
const toggleMutation = useMutation({
  mutationFn: ({ itemId, next }: { itemId: string; next: 'paused' | 'published' }) => {
    if (stopListLocationId === undefined) return Promise.reject(new Error('no active location'));
    return toggleStopList(brandSlug, itemId, next, stopListLocationId);
  },
  ...
});
```
