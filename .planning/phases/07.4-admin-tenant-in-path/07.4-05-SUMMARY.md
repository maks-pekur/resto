**Vite serves the admin SPA under `/admin/`, the router's `basepath: '/admin'` is proven against the real route tree (not the `.d.ts`) with a router built directly from an extracted `route-tree.ts` module, and the two absolute navigations that used to bypass `adminPath()` — the expired-session redirect and the password-reset link — now compose under whatever base is configured.**

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The plan's literal negative test case is empirically false; TanStack Router's `basepath` does not reject unprefixed pathnames at match time**

- **Found during:** Task 1, writing the RED transcript for the fifth `router-basepath.spec.ts` case ("does not resolve the same path without the base").
- **Issue:** The plan specified: build a router with `basepath: '/admin'` and a `createMemoryHistory({ initialEntries: ['/dashboard'] })`, then assert no match to the dashboard route. Read from the `.d.ts` at plan-write time, never run. Running it against the real `routeTree` (`@tanstack/router-core@1.171.13`) showed the assertion is false in **both** configurations:
  ```
  $ pnpm --filter admin exec vitest run test/__scratch-basepath-probe.spec.ts
  UNPREFIXED /dashboard with basepath /admin -> matches: ["/","/dashboard"]
  PREFIXED /admin/dashboard with basepath /admin -> matches: ["/","/dashboard"]
  ```
  Reading `node_modules/.pnpm/@tanstack+router-core@1.171.13/.../dist/esm/rewrite.js`'s `rewriteBasepath.input`: it strips the prefix only when the pathname starts with it; when it doesn't, it returns the URL **unchanged**, and the router then matches that literal pathname against the tree. Since `/dashboard` is a real registered route independent of any basepath, it matches regardless. `basepath` is an output/href-composition option, not an input access boundary — confirmed by a second probe:
  ```
  WITH basepath buildLocation href: /admin/dashboard
  WITHOUT basepath buildLocation href: /dashboard
  NEG: matches for bare /dashboard under basepath /admin: ["/","/dashboard"]
  ```
- **Fix:** Replaced the fifth case with an assertion that **is** load-bearing and does distinguish the two configurations: `router.buildLocation({ to: '/dashboard' }).href` must equal `/admin/dashboard` with `basepath` configured, and must not with it omitted. This is the actual mechanism T-07.4-05-05 ("basepath silently ignored") needs to catch — a future refactor that drops `basepath` would break every generated in-app link, which this case now catches; it would not have broken the plan's literal (always-true) negative assertion.
- **Files modified:** `apps/admin/test/router-basepath.spec.ts`
- **Verification:** RED transcript below (all 5 cases fail with `basepath` removed from the test's `createRouter` call, including the corrected fifth case); GREEN transcript with it restored.
- **Committed in:** `156aef16`

**2. [Rule 1 - Bug] The first positive case initially passed for the wrong reason — an accidental collision with the `/$locationSlug` catch-all**

- **Found during:** Task 1, the first RED run (basepath removed): "resolves the dashboard deep link" passed even without `basepath`, while the other three matching cases correctly failed.
  ```
  ✓ resolves the dashboard deep link
  × resolves a nested deep link
  × resolves a parameterised deep link
  × resolves the auth deep link
  × composes a base-prefixed link...
  ```
- **Issue:** `apps/admin/src/routes/(protected)/index.tsx`'s sibling route `/$locationSlug` matches any first path segment. Without a rewrite stripping the `/admin` prefix, the router treated `admin` as a candidate location slug; the test's `apiFetch` mock hadn't handled `/v1/me/locations` explicitly, so it fell through to the mock's generic `/v1/me` branch and returned an operator object with no `.locations` field. `resolveLocationRoute([], 'admin', ...)` then took its `no-locations` branch, which — like the dashboard route itself — redirects to `/dashboard`. Two different mechanisms landing on the same URL made the RED run pass by coincidence, which is precisely the "verifier that cannot fail" failure mode the standing rule warns about.
- **Fix:** Added an explicit `/v1/me/locations` branch to the test's `apiFetch` mock returning one real location (`slug: 'podil'`), so an unmatched `admin` slug takes `resolveLocationRoute`'s `redirect` branch (to `/podil/dashboard`) instead of `no-locations` (to `/dashboard`) — the two branches are no longer aliased to the same URL, and the dashboard case now genuinely depends on `basepath` stripping.
- **Files modified:** `apps/admin/test/router-basepath.spec.ts`
- **Verification:** Corrected RED transcript below shows all 5 cases genuinely fail without `basepath`.
- **Committed in:** `156aef16`
