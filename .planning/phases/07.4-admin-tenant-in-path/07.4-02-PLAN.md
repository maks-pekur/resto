<objective>
Delete the browser's ability to name a tenant. `apps/website/lib/checkout-api.ts:80` sets
`x-forwarded-host` from `window.location.host` on every call — including `POST /v1/orders` — and
`effectiveHost()` honours it whenever `TRUST_PROXY` is non-empty, which is always in production.

Purpose: that is a client-controlled tenant selector on the order-creation path. Under one apex the
call is same-origin, so the header is not merely dangerous, it is unnecessary. Deleting it is the
root fix (07.4-CONTEXT D-03).

Output: browser calls go to root-absolute same-origin paths with no tenant header; the one
legitimate server-side sender keeps its header and gains the confirmation page's read; a committed
test fails if the header reappears in client code.
</objective>

`process.env.NEXT_PUBLIC_API_ORIGIN` and throws when unset. The private `apiFetch` is:

    async function apiFetch<T>(path, init, signal?, host?): Promise<T> {
      const resolvedHost = host ?? (typeof window !== 'undefined' ? window.location.host : '');
      const { headers: _ignored, ...rest } = init;
      const res = await fetch(`${getApiOrigin()}${path}`, {
        ...rest,
        signal: signal ?? AbortSignal.timeout(30_000),
        headers: { 'Content-Type': 'application/json', 'x-forwarded-host': resolvedHost },
      });
      ...
    }

Three exported callers, all built on it:

    export const createOrder = (input, signal?) => apiFetch<CreateOrderResponse>('/v1/orders', { method: 'POST', body: JSON.stringify(input) }, signal);
    export const createPaymentIntent = (orderId, signal?) => apiFetch<CreatePaymentIntentResponse>('/v1/checkout/payment-intent', { method: 'POST', body: JSON.stringify({ orderId }) }, signal);
    export const getOrderStatus = (orderId, signal?, host?) => apiFetch<OrderStatusResponse>(`/v1/orders/${orderId}/status`, { method: 'GET' }, signal, host);

`getOrderStatus` is the only one with two consumers: `components/checkout/order-status-poller.tsx:76`
calls it in the browser as `getOrderStatus(orderId)`, and

`getOrderStatus(orderId, undefined, host)` where `host` came from `await headers()`. That third
argument is the only reason the `host` parameter exists.

`apps/website/lib/api-client.ts` is the legitimate server-side pattern and the model to follow. It

<constraints>
- **`apps/website/lib/api-client.ts`'s two existing `x-forwarded-host` sends stay.** That file is
  `server-only` and forwards the *real inbound Host* during SSR. It is not the same thing as the
  browser naming a host, and deleting it would break tenant resolution for every server-rendered
  page (07.4-CONTEXT D-03).
- **Do not touch `infra/docker/Caddyfile`.** The `header_up X-Forwarded-Host {host}` pin is phase
  7.5's, and this plan is its prerequisite, not its peer.
- **Handoff that must not be lost:** once the browser calls `/v1/*` same-origin, production correctness
  depends on Caddy's `{$WEBSITE_HOST}, *.{$WEBSITE_HOST}` site block routing `/v1/*` to `api:3000`.
  That `handle` block is a phase 7.5 plan-06 edit and does **not** exist yet. There is no live
  production to break — go-live is 7.5 — but 7.5 must not reach its smoke without it. State this in
  the SUMMARY under `## Handoff to 7.5` in one sentence.
- No new package is installed by this plan.
- Comments: zero, except one ≤2-line WHY on the dev-only rewrite explaining that Caddy owns `/v1/*`
  in production so the rewrite must not exist there.
</constraints>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| guest browser → API | `POST /v1/orders`, `POST /v1/checkout/payment-intent`, `GET /v1/orders/:id/status`. Today the browser chooses the tenant by setting `x-forwarded-host` |
| Next.js SSR → API | server-side reads that must forward the *real* inbound `Host` so the storefront resolves its own tenant |
| Caddy → API | in production, `X-Forwarded-Host` reaching `api:3000` should be set by the proxy, not by anyone upstream of it |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07.4-02-01 | Spoofing | `checkout-api.ts` `apiFetch` | mitigate | Delete `x-forwarded-host` and the origin prefix; calls become same-origin root-absolute paths, so the tenant is the host the guest actually visited. Measured defect: research Pitfall 11 / M-07 shows Caddy forwards a client-supplied value verbatim under the committed `trusted_proxies static 0.0.0.0/0 ::/0` |
| T-07.4-02-02 | Spoofing | regression of the above | mitigate | `no-client-tenant-header.spec.ts` fails if any file outside the `server-only` module contains the header, and fails if that module stops being `server-only` |
| T-07.4-02-03 | Information Disclosure | `fetchOrderStatus` SSR caching | mitigate | `cache: 'no-store'`. An order status is per-request state; a shared revalidation cache keyed only on URL could serve one guest's status to another |
| T-07.4-02-04 | Tampering | dev `rewrites()` leaking into production | mitigate | Rewrite is gated on `NODE_ENV !== 'production'`. In production a `/v1/*` request that reaches Next must 404 loudly rather than hairpin, so a missing Caddy `handle` block is visible at the smoke |

| T-07.4-02-SC | Tampering | npm/pip/cargo installs | n/a | This plan installs nothing |
