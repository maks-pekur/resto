# 07.4-06 — API env collapses to a single apex

Executed by the orchestrator after the assigned executor hit a session rate limit mid-task. It had
completed Task 1's RED observation and part of the `env.schema.ts` edit; everything from there on
was finished by hand, with the same RED-before-GREEN discipline.

## Task 1 — the cookie goes host-only, the per-tenant admin origin is deleted

`AUTH_COOKIE_DOMAIN` left the required-outside-dev list, so a production boot with the key absent
now succeeds and Better Auth omits `Domain` entirely — a host-only cookie that reaches the apex and
nothing else. That is **narrower** than the `.admin.<apex>` value it replaces. The leading-dot shape
rule survives for anyone who deliberately sets one, and its message no longer advises a dotted admin
host.

`ADMIN_WEB_ORIGIN_WILDCARD` is gone from the schema, the identity module, `.env.example`,
`infra/docker/env/api.env.example`, `local-prod-rehearsal.sh` and `assert-hostname-depth.sh`. The
only surviving mention outside `.planning/` is the spec that asserts a stale value left in a `.env`
on a box has no effect.

`admin-origin-wildcard.spec.ts` deleted — its subject no longer exists.

## Task 2 — one module owns every admin deep link

`apps/api/src/shared/admin-links.ts` is new: `adminLink()`, `adminOrigin()`, and the two paths the
API actually emits (`ADMIN_ACCEPT_INVITATION_PATH`, `ADMIN_PAYOUTS_PATH`).

`grep -rl 'ADMIN_WEB_URL' apps/api/src` now returns **exactly three files** — `env.schema.ts`,
`prod-guardrails.ts`, `admin-links.ts`.

## RED before GREEN

- **Task 2's helper.** The spec was written and run before `admin-links.ts` existed:
  `Cannot find module '../../../src/shared/admin-links'`, 1 file failed. Then green.
- **The trusted origin.** `new URL('https://restos.pp.ua/admin').origin` is asserted to be
  `'https://restos.pp.ua'`. Better Auth compares a non-wildcard trusted origin as
  `pattern === getOrigin(url)` (`better-auth@1.6.30 dist/auth/trusted-origins.mjs`), so the unfixed
  value could never match and every mutating admin request would have been rejected as untrusted.
- Final: 20 unit tests green across three specs, 9 e2e green across `identity-invitation` and
  `tenant-onboarding`, `tsc --noEmit` clean, `eslint` clean on all three changed source files.

## Pre-existing defects fixed in passing

**1. Three dead admin URLs, dead since the 7.6 Vite migration.**
`start-tenant-onboarding.service.ts:212` built `${ADMIN_WEB_URL}/payouts`, and both
`STRIPE_CONNECT_RETURN_URL` and `_REFRESH_URL` defaulted to `http://localhost:3001/stripe/{return,refresh}`
— a dead route on a stale port. `find apps/admin/src/routes -iname '*payout*'` returns exactly
`(protected)/tenant.payouts.tsx`, so the only real route is `/tenant/payouts`. All three repointed.
`tenant.payouts.tsx` declares no `validateSearch` (verified by reading it), so the `?stripe=return`
marker is inert today and preserves the distinction for whoever builds a real landing route.

**2. A test the 7.5 work left red.** `identity-boot-integration.spec.ts`'s staging fixture set
`RESEND_FROM: 'RestOS <noreply@resto.app>'` / `RESEND_REPLY_TO: 'support@resto.app'` — which
`07.5-06` added to the prod-guardrail **dev-default set**, so a production boot must now refuse
exactly those literals. Confirmed pre-existing by stashing this plan's changes and running the spec
on `HEAD`: identical failure, `1 failed | 8 passed`. Fixture retargeted to `*.example` values.
The 7.5 plan's own verify ran `prod-guardrails.spec.ts` but not this file, which is how it escaped.

## Deviations

- **The plan named only `env.schema.ts` for the dead Stripe defaults; `prod-guardrails.ts:21-22`
  carries the same two literals.** Changing one without the other would have left the dev-default
  detector comparing against a value the schema no longer produces. Both changed.
- **`identity-core.module.ts` was still reading `ADMIN_WEB_URL` directly** after the plan's edits —
  once for the trusted origin and once for the invitation's `!== undefined` branch — so the plan's
  own three-file confinement check would have failed. Added `adminOrigin()` to the module and made
  the invitation branch fall back through `adminLink`'s empty-string return. The confinement is now
  real rather than approximate.
- A stale doc comment in `identity-core.module.ts:160` still described the old inline composition;
  updated rather than left to mislead.

## Handoff to phase 7.5

- `ADMIN_WEB_URL` now carries a path (`https://<apex>/admin`). `infra/docker/env/api.env.example`
  renders it from `${PUBLIC_APEX_DOMAIN}`.
- The three GitHub repository **variables** are still the three-apex values —
  `PUBLIC_APEX_DOMAIN=resto.pp.ua`, `ADMIN_APEX_DOMAIN=restos.pp.ua`, `GUEST_APEX_DOMAIN=qmenu.pp.ua`.
  Under the single-apex scheme they should end as **`PUBLIC_APEX_DOMAIN=restos.pp.ua` alone**, with
  the other two deleted. Left untouched deliberately: the apex move is founder-facing.
- Whether a dedicated `/admin/stripe/*` landing route should exist is phase 8.x's call
  (`07.4-CONTEXT` open question 3).
