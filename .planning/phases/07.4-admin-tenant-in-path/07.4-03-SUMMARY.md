# Phase 07.4 Plan 03: Cross-tenant e2e proof (real stack) Summary

**One e2e file, `operator-tenant-binding.e2e.spec.ts`, proves against a real Postgres+RLS+AuthGuard stack that an operator session naming tenant A cannot reach tenant B's data by a forged header, a forged host, an org-less session, a stale membership row, or a tenant-B id in the path — with all five rejections shown failing against the pre-plan-01 guard first.**

## Accomplishments

- Wrote `operator-tenant-binding.e2e.spec.ts`: two tenants (A, B), two owners, one published item each, against `startRealStack()` (fresh testcontainer Postgres + full migration replay).
- **A5** (positive control, written and run first): owner A reading tenant A's own `/v1/catalog/items` returns 200 with A's item and none of B's.
- **A1**: a forged `x-tenant-id: tenantB.id` on owner A's cookie → 403 `auth.tenant_mismatch`.
- **A2**: a session with no active organization (`signIn`, not `signInAsOperator`) plus a forged `x-tenant-id: tenantB.id` → 403 `auth.tenant_mismatch` — the exact hole plan 01 closed.
- **A4**: a dedicated admin-role operator in tenant A, proven to succeed once, then its sole `member` row deleted directly via `AUTH_DRIZZLE_TOKEN`, then the identical request → 403 `auth.tenant_membership_missing`.
- **A3-pre** (negative control for A3, written and run first): an unauthenticated `GET /v1/menu` with `x-forwarded-host: <slugB>.<PUBLIC_APEX_DOMAIN>` resolves tenant B's own published menu (200).
- **A3**: owner A's cookie, no `x-tenant-id`, same forged host → 403 `auth.tenant_mismatch`.
- **A6**: owner A's cookie + `x-tenant-id: tenantA.id`, `GET /v1/catalog/items/<tenant-B item id>` → 404 `catalog.menu_item_not_found`, body does not contain B's item slug — `ScopedTx`/RLS territory, not the guard.
- Reproduced the pre-plan-01 RED transcript in a scratch `git worktree` at commit `4da7d5d7` (the commit immediately before the guard fix): A5 and A1 pass unchanged; A2 and A4 fail — both resolve 403 `auth.forbidden` from `PermissionsGuard` (no `baseRole` was ever attached under the old short-circuit), not the guard's own tenant codes. This is the literal "403 for the wrong reason" shape the founder's brief warned about — a status-only assertion would have gone green against the hole this file exists to catch.
- Proved A3-pre is load-bearing: with `PUBLIC_APEX_DOMAIN` temporarily unset, A3-pre fails (`expected 404 to be 200` — the forged host resolves to no tenant at all), confirming that without this control A3's 403 could fire for an unrelated reason.
- Added a required file-level header (the repo's one exception to the no-comments rule) recording the threat, the design, the stack choice and why, and the full red-then-green record — modeled on `cross-tenant-als-leak.e2e.spec.ts`'s header.

## Stack shape used, and why

`startRealStack()` — a fresh `testcontainers` Postgres 16-alpine container with the full migration chain replayed on every run — was tried first per the plan's constraint and kept, because it replayed clean on every single run of this exact file (four full runs across both tasks, plus the pre-plan-01 worktree run against a second fresh container). `organization-switch.e2e.spec.ts`'s own header documents a pre-existing `0079` idempotency bug (`ALTER POLICY organization_role_resto_auth_full`) on a fresh-container replay; this file did not reproduce that failure in any run. That is an observed result specific to this spec's migration/query path, not a claim that the older spec's documented bug is fixed — recorded here rather than assumed away, per the plan's own instruction to record the actual error seen (or, in this case, its absence) rather than the outcome expected.

## Blast radius, measured

A6 ("a tenant-B resource id addressed directly in the path is not readable") is **not** duplicated by either pre-existing catalog isolation spec:

- `catalog-tenant-isolation.e2e.spec.ts` covers write-path id-hijack (archive, overwrite-by-id, create-under-foreign-category) — its one `GET /v1/catalog/items/:id` call is a same-tenant "survivor" check after a failed hijack, not a cross-tenant GET.
- `catalog-tenant-read-isolation.e2e.spec.ts` covers cross-tenant read isolation on `/v1/menu` (the public, unauthenticated menu) and stop-list propagation — no test issues an authenticated cross-tenant GET on a specific resource id.

So A6 is new coverage, not a restatement of existing coverage. It stays in this file per the plan's own reasoning: this is the one place all six shapes are asserted together, and a reader should not have to assemble the property from four separate files.
