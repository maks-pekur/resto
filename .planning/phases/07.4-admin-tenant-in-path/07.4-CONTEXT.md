# Phase 07.4 — Admin tenant in path

## The decision

The founder settled the URL scheme on 2026-09-05: **one apex domain**.

| Hostname | Surface |
|---|---|
| `<apex>` | marketing landing |
| `<apex>/admin` | operator admin |
| `<slug>.<apex>` | the restaurant's storefront |
| `<slug>.<apex>/qr` | the QR menu |
| `api.<apex>` | API |

Rationale, industry check and the properties at stake: `.planning/notes/url-scheme-single-apex.md`.
The short version: Cloudflare's free Universal SSL covers an apex and its first-level subdomains
only, so `<slug>.admin.<apex>` (depth 2) has no certificate. Measured live on the founder's zone
2026-09-05 — SANs are exactly `restos.pp.ua, *.restos.pp.ua`; `probe123.restos.pp.ua` completes a
handshake (curl exit 28, no origin behind it), `probe123.menu.restos.pp.ua` fails it with
`sslv3 alert handshake failure` (curl exit **35**). Moving admin tenancy into the path removes the
only remaining depth-2 host.

## Why this is its own phase and not a plan inside 7.5

Every other plan in 7.5 changes infrastructure, configuration or CI. This one changes **which input
the server trusts to select a tenant**. 7.5's CONTEXT and its four review rounds are calibrated for
deployment risk — "does the box come up", "does the certificate cover the host". They are not
calibrated to review a tenancy change, and the reviewers observed that each round's defects
clustered in whichever subsystem the plans treated as incidental.

It is also a **prerequisite**, not a peer: 7.5 plan 08's `verify-prod-origin.sh --stage full` has a
mandatory tenant assertion that cannot pass until admin and API agree on where the tenant comes
from. Anything that must be finished before the next plan starts is a phase boundary.

And it has its own rollback story: a revert of an application commit, with no infrastructure
implication. Entangling it with the box bring-up would give a bad go-live two unrelated suspects.

## D-01 — The tenant leaves the URL entirely

**Locked.** The new trusted input for operator traffic is the Better Auth session's
`activeOrganizationId`. Nothing else. There is no `<slug>` path segment and no tenant host.

"Admin tenancy moves from the host to the path" reads as a relocation. It is not. Phase 10.2's
D-20 already deleted a `/{brandSlug}` admin path segment once, and D-21 chose a host over a path
precisely because *"a path segment changes on every navigation, so reconciling it against the
session costs a check in all 18 route files."* Re-adding a slug segment would reintroduce exactly
what D-20 deleted and buy nothing.

Server-side this is mostly a **removal**. `TenantContextMiddleware.resolveTenantOnly`
(`tenant-context.middleware.ts:89-120`) already tries `x-tenant-id` (the BA `activeOrganizationId`
UUID that `apps/admin/src/lib/api-client.ts:55,63` attaches to every `/v1/*` request, RES-181)
before it ever reaches the host branch. The host branch is a fallback. This phase removes the
fallback's only legitimate producer, not the mechanism.

## D-02 — `AuthGuard` must require agreement, not merely absence of disagreement

**Locked. This is the single most important change in the phase.**

`auth.guard.ts:119-136` refuses when the request's bound tenant and the principal's tenant disagree.
The condition chain includes `principal.tenantId &&`, so an operator session with **no** active
organization short-circuits the whole comparison, and whatever `x-tenant-id` the client sent binds
the ALS tenant unchecked.

Today the exposure is bounded because the host is the primary tenant source in production and
`lookupBaseRole` is guarded by the same `principal.tenantId`, so `PermissionsGuard` rejects any
`@Permissions(...)` route. But the set of routes carrying `@RequiresTenantContext` **without**
`@Permissions` has never been enumerated — so the residual blast radius is unknown, and "unknown"
is not a security argument. The moment the session becomes the tenant source, "must not disagree"
has to become "must agree".

Two deliverables, both in wave 1: the guard change, and the census that says what the hole was
worth. Do the fix even if the census comes back empty; an empty table today is not an invariant.

## D-03 — The browser stops sending a tenant selector

**Locked.** `apps/website/lib/checkout-api.ts:80` sets `x-forwarded-host` from
`window.location.host` on every call **including order placement**. `effectiveHost()`
(`apps/api/src/shared/effective-host.ts:13-18`) honours that header whenever `TRUST_PROXY` is
non-empty, which it always is in production by schema requirement. That is a client-controlled
tenant selector on the order-creation path, in production, today.

The two uses in `apps/website/lib/api-client.ts:24,43` are **different and legitimate** — that file
is `server-only` and forwards the real inbound `Host` during SSR. They stay.

Under a single apex the checkout call is same-origin (`<slug>.<apex>/v1/orders`, routed by Caddy),
so the browser header is not merely dangerous, it is unnecessary. **Deleting it is the root fix.**

The defence-in-depth half — `header_up X-Forwarded-Host {host}` on Caddy's
`{$WEBSITE_HOST}, *.{$WEBSITE_HOST}` blocks, measured working as M-08 — belongs to **phase 7.5's
Caddyfile and is explicitly not planned here.** With D-03 done, 7.5 may pin the header on every
block without breaking guest checkout.

## D-04 — Tenant switching stays a real page load, enforced by lint

**Locked.** Phase 10.2 closed *"a stale query cache serving another organization's data after a
switch"* (T-10.2-14-02, T-10.2-16-02) with a hard cross-origin navigation. A path scheme removes
the origin change.

Measured in Chromium via Playwright 1.60.0 (research M-10): `location.assign()` to a same-origin
path **discards** a module-scope object (stamp changed 40 → 4.7, new realm);
`history.pushState` — which is what TanStack Router's `navigate()` does — **does not** (stamp
unchanged). So the property survives, and "cross-**document**" was always the load-bearing half of
10.2's reasoning, not "cross-origin".

But the same measurement is the threat model. Under the host scheme a client-side route change
*could not* reach another tenant — the impossibility was structural. On a path,
`navigate({ to: '/dashboard' })` after a switch compiles, type-checks, passes review and silently
keeps tenant A's cache. **The property stops being enforced by physics and starts needing to be
enforced by the codebase.**

Three layers, all modelled on mechanisms this repo already uses:

1. One `switchTenant()` helper in `apps/admin/src/lib/switch-tenant.ts`, the only module that may
   POST to `/api/auth/switch-organization`.
2. An ESLint `no-restricted-syntax` rule confining that string literal to that module — the same
   shape as `runInTenantContext` restricted to `tenant-context.middleware.ts` (ADR-0020 I-6) and
   `withoutTenant` allowlisted by file path (RES-252 I-1).
3. A test asserting the helper clears the query cache and assigns `window.location`.

Layer 2 is the answer to *"what stops a later refactor from quietly turning it into a client-side
route change"*. A property defended only by a convention will be refactored away.

## D-05 — `AUTH_COOKIE_DOMAIN` goes unset; the cookie becomes host-only

**Locked.** Read from `better-auth@1.6.30 dist/cookies/index.mjs:22-42` (research M-11): `domain` is
`undefined` and the attribute is spread in only under `...crossSubdomainEnabled ? { domain } : {}`.
With the option absent the `Domain` attribute is **omitted entirely** → a host-only cookie, sent to
`<apex>` and nothing else. Not `<slug>.<apex>`, not `api.<apex>`.

That is **strictly narrower** than the `.<admin-apex>` domain cookie it replaces. The leading-dot
rule (D-24) existed because sign-in had to hop `admin.<domain>` → `<slug>.admin.<domain>`. With
admin on a path there is no hop.

`AUTH_COOKIE_DOMAIN` must therefore stop being in the `superRefine` required list
(`env.schema.ts:361`) — leaving it required would force a value, and **every legal value is now
wrong**. The leading-dot *shape* check stays (it is conditioned on the value being set) but its
message and the field comment must stop instructing the reader to set a dotted value: a stale
instruction here would talk a future operator into re-widening the cookie to `.<apex>`, delivering
the operator session to every tenant storefront.

**Public-suffix tripwire, recorded so nobody re-derives it wrong:** `pp.ua` is on the Public Suffix
List (ICANN section, `public_suffix_list.dat` line 15784), so `restos.pp.ua` is the registrable
domain and `Domain=.restos.pp.ua` would be legal if ever needed — but `Domain=.pp.ua` is rejected
outright by every browser. Any future "just drop a label off the apex" rule is wrong.

## D-06 — `ADMIN_WEB_URL` carries a path; Better Auth gets its origin only

**Locked.** `ADMIN_WEB_URL` becomes `https://<apex>/admin`. But read from
`better-auth@1.6.30 dist/auth/trusted-origins.mjs` (research M-12): non-wildcard patterns are
compared `pattern === getOrigin(url)`, so **a value carrying a path can never match**.
`identity-core.module.ts:240` must push `new URL(env.ADMIN_WEB_URL).origin`, not the raw value.

`ADMIN_WEB_ORIGIN_WILDCARD` and `VITE_ADMIN_HOST_SUFFIX` are deleted outright — there are no
per-tenant admin origins any more.

## Open questions — named here, not answered here

1. **The marketing landing does not exist.** `apps/website/app/page.tsx` resolves a tenant from the
   `Host`, throws `TenantNotFoundError` at the bare apex and renders `notFound()`. So `<apex>/`
   will serve **"Restaurant not found"** — on the same domain that appears in every operator
   invitation and password-reset email, which this phase points at `<apex>/admin`. That is product
   work, not this phase. It must be decided before 7.5's go-live smoke, not at it. Do not let the
   default 404 stand.
2. **`WEBSITE_PUBLIC_URL` is apex-scoped but the storefront is per-tenant.**
   `send-guest-notification.service.ts:117-118` builds
   `${WEBSITE_PUBLIC_URL}/checkout/confirmation/${orderId}` — under one apex that resolves no
   tenant and renders the same 404 as (1). Pre-existing (the three-apex map had it too), newly
   visible. Belongs with 7.5's guest-URL composition work.
3. **`STRIPE_CONNECT_RETURN_URL` / `_REFRESH_URL` point at `/stripe/return` and `/stripe/refresh`,
   which are not routes in the Vite admin** — dead since the 7.6 Next→Vite migration; the only
   payouts route is `/tenant/payouts`. `${ADMIN_WEB_URL}/payouts` in
   `start-tenant-onboarding.service.ts:211` is dead for the same reason. Plan 04 repoints both at
   the route that exists; whether a dedicated `/admin/stripe/*` landing route *should* exist is a
   payments-UX question for phase 8.x.
4. **`.pp.ua` as the production apex** — works and is free; not memorable to a restaurant owner and
   not neutral in a guest's address bar. Go-to-market question. The technical work is
   apex-parameterised throughout, so swapping later is an env change plus DNS.
5. **Two tabs on two separate companies.** Cookies and `activeOrganizationId` are per-origin, not
   per-tab, so an operator holding several *separate companies* can have one tab silently follow
   another's switch. A chain is one tenant with locations inside, so the ordinary operator has
   exactly one tenant and never meets this. **Accepted knowingly** by the founder in the URL-scheme
   note; recorded here so it is a decision and not a discovery.

## Two standing rules this phase inherits, both earned

**Any sentence asserting how a third-party component behaves needs a citation or a command.** Round
1 of the 7.5 review predicted a curl exit of 60 for a TLS failure; the real code is 35. Three days
ago both the planner and the founder approved `cf: { cacheTtl: 0 }` as a cache opt-out when
Cloudflare's own docs say it *forces* caching. The pattern the reviewers named: *"all three new
defects are claims about what a component does, asserted confidently and never executed."*

**A verifier that cannot fail is not a verifier.** Every assertion added by this phase must be shown
failing before it is shown passing, with the failing transcript recorded in the plan's SUMMARY.
This repo already has the discipline — see the header of
`apps/api/test/e2e/cross-tenant-als-leak.e2e.spec.ts`, which documents neutering
`#assertGucUnchanged` to prove the spec catches the bug it exists for.

## The property this phase must not lose

**An operator whose session names tenant A must not reach tenant B's data by any route** — including
a crafted path, a stale `x-tenant-id` header, and a session with no active organization at all.
Plans are weighted toward tests that would catch a regression in exactly that.
