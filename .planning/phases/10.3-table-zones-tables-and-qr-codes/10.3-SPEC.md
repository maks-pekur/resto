# Phase 10.3: Table zones, tables and QR codes — Specification

**Created:** 2026-08-29
**Ambiguity score:** 0.15 (gate: ≤ 0.20)
**Requirements:** 12 locked

## Goal

A dine-in guest scans the QR glued to their table and the order reaches the kitchen already carrying the table it came from — the guest types nothing, and the order lands on the location that table belongs to instead of the tenant's default location.

## Background

Nothing of this exists yet.

- **Zones and tables:** `packages/db/src/schema/locations.ts` holds only `locations` and `member_location_scope`. There is no zone or table concept anywhere — no schema, no endpoints, no admin screen.
- **QR:** no QR library in any `package.json`; nothing renders, downloads or prints a code.
- **Guest app:** `apps/qr-menu/src/App.tsx:117` reads `?table=` from the URL, passes it through `sanitizeTable` (trim, 20 chars) and displays that string verbatim in a read-only strip (`TableBanner.tsx`). The value is never checked against anything. Landed in PR #275; regression net is `apps/qr-menu/test/table.spec.tsx`.
- **Order:** the table is free text — `orders.table_identifier text` (`packages/db/src/schema/ordering.ts:33`), fed by `table: z.string().max(20)` in `CreateOrderInputSchema` (`ordering/application/dto.ts:28`), required for `dine_in` by a refine at line 46. It flows unchanged into the aggregate, the order-feed DTO and the operator DTO. No foreign key, no id.
- **Location:** `CreateOrderService` resolves the location with `DefaultLocationResolverService.resolveForTenant(tenantId)` (`create-order.service.ts:41`) — it never takes a location from the client. A tenant with two locations therefore has every QR order land on the first one.
- **Admin:** `apps/admin/src/routes/(protected)/location/` has `dashboard`, `orders`, `stop-list`. The operator cannot create orders at all (`operator-orders.controller.ts` exposes only feed / detail / accept / advance), so nothing in admin needs to pick a table by hand.

The delta this phase closes: the table zone and table records, their CRUD and bulk creation, the printable QR, the server-side resolution of a scanned id, and the order carrying a real reference to the table it came from.

## Requirements

1. **TBL-01 — Table zone schema**: A location can hold named table zones, tenant-isolated at the database level.
   - Current: no zone table exists; `locations.ts` has only `locations` and `member_location_scope`
   - Target: `table_zones (id, tenant_id, location_id, name, status active|archived, timestamps)` with a composite FK `(location_id, tenant_id) → locations (id, tenant_id)` per ADR-0020 I-2, an RLS policy, and a `tenantParentUniqueIndex`
   - Acceptance: the migration applies; inserting a zone whose `location_id` belongs to another tenant is rejected by the FK; a `ScopedTx` read as tenant B returns zero of tenant A's zones

2. **TBL-02 — Table schema**: A zone holds tables whose number is unique inside that zone, and whose id is the value printed on the sticker.
   - Current: nothing
   - Target: `restaurant_tables (id, tenant_id, zone_id, location_id, number, status active|archived, timestamps)`; composite FK to the zone and to the location; the `id` is an opaque UUID and is the only identifier the QR carries; `number` is a display label only
   - Acceptance: creating two active tables numbered `1` in the same zone fails; creating `1` in two different zones of the same location succeeds; a `zone_id` from another tenant is rejected by the FK

3. **TBL-03 — Bulk creation**: An operator creates a zone with N tables in one action, numbered automatically.
   - Current: no endpoint exists
   - Target: one API call takes a zone name and a table count N and creates the zone plus tables numbered `1..N` in a single transaction; N is capped; a constraint violation anywhere in the batch creates nothing
   - Acceptance: a call with N = 20 yields exactly 1 zone and 20 tables numbered 1..20; a call exceeding the cap is rejected with a 4xx and creates no rows; a call that violates a constraint mid-batch leaves zero rows

4. **TBL-04 — CRUD and archive cascade**: Zones and tables are listed, renamed, added to, and archived — never deleted.
   - Current: nothing
   - Target: list zones with their tables for a location; rename a zone; rename or renumber a table; add a single table to an existing zone; archive a table; archiving a zone archives all of its tables in the same transaction
   - Acceptance: archiving a zone of 20 tables sets `status='archived'` on the zone and on all 20 rows; archived zones and tables are excluded from the default listing and from the number-uniqueness check; the repository issues no `DELETE`

5. **TBL-05 — Location-scoped access**: Zones and tables obey the Phase 08.4 location scope.
   - Current: not applicable — no zone or table surface exists
   - Target: an operator scoped to location A can neither read nor mutate zones and tables of location B; an owner in `?location=all` sees every location and mutates per location
   - Acceptance: e2e — a member with `member_location_scope` on location A receives 403 (or an empty list) for location B's zones and for a mutation targeting them; an owner receives both locations

6. **TBL-06 — Server-side table resolution**: The guest menu learns the table from the server, never from the URL text.
   - Current: `App.tsx:117` reads `?table=` and renders whatever string the URL contains
   - Target: the sticker link is `https://<slug>.menu.<domain>/?t=<table id>`; the guest app sends the id to the API and renders the label the server returns (`Зал 1 · стол 14`); the free-text `?table=` path is removed — no stickers exist in the field yet, so nothing needs the old shape
   - Acceptance: a valid `?t=<id>` renders the server-supplied label; `?table=Стол%2099` renders no table label at all; `apps/qr-menu/test/table.spec.tsx` is updated to the new contract and passes

7. **TBL-07 — Unknown table fails softly**: A stale or forged sticker still opens the menu.
   - Current: not applicable
   - Target: an unknown, archived or malformed `?t=` value still loads the menu; in place of the table number the guest sees a "table not recognised — please ask a member of staff" line; a dine-in order cannot be created without a table that resolved
   - Acceptance: a request carrying a random UUID as `?t=` returns HTTP 200 for the menu and renders the not-recognised state; a `dine_in` create-order call carrying an unresolvable table id is rejected with a 4xx

8. **TBL-08 — Order references the table**: An order stores the table id plus the label as it read at order time.
   - Current: `orders.table_identifier` is free text with no FK; `table: z.string().max(20)` in the create-order DTO
   - Target: orders carry a nullable `table_id` (composite FK, tenant-scoped) and a `table_label` snapshot frozen at creation; the existing free-text column stays for orders created without a QR; renaming or renumbering a table later never rewrites a past order
   - Acceptance: an order created from a scanned table stores both the id and the label; renaming that table afterwards leaves the stored label unchanged while the id still resolves; a pickup or delivery order stores null for both

9. **TBL-09 — Order location comes from the table**: A scanned table decides which location the order belongs to.
   - Current: `CreateOrderService` always calls `DefaultLocationResolverService.resolveForTenant(tenantId)`, so every order lands on the tenant's default location
   - Target: when the order carries a resolved table, the order's `location_id` is that table's location; with no table, the default resolver is used exactly as today
   - Acceptance: for a tenant with two locations, an order created from a table in location B is stored with `location_id = B` and appears in location B's order feed and not in location A's; a pickup order with no table still lands on the default location

10. **TBL-10 — Printable QR output**: The operator gets stickers for a whole zone in one print, and a single code when one needs replacing.
    - Current: no QR library anywhere; no print or download surface
    - Target: from the zone screen, a printable sheet carrying one QR per non-archived table in the zone, each labelled with its number and the restaurant name as text; each table row additionally offers a single-QR download
    - Acceptance: printing a zone of 20 tables produces 20 distinct codes; every code decodes to `https://<slug>.menu.<domain>/?t=<that table's id>`; an archived table does not appear on the sheet

11. **TBL-11 — Admin zone and table screen**: A location-scoped list screen, not a floor map.
    - Current: `location/` has `dashboard`, `orders` and `stop-list` only
    - Target: a screen listing the location's zones, each expanding to its tables; actions are create-zone-with-N-tables, add table, rename, archive, print sheet, download single QR; an empty state when the location has no zones
    - Acceptance: the screen renders correctly at 0 zones (empty state), 1 zone, and a zone of 50 tables; every failed mutation surfaces a human-readable message rather than a stack trace

12. **TBL-12 — Order feed shows the table label**: The operator reads the zone and number, not a bare code.
    - Current: the feed DTO carries `tableIdentifier: string | null` and the card renders it raw
    - Target: a dine-in order card shows the stored `Зал 1 · стол 14` snapshot; no zone filter is added to the feed
    - Acceptance: a dine-in order from a scanned table renders the zone-and-number label; an order carrying only legacy free text still renders that text; a pickup order renders no table line

## Boundaries

**In scope:**

- `table_zones` and `restaurant_tables` schema with composite FKs, RLS and archive-only lifecycle (TBL-01, TBL-02)
- Bulk "zone with N tables" creation, plus per-item CRUD and the zone→tables archive cascade (TBL-03, TBL-04)
- Location-scoped authorisation on the whole surface (TBL-05)
- Server-side resolution of the scanned `?t=<id>` into a display label, and the soft-fail path (TBL-06, TBL-07)
- `table_id` + `table_label` snapshot on the order, and the order's location taken from the table (TBL-08, TBL-09)
- Printable QR sheet per zone and single-QR download (TBL-10)
- Admin list screen for zones and tables (TBL-11)
- Zone-and-number label in the operator order feed (TBL-12)

**Out of scope:**

- **Floor map with drag-and-drop placement** — the list covers setup and the map changes nothing about taking an order; no coordinate columns are added now, a later phase migrates them in
- **Table occupancy state ("table busy / free", open tabs)** — there is no concept of an open bill; an order is paid up front and closed
- **Moving an order to another table, and merging tables** — same reason: both are work on an open bill, which does not exist
- **Per-table analytics and reports** — Phase 13 owns reporting; this phase only lays down the data that makes those reports possible
- **Tenant branding (logo upload, theme editor at `/tenant/theme`)** — its own phase; the printed sheet carries the restaurant name as text only. The stub route stays a stub
- **Zone filter in the order feed** — the label alone answers "where does this go"; a filter is worth adding once a tenant actually runs several zones
- **`apps/website`** — dine-in reaches a guest only through the QR-menu host
- **Sticker artwork, NFC tags, short links** — a printable sheet of codes is the deliverable

## Constraints

- **The QR carries only the opaque table id** — `https://<slug>.menu.<domain>/?t=<id>`, never `zone=2&table=14`. Printed stickers live on furniture for years; renaming a zone or renumbering tables must not silently invalidate what is already glued to the floor (ROADMAP decision 1, founder 2026-08-29).
- **Naming is `table zones` / `table_zones`, never a bare `zone`** — Phase 9 owns `zone` for delivery polygons (DELV-01..03); an unqualified name would collide in the schema, the code and the conversation.
- **Every new table is doubly tenant-scoped** — `ScopedTx` in the application layer _and_ Postgres RLS, with a composite FK `(parent_id, tenant_id)` on every child per ADR-0020 I-2.
- **No hard deletes** — `resto_app` has no DELETE privilege; the lifecycle is `status = 'archived'`.
- **The display label always comes from the server** — the guest app must not derive it from the URL, so a guest cannot hand-edit their way to another table.
- **Bulk creation is bounded** — a single call must not be able to create an unbounded number of rows; the cap is a number, not a comment.
- **QR generation stays on the admin surface** — no QR dependency may be added to the guest bundle (`apps/qr-menu` has a bundle-size regression test).
- **`apps/qr-menu/test/table.spec.tsx` stays green** — updated to the new contract, not deleted.
- **Location scoping follows the Phase 08.4 model** — `member_location_scope`, same as every other location-scoped surface.

## Acceptance Criteria

- [ ] Migration creates `table_zones` and `restaurant_tables` with composite FKs to `locations` (and zone→table), and RLS policies on both
- [ ] A cross-tenant `location_id` or `zone_id` is rejected by the foreign key, not merely by application code
- [ ] One API call creates a zone plus N tables numbered 1..N in a single transaction; exceeding the cap creates nothing
- [ ] Two active tables numbered `1` cannot exist in the same zone; `1` in two different zones of one location is allowed
- [ ] Archiving a zone archives every table in it in the same transaction; no repository path issues a `DELETE`
- [ ] An operator scoped to location A gets 403 or an empty result for location B's zones and tables; an owner sees both
- [ ] A valid `?t=<id>` renders the server-supplied `Зал 1 · стол 14` label in the guest app
- [ ] `?table=<any text>` renders no table label — the free-text path is gone
- [ ] An unknown, archived or malformed `?t=` value still returns the menu with HTTP 200 and renders the "not recognised" state
- [ ] A `dine_in` create-order call whose table id does not resolve is rejected with a 4xx
- [ ] An order created from a scanned table stores `table_id` and `table_label`; renaming the table afterwards leaves the stored label unchanged
- [ ] For a two-location tenant, an order from a table in location B is stored with `location_id = B` and appears only in location B's feed
- [ ] Printing a zone of 20 tables produces 20 distinct QR codes, each decoding to that table's own `?t=<id>` URL; archived tables are absent
- [ ] The admin screen renders at 0 zones (empty state), 1 zone, and a zone of 50 tables, and shows a human-readable message on a failed mutation
- [ ] A dine-in order card in the feed shows the zone-and-number label; a pickup order shows no table line
- [ ] `apps/qr-menu/test/table.spec.tsx` passes against the new contract, and the guest bundle gains no QR dependency
