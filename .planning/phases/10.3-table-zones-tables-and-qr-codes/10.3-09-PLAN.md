<objective>
Make the order carry the table it came from, take its location from that table, and — critically — price and stop-check against that same location.

Purpose: TBL-09 on its own is a defect that hides itself. `CreateOrderService` calls `this.pricing.loadSnapshot(tenantId)` with the tenant only, and `CatalogMenuPricingAdapter` then resolves the **default** location internally and loads that location's stop list. Once a table decides the order's location, a guest at a table in location B is priced and 86-checked against location A: a dish sold out in B is orderable, the money is captured, and the kitchen cannot make it — while TBL-09's own acceptance criterion passes the whole time, because it only asserts the stored `location_id`. Both persona reviews found this independently and both graded it blocking.
Output: the ordering context resolves the table first, derives the location from it, and threads that location through pricing and through the whole tail of the transaction.
</objective>

Rewrite the opening of `CreateOrderService.execute` in this order:

1. `requireTenantContext()` and `TenantId.parse`.
2. The idempotency short-circuit — `findByIdempotencyKey`, return the existing order if there is one. This moves ABOVE the table resolution deliberately: resolution throws on an unresolvable table, so leaving it first would make a retry of an already-successful order start failing the moment an operator archives that table, which is a real window during service.

6. Pass `tableId`, `tableZoneName` and `tableNumber` into `Order.create` from the resolution result, and keep `tableIdentifier: null` — the free-text column has no writer from this phase on.
