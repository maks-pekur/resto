### Pattern 1: Composite FK + double RLS (tenant PERMISSIVE + location RESTRICTIVE)

**What:** Every tenant-scoped child table gets a default PERMISSIVE tenant policy (`USING (tenant_id = current_tenant_id())`) plus, when the table is also location-scoped, a second RESTRICTIVE policy that ANDs a location predicate on top.
**When to use:** Any table whose rows belong to exactly one location and whose id can appear in a URL path (rename/archive routes) — exactly the situation TBL-01/02 are in.
**Verified template (`packages/db/migrations/0000_baseline.sql:1175-1179`, for `menu_stop_list`):**

```sql
ALTER TABLE public.menu_stop_list ENABLE ROW LEVEL SECURITY;
-- (FORCE ROW LEVEL SECURITY is also set at table-creation time, baseline:512, for menu_stop_list's sibling tables — apply the same to table_zones/restaurant_tables)

CREATE POLICY menu_stop_list_iso ON public.menu_stop_list
  USING ((public.is_system_session() OR (tenant_id = public.current_tenant_id())))
  WITH CHECK ((public.is_system_session() OR (tenant_id = public.current_tenant_id())));

CREATE POLICY menu_stop_list_location_iso ON public.menu_stop_list
  AS RESTRICTIVE
  USING ((public.is_system_session() OR (public.current_location_id() IS NULL) OR (location_id = public.current_location_id())))
  WITH CHECK ((public.is_system_session() OR (public.current_location_id() IS NULL) OR (location_id = public.current_location_id())));
```

`current_location_id()` (`baseline.sql:101-107`) reads `app.current_location`, a GUC bound by `app_bind_location()` (`baseline.sql:62-77`), which `TenantAwareDb.withTenant()` calls automatically whenever `TenantContext.locationId` is set (`packages/db/src/client.ts:246-256`). `ScopedTx` itself (`packages/db/src/client.ts:80,123`) filters **tenant only** — it has no location dimension at all — so the RESTRICTIVE policy is the only DB-layer defense against a forged zone/table id in a path parameter, and the repository must ALSO filter on location explicitly (ADR-0020 I-1's "second layer", not redundant here). The exact repository pattern already exists in `apps/api/src/contexts/catalog/application/availability/stop-list.service.ts:19-20` (`requireLocationContext()` then pass `locationId` explicitly into `repo.addToStopList({...locationId})` / `repo.removeFromStopList({...locationId})`) — copy this shape for the table-zone/table repositories.

### Pattern 2: Public guest-resolution route (sibling of `PublicMenuController`)

**What:** A `@Public() @LocationNeutral()` controller that re-verifies the request's own host before trusting anything, exactly like `PublicMenuController.requireGuestTenantOr404` (`apps/api/src/contexts/catalog/interfaces/http/public-menu.controller.ts:255-261`).
**When to use:** Any new guest-facing (unauthenticated) endpoint. `LocationScopeGuard` does not check `IS_PUBLIC_KEY` at all — only `LOCATION_NEUTRAL_KEY` (`apps/api/src/contexts/identity/interfaces/http/guards/location-scope.guard.ts:27-31`) — so a public route WITHOUT `@LocationNeutral()` 403s with `location.context_required` the moment `getLocationId()` is empty, which it always is for an anonymous request.
**Example (adapted from the verified pattern):**

```typescript
// Source: apps/api/src/contexts/catalog/interfaces/http/public-menu.controller.ts:168-172,255-261
@ApiTags('tenancy')
@Public()
@LocationNeutral()
@Controller('v1/tables')
export class PublicTableResolutionController {
  constructor(
    @Inject(ResolveTableService) private readonly resolve: ResolveTableService,
    @Inject(TenantResolverService)
    private readonly tenants: TenantResolverService,
    @Inject(ENV_TOKEN) private readonly env: Env,
  ) {}

  @Get(':id')
  @ApiOkResponse({ type: TableResolutionResponseDto })
  @ApiNotFoundResponse({ type: ProblemDetailsDto })
  async resolve(
    @Param('id') id: string,
    @Req() req: FastifyRequest,
    @Res({ passthrough: true }) reply: FastifyReply,
  ): Promise<TableResolutionResponse | undefined> {
    const trustProxy =
      this.env.TRUST_PROXY !== undefined && this.env.TRUST_PROXY.length > 0;
    const host = effectiveHost(req.headers, trustProxy);
    const tenant = await this.tenants.resolveByCustomerHost(host);
    if (!tenant) throw new NotFoundException();
    const parsed = z.string().uuid().safeParse(id);
    if (!parsed.success) throw new NotFoundException();
    reply.header(
      'Cache-Control',
      'public, s-maxage=60, stale-while-revalidate=300',
    );
    return this.resolve.execute(tenant.id, parsed.data); // throws → 404 if not found/archived/wrong tenant
  }
}
```

The guest app's `fetchTable` wrapper should follow the exact catch-404 shape already established by `fetchAvailability` (`apps/qr-menu/src/api/client.ts:23-29`: `if (res.status === 404) return <safe default>`), so an unresolvable `?t=` renders the "not recognised" state instead of throwing — this is TBL-07's soft-fail requirement implemented at the client boundary, not the server one.

## Common Pitfalls

### Pitfall 1: Believing D-13's "?location=all asks the operator to pick a location" is buildable

**What goes wrong:** The planner writes a task to render an empty-state/picker for `/{locationSlug}/tables` when accessed in "all" mode.
**Why it happens:** CONTEXT.md was written against an older admin routing model (pre-`use-effective-location.ts:26-28`'s comment: "The owner's carrier moved out of `?location=` and into the path").
**How to avoid:** Confirmed directly: `apps/admin/src/routes/(protected)/location/_layout.tsx:16-32` resolves `/$locationSlug` or redirects before any child route (including a future `tables.tsx`) ever renders; `apps/admin/src/lib/location-path.ts:5` states "`/dashboard` is the only page with an every-location view." A route nested under `location/` cannot be reached without a resolved slug. Skip this task entirely.
**Warning signs:** A plan task titled anything like "render all-locations picker on tables screen."

### Pitfall 2: `MenuPricingPort.loadSnapshot` and `GetMenuAvailabilityService.execute()` both still resolve the DEFAULT location internally after TBL-09 ships

**What goes wrong:** TBL-09's acceptance criterion ("order lands on location B") passes while the guest was priced and stop-checked against location A's menu the whole time — a sold-out item in B is silently orderable.
**Why it happens:** `CatalogMenuPricingAdapter.loadSnapshot` (`apps/api/src/contexts/ordering/infrastructure/catalog-menu-pricing.adapter.ts:27-35`) calls `this.defaultLocation.resolveForTenant(tenantId)` internally, ignoring whatever location the order actually resolved to; `GetMenuAvailabilityService.execute()` (`apps/api/src/contexts/catalog/application/availability/get-menu-availability.service.ts:26-29`) does the same and takes no parameters at all.
**How to avoid:** This is TBL-13/D-16, already locked into scope. Concretely: change `MenuPricingPort.loadSnapshot(tenantId: TenantId): Promise<...>` (`apps/api/src/contexts/ordering/domain/ports.ts:58-60`) to `loadSnapshot(tenantId: TenantId, locationId: string)`, delete the `DefaultLocationResolverService` injection from `CatalogMenuPricingAdapter` (keep it in `CreateOrderService` for the "no table" fallback), and pass the already-resolved `locationId` from `create-order.service.ts:47`. For availability, add a location/table parameter to `GET /v1/menu/availability` — a five-second cache keyed additionally by location is not a cache-shattering change (`MENU_AVAILABILITY_S_MAXAGE_SECONDS = 5`, `apps/api/src/contexts/catalog/domain/menu-cache.ts:3`).
**Warning signs:** A unit test for `CreateOrderService` that mocks `MenuPricingPort` (as `apps/api/test/unit/create-order.service.spec.ts` already does) will stay green even with this bug present — this needs a real-DB e2e test with two locations and a location-specific stop-listed item to catch it (matches the "prove a test fails without the fix" discipline in `.planning/codebase/TESTING.md`).

### Pitfall 3: "An RLS policy" (singular, tenant-only) does not close the D-22-shaped hole this phase reopens

**What goes wrong:** `PATCH /v1/tenancy/table-zones/<a zone in location B>` sent by a caller scoped only to location A succeeds, because nothing checks that the zone id in the path actually belongs to the ALS-bound location.
**Why it happens:** `LocationScopeGuard` (`location-scope.guard.ts:61-76`) proves the caller may act _in the bound location_; it says nothing about which location the row named in the path belongs to. `ScopedTx` filters tenant only (`packages/db/src/client.ts:80,123`). Without a RESTRICTIVE location policy, the base tenant RLS policy (`locations_iso`-shaped: `tenant_id = current_tenant_id()`) allows any row of the same tenant regardless of location.
**How to avoid:** Both new tables need the paired policy shown in Architecture Patterns → Pattern 1, AND the repository must add an explicit `eq(table.locationId, requireLocationContext())` predicate on every read/write — not just rely on RLS. This is the ADR-0020 I-1 "second layer" rule applied literally.
**Warning signs:** A cross-location rename/archive e2e test (member scoped to A, `x-location-id: A`, target zone belongs to B) that only asserts a 403/404 from the _guard_ layer, without a second assertion at the raw-Postgres layer (mirroring `packages/db/test/integration/tenant-isolation.spec.ts:499-520`'s pattern for `menu_stop_list`'s location-grain binding) is not proof the RESTRICTIVE policy exists — it could pass on the guard check alone while a raw psql session (or a future code path that skips the guard) would still leak the row.

### Pitfall 4: `tenancy_erase_tenant` breaks the day this phase ships, silently, for every tenant that has tables

**What goes wrong:** GDPR erasure raises `foreign_key_violation` for any tenant with tables (which will be most of them post-launch), because the two new tables are location children and every existing location child in this schema is `ON DELETE RESTRICT`.
**Why it happens:** `tenancy_erase_tenant` (`packages/db/migrations/0000_baseline.sql:128-197`) explicitly lists every table it deletes, in dependency order, ending with `DELETE FROM locations WHERE tenant_id = p_tenant_id;` at line 184. A new table not added to that list is not "forgotten and cascades anyway" — it is a hard failure, because the FK is RESTRICT, not CASCADE. 10.1-CONTEXT records this happened three times already (migrations 0072/0074/0077).
**How to avoid:** The hand-written migration for this phase must `CREATE OR REPLACE FUNCTION public.tenancy_erase_tenant(...)` with two new `DELETE` statements inserted after the `orders`-related deletes (line ~165) and before `DELETE FROM locations` (line 184):

```sql
DELETE FROM restaurant_tables WHERE tenant_id = p_tenant_id;
DELETE FROM table_zones WHERE tenant_id = p_tenant_id;
```

Add a new integration test file modeled exactly on `packages/db/test/integration/erase-includes-ordering.spec.ts:1-165` — seed a tenant with a location, a zone, tables, and an order referencing one of those tables, run `tenancy_erase_tenant`, assert zero rows remain in all three new/touched tables.
**Warning signs:** None of the existing erasure tests (`erase-includes-ordering.spec.ts`, `erase-includes-tenant-pii.spec.ts`, `tenancy-erase-guard.spec.ts`) create zones or tables, so they will stay green with this bug present — a new test is mandatory, not incidental.

### Pitfall 5: The admin browser cannot legitimately compose the QR payload URL itself

**What goes wrong:** A `VITE_MENU_HOST_SUFFIX` env var gets added to `apps/admin` and used to build `https://${slug}.${suffix}/?t=${id}` client-side; this is permanently wrong for every tenant on a verified custom domain.
**Why it happens:** The guest host formula lives entirely server-side: `GUEST_HOST_LABEL = 'menu'` + `env.PUBLIC_APEX_DOMAIN` (`apps/api/src/contexts/tenancy/application/tenant-resolver.service.ts:9,108-110`), OR — for a tenant with a verified custom domain — a completely different shape resolved via `tenant_domains` (`packages/db/src/schema/tenants.ts:123-141`, `findByDomainHost`, `tenant-drizzle.repository.ts:89-101`). `apps/admin/src/env.ts:20-21` exposes exactly `VITE_STRIPE_PUBLISHABLE_KEY` and `VITE_ADMIN_HOST_SUFFIX` — no menu-host information reaches the admin bundle at all, by design.
**How to avoid:** Per D-21 (locked): the zone/table list response (and the single-table endpoint) carries a server-built `qrUrl` field per table. Build it in a small helper inside the `tenancy` context that checks for a verified primary custom domain first, else falls back to `<slug>.menu.<PUBLIC_APEX_DOMAIN>` — mirroring the exact resolution order `TenantResolverService.resolveByCustomerHost` already uses in reverse (`tenant-resolver.service.ts:75-92`).
**Warning signs:** Any new `VITE_*` env var whose name contains "menu," "guest," or "apex."

### Pitfall 6: The 8–9cm QR code size (D-09) does not leave room for its own mandatory quiet zone in a 2×3 A4 grid

**What goes wrong:** Codes are drawn edge-to-edge at 90mm in 105mm-wide grid columns, with no quiet zone margin — codes fail to scan reliably, especially once hand-cut.
**Why it happens (verified module math, cross-checked against a public QR capacity table):** A4 portrait is 210×297mm; a 2×3 grid gives 105mm-wide columns and 99mm-tall rows. The sticker URL `https://<slug>.menu.<domain>/?t=<uuid>` is roughly 65–75 bytes (8 for `https://`, ~8 for a typical slug, 6 for `.menu.`, ~9 for a typical apex domain, 4 for `/?t=`, 36 for the UUID). At error-correction level M, that requires QR **Version 5 (37×37 modules, 84-byte byte-mode capacity)** `[CITED: qrcode.com/DENSO WAVE version table, cross-verified via web search 2026-08-29]`. The QR spec's mandatory quiet zone is 4 modules on every side, so a code whose _drawn matrix_ (excluding quiet zone) is `C` mm wide actually occupies `C × (1 + 8/37)` mm once the quiet zone is included.
**How to avoid — concrete numbers that fit:** Target a total drawn footprint (module matrix + quiet zone, i.e. what a human perceives as "the code") of **≈85–90mm** — well inside the 105×99mm cell. At 37 modules, module size = 90mm / 45 = 2.0mm; the matrix-only area is 37 × 2.0mm ≈ 74mm, with the quiet zone adding ~8mm per side to reach the 90mm total footprint. This leaves ~7.5mm of margin on every side of the cell for the hairline cut guide plus the offcut-printed table number (D-24). **Do not hardcode "37 modules"** — compute module size dynamically as `targetFootprintMm / (matrixSize + 8)` where `matrixSize` comes from the actual generated QR object, because a longer custom-domain host or a longer slug can bump the symbol to Version 6 (41×41) and a hardcoded module count would silently produce an undersized quiet zone again.
**Warning signs:** A PDF-generation implementation that hardcodes a pixel/mm size for the "code area" without reading the actual module count back from `QRCode.create()`'s result.

### Pitfall 7: `orders.table_identifier` becomes a column with no writer, and the feed needs a fallback rule

**What goes wrong:** After D-03 removes the free-text `table` field from `CreateOrderInputSchema`, `orders.table_identifier` (`packages/db/src/schema/ordering.ts:33`) is legacy-read-only. If `order-feed-dto.ts:60` / `operator-orders.dto.ts:156` aren't given an explicit precedence rule, a future contributor might add a new writer and split the source of truth.
**How to avoid:** State explicitly in the migration header and in the DTO mapping code: render `table_zone_name`/`table_number` when present, fall back to `table_identifier` when both new columns are null, render nothing when all three are null. This is TBL-12's "an order carrying only legacy free text still renders that text" acceptance criterion — but note Skeptic MEDIUM-7's correction below.
**Warning signs:** A plan task that edits `order-card.tsx` expecting to find an existing table-rendering block there — see Pitfall 8.

### Pitfall 8: TBL-12's SPEC premise ("the card renders it raw") is wrong — the card renders nothing today

**What goes wrong:** A plan task scoped as "update the existing table rendering on the order card" undercounts the work, because there is no existing table rendering on the card.
**Why it happens:** Verified directly: `apps/admin/src/components/orders/order-card.tsx` has zero references to any table field. The only place `tableIdentifier` renders today is the detail sheet, conditionally (`apps/admin/src/components/orders/order-detail-sheet.tsx:266-268`).
**How to avoid:** Size TBL-12 as an **addition** to the card (a new small line/badge), not an edit to an existing one. The detail sheet's existing block can be left as-is or given the same fallback rule from Pitfall 7.
**Warning signs:** None specific — just read `order-card.tsx` before writing the task, as done here.

## Open Questions (RESOLVED)

All three were answered during planning on 2026-08-29 and are adopted by the plan set. Nothing here is still open; the dispositions are recorded so no downstream agent reopens them.

1. **Does `admin` get `table:update` per D-17, or only `table:read`?**
   - What we knew: D-17's text says `table:update` is "granted to owner and admin." `system-roles.ts:27` currently gives `admin` only `location:['read']` — a strictly more conservative posture than what CTO HIGH-5/Skeptic HIGH-1 originally flagged as the bug (owner-only). D-17 explicitly widens this for the new resource.
   - What was unclear: nothing, actually — D-17's text is unambiguous. Listed only so the planner did not second-guess it against `system-roles.ts`'s current (unrelated) `location` posture.
   - **RESOLVED — adopted verbatim.** Plan 10.3-02 Task 1 grants `table: ['read', 'update']` to both `owner` and `admin`, `table: ['read']` to the `manager` preset, and nothing to `staff`. It also adds a regression pin asserting `admin.location` still equals `['read']`, so a future edit cannot widen the location resource while adding a table grant.

2. **Exact shape of the bulk-create endpoint's transaction boundary for "N tables in one call."**
   - What we knew: TBL-03 requires one zone + N tables in a single transaction, capped, all-or-nothing. CTO MEDIUM-4 recommends a single multi-row `INSERT` rather than N round trips.
   - What was unclear: whether `ScopedTx.insertInto` needed a batch-array overload, given it types `values` as a singular `Omit<T['$inferInsert'], 'tenantId'>` (`packages/db/src/client.ts:94-112`).
   - **RESOLVED — no overload; use the documented escape hatch.** Plan 10.3-05 Task 2 performs the batch through the unrestricted `tx` inside `withTenant`, setting `tenant_id` explicitly on every row, which is the path `client.ts`'s own doc comment names. `ScopedTx` is left unchanged — widening a tenant-injection guard for one caller is a worse trade than one commented escape, and the composite FKs plus the RLS `WITH CHECK` still apply to every row in the batch.

3. **Numeric caps for bulk creation and per-location table ceiling.**
   - What we knew: SPEC says "the cap is a number, not a comment" but never states one. CTO MEDIUM-5 suggests 200/call, 500/location.
   - What was unclear: whether the founder had an opinion on the specific numbers.
   - **RESOLVED — CTO's numbers adopted, 200 per bulk call and 500 active tables per location.** Plan 10.3-06 encodes both as named constants in `table-dto.ts` and enforces them in the Zod DTO and again in the service; plan 10.3-07's e2e case 2 proves the over-cap call is refused with `tenancy.table_bulk_limit_exceeded` and writes nothing. The founder did not object during plan review. Both remain far above any real restaurant's floor size.
