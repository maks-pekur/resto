## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Composite unique indexes created after the FKs that reference them**
- **Found during:** Task 3, first `pnpm nx run db:db:migrate` attempt against the live DB
- **Issue:** `ALTER TABLE ONLY public.restaurant_tables ADD CONSTRAINT restaurant_tables_zone_fk FOREIGN KEY (zone_id, tenant_id) REFERENCES public.table_zones(id, tenant_id) ...` failed with `there is no unique constraint matching given keys for referenced table "table_zones"` — the migration's "Indexes" section (which creates `table_zones_id_tenant_uq`) was written *after* the "Foreign keys" section that needs it. Postgres requires the referenced composite to already be backed by a unique index/constraint before a composite FK can be added; `0000_baseline.sql` (pg_dump-generated) creates its `_id_tenant_uq` indexes before the FK section for the same reason.
- **Fix:** Reordered the migration file — Indexes section now precedes the Foreign Keys section. Transaction rolled back cleanly on the failed attempt (verified `select count(1) from information_schema.tables ...` = 0 before retry), so no partial state existed.
- **Files modified:** `packages/db/migrations/0003_table_zones_and_tables.sql`
- **Verification:** Re-ran `pnpm nx run db:db:migrate` — succeeded. All 8 live-DB assertions below passed. `pnpm nx run db:test` (183 tests against a fresh testcontainers Postgres) green.
- **Committed in:** `7b71dd52`

**2. [Rule 3 - Blocking] `__drizzle_migrations` tracker was stale relative to the live dev database (pre-existing, not caused by this plan)**
- **Found during:** Task 3, applying the migration
- **Issue:** The live dev database (`resto-postgres`, shared with the main checkout) has 84 rows in `drizzle.__drizzle_migrations` from the pre-10.2-squash migration history; the newest recorded `created_at` (`1787730547586`) matches migration `0001_two_factor_verified`'s journal timestamp, but migration `0002_location_slug_and_coords`'s row was never inserted — even though its schema changes (verified: `locations.slug`/`latitude`/`longitude` columns, `locations_slug_format_chk`, `locations_coords_range_chk`, `locations_tenant_slug_uq`) already exist in the live database. `db:migrate` therefore tried to re-run `0002` from scratch, and its non-idempotent `ADD CONSTRAINT` statements failed with `already exists`.
- **Fix:** Verified `0002`'s full intended schema state was already present (four separate `docker exec ... psql` checks), then inserted a single reconciling row into `drizzle.__drizzle_migrations` (`hash` = `sha256` of `0002_location_slug_and_coords.sql`'s file content, computed with the exact algorithm `drizzle-orm`'s migrator uses; `created_at` = the journal's recorded `when` for that entry) so the tracker matches reality. No schema DDL was executed by this fix — only the bookkeeping row.
- **Files modified:** none (live database only, via `docker exec resto-postgres psql`)
- **Verification:** Re-running `db:migrate` afterward correctly skipped `0000`/`0001`/`0002` and applied only `0003`, matching the migrator's own comparison logic (`lastDbMigration.created_at < migration.folderMillis`, read from `node_modules/drizzle-orm/pg-core/dialect.js`).
