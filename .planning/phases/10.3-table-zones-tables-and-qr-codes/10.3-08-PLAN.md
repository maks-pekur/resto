<objective>
Give the scanned sticker a server-side answer: `GET /v1/tables/:id` on a guest host returns the zone name and the table number, and returns 404 for anything else without ever making the menu fail to load.

Purpose: the guest app must not derive the label from the URL text, or a guest can hand-edit their way onto another table. And the label cannot ride `/v1/menu`, which carries `s-maxage=300` and must stay fast on a cold cache — a per-guest table label there would either serve five-minute-stale data or shatter the cache into one entry per table.
Output: one application service, one public controller, module registration, and the contract test that CONTEXT D-28 names as this phase's gate.
</objective>

<!-- Contract, decided here. -->
`GET /v1/tables/:id` → `200 { tableId: string, zoneName: string, number: string }`, or `404` (RFC 7807 problem) for an unknown, archived, malformed or wrong-tenant id.

Response headers on 200: `Cache-Control: public, s-maxage=60, stale-while-revalidate=300` and an `ETag` derived from the table row's `updated_at`. Not "a long public cache": archiving a table would otherwise leave its sticker resolving to a live label at the edge for the cache lifetime and TBL-07's not-recognised state would never appear. A table label is stable; it is not immutable, and this phase itself ships the rename that makes it mutable.

The response deliberately carries **no `locationId`**. Nothing in this phase consumes it, the order path re-derives the location from the table server-side, and shipping it would set the checkout phase up to send a location id from the client — the exact client-authority inversion `apps/api/src/contexts/ordering/application/dto.ts:5-7` exists to prevent. If a later surface needs location-derived data it asks for it keyed by the table id, never by a client-supplied location.

The path is `/v1/tables/:id`, off the `/v1/tenancy/*` authenticated prefix, so there is no ambiguity with plan 10.3-07's admin routes.

`ResolveTableService.execute(tenantId, tableId)` — runs `findActiveTableForResolution` inside the tenant context for the host-resolved tenant and returns `{ tableId, zoneName, number, updatedAt }`, or throws `RestaurantTableNotFoundError` when nothing matches. It returns `updatedAt` for the ETag but the controller must not put it in the body. It does not return `locationId`.

`PublicTableResolutionController` at `@Controller('v1/tables')`, decorated `@ApiTags('tenancy')`, `@Public()` and `@LocationNeutral()`. Both are required: `LocationScopeGuard` does not check `IS_PUBLIC_KEY`, only `LOCATION_NEUTRAL_KEY`, so a public route missing `@LocationNeutral()` 403s with `location.context_required` on every anonymous request.

The `GET :id` handler, in order: compute `effectiveHost(req.headers, trustProxy)` and resolve the tenant with `resolveByCustomerHost`, throwing `NotFoundException` when nothing resolves — do not trust whatever `TenantContextMiddleware` bound, for the reason spelled out above `PublicMenuController`. Then `z.string().uuid().safeParse(id)` and throw `NotFoundException` on failure, so a malformed id is a 404 rather than a validation error the guest app has to special-case. Then call the service, set `Cache-Control: public, s-maxage=60, stale-while-revalidate=300` and an `ETag` derived from the row's `updated_at`, honour `if-none-match` with a 304 exactly as the availability handler does, and return the three-field body. Map `RestaurantTableNotFoundError` to a 404 through the tenancy `mapDomainError`.

An unknown, archived or wrong-tenant id must be indistinguishable from a malformed one — all four are 404. There is no enumeration concern to trade against: table ids are `gen_random_uuid()` v4 with 122 bits of entropy, and the id is physically printed on furniture in a room open to the public, so treating it as a secret would be the wrong threat model. Spend no code on it.

Register `ResolveTableService` in `TenancyModule.providers` and `PublicTableResolutionController` in `controllers`.

Cover, one `it` per claim:

1. A valid id on tenant A's guest host returns 200 with `zoneName === 'Зал 1'` and `number === '14'`, and the body has exactly the three expected keys — assert the key set, so a future `locationId` cannot slip in unnoticed.
2. The response carries `Cache-Control: public, s-maxage=60, stale-while-revalidate=300` and an `ETag`; re-requesting with `if-none-match` set to that ETag returns 304.
3. A random UUID returns 404.
4. A non-UUID string returns 404, not a 400 or a 500.
5. An archived table returns 404 — archive it through the repository or directly in Postgres, then re-request.
6. A table whose zone is archived returns 404, even though the table row itself is still active.
7. Tenant A's table id requested on tenant B's guest host returns 404.
8. A request with no recognisable guest host returns 404 rather than 403 — this is the case that proves `@LocationNeutral()` is present; without it the route would 403 with `location.context_required` on every anonymous request.
