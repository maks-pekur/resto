# Phase 10.3 Plan 08: Public table resolution — the guest sticker's server-side answer Summary

**`GET /v1/tables/:id` resolves a scanned QR sticker to a zone name and table number under the guest's own host, 404s indistinguishably for unknown/archived/zone-archived/malformed/wrong-tenant ids, ignores a stray cross-tenant `x-location-id`, and ships with a 60-second edge cache + real ETag — proven by a 9-case e2e spec, CONTEXT D-28's named gate for this phase.**

## Accomplishments

- `ResolveTableService.execute(tenantId, tableId)`: looks up `findActiveTableForResolution`, throws `RestaurantTableNotFoundError` (already mapped to 404 in `error-mapping.ts` since plan 10.3-05/07) when nothing matches, returns `{ tableId, zoneName, number, updatedAt }` — `updatedAt` never leaves the service.
- `PublicTableResolutionController` at `v1/tables`, `@Public()` + `@LocationNeutral()` at class level: re-verifies the guest host per request (never trusts ALS), 404s a malformed path id before ever calling the service, sets `Cache-Control: public, s-maxage=60, stale-while-revalidate=300` + a real `ETag`, honours `if-none-match` with a genuine 304, returns exactly `{ tableId, zoneName, number }` — no `locationId` anywhere in the file.
- `TenancyModule`: `ResolveTableService` registered as a provider, `PublicTableResolutionController` registered as a controller.
- `public-table-resolution.e2e.spec.ts`: 9 cases, all seeding two tenants + locations + zones + tables directly in Postgres (no HTTP zone-creation dependency on `PUBLIC_APEX_DOMAIN`) — exact-key-set 200, real 304, 404 for random UUID / non-UUID / archived table / zone-archived table / wrong-tenant host / unrecognised host (asserting the response code is not `location.context_required`, proving `@LocationNeutral()` is present), and an unchanged 200 under a foreign `x-location-id` (proving `withoutLocation` from plan 10.3-05 holds).
- Regenerated `docs/api/openapi.yaml` + `packages/api-client/src/generated/api.ts` — purely additive (814 lines added, 0 removed), closing both this plan's new route and plan 10.3-07's table-zones routes that were never emitted after that plan landed.

## Decisions Made

- Followed the plan's exact controller/service shape (`ResolveTableService.execute(tenantId, tableId)`, `PublicTableResolutionController`'s `@Public()` + `@LocationNeutral()`), mirroring `PublicMenuController`'s `requireGuestTenantOr404` idiom byte-for-byte in structure.
- `updatedAt` was added to `RestaurantTableResolution`/`findActiveTableForResolution` (files not in this plan's `files_modified` list) because the plan's own `<action>` text requires the ETag be derived from the row's `updated_at`, and the 10.3-05 port never selected that column — a one-column addition to an existing narrow projection, not a new query.
- `tenantId` is threaded into `ResolveTableService.execute` per the plan's literal signature and parsed defensively (`TenantId.parse`), but not passed into the repository call — the repository already reads the tenant from ALS, which `TenantContextMiddleware` bound from the identical host before the guard/controller ran. Documented inline with a WHY comment referencing ADR-0020 I-6 (`runInTenantContext` is HTTP-middleware-only).
- Seeded the e2e fixture directly in Postgres via `db.withoutTenant(...)`, per the plan's explicit instruction, avoiding any dependency on `PUBLIC_APEX_DOMAIN` (this route's guest hosts use the `.menu.` label, which resolves without the apex env var — confirmed by reading `tenant-resolver.service.ts`'s `guestSlugLabel`).
