<domain>
## Phase Boundary

Give a location table zones and tables, print a QR per table carrying a stable opaque table id, resolve that id server-side into a display label, and make an order carry the table it came from — including taking the order's **location** from the table instead of the tenant's default location.

**What this phase does NOT deliver, discovered during discussion:** a guest cannot place a dine-in order from the QR-menu today, and this phase does not build that. See D-01.

</domain>

## Implementation Decisions

### The dine-in ordering gap — read this first

- **D-01:** **No client can create a dine-in order today, and this phase does not build one.** Verified three ways during the discussion:
  - `apps/qr-menu/src/api/client.ts` exposes exactly two calls, `fetchMenu` and `fetchAvailability`. There is no cart screen, no checkout, no `POST /v1/orders`. The app imports `@resto/cart` and holds a `table` in that store, but nothing ever submits it.
  - The only client that POSTs `/v1/orders` is `apps/website` (`lib/checkout-api.ts:118`), and `components/checkout/checkout-form.tsx:74` hard-collapses the mode to `'delivery'` or `'pickup'` — `dine_in` is never sent.
  - So the `dine_in` branch of `CreateOrderInputSchema` (`ordering/application/dto.ts:28,46`) is exercised by tests only.

  **Founder decision:** 10.3 delivers the platform — schema, CRUD, QR, resolution, the order's table reference and the table→location rule — and **the QR-menu checkout becomes its own phase after this one.** Consequence the planner must accept: TBL-08 and TBL-09 are provable by API-level e2e tests (a `POST /v1/orders` carrying a resolved table id), **not** by a browser walk-through. Do not plan a guest-facing dine-in checkout into this phase, and do not mark the phase incomplete for its absence.

- **D-02:** **Propose the follow-up phase in ROADMAP.md.** "QR-menu ordering and dine-in checkout" — cart screen, checkout form, Stripe payment, guest order-status screen — sequenced immediately after 10.3. This is a roadmap edit for the planner or the founder to apply; it is not built here.

### The order ↔ table contract

- **D-03:** **The free-text `table` field is removed from `CreateOrderInputSchema`.** The client sends only the opaque table id; the server resolves it and writes the label itself. Rationale: with a resolvable id, an accepted free-text field is a hole — anyone could declare themselves any table, and a guest could hand-edit "стол 1" onto their order. The `orders.table_identifier` **column stays** (past orders, seeds, and any non-QR order path that appears later) — only the input field goes.
- **D-04:** **The `dine_in` refine changes meaning.** Today `dto.ts:46` reads "a `dine_in` order must carry a non-empty `table` string". It becomes "a `dine_in` order must carry a table id that resolves". The failure mode moves from a validation error to a resolution failure, and TBL-07's acceptance criterion (4xx on an unresolvable table) is the check.
- **D-05:** **`apps/website` is not touched.** It never sent `dine_in`; removing the DTO field costs it nothing. Do not add a table selector to the site.
- **D-06:** **Location is resolved before the order is priced, from the table when there is one.** `CreateOrderService` currently calls `DefaultLocationResolverService.resolveForTenant(tenantId)` unconditionally (`create-order.service.ts:41`). It becomes: resolved table → that table's `location_id`; no table → the default resolver, exactly as today.

  > **CORRECTED 2026-08-29 after both persona reviews (CTO BLOCK-1, Skeptic BLOCK-2).** The original last sentence of this decision — "everything downstream (pricing, sequence, feed) already keys off `locationId`, so nothing else in the service changes shape" — **was wrong**, and verified wrong by reading the code:
  >
  > - `create-order.service.ts:47` calls `this.pricing.loadSnapshot(tenantId)` — tenant only, no location.
  > - `CatalogMenuPricingAdapter.loadSnapshot` (`ordering/infrastructure/catalog-menu-pricing.adapter.ts:28-35`) then calls `this.defaultLocation.resolveForTenant(tenantId)` **again, internally**, and loads `listStoppedItemIds(locationId)` against that default location.
  > - The guest read path has the identical defect: `GetMenuAvailabilityService.execute()` (`catalog/application/availability/get-menu-availability.service.ts:29`) takes no argument at all and resolves the default location itself.
  >
  > Consequence if left alone: after this phase a guest scanning a table in location B is priced and stop-checked against location A. The order is written to B, so B's stop list stops affecting QR orders entirely and the kitchen is handed a sold-out dish that the guest has already paid for. TBL-09's acceptance criterion passes while this is happening, because it only asserts the stored `location_id`.
  >
  > **This is now in scope — see D-16.**

### The printed output

- **D-07:** **The sheet is a downloadable PDF, generated in the admin browser.** Not a browser print view, and not a server endpoint.
  - _PDF over print view:_ founder's choice — the file can be saved and sent to a print shop.
  - _Browser over server (Claude's call, stated so it can be objected to):_ `apps/admin` is a static Vite SPA and needs a QR library anyway for the on-screen preview and the single-code download. Generating the PDF client-side adds no API surface, no new authenticated route, and no server dependency. If a persona review argues for a server endpoint, the argument to beat is "what does the server know that the browser does not" — the answer today is nothing.
- **D-08:** **The sheet carries bare QR codes. No table number, no restaurant name, no "scan me" line.** _Founder decision, taken against the recommendation and against SPEC.md TBL-10's original text._ Their reasoning: proper sticker layouts will be designed later as templates; this phase should not invent a half-designed one.
  - **Risk the founder accepted, recorded so nobody re-argues it:** a sheet of identical-looking codes has nothing on it telling the operator which sticker belongs to which table. Mis-sticking is possible and would be invisible until a guest's order arrives at the wrong table.
  - **Required mitigation (not a re-litigation — it is what makes the sheet usable at all):** the code order on the sheet MUST be deterministic and stated in the UI — tables ascending by number, left-to-right then top-to-bottom, one zone per document. The screen that offers the download says so in one line.
- **D-09:** **Six codes per A4, roughly 8–9 cm each.** Readable from a phone at arm's length in restaurant light; a 20-table zone is four sheets.
- **D-10:** **The single-table download is an SVG.** Vector, opens in any editor and at any print shop, and it is the right input for the sticker templates the founder plans to design later.

### The admin surface

- **D-11:** **SUPERSEDED 2026-08-29 — the screen is `/locations/:slug/tables`, inside the location's settings space.** It originally placed the screen at `/{locationSlug}/tables` in the sidebar's Operations group, next to the stop list.

  **Why it changed.** The founder is moving the admin to a model where the location stops being a mode you switch into and becomes a plain filter: operational screens (orders, dashboard) carry a `?location=` filter, and configuration screens name their location in their own path. Zones and tables are configuration — they describe a venue, not tonight's service. Putting them in the location's settings space is not only truer to what they are, it **structurally dissolves the write-in-all-mode problem**: you cannot reach the screen without naming a location, so there is no every-location state to guard against. Operational screens keep writing safely in `all` because their writes are per-row and each row carries its own location.

  **Why a sibling route and not a section inside the location card.** `/locations` and `/locations/$slug` are both gated `requirePermission('location', 'create')` — effectively owner-only. Nesting the tables UI inside that page would lock out exactly the manager that D-17's `table:read` was created to admit. `/locations/:slug/tables` sits in the same address space with its own `table:read` gate.

  **Navigation:** the sidebar entry moves from Operations to Administration, gated `table:read`, addressed `/locations/{slug}/tables`; and the location card gains a link to its own floor. Without the sidebar entry a manager would have no route to the screen at all, since `/locations` itself is closed to them.

- **D-12:** **SUPERSEDED by D-17.** It originally read "everything is gated on `location: ['update']` — creating, renaming, archiving and printing alike; no new permission resource is introduced", and described the effect as "owner or admin". Both persona reviews showed that description is factually wrong (`packages/domain/src/rbac/system-roles.ts:27` gives `admin` only `location: ['read']`), and that the gate leaks location archiving. Kept here only so the change is traceable; **implement D-17, not this.**
- **D-13:** **WITHDRAWN as unreachable — and doubly so after D-11's move. Do not build the all-mode picker.** It originally read "in `?location=all` the screen asks the operator to pick a location, same shape as the order feed". The intent stands — a write needs a concrete location (08.5 D-05, 10.1 D-21) — but the screen state it describes cannot occur, verified in the code during research:
  - `apps/admin/src/lib/location-path.ts:5` — `ALL_LOCATIONS_SUB_PATH = '/dashboard'`, commented "the only page with an every-location view, and so the only sub-path that survives without a slug".
  - `apps/admin/src/lib/hooks/use-effective-location.ts:23-28` — the owner's location carrier moved out of `?location=` and into the path segment; a slugless address simply _is_ the every-location view.

  `/{locationSlug}/tables` is a slugged route (D-11), so it always resolves to exactly one location and can never be in `mode: 'all'`. The sidebar already builds its link as `/{locationSlug ?? locations[0].slug}/tables` (`app-sidebar.tsx:60`), so an owner sitting on `/dashboard` lands on their default location's floor. **Plan no picker, no all-mode branch, and no empty state for it** — that code would be unreachable from the first commit. The `/$locationSlug` layout already corrects an unreachable slug before the page renders.

- **D-14:** **10.3 is built before 10.1.** Both phases rewrite the same few lines — the location resolution at `create-order.service.ts:41`. They compose in one order only: **resolve the location (from the table, else the default), then check that location's pause and schedule.** Building 10.3 first means 10.1's checks are written against the correct location from the start; the reverse order means writing them against the default location and reworking them later. 10.1's CONTEXT, RESEARCH, UI-SPEC and three persona reviews are already written and are unaffected.
- **D-15:** **Explicit note for whoever plans 10.1:** its D-15 order-creation gate must sit **after** the table→location resolution this phase introduces, not before it.

### Persona review dispositions (2026-08-29)

Both reviews ran at discuss, before any plan existed. Every BLOCK and HIGH finding was verified against the code by the orchestrator before being accepted — the claims below are confirmed, not relayed. Full reports: `10.3-PERSONA-CTO.md`, `10.3-PERSONA-SKEPTIC.md`. **The planner must read both.**

- **D-16:** **The location-correct stop list and pricing are folded into this phase.** _Founder decision._ Closes CTO BLOCK-1 and Skeptic BLOCK-2 (the same defect found independently from two directions; see the correction under D-06). Concretely: `MenuPricingPort.loadSnapshot` takes the resolved location instead of re-deriving the default one inside `CatalogMenuPricingAdapter`, and `GetMenuAvailabilityService.execute()` accepts a location instead of resolving it itself. The guest read path must answer for the **scanned table's** location, not the tenant's first one. 10.1 D-13's `s-maxage=300` argument does not block this: availability is a separate endpoint at `s-maxage=5` (`catalog/domain/menu-cache.ts:3`). Tracked as **TBL-13** in the amended SPEC.
- **D-17:** **A new `table` permission resource, superseding D-12.** _Founder decision, taken once the reviews showed D-12 did not do what it said._ Two verified problems with the old gate: `admin` holds only `location: ['read']` (`packages/domain/src/rbac/system-roles.ts:27`), so gating on `location: update` made the whole screen **owner-only**; and `location: update` also opens `PATCH /v1/tenancy/locations/:id/archive` on a `@LocationNeutral()` controller (`locations.controller.ts:103,153`) that `LocationScopeGuard` short-circuits, so any custom role handed the key to print a sticker could also archive any location by UUID. The new resource splits it: **`table: ['read']`** — view the floor and download or print a QR, granted to owner, admin and the manager preset; **`table: ['update']`** — create, rename, renumber, archive, granted to owner and admin. Accepted cost, stated so the planner sizes it: a role migration plus a preset re-sync, in the shape `sync-preset-roles.service.ts` already implements. Nothing about the `location` resource changes.
- **D-18:** **The sequencing objection was heard and rejected. Do not reopen it.** Skeptic BLOCK-1 argued the phase order is backwards: build the qr-menu checkout first on today's free-text `?table=`, because that is the shortest path to a guest actually paying, and let 10.3 refine it afterwards. The supporting facts are true — `packages/cart/src/cart.ts:23` types `mode` as `'delivery' | 'pickup' | null`, so the shared cart cannot even express dine-in today. **The founder reaffirmed 10.3 first (D-01, D-14) with the objection in front of them.** Recorded here as considered-and-rejected so no downstream agent re-litigates it.
- **D-19:** **Every new table must be added to `tenancy_erase_tenant`.** CTO BLOCK-3, verified: the function deletes location children by name and then the locations themselves (`packages/db/migrations/0000_baseline.sql:182-184`), and location children are `ON DELETE RESTRICT` (the pattern `member_location_scope_location_fk` uses). A new child table left out of that list turns GDPR erasure into a foreign-key violation for every tenant that ever had a table. Migrations 0072 / 0074 / 0077 exist because of exactly this omission. The phase is not done until an erasure test covers a tenant that has zones and tables.
- **D-20:** **Both new tables need a RESTRICTIVE location-isolation RLS policy, not just tenant RLS.** CTO BLOCK-2. `ScopedTx` filters on tenant only (`packages/db/src/client.ts:80,123`), and `LocationScopeGuard` checks the **bound** location, never an id in the path. A zone id necessarily appears in the path for rename and archive, which makes it exactly as forgeable as a location id would have been — the hole D-22 of phase 10.1 warned about, reappearing one level down. Model the policy on `menu_stop_list_location_iso` in the baseline, and add an explicit location predicate in the repository as the second layer, consistent with the project's ScopedTx-and-RLS rule.
- **D-21:** **The server supplies the QR payload URL; the browser never composes it.** CTO HIGH-2, verified: `apps/admin/src/env.ts` exposes exactly two variables to the bundle (`VITE_STRIPE_PUBLISHABLE_KEY`, `VITE_ADMIN_HOST_SUFFIX`) — the menu apex domain is server-only, and a tenant may carry a custom host in `tenant_domains`. So a table's API representation carries a ready `qrUrl`. This answers the challenge posed in "Claude's Discretion" below — the server does know something the browser cannot. **PDF assembly stays in the browser** (D-07); only the URL comes from the server.
- **D-22:** **Store the zone name and the table number as two columns on the order, not one pre-composed label.** Skeptic HIGH-3. `apps/qr-menu/src/i18n/{en,ru}.json:35` already interpolate `{table}` into a client-side translation, and admin ships three locales; freezing the string "Зал 1 · стол 14" at order time would pin the order's display language to whatever the operator's locale was that day. Same immutability, less work, no locale lock-in. **Amends SPEC TBL-08** — `table_label` becomes `table_zone_name` + `table_number`.
- **D-23:** **The table number gets a numeric sort key.** CTO HIGH-3. `number` is free text (an operator may want "A1" or "терраса-3"), so "ascending by number" sorts lexicographically — 1, 10, 11, 2, 20. That silently inverts D-08's only mitigation, and it is invisible on a six-table demo. Sort on an explicit integer ordinal, with the text number as the tiebreaker.
- **D-24:** **The sheet geometry is recomputed, and gets cut guides.** Skeptic HIGH-4, arithmetic confirmed: A4 is 210 mm, so a 2×3 grid gives 105 mm columns, while a 90 mm code plus its mandatory 4-module quiet zone needs roughly 112 mm. Six 8–9 cm codes per portrait A4 do not fit — the codes must shrink to fit the quiet zone, or the layout must change. Two additions that cost no design work and are not a re-opening of D-08: **cut guides placed outside the quiet zone**, and **the table number printed in the gutter**, so it lands on the offcut and is gone once the sticker is trimmed. The founder asked for bare stickers; a bare _sticker_ is not the same as an unusable _sheet_.
- **D-25:** **Removing `table` from the create-order input is a published contract change.** Skeptic BLOCK-1, verified: the field is in the committed artifact at `docs/api/openapi.yaml:3543` and CI runs an `openapi-drift` job. Regenerating the artifact is part of the change, not an afterthought; the drift job going red is the expected signal, not a surprise.
- **D-26:** **`@resto/cart` changes in this phase.** `packages/cart/src/cart.ts:23-27` holds `table: string | null` and a `setTable(string | null)`. It gains the resolved table id alongside the display parts. Its `mode` union stays `'delivery' | 'pickup' | null` — teaching the cart dine-in belongs to the checkout phase (D-02), not here.
- **D-27:** **Noted, not fixed: there is no operator-side way to create an order, in any milestone.** Skeptic HIGH-2, verified: `operator-orders.controller.ts` exposes feed, detail, accept and advance, and no create; nothing in ROADMAP.md schedules one. TBL-06 removes the last manual table affordance, so a destroyed sticker plus an unreachable owner means that table cannot order all evening. D-17 softens it — a manager can now reprint. The deeper gap is real and belongs to the roadmap, not to this phase.
- **D-28:** **Accepted risk, printing against an unexercised contract.** CTO HIGH-6: this phase ships a print-and-glue surface for a URL shape no client has yet exercised end-to-end, on a database that 10.2 D-12 still declares resettable. It follows directly from D-01 and D-18 and the founder chose that order knowingly. Mitigation available to the planner at no cost: verify one printed code by scanning it before the phase closes, and keep the resolution route's contract test as the phase gate.

### Claude's Discretion

Decided without asking, because they are infrastructure with one defensible answer. Each is open to a persona review's objection.

- **The resolution endpoint is its own public route, not a parameter on `/v1/menu`.** 10.1 D-13 is binding here: `GET /v1/menu` carries `s-maxage=300` and PROJECT.md requires it to stay fast on a cold cache. A per-guest table label on that response would either serve a five-minute-stale table or shatter the cache into one entry per table. A table's label is stable and keyed only by its own id, so its route can carry a long public cache of its own.
- **The resolution response carries what the order needs** — the table id, its display label (zone name + number), and the location it belongs to — so the guest app can both render the strip and later submit an order without a second round trip.
- **Authorisation shape for the admin endpoints.** 10.1 D-22 is a live landmine: `LocationScopeGuard` (`location-scope.guard.ts:39-85`) keys entirely on the ALS-bound location from the `x-location-id` header and never on a route parameter, and `@LocationNeutral()` bypasses it outright. A `/locations/:id/zones` route on a neutral controller would let an operator scoped to location B mutate location A's tables by editing a UUID. **Therefore: no location id in the path.** The zone and table endpoints ride the ALS-bound location like the stop list does. If a route parameter turns out to be unavoidable, the fallback is D-22's own minimum — assert the target location against `MemberLocationScopeReader`, owner bypassing per 08.4 D-05, out-of-scope answered with an existence-hiding 404.
- **Table names in the database:** `table_zones` and `restaurant_tables`. A bare `tables` collides with the `(table) => [...]` callback parameter used in every Drizzle schema file in `packages/db/src/schema/`, and a bare `zones` collides with Phase 9's delivery zones (ROADMAP decision 2).
- **Migrations are hand-written.** See the folded todo below — `drizzle-kit generate` cannot be trusted in this repo right now.
- **No QR dependency reaches the guest bundle.** QR generation lives in `apps/admin` only. `apps/qr-menu/test/bundle-no-dev-leak.spec.ts` guards the guest bundle; the guest app only ever reads a label from the API.

### Folded Todos

- **`drizzle-kit generate` emits a full schema recreation instead of a diff** (`.planning/todos/drizzle-generate-is-broken.md`, 2026-08-26). `packages/db/migrations/` has `0000_baseline.sql` from the 10.2 squash but `meta/` has no `0000_snapshot.json`, so Drizzle has nothing to diff against and treats the whole schema as new — a three-column change produced a 34 KB migration recreating every table. This phase adds two tables and alters `orders`, so it walks straight into it.
  **How it folds:** this phase does **not** own fixing the generator. It owns not being broken by it — **every migration in phase 10.3 is hand-written**, with a header saying why, exactly as `0001_two_factor_verified.sql` does. If a plan runs `pnpm db:generate` and commits the output, the phase ships a migration that fails on any database that already has the tables.

### Reusable Assets

### Established Patterns
