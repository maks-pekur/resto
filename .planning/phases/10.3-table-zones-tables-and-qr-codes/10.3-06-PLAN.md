Write `table-dto.ts` exporting the two cap constants and the Zod schemas plus their `createZodDto` classes:
- `CreateTableZoneInputSchema` — `{ name: TableZoneName, tableCount: z.number().int().min(0).max(MAX_TABLES_PER_BULK_CALL) }`. `tableCount: 0` creates an empty zone, which is a legitimate shape for an operator who will add tables later.
- `AddTablesInputSchema` — `{ count: z.number().int().min(1).max(MAX_TABLES_PER_BULK_CALL).default(1) }`.
- `RenameTableZoneInputSchema` — `{ name: TableZoneName }`.
- `UpdateTableInputSchema` — `{ number: TableNumber }`.
- Response shapes: `TableZoneResponse` (`id`, `name`, `status`, `tables`) and `TableResponse` (`id`, `number`, `ordinal`, `status`, `qrUrl`). `qrUrl` is on every table because the admin bundle cannot compose it — the guest host is server-only state and a tenant may sit on a verified custom domain no formula derives (CONTEXT D-21).

Note that there is no `locationId` field anywhere in these input schemas. The location rides the ALS binding exactly as the stop list does; a location id in a request path or body is the hole 10.1 D-22 identified, where `LocationScopeGuard` keys entirely on the bound location and never on a route parameter.

Write `CreateTableZoneService` with one `execute(input)`. It reads `tenantId` from `requireTenantContext()` and `locationId` from `requireLocationContext()`. Before writing anything: if `input.tableCount` exceeds `MAX_TABLES_PER_BULK_CALL`, throw `TableBulkLimitExceededError` (the Zod schema already refuses it at the HTTP boundary; the service check is what protects any future non-HTTP caller). Then call `countActiveTables(locationId)` and, if the current count plus `tableCount` would exceed `MAX_ACTIVE_TABLES_PER_LOCATION`, throw `LocationTableLimitReachedError` — again before any insert, so a rejected call creates nothing.

Build the table rows as `number: String(i)` and `ordinal: i` for `i` in `1..tableCount`, then hand the whole batch to `repo.createZoneWithTables` in one transaction. A partial-unique-index violation anywhere in the batch rolls the entire transaction back, which is what makes "a constraint violation mid-batch leaves zero rows" a guarantee rather than an accident.

Log at `this.logger.log({ tenantId, locationId, zoneId, tableCount }, 'Table zone created.')` in the project's structured style.
</action>

`ListTableZonesService.execute()` — reads the bound tenant and location, calls `listZonesWithTables(locationId)`, and maps every table through `GuestMenuUrlService` so each carries a ready `qrUrl`. Resolve the tenant snapshot once for the whole list rather than per table.

`AddTablesService.execute({ zoneId, count })` — reads the bound location, loads the zone with `findZoneById(zoneId, locationId)` and throws `TableZoneNotFoundError` when it is missing or archived (an archived zone must not gain tables). Applies the same two caps as Task 1: `count` against `MAX_TABLES_PER_BULK_CALL`, and `countActiveTables(locationId) + count` against `MAX_ACTIVE_TABLES_PER_LOCATION`, both before any write. Reads `maxOrdinalInZone(zoneId, locationId)` and numbers the new tables from there, so adding five tables to a zone of twenty produces 21..25 rather than colliding on 1..5.

`RenameTableZoneService.execute({ zoneId, name })` — loads through `findZoneById(zoneId, locationId)`, throws `TableZoneNotFoundError` when absent. Loading by `(zoneId, locationId)` rather than by `zoneId` alone is the point: the id in the path is exactly as forgeable as a location id would have been, and this predicate plus the RESTRICTIVE RLS policy are what stop a caller bound to location A from renaming location B's zone.

`RenameTableService.execute({ tableId, number })` — loads through `findTableById(tableId, locationId)`, throws `RestaurantTableNotFoundError` when absent. Renumbering changes the display `number` only; the `ordinal` sort key is not derived from it and is not touched here, and the table `id` — the value printed on the sticker — never changes. That is the whole reason the QR carries an opaque id: stickers live on furniture for years and a renumber must not invalidate what is already glued to the floor.

Each service is `@Injectable()` with exactly one public `execute`.

## Trust Boundaries

| Boundary                  | Description                                                                                            |
| ------------------------- | ------------------------------------------------------------------------------------------------------ |
| request body → row count  | An unbounded `tableCount` is a write-amplification vector on a path an authenticated operator controls |
| request path → target row | A zone or table id in the path names a row whose location the guard never checks                       |
| client → location choice  | Nothing in these DTOs lets a client name a location                                                    |

## STRIDE Threat Register

| Threat ID | Category               | Component                                                           | Disposition | Mitigation Plan                                                                                                                                                                                                                                              |
| --------- | ---------------------- | ------------------------------------------------------------------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| T-10.3-23 | Denial of Service      | Unbounded bulk creation                                             | mitigate    | `MAX_TABLES_PER_BULK_CALL = 200` in the Zod schema AND re-checked in the service; `MAX_ACTIVE_TABLES_PER_LOCATION = 500` checked with `countActiveTables` before any insert. Both refuse with a distinct domain error so the 4xx carries a real problem code |
| T-10.3-24 | Elevation of Privilege | Cross-location rename or archive via a forged zone/table id         | mitigate    | Every service loads its target through `findZoneById(id, locationId)` / `findTableById(id, locationId)` with the location taken from `requireLocationContext()`, never from the request                                                                      |
| T-10.3-25 | Tampering              | A client naming the location it wants to write to                   | mitigate    | No input schema in `table-dto.ts` carries a `locationId`; the location rides the ALS binding exactly as the stop list does                                                                                                                                   |
