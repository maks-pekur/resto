# Phase 10.3 Plan 10: Guest QR reader — opaque ?t= resolution, cart carries the table id Summary

**`apps/qr-menu` now reads an opaque `?t=<id>`, resolves it against `GET /v1/tables/:id` in parallel with the menu fetch, renders a server-composed zone+number label or a quiet not-recognised line without ever blocking first paint, and threads the resolved table id through both availability call sites — the free-text `?table=` path and its cart string field are gone entirely.**

## Accomplishments

- `@resto/cart`'s `CartState` replaced the single free-text `table: string | null` with `tableId`/`tableZoneName`/`tableNumber`, set together via `setTable({ tableId, zoneName, number } | null)` — `mode` untouched.
- `packages/ui/src/guest/cart-sheet.tsx` (the one consumer outside `apps/qr-menu`) renders the composed label from the new fields; no other consumer existed (`apps/website` confirmed clean by grep).
- `fetchTable(tableId, signal)` added to `apps/qr-menu/src/api/client.ts`, returning `null` on 404 instead of throwing — the client-side half of TBL-07's soft fail.
- `fetchAvailability` now takes `tableId` as its first parameter, building `/v1/menu/availability?t=<id>` via `URLSearchParams` when a table is present, and the exact bare `/v1/menu/availability` URL (byte-identical to today) when it is not.
- `App.tsx`: `?t=` is read synchronously at mount (a `useState` lazy initializer, never re-read) and `fetchTable` fires in the SAME effect as `fetchMenu`/`fetchAvailability` (lines 49-93: `fetchMenu` at line 52, `fetchTable` at line 72), sharing one `AbortController` — nothing about the menu render waits on table resolution. Both availability call sites (initial fetch line 66, 20s-poll line 100) now pass the table id first; the poll effect's dependency array is `[state.kind, tableIdParam]`.
- `TableBanner.tsx`: `sanitizeTable` and the `?table=` path are deleted outright. Renders nothing (no `?t=`), the resolved label (`t('table.current', { table: 'Zone · Number' })`), or a quiet not-recognised line (`table.notRecognized`, a new key added to both `en.json` and `ru.json`).
- `table.spec.tsx` rewritten against the new contract — 7 cases covering resolved/unrecognised/free-text-ignored/absent/no-textbox/both-availability-URLs-with-and-without-a-table.
- `bundle-no-dev-leak.spec.ts` gained a case asserting the built guest bundle contains no `jsPDF` or `qrcode` marker, making the SPEC's "no QR dependency reaches the guest bundle" constraint a real, checked assertion rather than a claimed one.

## Decisions Made

- Composed label shape: `${zoneName} · ${number}` (e.g. "Terrace · 12"), interpolated into the unchanged `table.current`/`cart.table` locale strings — matches the existing `·` separator convention (`cart.itemCount`).
- `TableBanner` takes one `notRecognized: boolean` prop from `App.tsx`; everything else it needs (`tableZoneName`/`tableNumber`) it reads straight from the cart store, same pattern as `cart-sheet.tsx`. This is the minimal addition needed because the cart store alone cannot distinguish "no `?t=`" from "`?t=` present but unresolved" — both leave `tableId` null.
- Task 3 cases 6/7 keep the App-level `vi.mock` (asserting the stub was called with the right id) AND separately call the REAL `fetchAvailability` (via `vi.importActual`) against a stubbed global `fetch`, per the plan's explicit "a stub can drift from the real function" instruction — this is the assertion that would have caught a caller regression that a pure stub-call-arg check cannot.
- Worktree `node_modules` hazard (documented in 10.3-05-SUMMARY.md) required MORE shadow symlinks than that summary's fix: this plan edits `packages/cart` and `packages/ui` and consumes both from `apps/qr-menu`'s `src/` AND `test/` directories, which are two separate real sibling directories both sitting under the same broken absolute top-level `node_modules` symlink. A shadow under `src/` alone left the test file resolving `@resto/cart` through the stale main-checkout copy — a SEPARATE Zustand store instance from the one `App.tsx` mutated, so `useCartStore.getState().tableId` in the test never reflected the App's `setTable` call. Fixed by adding a third shadow at `apps/qr-menu/test/node_modules/@resto/{cart,ui}` (filesystem-only, gitignored, confirmed via `git check-ignore`).

## Issues Encountered

Two acceptance-criteria greps in the plan undercount by construction, following the precedent set in 10.3-05-SUMMARY.md rather than treating them as failures:

- `grep -c "res.status === 404" apps/qr-menu/src/api/client.ts` returns `3`, not the plan's predicted `2`. The plan's own text ("fetchTable uses the same soft-fail shape as fetchAvailability") only accounts for `fetchTable` and `fetchAvailability`, but the pre-existing `fetchMenu` (untouched by this plan) already contained one `res.status === 404` check of its own before this plan started. Reading the file confirms the semantic bar: `fetchTable` and `fetchAvailability` both `return`/soft-fail on 404 rather than throw, matching exactly.
- `grep -c "fetchAvailability = async (tableId" apps/qr-menu/src/api/client.ts` returns `0`, not the plan's predicted `1`. Prettier (100-char print width, confirmed by running `prettier --write` directly and observing "unchanged") wraps the multi-parameter signature across lines, so the literal substring `async (tableId` never appears on one physical line — `async (` and `tableId: string | undefined,` end up on adjacent lines. `tableId` is confirmed as the first parameter by reading the function signature directly, and both `App.tsx` call sites were compiler-flagged and updated (`pnpm nx run-many -t typecheck` exits 0 across the workspace).
