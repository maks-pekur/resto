# Phase 10.3 Plan 12: Availability answers for the scanned table's location Summary

**`GET /v1/menu/availability` now resolves an optional `?t=<tableId>` to that table's location before answering, the response ETag folds in the answering location so a CDN cannot cross-serve stop lists between locations, and a 12-case e2e against a real two-location database proves both halves of TBL-13 — the guest's stop list and the order's rejection — now key on the identical scanned-table location.**

## Accomplishments

- `GetMenuAvailabilityService.execute(locationId?: string)` — when a `locationId` is supplied it is used directly; when absent, `DefaultLocationResolverService.resolveForTenant(tenantId)` runs exactly as before, so every pre-existing caller (the bare `GET /v1/menu/availability`) is byte-identical in behaviour. The result now also returns the answering `locationId` so the controller can build a location-aware ETag.
- `PublicMenuController.availability()` accepts an optional `@Query('t') t?: string`. After `requireGuestTenantOr404`, `resolveTableLocationId(t)` parses `t` as a UUID (`z.string().uuid().safeParse`) and, only if it parses, calls `TABLE_ZONE_REPOSITORY.findActiveTableForResolution(t)` (injected via `TenancyModule`, already imported by `CatalogModule`). An absent, malformed, unknown, or archived `t` all resolve to `undefined`, which `GetMenuAvailabilityService.execute` treats as "use the default" — the endpoint never 4xxs on a bad table id, satisfying TBL-07/T-10.3-54 (the guest app polls this every 20s and a dead sticker must still show a working menu).
- The ETag changed from `"<stopVersion>"` to `"<stopVersion>:<answeringLocationId>"` (`apps/api/src/contexts/catalog/interfaces/http/public-menu.controller.ts:205`: `const etag = '"' + stopVersion.toString() + ':' + answeringLocationId + '"';`), closing T-10.3-53 — a CDN could otherwise hand location A's cached response to a guest at a table in location B, since the URL differs by table id but a naive proxy keying purely on path+query could still coalesce identical stop-version responses across locations if the ETag itself didn't vary.
- `apps/api/test/e2e/table-location-availability.e2e.spec.ts` — 12 `it` cases, one real Postgres+NATS stack, one tenant, two locations (A default, B non-default), a published two-item menu, one item stopped in B only via the real `POST /v1/catalog/stop-list` write path. Covers: per-table stop-list answers (1-2), the unchanged no-`?t=` default (3), 200-not-4xx on unknown/malformed `?t=` (4-5), differing ETags across locations (6), the order-side rejection and acceptance from B vs. A (7-8), the pickup-with-no-table default-location fallback (9), the HTTP-level 400 `ordering.table_not_resolved` for both an unknown uuid and an archived table with a Postgres-verified zero-row-delta (10), the stray-`x-location-id`-changes-nothing proof on both `GET /v1/menu/availability` and `GET /v1/tables/:id` (11), and TBL-08's rename/renumber immutability — an order's frozen `table_zone_name`/`table_number` survive a later zone rename and table renumber, while the live `GET /v1/tables/:id` route reflects the new values (12).

### Case 7 regression proof (plan-required manual verification)

Per the plan's acceptance criteria ("Reverting plan 10.3-09's `loadSnapshot(tenantId, locationId)` change makes case 7 fail — confirm once by hand and record the observed failure"): `CatalogMenuPricingAdapter.loadSnapshot` was temporarily edited to ignore its `locationId` argument and instead resolve the tenant's default location internally (reintroducing the exact pre-10.3-09 shape, via `DefaultLocationResolverService` — already available in `OrderingModule`'s scope through its existing `CatalogModule` import, so no module wiring changes were needed). Running case 7 alone against that regression produced:

```
× case 7 — a dine_in order from table B for the stopped item is rejected as unavailable, and writes no orders row
  AssertionError: expected 201 to be 422 // Object.is equality

  + Received: 201
```

This confirms the defect this plan closes: with the location-blind pricing port, the order from table B (where the item is stopped) is priced against the tenant default (location A, where it is NOT stopped) and succeeds instead of being rejected — exactly the TBL-13 failure mode the plan describes. The temporary edit was reverted via `git checkout -- apps/api/src/contexts/ordering/infrastructure/catalog-menu-pricing.adapter.ts` immediately after observing the failure; `git diff` and `git status --short` confirmed a clean working tree before re-running the full 12-case suite green.
