# Phase 10.3 — CTO Review (pre-planning, technical shape)

**Reviewed:** 2026-08-29 · **Scope:** design shape only, no 10.3 code exists yet
**Inputs:** `10.3-SPEC.md` (12 locked requirements), `10.3-CONTEXT.md` (D-01..D-15 + Claude's Discretion), `ROADMAP.md:701-728`, `10.1-CONTEXT.md` (D-13/D-21/D-22), `CLAUDE.md` §Architectural Constraints, and the live code cited below. Every invariant claim here was verified against the code, not against the prior audits.

## Verdict

The phase is correctly scoped and the two big judgement calls — **opaque table id in the sticker** and **no location id in the path** — are both right and both well argued. The schema shape, the archive-only lifecycle, the separate resolution endpoint and the decision to defer checkout are all defensible.

What will break it is narrower and more specific than the document expects. **Three things must be settled before a plan is written:**

1. **D-06 is wrong about pricing.** `MenuPricingPort.loadSnapshot(tenantId)` re-derives the _default_ location internally and loads _that_ location's stop list. Once a table decides the order's location, a dine-in guest at location B is priced and 86-checked against location A. This is a wrong-food-to-a-paying-guest bug on the money path, and D-06 explicitly asserts the opposite ("nothing else in the service changes shape").
2. **"An RLS policy" (singular) is not enough.** Without a RESTRICTIVE `location_iso` policy on both new tables, "no location id in the path" does _not_ close D-22's hole — the zone id in the path reopens it identically.
3. **`tenancy_erase_tenant` will start failing** for every tenant that has tables, because the function deletes `locations` last and every location child in this schema is `ON DELETE RESTRICT`.

Beyond that: the admin browser **cannot** construct the QR payload URL (the guest host is server-only state), and D-08's deterministic-ordering mitigation is destroyed by the act of cutting the sheet. Both have cheap fixes that don't reopen founder decisions.

**Nothing here argues for a bigger phase.** Every fix below is tens of lines or a paragraph in the plan. My estimate of net added effort: ~1 day, almost all of it in the migration and the pricing port signature.

## Findings

### BLOCK-1 — D-06 is factually wrong: the stop list and pricing key on the DEFAULT location, not the order's location

D-06 says: _"Everything downstream (pricing, sequence, feed) already keys off `locationId`, so nothing else in the service changes shape."_ That is not what the code does.

`apps/api/src/contexts/ordering/application/create-order.service.ts:47` calls `this.pricing.loadSnapshot(tenantId)` — **tenant only, no location**. The adapter then resolves its own location:

```
apps/api/src/contexts/ordering/infrastructure/catalog-menu-pricing.adapter.ts:28-35
  const [version, locationId] = await Promise.all([
    this.versions.current(tenantId),
    this.defaultLocation.resolveForTenant(tenantId),   // ← the DEFAULT location
  ]);
  const [menu, stoppedItemIds] = await Promise.all([
    this.catalog.loadPublishedMenu(tenantId, version),
    this.catalog.listStoppedItemIds(locationId),        // ← that location's 86 list
  ]);
```

The stop list is location-grain — 08.4 D-02 says so and the schema proves it (`menu_stop_list` carries `location_id` and a RESTRICTIVE location policy, `packages/db/migrations/0000_baseline.sql:1179`). So after D-06 lands:

- A dish that is **sold out at location B** can still be ordered by the guest sitting at a table in location B, because `stopped` at `create-order.service.ts:52,61` was built from location A's list. The order is taken, the money is captured, and the kitchen cannot make it.
- A dish that is stopped only at **location A** is refused to a guest at location B for no reason.

This is invisible to every single-location test and to every test that mocks the pricing port — which `apps/api/test/unit/create-order.service.spec.ts` does.

**Do this (small):** change the port to `loadSnapshot(tenantId, locationId)` (`apps/api/src/contexts/ordering/domain/ports.ts:59`), pass the resolved location from `create-order.service.ts:47`, and delete `DefaultLocationResolverService` from `CatalogMenuPricingAdapter` entirely. ~10 lines plus the port signature. **Acceptance evidence must be a real-DB test:** two locations, an item stopped only at B, a table in B, `POST /v1/orders` → 4xx and zero `orders` rows.

Without this, D-06 ships a phase whose headline feature quietly corrupts the order path.

### BLOCK-2 — "an RLS policy" on the two new tables is not enough; without a RESTRICTIVE location policy, "no location id in the path" closes nothing

The discretion block gets the diagnosis exactly right — `LocationScopeGuard` keys entirely on the ALS-bound location and never on a route parameter (`apps/api/src/contexts/identity/interfaces/http/guards/location-scope.guard.ts:33,61-76`) — and then draws a remedy that does not follow.

**The zone id and the table id are unavoidably in the path.** TBL-04 requires "rename a zone", "archive a table", "add a table to an existing zone". Those are `PATCH /v1/tenancy/table-zones/:zoneId`, `PATCH .../tables/:tableId`. Removing the _location_ id from the path does not remove the _zone_ id, and the zone id is exactly as forgeable.

Check what actually guards that call today:

- `LocationScopeGuard` proves the caller may act **in the bound location**. It says nothing about the location the row in the path belongs to (`location-scope.guard.ts:61-76`).
- `ScopedTx` filters **tenant only** — `eq(table.tenantId, this.tenantId)` at `packages/db/src/client.ts:80` (select) and `:123` (update). There is no location dimension anywhere in `ScopedTx`.
- Postgres RLS: the tenant policy shape (`locations_iso`, baseline:1137) allows any row of the same tenant.

So `PATCH /table-zones/<a zone in location B>` with `x-location-id: <location A>` succeeds for a caller scoped only to A. Same class of bug as D-22, different key.

**Do this — all three, they are the CLAUDE.md double-enforcement rule applied honestly:**

1. **`restaurant_tables` carries `location_id`** (SPEC TBL-02 already says so — keep it, it is denormalised on purpose and it is what makes the policy possible) and **`table_zones` carries `location_id`**.
2. **Both tables get two policies, not one** — the tenant policy _and_ a RESTRICTIVE location policy copied verbatim from `menu_stop_list_location_iso` (baseline:1179):
   `AS RESTRICTIVE USING (is_system_session() OR current_location_id() IS NULL OR location_id = current_location_id())` with the same `WITH CHECK`.
3. **The repository filters location explicitly** on every read and write — `scoped.selectFrom(tableZones, and(eq(zones.locationId, requireLocationContext()), …))`. ADR-0020 I-1 requires the app-layer filter on top of RLS; here it is not redundant, it is the thing that turns a silent empty result into a deliberate one.

**Acceptance criterion to add to the SPEC:** the existing TBL-05 criterion ("403 or an empty list for location B's zones") passes with a location-scoped LIST while the MUTATION path stays wide open. Add: _"a member scoped to location A, sending `x-location-id: A`, cannot rename or archive a zone or table belonging to location B — verified at the e2e layer and again at the Postgres layer with a raw statement."_ `packages/db/test/integration/tenant-isolation.spec.ts:500` and `:823` are the existing templates for the DB half.

### BLOCK-3 — this phase breaks GDPR tenant erasure, and no existing test would catch it

`tenancy_erase_tenant` (`packages/db/migrations/0000_baseline.sql:128`) deletes children first and finishes with:

```
  DELETE FROM catalog_location_stop_version WHERE tenant_id = p_tenant_id;
  DELETE FROM member_location_scope WHERE tenant_id = p_tenant_id;
  DELETE FROM locations WHERE tenant_id = p_tenant_id;
```

Every location child in this schema declares its composite FK `ON DELETE RESTRICT` — `member_location_scope_location_fk` (`packages/db/src/schema/locations.ts:90`), `orders_location_fk` (`packages/db/src/schema/ordering.ts:76`), `order_daily_sequences_location_fk` (`ordering.ts:127`). Two new RESTRICT children plus `orders.table_id → restaurant_tables` means the erase function raises `foreign_key_violation` and the erasure **fails hard** for exactly the tenants that used the feature.

Neither `10.3-SPEC.md` nor `10.3-CONTEXT.md` mentions the function. And nothing will catch it:

- `packages/db/test/integration/erase-includes-ordering.spec.ts` and `tenancy-erase-guard.spec.ts` create no zones and no tables, so they stay green.
- The only schema-wide assertion in the repo covers RLS flags, not erasure coverage (`tenant-isolation.spec.ts:53`).
- 10.1-CONTEXT records that migrations `0072`, `0074`, `0077` existed _only_ because this was forgotten three times. This is the fourth opportunity.

CLAUDE.md lists GDPR full erasure as a hard compliance constraint. A silently-broken erasure pipeline is the single worst thing this phase can ship.

**Do this:** the phase's hand-written migration adds, in the correct order (after `orders`, before `locations`):

```
  DELETE FROM restaurant_tables WHERE tenant_id = p_tenant_id;
  DELETE FROM table_zones WHERE tenant_id = p_tenant_id;
```

and the phase adds one integration spec that seeds a zone + tables + an order referencing a table, runs `tenancy_erase_tenant`, and asserts it returns cleanly with zero rows left. ~30 lines.

**Recommend also (cheap, prevents the fifth time):** a schema-driven test that enumerates every table with a `tenant_id` column (the query at `tenant-isolation.spec.ts:57-68` already does the enumeration) and asserts the erase function's source text names each one. That is a ~15-line test that permanently closes a recurring class of defect.

### HIGH-1 — the guest's _availability_ read has the same default-location bug, so the menu shows the wrong 86 list

BLOCK-1's read-path twin. `GetMenuAvailabilityService.execute()` takes no location and resolves the default one itself:

```
apps/api/src/contexts/catalog/application/availability/get-menu-availability.service.ts:29
  const locationId = await this.defaultLocation.resolveForTenant(tenantId);
```

`apps/qr-menu/src/App.tsx:57,72` polls `/v1/menu/availability` every 20s. After 10.3, a guest scanning a table in location B browses location A's stop list — sold-out items look available right up to the moment BLOCK-1's fixed order path rejects them. That is a worse guest experience than today, because today the mismatch is at least consistent.

**Do this:** once a table has resolved, availability must be fetched for that table's location. Practical shape: `GET /v1/menu/availability?t=<tableId>` (server derives the location from the table; ignores an unresolvable id and falls back to the default, per TBL-07's fail-soft rule). This does shard the `s-maxage=5` cache per location — that is fine, five seconds and a handful of locations per tenant. Do **not** put it on `/v1/menu` (10.1 D-13 is right and the `s-maxage=300` is real: `apps/api/src/contexts/catalog/domain/menu-cache.ts:1`, applied at `public-menu.controller.ts:221`).

If the planner wants to keep this out of 10.3, that is arguable — but then say so explicitly and record that a scanned guest sees the wrong stop list until the checkout phase. Silently shipping it is not an option.

### HIGH-2 — the admin browser cannot build the QR payload URL; the server is the only thing that knows the guest host

D-07 invites an objection and names the bar: _"the argument to beat is 'what does the server know that the browser does not' — the answer today is nothing."_ The answer is not nothing.

The sticker URL is `https://<slug>.menu.<domain>/?t=<id>`. Where does `<domain>` come from?

- Server side it is `PUBLIC_APEX_DOMAIN` (`apps/api/src/config/env.schema.ts:154`), combined with the literal `menu` label in `apps/api/src/contexts/tenancy/application/tenant-resolver.service.ts:9,105`.
- **Or it is not that shape at all.** `resolveByCustomerHost` tries `findByDomainHost(hostname)` _first_ (`tenant-resolver.service.ts:80`). `tenant_domains` (`packages/db/src/schema/tenants.ts:123-142`) holds `kind ∈ {'subdomain','custom'}` with `is_primary`, and `apps/admin/src/routes/(protected)/tenant.domains.tsx` already lists them. A tenant on a verified custom domain has a guest host that no formula can derive.
- Admin side, the entire client env surface is two variables: `VITE_STRIPE_PUBLISHABLE_KEY` and `VITE_ADMIN_HOST_SUFFIX` (`apps/admin/src/env.ts:20-21`). There is no menu host and no apex.

Adding a `VITE_MENU_HOST_SUFFIX` would produce a **permanently wrong URL for every custom-domain tenant**, baked into vinyl glued to furniture. This is the exact class of thing server-side authority exists for.

**Do this — it preserves D-07 entirely:** the zone/table list response carries a server-built `qrUrl` per table (and the single-download endpoint returns the same string). The browser keeps generating both the SVG and the PDF; it just stops inventing the payload. The server builds it from the tenant's primary verified domain if one exists, else `<slug>.menu.<PUBLIC_APEX_DOMAIN>`. ~20 lines in a small `guest-menu-url.ts` helper in the tenancy context, and it becomes the one place that shape is written down.

Everything else in D-07 stands: browser generation, no new authenticated route for the PDF, no server rendering dependency. I agree with client-side generation. I disagree that the browser knows what to encode.

### HIGH-3 — if `number` is free text, "ordered by table number ascending" is lexicographic, and D-08's only mitigation inverts

TBL-10 requires the sheet to be _"ordered by table number ascending, left-to-right then top-to-bottom"_, and D-08 elevates that ordering from an implementation detail to **the entire reason an unlabelled sheet is usable**. The SPEC never says what type `number` is, and TBL-02 calls it _"a display label only"_ while TBL-04 requires _"renumber a table"_ — which reads like `text`.

With `text`, ascending is `1, 10, 11, 12, …, 19, 2, 20, 3, …`. A 20-table zone prints in an order no operator will ever guess, and the mitigation becomes the mis-sticking machine it was meant to prevent. Worse, it works perfectly in the 6-table demo and breaks at 10.

**Do this — decide it now, do not leave it to the planner.** Two acceptable answers:

- **`integer`.** Bulk creation is already `1..N` (TBL-03) so the numeric case is the designed one. Loses `A1` / `Терраса-3` labels; a restaurant that wants those uses a zone name plus a number.
- **`text` plus an explicit sort key.** Store `number text` for display and a generated `sort_key` (zero-padded, or a `(numeric_part, text_part)` pair) and sort on that. More code, keeps real-world labels.

I would take `integer` for MVP-1 and let a later phase add an optional `label` column beside it if a tenant actually asks. But whichever is chosen, the acceptance criterion must exercise a zone of **at least 12** tables, not the 20 that happens to be even — a 20-table zone in lexicographic order still puts `1,10,11,12,…` on page one, which is visibly wrong; the plan should assert the exact expected sequence.

### HIGH-4 — D-08's mitigation does not survive the physical workflow, and the phase ships no way to check a stuck sticker

I am not re-litigating bare codes. The founder decided, the reasoning (don't invent a half-designed layout) is sound, and the SPEC is amended. But the _stated mitigation_ does not work, and saying so is the job.

**Deterministic ordering exists only while the codes are attached to the sheet.** The operator prints four A4 sheets, cuts out 24 squares, and carries a stack of visually identical white squares onto the floor. At the moment of cutting, the ordering information is destroyed. Nobody cuts one code, walks it to a table, comes back, cuts the next. The mitigation protects the one step of the workflow that was never at risk.

For calibration: Toast's equivalent tool generates **labelled signs per service area and table** — labelling is the industry default precisely because of this failure mode ([Toast Mobile Order & Pay FAQ](https://support.toasttab.com/en/article/Toast-Mobile-Order-and-Pay-FAQs), [Toast QR code generation](https://support.toasttab.com/en/article/Generating-QR-Codes-for-Menus-and-Online-Ordering)).

**Two fixes, neither of which touches the sticker artwork the founder is deferring:**

1. **The PDF's first page is a plain checklist**, not a sticker: a text table of `sheet 2, position 3 → стол 9`, with a tick column. It is not a design; it is a packing slip. The operator cuts, then works down the list. This restores the ordering guarantee across the cut.
2. **Say in the UI how to verify a stuck sticker.** TBL-06 already makes this free: scan the sticker with any phone and the guest strip shows `Зал 1 · стол 14`. Without one line of copy saying so, a mis-stick is undetectable until a guest's food goes to the wrong table weeks later, and the operator has no idea a verification path exists. One sentence next to the download button.

If both are rejected, record explicitly that the phase ships a physical artifact whose correctness cannot be verified after installation. That is a decision the founder can make, but it should be made knowingly.

### HIGH-5 — D-12's permission claim is wrong, and gating on `location:update` hands out location archive

D-12 states the consequence as _"a manager cannot reprint a damaged sticker without an owner or admin."_ Checked against the code, it is stricter and more dangerous than that.

- `packages/domain/src/rbac/system-roles.ts:13` — **only `owner`** has `location: ['update']`.
- `system-roles.ts:27` — `admin` has `location: ['read']`. An admin cannot reprint either.
- `packages/domain/src/rbac/preset-roles.ts:13-40` — `manager`, `cashier-foh` and `kitchen` have **no `location` verb at all**, not even `read`. If the list/read path is gated on any `location` action, none of them can open the screen.

So D-12 as written makes the entire table surface **owner-only**, including reading it. That is not what the sentence in the document describes, and it is worth the founder knowing before it ships.

Then the second-order problem. The only way for an owner to delegate table management is to mint a custom role carrying `location:update` via the `ac` surface. The moment they do:

- `LocationsController` is `@LocationNeutral()` (`apps/api/src/contexts/tenancy/interfaces/http/locations.controller.ts:103`) and exposes `PATCH :id` and `PATCH :id/archive`, both gated on `location:update` (`:138`, `:153`).
- `UpdateLocationService.execute` (`apps/api/src/contexts/tenancy/application/update-location.service.ts:23-37`) and `ArchiveLocationService.execute` (`archive-location.service.ts:17-33`) do **zero** location-scope checking. They load by id under tenant scope and write.

So a "manager, location A" custom role created to let someone manage tables can **archive location B** by editing a UUID. Today that path is unreachable only because `location:update` is owner-only and owners bypass scoping anyway (08.4 D-05). D-12 is the decision that makes it reachable.

**Do this:**

1. **Split the gate.** List + print → `location: ['read']` (admin and staff already have it; presets need one line each if managers should see the screen). Create / rename / archive → `location: ['update']`. Printing is a read of data the operator can already see; treating it as a write is what forces the dangerous grant. This introduces no new permission resource, which was D-12's stated constraint.
2. **Close the existing hole in the same pass** — it is D-22's own stated minimum and it is ~15 lines: in `UpdateLocationService` and `ArchiveLocationService`, assert the target location is in the caller's scope via `MemberLocationScopeReader` (`apps/api/src/contexts/identity/application/ports/member-location-scope-reader.port.ts`), owner bypassing per 08.4 D-05, out-of-scope → existence-hiding 404. This phase is the first one whose decisions make the hole reachable; it should be the one that closes it.

If the founder wants to keep printing owner-only, that is a legitimate product call — but then the read path must still be `location:read` or the screen is invisible to everyone but the owner.

### HIGH-6 — D-01 is the right call for the API; it is the wrong call for the _printed sheet_

**On the deferral itself: I agree.** The three verifications in D-01 are correct — `apps/qr-menu/src/api/client.ts` exposes exactly `fetchMenu` and `fetchAvailability` and nothing else; `apps/website/components/checkout/checkout-form.tsx:74` does collapse the mode to `'delivery' | 'pickup'`, so `dine_in` is never sent from any client. Building the schema, the resolution and the order↔table contract without the checkout is a legitimate slice, and the API-level e2e evidence D-01 proposes is genuinely sufficient for TBL-08 and TBL-09. `apps/api/test/e2e/` already holds `order-lifecycle`, `order-short-number` and `location-isolation` specs — the harness exists.

**Where the deferral breaks down is TBL-10.** The PDF is not code; it is an instruction to a human to perform an irreversible physical act. Shipping a download button that produces stickers for an ordering flow that does not exist means one of two things happens: the operator glues 300 codes that lead to a menu with no checkout (and concludes the product is broken), or nobody uses the feature and it ships unexercised anyway.

Two compounding risks:

- **The ids are minted from a database that is still declared resettable.** 10.2 D-12 records that a dev-database reset is acceptable "while no real tenant data exists". `id` is `gen_random_uuid()` (`packages/db/src/schema/_columns.ts:9-12`), so a reset re-mints every table id and kills every glued sticker. Between D-01 and D-12, the window in which someone prints against throwaway ids is exactly this phase.
- **The URL contract has never been walked end-to-end by a browser.** Scan → resolve → cart → checkout → kitchen has never run. The first time it runs is after the stickers are on the furniture.

**Do this (cheap, no scope change):**

1. **The phase's own acceptance bar keeps a browser step** even without checkout: scan a real `?t=<id>` link on a phone against the dev stack, confirm the server-supplied label renders, confirm an unknown id renders the not-recognised state. That is TBL-06/TBL-07 and it costs ten minutes.
2. **The download surface carries an explicit not-yet-orderable state** until the checkout phase lands — one banner line on the tables screen. Remove it in the checkout phase's plan.
3. **Record in the ROADMAP entry for the checkout phase** that the dev-database reset allowance (10.2 D-12) is void once any tenant has printed a sheet. This is the trigger; write it down where someone will read it.

And D-02's roadmap edit — "QR-menu ordering and dine-in checkout" sequenced immediately after 10.3 — should be applied _with_ the first plan of this phase, not after it. A platform phase whose payoff phase is not on the roadmap is how a platform phase becomes permanent.

### MEDIUM-1 — the resolution response should not carry `locationId`

The discretion block says the response carries _"the table id, its display label, and the location it belongs to — so the guest app can both render the strip and later submit an order without a second round trip."_

Nothing in this phase consumes it (D-01: no client submits an order), and the order path re-derives the location from the table server-side anyway (D-06). Shipping it now sets up the next phase to **send** a location id from the client — which is precisely the client-authority inversion this codebase deliberately avoids:

```
apps/api/src/contexts/ordering/application/dto.ts:5-7
  // Prices and discounts are resolved server-side from the published catalog
  // (API review 2026-06-15 BLOCK-1) — the client sends only what it selected
  // (item, size, modifier options, quantity, display names), never money.
```

Same principle: the client sends the table id it scanned; the server decides everything that follows from it. **Return `{ tableId, label }`.** If the checkout phase needs location-derived data (a location-correct stop list — see HIGH-1), it should ask for it _keyed by the table id_, never by a client-supplied location id.

Consistent with this: D-03's removal of the free-text `table` field from `CreateOrderInputSchema` is exactly right and for exactly this reason. Do not undo it one field over.

### MEDIUM-2 — "a long public cache" is the wrong TTL, and the endpoint must re-verify the host

The reasoning for a separate route is correct and I agree with it — the `s-maxage=300` on `/v1/menu` is real (`apps/api/src/contexts/catalog/domain/menu-cache.ts:1,5`, applied at `public-menu.controller.ts:221`), and per-guest table state on that response would either serve five-minute-stale data or shred the hit rate. 10.1 D-13 binds and the discretion block honours it.

Two corrections to the shape:

**TTL.** _"A long public cache of its own"_ means that archiving a table (TBL-04) leaves its sticker resolving to a live label at the edge for the cache lifetime, and TBL-07's "not recognised" state never appears. The order path is the real gate so this is display-only — but the honest shape is `public, s-maxage=60, stale-while-revalidate=300` plus an `ETag` derived from the row's `updated_at`, mirroring the discipline already applied to availability (`menu-cache.ts:3`, `public-menu.controller.ts:194-200`). A table label is stable; it is not immutable, and the phase itself ships the rename that makes it not immutable.

**Host verification.** The endpoint must be `@Public()` **and** `@LocationNeutral()` — `LocationScopeGuard` does not check `IS_PUBLIC_KEY`, only `LOCATION_NEUTRAL_KEY` (`location-scope.guard.ts:27-31`), so a public route without it 403s with `location.context_required`. And it must re-verify the request's own host through `resolveByCustomerHost` exactly the way every handler on `PublicMenuController` does (`public-menu.controller.ts:255-261`), not trust whatever `TenantContextMiddleware` bound. The comment at `public-menu.controller.ts:156-167` explains why: the middleware's fallback chain also resolves the reserved plain `<slug>.<apex>` host, and trusting ALS would let table resolution answer there too.

### MEDIUM-3 — a guest-supplied `x-location-id` can 500 every order, and D-06 is the free moment to fix it

`TenantContextMiddleware.resolveLocationHeader` (`apps/api/src/shared/tenant-context.middleware.ts:83-87`) accepts `x-location-id` from **any** caller on **any** route — including the `@Public()` guest host, since `resolveContext` attaches it before the customer-host branch returns (`:68-73`). `withTenant` then binds it as a GUC (`packages/db/src/client.ts:252-253`).

`POST /v1/orders` is `@Public() @LocationNeutral()` (`apps/api/src/contexts/ordering/interfaces/http/orders.controller.ts:36-38`). Inside, `OrderSequenceDrizzleRepository.nextShortNumber` inserts into `order_daily_sequences` (`apps/api/src/contexts/ordering/infrastructure/order-sequence-drizzle.repository.ts:11-28`) — **outside** any `withLocation`, because `create-order.service.ts` only wraps the save (`:151`) and not the sequence (`:126`). `order_daily_sequences_location_iso` is RESTRICTIVE (baseline:1187), so a bound location that differs from the row's `location_id` fails `WITH CHECK` and the request 500s.

Net: any anonymous caller sending `x-location-id: <random uuid>` breaks order creation. Pre-existing, but D-06 is rewriting exactly these lines.

**Do this:** resolve the location first (from the table, else the default), then wrap the **whole remainder** of `execute()` in `withLocation(locationId, …)` rather than wrapping only `repo.save`. That makes the ALS location authoritative from the resolution point onward, kills the header vector for free, and is the correct shape for 10.1's schedule gate to sit inside (D-15).

Separately worth a todo, not this phase: `x-location-id` should be ignored on `@Public()` routes at the middleware. And `nextShortNumber` uses raw `tx.insert` rather than `ScopedTx.insertInto`, which is an ADR-0020 I-1 exception nobody recorded.

### MEDIUM-4 — number uniqueness must be a partial unique index, not application code

TBL-02 requires two active tables numbered `1` in one zone to fail; TBL-04 requires archived rows excluded from the check; TBL-03 requires a mid-batch violation to leave zero rows. All three are only simultaneously true if the constraint lives in Postgres:

```
CREATE UNIQUE INDEX restaurant_tables_zone_number_active_uq
  ON restaurant_tables (tenant_id, zone_id, number) WHERE status = 'active';
```

An application-level "does this number exist" pre-check races with a concurrent add-table and makes TBL-03's "creates nothing" criterion accidental rather than guaranteed. State the index in the plan so it does not get invented at implementation time.

Also: bulk creation should be **one multi-row insert**, not N round trips inside the transaction — at the cap (see MEDIUM-5) the difference is a hundred network hops on a write path an operator is watching.

### MEDIUM-5 — the bulk cap is still not a number

`10.3-SPEC.md:118` says _"the cap is a number, not a comment"_ and then never gives one. `10.3-CONTEXT.md` does not either. That means the planner invents it, and an invented number never gets reviewed.

## Direct answers to the questions asked

### The opaque table id in a public URL — enumeration, scraping, ordering from home, rate limiting

**Enumeration: not a risk.** `gen_random_uuid()` is v4 — 122 bits. There is no enumeration attack. Do not spend a line of code on it.

**Scraping: treat the id as public knowledge, not a secret.** It is printed on furniture in a room open to the public; anyone who has ever sat at the table has it forever, and can photograph every table in the venue in five minutes. Any design that assumes the id is confidential is wrong from the start. The current design does not make that assumption — good.

**Ordering "to a table" from home: real, unmitigated, and correctly left unmitigated in this phase.** The economics bound it: the order is paid up front (SPEC boundaries: _"an order is paid up front and closed"_), so the prankster funds their own prank. The damage is a plated dish carried to an empty table and an operator cancel-with-refund, which shipped in Phase 10. Do **not** attempt to solve it with geofencing, short-lived tokens or rotating ids — every one of those contradicts ROADMAP decision 1 ("stickers outlive renames") and would be the single most expensive mistake available here. If it ever becomes a real problem, the right lever is in the checkout phase: flag a dine-in order for a table with no recent activity as operator-visible, do not reject it.

**Rate limiting: adequate, with one thing worth knowing.** The public bucket is `RATE_LIMIT_PUBLIC_PER_MIN`, default **60/min** (`apps/api/src/config/env.schema.ts:255`), keyed by `ip:${req.ip}` for a caller with no session cookie (`apps/api/src/shared/security.ts:66-74`). One resolution call per scan sits nowhere near that. Two caveats: the store is in-process, so with N replicas the effective ceiling is N×60 (fine here, relevant elsewhere); and **every guest in a venue behind one NAT shares one bucket**. A 200-seat restaurant on a single public IP is already within an order of magnitude of 60/min once the menu poll (20s, `App.tsx:23`) and the checkout phase's calls are counted. Not a 10.3 blocker. Worth a todo before the checkout phase: the guest bucket should key on something with per-device cardinality, or the public cap should be raised with the CDN carrying the load.

### Scalability and cost: many locations, hundreds of tables, the resolution endpoint on the hot path

**Data volume is a non-issue.** 10k tenants × 200 tables = 2M rows in `restaurant_tables`. That is a small table. Index `(tenant_id, location_id, zone_id, status)` for the admin list; the PK covers resolution. Nothing here needs partitioning, caching infrastructure, or a read replica.

**The resolution endpoint is not a hot path.** One request per scan — say 300 tables × 3 turns/day = 900 requests/day/venue. It is a point lookup on a primary key, edge-cacheable, and returns a payload of a few dozen bytes. Compare with the menu poll every 20 seconds per open tab, which is orders of magnitude more traffic and already in production. **Do not over-engineer this.**

The one hot-path rule that does matter: **fire the resolution call in parallel with `fetchMenu` and `fetchAvailability`, never before them.** `apps/qr-menu/src/App.tsx:43,57` already runs those two in parallel from one effect; the resolution belongs in the same effect. TBL-07 requires the menu to render even when the id is unknown, so nothing about the menu render may block on it. A sequential resolve-then-fetch would add a full RTT to the first paint of the app's only screen, on a phone, on restaurant wifi.

**Admin list at scale.** TBL-11's acceptance ceiling is "a zone of 50 tables". The real ceiling is a location with 8 zones × 40 tables. Ask for **300 tables across multiple zones** in the acceptance criterion and confirm the screen does not re-fetch the whole tree per mutation — TanStack Query's default would, and `apps/admin/src/routes/(protected)/location/stop-list.tsx:34-37` is the pattern to follow for the query shape.

**Cost: zero new infrastructure.** The PDF is client-side (D-07), the QR is client-side, the resolution endpoint is a PK lookup behind a CDN. This phase adds no service, no queue, no cache. That is the right shape for a bootstrap budget and it should stay that way.
