# Phase 10.3 Plan 02: table RBAC resource + preset backfill Summary

**Registered a disjoint `table:['read','update']` permission resource (owner+admin hold both, manager preset holds read-only, staff holds neither), then backfilled it onto all 873 existing tenants' manager `tenant_role` rows via the existing idempotent `sync-preset-roles` CLI.**

## Accomplishments

- `table: ['read', 'update']` exists in exactly one place (`PERMISSIONS_STATEMENT`) and flows into Better Auth's access-control roles, the admin app's `hasPermission`/`requirePermission`, and the `Permissions(...)` decorator with zero second registration — proven by `domain:typecheck`, `api:typecheck`, and `admin:typecheck` all passing.
- `location` resource was left completely untouched — `admin.location` still equals `['read']` (regression-pinned in both `system-roles.spec.ts` and `rbac.spec.ts`), closing the CONTEXT D-12 gate-on-`location:update` mistake that would have made every table read owner-only and exposed brand-archive to a floor-manager custom role.
- Every one of the 873 non-archived `tenant_role` rows with `role='manager'` in the dev database now carries `table:['read']` and none carries `table:['update']` — verified directly against Postgres, not just via CLI exit code.
- Re-running `sync-preset-roles --all` a second time reports `updated: 0` across all 873 tenants, proving the backfill is genuinely idempotent.

- `NON_DELEGATABLE` left untouched for `table` — an owner minting a custom floor-manager role is the intended delegation path this split enables.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Pre-existing exhaustive resource-list regression test broken by the new resource**
- **Found during:** Task 1 verification (`pnpm nx run domain:test`)
- **Issue:** `packages/domain/test/rbac.spec.ts` (not listed in the plan's `files`) has its own assertion pinning the full sorted list of `PERMISSIONS_STATEMENT` keys. Adding `table` broke it — the plan's `read_first` list only named `test/rbac/system-roles.spec.ts`, missing this second, broader regression test in the same package.
- **Fix:** Added `table` to the expected sorted key list and added one new assertion (`table resource has read/update actions, disjoint from location`) matching the file's existing per-resource assertion style (mirroring how `location` and `ac` are each separately pinned).
- **Files modified:** `packages/domain/test/rbac.spec.ts`
- **Verification:** `pnpm nx run domain:test` — 170/170 tests green (was 169/170 before the fix, 1 failing).
- **Committed in:** `e07c9865` (Task 1 commit)

**2. [Rule 3 - Blocking] Worktree's shared `node_modules` symlinks silently resolved `@resto/domain` to the main checkout, not this worktree's edited source**
- **Found during:** Task 2's first `sync-preset-roles --all` run — it exited 0 and printed `{"tenants":873,"updated":0,"inserted":0,"skippedArchived":0}`, which looked like a clean idempotent no-op but was actually silently wrong.
- **Issue:** Every `node_modules` directory in this worktree (`node_modules`, `tools/scripts/node_modules`, every `apps/*/node_modules` and `packages/*/node_modules`) is an **absolute symlink to the corresponding path in the main checkout** (`/Users/mp_dev/projects/RestOS/...`), not a worktree-local install. `tools/scripts/node_modules/@resto/domain` is itself a *relative* symlink (`../../../../packages/domain`) that gets resolved **relative to the main checkout**, because the containing `node_modules` directory physically lives there. `tsc`/`vitest` (used for Task 1's verification) resolve `@resto/domain` via tsconfig path-mapping straight to worktree-local source and were unaffected — but `tsx` (used by the `pnpm resto:seed` CLI in Task 2) uses real Node module resolution and silently read the **main checkout's unmodified** `PRESET_ROLES` (no `table` key), so the DB comparison found no diff and reported `updated: 0` for all 873 tenants even though the actual backfill had not happened.
- **Fix:** Rebuilt `tools/scripts/node_modules` as a real, worktree-local directory: symlinked every third-party package entry (`@nestjs`, `@types`, `eslint`, `postgres`, `reflect-metadata`, `sharp`, `tsx`, `typescript`, `vitest`, `yaml`, `zod`) back to the shared main-checkout location (preserving the install-sharing optimization for unmodified deps), but pointed `@resto/domain`, `@resto/config-eslint`, and `@resto/config-typescript` at this worktree's own `packages/*` sources. Verified resolution with a standalone `tsx -e` probe before re-running the CLI. This change is confined entirely to `node_modules` (gitignored, worktree-only, not committed) and does not touch the main checkout.
- **Files modified:** none tracked (worktree-local `node_modules` symlink structure only)
- **Verification:** Re-ran `pnpm resto:seed sync-preset-roles --all`; got the expected `{"tenants":873,"updated":873,"inserted":0,"skippedArchived":0}`. Confirmed against Postgres directly (both acceptance-criteria SQL counts return `0`). Re-ran a third time to re-confirm idempotency (`updated: 0`).
- **Committed in:** not applicable (no tracked files changed)
- **Flag for the orchestrator:** this is an environment/infrastructure characteristic of how this worktree was spawned (cross-worktree `node_modules` symlink sharing for install-speed), not a defect in this plan's code. Any other wave/plan in this phase (or a future phase) that runs a `tsx`/Node CLI importing an `@resto/*` package it just edited in the same worktree is at risk of the identical silent-stale-resolution failure — the CLI will exit 0 and look idempotent while actually operating on unmodified code. Worth a systemic fix (e.g., excluding `@resto/*` workspace packages from the cross-worktree symlink, or a `tsx`-side path-mapping loader) rather than a per-plan workaround.
