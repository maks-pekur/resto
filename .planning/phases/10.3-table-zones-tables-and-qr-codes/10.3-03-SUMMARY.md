# Phase 10.3 Plan 03: QR Sheet Geometry, Print, and SVG Download Summary

**Client-side QR toolkit for the tables screen — pure A4 geometry, a lazy-loaded whole-zone print sheet built from inline vector `<svg>` and printed via the browser's own `window.print()` pipeline, and a lazy single-table SVG download, all reaching `qrcode` only through its browser entry point so the CLI's `yargs`/`pngjs` dependencies never enter the bundle.**

## Assumption A2 (real declaration recorded)

`node_modules/@types/qrcode/index.d.ts` declares:

```ts
export function create(text: string | QRCodeSegment[], options?: QRCodeOptions): QRCode;
export interface QRCode {
  modules: BitMatrix;
  version: number;
  errorCorrectionLevel: ErrorCorrectionLevel;
  maskPattern: QRCodeMaskPattern | undefined;
  segments: GeneratedQRCodeSegment[];
}
export interface BitMatrix {
  size: number;
  data: Uint8Array;
  reservedBit: Uint8Array;
  set(row: number, col: number, value: number, reserved: boolean): void;
  get(row: number, col: number): number;
  ...
}
```

Assumption A2 **held**: `create()` returns `.modules` with a numeric `.size` and a `data: Uint8Array` indexed `row * size + col`. The runtime source (`node_modules/qrcode/lib/core/bit-matrix.js`) confirms `BitMatrix.prototype.get = function (row, col) { return this.data[row * this.size + col] }` — exactly the assumed indexing, exposed as a documented `.get(row, col)` method, which `print-tables-sheet.tsx` calls directly instead of hand-indexing the raw array. No fallback to `toString(..., { type: 'svg' })` for the sheet renderer was needed (that call form is used deliberately in `download-table-svg.ts`, per the plan's own design, not as a fallback).

## Import specifier and browser-entry evidence

- **Exact specifier used in both new runtime files:** `await import('qrcode/lib/browser.js')` — the literal browser entry file (`node_modules/qrcode/package.json` maps `"browser": { "./lib/index.js": "./lib/browser.js" }`; the deep path is used explicitly instead of relying on that remap so the choice does not depend on a bundler applying the `browser` field).
- **TypeScript resolution:** `node_modules/qrcode` ships no `.d.ts` for `lib/browser.js` specifically, so `apps/admin/src/lib/qr/qrcode-browser.d.ts` declares `declare module 'qrcode/lib/browser.js' { export { create, toString } from 'qrcode'; }`, re-using the real `@types/qrcode` declarations. `pnpm nx run admin:typecheck` passes with this shim in place.
- **Built-output proof (temporary probe, reverted):** Added two throwaway `void import('./lib/qr/print-tables-sheet')` / `void import('./lib/qr/download-table-svg')` lines to `apps/admin/src/main.tsx`, ran `pnpm nx run admin:build`, inspected `dist/assets/`, then reverted the probe with `git checkout -- apps/admin/src/main.tsx` (confirmed clean via `git status`) before the final, plan-faithful build.
  - Result: a distinct lazy chunk `browser-<hash>.js` (25.78 KB / 10.13 KB gzip) appeared, separate from the entry chunk.
  - `grep -c "qrcode" dist/assets/index-*.js` → `0` (entry chunk carries zero references).
  - `grep -c "find_path\|dijkstra" dist/assets/browser-*.js` → `2` (the shared QR-encoding algorithm, used by both browser and server builds, is present, confirming real code was bundled, not a stub).
  - `grep -o "IHDR\|IDAT\|zlib\|Not enough non-option\|yargs\|Usage:" dist/assets/browser-*.js` → no matches (no PNG-renderer or CLI/yargs fingerprints — the CLI-only dependencies did not leak in).
  - The final, un-probed build (matching the actual committed source, where nothing yet calls the two new files) also shows zero `qrcode` references anywhere in `dist/assets/`, since no caller exists yet in this plan's scope — the probe above is what supplies the "evidence the built entry chunk does not contain the library" the harness requires.

## Decisions Made

- Followed the founder's pre-execution decision to drop `jspdf`; no PDF library exists anywhere in the diff.
- Chose the explicit `qrcode/lib/browser.js` deep-import specifier over the bare `qrcode` specifier, trading one small ambient-`.d.ts` file for independence from bundler-specific `browser`-field remapping behavior (see "Import specifier" above).
- Grouped the ten geometry constants into a single `A4_SHEET` export object (matching the plan frontmatter's declared `exports: ['A4_SHEET', 'layoutSheet', 'moduleSizeMm']`) rather than exporting each constant individually as the prose `<interfaces>` section's naming list might suggest in isolation — the two plan sections describe the same values at different levels (names vs. module surface); the structured `must_haves.artifacts.exports` field was treated as authoritative for the actual export shape.
- Used the `qrcode`-native `BitMatrix.get(row, col)` method instead of hand-indexing `data[row * size + col]`, since the shipped type declares `get` as the public accessor for exactly that computation.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] pnpm virtual-store-dir mismatch in the shared-symlink worktree**
- **Found during:** Task 2, first `pnpm --filter @resto/admin add qrcode`
- **Issue:** This worktree's `node_modules` (root and every `apps/*`/`packages/*` subdirectory) is an absolute symlink into the main checkout, per the known worktree hazard called out in the launch prompt. Running `pnpm add` from the worktree path made pnpm compute a *different* default virtual-store location (`<worktree>/node_modules/.pnpm`) than the one the symlink actually points at (`<main-checkout>/node_modules/.pnpm`), and it refused to proceed (`ERR_PNPM_UNEXPECTED_VIRTUAL_STORE`) rather than silently duplicating the store.
- **Fix:** Passed `--virtual-store-dir /Users/mp_dev/projects/RestOS/node_modules/.pnpm` explicitly on both `pnpm add` invocations (runtime dep, then dev dep), forcing pnpm to reuse the existing, correctly-shared store instead of creating a worktree-local one. No structural change to `node_modules` was needed this time (unlike 10.3-02's `tools/scripts/node_modules` rebuild) because this is a single top-of-tree `pnpm add`, not a `tsx`-resolved runtime import of an edited workspace package.
- **Files modified:** none beyond the intended `apps/admin/package.json` + `pnpm-lock.yaml`.
- **Verification:** `apps/admin/node_modules/qrcode/package.json` resolves correctly inside the worktree; `pnpm nx run admin:typecheck`/`test`/`build` all pass from within the worktree.
- **Committed in:** `4a90524d` (Task 2 commit).
- **Flag for the orchestrator:** any future plan in this phase (or beyond) that runs `pnpm add`/`pnpm install` from inside a shared-symlink worktree will hit the identical `ERR_PNPM_UNEXPECTED_VIRTUAL_STORE` and needs the same `--virtual-store-dir <main-checkout>/node_modules/.pnpm` override — a third distinct symptom of the same root cause already flagged twice in 10.3-02 and 10.3-05/10 (see this phase's other SUMMARYs).

**2. [Rule 3 - Blocking] Deep-path qrcode import has no shipped type declaration**
- **Found during:** Task 3, first `pnpm nx run admin:typecheck` after writing `print-tables-sheet.tsx`
- **Issue:** `qrcode` ships no `.d.ts` next to `lib/browser.js`; `@types/qrcode` only covers the package root. Importing `'qrcode/lib/browser.js'` via a bare `import()` would fail to resolve any type (TS2307), and the plan explicitly forbids a top-level `from 'qrcode'` in either new file (which rules out a type-only `import type * as X from 'qrcode'` at the top of those files too, since that syntax still literally contains `from 'qrcode'`).
- **Fix:** Added `apps/admin/src/lib/qr/qrcode-browser.d.ts`, a third file (not one of the "two new files" the plan's grep check names) that ambiently declares the deep-path module and re-exports the real `create`/`toString` types from `qrcode`.
- **Files modified:** `apps/admin/src/lib/qr/qrcode-browser.d.ts` (new).
- **Verification:** `pnpm nx run admin:typecheck` passes with full type safety on `QRCode.create(...).modules.get(row, col)` and `QRCode.toString(...)`.
- **Committed in:** `13ad04b9` (Task 3 commit).
