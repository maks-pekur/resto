<objective>
Close the read half of TBL-13: make `GET /v1/menu/availability` answer for the scanned table's location, and prove with a real two-location database that both halves — the guest's stop list and the order's rejection — now key on the same location.

Purpose: `GetMenuAvailabilityService.execute()` takes no argument at all and resolves the tenant's default location itself. Today that is merely wrong-but-consistent: the guest sees location A's stop list and the order lands at location A. After plan 10.3-09 it becomes inconsistent — a guest at a table in location B browses A's stop list, orders something B has run out of, and the order lands in B's feed. B's stop list, which is the operator's only "we ran out" tool, stops affecting QR orders entirely.
Output: the availability endpoint takes a table, and one e2e file that would fail if either half of TBL-13 regressed.
</objective>

  <action>
Change `GetMenuAvailabilityService.execute` to take an optional `locationId`. When one is supplied, use it; when it is absent, fall back to `this.defaultLocation.resolveForTenant(tenantId)` exactly as today, so every existing caller keeps its current behaviour. Return the answering `locationId` alongside `stoppedItemIds` and `stopVersion` so the controller can build a location-aware ETag.

In the `availability` handler on `PublicMenuController`, accept an optional `t` query parameter. After `requireGuestTenantOr404`, if `t` is present and parses as a UUID, look it up with `findActiveTableForResolution` under that tenant and use the returned `locationId`. If it is absent, malformed, unknown or archived, pass nothing and let the service resolve the default — the endpoint must never 4xx on a bad table id, because the guest app polls it every twenty seconds and TBL-07's rule is that a dead sticker still gets a working menu.

Change the ETag so it varies by the answering location as well as the stop version — a bare `"<stopVersion>"` would let a CDN hand location A's cached stop list to a guest at a table in location B, which is the exact bug this task exists to close. Keep the `if-none-match` 304 short-circuit and `MENU_AVAILABILITY_CACHE_CONTROL` unchanged; five seconds with one entry per location is not a cache problem.

Add a `Vary` consideration only if the implementation needs it — the location travels in the query string, so the URL already differs per table.

Do not put the table on `/v1/menu`. That response carries `s-maxage=300` and per-guest state there would either serve five-minute-stale data or shatter the hit rate on the product's hottest public read.
</action>

## Trust Boundaries

| Boundary                                       | Description                                                                 |
| ---------------------------------------------- | --------------------------------------------------------------------------- |
| anonymous guest → `GET /v1/menu/availability`  | Public, polled every twenty seconds, edge-cached                            |
| `?t=` query parameter → which location answers | A guest-supplied value now selects which stop list is returned              |
| CDN cache key → tenant/location pairing        | A shared cache entry across locations would be a silent cross-location leak |
