<objective>
Replace the guest app's free-text `?table=` reader with the opaque `?t=<id>` it resolves against the server, and give the cart the resolved id alongside the display parts.

Purpose: the display label must always come from the server, or a guest can hand-edit their way onto another table. And TBL-07's soft fail is the difference between a stale sticker being a mild annoyance and being a dead menu — the menu must render at HTTP 200 whatever the id turns out to be.
Output: `apps/qr-menu` reads `?t=`, resolves it, renders a locale-formatted label or a not-recognised line; `@resto/cart` carries the id the checkout phase will submit.
</objective>

```
export const fetchAvailability = async (signal?: AbortSignal): Promise<MenuAvailability> => {
  const init: RequestInit = {};
  if (signal) init.signal = signal;
  const res = await fetch('/v1/menu/availability', init);
  if (res.status === 404) return { stoppedItemIds: [] };   // catch-404, return a safe default
  if (!res.ok) throw new Error(`fetchAvailability failed: ${res.status.toString()}`);
  return res.json() as Promise<MenuAvailability>;
};
```

Do not gate the availability request on `fetchTable` returning — that would serialise two calls that are meant to be parallel and would delay the stop list behind a round trip on restaurant wifi.
