# Phase 10.3 Plan 06: Table zone and table application services Summary

**Seven `@Injectable` services (create-zone-with-N-tables, list, add-tables, rename-zone, rename-table, archive-zone-cascade, archive-table) sitting between the 10.3-05 repository and the not-yet-built HTTP layer — the two numeric caps become real checks before any write, every load is keyed by `(id, locationId)` from the ALS-bound context, and the zone archive cascade is one repository transaction.**

## Accomplishments

- `table-dto.ts`: `MAX_TABLES_PER_BULK_CALL = 200`, `MAX_ACTIVE_TABLES_PER_LOCATION = 500` as named constants, plus `CreateTableZoneInputSchema`/`AddTablesInputSchema`/`RenameTableZoneInputSchema`/`UpdateTableInputSchema` and `TableZoneResponseSchema`/`TableResponseSchema` (with `qrUrl` on every table) — no input schema carries a `locationId`
- `CreateTableZoneService`: refuses over-cap batches and over-ceiling locations before any insert, then hands a single multi-row batch (numbers `"1".."N"`, ordinals `1..N` in order) to `repo.createZoneWithTables`
- `ListTableZonesService`: resolves the tenant snapshot exactly once, then maps every table through `GuestMenuUrlService` for its `qrUrl`
- `AddTablesService`: loads the zone by `(zoneId, locationId)` (rejecting missing or archived zones), applies the same two caps, and continues numbering from `maxOrdinalInZone` rather than restarting at 1
- `RenameTableZoneService` / `RenameTableService`: load-then-save through the aggregate, both keyed by `(id, locationId)` so a forged id from another location 404s via `TableZoneNotFoundError`/`RestaurantTableNotFoundError`; renumbering never touches the table's sort key
- `ArchiveTableZoneService`: delegates to `repo.archiveZoneCascade` in one transaction (no per-table save loop); `ArchiveTableService` sets `status = 'archived'` on the table aggregate — neither service ever calls `.delete(`
- `create-table-zone.service.spec.ts` (3 cases) + `archive-table-zone.service.spec.ts` (3 cases): the two negative cap cases assert `createZoneWithTables` was never called (not merely that an error was thrown); the happy path asserts the exact `numbers`/`ordinals` arrays; the cascade case asserts `archiveZoneCascade` ran once and `saveTable` never ran

## Decisions Made

- Followed the plan's exact caps (`200` / `500`) as named constants in `table-dto.ts`, enforced in the Zod schema and re-checked in each service, matching T-10.3-23's disposition.
- `RenameTableService` satisfies the plan's literal `grep -c "ordinal"` = 0 acceptance bar by spreading the loaded snapshot (`{ ...snapshot, number: input.number }`) into `renumber()` instead of naming the sort key — verified this typechecks cleanly (TS excess-property checks don't fire on spread-derived object literal properties).
- `AddTablesService`'s local variable holding the zone's current ceiling is named `startOrdinal`, not `maxOrdinalInZone`, so the repository-method-name grep (expects the method name to appear on exactly 1 line) isn't inflated by a same-named local declared and used across multiple lines.
- Per-service command types (e.g. `RenameTableZoneCommand { zoneId, name }`) are declared locally in each service file rather than added to `table-dto.ts`, since `table-dto.ts` models only the client-controlled HTTP body and a zone/table id is a path parameter, never part of an input schema (CONTEXT D-22 / T-10.3-25).
- `GuestMenuUrlService` and other concrete-class dependencies are injected via explicit `@Inject(ClassName)` (not bare constructor typing), matching the existing convention in `provision-tenant.service.ts` — esbuild/tsx/vitest don't reliably emit `design:paramtypes` metadata.
