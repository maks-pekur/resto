# Phase 10.3 Plan 09: Table resolves the order's location, and pricing follows it Summary

**`CreateOrderService` now resolves a scanned table to its own location BEFORE pricing and stop-list checks run, closing the defect where a guest at location B's table was priced and 86-checked against location A's default; the free-text `table` field is gone from the API in favor of an opaque `tableId`, and both the resolved zone name and table number are frozen on the order at creation.**

## Accomplishments

- `MenuPricingPort.loadSnapshot(tenantId, locationId)` — `CatalogMenuPricingAdapter` no longer injects `DefaultLocationResolverService` or resolves a location itself; it prices and reads the stop list strictly for whatever location the caller already resolved.
- `OrderTableLookupPort` / `TenancyTableLookupAdapter` — ordering reaches tenancy's table resolution only through a Symbol-keyed port (`grep -rc "TableZoneDrizzleRepository" apps/api/src/contexts/ordering/` returns `0`), delegating to `findActiveTableForResolution` (which itself runs inside `withoutLocation`, so the lookup needs no bound location).
- `CreateOrderService.execute()` rewritten in the plan's required order: `requireTenantContext` → idempotency short-circuit (ABOVE table resolution, so a retry of an already-successful order never re-resolves a table that may since have been archived) → resolve `locationId` from `input.tableId` (throwing `OrderTableNotResolvedError` on a miss) or the tenant default → `withLocation(locationId, () => this.#createUnderLocation(...))` wrapping pricing, the business-date read, `nextShortNumber`, `Order.create`, `repo.save`, and the final re-fetch.
- `CreateOrderInputSchema.table` (free-text, max 20 chars) replaced by `tableId: z.string().uuid().optional()`; the `dine_in` refine now requires `tableId` instead of a non-empty string. No location field of any kind was added — the order's location is derived server-side only.
- `OrderSnapshot` gained `tableId` / `tableZoneName` / `tableNumber` (all `string | null`), persisted by `OrderDrizzleRepository` and read back by its row mapper; `tableIdentifier` (the old free-text column) is left in place for historic rows but has no writer from this plan on — every new order writes `null` there.
- `OrderTableNotResolvedError` added and mapped in `mapOrderError` to `BadRequestException({ code: 'ordering.table_not_resolved' })`, sitting above the terminal `return err;` so the `ProblemDetailsFilter` never redacts it into an opaque 500.

**1. [Rule 3 - Blocking] Tasks 1, 2 and 3 could not be committed independently under this repo's pre-commit hook**
