<objective>
Build the tenancy-context foundation for zones and tables: two aggregates, their errors and Symbol-keyed port, a Drizzle repository that filters location explicitly on every path, and the small service that is the only place in the system where the guest sticker URL shape is written down.

Purpose: `ScopedTx` filters tenant only and has no location dimension at all, so the RESTRICTIVE RLS policy from plan 10.3-01 is the database's defence and this repository's explicit predicate is the application's — CLAUDE.md's double-enforcement rule applied honestly rather than as ceremony. And the admin browser cannot build the QR payload: its whole client env surface is two variables, the guest host label lives server-side, and a tenant on a verified custom domain has a host no formula derives.
Output: `apps/api/src/contexts/tenancy/{domain,infrastructure,application}` gains the zone and table layer. No HTTP surface yet — plan 10.3-07 wires the controllers and the module.
</objective>

Implement `TableZoneDrizzleRepository extends TenantScopedRepository implements TableZoneRepository`, injected with `TenantAwareDb`.

Every read and every write must compose an explicit `eq(schema.tableZones.locationId, locationId)` (or the `restaurantTables` equivalent) into the predicate passed to `scoped.selectFrom` / `scoped.updateTable`. This is not redundant with RLS. `ScopedTx` filters tenant only, `LocationScopeGuard` proves the caller may act in the bound location and says nothing about which location a row named in a path belongs to, and the RESTRICTIVE policy is the database's backstop. The application-layer predicate is what turns a silent empty result into a deliberate one, and it is CLAUDE.md's double-enforcement rule (ADR-0020 I-1) applied where it actually matters.

`listZonesWithTables` — one query per table (or a join), active rows only, zones ordered by `name`, tables ordered by `ordinal` ascending with `number` as the tiebreaker. Never order by `number` alone: it is free text, so a lexicographic sort produces 1, 10, 11, 2, 20 and silently inverts the only thing that makes TBL-10's unlabelled sheet usable — and it looks correct on a six-table demo (CONTEXT D-23).

`createZoneWithTables({ locationId, name, tables })` — a single `withTenant` transaction: insert the zone, then insert all N table rows in ONE multi-row insert rather than N round trips. `ScopedTx.insertInto` takes a single row object and has no array form, so use the unrestricted `tx` inside the transaction for the batch and set `tenant_id` explicitly on every row from the bound context; note in a comment that this is the escape hatch `client.ts` documents, and that the composite FKs plus RLS `WITH CHECK` still apply to every row. Return the created zone with its tables. Because it is one transaction, a partial-unique-index violation anywhere in the batch rolls the whole thing back and creates nothing — which is what makes TBL-03's acceptance criterion guaranteed rather than accidental.

`addTables({ zoneId, locationId, tables })` — same transaction shape; the caller supplies already-computed numbers and ordinals.

`archiveZoneCascade(zoneId, locationId)` — one `withTenant` transaction that sets `status = 'archived'` and `archived_at = now()` on every active table of that zone and then on the zone itself, returning the archived table count. Never `DELETE`; `resto_app` has no DELETE grant on either table and hard deletes are forbidden.

`findActiveTableForResolution(tableId)` — the only method without a location argument, because the public resolution route is unauthenticated and has no bound location. Join `restaurant_tables` to `table_zones` on `(zone_id, tenant_id)`, require `status = 'active'` on both, and return `{ tableId, zoneName, number, locationId }` or null. Tenant scoping still applies through `ScopedTx` and RLS.

`countActiveTables(locationId)` and `maxOrdinalInZone(zoneId, locationId)` — plain scoped aggregates.

Write a `ROW_TO_SNAPSHOT` mapper per entity in the style of `location-drizzle.repository.ts`, so the row shape is converted once at the boundary.
</action>
