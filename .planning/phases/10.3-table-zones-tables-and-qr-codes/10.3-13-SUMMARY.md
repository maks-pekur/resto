# Phase 10.3 Plan 13: Table on the Order Card Summary

**The operator's order feed card and detail sheet now show a dine-in order's zone and table number (composed client-side per locale from two frozen snapshot columns), fall back to the legacy free-text identifier on old orders, and render nothing for pickup/delivery — closing the gap where triaging a busy Friday feed required opening the detail sheet per order just to see the table.**

## Performance

- **Duration:** ~70 min (includes diagnosing a pre-existing worktree gap: no `.env` file, which silently swallowed NestJS bootstrap errors during manual `openapi:emit` verification — see Issues Encountered)
- **Started:** 2026-08-29T~21:00:00Z
- **Completed:** 2026-08-29T22:11:49Z
- **Tasks:** 3 (plus one additional commit regenerating the OpenAPI artifact, per the plan's own instruction to close that drift here rather than leave it for 10.3-14)
- **Files modified:** 19

## Accomplishments

- `OrderFeedRowSchema`, `OrderFeedResponseRow`/`toOrderFeedResponseRow`, `OrderFeedRowResponseSchema`, and `OrderSnapshotResponseSchema`/`toOrderSnapshotResponse` all carry `tableZoneName`/`tableNumber` (`string | null`) alongside the surviving legacy `tableIdentifier` — no composed label anywhere on the wire (`grep -rc "tableLabel" apps/api/src/contexts/ordering/` is `0` everywhere).
- The three-way precedence rule (zone+number → legacy identifier → nothing) is written as a code comment directly above `toOrderFeedResponseRow` in `order-feed-dto.ts`, next to the schema-level comment already left by 10.3-09 in `packages/db/src/schema/ordering.ts`.
- `OrderCard` renders a new table line following the precedence rule, composed via `t('card.tableLabel', { zone, number })`; `OrderDetailSheet`'s previously `tableIdentifier`-only condition now branches the same three ways, so a scanned-table order shows its zone and number in the detail sheet too, not an empty line.
- `orders.card.tableLabel` was added to all three locale files with an identical key set (`en`/`es`/`ru`), verified programmatically (no diff in the flattened key lists).
- `order-card.spec.ts` renamed to `.tsx` and extended with three cases proving the precedence rule against a rendered `<OrderCard/>`: composed zone+number, legacy-identifier fallback, and true absence (via `queryByTestId` returning `null`, not merely an empty string) for a pickup order.
- `pnpm openapi:check` was left green — the drift the DTO change caused was regenerated and committed in this plan rather than deferred to 10.3-14, per the plan's own instruction.

## Issues Encountered

- **Worktree had no `.env` file**, which is untracked/gitignored per-worktree state, not shared from the main checkout by `git worktree add`. Manually invoking `pnpm exec nx run api:openapi:emit` (bypassing `openapi:check`'s own env-placeholder wrapper) failed silently — NestJS's `NestFactory.create(..., { logger: false })` combined with its default `abortOnError: true` swallows the bootstrap error message when the internal Logger is disabled, then calls `process.exit(1)` directly (bypassing normal promise rejection), so no error ever reached `emitOpenApi`'s own `.catch()`. Root-caused by temporarily re-enabling the Nest logger in an isolated debug script, which revealed `EnvValidationError: DATABASE_URL: Required; NATS_URL: Required`. This is not a plan-code defect — `tools/openapi-check.ts` (the actual command `pnpm openapi:check` runs) already injects placeholder env vars for exactly this reason and does not depend on a real `.env`; the failure only reproduced under a direct, non-standard invocation used for diagnosis. Recreated a local `.env` (copied from the main checkout's own dev values, all local secrets, gitignored, never committed) so the isolated e2e run and manual verification could also boot against the real dev Postgres/NATS containers already running on this machine.
