## Finding that reframed the first area

Before the first question, three greps established that **no client can create a dine-in order today**:

- `apps/qr-menu/src/api/client.ts` exposes only `fetchMenu` and `fetchAvailability` — no cart screen, no checkout, no `POST /v1/orders`
- `apps/website/components/checkout/checkout-form.tsx:74` collapses the mode to `'delivery'` or `'pickup'`, so `dine_in` is never sent
- therefore the `dine_in` branch of `CreateOrderInputSchema` is exercised by tests only

The area was re-framed around that fact rather than around the originally-planned question ("do we remove dine-in from the site?"), which turned out to be moot.

## Where the tables screen lives

Grounded first in the admin's actual navigation model: the sidebar has an **Operations** group whose pages carry the location slug in the URL (`/{slug}/orders`, `/{slug}/stop-list`) and an **Administration** group for company-level pages (Locations, Payments, Team, Roles, Settings). The permission resources that exist are `ac`, `billing`, `location`, `menu`, `order`, `settings`, `staff`.

| Option                                      | Description                                                                                                                                                             | Selected |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| Operations: `/{location}/tables`            | Next to the stop list and the order feed; the location comes from the header switcher. A dining room is about how the venue runs, not about the company's record of it. | ✓        |
| Inside the location card `/locations/:slug` | Together with address, contacts and — once 10.1 lands — the schedule. Everything about a venue in one place, but with no location switcher.                             |          |

**User's choice:** Operations, `/{location}/tables`

| Option                                                          | Description                                                                                             | Selected |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | -------- |
| Setup and printing both owner/admin                             | Tables are entered once at opening. Everything gated on `location: update`; no new permission resource. | ✓        |
| Setup owner-only, printing open to anyone who sees the location | A sticker gets destroyed mid-shift when the owner is unreachable.                                       |          |

**User's choice:** setup and printing both gated on `location: update`
**Notes:** chosen against the recommendation. Consequence recorded: a manager cannot reprint a damaged sticker without an owner or admin. Listed as a deferred idea to revisit if it bites in practice.

## Claude's Discretion

Decided without asking, because each is infrastructure with one defensible answer. All are listed in CONTEXT.md under "Claude's Discretion" so a persona review can object to any of them.

- The table resolution lives on its own public route rather than as a parameter on `GET /v1/menu` — that response is cached for five minutes and a per-guest table label would either go stale or shatter the cache
- The resolution response returns id, display label and location, so the guest app needs no second round trip before ordering
- No location id in the URL path for the admin endpoints — the location rides the request context like the stop list does, because the location guard keys on the header and never on a route parameter
- Database names `table_zones` and `restaurant_tables`, avoiding collisions with Drizzle's `table` callback parameter and with Phase 9's delivery zones
- Migrations are hand-written for the whole phase
- The QR library stays in admin and never reaches the guest bundle
- PDF generation happens in the admin browser, not on the server
