<!-- Geometry decided here so the implementer does not invent it. All numbers are millimetres. -->

A4 portrait is 210 × 297. A 2 × 3 grid gives cells of 105 × 99.

Named constants the geometry module exports:

- `PAGE_WIDTH_MM = 210`, `PAGE_HEIGHT_MM = 297`
- `COLUMNS = 2`, `ROWS = 3`, `CODES_PER_PAGE = 6`
- `CELL_WIDTH_MM = 105`, `CELL_HEIGHT_MM = 99`
- `CODE_FOOTPRINT_MM = 84` — the whole drawn code INCLUDING its quiet zone, which is what a human perceives as "the code". Inside D-09's "roughly 8–9 cm".
- `CUT_BOX_MM = 90` — the hairline cut guide, drawn 3 mm outside the footprint on every side so scissors never have the quiet zone as their target. Leaves 7.5 mm horizontal and 4.5 mm vertical margin inside the cell.
- `QUIET_ZONE_MODULES = 4` — the QR spec's mandatory margin, on all four sides.

`moduleSizeMm(matrixSize)` returns `CODE_FOOTPRINT_MM / (matrixSize + 2 * QUIET_ZONE_MODULES)`. `matrixSize` MUST come from the actual generated symbol, never a hardcoded number: the sticker URL length varies with tenant slug and apex domain, and a longer custom domain pushes the symbol from Version 5 (37 × 37) to Version 6 (41 × 41). A hardcoded module count silently produces an undersized quiet zone (RESEARCH.md Pitfall 6).

`layoutSheet(count)` returns, for each index 0..count-1, its `{ page, column, row, footprintX, footprintY, cutBoxX, cutBoxY, gutterTextX, gutterTextBaselineY }`. Ordering is left to right then top to bottom, one zone per document — that ordering IS the requirement, not an implementation detail, because a sheet of identical unlabelled squares has nothing else telling the operator which sticker belongs to which table (CONTEXT D-08).

The gutter baseline sits below the cut box, inside the 4.5 mm offcut band, so the number is gone once the sticker is trimmed (CONTEXT D-24).

Packages. **Founder decision, 2026-08-29 — `jspdf` is NOT used.** RESEARCH.md planned a
jsPDF-assembled document; the founder reviewed the dependency cost and chose the browser's
own print pipeline instead. `jspdf` unpacks to 29.5 MB and pulls `@babel/runtime`, `fflate`
and `fast-png`, all to produce a document whose only purpose is to be printed — which the
browser does natively from CSS. Dropping it also removes a download-then-open-then-print
detour the operator does not need.

Kept, with the founder having reviewed the registry evidence (version, repository, weekly
downloads, absence of any `postinstall`, and an npm search showing no lookalike ranking
above it) before approving the install:

- `qrcode@1.5.4` — 23.4 KB min / 8.75 KB gzip, MIT, no postinstall, repo `github.com/soldair/node-qrcode`, 23.9M downloads/week, published since 2010-12-21. The QR algorithm (Reed-Solomon, masking, bit packing) is not worth hand-rolling: an error there produces a symbol that fails to scan on only some phones.
- `@types/qrcode@1.5.6` — dev only, DefinitelyTyped, zero runtime weight.

Import the **browser entry point**, not the package root — `qrcode` ships a CLI and therefore
declares `yargs` and `pngjs`, neither of which belongs in a browser bundle.

Assumption A2, flagged LOW and actionable: `QRCode.create(text, { errorCorrectionLevel: 'M' })` is expected to return an object whose `.modules` is a bit-matrix of shape `{ size: number, data: Uint8Array }`, indexed `data[row * size + col]`. Verify against the installed package's own TypeScript declarations before writing the PDF assembler. Documented fallback if it differs: `QRCode.toString(url, { type: 'svg' })`, whose SVG string can be inlined into the print sheet directly — a different call, not a redesign.

Write `print-tables-sheet.tsx` exporting `printTablesSheet(input)` where `input` carries the zone name (for the document title only, never printed on a sticker) and an ordered list of `{ tableId, number, ordinal, qrUrl, status }`. The `qrUrl` is supplied by the server per CONTEXT D-21 — this module must never compose a URL from parts, because the guest host is server-only state and a tenant may sit on a verified custom domain that no formula derives.

**There is no PDF library.** The founder removed `jspdf` from this plan; the browser's own print pipeline produces the document. The operator clicks print, the browser's print dialog opens, and they either print directly or choose "Save as PDF" there. This is both one fewer dependency and one fewer step for the operator.

`qrcode` must be reached through `await import(...)` inside the function body, and through its **browser entry point** — the package root declares `yargs` and `pngjs` for its CLI, which must not reach a browser bundle. A top-level import would also put the library into the admin's initial bundle for a screen an operator opens during setup and rarely again (CTO MEDIUM-6).

Sort the list by `ordinal` ascending with `number` as the tiebreaker before laying anything out. Sorting on the free-text `number` alone would produce 1, 10, 11, 2, 20 — which silently inverts the only thing that makes an unlabelled sheet usable, and looks correct on a six-table demo (CONTEXT D-23). Filter out anything not active; archived tables must not appear on the sheet.

Build the sheet as DOM, not as a drawing API:

- A print-only container appended to `document.body`, hidden on screen and visible only inside `@media print`.
- `@page { size: A4 portrait; margin: 0 }` — the zero margin is load-bearing. Without it the browser adds its own margins plus a header and footer, which shifts every code off the geometry `qr-sheet.ts` computed and can clip the quiet zone. Add the print CSS alongside the component rather than in the global stylesheet, so nothing about it can affect the on-screen app.
- One absolutely-positioned page block per page, each `210mm × 297mm`, with `break-after: page` between them. CSS understands `mm` natively, so every constant from `qr-sheet.ts` is used verbatim — no unit conversion anywhere.
- Per code: generate the symbol at error-correction level M, read `matrixSize` back from the generated object, compute the module size with `moduleSizeMm(matrixSize)`, and emit an inline `<svg>` whose dark modules are `<rect>` elements of that size, offset by the 4-module quiet zone from the footprint origin. Inline SVG, never an `<img>` with a data URL and never a canvas raster — a 90 mm code at 300 dpi is roughly 1060 px per side, and a 50-table zone would become nine sheets of large base64 images assembled in a browser tab (RESEARCH.md "Don't Hand-Roll").
- The hairline cut guide is a bordered element at `CUT_BOX_MM` with no fill; the table number sits at the gutter baseline at a small font size, so it lands on the offcut and is gone once the sticker is trimmed (CONTEXT D-24).

Then call `window.print()`, and remove the container afterwards — listen for `afterprint` rather than removing synchronously, because a synchronous removal races the print rendering in some browsers. Set `document.title` to a zone-derived name before printing and restore it after, since browsers use the title as the default "Save as PDF" filename.

Write `download-table-svg.ts` exporting `downloadTableSvg({ number, qrUrl })`, which dynamically imports `qrcode`, calls its SVG string form at error-correction level M with the 4-module margin, and downloads the result as `.svg`. SVG is the locked format because it is vector, opens in any editor and at any print shop, and is the right input for the sticker templates the founder plans to design later (CONTEXT D-10).

Neither file may import from `apps/qr-menu` or add any dependency to it — QR generation stays on the admin surface (SPEC constraint; the guest app only ever reads a label from the API).

Then write `apps/admin/src/lib/qr/print-tables-sheet.spec.tsx`, co-located so the same vitest `include` glob picks it up. `vi.mock` `qrcode` with a stub returning a fixed 37 × 37 matrix, and stub `window.print`. Nothing is really printed — the spec is about what the sheet decides, not about rendered pixels.

Cover:

1. **Placement count** — a zone of 20 active tables produces 20 code groups across 4 page blocks: the container holds exactly 4 page elements and exactly 20 `<svg>` elements.
2. **Ordinal ordering** — given a list deliberately shuffled and numbered `"1".."20"`, the sequence of gutter numbers in document order is `1, 2, 3, ... 20`, not the lexicographic `1, 10, 11, 12, ...`. Assert the exact array. This is the one thing making an unlabelled sheet usable (CONTEXT D-23), and a lexicographic regression looks entirely normal on a six-table fixture.
3. **Archived exclusion** — a list of 7 tables of which 2 carry `status: 'archived'` produces 5 codes and 5 gutter numbers, and neither archived number appears anywhere in the container. SPEC TBL-10's acceptance criterion is that an archived table does not appear in the document, and until this case exists nothing anywhere covers it: the geometry spec tests pure numbers, plan 10.3-11 mocks the API, and plan 10.3-14's human walk-through never prints an archived table.
4. **The `qrUrl` is encoded verbatim** — the string handed to the `qrcode` stub for each table is exactly that table's `qrUrl`, with no host, scheme or query composed by this module (CONTEXT D-21).
5. **Cleanup** — after an `afterprint` event the container is gone from `document.body` and `document.title` is back to what it was, so printing twice does not leave two sheets in the DOM.

Do not assert pixel output or exact CSS strings — assert the decisions the module makes.
