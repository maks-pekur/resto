**Two testcontainers-backed integration specs proving GDPR erasure survives zones/tables/a table-referencing order, and that tenant RLS, RESTRICTIVE location RLS (both directions), composite FKs, and the partial unique index all hold at the raw Postgres layer — both specs independently proven to fail when the behavior they test is removed.**

## Accomplishments

- `erase-includes-table-zones.spec.ts`: seeds a tenant with a location, a zone, two tables, and an order referencing the first table; calls `tenancy_erase_tenant` and asserts zero rows remain in `restaurant_tables`, `table_zones`, `orders` and `locations`, plus a `pg_get_functiondef`-based assertion that the erase function's own source names both new tables
- `table-zones-isolation.spec.ts`: seeds tenant A (two locations, A1 and A2) and tenant B; 8 `it` cases cover tenant isolation on both tables, both composite FKs (zone→location, table→zone), the RESTRICTIVE location policy on both tables in both directions, the RESTRICTIVE `WITH CHECK` on insert, the partial unique index including the archive-then-reuse path, and the absence of `resto_app` DELETE privilege on either table
- Both specs were proven to fail against the behavior they test, by hand, once each: the erasure spec against the migration with its two `DELETE`s removed, the isolation spec against the migration with both RESTRICTIVE policies removed — see "Fix-proof verification" below
- Full `pnpm nx run db:test` run after restoring the migration: 27 test files, 193 tests, all green — no regressions in the wider suite

## Fix-proof verification (required by both tasks' acceptance criteria)

### Task 1 — erasure spec fails without the migration's two DELETEs

Temporarily replaced the two lines
```sql
DELETE FROM restaurant_tables WHERE tenant_id = p_tenant_id;
DELETE FROM table_zones WHERE tenant_id = p_tenant_id;
```
in `tenancy_erase_tenant` (migration 0003) with SQL comments, leaving `DELETE FROM locations WHERE tenant_id = p_tenant_id;` in place. Re-ran `pnpm vitest run test/integration/erase-includes-table-zones.spec.ts` against a fresh testcontainers Postgres built from the modified migration.

**Observed failure** (real Postgres error, not a mock):
```
PostgresError: update or delete on table "locations" violates foreign key constraint "table_zones_location_fk" on table "table_zones"
detail: 'Key (id, tenant_id)=(9e5fc6b8-6a32-460e-b040-e9ece1a46c53, 424077de-73b8-4f4f-aaec-9e0ce0a03bed) is still referenced from table "table_zones".'
where: 'SQL statement "DELETE FROM locations WHERE tenant_id = p_tenant_id"\nPL/pgSQL function tenancy_erase_tenant(uuid,text,text) line 56 at SQL statement'
code: 23503
```
1 of 2 tests failed (the erasure assertion; the `pg_get_functiondef` source-check test also failed independently since the DELETE statements were textually removed). Restored the migration file, confirmed `git diff --stat` was empty, re-ran the spec — both tests green again.

### Task 2 — isolation spec fails with the RESTRICTIVE location policies dropped

Temporarily commented out the two `CREATE POLICY ..._location_iso ... AS RESTRICTIVE ...` statements (one on `table_zones`, one on `restaurant_tables`) in migration 0003. Re-ran `pnpm vitest run test/integration/table-zones-isolation.spec.ts` against a fresh testcontainers Postgres built from the modified migration.

**Observed failure** (3 of 8 cases failed, real assertion failures against real Postgres reads):
- Case 4 (table_zones RESTRICTIVE, both directions): `AssertionError: expected [ …(2) ] to not include 'b4fa89f2-936c-4bdb-9ba9-d4bcafe226c0'` — a read bound to location A1 now also returned the A2 zone, because nothing filtered by location anymore.
- Case 5 (restaurant_tables RESTRICTIVE, both directions): `AssertionError: expected [ …(3) ] to not include 'c9ef49eb-e1c2-408a-b2b1-df7917deacb0'` — same shape, for tables.
- Case 6 (RESTRICTIVE `WITH CHECK`): `AssertionError: expected null to be an instance of Error` — the cross-location insert that should have been rejected by `WITH CHECK` now succeeded.

Cases 1, 2, 3, 7 and 8 (tenant isolation, composite FKs, partial unique index, no-DELETE-privilege) stayed green, correctly showing they do not depend on the location-RESTRICTIVE policies. Restored the migration file, confirmed `git diff --stat` was empty, re-ran the spec — all 8 cases green again, then re-ran the full `pnpm nx run db:test` suite (27 files, 193 tests, all green) to confirm no wider regression from the round-trip edit.
