the current session and issues a new one bound to the target organization without a password re-prompt,
delete the brand-pin hook, and open the wildcard admin origin safely.

founder's "each login to a restaurant is a new session" statement becomes real.

`*.admin.<domain>` is a trusted origin matched at the label boundary.

<interfaces>
Endpoint this plan CREATES. Plan 17's `pick-organization.tsx` calls it.

POST /api/auth/switch-organization
body: { organizationId: string }
requires: a valid current session (BA `sessionMiddleware`)
behaviour: verify membership -> create a new session pre-bound to the target organization ->
delete the old session row -> write the new session cookie
200 -> { organizationId: string, slug: string } // slug is required by the caller's hard navigation
403 -> caller is not a member of the target organization
401 -> no valid current session

ADMIN_WEB_ORIGIN_WILDCARD e.g. https://\*.admin.resto.app (optional; absent = wildcard disabled)
ADMIN_WEB_URL unchanged, e.g. https://admin.resto.app (apex, pre-organization sign-in)
AUTH_COOKIE_DOMAIN value guidance changes: .admin.resto.app, NOT .resto.app
CORS_ALLOWED_ORIGINS gains the same wildcard pattern

Create `apps/api/src/contexts/identity/infrastructure/better-auth/organization-switch.plugin.ts`: a
plugin-shaped object with one `createAuthEndpoint('/switch-organization', { method: 'POST', use: [sessionMiddleware], requireHeaders: true }, handler)`,
registered in `auth.config.ts`'s existing `plugins: [...]` array next to `organization()`.

Handler sequence, in this order — the order is the security property:

1. Read `{ user, session }` from `ctx.context.session` (guaranteed by `sessionMiddleware`; absence is a 401).
2. Validate the body's `organizationId` as a uuid before it reaches any query.
3. Verify membership: `ctx.context.adapter.findOne({ model: 'member', where: [userId eq, organizationId eq] })`.
   If absent, throw `APIError('FORBIDDEN')`. This check must precede session creation — issuing first and
   validating after would hand out a session bound to an organization the caller does not belong to.
4. Create the new session with the binding already applied:
   `internalAdapter.createSession(user.id, false, { activeOrganizationId: targetOrgId, activeLocationId: null })`.
   `activeLocationId` is reset to null deliberately — a location from the previous organization has no
   meaning in the new one, and carrying it over would point the location fence at a foreign row.
5. Delete the old session: `internalAdapter.deleteSession(session.token)`. This is a hard row delete, not a
   soft expiry, so `getSession()` on the old token returns null immediately (D-15).
6. Write the new cookie with BA's own `setSessionCookie(ctx, { session, user }, false)`. Do NOT hand-roll a
   `Set-Cookie` header: BA's cookie carries a signed cache payload whose format `getSession()` reads back,
   and a hand-built header would silently disagree with it.
7. Return `{ organizationId, slug }` — the caller needs the slug for its cross-origin navigation.

If `setSessionCookie` turns out not to be importable from `better-auth/cookies` despite the declaration
file, the documented fallback (RESEARCH Open Question 1) is to implement the same sequence inside a
`hooks.after` on `/organization/set-active`, which already runs with a full endpoint `ctx` — reuse the
existing `databaseHooks.session.update.after` code path rather than reconstructing cookie plumbing. Record
which route was taken in the SUMMARY.

interface (~line 90), its invocation inside `databaseHooks.session.update.after` (~391-410), the
