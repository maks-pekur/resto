## The 8 fields of typecheck-clean don't prove a working journey — what actually broke live

Both apps were green (per Wave 11 / plan 15) before this plan touched anything, and stayed green after every commit. None of the following would have been caught by `tsc` or `vitest`:

1. **`POST /v1/signup` never establishes a session** (D-06 enumeration parity, plan 13) — the plan/UI-SPEC's own text assumed otherwise. Fixed in `signup.tsx` (see key-decisions). Confirmed live: the response body is genuinely `{status:'pending_verification'}` with no `Set-Cookie`, and the browser has zero cookies until the chained `signIn.email()` call.
2. **`GET /v1/me/tenants` 403'd for every fresh sign-in**, not just multi-org ones — `login.tsx`'s own first call after `signIn.email()` hit this before ever reaching the branching logic. Root cause and fix: see key-decisions. This is the single most important bug this plan's own walkthrough found, because it broke the picker for 100% of accounts, not an edge case.
3. **Local dev topology gap**: `ADMIN_WEB_URL=http://localhost:4000` (bare, pre-dating this plan) doesn't match the `admin.localhost:4000` apex this plan's own `admin-host.ts` design uses — Better Auth rejected every request as an untrusted origin until `.env` was corrected locally (not committed — see key-decisions).
4. **A stale dev-server process from the MAIN repo checkout** (`/Users/mp_dev/projects/RestOS/apps/admin`, not this worktree) was already bound to `[::1]:4000` (IPv6-only) before this session started. Because `admin.localhost` resolves to `::1` first on this machine, every browser request silently hit the OLD code until that process was killed. Not a code issue — a process-hygiene trap worth naming for whoever next runs two admin dev servers on the same machine.
5. **Third-party cookie blocking — the architecturally significant finding, see the dedicated section below.**

## THE FINDING THAT NEEDS A DECISION: third-party cookie blocking breaks the session cookie entirely in a real browser

`apps/admin/src/lib/api-client.ts` and `auth-client.ts` call `VITE_API_ORIGIN` (an absolute cross-origin URL, `http://localhost:5001`) directly — they do **not** go through Vite's own same-origin `/api` and `/v1` proxy entries that already exist in `vite.config.ts`. This has always been the pattern; it "worked" only because, before this plan, the admin app was ever only served from `localhost:4000` — same hostname as `localhost:5001`, different port only, which browsers treat as **same-site**.

This plan is the first to serve the app from `admin.localhost` / `<slug>.admin.localhost` — a genuinely **different hostname**. Confirmed live with Playwright (Chromium, both the lightweight `chrome-headless-shell` and verified via raw `fetch()` from the page context): `POST http://localhost:5001/api/auth/sign-in/email` from a page at `http://admin.localhost:4000` returns a perfectly correct `Set-Cookie: better-auth.session_token=...; SameSite=Lax` header (confirmed present in the response, byte for byte), and CORS is configured correctly (`Access-Control-Allow-Origin`/`-Credentials` both present and correct) — but `context.cookies()` shows **the cookie is never stored**. This is Chrome's default third-party-cookie policy: `localhost:5001` is a third party relative to `admin.localhost:4000`, and the browser silently drops the Set-Cookie regardless of `SameSite=Lax` and regardless of correct CORS.

**I could not complete the walkthrough without a diagnostic workaround** — a Playwright route-interception shim that manually injects the session cookie via the CDP-level `addCookies` API (which bypasses the browser's own policy, since it's a test/debug primitive, not a real page mechanism) after every `/api/auth/*` and `/v1/*` response. This is documented in the code above only as a comment in scratch scripts that were **not committed** — it is not a fix, it proves nothing about what a real user's browser will do.

**Why this matters beyond dev:** `AUTH_COOKIE_DOMAIN`'s own documented production value (`.admin.resto.app`) only works if the API is reachable at a host _under_ `.admin.resto.app` in production (e.g., via a reverse proxy forwarding same-origin `/api/*` requests) — matching exactly the proxy pattern `vite.config.ts` already has for dev but `api-client.ts`/`auth-client.ts` don't use. If production instead points `VITE_API_ORIGIN` at a genuinely different domain (`api.resto.app`, the shape implied by `.env.example`'s "real HTTPS origin" guidance), the identical third-party-cookie blocking will silently break authentication for every real user on a modern Chrome, Safari, or Firefox — Safari and Firefox have been blocking third-party cookies by default for **years**, well before Chrome's own rollout.

**Not fixed in this plan.** `api-client.ts` and `auth-client.ts` are not in `files_modified`, and the correct fix — routing every API call through a same-origin relative path so the dev Vite proxy and a production reverse-proxy both make requests first-party — is a genuine architectural decision (Rule 4), not a mechanical patch: it touches how _every_ screen in the admin app talks to the API, needs a production ingress/proxy design decision this plan cannot make, and risks masking itself as "working" in any test that doesn't specifically exercise a cross-hostname scenario (exactly how this went unnoticed until now).
