## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Brand-RLS teardown count is 8, not the plan's stated 7**

- **Found during:** Task 1, cross-checking every migration touching `locations`
- **Issue:** `locations_brand_iso` (migration `0063_locations.sql`, RESTRICTIVE, references
  `brand_id`/`current_brand_id()`) is live and undropped. The plan's Task 1 action list and
  acceptance criteria enumerate only 7 policies (menu ×6 + orders), omitting it. Dropping
  `locations.brand_id` (required by D-08's "tenth column") without first dropping this policy
  would fail the migration at apply time — Postgres refuses to drop a column an RLS policy's
  USING/WITH CHECK expression still references.
- **Fix:** Added `DROP POLICY IF EXISTS locations_brand_iso ON locations;` as an 8th teardown
  statement, documented in the migration's own header comment with the verification trail.
- **Files modified:** `packages/db/migrations/0079_organization_merge.sql`
- **Verification:** `rg -c "DROP POLICY IF EXISTS.*_brand_iso" packages/db/migrations/0079_organization_merge.sql` → 8.
  The plan's literal acceptance criterion (`rg -c "_brand_iso"` equals 7) does not hold against
  this corrected, more-complete migration — see amended criteria below.
- **Committed in:** `1984252d`

**2. [Rule 3 - Blocking] `tenancy_erase_tenant()` GDPR erasure function references renamed/dropped objects**

- **Found during:** Task 1, after writing the D-41 rename block, cross-checking every migration
  that touches `organization_id`/`brands`/`brand_domains`/`member_brand_scope`
- **Issue:** The live function (last defined in `0077_tenancy_erase_payment_refunds.sql`)
  `DELETE`s from `invitation`/`organization_role`/`member` using `organization_id = p_tenant_id`,
  and `DELETE`s from `member_brand_scope`, `brand_domains`, `brands`. All of these are renamed or
  dropped by this migration. A PL/pgSQL function body is stored as source text and re-parsed on
  every call — it does not automatically track a renamed column or dropped table the way a view,
  index, or RLS policy does. Left unfixed, the next `tenancy_erase_tenant()` call (the GDPR
  30-day-cool-off erasure path, CLAUDE.md-mandated) would throw "relation/column does not exist"
  and fail closed on every tenant erasure going forward.
- **Fix:** Added a `CREATE OR REPLACE FUNCTION tenancy_erase_tenant(...)` as the final step of
  migration 0079, identical to the 0077 body except: `organization_id` → `tenant_id` on the three
  affected `DELETE`s, `organization_role` → `tenant_role`, and the three
  `member_brand_scope`/`brand_domains`/`brands` `DELETE`s removed (tables no longer exist).
  Signature unchanged, so no `DROP FUNCTION` needed first.
- **Files modified:** `packages/db/migrations/0079_organization_merge.sql`
- **Verification:** Read against the full source of `0077_tenancy_erase_payment_refunds.sql` line
  by line to confirm the replacement is a faithful diff, not a rewrite. Cannot be verified against
  a live database until Task 3 runs (blocked on human approval) — flagged as a specific thing to
  smoke-test post-migration.
- **Committed in:** `1984252d`

**3. [Rule 3 - Blocking] `packages/db/sql/auth-role.sql` grants/policies named `organization_role` by string**

- **Found during:** Task 2b, tracing every importer/reference of `organizationRole` before renaming it
- **Issue:** `provisionAuthRole()` (called on every API boot) runs `GRANT SELECT, INSERT, UPDATE,
DELETE ON ..., organization_role TO resto_auth` and a `DO $$` block that creates
  `organization_role_resto_auth_full ON organization_role` if the table exists. After migration
  0079 renames the table to `tenant_role`, the `GRANT` statement fails outright (table does not
  exist) and would abort every boot; the `DO $$` block's `tablename = 'organization_role'` check
  would also silently become a permanent no-op even if the GRANT were somehow skipped, leaving
  `resto_auth` without its RLS bypass policy on the renamed table.
- **Fix:** Renamed `organization_role` → `tenant_role` in the `GRANT` list and in the `DO $$`
  block's table-existence check, policy-existence check, `CREATE POLICY ... ON` target, and
  policy name (`tenant_role_resto_auth_full`). Also reworded the accurate-but-now-stale doc
  comment in `packages/db/src/auth-role.ts`.
  This was explicitly foreshadowed by Task 2b's own action text ("so is
  `packages/db/sql/auth-role.sql`'s companion code if any"), so treated as in-scope for Task 2b's
  commit rather than a separate out-of-scope deferral.
- **Files modified:** `packages/db/sql/auth-role.sql`, `packages/db/src/auth-role.ts`
- **Verification:** `rg -in "organization_role" packages/db/sql/auth-role.sql packages/db/src/auth-role.ts` → no matches.
- **Committed in:** `768f90dc`

**4. [Rule 1 - Bug] Two `packages/db` integration test fixtures broke on the Drizzle rename**

- **Found during:** Task 2b, `npx tsc -p packages/db/tsconfig.json --noEmit`

- **Fix:** Renamed the seed field to `tenantId:` in both files. Pure field-name update, no

- **Files modified:** `packages/db/test/integration/composite-tenant-fk.spec.ts`,

### Deliberate departures from the plan's literal text (not bugs in my work — corrections to the plan)

**5. Better Auth `schema.fields` override values: camelCase, not the plan's snake_case snippet**

- **Found during:** Task 2b, before writing the `organization({ schema: {...} })` config
- **Issue:** The plan's illustrative code block uses `fields: { organizationId: 'tenant_id' }` and
  `fields: { activeOrganizationId: 'active_tenant_id' }` — i.e., the raw SQL column name as the
  override target.
- **Investigation:** Read the installed `better-auth@1.4.22` drizzle-adapter source directly
  (`node_modules/.pnpm/better-auth@1.4.22.../dist/adapters/drizzle-adapter/drizzle-adapter.mjs`
  and `@better-auth/core/dist/db/adapter/get-field-name.mjs`). Confirmed: `getFieldName({model,
field})` returns `schema[model]?.fields[field]?.fieldName || field` (the raw override string,
  unmodified), and every query-building path in the drizzle adapter does `schemaModel[field]` —
  a **literal JS property-key lookup** on the Drizzle table object passed via `schema:
authSchema`. There is no separate step that maps a raw SQL column name back to a Drizzle
  property; the override value IS the property key the adapter looks for.
- **Conclusion:** If the override value is the raw physical column name (`'tenant_id'`) but our
  Drizzle schema's JS property is `tenantId` (camelCase, matching this codebase's 100% Drizzle
  convention and Task 2b's own step-1 instruction to rename the field to `tenantId`), the adapter
  would do `schemaModel['tenant_id']` — undefined — and every Better Auth read/write against
  `member`, `invitation`, `tenant_role`, and `session.activeTenantId` would throw
  `BetterAuthError: The field "..." does not exist in the schema for the model "..."` on first
  use. This is exactly the "typechecks, fails on first session write" failure mode the amendment
  note warned about, one level deeper than the migration/schema mismatch it was written for.
- **Fix:** Used `fields: { organizationId: 'tenantId' }`, `fields: { activeOrganizationId:
'activeTenantId' }` — matching the literal Drizzle property names — instead of the plan's
  snake_case suggestion.
- **Consequence for the plan's stated acceptance criteria:** `rg -n "activeOrganizationId:
'active_tenant_id'"` and `rg -c "organizationId: 'tenant_id'"` (equals 3) do **not** match the
  committed code. `rg -n "modelName: 'tenant_role'"` still matches (unaffected — `modelName` is a
  separate option, unambiguously the table name, not a field lookup).
- **Files modified:** `apps/api/src/contexts/identity/infrastructure/better-auth/auth.config.ts`
- **Verification:** `npx tsc -p packages/db/tsconfig.json --noEmit` exits 0 (this only proves
  `packages/db`'s own types are consistent, not that the BA wiring is runtime-correct — BA runtime
  behavior cannot be verified without a live database and a live sign-in, which is gated behind
  Task 3's human approval). **Flagging explicitly for post-Task-3 smoke verification:** sign in,
  switch organizations, and read a custom role from `tenant_role` before considering this plan's
  BA wiring proven, not just typechecked.
- **Committed in:** `768f90dc`
