## Process & tooling

### F-01 · The phase plan and the pre-commit hook contradicted each other · `fixed`

`.husky/pre-commit` ran `nx affected -t typecheck --uncommitted`, which requires every
commit to leave the whole repo type-green. Phase 10.2 is a spine migration whose plans
explicitly say the repo is red from plan 01 until plan 19. Nobody checked one against
the other, so it surfaced on the first commit of the first agent.

Cost: plan 01's executor blocked mid-plan and had to be re-run from scratch in a fresh
agent; plan 03's executor completed all three tasks and could commit none of them, and
its work had to be rescued from a worktree by hand.

Fixed by commit `3403657e` — a documented `RESTO_SPINE_MIGRATION=1` opt-out that skips
only the typecheck step, never `lint-staged`.

**Norm worth adding:** `gsd-plan-checker` should compare a phase's stated verification
posture ("repo-wide typecheck EXPECTED TO FAIL") against the repo's actual commit gates.
A plan that plans to be red needs a sanctioned way to commit while red.

### F-02 · Authorization cannot be relayed to a subagent · `fixed`

The founder approved the hook change through a question to the orchestrator. The
orchestrator then relayed it to a running subagent as "the founder decided X, here is
the commit". The subagent refused, correctly: the commit was unsigned, unpushed, and
the git author field is trivially forgeable in a shared environment, so a relayed
approval is indistinguishable from a prompt-injection attempt.

Compounding it, the relay asked the agent to modify `.husky/pre-commit` **and leave the
change uncommitted** — which reads as "change configuration and leave no trace".

Fixed by inverting the order: commit the approved change to the repository first, then
let a fresh agent work in a world where the change is already tracked content it can
verify with `git log`. The re-run agent did exactly that and proceeded without friction.

**Norm worth adding:** never ask a subagent to act on approval it cannot verify, and
never ask one to make an untracked change to shared configuration.

### F-03 · The permission classifier blocks the sanctioned flag · `fixed`

`RESTO_SPINE_MIGRATION=1 git commit ...` was denied by the auto-mode classifier as a
hook bypass — which is what it looks like from outside. It blocked the orchestrator and
the plan-03 executor alike.

Fixed in `.claude/settings.json`: one narrow allow rule for that exact prefix, plus four
deny rules covering `--no-verify` and `HUSKY=0` (deny wins over allow, so the allow rule
is not a hole).

**Caveat, deliberately not fixed:** permission rules match on command prefix, so
`git commit -m "..." --no-verify` slips past the deny rules while
`git commit --no-verify -m "..."` is caught. The real guarantee is the agent
instructions plus the green gate at plans 19/20, not the rules.

### F-04 · Agent worktrees fork from the default branch, not current HEAD · `open`

Claude Code's `isolation="worktree"` creates worktrees from `main`. On this repo `main`
is 416 commits behind `admin-vite-spa`, so every agent starts ~70k lines out of date and
silently works against a stale tree unless the prompt carries an explicit
`EXPECTED_BASE` assertion and reset.

The GSD executor template does include that guard, which is why nothing broke. But it is
load-bearing in a way that is easy to miss, and it fires on **every** agent in this
phase.

Possible real fix: the `worktree.baseRef: "head"` setting exists in the Claude Code
settings schema. Worth setting for this repo rather than relying on per-prompt guards.

### F-05 · A blocked plan still looks complete to GSD · `open`

`gsd-sdk query phase-plan-index` decides a plan is done purely by the presence of
`<plan>-SUMMARY.md`. Plan 01's blocked executor wrote a SUMMARY documenting its blocker —
correct behaviour — and that alone would have made the orchestrator skip the plan as
finished on the next run. Same for plan 03.

Both were caught by reading the agent reports rather than trusting the index. A phase run
without a human reading those reports would have silently shipped two partial plans.

**Norm worth adding:** SUMMARY frontmatter already carries enough to tell these apart
(plan 01's said `provides: ['BLOCKED (patch ready, not committed)']`). The index should
treat a SUMMARY as completion only when it does not declare a blocker.

### F-06 · Nx cache can mask the real state during a migration · `open`

Plan 01's executor reported that its repo-wide typecheck showed `admin:typecheck` as a
**cache hit rather than an actual run**, so `apps/admin`'s error count was never
independently confirmed that session.

During a rename this large, a cached green is exactly the false positive that matters.
Plans 19 and 20 should run their gates with cache disabled (`nx ... --skip-nx-cache`) or
verify the task actually executed.

### F-07 · Agents guess plan ownership instead of grepping for it · `open`

Plan 04 logged a broken file to `deferred-items.md` and assigned it to plan 10. The file
(`packages/events/src/contracts/tenancy.ts`) is in plan **06**'s `files_modified` and not
in plan 10's — six waves earlier. Corrected by the orchestrator in `14780da2`.

Nothing was lost, but a later plan reading that file would have skipped a break it owns.
Ownership is mechanically derivable: `grep -l "<path>" *-PLAN.md`. Agents should be told
to derive it, not infer it from prose.

### F-12 · Better Auth `schema` mapping takes JS names, not SQL names — plan text was wrong · `fixed`

The D-41 amendment I wrote into plan 05 gave this Better Auth wiring snippet:

```ts
organizationRole: { modelName: 'tenant_role', fields: { organizationId: 'tenant_id' } },
```

Both halves are wrong. `better-auth@1.4.22`'s Drizzle adapter resolves both by plain
property lookup against the schema module, not by SQL name:

- `getSchema(model)` does `schema[model]` where `schema` is the `@resto/db/schema`
  module namespace → `modelName` must be the **export name**, `tenantRole`.
- `convertWhereClause` does `schemaModel[field]` → each `fields` value must be the
  **Drizzle property name**, `tenantId` / `activeTenantId`.

Source: `dist/adapters/drizzle-adapter/drizzle-adapter.mjs` lines 9-16 and 47-68.

Plan 05's executor caught the `fields` half on its own by reading the adapter source,
deviated from my snippet, and said so — good work. It then applied the opposite rule to
`modelName` and shipped `'tenant_role'`, which would have thrown
`BetterAuthError: The model "tenant_role" was not found in the schema object` on the
first role read. Typecheck passes either way; this only fails at runtime.

Fixed in the main tree, and plan 05's snippet, `<verify>` block and acceptance criteria
were all corrected so a re-run cannot reintroduce it.

**Two lessons worth keeping:**

1. When a plan hands an executor a literal code snippet, that snippet is a claim about
   a third-party API and needs the same verification as any other claim. Mine did not
   get it. The executor's instinct — read the installed adapter source — was right and
   should be the default for any framework-mapping config.
2. The executor flagged exactly this area as "what I'm less certain about … only shows
   up at runtime, on a real sign-in." That self-assessment was accurate and pointed
   straight at the one thing that was still broken. Treat an executor's stated
   uncertainty as a work item, not as a disclaimer.

### F-14 · Plan 05's tenant-RLS regression check was vacuous · `fixed`

Task 3's acceptance criteria required recording
`SELECT count(*) FROM pg_policies WHERE policyname LIKE '%_tenant_iso'` before and after
the migration, "unchanged" proving tenant RLS was not collaterally dropped.

No policy in this database is named `*_tenant_iso`. The tenant-isolation policies are
named `*_iso` (`orders_iso`, `menu_items_iso`, …). The check returns 0 before and 0
after, so it passes trivially while proving nothing — the single most important safety
assertion in the riskiest task of the phase.

Replaced with a real one: snapshot every policy name before, diff against after. Actual
result — 51 policies before (12 brand-related), 40 after; **zero** non-brand policies
disappeared, one appeared (the rename target). That is the assertion the criterion meant
to make.

**Norm worth adding:** an acceptance criterion that counts something should be run once
against the live system while writing it. A criterion that has never returned a non-zero
value is indistinguishable from a criterion that cannot fail.

### F-16 · A composite-FK invariant violation, pre-existing and previously invisible · `open`

`member_location_scope_member_fk` declares
`FOREIGN KEY (member_id) REFERENCES member(id)` — no `tenant_id`. ADR-0020 I-2 requires
`FOREIGN KEY (member_id, tenant_id) REFERENCES member(id, tenant_id)` for any
tenant-scoped child table. Without it, a `member_location_scope` row can reference a
`member` belonging to a different tenant; RLS still scopes reads, but the referential
guard the ADR exists to provide is absent.

Origin: migration **0064** (phase 08.4). Migration 0079 does not touch it.

Why it surfaced only now: before this phase `member` carried `organization_id`, not
`tenant_id`, so it was not in the set of tables an invariant check recognizes as
tenant-scoped. D-41's rename brought it into that set. Combined with F-15 (the audit that
would have caught it has not run since June), it had two independent reasons to stay
hidden.

To fix it: `member` needs `UNIQUE (id, tenant_id)` before the FK can be redeclared as a
composite. That is a change to a Better-Auth-managed table and deserves its own reviewed
step — deliberately NOT folded into plan 05's checkpoint. Recommend closing it inside this
phase (plan 19 or 20) rather than deferring past it, since this phase is what made the gap
visible and the database resets freely right now.

### F-18 · Squash the 79 migrations into one baseline — after the phase, generated not written · `open`

Founder, 2026-08-20: "по сути ты можешь снести все миграции и оставить только одну
актуальную." Agreed on substance — there is no deployed database, no paying customer, and
79 migrations is a lot of history to re-read every time someone needs the current shape.

**Not now, and not by hand.** Two reasons:

1. **Timing.** Sixteen plans still run against this migration chain. Replacing a chain that
   is correct by construction with a fresh artifact, mid-phase, changes the foundation
   everything else is being built on.
2. **Method.** A hand-written baseline must reproduce every table, RLS policy, function,
   grant, check constraint, index and composite FK. One omitted policy is a tenancy hole —
   and this phase has already had two objects hide from two different kinds of check
   (F-15, F-17). Hand-authoring is the wrong tool.

**Recommended shape, after plan 20 closes the phase green:**

1. `pg_dump --schema-only --no-owner --no-privileges` the freshly migrated dev database.
2. Commit that as `0001_baseline.sql`; delete migrations `0000`–`0079` and rewrite
   `meta/_journal.json` to the single entry.
3. Prove it: `db:reset`, apply the baseline alone, `pg_dump` again, and **diff the two
   dumps**. Empty diff is the proof. Anything else and the baseline is wrong.
4. Re-run the catalog sweeps and the composite-FK invariant against the rebuilt database.

`sql/roles.sql` and the grant surface are applied separately from the migration chain —
confirm they still run in the right order against a single-migration history.

**Bonus this unlocks:** plan 20 could drop its "migration history is a documented exception"
carve-out entirely. The `brand` and `organization` greps would return zero everywhere,
including `packages/db/migrations/`, with no exception to explain.

Fix F-15 (`db:audit-fks`) before doing this, so the invariant audit is available to check
the result.

### F-19 · Plan 09 shimmed a method plan 06 has not agreed to provide · `fixed`

`get-stop-list.service.ts` and `get-stop-list-aggregate.service.ts` (plan 09) call
`this.locations.listForTenant(tenantId)` and declare, locally:

```ts
interface TenantScopedLocationRepository extends LocationRepository {
  listForTenant(tenantId: TenantId): Promise<readonly LocationSnapshot[]>;
}
```

with a comment saying plan 06 adds this to the tenancy port.

**Plan 06's plan text never mentions `listForTenant`.** What exists today is
`LocationRepository.listForBrand(brandId: BrandId, tenantId: TenantId)`; `listForTenant`
lives on a different port entirely (`BrandRepository`, in `brand-drizzle.repository.ts`).
Plan 06 does own `tenancy/domain/ports.ts` and must change `listForBrand` — its `BrandId`
parameter no longer exists — but nothing binds it to that particular name or signature.

**Why this is worse than the error it avoids.** A local interface augmentation is not a
request, it is an assertion. If plan 06 names the method anything else, catalog still
compiles — the augmentation says the method exists — and the concrete adapter injected at
`LOCATION_REPOSITORY` does not have it. A compile error becomes a runtime crash on the
stop-list endpoint. Typecheck cannot see it; only a live request can.

Plan 09 was right to stay out of a concurrent plan's file, and right to log it. The shim
shape is the problem, not the instinct.

**Reconciliation, required before wave 5 dispatches:**

1. Merge plan 06, then plan 09.
2. `grep -n "listForTenant\|listForBrand" apps/api/src/contexts/tenancy/domain/ports.ts` —
   read what plan 06 actually named it.
3. Delete both local `TenantScopedLocationRepository` augmentations and type the
   constructor params as `LocationRepository`.
4. If the name differs, update catalog's two call sites to the real name.
5. Confirm the concrete adapter implements it:
   `grep -n "<method>" apps/api/src/contexts/tenancy/infrastructure/*.ts`. An interface
   without an implementation is the same runtime crash wearing a different hat.
6. `apps/api/src/contexts/catalog/` must still typecheck clean afterwards.

**Norm worth adding:** when two concurrent plans need a shared signature, the plan that
_owns_ the file defines it and the other waits, or the signature is settled in the phase
plan before either runs. A cross-worktree type augmentation should never be the mechanism
— it silently converts a build failure into a production failure.

**F-19 resolution (2026-08-20).** Plan 06 independently chose the same name,
`listForTenant(tenantId)`, so the guess happened to be right. Both augmentations were
deleted after the merge and the constructor params typed as `LocationRepository`;
`apps/api/src/contexts/catalog/` typechecks with zero errors without them. Removing the
shim also orphaned a `LocationSnapshot` import in each file — caught by `lint-staged`
eslint on the commit, which is the hook earning its keep.

The near-miss stands as the lesson: this worked because two agents guessed alike, not
because anything made them agree. Also worth recording — the worst case was smaller than
feared, because `LocationDrizzleRepository` declares `implements LocationRepository`, so a
mismatch surfaces as `TS2420` rather than a runtime crash. An `implements` clause is what
turned this from a production failure into a compile error; ports without one do not get
that protection.

### F-25 · An executor stalled and the loss window was the uncommitted work · `mitigated`

Plan 11's first executor died to a stream watchdog — 600 seconds with no output. Its worktree held
zero commits and zero file changes, so nothing was lost and it was relaunched cleanly.

That outcome was luck, not design. The same stall arriving 40 minutes later would have destroyed
everything not yet committed, because the orchestrator force-removes the worktree on cleanup. This phase
has already had to hand-rescue one agent's uncommitted work (plan 03, 2578 lines extracted as a patch
before the worktree was removed).

Two mitigations now in the executor prompt:

- commit after **each** task rather than batching, so a stall costs at most one task;
- the orchestrator checks a dead agent's worktree for commits **and** uncommitted changes before removing
  it, and rescues via `git diff --cached HEAD` when there is anything there.

**Norm worth adding:** GSD's stall handling (`executor.stall_threshold_minutes`) offers "continue
waiting / kill and retry / switch to inline". None of those three preserve uncommitted work. A fourth —
"rescue the worktree, then decide" — should come first, and should be automatic rather than something the
orchestrator remembers to do.

### F-26 · Every worktree agent was reinstalling 1.2 GB of dependencies · `fixed`

Plan 11's second executor died with its last words being "Need to install dependencies in this worktree
first." Plan 01's retry agent had reported the same thing earlier ("missing `node_modules` in this fresh
worktree"). Claude Code's `isolation="worktree"` creates a bare checkout — `node_modules` is gitignored, so
it is absent, and every agent in this phase has been running `pnpm install` before it could typecheck
anything.

For this repo that is 1.2 GB across 14 `node_modules` directories (root plus 13 workspace packages). It is
also a long operation that produces almost no output, which is a plausible contributor to both stalls: two
consecutive agents died around it.

Fixed by setting `worktree.symlinkDirectories` in `.claude/settings.json` to all 14 paths. Verified on the
next dispatch: `node_modules` and `apps/api/node_modules` are symlinks in the fresh worktree, and the agent
skips installing entirely.

Two caveats worth writing down:

- All worktrees now **share** one `node_modules`. Fine for typecheck/lint/test, which only read it. An
  agent that ran `pnpm install` or `pnpm add` would now mutate the main checkout's dependencies — no plan in
  this phase does, but it is a real edge.
- A pnpm workspace needs the per-package directories too, not just the root; each holds its own symlink
  farm into the shared store. Listing only `node_modules` would have half-worked, which is worse than not
  working.

**Norm worth adding:** any repo using worktree isolation should configure this once, at setup. The cost of
not doing it is paid by every agent, every time, and it is invisible until something dies during the
install.

### F-27 · `set-active-location` is dead, and nothing in the toolchain can see it · `fixed (assigned)`

The staff "pick a location" endpoint currently fails on every request. The chain:

1. Plan 03 dropped the `session.active_brand_id` column.
2. `auth.guard.ts:150` still runs `req.activeBrandId = sessionData.session.activeBrandId ?? null`. The
   right-hand side is now permanently `undefined`, so `req.activeBrandId` is permanently `null`.
3. `set-active-location.controller.ts:91-92` and `:125-126` read it and take an early error return when it
   is falsy. Both handlers therefore always fail.
4. `me.controller.ts` still reports `activeBrandId` in the principal, so every client sees a permanently
   null field.

**Nothing catches this.** `activeBrandId?: string | null` is optional on a locally-declared request shape,
so `tsc` is satisfied. The unit tests pass because they construct the request themselves
(`makeReq = () => ({ activeBrandId: null })`) — the fixture supplies exactly the value that production can
no longer produce, so a green test proves the null path works rather than proving the endpoint does.

This is the sharpest example this phase has produced of the `verify-feature-not-call-shape` problem: every
automated gate the repo has is green on a dead endpoint.

Found by grepping the live tree for surviving `brandId` after Task 0a rather than by any gate. Assigned to
plan 11 as **Task 0b**, which also pulls `auth.guard.ts` into the plan — it belongs to plan 08 on paper, but
plan 08 has completed and left the line standing, and repairing the two consumers while the producer keeps
writing a dead field would be half a fix.

**Norm worth adding:** when a phase drops a database column, the sweep must include _readers of the
in-memory shape derived from it_, not only SQL references. `grep active_brand_id` finds the schema and the
migration; `grep activeBrandId` finds the four TypeScript files that actually break. Both spellings belong
in the completeness proof — plan 20's greps currently cover only the first.

### F-28 · A widening was performed correctly but recorded only as a side note · `open`

Task 0a dropped `findPinnableLocations`'s brand-filtering predicate, widening its result set from
brand-scoped to tenant-scoped, and left a vestigial `brandId` field on the port contract so its
out-of-scope caller kept compiling.

Under the merged model that widening is **correct** — one tenant is one restaurant is one former brand — so
tenant-scope reproduces exactly what brand-scope used to mean. But before this phase a tenant could hold
several brands, so the same edit against the old model would have been a scope escalation on the endpoint
that decides which locations a staff member may pin.

It was right, it was documented in the executor's own SUMMARY, and it was still only visible to someone
reading a paragraph in the middle of a report. Task 0b now requires the resulting scope to be stated in one
sentence, deliberately.

Worth keeping as a pattern: a deletion that widens an authorization-relevant result set should be an
explicit decision with its own line, not a consequence of a predicate becoming uncompilable.
