## Process & tooling

### F-01 · The phase plan and the pre-commit hook contradicted each other · `fixed`

`.husky/pre-commit` ran `nx affected -t typecheck --uncommitted`, which requires every
commit to leave the whole repo type-green. Phase 10.2 is a spine migration whose plans
explicitly say the repo is red from plan 01 until plan 19. Nobody checked one against
the other, so it surfaced on the first commit of the first agent.

Cost: plan 01's executor blocked mid-plan and had to be re-run from scratch in a fresh
agent; plan 03's executor completed all three tasks and could commit none of them, and
its work had to be rescued from a worktree by hand.

Fixed by commit `3403657e` — a documented `RESTO_SPINE_MIGRATION=1` opt-out that skips
only the typecheck step, never `lint-staged`.

**Norm worth adding:** `gsd-plan-checker` should compare a phase's stated verification
posture ("repo-wide typecheck EXPECTED TO FAIL") against the repo's actual commit gates.
A plan that plans to be red needs a sanctioned way to commit while red.

### F-02 · Authorization cannot be relayed to a subagent · `fixed`

The founder approved the hook change through a question to the orchestrator. The
orchestrator then relayed it to a running subagent as "the founder decided X, here is
the commit". The subagent refused, correctly: the commit was unsigned, unpushed, and
the git author field is trivially forgeable in a shared environment, so a relayed
approval is indistinguishable from a prompt-injection attempt.

Compounding it, the relay asked the agent to modify `.husky/pre-commit` **and leave the
change uncommitted** — which reads as "change configuration and leave no trace".

Fixed by inverting the order: commit the approved change to the repository first, then
let a fresh agent work in a world where the change is already tracked content it can
verify with `git log`. The re-run agent did exactly that and proceeded without friction.

**Norm worth adding:** never ask a subagent to act on approval it cannot verify, and
never ask one to make an untracked change to shared configuration.

### F-03 · The permission classifier blocks the sanctioned flag · `fixed`

`RESTO_SPINE_MIGRATION=1 git commit ...` was denied by the auto-mode classifier as a
hook bypass — which is what it looks like from outside. It blocked the orchestrator and
the plan-03 executor alike.

Fixed in `.claude/settings.json`: one narrow allow rule for that exact prefix, plus four
deny rules covering `--no-verify` and `HUSKY=0` (deny wins over allow, so the allow rule
is not a hole).

**Caveat, deliberately not fixed:** permission rules match on command prefix, so
`git commit -m "..." --no-verify` slips past the deny rules while
`git commit --no-verify -m "..."` is caught. The real guarantee is the agent
instructions plus the green gate at plans 19/20, not the rules.

### F-04 · Agent worktrees fork from the default branch, not current HEAD · `open`

Claude Code's `isolation="worktree"` creates worktrees from `main`. On this repo `main`
is 416 commits behind `admin-vite-spa`, so every agent starts ~70k lines out of date and
silently works against a stale tree unless the prompt carries an explicit
`EXPECTED_BASE` assertion and reset.

The GSD executor template does include that guard, which is why nothing broke. But it is
load-bearing in a way that is easy to miss, and it fires on **every** agent in this
phase.

Possible real fix: the `worktree.baseRef: "head"` setting exists in the Claude Code
settings schema. Worth setting for this repo rather than relying on per-prompt guards.

### F-05 · A blocked plan still looks complete to GSD · `open`

`gsd-sdk query phase-plan-index` decides a plan is done purely by the presence of
`<plan>-SUMMARY.md`. Plan 01's blocked executor wrote a SUMMARY documenting its blocker —
correct behaviour — and that alone would have made the orchestrator skip the plan as
finished on the next run. Same for plan 03.

Both were caught by reading the agent reports rather than trusting the index. A phase run
without a human reading those reports would have silently shipped two partial plans.

**Norm worth adding:** SUMMARY frontmatter already carries enough to tell these apart
(plan 01's said `provides: ['BLOCKED (patch ready, not committed)']`). The index should
treat a SUMMARY as completion only when it does not declare a blocker.

### F-06 · Nx cache can mask the real state during a migration · `open`

Plan 01's executor reported that its repo-wide typecheck showed `admin:typecheck` as a
**cache hit rather than an actual run**, so `apps/admin`'s error count was never
independently confirmed that session.

During a rename this large, a cached green is exactly the false positive that matters.
Plans 19 and 20 should run their gates with cache disabled (`nx ... --skip-nx-cache`) or
verify the task actually executed.

### F-07 · Agents guess plan ownership instead of grepping for it · `open`

Plan 04 logged a broken file to `deferred-items.md` and assigned it to plan 10. The file
(`packages/events/src/contracts/tenancy.ts`) is in plan **06**'s `files_modified` and not
in plan 10's — six waves earlier. Corrected by the orchestrator in `14780da2`.

Nothing was lost, but a later plan reading that file would have skipped a break it owns.
Ownership is mechanically derivable: `grep -l "<path>" *-PLAN.md`. Agents should be told
to derive it, not infer it from prose.

### F-12 · Better Auth `schema` mapping takes JS names, not SQL names — plan text was wrong · `fixed`

The D-41 amendment I wrote into plan 05 gave this Better Auth wiring snippet:

```ts
organizationRole: { modelName: 'tenant_role', fields: { organizationId: 'tenant_id' } },
```

Both halves are wrong. `better-auth@1.4.22`'s Drizzle adapter resolves both by plain
property lookup against the schema module, not by SQL name:

- `getSchema(model)` does `schema[model]` where `schema` is the `@resto/db/schema`
  module namespace → `modelName` must be the **export name**, `tenantRole`.
- `convertWhereClause` does `schemaModel[field]` → each `fields` value must be the
  **Drizzle property name**, `tenantId` / `activeTenantId`.

Source: `dist/adapters/drizzle-adapter/drizzle-adapter.mjs` lines 9-16 and 47-68.

Plan 05's executor caught the `fields` half on its own by reading the adapter source,
deviated from my snippet, and said so — good work. It then applied the opposite rule to
`modelName` and shipped `'tenant_role'`, which would have thrown
`BetterAuthError: The model "tenant_role" was not found in the schema object` on the
first role read. Typecheck passes either way; this only fails at runtime.

Fixed in the main tree, and plan 05's snippet, `<verify>` block and acceptance criteria
were all corrected so a re-run cannot reintroduce it.

**Two lessons worth keeping:**

1. When a plan hands an executor a literal code snippet, that snippet is a claim about
   a third-party API and needs the same verification as any other claim. Mine did not
   get it. The executor's instinct — read the installed adapter source — was right and
   should be the default for any framework-mapping config.
2. The executor flagged exactly this area as "what I'm less certain about … only shows
   up at runtime, on a real sign-in." That self-assessment was accurate and pointed
   straight at the one thing that was still broken. Treat an executor's stated
   uncertainty as a work item, not as a disclaimer.

### F-13 · Two live objects the phase's own decision record missed · `open`

Plan 05's executor found, by reading every migration that ever touched a brand column
rather than trusting the plan's citations:

- **`locations_brand_iso`** (migration 0063) — an RLS policy neither CONTEXT.md's D-09
  count nor plan 05's own "corrected" count included. Postgres refuses to drop a column
  an RLS policy still references, so migration 0079 would have failed to apply.
- **`tenancy_erase_tenant`** — the GDPR erasure function names tables and columns this
  migration drops or renames. Left alone, the next real erasure request would have
  thrown at the worst possible moment.

Both fixed inside 0079. Recorded because the pattern matters: CONTEXT.md's D-08/D-09
counts were wrong twice in this phase (nine policies vs seven, ten columns vs the nine
listed), and both times the correction came from reading migration history rather than
the decision record. Later phases should treat CONTEXT.md counts as a starting hypothesis.
