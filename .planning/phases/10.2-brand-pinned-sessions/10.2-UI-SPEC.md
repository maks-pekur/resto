# Phase 10.2 — UI Design Contract

> Visual and interaction contract for "Organization-per-restaurant and account onboarding." Covers 6 surfaces in `apps/admin` (signup, organization picker, organization switching, onboarding, the brand-switcher removal + its chrome consequences, the language switcher extension) plus one non-visual i18n deliverable in `apps/website`. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Founder/CONTEXT.md decisions locked before this document (do not re-open):**

1. The organization picker mirrors `pick-location.tsx` exactly — same Card shell, same button-list pattern, same loading/empty/error copy shape (D-18).
2. Switching organizations revokes the current session and issues a new one, server-side, with **no password re-prompt** (D-15/D-16). Because the organization lives in the host (`<orgSlug>.admin.resto.app`, D-21), a switch is a **hard navigation to a new origin**, not a client-side route change.
3. Signup collects **Name, Email, Password, Country** — nothing else (D-25) — and must call `/v1/signup`, not Better Auth directly (D-26).
4. Onboarding collects the **restaurant name only** (D-30); the slug is derived silently, never shown as an editable field.
5. The brand switcher is deleted outright (D-10). **No new persistent in-app organization-switcher widget ships this phase** — this is a discretion resolution, explained and flagged below, not a CONTEXT.md decision — switching happens by re-entering the picker, not by a live dropdown.
6. The `/{brandSlug}` path segment is removed everywhere (D-20). Every admin route in this document is written without it.
7. The language switcher **already exists** (`NavUser` → `LocaleSwitcherItems`) — this phase extends it with `es`, it does not build a new one (D-36/D-37).

### S1 — Signup (`apps/admin/src/routes/(auth)/signup.tsx`)

Current state (read in full, 119 lines): `SignUpSchema` has `displayName` / `email` / `password` / `defaultCurrency`; the `displayName` field is labeled "Restaurant name" (`signup.tsx:63`) but is sent to Better Auth as the **person's** name (`signup.tsx:46`); the currency `<select>` (`signup.tsx:88-100`) is collected but never sent anywhere; the submit handler calls `authClient.signUp.email(...)` directly (`signup.tsx:43-47`), which is exactly D-26's "produces a user with zero memberships" bug.

**Changes:**

- `SignUpSchema` fields become `name` / `email` / `password` / `country` (`country` a `z.enum(['UA', 'GB', 'ES'])` against the `packages/domain` country config).
- Field 1 label changes from "Restaurant name" to `auth.signup.nameLabel` ("Your name") — this is the fix, not a rename of the same wrong thing.
- Field 4 changes from the raw currency `<select>` to a shadcn `Select` bound to `country`, three `SelectItem`s in D-33's order (UA, GB, ES), each showing the country + derived currency per the Copywriting Contract table above.
- Submit handler calls `POST /v1/signup` (D-26) instead of `authClient.signUp.email`. On success, the response already establishes a session bound to the new organization (per RESEARCH.md, `/v1/signup` provisions organization + owner atomically and the existing code already calls `setActiveOrganization` internally) — navigate straight to `/onboarding`, never through the picker (a brand-new account has exactly one organization).
- **Card title, field labels, button states, and the footer link all move behind `useTranslation('translation', { keyPrefix: 'auth.signup' })`**, matching `login.tsx`'s already-correct pattern — closing this file's specific localization gap as a direct consequence of D-25/D-26/D-28, not as separate scope.
- Error state: on a `4xx`/`5xx` from `/v1/signup`, show `auth.signup.errorGeneric` in the existing `role="alert"` paragraph (unchanged position/styling, `signup.tsx:101-105`) — the form remains filled in, no field is cleared, matching the existing pattern.

**Layout is otherwise unchanged** — same `Card`/`CardHeader`/`CardContent` shell, same `space-y-4` field stack, same submit-button-then-footer-link order.

### S2 — Organization picker at sign-in (`apps/admin/src/routes/(auth)/pick-organization.tsx`, new)

**Structurally a direct port of `pick-location.tsx`** (84 lines, read in full) with organization-shaped data:

- `Card` → `CardHeader` (`CardTitle` = `pickOrganization.title`, `CardDescription` = `pickOrganization.description`) → `CardContent` with a `grid gap-2` button list — identical shell.
- Each organization renders as `<Button variant="outline" className="justify-start">` showing the organization's display name — same visual weight as `pick-location.tsx`'s location buttons, no logo/avatar/subtitle (keeps parity with the mirrored pattern; an organization-branding treatment here would be new scope this phase doesn't need).
- **Three states, matching `pick-location.tsx`'s exact shape:**
  - Loading: `pickOrganization.loading` ("Loading…"), `text-muted-foreground text-sm`.
  - Empty (defensive, should not occur): `pickOrganization.empty` + `pickOrganization.emptyDescription`.
  - Populated: the button list. Clicking a button sets a per-button pending id (mirrors `pendingId` state in `pick-location.tsx:27`), disables the rest, and swaps that button's label to `pickOrganization.enteringState` (with the org's name interpolated).
- **On selection — the interaction contract the phase objective explicitly asks for:**
  1. Call the switch/bind endpoint (revoke-and-reissue per D-15/D-16).
  2. On success: **hard navigate** (`window.location.assign`, not TanStack Router's `navigate`) to `https://<selectedOrgSlug>.admin.resto.app/dashboard` (local dev: `http://<selectedOrgSlug>.admin.localhost:4000/dashboard`) — a client-side route push cannot cross origins, and D-21 puts the organization in the host, so this redirect **must** be a real navigation, not a router transition.
  3. On failure: re-enable all buttons, show `pickOrganization.error` in the same `role="alert"` position `pick-location.tsx:75-79` already uses — the failed button's label reverts from "Entering {{name}}…" back to the plain org name (a real retry, not a dead-end message).
- **When is this screen shown?** Two triggers, one screen (see S3 for the second):
  - Automatically after a successful sign-in, when the signed-in owner belongs to 2+ organizations and the fresh session has no organization bound yet (confirmed by RESEARCH.md: `signInEmail` never auto-populates `activeOrganizationId`). Exactly one organization → skip this screen entirely, bind it, and land on the dashboard directly. Staff always belong to exactly one organization and never see this screen (D-17).
  - `login.tsx:55-58` currently does `authClient.organization.list()` then blindly activates `orgs.data?.[0]` — **this blind first-pick must be replaced** with: if `orgs.data.length > 1`, navigate to `/pick-organization`; if exactly 1, bind it directly (no picker) and proceed to the existing post-login routing (staff pick-location check, then dashboard).

### S3 — Organization switching (interaction contract + the one new in-app entry point)

**Discretion resolution, stated explicitly because it is not a CONTEXT.md decision:** this phase does **not** reintroduce a persistent, always-visible organization switcher in the sidebar (the role `brand-switcher.tsx` used to play). `10.2-RESEARCH.md`'s own conclusion (State of the Art table) is that switching is framed as "leaving and re-entering," not a live control, and nothing in CONTEXT.md's `<deferred>` section flags a missing switch-entry-point as a problem — only a missing **create**-entry-point is flagged. Given that, the single in-app trigger this phase adds is a **`NavUser` dropdown item**, not a sidebar-header control:

- New `DropdownMenuItem` in `nav-user.tsx`, labeled `nav.user.switchOrganizationItem` ("Switch organization"), placed in its own group directly above the existing Account item, **visible only when `operator.baseRole === 'owner'` AND the owner belongs to 2+ organizations** — same conditional-render shape `location-switcher.tsx:36` already uses (`if (!isOwner || locations.length === 0) return null`). Staff and single-organization owners never see this item, matching D-17's "staff... never see it."
- Clicking it navigates (client-side is fine here — no host change happens until a selection is made) to the same `/pick-organization` route S2 describes. **One picker screen, two entry paths** — no second component, no copy fork.
- The revoke/reissue mechanism, the hard-navigation redirect, and the loading/error states are **identical to S2's**, described once there, not repeated here.

**What a stale second tab sees after a switch (no new UI needed — existing plumbing already covers it):** because the session cookie is shared across `*.admin.resto.app` and the old token is deleted server-side (D-15), a second tab still open on the pre-switch organization's host will get a `401` (or an `auth.tenant_mismatch`) on its next request. That already routes through the existing `/login?expired=1` flow (`login.tsx:39,81-89`, the `tAuth('sessionExpired')` banner) — no new copy, no new screen.

### S4 — Onboarding (`apps/admin/src/routes/(protected)/onboarding/` → recommend `index.tsx`)

Current state (read in full, 260 lines): a two-field form (Brand name + editable URL slug) with a 300ms-debounced live availability check (`SlugAvailabilityHint`, 5 states) and a "Take suggestion" inline action on collision.

**Changes — this shrinks, it does not grow:**

- **One field: "Restaurant name."** No slug field is rendered. D-30 is explicit ("asks name only; the slug is derived") and RESEARCH.md's Pitfall 5 confirms the slug-availability check is still needed **server-side** — but nothing here requires exposing it as user-facing UI. Collisions are resolved **silently** by the server (auto-suffix), never surfaced as a "taken" error — a deliberate simplification over the old flow, not an oversight.
- **Read-only host preview beneath the input**, live-updating as the owner types (same debounce timing as before, ~300ms, but now driving a **preview string**, not an availability check the user must react to): `onboarding.hostPreview` → "You'll be reachable at **{{host}}**", where `{{host}}` is `<derived-slug>.admin.resto.app`, monospace or otherwise visually distinct from body text (e.g. `font-mono text-muted-foreground`) so it reads as a system-generated value, not another editable field.
- Submit button: `onboarding.submitIdle` ("Continue") / `onboarding.submitPending` ("Creating your restaurant…") — same idle/pending pattern as every other form in this phase.
- On success: `toast.success(t('onboarding.createdToast', { name }))`, then navigate straight to `/dashboard` (no `/{brandSlug}` param — D-20).
- On failure: `onboarding.errorGeneric` in the existing `role="alert"` position.
- **D-31's "resume where abandoned" is a routing concern, not a new UI state on this screen.** The screen itself has exactly one field and one submit — there is no multi-step progress to visually resume. What "resume" means concretely: a signed-in user with an account but zero organizations is routed to `/onboarding` (not re-shown signup); a user with exactly one organization is routed straight to the dashboard; a user with 2+ is routed to the picker (S2). This derivation lives in the post-login/protected-layout routing logic (mirrors the existing `brands.length === 0` check at `$brandSlug/_layout.tsx:48-51`, which moves to the new top-level protected layout once the `/{brandSlug}` param is gone) — not a visual state this UI-SPEC needs to draw.

### S5 — Removal surfaces: sidebar chrome after the brand switcher is deleted

`app-sidebar.tsx`'s `SidebarHeader` currently stacks `<BrandSwitcher>` then `<LocationSwitcher>` (`app-sidebar.tsx:132-135`).

**Change:** `<BrandSwitcher>` is deleted outright, not replaced with an interactive equivalent (per the S3 discretion resolution). It is replaced with a **static, non-interactive organization-identity block**, same visual footprint as the old switcher's trigger (avatar-initials square + two-line name/slug text, `SidebarMenuButton size="lg"` styling) but with **no `DropdownMenu` wrapper, no chevron, no hover/active affordance** — it must visibly read as inert, not as a broken or disabled control.

**Why keep anything here at all, given the organization is already visible in the host (address bar)?** RestOS's admin surface targets tablet-in-the-kitchen usage, where the browser chrome (and therefore the address bar) is frequently minimized, covered by a case, or simply not where a rushed operator looks. Removing the last visual "which restaurant is this" cue from the persistent sidebar — leaving it discoverable only in a URL bar — is a real regression for that usage pattern, not a neutral cleanup. A static label costs nothing interaction-wise and closes that gap.

`<LocationSwitcher>` itself is **functionally and visually unchanged** — same component, same file, same position (second in the header stack), unaffected by the merge per D-19.

**The GAP this restates from CONTEXT.md `<deferred>`, so it is not silently absorbed:** deleting `brand-switcher.tsx` removes its "+ Add brand" entry point, and no replacement create-organization surface ships in this phase. An owner cannot create a second restaurant after this phase ships. If a future phase adds one, the organization-picker screen (S2) — not the now-static sidebar block — is the natural place for a trailing "+ Create another restaurant" action, mirroring where `brand-switcher.tsx` used to put it. **Not built here.**

### S6 — Language switcher extension (`locale-switcher-items.tsx`)

No structural change — `LocaleSwitcherItems` (39 lines) already lives inside `NavUser`'s dropdown and already renders a `Globe`-icon-prefixed list with a `Check` mark on the active locale. This phase's only change:

- `LOCALES` grows from `['ru', 'en']` to `['ru', 'en', 'es']`.
- `LABEL_KEY` gains `es: 'localeEs'`, and `nav.user.localeEs` ("Español") is added to all three message catalogues (`ru.json`, `en.json`, and the new `es.json`).
- No visual change beyond a third row appearing in the same list — the component's existing `idx === 0 ? <Globe /> : <span className="size-4" aria-hidden="true" />` spacer logic already handles a 3rd+ item correctly (only the first row gets the `Globe` icon; the rest get an invisible same-size spacer to keep the check-mark column aligned).

**Default locale on first render of a fresh dashboard (D-36's "seeded from the signup country's default locale") — a concrete mapping this UI-SPEC locks, because leaving it unstated would leave the very first screen a new owner sees in an undetermined language:**

| Country | Default locale | Why                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| UA      | `ru`           | `apps/admin`'s i18next only ships `ru`/`en` (+ `es` this phase) — **not** `uk`. Mapping UA → `ru` (not the more "natural" `uk`) keeps every supported country's default inside the intersection of what `apps/admin` actually ships, avoiding a state where the langSwitcher shows "Українська" selected while every visible string silently renders in Russian (i18next's configured `fallbackLng: 'ru'`, confirmed in `apps/admin/src/lib/i18n/index.ts:12`). This is `10.2-RESEARCH.md` Pitfall 6's own recommendation, adopted here as the locked default rather than left open. |
| GB      | `en`           | Unambiguous                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ES      | `es`           | Unambiguous, and the reason the catalogue exists                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |

**`es.json` must ship as a complete catalogue at merge time, not partial.** Because `fallbackLng` is `ru` (not `en`), a missing Spanish key does not fail loud or fall back to English — it silently renders **Russian** text inside an otherwise-Spanish UI, which is a more confusing failure mode than a raw i18n key would be (D-38's "must fall back deliberately, never render raw keys" is satisfied by i18next's mechanism, but only if the catalogue itself is complete; an incomplete catalogue produces a different, still-bad failure this UI-SPEC flags explicitly).

## Accessibility Contract

- **Color is never the sole signal.** No surface in this phase uses color-coded state (no chips, no badges) — every state (loading/empty/error/pending) is communicated through text.
- **Every error/status region reuses the existing `role="alert"` / `role="status"` pattern** already established in `login.tsx`, `signup.tsx`, and `pick-location.tsx` — no new accessibility pattern is introduced, the existing one is extended to two new screens.
- **The organization picker's live pending-state change** (all buttons disabling, one button's label swapping to "Entering {{name}}…") is communicated the same way `pick-location.tsx` already does it today — through the button's own text content change, which a screen reader picks up as part of normal focus/activation feedback. No extra `aria-live` region is required beyond what the pattern already provides.
- **The country `Select` is a standard Radix `Select`** — full keyboard operation (arrow keys, type-ahead, `Enter`/`Escape`) and screen-reader semantics come from the primitive itself; no custom work needed.
- **The new `NavUser` "Switch organization" item** is a standard `DropdownMenuItem` inside an already-accessible Radix `DropdownMenu` — no custom keyboard handling needed.
- **The static organization-identity block in the sidebar (S5) must not be a focusable/interactive element** — no `button`, no `tabIndex`, no `role="button"`. It is decorative-but-informative chrome; making it focusable-but-inert would be a worse accessibility outcome than a truthful plain `<div>`.
