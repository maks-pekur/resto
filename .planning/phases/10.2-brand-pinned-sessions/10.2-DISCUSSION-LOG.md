# Phase 10.2 — Discussion Log

**Date:** 2026-08-19
**For human reference only.** Downstream agents read `10.2-CONTEXT.md`, not this file.

## Why this log matters

Three decisions in this discussion **reversed or corrected an earlier position** —
one of them the assistant's own recommendation, one the ROADMAP's sketch, one the
user's own first answer. A reader who sees only CONTEXT.md will not know which
alternatives were weighed and rejected on purpose versus never considered.

---

## Areas discussed

All four offered areas were selected: brand authority, countries and languages,
brand switching, onboarding shape.

## Path of the discussion

### 1. Brand authority

Offered: session-wins-but-keep-URL / session-only-clean-URL / URL-wins.
**Chosen: session-only, URL segment removed entirely.**

Flagged to the user before they chose that this is the most expensive of the three.
Verified cost afterwards: 18 route files under `$brandSlug`, 58 admin files
referencing `brandSlug`.

### 2. Countries

The user's instruction was _"первые страны это ua и en и es"_. `en` is not a country
code. Resolved to **GB** rather than US — Stripe Connect Express is long-stable there
and the currency is unambiguous (GBP vs state-level US tax complexity).

Spanish had no message catalogue in either app (admin: `ru`/`en`; website:
`ru`/`uk`/`en`). Options were fallback-to-English, add the catalogue, or drop ES from
the first list. **Chosen: add the Spanish catalogue in this phase**, and on the follow-up
the user scoped it to _"язык интерфейса и коммуникации"_ — so emails/notifications
are in scope, not interface alone.

### 3. Brand switching — the user's own answer was superseded mid-discussion

**First answer:** "лёгкий повторный выбор" — separate picker screen, no password,
session stays, only the pin changes.

**Later answer:** _"по сути каждый логин к бренду это должна быть новая сессия и при
смене бренда мы должны отозвать текущую и создать новую"_.

These are not the same. The user-facing feel is identical (no password re-entry), but
the second is strictly stronger: the old session token is dead after a switch and can
never be replayed against the new brand. **The later statement was taken as
authoritative** and recorded as D-08/D-09 with the supersession noted inline, so a
future reader does not "fix" it back to the weaker model.

A consequence the user did not answer directly but which follows from D-08: a fresh
sign-in has no brand bound yet, so there is nothing to remember — the **picker must
appear at every sign-in** when the owner has more than one brand. Recorded as D-10.

### 4. Onboarding — the ROADMAP's sketch was wrong

ROADMAP.md sketched onboarding as "restaurant name, then the first brand". The user
corrected the underlying model:

> _"бренд это и есть компания, тенант это просто как связующее звено на котором будет
> подписка и общие параметры, а бренд это конкретное ооо или ип со своим счетом и тд"_

Checked this against the schema and it already matches: `brands` carries
`legal_name`, `legal_form` (`IP`/`OOO`/`LLC`/`SOLE_PROP`/`OTHER`), `tax_id`,
`stripe_account_id`, `fiscalization_config`; `tenants` carries only `slug`,
`display_name`, `locale`, `default_currency`. So the "restaurant name" step had no
referent and was dropped — onboarding is creating the brand, full stop.

The brand step asks **name only**: Stripe Connect Express collects legal details at
payout setup, and asking twice is waste.

### 5. The foundational detour — `tenant = brand`?

The user then questioned the model itself:

> _"а может тогда было бы правильно чтобы owner мог владеть несколькими тенантами а не
> брендами то есть tenant = brand но тогда нужно подписка на owner"_

This was out of phase scope but **upstream** of it — 10.2's shape depends on the
answer — so it was worked rather than deferred.

Verified first: Better Auth natively supports multi-organization membership
(`activeOrganizationId` on the session, `setActiveOrganization` already called in
`signup.service.ts`). So the collapse was technically cheap in the auth layer.

Presented the real trade-off — what is _shared_ between an owner's restaurants:
staff, guest base, loyalty, cross-brand analytics, and the subscription.

**The assistant recommended the collapse** (`tenant = brand` 1:1), because it would
have deleted the entire brand-pin mechanism and roughly halved the phase, at zero
migration cost. **The user chose the opposite** — _"Да, это одна группа"_ — restaurants
of one owner do share staff, guests and loyalty.

That choice preserves the work already shipped in 08.4/08.5 and keeps this phase at
full size. Recorded as D-01/D-02 with the rejected alternative and its rationale, so
the question is not reopened from scratch later.

On billing the user chose _"На владельце, тариф задаёт число"_ — one subscription per
owner/group, plan caps brand count. Billing does not exist, so the cap itself is
deferred (D-03) rather than built here.

### 6. Country and language placement

The user first put country **"только на бренде"**. That left signup with a country
question and nowhere to store it before a brand exists, and left the interface with no
language to render in.

Asked where the interface language lives. The user answered sideways —
_"давай добавим langSwitcher в ui"_ — which resolves it: language is a **user**
property the person controls directly, seeded from the signup country's default
locale. Recorded as D-24.

### 7. Questions resolved without asking

Two were decided rather than put back to the user:

- **Old `/{brandSlug}/...` URLs.** The first framing confused the user
  (_"тут вообще не понял о чем ты"_). Re-explained in plain terms, then decided:
  no compatibility shim. The product is unlaunched, no bookmarks exist, and the user's
  standing instruction is to not carry dead code. (D-06)
- **`tenants.display_name`.** Once the tenant became "the group", naming it after its
  first brand reads better than naming it after the owner, and needs no extra question.
  (D-04)

## Standing instruction captured

Sent mid-discussion: _"и при реализации выпиливай все лишние чтобы не тянулся старый
ненужный код"_. Recorded as D-27 with a concrete named list rather than as a vague
principle — including `@RequireBrand` / `REQUIRE_BRAND_KEY`, which spans 8 api files
and is read by no guard.

## Scope explicitly pushed out

Brand-count enforcement, the owner-level subscription entity, shared-staff UI,
country-config extensions (timezone, address shape, fiscal rules), US as a supported
country. All in CONTEXT.md `<deferred>`.

## Follow-up round — tenant naming, and a defect found in D-04

The founder revisited D-04: _"может тенанта регестрировать вместо name на фамилию и имя
owner или какая вообще практика для saas подобного, поресерч как у других"_.

### What the research said

- Signup forms of 3 fields or fewer convert ~25%; 6+ fields ~15%. Consistent advice:
  email and password only, defer everything else. (CXL, Custify, Raze)
- The closest comparables collect the business name at **activation**, not signup:
  Square asks legal name / DBA / registration number when connecting payouts; Toast
  confirms the restaurant name during onboarding. This matches what the phase already
  decided (brand name at onboarding, legal details to Stripe).
- Slack is the counter-example — it asks for the team name at signup — but Slack sells
  the team itself, whereas our tenant is plumbing.
- Not from search, recorded as assistant knowledge: Stripe identifies accounts by ID
  until KYB; Shopify has no group object for standard merchants (a store _is_ the
  account, multi-store = several stores); Vercel's personal scope is the username and a
  team is named only when created.

**Unifying pattern:** the group layer is named only once a group actually exists.

### The defect

While checking whether the tenant name is publicly visible, found that
`provision-tenant.service.ts:40` writes `<tenantSlug>.menu.resto.app` into
`tenant_domains` — the **same suffix** brands use for the guest menu.

Two consequences:

1. The founder's proposal (tenant named after the owner) would have published a
   **personal name as a guest-facing hostname** — bad on its own, worse alongside the
   GDPR erasure pipeline.
2. **The assistant's own D-04 was worse.** "Tenant named after the first brand" plus
   onboarding creating exactly one brand = the identical hostname written into both
   `tenant_domains` and `brand_domains` on **every single signup**. The two tables have
   separate unique indexes, so nothing prevents it; both inserts use
   `onConflictDoNothing` scoped to their own table, so it would fail silently rather
   than loudly. This was written into CONTEXT.md without checking the hostname path,
   and is corrected here as D-28.

### Resolution

- Tenant loses its subdomain entirely (D-28). Guest traffic resolves brands first
  (`tenant-and-brand-resolver.service.ts:27`), so the tenant never needed one.
- Tenant name: silent default = first brand's name, **never displayed while there is one
  brand** (verified: no admin surface reads it today), and the group-naming question is
  asked when the owner creates a _second_ brand. That dissolves the founder's objection
  that every option looked wrong — a value nobody sees does not have to be right yet.

### Host scheme settled

The founder redirected to a host-based model: _"у каждого бренда свой домен а не у
тенанта... при логине к бренду переходит на brand.resto.app"_.

Assessed honestly, this improves on D-05 rather than reversing it: a path segment
changes on every navigation (18 route files to reconcile), a host is constant for the
session (**one** check at bootstrap). `AUTH_COOKIE_DOMAIN` already mandates a leading
dot for cross-subdomain cookies, so the design anticipated it.

Raised the conflict over the bare `<brandSlug>.resto.app` — wanted by both the admin and
the future public website. Founder assigned it to the **website**; admin goes to
`<brandSlug>.admin.resto.app` (D-29/D-30). Cookie scoped to `.admin.resto.app` so the
guest menu never receives the operator session.

### Gap surfaced, not absorbed

There is no brand-creation route outside `onboarding/brand.tsx`; the only entry point
was "add brand" in the switcher this phase deletes. After 10.2 an owner cannot create a
second brand. Recorded in `<deferred>` for the planner to place, rather than left to be
discovered during execution.
