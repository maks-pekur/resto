## Onboarding-resume redirect — what triggers it, before and after

**Before:** `$brandSlug/_layout.tsx`'s `BrandLayout` component read `meBrandsQuery()`. If the operator had zero brands, it redirected to `/onboarding/brand`. This check only ever ran once the operator was already inside the `/{brandSlug}/*` subtree — reachable only via the top-level `routes/index.tsx`'s own separate auth-check-and-redirect, or a direct URL. There was no `pending_setup`-style status check available to it; that status is itself introduced by this same merge's earlier plans (signup/finalize-tenant-setup, plan 08 range) and had no consumer in the admin UI before this plan.

**After:** `(protected)/_layout.tsx`'s `ProtectedLayout` reads `meTenantsQuery()` on every protected navigation (not just a brand-scoped subtree, since there is no longer a separate subtree). If zero tenants, or exactly one tenant with `status === 'pending_setup'`, it redirects to `/onboarding/brand` — unless already there, in which case it renders a bare `<Outlet/>` with no sidebar chrome (an onboarding-bound owner has no tenant data to render a dashboard from). Two or more tenants render normally; picking among them is plan 17's sign-in-time picker, not this layout's job.

**What a half-onboarded owner sees on their next visit:** identical UX shape to before (landed straight on the "Create your restaurant" card, no dashboard flash) but now also covers the `pending_setup` case the old code had no way to express — an owner who signed up, has exactly one tenant, but never named their restaurant is now correctly kept on the onboarding screen on every subsequent visit, not just a first-time zero-tenant state. The card's own field changed too (see Deviations): one field, "Restaurant name," no slug input — D-30/UI-SPEC S4's explicit shape, not a UX invention.
