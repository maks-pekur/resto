### What a person must do after seeding to reach a paid test order

This is the deliverable this task exists to produce — instructions for someone who has not read
this phase, ending at a paid test order:

1. **Get a real Stripe test-mode connected account id — the one step this seed cannot do.** Express
   accounts can only accept Stripe's Terms of Service through Stripe's own hosted onboarding form;
   there is no API-only path around that (confirmed live above — the real Stripe SDK genuinely
   rejects anything that isn't a real, existing connected account). Two ways to get one, both
   one-time:
   - **Recommended:** run `pnpm resto:seed seed-demo` (no flag) if you haven't, sign in as
     `owner@demo.local` / `DevPassword123!` at `http://localhost:4000`, switch into the `pizza`
     organization, and start Stripe Connect onboarding from the payments-settings screen (calls
     `POST /v1/tenancy/onboarding/account-link` and redirects to Stripe's hosted form). In Stripe's
     **test mode**, that form has a one-click "skip and use test data" shortcut — no real business
     details needed, takes under a minute.
   - **Alternative:** create a test-mode Express account directly from the Stripe Dashboard
     (test mode toggle ON, Connect → Accounts → New).
     Either way, copy the resulting `acct_...` id — from the dashboard, or from
     `SELECT stripe_account_id FROM tenants WHERE slug = 'pizza';` after onboarding completes.
2. **Re-seed with the flag:**
   `SEED_STRIPE_TEST_ACCOUNT_ID=acct_xxx NODE_ENV=development pnpm resto:seed seed-demo --payments-ready`
   — this is idempotent and safe to re-run; it only touches `pizza`'s four (five, counting
   `account_type`) Stripe columns.
3. **Place a guest order:** `POST http://localhost:5001/v1/orders` with header
   `x-tenant-id: <pizza's tenant id>` and `x-location-id: <a pizza location id>` (both readable
   from `GET /v1/menu` with the same `x-tenant-id` header, and from the `tenants`/`locations`
   tables). Note the returned `orderId`.
4. **Start checkout:** `POST http://localhost:5001/v1/checkout/payment-intent` with the same
   `x-tenant-id` header and body `{"orderId": "<orderId>"}`. This now succeeds and returns a real
   Stripe `clientSecret` instead of `payments.not_enabled`.
5. **Confirm the payment.** This last step needs Stripe's client-side confirmation flow (Stripe.js
   / a hosted checkout UI) — the admin/qr-menu UI wires this in Phase 10 plan 13's walkthrough;
   from a raw API session, confirm the PaymentIntent directly against Stripe's test API using
   `pm_card_visa` (Stripe's standard test payment method token) and the `clientSecret` from step 4.
   A successful confirmation flips the order to `requires_action` → `paid` via the webhook path
   already covered by `apps/api/test/e2e/payment-lifecycle.e2e.spec.ts`.

Step 1 is the one step neither this seed nor any script performs — it is the founder's own
reasoning for choosing Option A, stated plainly rather than worked around.
