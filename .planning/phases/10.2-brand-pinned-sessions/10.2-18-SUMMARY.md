## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `tools/scripts/seed/lib/auth-db.ts` queried the renamed `organization_id` column**

- **Found during:** Task 1, before the first seed run
- **Issue:** `member.organization_id` was renamed to `member.tenant_id` by migration 0079 (D-41). This file (not in the plan's `files_modified`) still queried the old name in `findMemberId`/`insertStaffMember` — the seed would fail on every staff-member lookup/insert against the live schema.
- **Fix:** Renamed the column reference and the function parameters (`organizationId` → `tenantId`) to match.
- **Files modified:** `tools/scripts/seed/lib/auth-db.ts`
- **Verification:** Live seed run succeeded; member rows created/queried correctly.
- **Committed in:** `14177002`

**2. [Rule 3 - Blocking] `POST /api/auth/sign-up/email` now rejects the seed's staff-account creation**

- **Found during:** Task 1, before implementing (traced from plan 13's already-merged D-29 closure, then confirmed live)
- **Issue:** The original seed created staff BA accounts via a direct `fetch` to `/api/auth/sign-up/email`. Plan 13 closed that route to external callers without a pending invitation for their email (403 `signup.direct_disabled`). None of the seed's fixture staff emails have one.
- **Fix:** Staff accounts are now created via `/internal/v1/tenants/:id/owner` (the internal-token-gated path `auth.api.signUpEmail` still reaches without the D-29 `ctx.request` gate), which always grants BA `role: 'owner'` — immediately downgraded to `'staff'` via the same raw-SQL escape hatch the file already used for member-row idempotency. Safe only because staff are always bootstrapped before the real owner for the same organization in `runSeedDemo`'s per-org loop, so `findOwnerByOrganization` finds no existing owner when the trick runs. Documented inline (`seed-demo.ts`, `ensureStaffAccount`'s doc comment) since the safety argument is not obvious from the code alone.
- **Files modified:** `tools/scripts/seed/commands/seed-demo.ts`
- **Verification:** Two live, consecutive full seed runs; member roles queried directly from Postgres both times — owner has role `owner` on all 3 organizations, manager/cashier have role `staff` on their one organization each, unchanged across the re-run.
- **Committed in:** `14177002`

**3. [Rule 1 - Bug] `tenancy_erase_tenant()` silently stopped erasing `legal_name`/`legal_form`/`tax_id`/`stripe_account_id`**

- **Found during:** Task 2, reading the SQL function `tools/scripts/erase-tenant/cli.ts` actually calls (transitively, via `OffboardTenantService`/`TenantRepository.eraseTenant`) rather than assuming the plan's premise that the CLI itself enumerates PII columns
- **Issue:** Migration 0077's `tenancy_erase_tenant()` hard-deleted the whole `brands` row on erasure, which erased `legal_name`/`legal_form`/`tax_id`/`stripe_account_id` as a side effect (confirmed via `git show a20a4a34:packages/db/migrations/0077_tenancy_erase_payment_refunds.sql`). Migration 0079 correctly dropped `DELETE FROM brands` (the table no longer exists) but added no replacement — those four columns now live on `tenants`, which is never deleted (hard deletes forbidden; it's the tombstoned root aggregate). A real GDPR erasure has been silently leaving a restaurant's legal name and tax id behind since migration 0079 landed.
- **Fix:** New migration `0080_tenancy_erase_tenant_pii.sql`, `CREATE OR REPLACE FUNCTION tenancy_erase_tenant(...)` (same signature) adding one `UPDATE tenants SET legal_name = NULL, legal_form = NULL, tax_id = NULL, stripe_account_id = NULL WHERE id = p_tenant_id` step, placed alongside the existing `audit_log` anonymization step (same "anonymize the surviving row" pattern).
- **Files modified:** `packages/db/migrations/0080_tenancy_erase_tenant_pii.sql` (new), `packages/db/migrations/meta/_journal.json`
- **Verification:** Live probe against a scratch tenant (not one of the 3 demo organizations) — see "Live Verification" above. All four columns confirmed `NULL` post-erasure.
- **Committed in:** `f84debf7`

## What a person must do after seeding to reach a paid test order

**Not implemented yet (Task 3 is the blocking checkpoint) — this section is upfront disclosure of what the founder is choosing between, not a completed deliverable.**

Regardless of which option is chosen for Task 3, two things are true independent of this plan's work, discovered while reading `payments.module.ts`/`tenancy.module.ts` for the checkpoint report:

1. **The payments module always wires the real Stripe SDK adapter** (`createStripeProviderAdapter`), never a stub — `env.STRIPE_SECRET_KEY ?? 'sk_test_placeholder'`. There is no code-level bypass of real Stripe for PaymentIntent creation. `STRIPE_SECRET_KEY` is already set in this environment's `.env` (confirmed present, value not inspected/logged).
2. **`Tenant.canAcceptPayments()` only checks `stripeAccountId !== null && stripeChargesEnabled`** — `stripeOnboardingStatus` is not part of the gate `create-checkout-payment.service.ts` actually enforces, even though the plan's acceptance criteria ask for it to be `'complete'` too (for realism/consistency, not because the code requires it).

This means: **whichever option is chosen, `stripe_account_id` must be a real Stripe test-mode connected account id that genuinely exists under the founder's Stripe test-mode account** — a seed cannot fabricate a working connected-account id; Stripe's API will reject a PaymentIntent creation call against a nonexistent account regardless of what the local `tenants` row claims.
