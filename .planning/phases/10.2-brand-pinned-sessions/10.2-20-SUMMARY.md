## Proof 2 — both spellings of the session pin

`rg -c "activeBrandId|active_brand_id" apps packages tools` (excluding migrations) → **0**.

Both spellings matter. `grep active_brand_id` finds the schema and the migration; `grep activeBrandId`
finds the TypeScript that actually breaks. F-27 is the endpoint that was dead on every request while every
static gate stayed green, precisely because only one spelling was being looked for.

## Proof 3 — the live database catalog

Run **as the schema owner `resto`**, never as `resto_app` — `information_schema` filters by privilege, so a
restricted role returns zero for everything and every probe passes for the wrong reason. That exact false
green happened earlier in this phase.

For both `brand` and `organi`, across tables, columns, indexes, constraints, functions (printed as
`oid::regprocedure` so overloads are distinguishable), policies and sequences: **empty**.

Run twice — before and after applying the two migrations the database was behind on. The database was at 81
of 82 migrations; `0080_tenancy_erase_tenant_pii` and `0081_member_location_scope_composite_fk` were
applied, and the sweep re-run clean.

This proof exists because file greps cannot see a database object name. Four objects hid from every source
grep during this phase — a surviving `app_bind_brand(text, boolean)` overload, a policy whose table had
been renamed but not the policy, and an `organization_role` primary key plus two policies that
`ALTER TABLE ... RENAME` does not touch (F-17).

## Proof 4 — the composite-FK invariant (ADR-0020 I-2)

`db:audit-fks` → **no I-2 violations**.

Worth stating plainly: this audit had not run since 2026-06-21 because `packages/db/src/roles.ts` imported
a `.sql` file as a module, which Node 24 cannot resolve (F-15). The same break disabled role provisioning,
which is why the dev database sat unusable for two waves after plan 05's reset (F-30). With the tool
repaired it immediately found a real violation — `member_location_scope_member_fk`, missing `tenant_id`,
originating in phase 08.4 (F-16) — which plan 19 fixed in migration 0081. The audit now passes against the
live database.

**The website build is excluded on purpose, and this is not a phase regression.** `apps/website` validates
its environment at build time and refuses development values — `NEXT_PUBLIC_API_ORIGIN must not be a
localhost URL in production`. Supplying a production-shaped origin makes the next guardrail fire on
`WEBSITE_URL`. It is a chain, by design: a production build with a development `.env` is meant to be
impossible. This phase never touched the website's env or config.

The alternative — setting environment variables one at a time until the chain stops — would convert a real
production guardrail into a formality. It was not done. Recorded as F-44.

## What is proven, and what is only proven statically

**Proven by running it:** the typecheck and build gates, the test suites above, the database catalog sweep,
the FK audit, the contract sync, the route reconciliation. Also, earlier in the phase and against a live
server: signup through to a working dashboard, the session-switch dead-token guarantee (old cookie replayed
→ 401), the `set-active-location` repair, the invitation carve-out, and the same-origin session transport
verified in a real browser on a per-organization host.

**Proven only statically:** the guard-bypass route set (18 controllers before and after — verified by set
diff and by occurrence count, but the authenticated routes could not be probed because `AuthGuard` returns
401 before `LocationScopeGuard` is reached).

**Not proven at all:** a paid test order. Migration to a payment-ready seed is done and gated behind
`--payments-ready`, but completing a real payment needs a Stripe test-mode connected account, and Express
accounts can only accept Stripe's terms through Stripe's own hosted form. That step is the founder's and
takes about a minute; the walkthrough is written out in `10.2-18-SUMMARY.md`.
