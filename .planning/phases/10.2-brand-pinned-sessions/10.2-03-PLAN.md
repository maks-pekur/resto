<objective>
Collapse `brands` into `tenants` at the Drizzle-schema level: move every brand-only column onto the merged
entity, add `country`, merge the two domain tables into one, relocate the surviving `locations` and
`member_location_scope` tables out of the file being deleted, and drop `session.active_brand_id`.

Purpose: this is the spine of the phase. Every API and admin sweep downstream reads the shape this plan
defines. It must land before the migration (plan 05) and before any code that queries the new columns.
Output: the Drizzle schema describes one restaurant entity with no second dimension. `packages/db`
typechecks; the live database does not match yet — plan 05 applies it.
</objective>

`stripeRequirementsDue` (jsonb `$type<string[] | null>()`), `fiscalizationConfig` (jsonb).

Resolve the five collision columns in favour of the existing `tenants` definitions, which already carry
NOT NULL constraints and defaults that the rest of the codebase relies on:
`slug` (citext NOT NULL), `displayName` (text NOT NULL), `status` (NOT NULL default 'active'),
`locale` (NOT NULL default 'en'), `defaultCurrency` (NOT NULL default 'USD'). The `brands` versions were
nullable; nothing is lost by taking the stricter side, and every writer already supplies these.

Add the new `country` column (D-34): `country: text('country').notNull()`. NOT NULL is deliberate — every
organization is created by `/v1/signup` or the seed CLI, both of which supply a country after plan 12/17,
and D-12 gives a database reset so there are no legacy rows to backfill. A nullable column would let a
provisioning path silently create a market-less organization whose currency and locale cannot be derived.

Carry over the brand `check()` constraints, renamed to the `tenants_` prefix:
`tenants_legal_form_chk` (NULL or IN 'IP','OOO','LLC','SOLE*PROP','OTHER'),
`tenants_payment_provider_chk` (IN 'stripe'),
`tenants_account_type_chk` (NULL or IN 'express','standard'),
`tenants_stripe_onboarding_status_chk` (IN 'not_started','pending','complete','restricted').
Add `tenants_country_chk` (IN 'UA','GB','ES') mirroring `COUNTRY_REGISTRY`'s key set from plan 01.
Keep the four existing `tenants*\*\_chk` constraints unchanged, including the richer status check that
already covers 'pending_offboarding' and 'erased'.

Extend `tenants_status_chk` with one new value: `'pending_setup'`, giving
`IN ('pending_setup','active','suspended','archived','pending_offboarding','erased')`.

> RECONCILIATION — read this before implementing. CONTEXT.md's locked decisions conflict on when the
> organization is created. D-25 says signup "creates the user and their first organization"; D-30 says
> "onboarding is creating the first organization"; D-34 says country is "collected at signup, applied to
> the first organization at onboarding"; D-31 requires the resume point to be derived from existing data
> rather than a progress flag; D-06 requires the owner be asked for a name exactly once, at onboarding.
> The reading that satisfies all of them: `/v1/signup` creates the user AND the organization atomically
> (so no stranded account, D-26) with the signup country applied and a provisional name/slug, marked
> `status = 'pending_setup'`; onboarding is where the owner names the restaurant, which sets
> `display_name`/`slug` and flips the status to `'active'`. The resume point is then derived from
> `status`, a lifecycle column that already models exactly this kind of state — not a new boolean flag.
> Plan 13 implements both halves and restates this note. If the founder rejects the reading, the only
> change needed here is removing this one enum value.

`'pending_setup'` is safe to add because every public-serving path gates positively on `'active'` —
`SERVABLE_STATUSES` in `tenant.aggregate.ts:29` is `new Set(['active'])`, and the host resolvers test
`status === 'active'`. A `pending_setup` organization therefore serves no guest menu and accepts no order
without any new check being written. Verify that claim by reading `tenant.aggregate.ts` before relying on it.

DROP, do not port, `brands_tenant_display_name_active_uq` (per-tenant case-insensitive unique display name).
Post-merge there is no tenant above the organization for it to be scoped within, so the only faithful
translation would be a GLOBAL unique display name — which would stop two unrelated restaurants both being
called "Pizzeria". Global `tenants_slug_uq` remains the uniqueness guarantee. Record this in the SUMMARY
as a deliberate behaviour change.

Add `tenantParentUniqueIndex('tenants', { id: table.id, tenantId: ??? })` ONLY if reading `_columns.ts`
shows child tables still need a composite FK target on `tenants` — `tenants` has no `tenant_id` column of
its own (each row IS the tenant), so the composite-FK parent for child tables is `(id, id)`-shaped, not
`(id, tenant_id)`. Read `_columns.ts`'s `compositeTenantFk` implementation and state in the SUMMARY how
child tables that previously pointed at `(brands.id, brands.tenantId)` now anchor to `tenants` — this is
the ADR-0020 I-2 invariant and must not be weakened, only reduced by one dimension.

`tenantDomains` is unchanged structurally (D-23 merges rows into it, not columns). Leave it in this file.
</action>
