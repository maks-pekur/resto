# Phase 10.2 Plan 12: Session revoke-and-reissue, wildcard admin origin Summary

**`POST /api/auth/switch-organization` revokes the calling session and issues a new one bound to the target organization only after verifying membership, proven end-to-end by a 4-case live-server regression that asserts the pre-switch token is rejected (401), not merely stale; `*.admin.<domain>` is now a trusted Better Auth origin, matched at the hostname label boundary by BA's own anchored matcher, with `evil-admin.resto.app.attacker.com` and `admin.resto.app.attacker.com` both proven to fail that match by name.**

## Accomplishments

- `organization-switch.plugin.ts`: a Better Auth plugin exposing `POST /api/auth/switch-organization` — `sessionMiddleware`-gated, validates `organizationId` as a UUID, checks membership via `ctx.context.adapter.findOne({model:'member', ...})` (line 43) strictly before `internalAdapter.createSession(...)` (line 66), then `internalAdapter.deleteSession(session.token)`, then `setSessionCookie` (BA's own helper — no hand-rolled `Set-Cookie`). `activeLocationId` is explicitly reset to `null` on the new session.

## The membership check that authorizes a switch

`ctx.context.adapter.findOne<MemberRow>({ model: 'member', where: [{ field: 'userId', ... }, { field: 'organizationId', ... }] })` in `organization-switch.plugin.ts` (line 43). It runs strictly before `internalAdapter.createSession` (line 66) — a caller who is not a member of the target organization never reaches session creation. A second `findOne` against `model: 'organization'` (the `tenants` table, aliased) confirms the target exists and supplies its `slug` for the response body; both the "not a member" and "no such organization" paths return the identical `FORBIDDEN` response, matching T-10.2-12-07's accepted-risk disposition (no enumeration signal).

## Old token dead, not merely stale

`test/e2e/organization-switch.e2e.spec.ts` case 1 captures a session bound to organization A, switches to B, then re-uses the A-bound cookie against `GET /v1/tenants/me` (an `AuthGuard`-protected route) and asserts **401**. `GET /api/auth/get-session` was deliberately NOT used for this assertion — BA's own `getSessionFromCtx` swallows a missing/deleted session and returns 200 with a null body, which would prove nothing; only a route that genuinely gates on a resolved principal can prove the token is dead rather than just "session row eventually cleaned up."

## Route naming: BA's `organization` spelling kept, deliberately

`POST /api/auth/switch-organization` and its `{ organizationId }` body field keep Better Auth's vocabulary rather than becoming `switch-tenant`/`{tenantId}`. This is the D-41-sanctioned exception, not an oversight: the endpoint is a Better Auth plugin, defined inside `infrastructure/better-auth/` (the one directory D-41 confines BA's vocabulary to), mounted under BA's own `/api/auth/*` route namespace — the same namespace `/api/auth/organization/set-active` and `/api/auth/organization/create` already live in. Everywhere this plan touches outside that one file and that one route says `tenant` (`identity-core.module.ts`'s `ADMIN_WEB_ORIGIN_WILDCARD` wiring, this SUMMARY, `deferred-items.md`).

**1. [Rule 1 - Bug] `databaseHooks.session.update.after`'s location-pin logic depended on a variable deleted by this same task**

- **Found during:** Task 1, while deleting the brand-pin sub-block per the plan's own action text

- **Fix:** Replaced `pinnedBrandId` with `session.activeOrganizationId` (already validated as a non-empty string earlier in the same function) — correct because the tenant IS the former brand post-merge (D-40/D-41), so this is what a freshly-pinned brand id used to mean, not a workaround. Renamed the ctx-scoped single-fire gate (`brandPinDone` WeakMap / `BrandPinDoneStash` interface) to `locationPinDone`/`LocationPinDoneStash`, and changed its guarding early-return from checking the now-gone `session.activeBrandId` to `session.activeLocationId` — same "don't re-fire if already set" intent, checked against the right field.

- **Verification:** `rg -in "brand" apps/api/src/contexts/identity/infrastructure/better-auth/` — zero matches. `cd apps/api && npx tsc -p tsconfig.json --noEmit | grep '^apps/api/src/'` — zero.
- **Committed in:** `88e6ad6e` (Task 1)

**2. [Rule 3 - Blocking] `test/unit/shared/admin-origin-wildcard.spec.ts`'s wildcard-matcher test proved nothing under vitest's `NODE_ENV=test`**

- **Found during:** Task 2, writing the required "imports Better Auth's matchesOriginPattern directly" unit test
- **Issue:** `matchesOriginPattern` is not part of Better Auth's public `exports` map (deep-import throws `ERR_PACKAGE_PATH_NOT_EXPORTED`, confirmed empirically). The adapted approach — exercise it through a real `buildAuth()`/`.handler()` call — silently passed with the WRONG assertions the first two attempts: `@better-auth/core`'s `isTest()` disables origin-check whenever `NODE_ENV==='test'` (vitest's default) unless `advanced.disableOriginCheck` is set, and that field is baked in at `betterAuth()` construction from a MODULE-LEVEL constant captured at first import — `vi.stubEnv` before/after construction, and even awaiting `$context`, had no effect once the module had already loaded.
- **Fix:** Construct a raw `betterAuth()` (not this repo's `buildAuth()` wrapper — its `BuildOpts` has no `advanced` passthrough) with `advanced: { disableOriginCheck: false }` set explicitly, forcing the real check deterministically regardless of `NODE_ENV`. Verified with `NODE_ENV=test` set explicitly via a throwaway script before trusting it inside vitest.
- **Files modified:** `apps/api/test/unit/shared/admin-origin-wildcard.spec.ts`
- **Verification:** `cd apps/api && npx vitest run test/unit/shared/admin-origin-wildcard.spec.ts` — 7/7 pass, including both attacker-origin rejections logged via BA's own `logger.error('Invalid origin: ...')`.
- **Committed in:** `b2b3ee1b` (Task 2)

**3. [Rule 3 - Blocking] `operator-fixture.ts`'s `provisionTenant` sends a field the internal tenants endpoint no longer accepts**
