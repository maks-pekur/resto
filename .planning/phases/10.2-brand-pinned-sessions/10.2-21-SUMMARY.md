## A discovered environment gap: worktree-symlinked `@resto/api-client` was invisible to tsc

While verifying the `MenuBrandDto` rename, `apps/qr-menu` and `apps/website`'s typecheck failed with `Property 'tenant' does not exist on type 'MenuDto'` — even though the source was correctly edited. Root cause: `apps/{qr-menu,website}/node_modules` is a whole-directory symlink to the **main checkout** (this repo's `.claude/settings.json` `worktree.symlinkDirectories` setting, which shares `node_modules` across worktrees for install-cost reasons — see phase FINDINGS.md F-26). `node_modules/@resto/api-client` inside that shared directory resolves, via a _relative_ symlink, back to the main checkout's own (unmerged) `packages/api-client` — not this branch's edited copy. Neither `apps/qr-menu/tsconfig.json` nor `apps/website/tsconfig.json` had a `paths` override for `@resto/api-client`, so plain node_modules resolution silently won, and both `tsc` and `typescript-eslint`'s type-aware rules checked the rename against stale code (the eslint failure is what actually blocked the commit — see Deviations below).

Fixed by adding an explicit `@resto/api-client` path mapping (matching the exports map: `.`, `/public`, `/internal`) directly to both apps' own `tsconfig.json`, widening `rootDir` to `../..` so the cross-package source is in scope. Verified the fix is honest, not a workaround that papers over a real error: before applying it permanently, a throwaway `tsconfig.verify.json` (never committed, deleted after use) with the same `paths` override proved `tsc` was clean against the actual worktree source; the permanent fix reproduced the identical result through the app's real `tsconfig.json`.

**This is a wider pattern than this one fix covers.** The root `/tsconfig.base.json` already has `paths` entries for `@resto/{domain,db,events}` — but `grep`ing the whole repo for anything that extends it returns zero files. Every real app/package instead extends `packages/config-typescript/*.json`, which has no `paths` at all. This means the _same_ silent-stale-resolution risk exists today for `@resto/domain`, `@resto/db`, and `@resto/events` too, for any worktree-isolated agent that changes one of their exported _type shapes_ (not just values — this plan's own `reserved-slugs.ts` change was a value-only edit and genuinely did not need this fix; see `Known Gaps` below for the one test that surfaced that half of the picture). Recommend a follow-up: either wire `packages/config-typescript/base.json` to carry the same `paths` map (fixing it for every project at once), or accept this as a documented, standing verification caveat for the phase.
