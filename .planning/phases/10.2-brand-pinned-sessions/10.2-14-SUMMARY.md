# Phase 10.2 Plan 14: Admin data-access layer rewrite onto the merged API contract Summary

**`apps/admin/src/lib/` now sends `x-tenant-id`/`x-location-id` only (no `x-brand-slug`), every query module targets a real endpoint under the merged tenant contract, and the two duplicate/dead Stripe-payments client modules are collapsed into one (`tenant-payments-api.ts`) pointed at the live `TenantOnboardingController` routes — a plan-vs-live-contract mismatch neither predecessor file had correct.**

## Performance

- **Duration:** ~35 min (includes reading the live API source for every endpoint touched, per the "read it rather than guessing" instruction)
- **Tasks:** 3 of 3 committed
- **Files modified:** 10 (2 created, 6 modified, 4 deleted)

## Accomplishments

- `api-client.ts`'s `apiFetch` carries `x-tenant-id` (from `session.activeOrganizationId`) and `x-location-id` only; the `brandSlug` option and its `x-brand-slug` header are gone. The 2s session cache, GET retry/backoff, and `/login?expired=1` redirect are all untouched.
- `queries/identity.ts`: `meBrandsQuery` replaced with `meTenantsQuery()` calling `GET /v1/me/tenants`, typed `{ tenants: Array<{id; slug; displayName; status}> }` — verified field-for-field against the live `MeTenantsController`. `MeResponse`'s stale `activeBrandId` field removed (confirmed the live `/v1/me` controller never returned it).
- `queries/tenancy.ts`: `TenantResponse` extended to the full merged shape (`country`, `locale`, `theme`, `legalName`/`legalForm`/`taxId`, `paymentProvider`/`accountType`, all four `stripe*` fields, `primaryDomain`, timestamps) — verified against `apps/api/src/contexts/tenancy/interfaces/http/tenant-response.ts`.
- `queries/catalog.ts`, `queries/locations.ts`, `queries/orders.ts`: every `brandSlug` parameter, brand-flavored query-key segment, and brand response field (`LocationView.brandId`, `PinnableLocation.brandId`, `OrderDetailApi.brandId`) removed. `roles.ts`/`team.ts` needed zero changes — already brand-free. `use-effective-location.ts` needed zero changes to its own query calls.
- `tenant-payments-api.ts` (new): merges `brand-payments-api.ts` and the fully-dead `payments-api.ts` into one client, repointed at the live `/v1/tenancy/onboarding/{status,account-session,account-link,oauth/start}` routes — dropping the slug/id parameter entirely, since the live controller resolves the tenant from `@RequireActiveTenant()` session context, not a path segment.
- `slugify-tenant.ts` (new): display-only host-preview derivation, WHY-commented as non-authoritative, mirroring `TenantSlugValue`'s character rules.
- `brand-payments-api.ts`, `payments-api.ts`, `slugify-brand.ts`, `menu/catalog-errors.ts` deleted outright — all four confirmed zero live callers before deletion.
- `apps/admin/src/lib/` typechecks with **zero errors** (confirmed both after each task and at the end, via a direct `npx tsc` run — not an Nx cache hit).

## Where the plan's description disagreed with the live contract

1. **`payments-api.ts` was not a live sibling to merge — it was entirely dead.** The plan's Task 3 read_first text calls it "the sibling that already exists — check whether the two should merge." Reading the live API confirmed `payments-api.ts` had zero callers anywhere in `apps/admin/src` AND called two routes (`GET /v1/tenancy/stripe-status`, `POST /v1/tenancy/stripe-onboarding`) that do not exist — `stripe-onboarding.controller.ts` was deleted outright in plan 07's Task 2 (`10.2-07-SUMMARY.md`: "confirmed dead: no-op `linkStripeAccount`, hardcoded `not_started` status"). There was no live surface to reconcile between the two files; `payments-api.ts` simply had nothing left to contribute.
2. **`brand-payments-api.ts`'s own routes were equally stale.** It called `/v1/tenancy/brands/:brandSlug/onboarding/{status,account-session,account-link,oauth/start}` — a per-brand-slug URL shape. The live controller (`TenantOnboardingController`, `apps/api/src/contexts/tenancy/interfaces/http/tenant-onboarding.controller.ts`) serves `/v1/tenancy/onboarding/*` with **no slug segment at all**, gated by `@RequireActiveTenant()` reading the session. Neither predecessor file matched the live contract; `tenant-payments-api.ts` is not a rename-in-place, its call shape changed (zero parameters, not one).
3. **`MeResponse.activeBrandId`** was in the admin's own type but was never present in the live `/v1/me` controller's response, confirmed by reading `me.controller.ts` directly — a pre-existing stale type, not something this phase's merge removed.
4. **`GET /v1/me/tenants` and `queries/identity.ts`'s `meTenantsQuery`**: matched the plan's own locked `<interfaces>` contract exactly (`{tenants: Array<{id; slug; displayName; status}>}`) — no divergence found here.

## `x-tenant-id` handling for the location endpoints

Already encoded, unconditionally — `apiFetch` sends `x-tenant-id` from `session.activeOrganizationId` on every request where the session has an active organization, not specifically for the location endpoints. This predates this plan (it was already in `api-client.ts` before Task 1 touched the file) and was proven live end-to-end by plan 13 (`10.2-13-SUMMARY.md`: `GET /v1/me/locations` and `POST /v1/me/set-active-location` both returned 200 with this exact header). No special-casing was needed or added; Task 1's only change to this mechanism was deleting the now-dead `x-brand-slug` sibling header.
