## Task 3 implementation — invitation carve-out (D-29)

**The founder's decision:** implement the carve-out. Close the public route, but admit a request whose email has a valid pending invitation for account creation only — membership still goes through `acceptInvitation` with its own checks (unmodified). This resolves the tension the investigation above surfaced: inviting staff is a shipped, reachable feature (`apps/admin/src/components/team/invite-form.tsx`), and `POST /v1/signup` cannot serve an invitee because it unconditionally provisions a new restaurant (`signup.service.ts` ~line 160), so a blanket closure would strand every invitee who doesn't already have an account.

### Mechanism

`auth.config.ts`'s existing `hooks.before` middleware gained one new branch, matched on `path.endsWith('/sign-up/email')`:

1. **External-vs-internal split:** `if (!ctx.request) return;` — an unconditional pass-through when the call did not arrive via BA's own `auth.handler()` router. This is the SAME distinguishing signal BA's own organization plugin already relies on (see "Proving the control was actually running" below), not a new convention this plan invented.
2. **Invitation lookup (external calls only):** the submitted `body.email` is normalised with `.trim().toLowerCase()`, then matched against `invitation.email` (exact `eq()`, never a partial/LIKE match) with `status = 'pending'` AND `expiresAt > now()`. A hit returns (admits); a miss throws `new APIError('FORBIDDEN', { code: 'signup.direct_disabled', message: '...' })`.
3. **Nothing else changes.** `requireEmailVerificationOnInvitation: true` (Pitfall 8, already in the file) is untouched — an invitee admitted through the carve-out still cannot `acceptInvitation` until their email is verified, exactly as it worked for the direct-signup path before closure.

**Email normalisation, stated explicitly per the task's requirement:** BA's own `crud-invites.mjs:76` writes `invitation.email` as `ctx.body.email.toLowerCase()` — lowercased, **never trimmed**. The carve-out's read-side lookup normalises the SUBMITTED signup email with `.trim().toLowerCase()` before comparing. Trimming only the read side (not re-deriving how the row was written) is deliberate: it cannot cause a false admit, because the comparison is still an exact match against whatever BA actually persisted, and it prevents a legitimate invitee from being falsely rejected by incidental whitespace their browser/autofill introduced. It does not "spoof" anything either direction — verified with a dedicated e2e case (below).

### Proving the control was actually running (F-32 discipline)

10.2-FINDINGS.md F-32 records that vitest's `NODE_ENV=test` silently disabled BA's origin check in an earlier plan, so a security test written the "obvious way" passed without ever exercising the matcher. The same risk applies here: a suite where every case merely "passes" cannot distinguish "the gate rejected the spoof" from "the gate never ran, or a wrapper resolved it to always-200."

This carve-out's proof is stronger than a single reject/accept pair: **case 1 and case 2 hit the exact same endpoint, the exact same code path, with only the DB state differing (no invitation vs. a valid one).** If the `hooks.before` branch were absent, a no-op, or short-circuited to an unconditional pass, case 1 would ALSO return 200 — it does not; it returns 403 with the specific `signup.direct_disabled` code this branch is the only place in the codebase that emits (`rg -n "signup.direct_disabled" apps/api/src` — one match, `auth.config.ts`). Conversely, if the branch were a blanket deny, case 2 would ALSO return 403 — it does not, and the chain continues all the way to a real `member` row. Differential behaviour on the same code path, not merely "one case passed," is the proof the hook is live. Additionally: `NODE_ENV=test` was confirmed NOT to disable anything relevant here — a source-level check (`rg -rn "NODE_ENV" node_modules/.../better-auth/dist`) shows the only `NODE_ENV` reference in BA's entire dist is in an unrelated Vue devtools helper; `hooks.before` itself has no environment gate, and the same `ctx.request` truthy check the closure relies on is BA's OWN production code path (`crud-invites.mjs`'s `list-invitations` endpoint uses the identical check to reject client-side callers passing a query-string email — confirmed by reading that file, not inferred).

### `identity-invitation.e2e.spec.ts` — new automated coverage

The existing spec (2 pre-existing regression tests, unmodified in behaviour) was converted from `startRealStack()`'s fresh-testcontainer-plus-full-migration-replay harness to the live-dev-Postgres pattern established by Tasks 1-2 in this same plan — `startRealStack()` hits the pre-existing 0079 idempotency bug (`deferred-items.md`, owned by plans 05/19) on every run, and this spec is Task 3's own named `<verify>` target, so the blocker now sits directly in this task's path. 1. `rejects a direct signup for an email with no pending invitation` → 403 `signup.direct_disabled`.
2. `admits a direct signup submitted in a different case than the invitation, through to membership` → 200 → verify-email (captured adapter, real JWT token) → accept-invitation → 200 → asserts the persisted `member` row (`tenantId`, `role`) directly, not just the HTTP response. Uses an UPPERCASE variant of the invited email to prove case-insensitive matching (BA writes `invitation.email` lowercased).
3. `rejects a direct signup when the only invitation for that email has expired` → invitation created via the real invite endpoint, `expiresAt` pushed into the past via a direct DB update, then 403 `signup.direct_disabled`.
