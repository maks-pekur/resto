# Phase 10.2 Plan 13: Signup + onboarding finalize (Tasks 1-2 of 3) Summary

**`POST /v1/signup` now takes `{name, email, password, country}` and atomically creates a Better Auth user plus a `pending_setup` organization with country/currency/locale correctly derived and a random-suffixed provisional slug; `POST /v1/me/tenants/onboarding` takes `{displayName}`, resolves the organization from the session (never a body parameter), derives a real slug with silent collision resolution, rewrites the primary domain row and flips the organization to `active` — both proven end-to-end against the live dev database, including the two tenancy-layer bugs (a missing `pending_setup` runtime allow-list entry, a domain-row upsert that silently no-ops on the exact write this feature needs) that a static build could not have caught. Task 3 — closing Better Auth's public signup route — is a blocking checkpoint and was deliberately NOT executed; this plan stops here with investigation evidence for that decision.**

## Accomplishments

- `POST /v1/signup` rebuilt around `{name, email, password, country}` (D-25/D-27/D-32/D-34): the person's name goes to the BA user only; the organization gets a provisional `slugify(name)-<random6>` slug/displayName that is never shown to the owner; provisioning carries `status: 'pending_setup'`; currency and locale are derived from country, never accepted as separate fields. D-06's enumeration-parity floor (`PARITY_FLOOR_MS`, the collapsed `{status: 'pending_verification'}` response) is untouched.
- `POST /v1/me/tenants/onboarding` (new): resolves the target organization from `operator.tenantId` (session-derived, never a body field — closes T-10.2-13-02), 409s if the organization isn't `pending_setup`, derives a real slug reusing signup's own `slugify`/`findFreeSlug`, rewrites the `<slug>.menu.resto.app` domain row in place, and flips the organization to `active`.
- Two tenancy-layer bugs found and fixed as Rule 2/Rule 1 additions, neither of which a static typecheck could see: (1) `tenant-drizzle.repository.ts`'s runtime `ALLOWED_STATUSES` set didn't include `pending_setup`, so every signup 500'd with `Unknown tenant status "pending_setup" in DB` the first time it ran against a real database; (2) the same file's domain-row upsert used `onConflictDoNothing`, which silently skips updating the primary domain's hostname on `finalizeSetup` — an owner's restaurant would activate with the stale, provisional `.menu.resto.app` hostname forever.
- `GET /v1/me/locations` and `POST /v1/me/set-active-location` (plan 11's F-27 repair) verified end-to-end for the first time with a real authenticated, tenant-scoped session — see "Inherited debt closed" below.

## Inherited debt closed (F-27, plan 11)

Plan 11 repaired `POST /v1/me/set-active-location` and `GET /v1/me/locations` after finding them dead on every request, but could only probe them unauthenticated (both 401'd at `AuthGuard`, which runs before the repair). This plan produced the first real authenticated session in the phase, so I closed the gap:

1. Signed up a real owner via the running server (`POST /v1/signup`), signed in via BA, called `POST /api/auth/organization/set-active` with an `Origin` header (required — BA rejects same-site POSTs with a missing/null Origin) to bind the session to the new organization.
2. `GET /v1/me/locations` **403'd** on the first attempt: `auth.tenant_context_missing`. This is `@RequiresTenantContext()` requiring ALS tenant binding via `TenantContextMiddleware`, which is satisfied by an `x-tenant-id` header (or host resolution) — **not** merely by `session.activeOrganizationId` existing. Retried with `x-tenant-id: <tenantId>` (matching `apps/admin/src/lib/api-client.ts`'s documented behavior per CONTEXT.md) → **200 `{"locations":[]}`** (correct — this owner's organization has no locations yet).
3. `POST /v1/me/set-active-location` with the same headers and `{"locationId": null}` → **200 `{"locationId": null}`**.

Both endpoints work correctly for a real, fully authenticated, tenant-scoped caller. F-27's repair is confirmed live, not just statically. This also validates the design decision documented above: `POST /v1/me/tenants/onboarding` correctly does NOT require the same `x-tenant-id` header, because a freshly-signed-up owner has no reason to have sent one yet — and its own service path never touches `ScopedTx`.

- **Proven live:** invited `invitee-live@example.com` (role `staff`) to my live signup's organization via `POST /api/auth/organization/invite-member`; captured the real invitation email from MailHog (`http://localhost:4000/accept-invitation/<id>`); called `accept-invitation` with **no session at all** → **401 Unauthorized** (confirms an accountless invitee is stuck today, before any Task 3 change).
