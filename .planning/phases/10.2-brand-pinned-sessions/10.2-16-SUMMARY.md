## Persistence mechanism removed — before/after (D-39)

**`AutoSaveIndicator` / `useDebouncedAutosave`:** Before this task, `useDebouncedAutosave` had exactly one caller in the entire `apps/admin/src` tree — its own spec file. No production menu-editor component ever invoked it. **Before and after this deletion, every menu editor form (`item-detail-form.tsx`, `modifier-group-form.tsx`, `category-form.tsx`, `item-sizes-card.tsx`, `modifier-options-list.tsx`) saves identically: an explicit Save/Create button triggers `form.handleSubmit(onSubmit)` → a TanStack Query mutation's `.mutateAsync()`.** There is no behavior change here — the debounced-autosave-on-blur/change model was dead code, declared but never wired to a live form, so deleting it changes nothing an operator can observe. Confirmed by reading every hit of `rg -n "AutoSaveIndicator|useDebouncedAutosave" apps/admin/src` before deleting (per the task's own instruction) and by the fact that `apps/admin/src/lib/menu/types.ts`'s `SaveState` — the state shape the indicator rendered — also had zero remaining importers once the indicator itself was gone.

## Scoping that remains after brand-filter removal

**Order feed (`order-card.tsx`, `order-detail-sheet.tsx`, `accept-popover.tsx`, `reject-popover.tsx`, `cancel-dialog.tsx`):** the `brandSlug` argument these components threaded into `apiFetch`-backed mutation functions was never itself a data filter in this codebase's current (post-plan-14) shape — plan 14 had already made every one of these mutation functions ignore any brand/tenant argument and resolve the tenant internally from `session.activeOrganizationId` inside `apiFetch`. What remains, unchanged by this plan: **`locationId`**, threaded explicitly on every order query/mutation (`orderDetailQuery(order.id, order.locationId)`, `advanceOrderStatusMutation({orderId, locationId, targetStatus})`, etc.) — Phase 10's single-location-per-order-feed decision (2026-08-18) is untouched — plus the implicit **tenant scope** enforced server-side via the `x-tenant-id` header `apiFetch` already attaches from the session, which this plan did not add or modify.

**Role editor (`role-form.tsx`, `role-list.tsx`):** `brandSlug` here was never a data filter either — `RoleForm`/`RoleList` never passed it into any query or mutation, only into the two typed-router `navigate()` calls building the (now-obsolete) `/{brandSlug}/roles` URL. No permission-scoping predicate existed to remove and none was removed; the permission matrix itself (`PermissionCatalog`, unmodified by this plan) is scoped to the operator's own tenant the same way every other admin query is — via the session-derived `x-tenant-id` header. Confirmed by reading `role-form.tsx`/`role-list.tsx` in full before editing: the only two `brandSlug` uses in both files were the navigation `params` objects rewritten in Task 2.
