## User Constraints (from CONTEXT.md)

### Locked Decisions

**The model — one restaurant is one organization**

- **D-01:** Tenant and brand merge into one entity, which is the Better Auth organization. One restaurant = one organization = one legal entity with its own Stripe account, country, currency, theme and domains.
- **D-02:** An owner may belong to several organizations. Better Auth supports this natively — `session.active_organization_id` plus `setActiveOrganization`, already called in `signup.service.ts:229`. Nothing new is needed in the auth layer.
- **D-03:** This reverses D-01/D-02 of the first version of this document, where the tenant was a group sharing staff, guests and loyalty across brands. The founder was shown that consequence explicitly and chose the merge anyway. What is knowingly given up: a cook working in two of the owner's restaurants is two separate memberships; guest base and loyalty do not cross restaurants; there is no group-level analytics; ownership transfer and co-ownership must be solved per organization.
- **D-04:** Physically merge into one table — brand fields move into `tenants`, and `brands` is dropped. The alternative (keep `brands` as a strict 1:1 satellite) was offered as cheaper and not taken. Real upside that justifies it: menu tables currently carry both `tenant_id` and `brand_id`, and the merge removes that redundant second dimension permanently along with its composite FKs.
- **D-05:** The whole merge lands inside phase 10.2. Splitting it into a preceding phase was offered and declined.
- **D-06:** The tenant-naming problem dissolves. There is no unnamed container any more — the organization's name is the restaurant's name, asked once in onboarding.

**Merge scope — what is deleted**

- **D-07:** Tables dropped: `brands`, `brand_domains`, `member_brand_scope`.
- **D-08:** Columns dropped: `brand_id` in 9 places — `menu.ts` ×6 (lines 35, 89, 170, 207, 240, 288), `ordering.ts` ×1 (line 27), `customer-profiles.ts` ×1 (nullable, line 18), `outbox.ts` ×1 (nullable, line 39) — plus `session.active_brand_id` (`auth.ts:33`). `active_organization_id` is the only context pin that remains alongside `active_location_id`.
- **D-09:** RLS: the `app_bind_brand` GUC and every brand policy go away (lineage: migrations `0058_brand_rls.sql`, `0061_drop_app_bind_brand_is_system_param.sql`, `0065_location_guc.sql`; binding in `packages/db/src/client.ts`). Tenant and location bindings stay. The ScopedTx + RLS double-enforcement rule is unchanged — it now has one fewer dimension, not one fewer layer.
- **D-10:** Code deleted: `BrandScopeGuard`, `SetActiveBrandService` and its controller, `member-brand-scope-drizzle.reader.ts`, `initial-brand-drizzle.repository.ts`, `onInitialBrandPin` in `auth.config.ts`, `brand-switcher.tsx`, and `@RequireBrand`/`REQUIRE_BRAND_KEY` (8 api files, read by no guard even today).
- **D-11:** Measured blast radius: 137 files reference `brandId`/`brandSlug` (70 in `apps/api/src`, 58 in `apps/admin/src`, 7 in `packages/db/src`, 2 elsewhere). This is larger than everything else in the phase combined; plan it as the spine, not a step.

**Migration strategy**

- **D-12:** Ship as a schema rewrite with a dev-database reset, not a data-preserving migration. There is no production deployment and no paying customer; the founder reset the database earlier the same day. Assumption stated for the record — only valid while no real tenant data exists.
- **D-13:** Seeds and fixtures are rewritten to the merged model as part of the phase, not left for later.

**Session context and the sign-in picker**

- **D-14:** The active organization is the session's entire context. Better Auth owns it; do not build a parallel pin.
- **D-15:** One session = one organization, for the life of that session. Switching organizations revokes the current session and issues a new one; the old token is dead immediately after the switch.
- **D-16:** Switching does not re-prompt for the password — the owner picks, the server revokes and re-issues server-side.
- **D-17:** The picker appears at every sign-in when the owner belongs to more than one organization — a fresh session has no organization bound yet, so there is nothing to remember. Exactly one → skipped, straight to the dashboard. Staff belong to exactly one organization and never see it.
- **D-18:** Mirror the existing staff pick-location interstitial rather than inventing a second pattern.
- **D-19:** The location switcher survives and becomes the only in-app context control. Locations live inside an organization and are unaffected by the merge.

**URLs and hosts**

- **D-20:** The `/{brandSlug}` path segment is removed — admin paths become `/orders`, `/menu/items`.
- **D-21:** The organization lives in the host: admin is served per-organization at `<orgSlug>.admin.resto.app`.
- **D-22:** The bare `<orgSlug>.resto.app` is reserved for the organization's future public website (`apps/website`) and must not be taken by the admin. Guest menu keeps `<orgSlug>.menu.resto.app`. Three branches: `.menu.` guests, `.admin.` staff, bare for the public site.
- **D-23:** One domain table. `tenant_domains` and `brand_domains` merge with their rows' entities.
- **D-24:** Consequences of D-21 the planner must handle: `AUTH_COOKIE_DOMAIN` scoped to `.admin.resto.app`, not the apex; `ADMIN_WEB_URL`/`trustedOrigins` need wildcard matching, anchored at the label boundary, not a naive suffix check; wildcard DNS/TLS for `*.admin.resto.app`; local dev on `*.localhost`.

**Signup**

- **D-25:** Signup asks Name, Email, password, Country — nothing else. It creates the user and their first organization.
- **D-26:** The form must call `/v1/signup`, not Better Auth directly. Today it calls Better Auth and produces a user with zero memberships — a stranded account that cannot create anything (verified live 2026-08-19).
- **D-27:** `signup.service.ts:137-152` currently makes one `displayName` field serve three roles at once — organization display name, organization slug source, and the person's name in Better Auth. Split them.
- **D-28:** Remove the dead currency field (collected, never sent) and fix the mislabelled "Restaurant name" field.
- **D-29:** Close direct Better Auth signup (`POST /api/auth/sign-up/email`). Check invitation acceptance first — it may share the same path, and blindly disabling it would break invite redemption.

**Onboarding**

- **D-30:** Onboarding is creating the first organization — the restaurant. It asks name only; the slug is derived. Legal details are not collected here — Stripe Connect Express collects them at payout setup.
- **D-31:** Onboarding resumes at the step where it was abandoned, with the ability to go back and change the previous step. Derive the resume point from the data that exists, not from a separate progress flag.

**Countries, currency and language**

- **D-32:** Supported countries are a config in `packages/domain`, alongside the other shared registries (`money.ts`, `rbac/`, `reserved-slugs.ts`) — no infrastructure imports, usable from api and both web apps.
- **D-33:** First supported list: UA, GB, ES.
- **D-34:** Country lives on the organization. Collected at signup, applied to the first organization at onboarding. No `country` column exists anywhere today; this phase adds it to the merged table.
- **D-35:** Currency derives from country and is never asked. UA→UAH, GB→GBP, ES→EUR. The Stripe adapter (`stripe-provider.adapter.ts`) already accepts `country` and `default_currency` as optional inputs and nothing supplies them.
- **D-36:** Interface language is a user-level choice, surfaced by a `langSwitcher` in the admin UI, seeded from the signup country's default locale. A cook who speaks Ukrainian in a Spanish restaurant keeps their language.
- **D-37:** The Spanish (`es`) catalogue is added in this phase for both admin and website, covering interface and communication (emails/notifications). Admin ships `ru`/`en` today; website ships `ru`/`uk`/`en`.
- **D-38:** A country whose default locale has no catalogue must fall back deliberately rather than render raw keys.

**Code hygiene**

Beyond the merge deletions in D-07 to D-10: a second, legacy Stripe onboarding path (`start-stripe-onboarding.service.ts` vs `start-brand-onboarding.service.ts` — verify and remove the wrong one); `AutoSaveIndicator`/`useDebouncedAutosave`; `friendlyCatalogError` in `apps/admin/src/lib/menu/catalog-errors.ts`; `apps/admin/app/` leftover Next.js directory.

## Summary

This phase is mechanically well-understood after reading the installed `better-auth@1.4.22` source directly: BA already supports everything D-14–D-19 need natively at the API-surface level (multi-org membership, `activeOrganizationId` on session, wildcard `trustedOrigins`), but the ONE mechanism the founder explicitly wants — revoke the current session and issue a brand-new token on organization switch, with no password re-prompt — is **not** a stock BA endpoint. BA's own `setActiveOrganization` mutates the session **in place** (same token); it does not rotate it. Implementing D-15/D-16 correctly requires a small custom Better Auth endpoint (a `createAuthEndpoint`, added the same way the codebase already extends BA with custom `hooks.before`/`hooks.after`) that calls `ctx.context.internalAdapter.createSession(userId, ...)` for the new session and `ctx.context.internalAdapter.deleteSession(oldToken)` for the old one, then writes the cookie via BA's own `setSessionCookie(ctx, ...)` helper. This is new code but a small, well-precedented amount of it, and it reuses BA's own cookie-signing plumbing rather than hand-rolling it.

The wildcard-hosting requirement (D-21/D-24) is cheaper than it looks: BA 1.4.22's `trustedOrigins` matcher already supports `*`-wildcard patterns anchored end-to-end (`matchesOriginPattern` + `wildcardMatch`, verified in source), so a single static array entry `'https://*.admin.resto.app'` is sufficient — no need for `trustedOrigins` as a function, though BA does support that form too if ever needed. Vite 5.4.21 (the resolved, installed version — well above the 5.4.12 floor where the option was introduced) supports `server.allowedHosts: ['.admin.localhost']` for local wildcard-subdomain dev, and modern Chrome/Edge/Firefox resolve any `*.localhost` name to loopback with zero configuration (Safari has a documented history of gaps here — verify in the actual browser before relying on it).

The schema merge itself is the highest-leverage finding: reading `tenants.ts` and `brands.ts` side-by-side plus the full migration history (not just the three files CONTEXT.md cited) shows the RLS teardown is **smaller** than CONTEXT.md's citation implies — two of the nine original brand policies (`menu_stop_list`, `catalog_brand_stop_version`) were already dropped in migration `0068` when stop-lists were re-grained to locations in Phase 08.4. The live count is 7 policies + 2 functions, not 9. There is also a boot-time preflight assertion (`assertBrandRlsInstalled` in `apps/api/src/main.ts`) that will make the API refuse to start if brand RLS is torn down without also removing this check — CONTEXT.md does not mention it, and it is a hard blocker if missed. `drizzle-kit generate` has been unusable since roughly migration 0018 due to snapshot drift (confirmed: only 10 of 79 migrations have a matching `meta/*_snapshot.json`); every migration since has been hand-written SQL plus a manually-appended `_journal.json` entry. The merge migration must follow the same pattern — there is no alternative.

**Primary recommendation:** Keep the table name `tenants` (do not rename to `organizations`) — the codebase already treats "tenant" (ours) and "organization" (BA's) as synonyms at a well-documented boundary, and a physical rename would touch ~99 `TenantId`-referencing files for zero functional gain, on top of the already-large 137-file D-11 blast radius. Implement the org-switch revoke-and-reissue as a custom BA endpoint, not a hand-rolled cookie/session mechanism. Trust BA's native wildcard `trustedOrigins` matching rather than building a parallel origin-matcher (a working anchored-wildcard matcher, `buildOriginMatcher` in `apps/api/src/shared/security.ts`, already exists in this codebase for CORS — it's a good template if BA's own matching is ever found insufficient, but it isn't needed here).

### Pattern 1: Custom Better Auth endpoint for revoke-and-reissue

**What:** A plugin-shaped object with one `createAuthEndpoint`, registered in the same `plugins: [...]` array as `organization()`, `twoFactor()`, `bearer()` in `auth.config.ts`.
**When to use:** Any time D-15/D-16's "revoke current session, issue a new one, no password" behavior is needed — both the first-pick-after-sign-in case and a later explicit "switch organization" action route through the same endpoint.
**Example (sketch — not exact code, illustrates the verified API surface):**

```typescript
// Source: verified against node_modules/.pnpm/better-auth@1.4.22.../dist/db/internal-adapter.mjs,
// dist/api/routes/session.mjs, dist/cookies/index.mjs
import { createAuthEndpoint, sessionMiddleware } from 'better-auth/api';
import { setSessionCookie } from 'better-auth/cookies'; // path illustrative — resolve exact export at implementation time

const switchOrganization = createAuthEndpoint(
  '/switch-organization',
  { method: 'POST', use: [sessionMiddleware], requireHeaders: true },
  async (ctx) => {
    const { user, session } = ctx.context.session;
    const targetOrgId = ctx.body.organizationId;

    const isMember = await ctx.context.adapter.findOne({
      model: 'member',
      where: [
        { field: 'userId', operator: 'eq', value: user.id },
        { field: 'organizationId', operator: 'eq', value: targetOrgId },
      ],
    });
    if (!isMember) throw new APIError('FORBIDDEN');

    const newSession = await ctx.context.internalAdapter.createSession(
      user.id,
      false, // dontRememberMe
      { activeOrganizationId: targetOrgId, activeLocationId: null }, // override
    );
    await ctx.context.internalAdapter.deleteSession(session.token);
    await setSessionCookie(ctx, { session: newSession, user }, false);

    return ctx.json({ organizationId: targetOrgId });
  },
);
```

**Verified facts backing this sketch:**

- `internalAdapter.createSession(userId, dontRememberMe, override, overrideAll)` — signature read directly from `dist/db/internal-adapter.mjs:132`. `override` is spread into the new session row, so `activeOrganizationId`/`activeLocationId` can be pre-set on creation. [VERIFIED: better-auth 1.4.22 source]
- `internalAdapter.deleteSession(token)` — confirmed at `dist/db/internal-adapter.mjs:310`. [VERIFIED]
- `setSessionCookie(ctx, session, dontRememberMe, overrides)` — confirmed at `dist/cookies/index.mjs:125`; requires a full endpoint `ctx` (cookie-signing helpers), which is why this must run inside a BA endpoint, not a plain NestJS service. [VERIFIED]
- BA's own `/organization/set-active` endpoint (`dist/plugins/organization/routes/crud-org.mjs:365-420`) does the "weak" version of this today: `adapter.setActiveOrganization(token, orgId, ctx)` → `internalAdapter.updateSession(sessionToken, { activeOrganizationId })` — same token, in place. This is NOT what D-15/D-16 want; it is kept as evidence that stock BA does not already solve this. [VERIFIED]
- A fresh session created by `signInEmail` has no `databaseHooks` in the organization plugin that auto-populates `activeOrganizationId` — grepped the entire `organization.mjs` for `databaseHooks`/session-create hooks and found none. This confirms D-17's "a fresh session has no organization bound yet" as fact, not assumption. [VERIFIED]

### Pattern 2: Wildcard trustedOrigins — static array, not a function

**What:** BA 1.4.22's `trustedOrigins` option accepts either a static `string[]` or `(request: Request) => string[] | Promise<string[]>` (confirmed in `dist/api/middlewares/origin-check.mjs:83`: `Array.isArray(ctx.context.options.trustedOrigins) ? ... : [...ctx.context.trustedOrigins, ...(await ctx.context.options.trustedOrigins?.(ctx.request))...]`). Because org slugs are dynamic but always match the existing `^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$` slug regex (no dots), a single wildcard array entry is sufficient — no per-request function needed.
**When to use:** `identity-core.module.ts:234`, where `trustedOrigins` is currently built as `[env.ADMIN_WEB_URL]`.
**Example:**

```typescript
// Source: verified against dist/auth/trusted-origins.mjs + dist/utils/wildcard.mjs
const trustedOrigins: string[] = [];
if (env.ADMIN_WEB_URL) trustedOrigins.push(env.ADMIN_WEB_URL); // e.g. https://admin.resto.app (apex, pre-org-pick)
if (env.ADMIN_WEB_ORIGIN_WILDCARD)
  trustedOrigins.push(env.ADMIN_WEB_ORIGIN_WILDCARD); // e.g. https://*.admin.resto.app
```

**How BA matches it safely (verified, not assumed):** `matchesOriginPattern(url, pattern)` (`dist/auth/trusted-origins.mjs:14`) — when the pattern contains `*` and `://`, it calls `wildcardMatch(pattern)(getOrigin(url))`, and the whole match is anchored `^...$`. Because the pattern's literal segment `.admin.resto.app` includes the leading dot, `https://evil-resto.app` cannot match `https://*.admin.resto.app` even though BA's `*` wildcard segment itself permits dots within the matched span (unlike this repo's own stricter `buildOriginMatcher` in `security.ts`, which explicitly forbids dots inside the wildcard segment via `[^./:]+`). Since org slugs never contain dots (enforced by the slug regex, `TenantSlug`/soon-renamed equivalent), this looser-than-`buildOriginMatcher` matching is still safe in practice — but note the difference for anyone reviewing this later: BA's own matcher is not as strict as this project's home-grown CORS matcher.

### Anti-Patterns to Avoid

- **Reintroducing a brand/org cookie for context:** Forbidden by `apps/CLAUDE.md` and already the subject of a prior retirement (phase 02-03's `resto.active_brand` HMAC cookie). The session (`activeOrganizationId`) is the only context pin — this phase does not change that rule, it removes a dimension (`activeBrandId`) from it.
- **Trying `drizzle-kit generate` for the merge migration:** Will produce an incorrect diff. Confirmed via file inventory: only `0000`–`0018` have matching `meta/*_snapshot.json` files; migrations `0019`–`0078` (60 of them) are hand-written with no snapshot. `drizzle-kit generate` diffs against the last snapshot it has (0018), which is 60 migrations stale.
- **Assuming the 9-policy/3-migration RLS citation in CONTEXT.md is complete:** It is not (see Common Pitfalls below) — verify against the full migration list before writing the teardown migration.

## Common Pitfalls

### Pitfall 1: CONTEXT.md's RLS-teardown citation is incomplete

**What goes wrong:** Writing the teardown migration against only migrations `0058`/`0061`/`0065` (as literally cited in CONTEXT.md) misses that migration `0068_stop_list_location_regrain.sql` already dropped `menu_stop_list_brand_iso` and `catalog_brand_stop_version_brand_iso` in Phase 08.4 (stop-list was re-grained from brand to location). Also missed: migration `0060_brand_rls_restrictive.sql` recreated the remaining 7 policies as `RESTRICTIVE` (not the original `PERMISSIVE` shape from 0058), and `0071_orders_location_rls.sql` layered a **second**, separate `orders_location_iso` policy on `orders` alongside `orders_brand_iso` — only the brand one should be dropped.
**Why it happens:** CONTEXT.md's citation was written from grep-for-"brand_rls"-named-files, which misses migrations named for their own subject (`stop_list_location_regrain`, `orders_location_rls`) that happen to also touch a `*_brand_iso` policy as a side effect.
**How to avoid:** The live, current set of DROP targets (verified 2026-08-19 against the full migration directory) is:

- Policies: `menu_categories_brand_iso`, `menu_items_brand_iso`, `menu_item_sizes_brand_iso`, `menu_modifier_groups_brand_iso`, `menu_modifier_options_brand_iso`, `menu_item_modifier_groups_brand_iso`, `orders_brand_iso` (7, not 9 — `menu_stop_list_brand_iso` and `catalog_brand_stop_version_brand_iso` are already gone as of `0068`).
- Functions: `current_brand_id()`, `app_bind_brand(text)`.
- `orders_location_iso` (from `0071`) is NOT touched — it stays.
  **Warning signs:** A migration that tries `DROP POLICY menu_stop_list_brand_iso` will fail with "policy does not exist" if run against a freshly-reset+migrated dev DB — a cheap, immediate signal that the citation was trusted uncritically.

### Pitfall 2: The boot preflight will refuse to start after RLS teardown unless updated

**What goes wrong:** `apps/api/src/main.ts` calls `assertBrandRlsInstalled(env.DATABASE_URL)` at boot (imported from `apps/api/src/shared/preflight/assert-brand-rls.ts`), which checks for `app_bind_brand(text)` and the `orders_brand_iso` policy and **throws `BrandRlsNotInstalledError`** if either is missing. This file is not mentioned anywhere in CONTEXT.md.
**Why it happens:** It was added in an earlier phase (08.2) specifically to catch a mis-deployed environment that skipped the brand RLS migration — it has no knowledge that a later phase intentionally removes brand RLS entirely.
**How to avoid:** Delete `apps/api/src/shared/preflight/assert-brand-rls.ts` and its import + call site in `main.ts` (currently lines ~25 and ~62-64) as part of this phase's D-09 work, not as an afterthought.
**Warning signs:** API fails to boot immediately after the merge migration runs, with a `BrandRlsNotInstalledError` whose message says "Run `pnpm db:migrate` (migration 0058)" — a very specific, easy-to-misdiagnose error if this file isn't on the deletion checklist.

### Pitfall 3: `drizzle-kit generate` will silently produce a wrong migration

**What goes wrong:** Running `pnpm db:generate` after editing the schema files will not error — it will happily emit a migration SQL file, but that file will be computed against the stale `0018_snapshot.json` baseline (the last committed drizzle-kit snapshot), not against the actual current schema shape (61 hand-written migrations later). The output is very likely to be wrong (either re-declaring already-existing objects or missing intervening changes).
**Why it happens:** This has been true since roughly migration 0018 in this repo (confirmed: `packages/db/migrations/meta/` contains snapshot files only for `0000`–`0018`; migrations `0019`+ have none). It is documented in project memory ("drizzle-kit generate unusable past migration ~0018") but not in this phase's CONTEXT.md.
**How to avoid:** Hand-write the merge migration SQL directly (following the exact style of the 60+ hand-written migrations already in the directory — `DO $$ ... IF EXISTS ... END $$` guards before `DROP POLICY`/`DROP TABLE`, `--> statement-breakpoint` between statements), and manually append the matching entry to `packages/db/migrations/meta/_journal.json` (same `idx`/`version: "7"`/`tag`/`breakpoints: true` shape as every entry from `0019` onward). Do not run `pnpm db:generate` for this phase's schema changes.
**Warning signs:** `pnpm db:generate` output references tables/columns that already exist or omits ones that don't — a diff review before committing the generated file would catch this, but the safer path is to skip `drizzle-kit generate` for this migration entirely.

### Pitfall 4: RBAC `brand` permission resource has no clean successor

**What goes wrong:** `packages/domain/src/rbac/permissions.ts`'s `PERMISSIONS_STATEMENT` and `system-roles.ts`'s `SYSTEM_ROLES` both define a `brand: ['read', 'create', 'update', 'delete']` resource, granted to `owner` and `admin`. After the merge, "brand" as a sub-entity of tenant no longer exists, so `brand:create`/`brand:update`/`brand:delete` have no operation left to gate — and BA's `dynamicAccessControl` (enabled, `maximumRolesPerOrganization: 25`) lets owners build custom roles referencing this resource today, so a stale `brand` resource left in the statement is not just dead code, it is a permission an owner could still grant that maps to nothing.
**Why it happens:** CONTEXT.md's D-07–D-10 deletion list is schema/guard/service-focused and does not mention the RBAC permission catalogue.
**How to avoid:** Drop the `brand` resource from both `PERMISSIONS_STATEMENT` and `SYSTEM_ROLES` entirely (D-39 "delete, don't deprecate" applies squarely here). Recommendation, not a menu: do not fold `brand:*` into `tenant:*` — `tenant` today only has `['read', 'delete', 'transfer']` (no `update`), and "update my org's settings" already has a home in the existing `settings: ['update']` resource. `brand:create` (create a second organization) has no permission-gated home at all after the merge — organization creation happens through signup/onboarding, outside the in-app permission system, and the deferred GAP (no second-org creation surface in this phase) means there is nothing to gate yet.
**Warning signs:** `packages/domain`'s own RBAC regression test (`non-delegatable.spec.ts` — "adding a permission to admin requires a passing regression test") would need updating if `brand` permissions are silently kept; a stale `brand:create` grant surviving in a seeded custom role is the kind of thing `08.3`'s `dynamicAccessControl` regression suite should catch but might not if it isn't specifically re-run against the updated statement.

### Pitfall 5: `BrandSlugRateLimitGuard` is brand-named but not in D-10's deletion list

**What goes wrong:** `apps/api/src/contexts/identity/interfaces/http/guards/brand-slug-rate-limit.guard.ts` gates `GET /v1/me/brands/slug-availability` (used live by `onboarding/brand.tsx`'s debounced availability check) via `RATE_LIMIT_BRAND_SLUG_CHECK_PER_MIN`. It is registered as a per-route guard (not one of the 5 global `APP_GUARD`s in `identity-http.module.ts`), so it is easy to miss in a search scoped to the global guard chain. Its functional behavior (rate-limit a slug-check endpoint) is still needed after the merge — organization slugs still need an availability check during onboarding — but its name and the endpoint it guards both say "brand."
**Why it happens:** D-10's deletion list was built from the global-guard-chain description ("Six global guards run in order") and named services/repositories; a route-scoped guard used by exactly one endpoint sits outside that scan.
**How to avoid:** Rename (not delete) this guard and its endpoint to match whatever the merged slug-availability endpoint becomes (e.g. `GET /v1/me/organizations/slug-availability` or similar, depending on the planner's chosen route naming under D-30's slug-derivation discretion). Functionally identical logic, cosmetic rename only.
**Warning signs:** If left unrenamed, it still works (nothing breaks) — this is a "don't let it silently survive as dead-looking-but-live code with a confusing name" pitfall, not a correctness bug.

### Pitfall 6: `country` default-locale mapping can point at a locale one app doesn't ship

**What goes wrong:** The most linguistically "natural" default locale for Ukraine is `uk` (Ukrainian). `apps/website`'s `LOCALES` already includes `'uk'`, but `apps/admin`'s i18next resources only register `ru`/`en` (plus `es` this phase, per D-37 — `uk` is NOT added). If the country config's `UA` entry maps `defaultLocale: 'uk'` and the admin `langSwitcher` seeds a new Ukrainian owner's `user.locale` to `'uk'`, i18next will not throw (its `fallbackLng: 'ru'` catches missing keys gracefully — verified in `apps/admin/src/lib/i18n/index.ts`), but the langSwitcher UI itself may display "uk" as the active/selected language while every visible string is actually rendered in `ru` — a confusing, silently-degraded state that is exactly the class of bug D-38 warns about ("the failure mode already seen in phase 10 when a component read a key from the wrong namespace"), even though it technically never renders a raw i18n key.
**Why it happens:** Website and admin ship different locale sets today (`ru/uk/en` vs `ru/en`) — a country config that is deliberately app-agnostic (per D-32, "no infrastructure imports") cannot itself know which locales each consuming app supports.
**How to avoid — concrete recommendation:** Map `UA → 'ru'` (not `'uk'`) as the country's default locale for THIS phase. This keeps every one of the three supported countries' default locale inside the intersection of both apps' shipped catalogues (`{ru, en, es}` after D-37) and sidesteps the mismatch entirely without touching D-33's country list or D-37's "es only" scope. `GB → 'en'`, `ES → 'es'` are unambiguous. (Rejected alternative: `UA → 'uk'` relying on i18next's graceful fallback — technically safe from crashing, but produces the confusing mixed-language-indicator UX described above; not recommended given a same-cost alternative exists.)
**Warning signs:** A UI screenshot/manual QA pass where the langSwitcher shows "Українська" selected but all surrounding text is Russian would be the symptom; automated tests would not catch this since i18next never errors.

### Pitfall 7: `TenantSlug` lacks the `Value`/branded pair convention `BrandSlug` already follows

**What goes wrong:** `packages/domain/src/tenant-slug.ts` exports only a single branded `TenantSlug` (no unbranded `TenantSlugValue`), while `brand-slug.ts` correctly follows the project's `FooValue`/`Foo` convention (documented in ADR-0020 I-7: branded types emit `unknown` in `nestjs-zod`-generated OpenAPI schemas, which is a documented contract bug). If the merged entity's slug field is typed as bare `TenantSlug` at an HTTP-boundary Zod schema (e.g. the onboarding `POST` body), the generated OpenAPI spec will show `type: unknown` for that field instead of `type: string`.
**Why it happens:** `TenantSlug` predates the `Value`/branded pairing convention that was established later (visible in `money.ts`'s doc comments referencing it explicitly, and `brand-slug.ts` following it correctly).
**How to avoid:** When consolidating the two slug schemas into one (BrandSlug is deleted per the merge), use `BrandSlug`'s file as the template — add a `TenantSlugValue` unbranded export to `tenant-slug.ts` (or rename the whole thing to a neutral name if the planner chooses) and use `TenantSlugValue` at every HTTP-boundary DTO, keeping the branded `TenantSlug` for domain-internal use only.
**Warning signs:** `pnpm openapi:check` (the CI drift-check gate already in the repo) would catch a `type: unknown` regression if the branded type leaks into a DTO — but only if that check is run before merging, so flag this explicitly in the plan's DTO task rather than relying on CI to catch it after the fact.

### Pitfall 8: Legacy Stripe onboarding path is a confirmed dead stub, not a "maybe"

**What goes wrong:** `StartStripeOnboardingService` (tenant-level, wired live at `POST /v1/tenancy/stripe-onboarding` via `StripeOnboardingController`) calls `tenant.linkStripeAccount(accountId)`, whose implementation is `linkStripeAccount(_accountId: string, ...): void {}` — a literal no-op with an intentionally-unused parameter (`tenant.aggregate.ts:247`). Its `getStatus()` method is hardcoded to always return `{ onboardingStatus: 'not_started', chargesEnabled: false, payoutsEnabled: false, canAcceptPayments: false, requirementsDue: null }` regardless of what actually happened. This is D-39's "second, legacy Stripe onboarding path" — verified as fully dead, not merely duplicated.
**Why it happens:** Stripe Connect linkage was moved from the `Tenant` aggregate to the `Brand` aggregate in an earlier phase (confirmed in STATE.md: "Stripe connect linkage moved from Tenant to Brand aggregate (D-04/D-05/D-06)"), and the tenant-level controller/service/route were never removed afterward.
**How to avoid:** Delete `start-stripe-onboarding.service.ts`, `stripe-onboarding.controller.ts`, and the `POST /v1/tenancy/stripe-onboarding` route entirely. `StartBrandOnboardingService` (which has real, functional Stripe columns behind it: `stripeChargesEnabled`, `stripePayoutsEnabled`, `stripeOnboardingStatus`, `stripeRequirementsDue`, all live-updated by the `account.updated` webhook per PAY-05) is the one that survives, becoming the tenant-level (post-merge) Stripe onboarding path.
**Warning signs:** None at runtime — the dead endpoint returns plausible-looking-but-always-`not_started` responses forever, which is exactly why it needs to be found by code reading (as this research did) rather than by observing broken behavior.
