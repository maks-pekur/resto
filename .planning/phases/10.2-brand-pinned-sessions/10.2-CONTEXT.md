# Phase 10.2: Organization-per-restaurant and account onboarding - Context

**Gathered:** 2026-08-19
**Rewritten from scratch:** 2026-08-19 — the tenancy model changed mid-discussion and
patching the earlier decisions would have left a self-contradicting document. The
superseded model and the path to this one are preserved in `10.2-DISCUSSION-LOG.md`.
**Status:** Ready for planning

<domain>
## Phase Boundary

Collapse tenant and brand into a single entity — the Better Auth organization — so one
restaurant is one organization, an owner may belong to several, and the active
organization chosen at sign-in is the entire context of a session. Give a new owner a
working path from "create account" to "first restaurant".

</domain>

<decisions>
## Implementation Decisions

### The model — one restaurant is one organization

- **D-01:** **Tenant and brand merge into one entity**, which is the Better Auth
  organization. One restaurant = one organization = one legal entity with its own
  Stripe account, country, currency, theme and domains.
- **D-02:** **An owner may belong to several organizations.** Better Auth supports this
  natively — `session.active_organization_id` plus `setActiveOrganization`, already
  called in `signup.service.ts:229`. Nothing new is needed in the auth layer.
- **D-03:** **This reverses D-01/D-02 of the first version of this document**, where the
  tenant was a _group_ sharing staff, guests and loyalty across brands. The founder was
  shown that consequence explicitly and chose the merge anyway. **What is knowingly
  given up:** a cook working in two of the owner's restaurants is two separate
  memberships; guest base and loyalty do not cross restaurants; there is no
  group-level analytics; ownership transfer and co-ownership must be solved per
  organization.
- **D-04:** **Physically merge into one table** — brand fields move into `tenants`, and
  `brands` is dropped. The alternative (keep `brands` as a strict 1:1 satellite) was
  offered as cheaper and **not** taken. Real upside that justifies it: menu tables
  currently carry **both** `tenant_id` and `brand_id`, and the merge removes that
  redundant second dimension permanently along with its composite FKs.
- **D-05:** **The whole merge lands inside phase 10.2.** Splitting it into a preceding
  phase was offered and declined.
- **D-06:** **The tenant-naming problem dissolves.** There is no unnamed container any
  more — the organization's name _is_ the restaurant's name, asked once in onboarding.
  Everything the earlier version wrestled with (owner's name / first brand's name /
  asking for an abstraction) is moot.

### Merge scope — what is deleted

- **D-07:** Tables dropped: **`brands`**, **`brand_domains`**, **`member_brand_scope`**
  (the last is 08.4/08.5 machinery for restricting a member to a subset of brands —
  membership is per-organization now, so it has no meaning).
- **D-08:** Columns dropped: **`brand_id` in 9 places** — `menu.ts` ×6 (lines 35, 89,
  170, 207, 240, 288), `ordering.ts` ×1 (line 27), `customer-profiles.ts` ×1 (nullable,
  line 18), `outbox.ts` ×1 (nullable, line 39) — plus **`session.active_brand_id`**
  (`auth.ts:33`). `active_organization_id` is the only context pin that remains
  alongside `active_location_id`.
- **D-09:** RLS: the **`app_bind_brand` GUC and every brand policy** go away
  (lineage: migrations `0058_brand_rls.sql`, `0061_drop_app_bind_brand_is_system_param.sql`,
  `0065_location_guc.sql`; binding in `packages/db/src/client.ts`). Tenant and location
  bindings stay. **The ScopedTx + RLS double-enforcement rule is unchanged** — it now
  has one fewer dimension, not one fewer layer.
- **D-10:** Code deleted: `BrandScopeGuard`, `SetActiveBrandService` and its controller,
  `member-brand-scope-drizzle.reader.ts`, `initial-brand-drizzle.repository.ts`,
  `onInitialBrandPin` in `auth.config.ts`, `brand-switcher.tsx`, and
  `@RequireBrand`/`REQUIRE_BRAND_KEY` (8 api files, read by no guard even today).
- **D-11:** **Measured blast radius: 137 files** reference `brandId`/`brandSlug` — 70 in
  `apps/api/src`, 58 in `apps/admin/src`, 7 in `packages/db/src`, 2 elsewhere. This is
  larger than everything else in the phase combined; plan it as the spine, not a step.

### Migration strategy

- **D-12:** **Ship as a schema rewrite with a dev-database reset, not a data-preserving
  migration.** There is no production deployment and no paying customer (target is
  Q1 2027 per CLAUDE.md Constraints); the founder reset the database earlier the same
  day. Writing a careful data-migration for the merge would be effort spent preserving
  data that only exists in dev fixtures.
  > **Assumption stated for the record** — this is only valid while no real tenant data
  > exists. If that changes before the phase executes, this decision must be revisited
  > before any migration is written.
- **D-13:** Seeds and fixtures are rewritten to the merged model as part of the phase,
  not left for later — a seed that still creates tenant+brand pairs would silently keep
  the old shape alive.

### Session context and the sign-in picker

- **D-14:** **The active organization is the session's entire context.** Better Auth
  owns it; do not build a parallel pin. This is what the earlier version needed a brand
  pin for.
- **D-15:** **One session = one organization, for the life of that session.** Switching
  organizations **revokes the current session and issues a new one**; the old token is
  dead immediately after the switch.
- **D-16:** Switching does **not** re-prompt for the password — the owner picks, the
  server revokes and re-issues server-side.
  > Carried over from the first version, where the founder first chose "lightweight
  > re-pick, session stays" then restated it as "each login to a brand should be a new
  > session; on switch we revoke the current one and create a new one". The later,
  > stricter statement stands.
- **D-17:** **The picker appears at every sign-in** when the owner belongs to more than
  one organization — a fresh session has no organization bound yet, so there is nothing
  to remember. Exactly one → skipped, straight to the dashboard. Staff belong to exactly
  one organization and never see it.
- **D-18:** Mirror the existing staff pick-location interstitial rather than inventing a
  second pattern.
- **D-19:** The **location switcher survives** and becomes the only in-app context
  control. Locations live inside an organization and are unaffected by the merge.

### URLs and hosts

- **D-20:** **The `/{brandSlug}` path segment is removed** — admin paths become
  `/orders`, `/menu/items`. This supersedes decision D-03 of phase 02-03 (brand-in-URL).
- **D-21:** **The organization lives in the host:** admin is served per-organization at
  `<orgSlug>.admin.resto.app`.
  > **Why host and not path.** A path segment changes on every navigation, so
  > reconciling it against the session costs a check in all 18 route files. A host is
  > constant for the life of the SPA session — reconciliation is **one check at
  > bootstrap**. The session still decides; the host is display and routing. On mismatch
  > (bound to org A, opened `orgB.admin.resto.app`), redirect to the bound org's host.
- **D-22:** **The bare `<orgSlug>.resto.app` is reserved for the organization's future
  public website** (`apps/website`) and must not be taken by the admin. Guest menu keeps
  `<orgSlug>.menu.resto.app`. Three branches: `.menu.` guests, `.admin.` staff, bare for
  the public site.
- **D-23:** **One domain table.** `tenant_domains` and `brand_domains` merge with their
  rows' entities. Today `provision-tenant.service.ts:40` and
  `provision-brand.service.ts:48` both write `<slug>.menu.resto.app` into _separate_
  tables with _separate_ unique indexes — nothing prevented the same hostname existing
  twice. The merge removes that class of bug outright.
- **D-24:** Consequences of D-21 the planner must handle:
  - `AUTH_COOKIE_DOMAIN` already **requires a leading dot** (`env.schema.ts:291`,
    message: "to enable cross-subdomain cookies") — the design anticipated this. Scope
    the cookie to `.admin.resto.app`, **not** the apex, so the guest menu and public
    site never receive the operator session cookie.
  - `ADMIN_WEB_URL` is a **single URL** today and feeds Better Auth `trustedOrigins`
    (`identity-core.module.ts:234`). Per-org hosts need wildcard matching. A naive
    suffix check is an origin-spoofing hazard (`evil-resto.app` ends with `resto.app`) —
    match on a parsed hostname, anchored at the label boundary.
  - Wildcard DNS/TLS for `*.admin.resto.app`; local dev on `*.localhost`.

### Signup

- **D-25:** Signup asks **Name, Email, password, Country** — nothing else. It creates the
  user and their first organization.
- **D-26:** The form must call **`/v1/signup`**, not Better Auth directly. Today it calls
  Better Auth and produces a user with **zero memberships** — a stranded account that
  cannot create anything (verified live 2026-08-19).
- **D-27:** `signup.service.ts:137-152` currently makes one `displayName` field serve
  three roles at once — organization display name, organization slug source, and the
  person's name in Better Auth. Split them: the person's name goes to the user; the
  organization's name and slug come from onboarding.
- **D-28:** Remove the **dead currency field** (collected, never sent) and fix the
  mislabelled "Restaurant name" field.
- **D-29:** **Close direct Better Auth signup** (`POST /api/auth/sign-up/email`). Check
  invitation acceptance first — it may share the same path, and blindly disabling it
  would break invite redemption.

### Onboarding

- **D-30:** Onboarding is **creating the first organization** — the restaurant. It asks
  **name only**; the slug is derived. Legal details (`legal_name`, `legal_form`,
  `tax_id`) are **not** collected here — Stripe Connect Express collects them at payout
  setup, and asking twice is waste.
  > Matches the closest comparables: Square collects legal name / DBA / registration
  > number at payout activation, Toast confirms the restaurant name during onboarding —
  > neither asks at signup.
- **D-31:** Onboarding **resumes at the step where it was abandoned**, with the ability
  to go back and change the previous step. Derive the resume point from the data that
  exists, not from a separate progress flag.

### Countries, currency and language

- **D-32:** Supported countries are a **config in `packages/domain`**, alongside the
  other shared registries (`money.ts`, `rbac/`, `reserved-slugs.ts`) — no infrastructure
  imports, usable from api and both web apps. It is the seam every per-market setting
  lands on.
- **D-33:** First supported list: **UA, GB, ES**.
  > The founder said "ua and en and es". `en` is not a country; the English-speaking
  > market resolved to **GB** (not US) — Stripe Connect Express is long-stable there and
  > the currency is unambiguous, where US adds state-level tax complexity.
- **D-34:** **Country lives on the organization.** Collected at signup, applied to the
  first organization at onboarding. No `country` column exists anywhere today; this
  phase adds it to the merged table.
- **D-35:** **Currency derives from country and is never asked.** UA→UAH, GB→GBP,
  ES→EUR. The Stripe adapter (`stripe-provider.adapter.ts`) already accepts `country`
  and `default_currency` as optional inputs and nothing supplies them — this feeds a
  wire already in place.
- **D-36:** **Interface language is a user-level choice, surfaced by a `langSwitcher` in
  the admin UI**, seeded from the signup country's default locale. The founder's
  framing: the language serves as both interface and communication language, and the
  person — not the venue — is who reads it. A cook who speaks Ukrainian in a Spanish
  restaurant keeps their language.
- **D-37:** The **Spanish (`es`) catalogue is added in this phase** for both admin and
  website, covering **interface and communication** (emails/notifications). Admin ships
  `ru`/`en` today; website ships `ru`/`uk`/`en`.
- **D-38:** A country whose default locale has no catalogue must **fall back
  deliberately** rather than render raw keys — the failure mode already seen in phase 10
  when a component read a key from the wrong namespace.

### Code hygiene

- **D-39:** **Delete, do not deprecate** — founder's standing instruction for this
  phase: _"при реализации выпиливай все лишние чтобы не тянулся старый ненужный код"_.
  Beyond the merge deletions in D-07 to D-10:
  - **A second, legacy Stripe onboarding path.**
    `start-stripe-onboarding.service.ts:43` reads the _tenant's_ `displayName` and sends
    it to Stripe as `business_profile.name`, while `start-brand-onboarding.service.ts`
    does the brand-level equivalent. After the merge only one can be right — verify and
    remove the other.
  - `AutoSaveIndicator` / `useDebouncedAutosave` — abandoned auto-save model
  - `friendlyCatalogError` in `apps/admin/src/lib/menu/catalog-errors.ts` — dead,
    English-only
  - `apps/admin/app/` — leftover Next.js directory, untracked

### Naming — the surviving name is `tenant`

- **D-40:** **Everything named `brand` is renamed to `tenant`, not to `organization`.**
  Founder instruction, 2026-08-19: _"давай тогда все что именовано как brand переименуем
  в tenant"_. The merged entity keeps the table name `tenants`, `brands` merges into it,
  and the `brand` vocabulary leaves the codebase entirely. RESEARCH.md reached the same
  recommendation independently for a different reason: renaming `tenants` to
  `organizations` would touch ~99 additional `TenantId`-referencing files for zero
  functional gain, on top of the 137-file blast radius in D-11.

  Concretely, and not exhaustively:
  - `brands` → merged into `tenants`; `brand_domains` → merged into `tenant_domains` (D-23)
  - `brandId` / `brandSlug` → `tenantId` / `tenantSlug` wherever the reference survives
    the merge
  - `BrandSlug` (`packages/domain/src/brand-slug.ts`) → folded into `TenantSlug`, taking
    `brand-slug.ts`'s correct `Value`/branded pair shape with it — `tenant-slug.ts` is
    missing the unbranded `TenantSlugValue` today (RESEARCH.md Pitfall 7)
  - `BrandSlugRateLimitGuard` and `GET /v1/me/brands/slug-availability` → tenant-named
    equivalents; **renamed, not deleted** — the slug-availability check is still needed
    at onboarding (RESEARCH.md Pitfall 5)
  - `StartBrandOnboardingService`, `provision-brand.service.ts` → tenant-named, merged
    into the single surviving provisioning and Stripe-onboarding paths (D-39)
  - the RBAC `brand` permission resource → **dropped, not renamed** (RESEARCH.md Pitfall 4)
  - the admin host in D-21 reads `<tenantSlug>.admin.resto.app`
    > **The one boundary that stays as-is:** Better Auth's own API surface keeps its
    > `organization` vocabulary — `activeOrganizationId`, `setActiveOrganization`,
    > `organizationHooks`, `organization_role`. That is BA's namespace, not ours; renaming
    > it is neither possible nor desirable. The rule is: our code says `tenant`, BA says
    > `organization`, and the two are synonyms across a documented boundary that already
    > exists (`organization_role.organization_id` references `tenants.id`).
    >
    > **Narrowed by D-41 (2026-08-20).** The boundary is real but smaller than written
    > here: it covers BA's TypeScript and HTTP surface only, not the database. Table and
    > column names are ours to choose. See D-41.

- **D-41:** **`organization` is renamed to `tenant` too — in our code and in the
  database.** Founder instruction, 2026-08-20: _"давай organization тоже переименуем
  чтобы не было двухсмысленных — у нас организация и бренд и тенант это одно и то же,
  это одна сущность"_. D-40 removed one of the three names for this entity; D-41 removes
  the second, leaving exactly one.

  Three layers, and they are not equally free:
  - **Our own identifiers — renamed, no constraint.** ~104 files outside migration
    history carry an `organization` name that is ours: the Drizzle export
    `organizationRole`, `onActiveOrganizationSet`, `orgId` locals, port names, test
    names, and the `pickOrganization.*` i18n namespace plan 02 just added. All become
    tenant-named.
  - **Database names — renamed, and Better Auth supports it officially.** Verified
    against the pinned BA 1.4.22 (`plugins/organization/types.d.mts:232-267`): the
    organization plugin accepts a `schema` option with `modelName` and per-field
    mapping, including `session.fields.activeOrganizationId`. So `organization_role`
    → `tenant_role`, `organization_id` → `tenant_id`, `session.active_organization_id`
    → `session.active_tenant_id`, and the same for `member` and `invitation`. No fork,
    no patched dependency. There is no production data and the database is reset in
    this phase (D-12), so the migration cost is the DDL only.
  - **Better Auth's own API — NOT renamed, and confined.** `import { organization }
from 'better-auth/plugins'`, the `OrganizationOptions` type, `organizationHooks`,
    the `POST /api/auth/organization/set-active` route, and the logical field name
    `activeOrganizationId` that BA reads and writes are the public API of a third-party
    library. Renaming them means forking BA. Instead they are confined to
    `apps/api/src/contexts/identity/infrastructure/better-auth/` — the adapter that
    talks to BA — and everything outside that directory speaks `tenant`. This is the
    ports-and-adapters rule CLAUDE.md already states, applied to vocabulary.

  Where the work lands: the database half rides along in **plan 05**'s merge migration
  and BA config (it rewrites the schema anyway); the code half is **plan 21**, a single
  mechanical sweep at the end of the phase — plans 14–19 rewrite most of these files
  regardless, so renaming them twice would be waste. **Plan 20** proves it with a
  repo-wide grep whose one documented exception is the `better-auth/` directory plus
  migration history.

- **D-41 exception widened, 2026-08-22 (orchestrator, during plan 21's sweep).** D-41 confined Better
  Auth's `organization` vocabulary to `apps/api/src/contexts/identity/infrastructure/better-auth/`. That
  was written before anyone counted, and the real answer is **five** places — all of them legitimately BA's
  own API, none of them renameable:
  1. `apps/api/src/contexts/identity/infrastructure/better-auth/` — the adapter (as written).
  2. **`apps/admin/src/**`— BA's browser client SDK.**`authClient.organization.list()`,
`.setActive()`, `.acceptInvitation()`, `.inviteMember()`, `.listMembers()`, `.listInvitations()`.
     The admin is a client of Better Auth; there is no server adapter between it and the SDK.
  3. `tools/scripts/seed/lib/operator-http.ts` — calls BA's HTTP route `/api/auth/organization/set-active`
     directly, because a seed script has no application layer to go through.
  4. `packages/db/src/schema/auth.ts` — `export const organization = tenants`, the alias BA's Drizzle
     adapter resolves its model name against. Deleting it breaks BA at runtime.
  5. `apps/api/src/contexts/identity/identity-core.module.ts` — reads `data.organization.slug` out of a BA
     hook payload, whose shape BA defines.

  The rule is unchanged in spirit and now stated accurately: **our vocabulary is `tenant`; Better Auth's
  own API keeps its own words wherever that API is invoked.** Plan 20's completeness grep must exempt
  these five, not one, or it fails on correct code.

## Existing Code Insights

### Reusable Assets

- **The tenant already _is_ the Better Auth organization.** `organization_role
.organization_id` references `tenants.id`; there is no separate `organization` table.
