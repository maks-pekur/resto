# Phase 10.2 Learnings: brand-pinned-sessions

A 22-plan, 15-wave merge of two entities into one across ~330 files, four applications and the database.
The phase's own findings log (`10.2-FINDINGS.md`, 48 entries) is the raw record; this file is the part
worth carrying forward.

## Decisions

### Merge brand into tenant physically, in one phase

Tenant and brand became a single entity. The cheaper 1:1-satellite option was offered and declined, as was
splitting the merge into a preceding phase.

**Rationale:** The founder was shown the consequence — no shared staff, guest base, loyalty or group
analytics across an owner's restaurants — and chose the merge anyway. A real upside surfaced while
measuring: menu tables carried both `tenant_id` and `brand_id`, so the merge removed a redundant dimension
and its composite FKs permanently.
**Source:** 10.2-CONTEXT.md D-03, D-04, D-11

### One name for the entity — `tenant`, not `organization`

Everything named `brand` became `tenant` (D-40). Later the same treatment was extended to `organization`
(D-41), after the founder observed that organization, brand and tenant were three names for one thing.

**Rationale:** Renaming `tenants` to `organizations` instead would have touched ~99 additional
`TenantId`-referencing files for zero functional gain. Better Auth's own API keeps its `organization`
vocabulary — that is a third party's namespace, not ours.
**Source:** 10.2-CONTEXT.md D-40, D-41; 10.2-RESEARCH.md

### Ship as a schema rewrite with a dev reset, not a data migration

No production, no paying customer, database reset the same day.

**Rationale:** Writing a careful data migration for data that does not exist is waste. The assumption was
stated explicitly so it would be revisited rather than rediscovered.
**Source:** 10.2-CONTEXT.md D-12

### One session = one organization, enforced by revoke-and-reissue

Switching organizations revokes the current session and issues a new one without re-prompting for a
password. The old token is dead immediately.

**Rationale:** Stock Better Auth mutates the session in place and keeps the same token, which does not
deliver the guarantee. A custom endpoint was built. The founder first chose a lighter "re-pick, session
stays" and then restated it as the stricter form; the stricter one stands.
**Source:** 10.2-CONTEXT.md D-15, D-16; 10.2-12-SUMMARY.md

### A sanctioned commit-time opt-out for spine migrations

`.husky/pre-commit` gained `RESTO_SPINE_MIGRATION=1`, which skips only the affected-typecheck step;
`lint-staged` always runs.

**Rationale:** The phase plan and the commit hook contradicted each other — the plan deliberately runs red
from wave 3 to wave 13, the hook demands green per commit. The alternatives were worse: `--no-verify`
silently disables formatting and lint too, and squashing nine plans into one atomic commit produces ~200
files nobody can review.
**Source:** 10.2-FINDINGS.md F-01; .husky/pre-commit

### Payment-ready seeding by direct column stamp, not by driving Connect onboarding

`--payments-ready` sets the Stripe columns from a real test-mode connected account id supplied through the
environment, on one seeded organization only.

**Rationale:** Driving the real Connect onboarding needs a human clicking Stripe's hosted form, which is
not reliably scriptable. A seed whose setup requires manual clicking in someone else's UI is not a seed.
The accepted cost is that the Connect onboarding path stays unexercised.
**Source:** 10.2-18-SUMMARY.md

## Lessons

### Green is not running, and the gap held three separate blockers

`apps/api/src` reached zero typecheck errors and the process still would not start. Three unrelated things
sat between compiling and running: a `.sql` module import Node 24 cannot resolve, which had silently
disabled both `db:audit-fks` and role provisioning since June; a `db:reset` that drops schema grants and
prints only half the recovery sequence; and a `withoutTenant` allowlist entry pointing at a repository the
phase had deleted.

**Context:** None of the three was visible to any static gate. The plan that boots the API and hits
`/healthz` was added mid-phase specifically because a green build had stopped being convincing.
**Source:** 10.2-FINDINGS.md F-15, F-30, F-31; 10.2-22-SUMMARY.md

### A test whose fixture cannot occur in production is worse than no test

`POST /v1/me/set-active-location` failed on every request for several waves. Its unit tests passed because
they built the request themselves — `makeReq = () => ({ activeBrandId: null })` supplied exactly the value
production could no longer produce.

**Context:** The producing line (`req.activeBrandId = session.activeBrandId ?? null`) survived after the
column was dropped, so the field was permanently null and the handler always took its error branch. Found
by grepping the live tree, not by any gate.
**Source:** 10.2-FINDINGS.md F-27; 10.2-11-SUMMARY.md

### The test framework's defaults can make a security assertion vacuous

Under vitest, `NODE_ENV=test` disables Better Auth's origin check. A wildcard-origin test written the
obvious way passes without ever exercising the matcher — every origin is accepted, including the spoofs it
claims to reject.

**Context:** Nothing in the output distinguishes "the matcher rejected the spoof" from "the check never
ran". The fix was to construct a Better Auth instance with the check explicitly enabled, and to assert a
known-good input is accepted in the same suite.
**Source:** 10.2-FINDINGS.md F-32; 10.2-12-SUMMARY.md

### Only a browser on a production-shaped host finds a session-transport bug

The admin's session cookie was silently dropped once the app was served from a real subdomain. The server
sent a byte-correct `Set-Cookie` with correct CORS; the browser discarded it.

**Context:** It had worked because admin and API shared a hostname and differed only by port, and a port is
not part of a site for cookie purposes. curl cannot find this by construction — it does not enforce cookie
policy. Fourteen plans, a green build on both sides, a passing e2e suite and a live curl walkthrough all
missed it.
**Source:** 10.2-FINDINGS.md F-41; 10.2-17-SUMMARY.md

### A phase's decision record describes the codebase less accurately than the codebase does

CONTEXT.md's counts were wrong twice — nine RLS policies where seven plus two functions existed, ten
`brand_id` columns where the listed set was nine. D-41's exception named one directory; the real answer was
five. Executors that read migration history and grepped instead of trusting the citations found the
difference every time.

**Context:** Both decisions were drafted from reasoning rather than from a grep. The corrections came from
plans 05, 19 and 21 reading live artefacts.
**Source:** 10.2-FINDINGS.md F-17, F-46; 10.2-05-SUMMARY.md

### File greps prove half a rename

Four database objects hid from every source grep: a surviving `app_bind_brand(text, boolean)` overload
(migration 0061 added a one-argument version without dropping the two-argument one), a policy whose table
had been renamed but not the policy, and an `organization_role` primary key plus two policies that
`ALTER TABLE ... RENAME` does not touch. Separately, the admin was calling two API modules whose routes the
server does not serve, one of them fully dead code.

**Context:** A rename can be named in three places — source, schema, and the wire between them. The phase
discovered that list one failure at a time and ended with three independent proofs.
**Source:** 10.2-FINDINGS.md F-17, F-35, F-47; 10.2-20-SUMMARY.md

### Moving a column between tables is not only a compile problem

Migration 0079 correctly stopped `tenancy_erase_tenant` from naming dropped tables, and left four PII
columns un-erased because they had moved onto the surviving row. A GDPR erasure request would have
completed successfully and left `legal_name`, `legal_form`, `tax_id` and `stripe_account_id` populated.

**Context:** Plan 05 examined and rewrote that function. It answered "does it still run" and nobody asked
"does it still do what it was for".
**Source:** 10.2-FINDINGS.md F-36; 10.2-18-SUMMARY.md

### Authorization cannot be relayed to a subagent

A subagent refused an instruction that relayed the founder's approval, because the supporting commit was
unsigned, unpushed and authored by an identity trivially forgeable in a shared environment. It was right to
refuse.

**Context:** The relay also asked it to change a config file and leave the change uncommitted, which reads
as "modify configuration and leave no trace". Inverting the order — commit the approved change first, then
let a fresh agent verify it with `git log` — worked without friction.
**Source:** 10.2-FINDINGS.md F-02

## Patterns

### Prove a control is on before asserting it rejects

Any suite asserting that a security control rejects something must, in the same suite, assert a known-good
input is accepted. A suite where every case passes is indistinguishable from one where the control is
disabled.

**When to use:** Every security test. Adopted after F-32; `apps/api/test/unit/shared/admin-origin-wildcard.spec.ts`
is the reference implementation.
**Source:** 10.2-12-SUMMARY.md

### Negative assertions as removal guards

`tenant-isolation.spec.ts` asserts `to_regprocedure('current_brand_id()') IS NULL` — it proves the function
is gone rather than merely not using it.

**When to use:** After deleting a database object, function or endpoint that something might reasonably
recreate. Cheap, and it survives long after everyone forgets why the thing was removed.
**Source:** packages/db/test/integration/tenant-isolation.spec.ts; 10.2-20-SUMMARY.md

### Before/after set diff as the proof for a bypass change

Plan 11 deleted a decorator that granted a guard bypass to 18 controllers. The proof was an enumeration of
every bypassing route before the change and after, diffed both directions.

**When to use:** Any change to authorization surface where both "too little" and "too much" are silent
failures. Count occurrences, not just files — three controllers carried both markers and the file-level
diff hid a 39→36 change that turned out to be legitimate duplicate collapse.
**Source:** 10.2-11-SUMMARY.md; 10.2-FINDINGS.md F-38

### Route-level reconciliation between client and server

Every literal path the frontend constructs, checked against the routes the server registers, using the
generated OpenAPI artifact as the fixture. 63 registered, 40 constructed, 0 unmatched.

**When to use:** Whenever a phase changes an HTTP contract. There is no compiler, test or linter between a
wrong URL string and a user.
**Source:** 10.2-20-SUMMARY.md; 10.2-FINDINGS.md F-35

### Live catalog sweep alongside source greps

Query `pg_tables`, `information_schema.columns`, `pg_indexes`, `pg_constraint`, `pg_proc` (printed as
`oid::regprocedure` so overloads are visible), `pg_policies` and `pg_sequences` for the retired word — as
the schema owner, never as the restricted application role.

**When to use:** Any rename touching the database. `information_schema` filters by privilege, so a
restricted role returns zero for everything and every probe passes for the wrong reason. That false green
happened in this phase before the mistake was caught.
**Source:** 10.2-20-SUMMARY.md; 10.2-FINDINGS.md F-17

### Commit after every task in long agent runs

Three executor agents died mid-run to stream or API errors. The one that had committed after each task lost
nothing across 20 commits; an earlier one lost two half-edited files.

**When to use:** Any agent run expected to exceed ~20 minutes. The orchestrator's counterpart is to check a
dead agent's worktree for both commits and uncommitted changes, and to rescue via `git diff --cached HEAD`
before removing it.
**Source:** 10.2-FINDINGS.md F-25; 10.2-19-SUMMARY.md

## Surprises

### Agent worktrees fork from the default branch, not the current one

Claude Code's `isolation="worktree"` creates worktrees from `main`, which on this repo was 416 commits
behind the working branch. Every agent started ~70k lines out of date.

**Impact:** Nothing broke, because the GSD executor template carries an explicit `EXPECTED_BASE` assertion
and reset — but it is load-bearing in a way that is easy to miss, and it fired on all 22 dispatches.
`worktree.baseRef: "head"` exists in the settings schema and would remove the dependency.
**Source:** 10.2-FINDINGS.md F-04

### Every worktree agent was reinstalling 1.2 GB of dependencies

`node_modules` is gitignored, so a fresh worktree has none. Every agent ran `pnpm install` before it could
typecheck anything — a long operation producing almost no output, and a plausible contributor to two
consecutive stalls.

**Impact:** Fixed by `worktree.symlinkDirectories` covering all 14 workspace `node_modules` paths. Should be
configured once at repo setup; the cost of not doing it is paid by every agent, every time, and is invisible
until something dies during the install.
**Source:** 10.2-FINDINGS.md F-26

### The composite-FK audit had not run since June

`db:audit-fks` was broken by a `.sql` module import. When repaired it immediately found a real ADR-0020 I-2
violation — `member_location_scope_member_fk` missing `tenant_id`, originating in phase 08.4.

**Impact:** A tenancy invariant the project's own CLAUDE.md names as load-bearing went unverified for two
months, and was violated for that whole time. The violation was invisible for a second reason too: before
this phase `member` carried `organization_id`, so it was not in the set of tables an invariant check
recognises as tenant-scoped.
**Source:** 10.2-FINDINGS.md F-15, F-16

### Eight files in the phase belonged to no plan

`grep -l "<path>" *-PLAN.md` returned no owner for eight files the phase's own changes broke — a
four-file location cluster, a notification port, two location-scope infrastructure files, and the
`withoutTenant` allowlist. Each was found by an executor stumbling into it.

**Impact:** Each cost a mid-phase plan amendment. The union of every plan's `files_modified` is never
validated against the set of files the phase will break — and for a rename that set is computable, as the
reverse dependency closure of the renamed symbols.
**Source:** 10.2-FINDINGS.md F-20, F-22, F-24, F-31, F-39

### Three separate plans broke each other's contracts across a wave boundary

Plans 07 and 10 disagreed on a renamed field; plan 09 declared a local interface asserting a method plan 06
had not agreed to provide; plan 18's seed used a route plan 13 had just closed. In each case both plans were
individually correct and internally green.

**Impact:** The post-merge full-project typecheck caught the first. The second happened to guess the right
name. The third only surfaced when the seed was run. A phase changing a contract needs someone checking the
consumers who is not either of the two plans involved — and a runtime-free check does not suffice.
**Source:** 10.2-FINDINGS.md F-19, F-23, F-37
