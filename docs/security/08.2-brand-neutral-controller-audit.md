## BA-Managed Routes

Better Auth mounts its own HTTP handler at `/api/auth/*` (sign-in, session, password-reset,
email-verification, TOTP, invitation-accept, org management). These are **not NestJS controllers**;
they are handled by the BA `fastify-auth` integration before the NestJS guard chain runs.
`BrandScopeGuard` never fires for these routes. No `@BrandNeutral` annotation is possible or
needed.

## Brand-Scoped Controllers (D-14 Payout Audit)

`RefundsController`, `BrandOnboardingController`, and `StripeOnboardingController` are explicitly
brand-scoped and carry NO `@BrandNeutral`. They run under the default-on `BrandScopeGuard` with
full D-10 pin reconciliation. Cross-brand payout/refund access is denied by the guard.
Plan 06 adds the positive e2e proof.

## BrandScopeGuard Decision Tree (D-08 / D-10 / D-11)

`BrandScopeGuard` is default-on: it runs on EVERY route unless `@BrandNeutral` opts out. It runs
after `AuthGuard` + `PermissionsGuard`, so it can rely on `req.principal`. The decision order is
load-bearing — do not reorder without re-auditing:

1. `@BrandNeutral` present → pass (opt-out).
2. ALS has no brand → 403 `brand.context_required`.
3. Principal is not an operator → 403 `brand.operator_required`.
4. Operator has no `tenantId` → 403 `brand.tenant_required`.
5. Operator `baseRole === 'owner'` → pass. Owner bypass precedes the pin + scope checks so a
   freshly-onboarded owner with zero scope rows is never locked out (owner free-switch).
6. D-10 pin reconciliation (non-owner only):
   - `req.activeBrandId === null` (no pin) → **404** (existence-hiding; closes the null-pin bypass).
   - `req.activeBrandId !== ALS brand` → **404** (existence-hiding cross-brand mismatch).
     The 404 (not 403) is intentional: a 403 would confirm the brand exists. A future change that
     "corrects" this to 403 re-opens a brand-existence oracle — leave it as 404.
7. `member_brand_scope` lookup for `(userId, tenantId)`:
   - `null` (no scope rows) → 403 `brand.access_denied` (default-deny, D-08 — this is the flip).
   - `brandId` IN scope → pass.
   - `brandId` NOT IN scope → 403 `brand.access_denied`.

## MemberBrandScopeReader Contract

`findBrandScopeForMember` returns the explicit brand-id allow-list, or `null` when the member has
no scope rows. `null` is a **fact, not a decision**: the role-aware allow/deny lives in the guard
(owners treat `null` as all-brands; non-owners treat `null` as no-access per D-08). A non-null
array is always non-empty. Implementer invariant: implementations MUST run inside the request's
tenant context so RLS scopes the read to the active tenant — a read outside tenant context leaks
cross-tenant scope rows.
