# RES-237 — Canonical I-1 cross-tenant isolation regression net

**Status:** design approved 2026-05-24 — ready for plan.
**Ticket:** [RES-237](https://linear.app/restico/issue/RES-237/add-e2e-cross-tenant-isolation-test-per-bounded-context) — T1 freeze gate-blocker, High priority.
**Authority:** ADR-0020 I-1 (mandatory tenant filter); ADR-0021 Tier 1 freeze criteria.
**Branch:** `res-237` (off main at `de59481`).

## 1. Purpose

Ship one canonical e2e regression net for ADR-0020 I-1 (mandatory tenant filter on every tenant-scoped repo read). One spec file, four context-scoped suites, one representative read probe per context. If any repository under test loses its tenant filter and starts returning cross-tenant rows, this file fails fast.

This is distinct from the existing per-feature cross-tenant probes (in `catalog.e2e.spec.ts`, `me-brands.e2e.spec.ts`, `tenants-controller.e2e.spec.ts`, `outbox-rls.e2e.spec.ts`) which test feature behavior. The new spec tests the invariant directly and serves as the single discoverable file for "where do we prove I-1 holds at the HTTP boundary?".

## 2. Scope

### 2.1 In scope

A new file `apps/api/test/e2e/cross-tenant-isolation.e2e.spec.ts` with the following suites:

1. **tenancy** — `GET /tenants/me` read probe.
2. **catalog** — `GET /menu/<slug>` public-menu read probe under host A vs host B.
3. **identity** — `GET /me/brands` read probe.
4. **audit** — repository-level read probe (no HTTP surface): `withTenant(A)` reads `audit_log` and sees only A's rows; the `tenancy_erase_tenant` platform-level row (`tenant_id IS NULL`) is invisible under any `withTenant` binding.

Each probe seeds **comparable data with identical slugs / names** across tenants A and B so the only way to distinguish is `tenant_id`. If a repository loses its tenant filter, it returns B's row (or both) — the assertion `expect(response.slug).toBe('flagship')` would pass for the wrong reason, but `expect(response.tenantId).toBe(tenantA.id)` would not. Both assertions are made per probe.

### 2.2 Out of scope (filed as followups)

- **Tenancy write probe.** No user-facing tenancy-scoped writes today. The `internal-tenants.controller` endpoints (`provision`, `executeErasure`) are `INTERNAL_API_TOKEN`-gated system-context paths, not authenticated-as-tenant-A flows. AuthGuard cross-tenant principal isolation is already covered by `tenants-controller.e2e.spec.ts:174` (RES-126).
- **Catalog write probe.** Same shape: `internal-catalog.controller` writes are internal-token-gated, not tenant-authenticated. User-facing operator catalog writes ship in a later phase (post-T1, when the operator UI ADR lands).
- **Identity write probe.** `signup` writes the operator under the tenant resolved from the host/header at signup time — there is no user-supplied `tenantId` for cross-tenant attempt to exist. `me/*` is read-only today.
- **Audit write probe.** `audit_log` is append-only with no user-facing write path. The `tenancy_erase_tenant` insert path is already regression-tested in `tenancy-erase-guard.spec.ts` (RES-204, shipped today).

Each missing write probe is filed as a follow-up to add to the per-context suite when the corresponding write endpoint lands. The canonical regression net's surface grows monotonically with the API.

### 2.3 Why this PR does not modify the existing per-feature specs

The existing cross-tenant tests in `catalog.e2e.spec.ts`, `me-brands.e2e.spec.ts`, `tenants-controller.e2e.spec.ts`, and `outbox-rls.e2e.spec.ts` test feature behavior — they happen to include cross-tenant assertions inside larger feature suites. The new file is the canonical I-1 regression net, scoped narrowly to the invariant. Both layers stay green for two different reasons; if one regresses, the other catches it. Deleting or modifying existing tests is out of scope for RES-237.

## 3. Architecture

### 3.1 Spec structure

```ts
// apps/api/test/e2e/cross-tenant-isolation.e2e.spec.ts

suite('RES-237: ADR-0020 I-1 cross-tenant isolation regression net', () => {
  let stack: RealStack;
  let fixture: I1Fixture;

  beforeAll(async () => {
    stack = await startRealStack({ natsEnabledInApp: false });
    fixture = await seedI1Fixture(stack);
  }, 120_000);

  afterAll(async () => stack.stop());

  describe('tenancy', () => {
    /* GET /tenants/me probe */
  });
  describe('catalog', () => {
    /* GET /menu/<slug> probe */
  });
  describe('identity', () => {
    /* GET /me/brands probe */
  });
  describe('audit', () => {
    /* withTenant audit_log probe */
  });
});
```

### 3.2 Fixture shape

```ts
interface I1Fixture {
  tenantA: { id: string; slug: 'i1-flagship' };
  tenantB: { id: string; slug: 'i1-flagship-b' };
  // Same display slug across both tenants so RLS, not slug-uniqueness, is the
  // separator. Brand uses 'flagship' in both tenants; menu category 'pizza';
  // menu item 'margherita'.
  brandA: string;
  brandB: string;
  categoryA: string;
  categoryB: string;
  itemA: string;
  itemB: string;
  operatorACookie: string; // signed-in as operator of tenantA
}
```

Note: `tenant.slug` IS unique across tenants (platform-wide); we can't use the same slug. We DO use the same brand-slug / category-slug / item-slug across tenants — those uniqueness constraints are scoped to `(tenant_id, slug)` so duplicates are legal and intentional here.

### 3.3 Per-probe assertion pattern

```ts
const res = await app.inject({
  method: 'GET',
  url: '/some/endpoint',
  cookies: fixture.operatorACookie,
});
expect(res.statusCode).toBe(200);
const body = JSON.parse(res.body);
// Same-slug-different-tenant: assert tenant id, not display name.
expect(body.tenantId).toBe(fixture.tenantA.id);
expect(body.tenantId).not.toBe(fixture.tenantB.id);
```

If the repo loses its tenant filter:

- Best case: it returns both A and B → `body.tenantId` is undefined / array → assertion fails.
- Worst case: it returns B → `body.tenantId === tenantB.id` → assertion fails.

Either way, the test fails fast.

### 3.4 Audit probe (no HTTP)

```ts
const db = stack.app.get<TenantAwareDb>(DB_TOKEN);

const rowsUnderA = await runInTenantContext(
  { tenantId: fixture.tenantA.id },
  () => db.withTenant(async (tx) => tx.select().from(schema.auditLog)),
);
const allRows = await db.withoutTenant(
  'verify cross-tenant audit visibility',
  async (tx) => tx.select().from(schema.auditLog),
);

// Tenant A's view never contains tenant B's rows.
expect(
  rowsUnderA.every(
    (r) => r.tenantId === fixture.tenantA.id || r.tenantId === null,
  ),
).toBe(true);
// The platform-level (tenant_id IS NULL) rows are NOT in tenant A's view either
// — RLS WHERE `tenant_id = current_setting('app.current_tenant')::uuid`
// rejects NULL because NULL = uuid evaluates to NULL.
expect(rowsUnderA.every((r) => r.tenantId !== null)).toBe(true);
// withoutTenant sees the union (A + B + NULLs).
expect(allRows.length).toBeGreaterThan(rowsUnderA.length);
```

`tenancy_erase_tenant` running during the test (or test setup) would create a `tenant_id IS NULL` audit row — the second assertion guards that it remains invisible to any tenant-bound principal.

## 5. Test design

### 5.1 tenancy probe

```ts
describe('tenancy', () => {
  it('GET /tenants/me under operator-A cookie returns tenant A, not B', async () => {
    const res = await stack.app.inject({
      method: 'GET',
      url: '/tenants/me',
      cookies: { 'better-auth.session_token': fixture.operatorACookie },
    });
    expect(res.statusCode).toBe(200);
    const body = JSON.parse(res.body);
    expect(body.id).toBe(fixture.tenantA.id);
    expect(body.id).not.toBe(fixture.tenantB.id);
  });
});
```

### 5.2 catalog probe

```ts
describe('catalog', () => {
  it('GET /menu under host A returns A items only, not B items with the same slug', async () => {
    const res = await stack.app.inject({
      method: 'GET',
      url: '/menu',
      headers: { 'x-tenant-slug': fixture.tenantA.slug },
    });
    expect(res.statusCode).toBe(200);
    const body = JSON.parse(res.body);
    expect(body.items.length).toBeGreaterThan(0);
    expect(
      body.items.every(
        (it: { tenantId: string }) => it.tenantId === fixture.tenantA.id,
      ),
    ).toBe(true);
  });
});
```

Note: `body.items[*].tenantId` may not be in the response DTO today. If not, the probe asserts on item count and an item-id allowlist (`expect(body.items.map(i => i.id).sort()).toEqual([fixture.itemA].sort())`). Plan-phase will verify the actual DTO shape.

### 5.3 identity probe

```ts
describe('identity', () => {
  it('GET /me/brands under operator-A cookie returns only A brands, not B brands with same slug', async () => {
    const res = await stack.app.inject({
      method: 'GET',
      url: '/me/brands',
      cookies: { 'better-auth.session_token': fixture.operatorACookie },
    });
    expect(res.statusCode).toBe(200);
    const body = JSON.parse(res.body);
    const ids = body.brands.map((b: { id: string }) => b.id);
    expect(ids).toContain(fixture.brandA);
    expect(ids).not.toContain(fixture.brandB);
  });
});
```

## 9. Risks and mitigations

| Risk                                                             | Mitigation                                                                                                                          |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Duplicate coverage with existing per-feature cross-tenant probes | Intentional — see §2.3. Existing specs test feature behavior; new spec tests the invariant.                                         |
| Audit probe needs direct DB access via DI container              | Use `stack.app.get(DB_TOKEN)` per existing patterns (e.g. `outbox-rls.e2e.spec.ts`).                                                |
| `body.items[*].tenantId` may not exist in catalog DTO            | §5.2 has the fallback assertion shape (item-id allowlist).                                                                          |
| `singleFork: true` + 4-suite spec adds ~10s to e2e wall-clock    | Acceptable per existing e2e budget; single `startRealStack` + shared `beforeAll` keeps cold-start cost amortized.                   |
| Test isolation between the 4 `describe` blocks                   | One `beforeAll` seeds the fixture; tests are read-only against the seeded state, so no cleanup between `describe` blocks is needed. |

## 10. Acceptance criteria

- New file `apps/api/test/e2e/cross-tenant-isolation.e2e.spec.ts` exists.
- 4 `describe` blocks (tenancy, catalog, identity, audit). 1 `it` per block (one read probe each).
- All 4 cases pass against a fresh testcontainer Postgres + migrated schema.
- Each case is "same-slug-different-tenant" structured so a lost tenant filter would fail the assertion immediately.
- Full e2e suite green; typecheck + lint clean.
- Out-of-scope items (write probes per context) explicitly documented in §2.2 as followups, NOT half-implemented.
