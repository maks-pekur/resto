# RES-206 — Revoke `resto_app` from BA credential tables (Option B)

**Status:** design approved 2026-05-24 — combined design + plan (last T1 ticket).
**Ticket:** [RES-206](https://linear.app/restico/issue/RES-206) — Urgent T1 gate-blocker.
**Authority:** ADR-0013 (BA integration); 2026-05-14 code review CR-07.
**Branch:** `res-206` (off main at `42c07ee`).

## 1. Scope (Option B — pragmatic minimum)

Close the immediate threat ("any `SELECT * FROM account` from `resto_app` code path leaks all password hashes / OAuth tokens / 2FA secrets across platform") by REVOKING `resto_app` from 4 sensitive BA tables:

- `account` (BA password hashes, OAuth access/refresh/id tokens)
- `two_factor` (TOTP secrets + backup codes)
- `verification` (verification codes)
- `session` (live session bearer tokens)

Keep `user` (no password column — only id/name/email/etc.) and `member` accessible to `resto_app` because legitimate read paths exist:

- `apps/api/src/contexts/identity/infrastructure/member-brand-scope-drizzle.reader.ts:19-23` joins `member` for brand-scope checks.
- Future application code may read `user.name` / `user.email` for display.

**Out of scope (filed as T2 followup):** per-user RLS via `app.current_user` GUC + extending `TenantContext` + plumbing into BA session lookups. That is the full ticket scope; defer because it requires BA-internal changes and adds GUC pipeline complexity without closing additional threat after the revoke.

## 2. Deliverables

1. **Migration** `packages/db/migrations/0027_revoke_resto_app_ba_credential_tables.sql`:

   ```sql
   REVOKE SELECT, INSERT, UPDATE, DELETE ON account FROM resto_app;
   REVOKE SELECT, INSERT, UPDATE, DELETE ON two_factor FROM resto_app;
   REVOKE SELECT, INSERT, UPDATE, DELETE ON verification FROM resto_app;
   REVOKE SELECT, INSERT, UPDATE, DELETE ON session FROM resto_app;
   ```

   - journal entry `0027` (`when: 1779840300000`).

2. **`packages/db/sql/roles.sql`** — mirror the revokes after the broad GRANT block so fresh installs (testcontainer / new prod) match production state. Append:

   ```sql
   -- RES-206: BA credential tables are resto_auth-only (ADR-0013).
   -- Revoke resto_app to prevent SELECT * leak of password hashes,
   -- OAuth tokens, 2FA secrets, session tokens.
   REVOKE SELECT, INSERT, UPDATE, DELETE ON account FROM resto_app;
   REVOKE SELECT, INSERT, UPDATE, DELETE ON two_factor FROM resto_app;
   REVOKE SELECT, INSERT, UPDATE, DELETE ON verification FROM resto_app;
   REVOKE SELECT, INSERT, UPDATE, DELETE ON session FROM resto_app;
   ```

   The comment block here is policy-compliant: it's a security-critical WHY explaining the threat model — exactly the "non-obvious constraint" case the no-comments policy allows.

3. **`packages/db/test/integration/auth-role-grants.spec.ts`** — extend with new `describe('RES-206: resto_app cannot access BA credential tables', ...)` block. Boot a fresh testcontainer, provision both roles, attempt `SELECT * FROM <table>` as resto_app for each of the 4 tables, expect SQLSTATE `42501` (insufficient_privilege). Use the existing `expectPermissionDenied` helper (line 20-27 of the spec).

4. **`packages/db/README.md`** — add to the "Two-role connection model" section (~line 50) a note: "After RES-206, resto_app's grant excludes 4 BA credential tables (`account`, `two_factor`, `verification`, `session`). Those are reachable only via `resto_auth` per ADR-0013."
