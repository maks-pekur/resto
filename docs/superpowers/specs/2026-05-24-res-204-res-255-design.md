# RES-204 + RES-255 — Erasure lockdown + I-2 audit script

**Status:** design approved 2026-05-24 — ready for plan.
**Tickets:**

- [RES-204](https://linear.app/restico/issue/RES-204) — Urgent gate-blocker. `tenancy_erase_tenant` is currently a privilege-escalation primitive: any code path that enters `withoutTenant` can wipe any tenant.
- [RES-255](https://linear.app/restico/issue/RES-255) — High gate-blocker. `pnpm db:audit-fks` script promised by `packages/db/CLAUDE.md` does not exist yet; without it, the "all tenant-scoped tables pass the I-2 gate" Tier 1 freeze criterion is unverifiable.

**Builds on:** RES-205 (resto_auth grant restrictions, shipped), RES-236 Phase 3a+3b (composite FK helpers + applied to all current tables, shipped today at `a8df132`).

**Authority:** ADR-0020 I-2 (composite tenant FK); CTO review 2026-05-24 finding H5 (RES-255). RES-204 reference: 2026-05-14 full-project deep code review, finding `[05-pkg-db CR-05]`.

**Branch:** `res-204-255` (off main at `a8df132`).

## 1. Purpose

Two protective measures for ADR-0020 invariants, bundled into one PR because both close T1 gate-blockers and both live in `packages/db`:

1. **RES-204 — caller-specific erasure GUC.** Replace the current `app.is_system='true'` gate on `tenancy_erase_tenant` (which every `withoutTenant` call satisfies) with a `app.allow_erasure='<expected-tenant-uuid>'` gate that only the offboarding code path sets. Add an audit-log row for the erasure event itself.
2. **RES-255 — I-2 audit script.** Ship `pnpm db:audit-fks` that surfaces every tenant-scoped child whose parent FK is not composite. After today's RES-236 Phase 3b merge the schema is clean — the script can be wired hard-fail in CI from day one.

## 2. Scope

### 2.1 In scope (RES-204)

- New SECURITY DEFINER helper `app_allow_erasure(p_tenant uuid)` that sets `app.allow_erasure` to the tenant uuid via `set_config(..., true)` (transaction-local). REVOKE PUBLIC + GRANT EXECUTE to `resto_app`.
- New signature `tenancy_erase_tenant(p_tenant_id uuid, p_audit_salt text, p_actor_subject text)`:
  - Gate changes from `app.is_system='true'` → `current_setting('app.allow_erasure', true) = p_tenant_id::text`. Mismatch RAISEs.
  - First action after the gate: `INSERT INTO audit_log (tenant_id, actor_kind, actor_subject, action, target_type, target_id) VALUES (NULL, 'system', p_actor_subject, 'tenant_erased', 'tenant', p_tenant_id::text)`. `tenant_id=NULL` keeps the row out of the redaction `WHERE tenant_id = p_tenant_id` later in the same function.
  - Rest of body unchanged from the current 0019 implementation (delete cascade + audit redaction).
- DROP the old 2-arg signature so stale callers fail at compile/SQL time.
- Repository signature change in `apps/api/src/contexts/tenancy/infrastructure/tenant-drizzle.repository.ts:179`: `eraseTenant(id, auditSalt, actorSubject)`. Inside `withoutTenant`: `SELECT app_allow_erasure(${id})` then `SELECT tenancy_erase_tenant(${id}, ${auditSalt}, ${actorSubject})` — same transaction.
- Domain port `TenantRepository.eraseTenant` (`domain/ports.ts:36`) and `OffboardTenantService.executeErasure` (`application/offboard-tenant.service.ts:45`) plumb the new `actorSubject` parameter. For MVP the service passes a static `'system:tenant-offboarding'` — there is no richer operator identity available at this call site today (the internal endpoint is gated by `INTERNAL_API_TOKEN`, no per-operator binding yet).
- New integration spec `packages/db/test/integration/tenancy-erase-guard.spec.ts`:
  - **Happy path:** `withoutTenant` + `app_allow_erasure(X)` + `tenancy_erase_tenant(X, salt, actor)` succeeds; `audit_log` shows a `tenant_id IS NULL, action='tenant_erased', target_id=X` row.
  - **Sad path 1:** call `tenancy_erase_tenant` without prior `app_allow_erasure` → RAISE.
  - **Sad path 2:** `app_allow_erasure(A)` then `tenancy_erase_tenant(B, ...)` → RAISE (mismatch).
  - **Sad path 3:** plain `withoutTenant` (sets only `app.is_system='true'`) → erase still RAISEs. This is the regression net for the original CR-05 finding.

## 3. Architecture

### 3.1 RES-204 control flow

```
HTTP (internal endpoint, INTERNAL_API_TOKEN-gated)
  → InternalTenantsController
    → OffboardTenantService.executeErasure({ tenantId })
      → repo.eraseTenant(id, auditSalt, 'system:tenant-offboarding')
        → db.withoutTenant('tenancy.eraseTenant', async tx => {
            tx.execute(`SELECT app_allow_erasure(${id})`)   // sets GUC, TX-local
            tx.execute(`SELECT tenancy_erase_tenant(${id}, ${salt}, ${actor})`)
              ↳ gate: app.allow_erasure == p_tenant_id::text ? OK : RAISE
              ↳ INSERT audit_log (..., action='tenant_erased', ..., target_id=p_tenant_id)
              ↳ DELETE cascade across tenant-scoped tables
              ↳ UPDATE audit_log redaction WHERE tenant_id = p_tenant_id
              ↳ DELETE orphan users
            tx.update(schema.tenants) { ... }    // mark erased on the tenant row itself
            for event in tenant.pullEvents(): appendToOutbox(tx, ...)
          })
```

`app.allow_erasure` is set via `set_config(..., true)` which is transaction-local; it does not leak out of the `withoutTenant` block. Any subsequent code in another transaction does not see it.

### 3.2 RES-255 control flow

```
Local dev:   pnpm --filter @resto/db db:audit-fks
              → connects via DATABASE_URL
              → runAudit(db) → prints violations → exit 0 or 1

CI:          inside `Affected test`
              → audit-fks.spec.ts on testcontainer
              → happy path: 0 violations
              → sad path: insert fixture-violating table, expect 1 violation, cleanup
```

### 3.3 Audit detection rule (RES-255)

A "violation" is: a table `t` with column `t.tenant_id NOT NULL` AND a column `t.<x>_id` that has a foreign key, where the FK is single-column (referencing only `parent.id`) rather than composite (referencing `parent(id, tenant_id)`).

Detection query shape (subject to refinement during implementation):

```sql
SELECT
  c.table_name        AS child_table,
  kcu.column_name     AS child_col,
  ccu.table_name      AS parent_table,
  tc.constraint_name  AS fk_name
FROM information_schema.table_constraints tc
JOIN information_schema.key_column_usage kcu
  ON kcu.constraint_name = tc.constraint_name AND kcu.table_schema = tc.table_schema
JOIN information_schema.constraint_column_usage ccu
  ON ccu.constraint_name = tc.constraint_name AND ccu.table_schema = tc.table_schema
JOIN information_schema.columns c
  ON c.table_schema = tc.table_schema AND c.table_name = tc.table_name AND c.column_name = 'tenant_id'
WHERE tc.constraint_type = 'FOREIGN KEY'
  AND tc.table_schema = 'public'
  AND c.is_nullable = 'NO'
  AND tc.constraint_name NOT IN (
    -- exclude the <table>_tenant_fk constraints themselves (those point at tenants(id))
    SELECT constraint_name FROM information_schema.constraint_column_usage WHERE table_name = 'tenants'
  )
GROUP BY tc.constraint_name, c.table_name, kcu.column_name, ccu.table_name
HAVING NOT (
  -- composite FK = the same constraint also has `tenant_id` as one of its columns
  EXISTS (
    SELECT 1 FROM information_schema.key_column_usage kcu2
    WHERE kcu2.constraint_name = tc.constraint_name AND kcu2.column_name = 'tenant_id'
  )
);
```

Implementation may prefer `pg_constraint` over `information_schema` for cleaner column-array introspection — that's a planning-time choice. The rule itself is fixed.

## 4. Migration: `0026_tenancy_erase_caller_specific_guc.sql`

Hand-authored (continues the 0024/0025 pattern). Approximate structure:

```sql
-- RES-204: caller-specific GUC for tenancy_erase_tenant.
-- The previous gate (app.is_system='true') was set by every withoutTenant
-- caller, making erasure available to any system-context code path. This
-- migration replaces the gate with app.allow_erasure=<expected-tenant-uuid>
-- and adds an audit_log row keyed to the actor.

CREATE OR REPLACE FUNCTION app_allow_erasure(p_tenant uuid)
RETURNS void
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = pg_catalog, public
AS $func$
BEGIN
  PERFORM set_config('app.allow_erasure', p_tenant::text, true);
END
$func$;
--> statement-breakpoint

REVOKE EXECUTE ON FUNCTION app_allow_erasure(uuid) FROM PUBLIC;
--> statement-breakpoint
DO $grant$
BEGIN
  IF EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'resto_app') THEN
    EXECUTE 'GRANT EXECUTE ON FUNCTION app_allow_erasure(uuid) TO resto_app';
  END IF;
END
$grant$;
--> statement-breakpoint

DROP FUNCTION IF EXISTS tenancy_erase_tenant(uuid, text);
--> statement-breakpoint

CREATE OR REPLACE FUNCTION tenancy_erase_tenant(
  p_tenant_id uuid,
  p_audit_salt text,
  p_actor_subject text
) RETURNS void
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public, pg_temp
AS $func$
DECLARE
  orphan_users text[];
BEGIN
  IF current_setting('app.allow_erasure', true) IS DISTINCT FROM p_tenant_id::text THEN
    RAISE EXCEPTION 'tenancy_erase_tenant requires app.allow_erasure to match the target tenant uuid';
  END IF;

  IF p_audit_salt IS NULL OR length(p_audit_salt) < 32 THEN
    RAISE EXCEPTION 'tenancy_erase_tenant requires p_audit_salt of >= 32 chars';
  END IF;

  IF p_actor_subject IS NULL OR length(p_actor_subject) = 0 THEN
    RAISE EXCEPTION 'tenancy_erase_tenant requires non-empty p_actor_subject';
  END IF;

  -- Platform-level audit row (tenant_id IS NULL) so it survives the
  -- redaction WHERE tenant_id = p_tenant_id loop below.
  INSERT INTO audit_log (
    tenant_id, actor_kind, actor_subject, action, target_type, target_id
  ) VALUES (
    NULL, 'system', p_actor_subject, 'tenant_erased', 'tenant', p_tenant_id::text
  );

  SELECT array_agg(user_id) INTO orphan_users
  FROM member
  WHERE organization_id = p_tenant_id;

  -- ... (delete cascade — verbatim from 0019: outbox, inbox, menu_items,
  --      menu_modifiers, menu_categories, customer_profiles, invitation,
  --      organization_role, member, tenant_domains, member_brand_scope,
  --      brand_domains, brands)

  -- ... (audit redaction — verbatim from 0019)

  -- ... (orphan user cleanup — verbatim from 0019)
END;
$func$;
--> statement-breakpoint

REVOKE EXECUTE ON FUNCTION tenancy_erase_tenant(uuid, text, text) FROM PUBLIC;
--> statement-breakpoint
DO $grant$
BEGIN
  IF EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'resto_app') THEN
    EXECUTE 'GRANT EXECUTE ON FUNCTION tenancy_erase_tenant(uuid, text, text) TO resto_app';
  END IF;
END
$grant$;
```

### 6.2 `packages/db/test/integration/audit-fks.spec.ts`

```ts
import { afterAll, beforeAll, describe, expect, it } from 'vitest';
import { sql } from 'drizzle-orm';
import {
  isDockerAvailable,
  startPostgres,
  stopPostgres,
  type TestPg,
} from '../setup';
import { runAudit } from '../../src/cli/audit-fks';

const dockerOk = isDockerAvailable();
const suite = dockerOk ? describe : describe.skip;

suite(
  'RES-255: db:audit-fks detects non-composite parent FKs on tenant-scoped children',
  () => {
    let pg: TestPg;
    beforeAll(async () => {
      pg = await startPostgres();
    }, 90_000);
    afterAll(async () => stopPostgres(pg));

    it('happy: clean schema after migrations → 0 violations', async () => {
      const violations = await runAudit(pg.db);
      expect(violations).toEqual([]);
    });

    it('sad: a fixture-violating child table is detected, then cleaned up', async () => {
      await pg.db.withoutTenant('install fixture violation', async (tx) => {
        await tx.execute(sql`
        CREATE TABLE audit_fks_violation_fixture (
          id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
          tenant_id uuid NOT NULL REFERENCES tenants(id),
          brand_id uuid NOT NULL REFERENCES brands(id)
        )
      `);
      });

      try {
        const violations = await runAudit(pg.db);
        expect(violations).toContainEqual(
          expect.objectContaining({
            childTable: 'audit_fks_violation_fixture',
            childCol: 'brand_id',
            parentTable: 'brands',
          }),
        );
      } finally {
        await pg.db.withoutTenant('drop fixture', async (tx) => {
          await tx.execute(
            sql`DROP TABLE IF EXISTS audit_fks_violation_fixture`,
          );
        });
      }
    });
  },
);
```

The `try/finally` ensures the fixture table is dropped even on assertion failure — important because `singleFork: true` shares state across specs in the same vitest run.
